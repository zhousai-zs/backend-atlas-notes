# 第 150/208 课：Metrics 与指标基数

> 序号 150/208 · id `j-metrics` · 领域 J · 阶段 3 · 难度 进阶 · 子类 可观测性
> 前置：[`j-logging`](https://zhousai-zs.github.io/backend-atlas-notes/lessons/149.html)
> 节点摘要：Counter、Gauge 和 Histogram 表达不同观测语义；标签组合决定时间序列数量与存储成本。

## 导读

上一课用结构化日志记录单次 KV 请求。日志适合追查一条请求，指标则把多次请求压成可比较的计数、瞬时状态和延迟分布。字段选错会让错误率失真；标签选错会让时间序列数量失控。

教学假设：同一教学 KV 接口按区间暴露请求计数、延迟桶和在途请求数。以下指标名称、标签和分位数算法均为教学设计，不代表腾讯或微信内部实现。本课没有运行 Prometheus 服务器，也没有抓取真实生产流量。

## 学习目标

1. 解释速率与重置及适用边界
2. 独立完成实践：暴露请求计数、延迟桶和在途数，不把 user_id 作为标签。

## 为什么后端要懂

节点给出的理由是「监控服务健康与尾部体验。」健康要看区间内的失败比例是否在变化；尾部体验要看延迟分布，而不是只看平均值。把这两类问题混用同一种度量，容易得出无法复现的结论。

## 核心知识点

### 1. 速率与重置

**原理。** Prometheus 的 Instrumentation 指南写明：计数器只能上升（并在进程重启等情况下重置），适合累计事件次数或每次事件的量，例如 HTTP 请求总数；原始计数器很少直接有用，应使用 `rate()` 得到每秒增速。Gauge 可以上升或下降，适合快照，例如在途请求；指南明确不应对该类指标使用 `rate()`。

**直觉。** 计数器回答「从起点以来发生了多少次」；要回答「这一段时间有多快」，需要两个时间点之间的增量，并接受进程重启造成的重置。把瞬时在途数当成速率，会把涨跌都误读成吞吐。

**实践对照。** 第一区间累计 `http_requests_total{status="ok"}` 为 80、`status="error"` 为 20，错误率 0.2；第二区间另计 10 次成功与 10 次失败，错误率 0.5。这是用窗口内增量直接相除的教学计算，不是 Prometheus 服务器上的 `rate()` 查询，也没有模拟计数器重置。区间边界变化时，同一个计数器会给出不同错误率，因此必须先说明窗口。

### 2. 直方图桶

**原理。** 直方图把观测值放入预先声明的桶，并保留总和与次数。指南把 summary 与 histogram 列为更复杂的类型，并指向单独章节；本页没有展开分位数聚合公式。本课只实现教学用累积桶。

**直觉。** 桶回答「有多少请求不超过 10 毫秒、不超过 50 毫秒」，而不是先给一个虚假的精确 p99。桶边界是设计选择：过稀会看不清尾部，过密会增加序列数。

**实践对照。** 100 次教学请求中，77 次延迟 8 毫秒、20 次 40 毫秒、3 次 120 毫秒。暴露文本中 `le="10"` 为 77，`le="50"` 为 97，`le="+Inf"` 与 `_count` 为 100，`_sum` 为 1776.0。这些数字来自本课寄存器，不是线上抓取。

### 3. 标签基数

**原理。** 指南的 “Do not overuse labels” 指出，每一个标签组合都是额外的时间序列，会占用内存、CPU、磁盘和网络。它给出的一般建议是把指标基数保持在 10 以下；超过该值时也应限制在整个系统中的少数指标；绝大多数指标不应带标签。基数超过 100 或可能增长到该量级时，应减少维度，或把分析移出监控系统。

**直觉。** `status` 和 `route` 的取值通常有限；`user_id` 或 `request_id` 会随请求增加，序列数近似于用户数或请求数。

**实践对照。** 教学寄存器拒绝 `user_id` 标签。若为 100 次请求各建一条 `request_id` 序列，将得到 100 条；本次安全标签组合为 4。4 与 100 都只描述本课数据集，不是对指南中「10」「100」阈值的重复测量。

## 常见误区

1. **对每个请求 ID 建立时间序列。** 节点原句即此。请求 ID 几乎永不重复，序列数会随流量线性增长，监控系统会把预算消耗在几乎无法聚合的曲线上。需要追查单次请求时，应使用上一课的日志和下一课的 trace_id，而不是指标标签。
2. **把两个实例各自报告的 p99 平均后，当成整体 p99。** 见下面的实践对照。客户端分位数是在本机样本上先压缩后的结果，平均值不能还原联合分布。

## 设计权衡

节点原句是「精细标签提升定位能力，也可能使监控失控。」为 `status` 和 `route` 保留标签，可以直接算出某条路由的错误率；若再加上用户、实例、版本、机房的任意组合，序列数会相乘。本课选择拒绝无界标识，并接受因此无法按用户画指标曲线的限制。

## 动手实践

实践目录为 `practice150/`，需要 Python 3。本次使用 CPython 3.13.5。程序是教学用指标寄存器，不要把它说成正在运行的 Prometheus 或 C++ 服务。

```bash
cd practice150
bash test.sh
cat results.json
cat reports/metrics.txt
```

脚本在一个区间写入计数器、直方图和在途 Gauge，计算两个区间的错误率，拒绝 `user_id` 标签，并用两组教学样本比较「实例 p99 的平均」与「合并后再取 p99」。日志保存到 `run.log`，成功最后一行为 `ALL_CHECKS_PASSED`。

本次官方实践目录的结果：区间 1 错误率 0.2（80/20），区间 2 错误率 0.5（10/10）；在途数结束为 0；安全序列 4，若按请求 ID 标签则为 100；`user_id` 被拒绝。教学分位数采用索引 `ceil(q/100*(n-1))`：实例 A 的 99 个 10 与 1 个 1000，p99 为 1000；实例 B 的 100 个 100，p99 为 100；二者平均为 550；200 个样本合并后再取 p99 为 100。该算法是教学约定，用于说明「先取分位数再平均」与「先合并再取分位数」不是一回事，不是 Prometheus 的分位数实现，也不能外推到其他样本。

两项验收是「计算区间错误率」以及「说明客户端分位数为何难以跨实例聚合」。前者对应上述两个窗口的 0.2 与 0.5；后者对应 550 与 100 的差异：每个实例先把分布压成一个百分位数字，这些数字无法用算术平均恢复联合分布。官方 Instrumentation 页讨论了计数器、Gauge 和标签基数，直方图与 summary 的详细聚合指向其他章节；本课不把该页未给出的公式写成官方结论。

## 自测题

1. **为什么原始计数器很少直接用来做告警？** 它会持续累积，也包含重启前的历史；区间速率或窗口增量才能说明「最近是否变坏」。
2. **为什么不能对在途请求数使用 `rate()`？** 指南写明 Gauge 可升可降，对其取 `rate()` 没有计数器那种单调含义。在途数应看作快照。
3. **为什么两个实例的 p99 平均不是集群 p99？** 分位数发生在各实例内部，平均这些摘要会丢失联合分布。本课样本中平均得到 550，合并后是 100。

## 本课小结

用计数器的窗口增量计算错误率，用直方图观察延迟分布，用 Gauge 观察在途数；标签只保留有界维度，避免 user_id 或请求 ID 放大基数。客户端分位数要在原始样本或直方图桶上聚合，而不是平均各实例已经压缩的 p99。下一课是第 151 课 j-tracing（Tracing 与上下文传播）。
