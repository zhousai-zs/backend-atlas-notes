## 导读

上一课用单元测试保护模块的可观察行为，也用依赖替身控制边界。本课把测试边界扩大到真实子进程：客户端发出请求，服务监听端口、写入文件，再停止并启动，客户端能否读回先前的数据？单个函数正确，并不能保证这些环节接在一起仍然正确。

教学假设：一个内容后台或配置中心需要暂存配置与会话状态。实践用 Python 小型 KV 服务模拟这一需求，协议是为实验设计的，不代表腾讯或微信的内部协议、接口或实现。每条 TCP 连接发送一行 JSON；`SET` 写入，`GET` 读取，另外两种操作只用于触发受控故障。

## 学习目标

1. 解释测试环境隔离及适用边界。
2. 独立完成实践：启动 KV 子进程测试请求后重启恢复，自动回收临时文件和端口。
3. 用可控故障验证超时、恢复与清理，并判断重试是否掩盖了缺陷。

## 为什么后端要懂

节点给出的理由是「发现单元测试无法覆盖的系统边界错误」。一个独立测试可能证明字典可以存取值，另一个测试可能证明 JSON 可以编解码；只有把进程、套接字和文件接起来，才能检查服务启动时是否真的加载了上次写入的文件。集成测试的断言仍然应当落在可观察行为上：请求得到什么响应、重启后读到什么，以及退出后资源是否可用。

## 核心知识点

### 1. 测试环境隔离

**直觉。** 每个用例都有自己的一份数据和一个服务。某个用例写入的键不应成为另一个用例的初始条件；执行顺序也不应决定它能否通过。

**原理。** 本课 `kv` 是默认函数作用域 fixture，每次构造新的临时目录和服务子进程。服务自己绑定回环地址的动态端口，并把实际端口写到标准输出；测试读取这个端口后再连接。这样不必先挑选空端口、关闭套接字，再让服务绑定，避免两次操作之间的端口竞争。重启使用同一数据目录，但让新进程重新获取端口。

```python
@pytest.fixture
def kv():
    instance = KV()
    try:
        yield instance
    finally:
        pid, port, directory = instance.proc.pid, instance.port, instance.directory
        existed = directory.exists()
        instance.stop()
        shutil.rmtree(directory)
```

这里摘录了 fixture 的主要生命周期；完整代码还向外部审计文件记录清理信息。构造失败时 `KV.__init__` 也会停止已启动的进程并删除目录，因为尚未执行到 `yield` 时，不能依赖其后的拆卸代码。

对照用例将一个文件放进模块作用域的共享目录：写入者先运行时，读取者误以为初始目录必定为空而失败；顺序反过来则通过。本次 `bash test.sh` 记录：

```text
1 failed, 1 passed in 0.01s
shared_writer_then_reader: exit=1 elapsed=0.160s
2 passed in 0.01s
shared_reader_then_writer: exit=0 elapsed=0.184s
2 passed in 0.05s
isolated_reverse: exit=0 elapsed=0.212s
```

主套件按写入、读取的顺序运行隔离用例并通过；`isolated_reverse` 再按相反顺序运行相同的两个用例。对照表明这组共享状态用例有顺序依赖，两种顺序下的隔离版本均通过；它不证明所有并发或所有执行顺序都安全。

**适用边界。** 独立目录和动态端口隔离的是本实验管理的数据与监听资源。它们不能自动隔离外部数据库、全局环境变量或其他测试共用的远程服务；引入这些依赖时还要设计各自的隔离和回收方式。

### 2. 确定性故障注入

**直觉。** 想测试恢复，不必等待线上恰好断线。测试应能指定故障发生的位置，再验证客户端和服务的下一步行为。

**原理。** 服务的 `HANG` 指令接收请求后暂不回复，客户端设置较短的 socket 超时；`CRASH` 指令让服务进程在收到请求后立即退出。测试先写入会话值，再发送 `CRASH`，观察连接关闭，等待进程退出，使用同一目录拉起新进程并读取原值。恢复断言检查的是持久化后的外部结果，而非只检查进程启动成功。

```python
def test_crash_and_recover(kv):
    kv.request('SET', key='session', value='alive')
    with pytest.raises(ConnectionError):
        kv.request('CRASH')
    assert kv.proc.wait(timeout=2) == 23
    kv.stop()
    kv.start()
    assert kv.request('GET', key='session') == {'value': 'alive'}
```

`SET` 返回后才发送 `CRASH`，因此这验证的是已确认写入之后的进程退出与重启，不覆盖写文件中途崩溃、断电或文件系统损坏。本实验没有对文件做 `fsync`，不能把结果解释成断电持久性的保证。

运行日志明确记录注入参数和主套件结果：

```text
client timeout=0.05s; injected HANG=0.3s
5 passed in 0.24s
main: exit=0 elapsed=0.398s
```

超时之后测试停止仍在处理 `HANG` 的单线程服务，重新启动，再建立新连接并成功读取缺失键。它验证受控超时与重启后的重新连接，不是在证明生产客户端具备自动重试策略。

**适用边界。** 显式测试指令使故障位置可重复，适合检查指定分支；真实网络故障还有分片、丢包与资源竞争等情况，需要其他层次的测试。本例故障指令只用于教学服务，不应暴露给真实用户。

### 3. 超时与清理

**直觉。** 服务无响应时，测试必须在可控时间内失败；断言失败后，也不能留下服务占用端口和磁盘。

**原理。** 客户端给连接和读取设置超时；启动服务等待端口输出、等待进程退出也各有上限。fixture 在 `yield` 后的 `finally` 中停止子进程、等待回收并删除目录；若正常终止超过上限，则强制结束。监听套接字由进程退出关闭。与简单地发出终止信号相比，等待进程被回收并检查端口可重新绑定，提供了更具体的证据。

执行 `python3 -m pytest -q -p no:cacheprovider contrast.py::test_intentional_failure` 会故意在写入后断言失败；`test.sh` 让它在单独的 pytest 进程里运行，再从外部核查拆卸记录：

```text
1 failed in 0.03s
intentional_failure: exit=1 elapsed=0.182s
cleanup: pid=1212379 pid_gone=True port=43169 port_free=True dir_existed=True dir_gone=True
```

`pid_gone` 通过进程号探测，`port_free` 通过重新绑定该回环地址与端口检查；目录在拆卸前存在、拆卸后不存在。进程号与端口由本次运行动态产生，复跑时会变化。这个对照对应验收「失败测试不泄漏子进程」，也检查了端口与目录；它证明的是该次受控断言失败的清理结果，不是对机器突然断电的保证。

## 常见误区

1. **共享测试数据导致偶发失败。** 本课共享文件对照中，先写后读失败，先读后写通过；变化来自顺序而非业务功能的修复。把文件路径改成函数作用域的独立目录，并验证两种顺序，才能消除这组用例的污染。
2. **只断言重启进程活着。** 新进程可能成功监听，却忘记加载旧文件。必须写入已知值、停止并重启，再读取并比较该值；本课稳定缺陷对照正是让加载步骤失效。
3. **把重试成功当成缺陷已修复。** 顺序污染可能在另一次运行中暂时消失，稳定的恢复缺陷却会反复出现。记录每次结果，定位原因，再决定是否允许针对可恢复故障重试。
4. **只在成功路径清理。** 断言一旦抛出异常，测试体后面的手写清理可能不会执行。用 fixture 管理生命周期，并单独运行故意失败的用例检查拆卸效果；启动阶段失败也要自行回收已经取得的资源。

## 设计权衡

节点给出的权衡是「真实集成提高覆盖面，但执行成本更高。」本次主套件启动真实 Python 子进程、连接 TCP 并读写文件，pytest 报告 `5 passed in 0.24s`，外层进程计时为 `0.398s`；共享文件反例不启动 KV 服务，其一次 pytest 报告为 `1 failed, 1 passed in 0.01s`。两者用例和工作量不同，不能把差值当作精确的单次进程成本，但可以看到本实验包含额外的启动与系统资源操作。

集成测试适合保护协议、重启和资源边界；大量输入组合仍可在更快的单元测试中覆盖。真实依赖增加覆盖面的同时，也引入调度、端口和清理的复杂性，因此要明确超时与隔离边界。

## 动手实践

实践包位于 `practice146/`。需要 Python 3 和已安装的 pytest；运行入口优先使用 `python3 -m pytest`，不需要编译器。可以复制到新的临时目录后独立执行：

```bash
tmp_dir=$(mktemp -d)
cp -a practice146 "$tmp_dir/"
cd "$tmp_dir/practice146"
bash test.sh
```

脚本将完整输出写入 `run.log`，同时生成 `results.json`。退出前的最后一行应为 `ALL_CHECKS_PASSED`；日志中的故意失败属于受到检查的对照，不代表脚本整体失败。

1. **请求与恢复。** 主套件的 `test_restart_recovers` 发送 `SET theme=dark`，随后 `GET`，停止服务后用同一目录启动新子进程，再次 `GET` 并断言值仍为 `dark`。本次主套件 `5 passed in 0.24s`，退出码为 `0`。
2. **故障分支。** `HANG` 让读取在 `0.05s` 客户端超时后结束，重启后可重新连接；`CRASH` 让子进程以 `23` 退出，重新启动后仍读到已写入的会话值。主套件同时覆盖正常重启、超时恢复和崩溃恢复。
3. **失败测试不泄漏子进程。** 故意失败用例退出码为 `1`，外部审计显示 `pid_gone=True`、`port_free=True`、`dir_existed=True`、`dir_gone=True`。脚本要求这些条件全部成立，否则不会输出成功标记。
4. **重试不会掩盖稳定缺陷。** `--buggy` 让新进程忽略已有数据文件。驱动独立运行同一恢复断言三次，实际响应都是 `{'value': None}`，期望是 `{'value': 'dark'}`；三次退出码均为 `1`。这不是自动修复：脚本把每次预期失败作为对照检查，整体成功标记表示对照结果符合预期。
5. **共享数据对照。** 写入者在前时读取者失败，读取者在前时通过；函数作用域隔离的对应两个用例在两种顺序下均通过。这里展示的是顺序触发的偶发性，不能推断所有重试都会改变顺序。

`results.json` 保存每项外层退出码和耗时，以及失败清理的进程号、端口和检查结果；pytest 自身的摘要保留在 `run.log`。外层耗时包含 pytest 启动，不能与 pytest 摘要的测试耗时混为一谈。

阅读时沿着以下问题对照代码：

- **作用域。** 文档列出 function、class、module、package、session 等作用域；默认 function 在每个测试后销毁。作用域决定 fixture 实例何时复用，不会自动隔离 fixture 指向的外部共享资源。
- **setup / teardown。** yield fixture 在 `yield` 前准备资源、返回值给测试，在之后执行拆卸；测试体失败也会进入已成功 yield 的 fixture 拆卸。若某 fixture 在 yield 之前失败，不能指望其 yield 后代码执行，已成功完成的其他 fixture 仍会拆卸。
- **临时目录。** 临时目录文档说明 `tmp_path` 为每个测试提供独立路径，`tmp_path_factory` 为会话作用域的目录工厂；本课共享对照使用 `tmp_path_factory` 创建模块共享目录，而实际 KV fixture 用标准库 `tempfile.mkdtemp` 创建目录并显式删除，便于失败对照在测试进程外直接核查。pytest 的临时路径管理和本课手工立即删除不是同一机制。
- **资源清理。** 文档的安全拆卸讨论建议把状态改变与对应清理设计成可控单元，并注意 setup 阶段抛异常；本课在构造失败时额外处理子进程与目录，正常路径在 `finally` 中拆卸。

与本课实验的差异：Fixtures 页面用一般 fixture、资源管理和示例说明机制；临时目录页面展示内置路径 fixture 和工厂，而本课额外直接核查手工目录被删除。两页均不规定本课的 JSON 协议、`HANG` / `CRASH` 指令、重启恢复断言或外部进程与端口审计；这些是针对本节点目标增加的实验。文档说明 fixture 生命周期，本课另外实际检查该次失败后操作系统资源是否回收。

## 自测题

**1. 使用函数作用域 fixture，为什么仍可能出现共享数据污染？**

答：fixture 每次重新调用，不代表它引用的外部文件或服务也自动变成独立实例。若每次都连接同一个服务或打开同一个文件，状态仍然共享。本课为每个 KV fixture 创建目录并启动独立服务；共享文件对照则故意复用同一路径。

**2. 为什么先收到 SET 响应、再让服务崩溃并重启，仍不能证明断电持久性？**

答：这只测试该实验中已返回的写入在进程退出后能否被新进程读取。文件系统缓存可能尚未持久落盘，实验没有调用 `fsync`，也没有模拟写入中途崩溃或断电。

**3. 稳定缺陷连续失败三次，脚本为何仍能输出成功标记？**

答：每次失败是有缺陷恢复逻辑的预期对照，驱动检查每次退出码都为失败；主套件和清理检查也必须通过。成功标记表示检查机制观察到了预期结果，并不表示有缺陷的服务恢复正确。

## 本课小结

集成测试把模块接到真实进程、端口和持久化文件上，检查正常请求与重启恢复。函数作用域 fixture、动态端口和独立目录消除本课展示的共享状态依赖；受控超时与进程退出使恢复分支可重复。失败用例之后还要检查进程、端口和目录，连续重试也不能代替修复稳定缺陷。下一课是第 147 课 j-sanitizer（Sanitizer 动态检测）。
