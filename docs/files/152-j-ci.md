# 第 152/208 课：CI 与供应链检查

> 序号 152/208 · id `j-ci` · 领域 J · 阶段 3 · 难度 进阶 · 子类 构建与变更管理
> 前置：[`j-integration`](https://zhousai-zs.github.io/backend-atlas-notes/lessons/146.html) 和 [`j-sanitizer`](https://zhousai-zs.github.io/backend-atlas-notes/lessons/147.html)
> 节点摘要：CI 把干净构建、测试、依赖审查和产物记录自动化，使变更可重复验证。流水线需要能追溯代码版本、工具链、依赖和最终产物，避免环境偶然性。

## 导读

前面几课分别处理测试隔离、Sanitizer、崩溃现场和可观测性。这些检查如果只在某台已经装好工具的机器上偶然通过，换一台环境仍可能失败。持续集成的作用是在可复述的工具链上自动构建和测试，并把失败日志留下来，让有问题的变更不能被当成已验证。

教学假设：教学用 C++ 缓存组件进入一条本地流水线，固定模式会计算字符串字节和，故障模式在释放后继续读取。以下仓库布局、工作流文件和缺陷均为教学设计，不代表腾讯或微信内部实现。本次没有在 GitHub 托管的 runner 上执行工作流。

## 学习目标

1. 解释锁定依赖及适用边界
2. 独立完成实践：建立 GCC/Clang 构建及 ASan 测试流水线，保存失败日志。

## 为什么后端要懂

节点给出的理由是「减少本地可用而交付失败的问题。」本地通过可能依赖已经装过的库、缓存或不记版本的编译器。把工具链版本、编译标志和失败输出记录下来，才能判断一次通过是否可以在干净环境里重复。

## 核心知识点

### 1. 锁定依赖

**原理。** 锁定依赖是指构建只使用事先写下的工具和库版本，而不是在流水线里执行「安装最新编译器」这类不可复述的步骤。适用边界是：锁文件只能覆盖已经写入并校验过的部分；未锁定的系统库、缓存目录或临时下载仍然可能改变结果。

**直觉。** 版本范围写成「最新」时，今天和一周后安装到的工具可能不同，失败也无法用同一组版本重放。

**实践对照。** `lock/versions.txt` 固定 `ziglang==0.17.1`、Python 3.13.5、目标 `x86_64-linux-gnu` 以及编译标志 `-std=c++17 -g -O1 -fno-omit-frame-pointer`。本次流水线记录的时间为 2026-11-15 22:46:30 CST（北京时间），`zig c++` 报告 `clang version 22.1.8`，并写入源文件与脚本的 SHA-256。流水线没有从网络安装编译器。本机没有系统 `g++` 或 `clang++`，Clang 作业使用实践包内的 `tools/zig-c++` 包装器。

### 2. 构建矩阵

**原理。** 矩阵列出计划验证的编译器与检查组合，但只能声明实际跑到的格子。GitHub Actions 文档把工作流定义为由事件触发、包含一个或多个作业的自动化过程；作业在 runner 上执行若干步骤。全面的矩阵会增加时间和机器成本。

**直觉。** 把没有安装的编译器标记为通过，会制造「GCC 也验证过了」的假象。

**实践对照。** 本次作业结果为：`clang_test pass`，`clang_asan_fixed pass`，`clang_asan_broken_detected pass`，`gcc_test unavailable`。机器上没有 `g++`，该格被明确记为不可用，而不是通过。教学文件 `ci/ci.yml` 描述了与本地作业对应的工作流结构，但本文不声称它已在 GitHub 托管 runner 上执行。

### 3. 产物与来源记录

**原理。** 一次构建要能回答：哪份源码、哪条工具链、哪些标志、得到什么结果。失败时还要留下日志，否则「检查没通过」无法复盘。

**直觉。** 只有退出码、没有报告，就像只知道程序崩溃却没有 core。

**实践对照。** `reports/toolchain.txt` 记录日期、Python、ziglang 版本、编译器输出、目标、ASan 运行时路径 `/usr/lib/x86_64-linux-gnu/libasan.so.8` 以及源文件摘要。故障模式的 ASan 日志复制到 `reports/failures/asan-broken.txt`。该日志报告 `AddressSanitizer: heap-use-after-free`，读取发生在 `src/cache.cpp:29` 的 `cache_sum`，释放位于第 26 行，先前分配位于 `cache_set` 第 18 行。修复模式在同一标志下输出 `sum=1010 len=10`，且没有 ASan 错误。地址、进程号和 Build ID 依赖本次运行，读者应以自己的失败日志为准。

## 常见误区

1. **用不可固定版本的安装脚本构建。** 节点原句即此。若流水线每次都执行未钉版本的安装命令，工具链记录会与实际执行不一致，失败难以在一周后用同一组版本复现。
2. **把「本机已有的编译器」写进矩阵却不检查是否存在。** 本课在没有 `g++` 时记录 `unavailable`。若把该格改成通过，验收「失败检查能阻止错误合并」也会被削弱，因为矩阵本身已经不再诚实。

## 设计权衡

节点原句是「矩阵越全面成本越高，需选择真实支持范围。」同时验证多种编译器、优化级别和 Sanitizer 能扩大信心，但每多一个格子就多一次编译与一次日志存储。本次只实际运行了 Clang（经由 zig c++）的普通测试和 ASan；GCC 格子保留为不可用。这是在本环境上的真实范围，不是对 GCC 正确性的判断。

## 动手实践

实践目录为 `practice152/`，需要 Python 3 以及可调用的 C++ 编译器。脚本先查找系统 `clang++` 或 `g++`，否则使用 `tools/zig-c++`。本次 Zig 目标为 `x86_64-linux-gnu`，并链接系统 `libasan.so.8`。没有这些条件时，脚本应明确失败，而不是跳过 ASan 还报告通过。

```bash
cd practice152
bash test.sh
cat results.json
cat reports/toolchain.txt
cat reports/jobs.txt
cat reports/failures/asan-broken.txt
cat reports/fresh-gate.txt
```

`test.sh` 先在本目录运行 `ci/pipeline.sh`：锁定工具链记录、固定源码的 Clang 测试和 ASan 必须通过，故障模式必须被 ASan 抓住并保存日志，GCC 缺失时记为不可用。随后用「故障模式未通过 ASan」演示合并门禁拒绝。最后把源码、锁文件和脚本复制到全新临时目录再跑一遍流水线。日志保存到 `run.log`，成功最后一行为 `ALL_CHECKS_PASSED`。`build/` 中的二进制不应放入对外分发的实践包。

本次官方实践目录的作业状态见上；合并故障变更为 `blocked: required asan check failed on broken change`；全新目录的门禁文件为 `MERGE_ALLOWED_FOR_FIXED_TREE`。工具链记录时间为 2026-11-15 22:46:30 CST（北京时间）。

两项验收是「全新环境通过」以及「失败检查能阻止错误合并」。前者对应干净目录中固定源码流水线再次通过；后者对应故障模式的 ASan 日志被保存，并且门禁把该变更标记为阻止。本课的「全新环境」是新的临时目录和同样的锁定工具链，不是重新安装操作系统，也不是 GitHub 托管的干净虚拟机。

## 自测题

1. **锁文件写下版本后，是否还需要记录实际编译器输出？** 需要。锁文件是计划使用的版本，编译器 `--version` 和源文件摘要证明这次运行真正用到了什么。
2. **GCC 格子为 unavailable，能否算矩阵已经覆盖 GCC？** 不能。该格只说明本环境没有 `g++`，不能解释成 GCC 构建已通过或已失败。
3. **为什么要把 ASan 失败日志单独保存？** 门禁只能给出阻止或允许；没有日志就无法确认失败是教学中的堆释放后使用，还是环境缺失。验收要求失败检查能阻止错误合并，也要求这份证据可复查。
