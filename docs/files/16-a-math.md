## 1. 学习目标与为什么后端要懂

### 1.1 学习目标

完成本课后，你应该能够：

1. **解释期望与分位数**：说清「均值」描述什么、不描述什么；中位数、p95、p99 如何刻画尾部体验。
2. **警惕独立性假设与样本偏差**：知道「两段延迟各自 p99 相加 ≠ 端到端 p99」；小样本下的 p99 极不稳定，必须报告样本数量。
3. **做带宽 / 吞吐 / 并发的数量级估算**：会用 Little's Law 与「单位写清」的容量估算，快速判断量级是否离谱。
4. **独立完成节点实践**：生成长尾延迟样本，比较均值、中位数与 p99，并估算日志存储量（明确单位与假设）。
5. 在微信公众号后台场景里，能把「回调延迟、模板消息发送、日志落盘」用分位数与估算说话，而不是只甩一个平均值。

### 1.2 验收标准

节点给出的验收标准有两条，本课会反复回扣：

- **能解释分位数不能直接相加。** 网关 p99=50ms、业务 p99=80ms，端到端 p99 **不是** 130ms——相关性、共享队列、重试会让尾部叠在一起或分散，必须对**整条链路的样本**再算分位数（见实践演示）。
- **容量估算明确单位与假设。** 「一天多少 TB 日志」必须写出：QPS、平均每条字节数、保留天数、压缩比（若有）等假设，否则数字无法复核。

### 1.3 为什么微信公众号后台要懂概率与估算

节点对「为什么」写得很干脆：**避免仅凭平均值判断服务质量。** 放到即将入职的腾讯微信公众号后台：

- **回调 / 被动回复延迟。** 微信侧对回调有超时；均值 20ms 看起来很美，但若 p99 已经 800ms，大量用户会偶发失败或重试风暴——**用户感知的是尾部，不是均值**。
- **模板消息 / 群发推送。** 高峰 QPS、下游限流、队列积压：需要用吞吐与并发估算「要不要扩容」，而不是拍脑袋。
- **日志与审计存储。** 每个请求记 access log + 业务日志；按「平均 2KB × QPS × 86400 × 保留天数」估容量，决定落盘策略、采样率、冷热分层。
- **压测与容量规划。** 估算帮你选方向（该不该上缓存、该不该异步）；**不能替代真实压测**（节点 tradeoffs）。

所以本课要建立的肌肉是：**用分位数描述服务质量；用带单位的估算建立可检验假设；报告样本数；估算之后再用实验验证。**

## 2. 从直觉到原理：三个核心要点

### 2.1 期望与分位数

#### 直觉：班级平均分 vs「最差 1% 同学考几分」

- **期望（均值）**：所有样本的算术平均，对「总量 / 成本」友好（总流量、总账单），但对「单次体验」不敏感——一个 10s 的慢请求会被九千九百个 10ms 请求稀释。
- **中位数（p50）**：一半请求比它快、一半比它慢——「典型用户」感受。
- **p99**：大约 99% 的请求 ≤ 该值；剩下 1% 更慢——这才是 SLA、超时、重试预算要盯的地方。

长尾分布下常见现象：**均值 > 中位数**，且 **p99 ≫ 均值**。只看均值会系统性低估坏体验。

#### 原理：分位数是顺序统计量

对样本 \(x_{(1)} \le x_{(2)} \le \cdots \le x_{(n)}\)，经验 p99 可取第 \(\lceil 0.99 \cdot n \rceil\) 个（实现细节会有多种插值法；实践里我们用确定性索引，并**始终报告 n**）。

```python
import statistics

def percentile(sorted_xs, p):
    """p in [0, 100]; sorted_xs 非空已排序。"""
    n = len(sorted_xs)
    if n == 0:
        raise ValueError("empty")
    # 向上取整索引，保证 p99 反映尾部（小样本时更「悲观」）
    idx = min(n - 1, max(0, (n * p + 99) // 100 - 1))  # 见实践精确实现
    return sorted_xs[idx]
```

（实践代码里会给出清晰、可测的实现；上面只建立「按排序位置取」的直觉。）

#### 例子：公众号回调延迟

假设 10000 次回调延迟（毫秒）来自「大多很快 + 偶发下游超时」的长尾：

| 指标 | 可能量级（示意） | 含义 |
|------|------------------|------|
| 均值 | ~35 ms | 总成本 / 平均负载 |
| 中位数 | ~18 ms | 一半用户更快 |
| p99 | ~400 ms | 约 1% 请求很慢，接近超时边界 |

**监控告警**：对延迟用 p99（或 p95）+ 错误率，而不是只告均值——这与 [Google SRE Book · Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/) 的主张一致。

### 2.2 独立性假设和样本偏差

#### 直觉：两段堵车时间不能「各自最坏再相加」当常态

你上班：地铁段「最倒霉 1%」多花 20 分钟，公交段「最倒霉 1%」多花 15 分钟——**同一天两段同时最倒霉**的概率通常远小于 1%，所以「端到端最倒霉 1%」往往 **小于** 20+15；但若两段共享同一场大雨（正相关），又可能接近相加甚至更糟。**没有独立性，就不能把分位数当线性运算。**

#### 原理

1. **分位数一般不可加。** 若 \(X,Y\) 独立同分布，\(p99(X+Y)\) 与 \(p99(X)+p99(Y)\) 通常不等；相关时更不可预测。正确做法：对 \(X+Y\) 的样本直接算 p99。
2. **独立性假设常被悄悄用错。** 「各服务 SLA 相加 = 端到端 SLA」是常见拍脑袋；重试、共享连接池、同一机房故障会引入相关。
3. **样本偏差。** 只在低峰采样、丢掉慢请求的客户端超时样本、用「成功请求」算延迟——都会让 p99 **看起来更好**。小样本时 p99 方差巨大：n=100 时「第 99 个」几乎是噪声。

#### 例子：串联延迟演示（实践会跑）

```text
网关耗时 G ~ 长尾，业务耗时 B ~ 长尾，端到端 E = G + B（同一次请求配对）
比较：percentile(G,99) + percentile(B,99)   vs   percentile(E,99)
```

你会看到两者经常差一截——这就是验收标准「分位数不能直接相加」的可操作证明。

```bash
# 快速感受：小样本 p99 跳变
python3 -c "
import random, statistics
random.seed(1)
for n in (50, 100, 1000, 10000):
    xs = sorted(random.lognormvariate(3, 0.8) for _ in range(n))
    p99 = xs[min(n-1, (99*n + 99)//100 - 1)]
    print(f'n={n:5d} mean={statistics.mean(xs):7.1f} p99={p99:7.1f}')
"
```

### 2.3 带宽、吞吐与并发数量级

#### 直觉：水管粗细、流速、管里有多少水

- **带宽（bandwidth）**：链路能承载的比特率，如 1 Gbps ≈ \(10^9/8\) ≈ 125 MB/s。
- **吞吐（throughput）**：系统实际完成的工作率，如 QPS、MB/s 写入。
- **并发（concurrency）**：同一时刻「在飞」的请求数。

**Little's Law（稳态）**：\(L = \lambda W\)  
平均并发 ≈ 到达率 × 平均停留时间。  
例：QPS=1000，平均延迟 50ms=0.05s → 平均约 50 个在途请求。用 **p99 延迟** 估「尾部并发压力」时要标明你用的是哪个延迟——这又是「单位与假设」。

#### 原理：数量级估算三步

1. **写清假设**：峰值 QPS、平均响应体大小、复制因子、保留天数、压缩比……
2. **统一单位**：B / KB / MB / GB；秒 / 天；bit vs byte（网络常说 Mbps，存储说 MB）。
3. **算完做 sanity check**：结果是 GB/天 还是 PB/天？差两个数量级就说明假设错了。

#### 例子：公众号 access 日志存储

假设（必须写进估算）：

| 假设项 | 取值 | 单位 |
|--------|------|------|
| 峰值折日均有效 QPS | 5000 | 请求/秒 |
| 平均每条日志 | 800 | 字节/条 |
| 每天秒数 | 86400 | 秒/天 |
| 保留 | 30 | 天 |
| 压缩比（可选） | 0.3 | 存盘体积/原始 |

原始日增量 ≈ \(5000 \times 800 \times 86400\) B/天  
≈ \(3.456 \times 10^{11}\) B/天 ≈ **322 GB/天**  
30 天原始 ≈ **9.5 TB**；若压缩到 0.3 → 约 **2.9 TB**。

```bash
python3 -c "
qps, bytes_per, days, compress = 5000, 800, 30, 0.3
raw = qps * bytes_per * 86400 * days
print(f'raw_bytes={raw:.3e} raw_TB={raw/1e12:.2f} compressed_TB={raw*compress/1e12:.2f}')
"
```

公众号后台扩容讨论时，把这张「假设表」贴出来，比甩一句「日志挺多的」有用得多。

## 3. 常见误区与设计权衡

### 3.1 误区：小样本 p99 非常不稳定，应报告样本数量

节点 pitfalls：**小样本p99非常不稳定，应报告样本数量。**

- n=100 时，经验 p99 本质上由最慢的几个点决定，换一天采样可以差一倍。
- 看板只写「p99=320ms」却不写窗口内请求数，无法判断可信度。
- 实践建议：监控面板同时展示 **样本数 / 请求量**；告警用足够长的滚动窗口或 Holistic 指标；压测报告写明 n。

### 3.2 权衡：估算帮助选方向，不能替代真实压测

节点 tradeoffs：**估算帮助选方向，不能替代真实压测。**

| | 背信封估算 | 真实压测 / 线上观测 |
|--|------------|---------------------|
| 速度 | 分钟级 | 小时～天 |
| 作用 | 排除荒谬方案、定数量级 | 暴露队列、锁、GC、热点 key |
| 风险 | 假设错则全盘错 | 成本高、可能伤生产 |

正确姿势：先估算建立**可检验假设**（「若 QPS=5k 且 800B/条，30 天约 X TB」）→ 再用压测或灰度数据推翻或确认。估算不是终点。

## 5. 自测题（附答案）

**Q1.** 为什么后端监控延迟时不能只看平均值？期望、中位数、p99 各适合回答什么问题？  
<details><summary>答案</summary>

平均值（期望）对总量/成本有用，但会被少量极慢请求或大量快请求稀释，掩盖尾部体验。中位数回答「典型请求多慢」；p99 回答「最差约 1% 有多慢」，更贴近超时、SLA 与用户偶发失败。长尾服务里常见 p99 ≫ 均值，只看均值会系统性乐观。

</details>

**Q2.** 为什么「分位数不能直接相加」？网关 p99 与业务 p99 相加能否当端到端 p99？正确做法是什么？  
<details><summary>答案</summary>

分位数不是线性算子：两段延迟同时落入各自最差 1% 的概率通常不是 1%，且请求间可能正相关（共享故障域）或负相关。因此网关 p99 + 业务 p99 一般 ≠ 端到端 p99。正确做法是对**同一次请求的端到端耗时样本**直接计算分位数，并报告样本数。

</details>

**Q3.** 节点 pitfalls 与 tradeoffs 各说了什么？估算日志存储量时必须写清哪些东西？  
<details><summary>答案</summary>

Pitfalls：小样本 p99 非常不稳定，应报告样本数量。Tradeoffs：估算帮助选方向，不能替代真实压测。估算日志时必须写清假设与单位：QPS（或日请求量）、平均每条字节数、保留天数、是否含副本/多机房、压缩比等，并给出结果单位（B/GB/TB），以便他人复核。

</details>
