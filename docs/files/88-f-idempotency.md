## 导读

### 两个直觉

电梯按钮按一次和按五次，电梯都只会来接你一趟——多按几次不会叫来五部电梯。这是“幂等”的直觉：重复动作不改变最终效果。

自动售货机则相反：投一次币按一次出货，投两次币按两次出货。它是“非幂等”的直觉：每按一次都产生新的效果，重复就重复扣费。

后端接口大多更像自动售货机：每来一次写请求就多做一次事。幂等键要做的，是把“创建类”接口在重复请求下表现得像电梯按钮——无论按几次，结果只发生一次。

### 接上一课

上一课讲重试：当结果未知时，客户端会再发一次，让请求“至少一次”到达服务端。这是可用性的必要手段，但代价是服务端可能收到同一请求的多份副本。

> 重试让请求“至少一次”到达；幂等让“多次到达 = 一次效果”。

所以重试和幂等是一对搭档：没有重试，系统在抖动时容易失败；没有幂等，重试会把失败放大成重复副作用。重试解决“能不能成功”，幂等解决“成功了几次”。

### 为什么要用“键”

幂等键（idempotency key）是客户端为“一次业务意图”生成并随请求发送的标识。它表达的是“这一次业务意图”，而不是“这一次网络传输”。

- 同一个业务意图因为超时被重发多次，应携带同一个键。
- 用户真正发起了两次不同的提交，应使用不同的键。

这也解释了为什么键通常由客户端生成：只有客户端知道当前这次是“重试”还是“新的提交”，服务端无法从重复的请求体里可靠地推断。

### 一条教学时间线（教学假设）

1. 客户端提交一个群发任务，请求里带上幂等键 `K1`。
2. 服务端处理成功，已经在数据库里创建了任务 `T1`，但响应在返回途中超时丢失。
3. 客户端只看到“超时”，不知道任务到底建没建，于是用同样的 `K1` 重试。
4. 如果服务端没有幂等处理：它会再建一个任务 `T2`，同一次提交变成两个群发任务。
5. 如果服务端正确处理幂等：它发现 `K1` 已经存在，直接返回首次的结果 `T1`，不再新建任务。

这条时间线贯穿全课：客户端永远无法凭“超时”判断服务端状态，只有服务端能把重复请求收敛成一次效果。注意第 2 步和第 3 步之间没有“坏掉的代码”，只是一个正常的超时，就足以制造重复。
### 错误与正确做法对照

| 场景 | 常见但错误的做法 | 后果 | 更稳妥的做法 |
| --- | --- | --- | --- |
| 超时后重试提交任务 | 每次请求都直接插入一条新任务 | 同一次提交生成多个任务，可能重复触达 | 客户端带幂等键，服务端按键去重并复用首次结果 |
| 先查键、再执行业务、最后写键 | 检查与写入分成多步，不在同一原子操作里 | 并发下两个请求都查不到键，都执行业务 | 用唯一约束或事务把“键 + 结果”原子保存 |
| 同一键第二次请求参数不同 | 不比对参数，直接当成新请求执行 | 语义冲突，结果不可预期 | 保存参数指纹，不一致时拒绝并返回明确错误 |
| 幂等键永久保留 | 所有键永不过期 | 存储无限增长，边界语义难维护 | 明确保留时长，并在接口文档中说明 |
| 只靠网关去重 | 认为“入口拦一下重复包”就够了 | 网关窗口很短，且无法理解业务结果 | 传输去重只是辅助，业务幂等仍要自己保证 |

这张表里的每一行，本质上都是把“检查”和“执行”拆开、或把“契约”留给运气。后面实验会专门验证其中最容易出错的两处：并发提交与崩溃恢复。

### 本课三条主线

1. **业务幂等与传输去重。** 传输层去重（例如网关根据请求头丢弃重复包）只能覆盖很短的时间窗口，也不理解业务结果；业务幂等要保证“业务结果只发生一次”。两者层次不同，不能互相替代。
2. **键作用域和参数指纹。** 幂等键不是全局唯一的魔法字符串，它必须有明确作用域（哪个用户、哪类接口、哪段时间）。同一键配不同参数时，要靠参数指纹识别冲突，而不是默默执行或默默覆盖。
3. **原子提交、TTL 与结果复用。** “键 + 业务结果”必须在一次原子提交中落库；键要定义保留多久；重复请求要能取回首次结果，而不是重新执行业务。

这三条主线对应节点要点，也对应实验的验收方向：同键并发只产生一个任务、同键不同参数被拒绝、崩溃恢复后重复请求仍按契约处理。学习时不要只记结论，要把“为什么必须是原子提交”讲清楚。

### 常见误解

- **“幂等就是加个 if 查一下键。”** 单线程下看似可行，但在并发和崩溃面前会暴露竞态窗口。
- **“同一个键永远有效。”** 键需要保留时长；无限保留既贵，也会让很久以后的重放行为变得难以解释。
- **“参数不同也没关系，键相同就复用结果。”** 这会把两次不同的业务意图错误地合并，必须比对参数指纹。
- **“做了传输层去重就不需要业务幂等。”** 传输层看不到业务是否已提交，也无法覆盖长时间跨度的重试。
- **“幂等只影响写接口。”** 计数的重复累加、任务的重复提交，都是写副作用，一样需要处理。

## 学习目标

学完本课，你应当能够：

1. 能解释业务幂等与传输去重的区别，以及为什么传输层去重不能替代业务幂等。
2. 能独立完成：实现创建任务接口，同一键并发提交只产生一个任务且返回同一结果。
3. 能说明幂等键的作用域应该怎样界定，并解释为什么作用域不清会带来误判。
4. 能为请求参数设计稳定的参数指纹，并说明“同键不同参数”时应如何拒绝。
5. 能描述“键 + 结果”原子提交的必要性，并识别“先查键、再执行、再记键”的竞态与崩溃窗口。
6. 能为幂等键设定合理的保留时长（TTL），并说明结果复用的边界。
7. 能根据接口文档说明幂等契约，而不是把幂等当成某个函数里的临时判断。
8. 能在崩溃恢复后验证重复请求仍按契约处理，而不是产生第二次副作用。
## 为什么后端要懂

> 节点原文：“处理支付、写入和任务提交的结果未知。”

“结果未知”不是一句抽象的话。一次请求从客户端发出到收到响应，中间要经过网络、网关、服务进程、数据库等多个环节，任何一个环节都可能让“结果”变得不可见。

对客户端来说，失败通常只有两种表现：

- 一直没有响应，最后超时；
- 收到错误，但这个错误无法说明业务到底执行没有。

而服务端的真实状态，至少有以下三种。

### 三种“结果未知”

1. **请求没到。**
   请求在网络中丢失，或还没进入服务端。
   服务端什么都没做，重试通常是安全的。

2. **到了，没执行完。**
   请求已经进入服务端，业务只完成了一部分，进程崩溃、超时或被中断。
   数据可能处于中间状态，重试可能补完，也可能重复。

3. **执行完，响应丢了。**
   业务已经成功提交，但响应在返回路上丢失。
   数据已经改了，客户端却以为失败，重试会再改一次。

| 服务端真实状态 | 客户端看到的现象 | 客户端能区分吗 |
| --- | --- | --- |
| 请求没到 | 超时 / 无响应 | 不能 |
| 到了没执行完 | 超时 / 错误 | 不能 |
| 执行完响应丢了 | 超时 / 无响应 | 不能 |

这张表的关键在最后一列：三种完全不同的真实状态，在客户端看来几乎一样。

### 为什么客户端只能重试

客户端不知道服务端发生了什么，只知道“这次没有拿到确定结果”。

- 不重试：如果是请求丢了，业务永远不成功；
- 重试：如果服务端其实已经成功，就会重复执行。

两害相权，大多数系统选择重试，因为“可能重复”至少比“确定失败”更有机会完成任务。于是，“结果未知”被转化成了“可能重复”。

### 重复的代价

不同场景下，重复的代价差别很大：

- **支付。** 重复执行可能重复扣款，直接涉及资金，通常不可接受。
- **写入。** 重复写入会造成数据重复、计数翻倍、状态被覆盖，事后修复成本高。
- **任务提交。** 一次提交变成两个任务，可能触发两次群发、两次推送，用户直接感知到重复。
- **素材与内容（教学假设）。** 同一张图片被重复上传、同一篇图文被重复创建，既浪费存储，也让后续统计失真。

在通用内容后台里，素材上传、图文发布、群发任务提交、计数更新往往都不是“重放一遍没关系”的纯查询（教学假设）。它们会留下副作用，而副作用一旦重复，就很难优雅地撤回。

### 重复不是异常，而是常态

更重要的是：重复请求本来就会不断出现，并不是“客户端不听话”的偶发事故。

- **消息队列重投。** 消费者处理完但确认丢失，消息会被再次投递。
- **网关或代理重试。** 上游超时后按策略重发，下游可能收到重复请求。
- **用户连点。** 页面卡顿时用户重复点击“提交”，浏览器可能发出多个请求。
- **定时任务补偿。** 补偿逻辑可能把已经成功的任务再提交一次。

这些机制的共同点是“至少一次”（at-least-once）语义：消息或请求至少到达一次，但可能到达多次。

> 在“至少一次”的投递世界里，服务端不能假设“每个请求只会来一次”。

既然重复必然存在，正确做法不是要求客户端永不重试，而是在服务端把重复收敛成一次效果。
### 幂等是接口契约，不是一个 if

很多人的第一反应是：在接口里加一句“如果键已存在就返回旧结果”。这通常不够，原因有三。

1. **契约要写清楚。**
   幂等键字段叫什么、作用域是什么、保留多久、同键不同参数怎么处理，这些都要在接口文档里说明，而不是藏在实现里。

2. **并发下要成立。**
   两个携带同一键的请求可能同时到达，简单的“先查再写”会让它们都查不到键，于是都执行。

3. **崩溃后要成立。**
   服务端可能在“业务已执行、键还没记录”的瞬间崩溃。如果两者不是原子保存，恢复后重复请求仍可能产生第二次副作用。

#### 契约至少要说明什么

一个可用的幂等契约，通常要交代以下内容：

- 键字段的名称和类型；
- 键由谁生成、建议格式；
- 键的作用域；
- 保留时长；
- 同键重复请求返回什么；
- 同键不同参数如何处理；
- 键过期后如何解释。

参考 Google AIP-155 的思路（以所读文档版本为准）：请求可带 `request_id` 字段（字符串，建议 UUID v4），服务端在一段时间内看到同一 `request_id` 时应返回与首次相同的响应而不重复执行；`request_id` 应在 API 文档中说明保留时长。它与 HTTP 的 `Idempotency-Key` 头思路相同（IETF 草案，以版本为准）。

#### 一个简单的判断方法

判断一个接口是否真正幂等，不要只看代码里有没有“查键”，而要问四个问题：

1. **同一键并发提交会怎样？** 两个请求同时到达，会不会都认为键不存在？
2. **执行到一半崩溃会怎样？** 业务已改、键未记，恢复后重放会不会再来一次？
3. **键过期后重放会怎样？** 过期边界是否在文档里说清楚，客户端是否知道？
4. **同键不同参数会怎样？** 是拒绝、报错，还是悄悄复用旧结果？

四个问题都能按文档回答，幂等才算真正落地。

#### 为什么这属于后端基本功

因为幂等的每一个关键点，都落在后端最熟悉的地方：

- 数据模型：键和业务结果放在哪里、如何建唯一约束；
- 事务与并发：如何把“检查 + 执行 + 记录”收敛成原子操作；
- 存储生命周期：TTL、归档、清理策略；
- 接口契约：文档、错误码、返回语义。

这些都是后端工程师每天要做的取舍，也是“能写接口”和“能写可靠接口”的分界线。幂等做得好，重试才是安全的；幂等没做好，重试越多，重复越多。

（再次说明：本课中的“公众号后台”“群发”“素材”“计数”等均为教学假设，仅用于说明通用后台场景，不涉及任何具体产品的内部实现；相关规范细节以所读文档版本为准。）

## 核心概念

幂等的目标不是“请求永不重复”，而是**重复执行产生受控的等价效果**：调用方在结果未知时可以重试，服务端不会把同一件事做成两件或多件。本课面向通用内容后台，下面涉及图文发布、素材上传、群发任务提交、计数等例子，均为教学假设，不代表任何具体产品的内部实现。

Google AIP-155（Request identification）公开要点是：请求可以携带 `request_id` 字段（字符串，建议 UUID v4）；服务端在一段时间内看到同一 `request_id` 时，应返回与首次相同的响应，而不是重复执行；`request_id` 的保留时长应写入 API 文档。它与 HTTP 的 `Idempotency-Key` 头（IETF 草案）思路相同。具体字段、错误码和保留期以所读文档版本及团队规范为准。

### 1. 业务幂等与传输去重

先明确两个层次。

- **传输去重**：解决“同一条报文在传输链路上出现多次”。典型机制包括 TCP 序号与重传、消息队列的 message id 去重、网关的 request id 映射。它的作用域是某条连接、某个队列或某个网关的去重窗口。
- **业务幂等**：解决“同一件业务动作被发起多次”。它由业务定义什么是“同一件事”，通常落在业务键或客户端生成的幂等键上，并把判定结果持久化。

传输去重只能挡住同一传输链路上的重复，挡不住用户换一条连接重试、上游系统重新发起、跨网关重放，或者进程崩溃后客户端再次提交。因此，**传输层去重不能替代业务幂等**；前者是优化和减噪，后者才是结果契约。

| 层次 | 判重依据 | 能挡住 | 挡不住 |
| --- | --- | --- | --- |
| TCP | 连接内的序号 | 链路层重传造成的重复字节 | 新连接上的业务重试 |
| 消息队列 | message id + 去重窗口 | 同一消息的重复投递 | 生产者重新构造消息再次发送 |
| 网关 | request id / trace id | 经过同一网关的重复转发 | 绕过网关的调用、跨网关重放 |
| 业务层 | 业务唯一键 / 幂等键 | 同一业务动作的重复提交 | 业务键本身设计错误导致的误合并 |

#### 天然幂等与非幂等

有些操作天然幂等，重复执行的结果与执行一次等价：

- `GET /tasks/{id}`：只读查询，不改变状态。
- `PUT /tasks/{id}` 整体覆盖：同一份表示覆盖多次，最终状态相同。
- `DELETE /tasks/{id}`：第一次删除成功，后续按“已不存在”处理，效果可控。
- 条件状态更新：`UPDATE tasks SET status='paid' WHERE id=? AND status='pending'`。只有第一次能把 `pending` 推到 `paid`，重复执行影响 0 行。

非幂等操作则会在每次执行时产生新效果：

- `INSERT` 一条新任务：执行两次就有两条任务。
- `count = count + 1`：执行两次计数加 2。
- 扣款、发券、发送通知：执行两次就是两笔资金或两次触达。
- 追加日志或追加消息：每次都会多一条记录。

设计新接口时，优先问一句：能不能把它改造成天然幂等？例如把“创建任务”改成“以业务单号 upsert 任务”，把“设置状态”改成带前置状态的条件更新。改造不了，再引入幂等键。

#### 三种常用实现手段

1. **天然幂等设计**：用 `PUT`、按业务主键 upsert、条件更新表达语义，让重复请求落到同一行或影响 0 行。
2. **唯一约束**：给业务唯一键加数据库唯一索引，让重复插入在数据库层失败或变成无操作。这是最后一道兜底，成本低、可靠性高。
3. **幂等键表**：客户端为一次逻辑操作生成 key，服务端持久化 key、参数指纹、处理状态和首次响应；重复请求复用结果。它适合“创建类”接口，尤其是任务提交这类不能靠业务自然键完全表达的操作。

唯一约束的两种常见写法如下。MySQL 风格（`biz_no` 是业务唯一号）：

```sql
CREATE TABLE tasks (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  tenant_id BIGINT NOT NULL,
  biz_no VARCHAR(64) NOT NULL,
  payload JSON NOT NULL,
  UNIQUE KEY uk_tasks_tenant_biz (tenant_id, biz_no)
);

INSERT INTO tasks (tenant_id, biz_no, payload)
VALUES (?, ?, ?)
ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(id);
```

PostgreSQL 风格：

```sql
INSERT INTO tasks (tenant_id, biz_no, payload)
VALUES ($1, $2, $3)
ON CONFLICT (tenant_id, biz_no) DO NOTHING
RETURNING id;
```

`ON CONFLICT DO NOTHING` 可能不返回行，调用方需要再按 `(tenant_id, biz_no)` 查询已有记录。注意：唯一约束只能保证“业务键不重复”，不能自动保证“返回首次响应”；如果契约要求同键返回同一响应体，仍需要幂等记录或可重建的稳定表示。
### 2. 键作用域和参数指纹

幂等键由客户端生成。AIP-155 建议 `request_id` 使用 UUID v4；实际落地时，键必须是足够随机、不可预测，并由调用方在“一次逻辑操作”开始时生成。不要用时间戳、自增 ID 或“用户 ID + 秒级时间”拼一个容易碰撞的键。

#### 作用域：先回答“这是谁的哪件事”

只存一个 key 不够。不同租户或用户可能生成相同的 key，同一个 key 也可能被误用到另一个接口。因此幂等记录的主键应是：

```text
(tenant_id / user_id, operation, key)
```

其中：

- 第一维是身份或租户边界，避免跨用户撞键；
- 第二维是接口或操作名，避免同一个 key 在“创建任务”和“上传素材”之间复用；
- 第三维才是客户端生成的 key。

如果系统是多租户的，建议把 `tenant_id` 纳入作用域，而不是只依赖当前登录用户。身份切换、代理调用、后台代操作都要在作用域设计里说清楚。

Python 中可以把身份和操作规范化成一个 `scope`，再与 key 组成主键：

```python
import json

def scope_key(user_id: str, operation: str, key: str) -> tuple[str, str]:
    scope = json.dumps(
        [user_id, operation],
        ensure_ascii=False,
        separators=(",", ":"),
    )
    return scope, key

scope, key = scope_key("u_1001", "create_publish_job", "6f1c2f8e-4d7a-4c31-9b2e-7a8d5c1e9b20")
print(scope, key)
```

用 JSON 数组而不是用冒号拼接，是为了避免 `a:b` 与 `a`、`b` 之类组件的边界歧义。若团队已有统一的 scope 编码规则，以团队规范为准。

#### 参数指纹：同一个 key 必须对应同一份请求

只有 key 还不够。客户端可能复用了 key，却改了请求体；这时不能把新请求当成旧请求执行，也不能返回第一次的响应，否则调用方会以为新参数生效了。常见做法是对**规范化后的业务参数**计算指纹：

```python
import hashlib
import json

EXCLUDED_FIELDS = {
    "request_id",
    "idempotency_key",
    "trace_id",
    "timestamp",
    "client_time",
}

def fingerprint(body: dict) -> str:
    clean = {k: v for k, v in body.items() if k not in EXCLUDED_FIELDS}
    canonical = json.dumps(
        clean,
        ensure_ascii=False,
        sort_keys=True,
        separators=(",", ":"),
    )
    return hashlib.sha256(canonical.encode("utf-8")).hexdigest()
```

规范化至少要做到：对象键排序、无多余空白、统一字符编码、明确数字与金额的表示（金额建议用最小货币单位的整数字符串，避免浮点误差），数组保持业务顺序。对于嵌套对象，`sort_keys=True` 会递归排序；如果业务上数组顺序不重要，需要在计算指纹前显式排序或转成集合语义。

指纹应排除“每次重试都会变化、但不改变业务含义”的字段，例如请求 ID、链路追踪 ID、客户端时间戳、传输签名和重试次数。反过来，**任何会改变业务结果的字段都不能排除**，例如任务类型、目标账号、图文内容 ID、定时发送时间、金额。是否排除某个字段，要看它是否属于业务输入，不能为了“让重试通过”而随意放宽。

#### 同键不同指纹的冲突语义

服务端查到同一作用域下的 key 后，按指纹和状态分支：

| 已有记录 | 新请求指纹 | 处理 |
| --- | --- | --- |
| 无 | 任意 | 创建幂等记录并执行业务 |
| 有，指纹相同，`DONE` | 相同 | 返回首次保存的响应，不再执行业务 |
| 有，指纹相同，`PROCESSING` | 相同 | 返回“处理中”，让客户端按契约重试 |
| 有，指纹不同 | 不同 | 拒绝，提示幂等键被复用于不同参数 |
| 有，但已过期 | 任意 | 按新请求处理，具体语义写入 API 契约 |

“同键不同参数被拒绝”是本课的验收点之一。HTTP 可以用 `422 Unprocessable Content` 或 `409 Conflict` 表达，gRPC 可以用 `INVALID_ARGUMENT` 或 `ALREADY_EXISTS` 的语义；具体选哪个、错误详情怎么放，以团队 API 规范和所读文档版本为准。关键是：**拒绝必须可观测、可区分**，不能让调用方误以为请求成功。

还有一个容易忽略的点：指纹要在进入业务逻辑之前计算，并且基于原始业务参数，而不是基于某个已经补全了默认值、时间戳或服务端生成字段的对象。否则同一个逻辑请求在不同时间可能得到不同指纹。
### 3. 原子提交、TTL与结果复用

本课节点给出的陷阱是：「先查键再执行业务再记键会留下竞态和崩溃窗口」。下面两条时间线说明它为什么不是理论问题。

**时间线 A：并发请求各执行一次。**

```text
请求 A：SELECT 幂等键 -> 不存在
请求 B：SELECT 幂等键 -> 不存在
请求 A：INSERT 任务 1 -> 成功
请求 B：INSERT 任务 2 -> 成功
请求 A/B：记录幂等键（此时已晚）
```

两个请求都通过了“查不到键”的检查，结果产生两个任务。最后记录键时即使唯一冲突，另一条业务写入也已经发生，无法靠幂等表回滚。

**时间线 B：业务成功、记键前崩溃。**

```text
请求 A：SELECT 幂等键 -> 不存在
请求 A：INSERT 任务 1 -> 提交成功
进程崩溃，尚未写幂等键
客户端重试：SELECT 幂等键 -> 不存在
请求 A'：INSERT 任务 2 -> 成功
```

客户端看到超时，自然会重试；服务端却因为“键还没记上”再次执行，产生重复任务。

#### 正确结构：幂等记录与业务结果同事务提交

把幂等记录当成业务数据的一部分，而不是事后日志。推荐流程：

1. 在同一个数据库事务中，先 `INSERT` 幂等记录，状态为 `PROCESSING`，靠 `(scope, key)` 唯一约束抢占。
2. 唯一约束冲突时读取已有记录：`DONE` 返回保存的响应；`PROCESSING` 返回“处理中/稍后重试”；指纹不同则拒绝。
3. 抢占成功后执行真正的业务写入，例如插入任务行。
4. 在**同一事务**内把幂等记录更新为 `DONE`，保存响应体或可重建响应的业务对象 ID。
5. 提交事务。业务写入与幂等记录要么都成功，要么都回滚。

表结构示例（SQLite/MySQL 风格；MySQL 中 `key` 是保留字时需按方言加反引号）：

```sql
CREATE TABLE idempotency_keys (
  scope         VARCHAR(255) NOT NULL,
  key           VARCHAR(128) NOT NULL,
  fingerprint   CHAR(64)     NOT NULL,
  status        VARCHAR(16)  NOT NULL,
  response      TEXT,
  created_at    TIMESTAMP    NOT NULL,
  expires_at    TIMESTAMP    NOT NULL,
  PRIMARY KEY (scope, key)
);

CREATE INDEX idx_idempotency_expires
  ON idempotency_keys (expires_at);
```
Python `sqlite3` 伪代码骨架如下；生产代码还要补齐错误映射、超时、日志和指标。

```python
import json
import sqlite3
import uuid
from datetime import datetime, timedelta, timezone

def handle_create_task(conn, scope, key, fp, payload):
    now = datetime.now(timezone.utc)
    expires = now + timedelta(hours=24)
    try:
        with conn:
            conn.execute(
                "INSERT INTO idempotency_keys "
                "(scope, key, fingerprint, status, response, created_at, expires_at) "
                "VALUES (?, ?, ?, 'PROCESSING', NULL, ?, ?)",
                (scope, key, fp, now.isoformat(), expires.isoformat()),
            )
            task = {"id": str(uuid.uuid4()), "payload": payload}
            conn.execute(
                "INSERT INTO tasks (id, payload) VALUES (?, ?)",
                (task["id"], json.dumps(payload, ensure_ascii=False)),
            )
            conn.execute(
                "UPDATE idempotency_keys SET status='DONE', response=? "
                "WHERE scope=? AND key=?",
                (json.dumps(task, ensure_ascii=False), scope, key),
            )
            return task
    except sqlite3.IntegrityError:
        row = conn.execute(
            "SELECT fingerprint, status, response FROM idempotency_keys "
            "WHERE scope=? AND key=?",
            (scope, key),
        ).fetchone()
        if row is None:
            raise
        saved_fp, status, response = row
        if saved_fp != fp:
            raise ValueError("IDEMPOTENCY_KEY_REUSED_WITH_DIFFERENT_PAYLOAD")
        if status == "DONE":
            return json.loads(response)
        raise RuntimeError("REQUEST_IN_PROGRESS")
```

> 补充：在 SQLite 这类“写事务串行化”的库里，`PROCESSING` 占位在提交前对其他连接不可见，并发的第二个请求会等锁，拿到锁后直接读到 `DONE`；只有当你把“占位”和“完成”拆成两个事务（例如业务里要调外部系统）时，`PROCESSING` 分支才真正会被别的请求看到，这时必须给它定义超时与接管规则。

关键不是 SQL 写法，而是**顺序**：先占位，再执行业务，最后标记完成，三步同事务。若业务写入失败，事务回滚，幂等记录也不会留下，客户端可以安全重试；若进程在提交前崩溃，数据库回滚，同样可以重试；若提交成功但响应在网络上丢失，客户端重试会读到 `DONE` 并拿到首次结果。这是“崩溃恢复后重复请求仍按契约处理”的基础。

注意方言差异：这段骨架按 SQLite 语义书写；PostgreSQL 中唯一冲突会让当前事务进入失败状态，捕获异常后通常需要 `SAVEPOINT`，或改用 `INSERT ... ON CONFLICT DO NOTHING` 后再查询；MySQL 的重复键错误一般不会中止整个事务。并发行为还要按实际数据库版本和隔离级别验证。

#### 跨存储：键在 Redis、业务在数据库

如果幂等键放 Redis、业务数据放数据库，就无法用一个本地事务原子提交两边。常见流程是用 `SET key value NX PX ttl` 抢占，再执行业务，最后把 Redis 值改成完成状态。它的问题与上面的时间线同构：

- 业务已提交、Redis 尚未标记完成时崩溃，重试会看到“处理中”，可能长时间拿不到结果；
- Redis 过期或故障切换后，同一个 key 可能被当成新请求，业务再次执行；
- Redis 的 `SET NX` 只能做占位或锁，不能保证“键记录与业务结果同时生效”。

因此，跨存储时至少要有数据库层的业务唯一约束兜底，或者用 outbox/事务消息把状态变更可靠地传播到幂等存储。更稳妥的默认方案是：**幂等记录与业务数据同库同事务**；Redis 只承担缓存、限流或短期锁，不作为唯一的正确性来源。这些取舍要结合团队已有基础设施，以实际组件文档版本为准。

#### TTL：保留多久，过期后算什么

节点给出的权衡是：「长期去重更可靠，但存储成本与业务有效期需明确」。保留期至少要覆盖客户端的最大重试窗口，包括网络超时后的重试、消息队列重投、批量任务重跑和人工补偿。若客户端可能在 24 小时后用同一个 key 重试，而服务端只保留 1 小时，那么第 25 小时的请求会被当成新请求，重复执行。

保留期还要写进 API 契约：AIP-155 也强调 `request_id` 的保留时长应在文档中说明。过期后的语义必须明确，例如“过期后同一 key 视为新请求”，或者“过期后拒绝并要求客户端生成新 key”。不要留下“可能复用、也可能新建”的模糊地带。

过期清理可以定时按 `expires_at` 分批删除，但不要删除仍在 `PROCESSING` 的记录；删除前确认没有事务正在使用；大批量删除要限速，避免影响在线业务。长期保留的收益是更可靠的重放保护，成本是存储、索引和隐私合规；保留多久由业务有效期和重试契约共同决定。

#### 结果复用：存响应体还是存业务对象 ID

两种做法都可行，取决于契约：

- **保存首次响应体**：重放时原样返回状态码和响应内容，最贴近“同一请求返回同一响应”的要求。适合响应较小、包含创建时间或服务端生成字段的场景；要注意敏感信息、序列化版本和字段演进。
- **保存业务对象 ID，重放时重建响应**：节省存储，但重建出的响应可能随对象状态变化，不再是“首次响应”。只有在契约允许返回“当前表示”，且对象未被删除或改变语义时才适合。

如果选择保存响应，建议把状态码、内容类型和响应体一起序列化到 `response` 字段，避免只存 body 导致重放时状态码不一致。无论哪种方式，都要保证读取响应和判断状态在同一个一致性视图内完成，不能出现“读到 `DONE` 但响应还没写完”的中间态。

#### 收束

三点可以连成一条线：**业务幂等**定义“什么是同一件事”，**键作用域和参数指纹**定义“如何认出同一件事、如何发现参数变了”，**原子提交、TTL 与结果复用**定义“如何可靠地记住并重放这件事”。只做传输去重，会在换连接或上游重发时失效；只做先查后写，会留下竞态和崩溃窗口；只设 TTL 而不写清过期语义，则会把可靠性问题推迟到未来。把唯一约束、同事务提交和明确的保留契约组合起来，重复请求才会变成可预测的等价效果。

## 常见误区与设计权衡

本实践用请求头 `Idempotency-Key` 承载幂等键，与 AIP-155 把 `request_id` 放在请求体里的思路相同，只是载体不同。

### 误区

| 误区 | 问题 | 更稳妥的做法 |
|---|---|---|
| 只靠前端防连点 | 前端禁用按钮或防抖只能减少同一页面内的重复点击，无法阻止超时重试、网关重试、多标签页或多实例提交。 | 服务端定义幂等键契约，并让重复请求返回首次结果。 |
| 用 Redis 锁代替持久记录 | 锁只能提供短期互斥；锁过期、进程重启或主从切换后，服务端可能已经忘记首次结果，无法按契约重放。 | 把幂等键、参数指纹和业务结果持久化；分布式锁只作为减少竞争的优化。 |
| 键作用域只用 key，不含用户或路由 | 不同用户或不同接口复用同一个字符串时可能互相撞键，甚至返回他人的结果。 | 作用域至少包含调用方/租户、HTTP 方法和路由，再与 key 组成唯一约束。 |
| 同键不同参数也返回旧结果 | 客户端误用键或篡改参数时，旧结果会被当成本次请求的结果，造成隐蔽的数据错误。 | 保存规范化参数指纹；同键但指纹不同明确拒绝，本实践返回 422。 |
| 把失败也缓存成永久结果 | 5xx、超时和连接中断代表结果未知；把其缓存成永久失败会阻止本可成功的重试。校验失败等是否记录也要看契约。 | 区分确定性拒绝与暂态失败；结果未知的请求允许同键重试，成功后才记录可重放响应。 |
| TTL 短于客户端重试窗口 | 键记录先过期，客户端仍在重试窗口内，后续请求会被当成新请求，重复创建任务。 | 保留时长覆盖客户端重试、回调重试和业务对账周期，并在 API 文档中写清。 |
| 服务端自己生成幂等键 | 每次请求生成新键，重试自然无法命中；若通过响应返回键，客户端也未必能在重试时稳定带上。 | 由发起方生成并复用同一个键，服务端只负责校验、记录和重放。 |
| 把“查键—执行业务—记键”拆成三个独立步骤 | 先查键再执行业务再记键会留下竞态和崩溃窗口：并发请求可能都查不到键，崩溃可能发生在业务已写、键未写之间。 | 在同一事务中完成键占用、业务写入和结果记录；用唯一约束和事务串行化保护。 |

失败缓存需要单独定契约。进入业务副作用之前就被拒绝的格式错误、鉴权失败或参数校验失败，通常不产生业务结果，可以不写入幂等结果，允许客户端修正后重试；明确且可复现的业务拒绝是否缓存，要看 API 文档。5xx、超时、连接中断属于“结果未知”，不应缓存成永久成功，也不应让同键重试永久失败。AIP-155 的要点是同一 `request_id` 返回首次响应而不重复执行，但“哪些响应算首次响应、保留多久”仍要以所读文档版本和自己的 API 文档为准。

计数类副作用尤其要小心：重试不能重复加一。更稳妥的做法是让计数由唯一业务事件派生，或者在业务事务内做带条件的更新；不要先加计数再单独记录幂等键。

### 权衡

节点给出的总权衡是：“长期去重更可靠，但存储成本与业务有效期需明确。”

| 权衡 | 偏向 | 需要明确的代价 |
|---|---|---|
| 长期去重 vs 存储成本 | 保留更久能覆盖更长的重试与对账窗口，减少重复副作用。 | 键表会增长；需要 TTL、归档、清理策略和可观测的过期指标。 |
| 存完整响应 vs 存引用 | 存完整响应便于原样重放，不依赖业务表还能查到旧结果。 | 占空间，可能包含敏感字段；存引用则要保证引用生命周期不短于幂等记录，并能还原状态码和响应体。 |
| DB 事务内 vs Redis | 与业务表同库同事务，键记录和业务写入能一起提交或一起回滚。 | 数据库压力与锁竞争；Redis 方案快，但跨存储一致性、持久化和故障恢复要额外设计，不能想当然。 |
| 业务唯一键 vs 通用幂等键表 | 业务唯一键直接表达“同一资源只能有一个”，查询简单。 | 只适用于有自然唯一性的场景；通用幂等键表可覆盖创建任务、提交批处理等更多接口，但要处理作用域、指纹、TTL 和响应存储。 |

选择时先问三个问题：重复请求的最长窗口有多长？失败是否允许重试？响应里是否含敏感数据？答案不明确时，不要把幂等实现成“只加一把锁”。
## 动手实践：practice88

> practice 原文：实现创建任务接口，同一键并发提交只产生一个任务且返回同一结果。

下面的“创建任务”是教学假设：它可以是内容后台的一次图文发布准备任务，也可以是素材处理或群发提交任务。重点是接口契约与数据库事务，不依赖任何平台内部接口。

### 1. 准备目录与解释器

```bash
mkdir -p ~/practice88 && cd ~/practice88
python3 --version
```

本实践只使用 Python 标准库：`sqlite3`、`http.server`、`threading`、`hashlib`、`json`、`uuid`。不需要安装 Web 框架或数据库驱动。

### 2. server.py 的接口与数据约束

- `POST /tasks`，请求头 `Idempotency-Key`（必填）和 `X-User`（模拟鉴权主体，默认 `u1`），请求体 `{"title": "...", "payload": ...}`；`GET /stats` 返回 `{"tasks_in_db": N}` 方便验证。
- 表 `tasks` 存业务任务；表 `idempotency_keys` 存作用域、键、参数指纹、状态、响应体和过期时间，主键 `(scope, key)`。
- 作用域 = `用户:操作`（如 `u1:create_task`），再与 key 组成主键；参数指纹 = 规范化后 `{title, payload}` 的 SHA-256，所以字段顺序不同仍算同参数。
- `tasks` 与 `idempotency_keys` 在同一个 SQLite 事务中提交；写事务用 `BEGIN IMMEDIATE` 拿写锁，让同键并发请求排队，而不是都读到“键不存在”。
- 首次成功返回 `201` 和 `{"task_id": "..."}`；同键同参数重放返回同样的 `201` 和响应体；同键不同参数返回 `422`；缺少键返回 `400`；记录过期（TTL 24 小时）后同键按新请求处理。
- 设置 `CRASH_AFTER_BUSINESS=1` 时，在业务行写入后、事务提交前用 `os._exit(1)` 模拟进程崩溃；未提交事务随之回滚。
- 端口被占用时进程以退出码 2 结束。

表结构：

```sql
CREATE TABLE tasks(id TEXT PRIMARY KEY, owner TEXT, title TEXT, payload TEXT, created_at REAL);
CREATE TABLE idempotency_keys(
  scope TEXT, key TEXT, fingerprint TEXT, status TEXT, response TEXT,
  created_at REAL, expires_at REAL, PRIMARY KEY(scope, key));
```

下面是 `server.py` 里的指纹与事务核心（完整文件见附件 practice88）：

```python
def handle_create(db, owner, key, body):
    """返回 (http_status, response_dict)。"""
    scope = f"{owner}:create_task"
    fp = fingerprint(body)
    conn = sqlite3.connect(db, timeout=10, isolation_level=None)
    try:
        conn.execute("BEGIN IMMEDIATE")          # 拿写锁：同库并发写串行化
        row = conn.execute("SELECT fingerprint,status,response,expires_at FROM idempotency_keys "
                           "WHERE scope=? AND key=?", (scope, key)).fetchone()
        now = time.time()
        if row and row[3] < now:                 # 过期：按契约视为新请求
            conn.execute("DELETE FROM idempotency_keys WHERE scope=? AND key=?", (scope, key))
            row = None
        if row:
            conn.execute("COMMIT")
            if row[0] != fp:
                return 422, {"error": "idempotency key reused with different parameters"}
            return 201, json.loads(row[2])       # 重放：返回首次结果
        task_id = str(uuid.uuid4())
        conn.execute("INSERT INTO tasks VALUES(?,?,?,?,?)",
                     (task_id, owner, body.get("title"), json.dumps(body.get("payload")), now))
        if os.environ.get("CRASH_AFTER_BUSINESS") == "1":
            print("simulated crash before commit", file=sys.stderr, flush=True)
            os._exit(1)                          # 未提交 -> 事务随进程消失
        resp = {"task_id": task_id}
        conn.execute("INSERT INTO idempotency_keys VALUES(?,?,?,?,?,?,?)",
                     (scope, key, fp, "DONE", json.dumps(resp), now, now + TTL_SECONDS))
        conn.execute("COMMIT")                   # 业务 + 幂等记录 一起提交
        return 201, resp
    except Exception:
        if conn.in_transaction:
            conn.execute("ROLLBACK")
        raise
    finally:
        conn.close()
```

这段代码的关键点不是函数名，而是顺序：先开启写事务，再检查键；键不存在时写业务行和键记录，最后一起提交。重放路径只读取已提交的键记录，不会重新执行业务。
### 3. 启动服务并做三次手工请求

```bash
python3 server.py --port 18088 --db tasks.db &
```

首次请求：

```bash
curl -i -X POST http://127.0.0.1:18088/tasks \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-key-001' \
  -d '{"title":"周末图文任务","payload":{"article_id":"a-1001"}}'
```

预期：HTTP `201`，响应体包含 `{"task_id": "<首次生成的 UUID>"}`。

同键、同参数重放：

```bash
curl -i -X POST http://127.0.0.1:18088/tasks \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-key-001' \
  -d '{"title":"周末图文任务","payload":{"article_id":"a-1001"}}'
```

预期：仍为 HTTP `201`，`task_id` 与首次完全相同，数据库中没有新增任务。

同键、改参数：

```bash
curl -i -X POST http://127.0.0.1:18088/tasks \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-key-001' \
  -d '{"title":"另一个任务","payload":{"article_id":"a-1001"}}'
```

预期：HTTP `422`，响应体为 `{"error": "idempotency key reused with different parameters"}`；这是“同键不同参数被拒绝”的直接验证。

缺少 `Idempotency-Key` 时返回 `400`，可以在浏览器或 curl 中自行补测；它不属于上面三条主实验，但应在 `test.sh` 中断言。

### 4. 并发提交实验

```bash
# 用一个新库重启，避免手工请求的任务干扰计数
kill %1; rm -f tasks.db*; python3 server.py --port 18088 --db tasks.db &
python3 client.py --concurrency 20 --same-key
```

客户端启动 20 个线程，使用相同的 `Idempotency-Key` 和相同 body 同时 POST。预期输出包含：

```text
statuses=[201] distinct_task_ids=1 tasks_in_db=1
```

这说明同键并发请求只产生一个任务，所有调用方拿到同一个 `task_id`。如果输出中 `tasks_in_db>1`，优先检查是否真的把键记录与任务写入放在同一事务中，以及是否用了 `BEGIN IMMEDIATE` 或等价的唯一约束保护。

### 5. 崩溃恢复实验

```bash
CRASH_AFTER_BUSINESS=1 python3 server.py --port 18088 --db tasks.db &
```

用 `crash-key-001` 和固定 body 发起一次请求。该请求可能直接断开连接，预期不会得到成功的 `201` 响应。随后停止服务进程，正常启动：

```bash
python3 server.py --port 18088 --db tasks.db &
```

用同一个 `crash-key-001` 和完全相同的 body 重试，预期得到 `201` 和某个 `task_id`；再用同一键重放，预期得到相同的 `task_id`。再 `curl -s 127.0.0.1:18088/stats`，若这是一个新库，预期 `tasks_in_db` 为 `1`。

这一步验证的是“崩溃恢复后重复请求仍按契约处理”：崩溃时业务行虽已执行，但事务没有提交，恢复时回滚；正常重试会重新执行并提交一份结果。不同 SQLite 日志模式或操作系统行为可能有差异，具体以实际版本和文档为准。
### 6. 反例：先查键再执行再记键

```bash
kill %1 2>/dev/null; rm -f naive.db*
python3 server_naive.py --port 18088 --db naive.db &
python3 client.py --concurrency 20 --same-key
```

`server_naive.py` 故意把流程拆成“查键—执行业务—记键”，并在业务执行中加入 `sleep` 放大竞态。并发提交同一键时，多个请求都可能先查不到键，于是各自创建任务，预期 `tasks_in_db>1`。具体条数取决于调度顺序，不要把它写成固定值。

这个反例对应误区表中的原句：先查键再执行业务再记键会留下竞态和崩溃窗口。修复思路不是加更多日志，而是把键占用、业务写入和结果记录收进同一事务，并用唯一约束兜底。

### 10. 排障清单

- `database is locked`：确认每个请求使用独立连接、事务尽量短、没有在持有写事务时做网络 IO；给连接设置合理 `timeout`，并检查异常路径是否回滚和关闭连接。不要用“加大超时”掩盖长事务。
- 键作用域错误：同一字符串在不同用户、租户或路由下可能撞键。把作用域定义为“调用方/租户 + HTTP 方法 + 路由”，再与键建立唯一约束；不要只用 key，也不要把 body 放进作用域。
- 参数指纹不一致：确认客户端重试时 body 的字段集合和值完全一致；服务端固定规范化规则（例如排序键、稳定分隔符），并明确哪些字段参与指纹。若两次请求的指纹不同，应按同键不同参数拒绝，而不是返回旧结果。
- 重放结果不一致：检查是否只保存了 `task_id` 却临时拼装响应，或状态码没有和响应一起保存。把需要重放的状态码和响应体一起持久化，按契约返回。
- 崩溃后出现重复任务：检查业务写入和键记录是否在同一事务、是否真的提交前崩溃、恢复后是否用同一作用域和同一键重试。以所读 SQLite 文档和实际运行结果为准。

**三个常见误读**

- 把 `request_id` 当成业务单号：业务单号通常由业务创建，而请求标识用于识别一次调用；二者可能相同，但不能混为一谈。
- 把“建议 UUID v4”当成唯一合法格式：本课按字符串接收，格式校验强度由接口文档决定。
- 把“返回相同响应”理解成“任何同键请求都返回旧响应”：同键不同参数属于冲突，必须拒绝；这是本课的扩展规则。

### 1. request_id 的公开要点

按本课可引用的 Google AIP-155 公开要点（以所读版本为准）：

- **字段定义**：请求可以带 `request_id` 字段，用于标识一次请求；它是字符串。
- **格式建议**：建议使用 UUID v4。客户端应为一次新的业务操作生成新值，而不是每次重试都换值。
- **保留期内行为**：服务端在一段时间内看到同一 `request_id` 时，应返回与首次相同的响应，并避免重复执行。
- **文档义务**：API 文档应说明 `request_id` 的保留时长，让客户端知道多久之内可以安全重试。
- **与 HTTP 头的关系**：`request_id` 与 HTTP 的 `Idempotency-Key` 头思路相同；相关 IETF 草案的字段、错误码和语义以所读版本为准。

> 注：公开要点描述的是可观察契约，不等于某家公司内部如何建表、如何清理、如何部署。具体实现应回到你所读的接口文档和代码。

## 自测题

### 题 1：先查键、再执行、再记键，会漏在哪里？

**题干**

某创建任务接口的实现顺序是：查询幂等表，若没有记录就创建任务，创建成功后再写入幂等表。请指出两种会出错的时间线，并给出修正方案。

**答案**

- 时间线 A（并发）：两个请求几乎同时查询，都看到“无记录”，于是都创建任务。若幂等键没有唯一约束，会产生两个任务；若有唯一约束，后写入者可能失败，但如果没有把首次结果读回来，仍可能给调用方返回错误或不一致结果。
- 时间线 B（崩溃）：请求创建任务成功，但在写入幂等记录之前进程崩溃。客户端重试时仍查不到键，于是再创建一个任务，造成重复执行。

修正方向是不要把“检查”和“执行”拆成两个可被并发或崩溃打断的步骤：在同一事务中创建任务并写入幂等记录，并用唯一约束保护作用域加幂等键；插入冲突时读取已保存的首次结果并返回。若业务写入涉及外部系统，还应设计状态机、补偿或对账，不能假装数据库事务能覆盖一切。

**解析**

这正对应本课 pitfalls：“先查键再执行业务再记键会留下竞态和崩溃窗口。”关键不是把检查写得更早，而是让“业务结果”和“幂等记录”成为一个原子提交单元，并让重复请求走结果复用路径。

补充：只加唯一约束仍不够。若冲突后直接报错，客户端拿不到首次结果；若冲突后重新执行，又回到重复执行。需要“冲突时读取首次记录”的结果复用路径。

### 题 2：同一把键，先 A 后 B，应该返回 A 的结果吗？

**题干**

客户端使用同一个 `Idempotency-Key` 先提交 `title=A` 的任务创建请求，随后又用同一把键提交 `title=B`。服务端应如何响应？为什么不能直接返回 A 的结果？

**答案**

服务端应拒绝第二个请求，返回契约中定义的冲突错误，并明确说明同一个幂等键已经绑定到不同参数。不能执行 B，也不能把 A 的结果当作 B 的结果返回。具体状态码和错误体以所读接口文档为准。

不能返回 A 的结果，是因为幂等键代表“同一个操作”的重试，不是“随便复用上一次响应”。如果客户端拿到 A 的结果，会误以为 B 已经创建成功；服务端则悄悄丢掉了 B 的意图。正确做法是让客户端为新业务操作生成新键，或由客户端显式发起一个不同的操作。

**解析**

这对应验收项“同键不同参数被拒绝”。实现上要对参与业务语义的参数做规范化后计算指纹，并把指纹与幂等记录一起保存；重复请求先比较指纹，再决定是返回旧结果还是拒绝冲突。哪些参数进入指纹属于本课扩展，应按接口契约明确列出。

补充：参数指纹应有稳定的规范化规则，例如字段顺序、空白和可选字段默认值的处理；规则应写入接口契约，避免客户端与服务端对“同参数”理解不同。

### 题 3：TTL 太短、重试窗口太长，会发生什么？

**题干**

幂等记录 TTL 设为 10 分钟，而客户端最长重试窗口是 24 小时。两者不一致会发生什么？应如何确定保留期？如果业务已经写完，进程在提交前崩溃，重试又会怎样？

**答案**

TTL 只有 10 分钟时，10 分钟后幂等记录被清理；客户端在 24 小时内重试时，服务端已经无法识别这是旧请求，会把它当成新请求再次执行，可能产生重复任务。保留期应至少覆盖客户端最长重试窗口，并留出时钟偏差、清理延迟和运维处置的余量；同时要结合业务有效期与存储成本，把最终时长写进 API 文档。公开要点只要求文档说明保留时长，具体取值以所读文档版本为准。

关于崩溃：如果任务和幂等记录在同一事务中提交，业务写完但事务尚未提交时崩溃，事务回滚，重试会重新执行一次，因此只产生一次可见结果；如果已经提交，任务和幂等记录都在，重试会命中记录并返回同一结果。若业务写入先独立提交、幂等记录后写，那么提交前崩溃就会留下“业务已存在但键不存在”的窗口，重试可能重复创建，需要靠原子提交或恢复对账处理。

确定保留期可按四步记录：

1. 读取客户端重试策略，确认最长重试窗口。
2. 确认业务结果的有效期和可撤销、可补偿时间。
3. 加上清理延迟、时钟偏差和人工排障余量。
4. 把最终值、起算点和过期语义写进 API 文档，并用测试覆盖边界。

**解析**

这对应验收项“崩溃恢复后重复请求仍按契约处理”。判断标准不是“进程有没有崩”，而是“恢复后能否从事务状态和幂等记录判断原请求是否已经生效”。先记键后执行、执行后补记键、TTL 短于重试窗口，都会破坏这个判断。

## 本课小结

- 幂等不是“请求不重复到达”，而是重复执行只产生受控的等价业务效果；传输去重解决重复投递，业务幂等解决重复生效。
- 幂等键要有明确作用域，至少区分调用方/租户、操作类型和键值；脱离作用域谈唯一性容易让不同接口互相碰撞。
- 参数指纹把“同一个操作”具体化：同键同参数可复用首次结果，同键不同参数必须拒绝，不能静默覆盖或返回旧结果。
- 原子提交是核心：业务结果与幂等记录应在同一事务中落定，避免“先查键、再执行业务、再记键”留下的并发竞态和崩溃窗口。
- TTL 要覆盖客户端最长重试窗口并留余量，同时把保留时长写进文档；TTL 过短会让旧请求在过期后被当成新请求。
- 崩溃恢复后能否按契约处理，取决于提交是否原子、记录是否可读；若业务已独立提交而键未写入，需要恢复或对账机制兜底。
- 长期去重更可靠，但会增加存储与清理成本；保留期、业务有效期和存储预算必须一起明确，不能只追求“永久保存”。
- 公开的 AIP-155 要点和 IETF 草案只能支撑公开语义；具体保留时长、错误码、存储和清理方式，以所读文档版本及实际接口契约为准。
