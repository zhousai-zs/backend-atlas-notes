## 导读

### 上一课留下的缺口

上一课的 `PaxosEngine` 关心的是「一个值」：两个 proposer 交错时，新提案必须继承已被选中的 `Weekly digest (draft)`；三台 acceptor 上跑 2 个实例，就选出 2 条命令，`instances_equal_replicas=false`。那一课特意强调，实例数量不是副本数量。但它没有回答另一件同样常见的事：数据量和写入量涨到一组节点放不下时，**不同的键**怎么分到**不同组**的节点上；以及在不停写入的情况下，把一部分键从一组节点搬到另一组时，路由、数据和版本怎样保持一致。

共识解决的是「同一份数据的多个副本怎么对齐」，分片解决的是「不同键由谁服务」。两件事正交：一个分片内部可以用 116–119 课的复制状态机、Raft 或 Paxos 保持副本一致，但分片之间的搬迁要靠另一套机制。本课补的就是这套机制：带版本的路由表、迁移期间的双写或转发，以及从「源节点负责」切到「目标节点负责」的那个切换窗口。

### 接上前置

前置之一 [第 116 课](https://zhousai-zs.github.io/backend-atlas-notes/lessons/116.html) `h-replication` 讲复制状态机：确定性命令按同一顺序应用到多个副本，副本在相同日志前缀上得到相同状态。本课沿用两个思路：每个键带单调版本号，迁移时目标节点只接受**更新的版本**（`apply_if_newer`），所以拷贝和转发即使乱序到达，也不会把新值覆盖成旧值；以及「已确认的写」必须在切换后仍然存在，这是 116–118 课「已提交不能丢」在分片迁移里的对应物。

前置之二 [第 110 课](https://zhousai-zs.github.io/backend-atlas-notes/lessons/110.html) `g-sharding` 已经比较过取模、一致性哈希与范围分片，统计了增删节点时的迁移比例，并用 Redis Cluster 风格的槽演示过 `ASK` / `MOVED`。那一课的迁移是在没有并发写压测的条件下做的，热点实验也只用了一种虚拟节点数。本课往前推两步：一是**在持续写入时**迁移一个分片，并用「总键数 + 每个键的版本」做验收；二是把虚拟节点数从 `1` 扫到 `128`，再加一台节点，直接回答「一致性哈希为什么不能自动消除热点键」。

### 教学场景（教学假设）

假设内容后台把 4000 篇文章的标题键 `article:00000:title` 到 `article:03999:title` 存在分片 KV 里，初值都是 `Weekly digest`，版本 `1`。键用 Redis 规范的 CRC16 算出 0–16383 的槽，每 2048 个槽为一个教学分片，共 8 个分片。初始路由表 `route_version=1`：分片 0、3、6 在 `n1`，分片 1、4、7 在 `n2`，分片 2、5 在 `n3`，`n4` 是刚扩容进来的空节点。4 个客户端各自缓存一份路由表。压测从 `0.0` 持续到 `0.6`：每 `0.001` 秒一次写，共 `600` 次；其中约 10% 是新文章插入，其余是把已有标题改成 `Weekly digest (draft)`、`Weekly digest (revised)` 或 `Weekly digest (hotfix)`，并且 30% 的更新故意打在分片 0 上，好让被迁移的分片足够「热」；每 `0.002` 秒一次读，共 `300` 次。`0.1` 开始把分片 0 从 `n1` 迁到 `n4`。这些数字都是教学虚拟时钟上的值，不是线上配置。

### 本课三条主线

1. **范围分片与哈希分片**：范围分片按键的顺序切段，扫描连续区间只碰一个分片，但递增 id 的新写入会全部落在最后一段；哈希分片把键打散，写入均匀，但范围扫描要扇出到所有分片。
2. **虚拟节点与热点键**：虚拟节点改善的是**键数**在节点间的均衡；一个热点键无论放到哪里，都只落在一个节点上，所以访问量的不均衡不会因为虚拟节点或加机器而消失。
3. **迁移期间双写和转发**：路由表必须带版本；迁移要先拷贝存量，再用双写转发或变更日志追平增量，最后在一个短的冻结窗口里切换路由、清理源节点。只改路由表，或拷完存量不追增量，都会丢已确认的写。

## 学习目标

- 能解释范围分片与哈希分片及适用边界：什么时候扫描友好更重要，什么时候写入均匀更重要；能说清 Redis Cluster 的 16384 槽属于哪一类。
- 能独立完成实践：实现带版本路由表的分片 KV，在写压测中迁移一个分片，并用总键数和每个键的版本验收迁移结果。
- 能用实验数字解释一致性哈希不能自动消除热点键，并说明拆分热点键和加机器、加虚拟节点分别改变了什么。

## 为什么后端要懂

公众号内容后台（教学假设）的文章元数据，最先遇到的瓶颈往往不是单条读写慢，而是一台机器装不下、扛不住。分片几乎是必经之路，但真正出事故的通常不是「怎么切」，而是「怎么搬」。扩容那天，运维把分片 0 从旧节点改到新节点；如果只改了路由，没有把数据搬过去，读请求就会落到一台没有这批标题的机器上，编辑看到文章标题变成空；如果拷完存量就切换，拷贝期间编辑改过的标题会悄悄回到旧值。两种情况在监控上可能都只表现为「迁移期间有少量错误」，事后却要逐篇对账。

热点是另一类问题。一篇爆款推文的标题和阅读计数在几分钟内被读几十万次，键在节点间分得再均匀，这一个键也只在一台机器上。如果以为「上了一致性哈希、虚拟节点开到 128，就不会有热点」，容量规划会漏掉最关键的那一台。理解分片的边界，才能在扩容、迁移和应对爆款时分清：哪些问题靠路由解决，哪些问题必须改数据模型。

## 核心知识点

### 1. 范围分片与哈希分片

范围分片把键按顺序切成连续的段，每段交给一个分片。它的好处是保序：要列出 id 1000 到 1099 的文章，只需访问持有这一段的分片。哈希分片先对键算哈希，再按哈希值分配，好处是把相邻的键打散到不同分片，写入和容量更均匀，代价是失去顺序，范围扫描要问遍所有分片。

Redis Cluster 属于哈希分片。规范的 Key distribution model 一节写明：键空间被分成 16384 个槽，基本算法是 `HASH_SLOT = CRC16(key) mod 16384`，CRC16 采用 XMODEM 参数（多项式 `1021`，初值 `0000`，不反射，输出不异或），对字符串 `"123456789"` 的输出是 `31C3`；只用 16 位输出中的 14 位，所以是对 16384 取模。每个主节点负责其中一部分槽。Hash tags 一节又给出例外：键里有 `{...}` 时，只对花括号内的子串算槽，用来把多个键放进同一槽，从而支持多键操作。

教学引擎直接实现了这套槽计算并做了核对：`crc16("123456789")` 的结果是 `31C3`，与规范一致；`{user:1000}.name` 与 `{user:1000}.surname` 都落在槽 `1649`；`article:00042:title` 落在槽 `10587`，按每 2048 槽一组属于分片 `5`。

实验 `range_vs_hash` 把两种分片的取舍变成数字，两边都是 8 个分片，范围分片每段 500 个 id：

| 场景 | 范围分片 | 哈希分片（CRC16 槽 → 8 分片） |
|---|---:|---:|
| 扫描 id 1000–1099 要访问的分片数 | 1 | 8 |
| 4000 个已有键的最大分片份额 | — | 0.125（每个分片恰好 500 个键） |
| 新插入 id 4000–4399 落到的分片数 | 1 | 8 |
| 新插入的最大分片份额 | 1.0 | 0.13 |

范围分片下，100 个连续 id 的扫描只碰 1 个分片；哈希分片要碰全部 8 个。反过来，400 篇新文章的 id 是递增的，在范围分片里全部落在最后一段，那个分片承担 100% 的插入；在哈希分片里分到 8 个分片，最大份额 0.13。这就是节点的权衡：范围分片利于扫描，哈希分片更容易均匀分布。

「每个分片恰好 500 个键」看起来过于整齐，但这是这次运行的真实结果：CRC 对输入是线性的，连续十进制编号的键名在高 3 位上恰好均匀轮转；4000 个键实际只占了 `2464` 个不同的槽。换一组键名，就不会这么整齐，不要把它当成 CRC16 的一般性质。

### 2. 虚拟节点与热点键

一致性哈希把节点放到一个哈希环上，键顺时针找到第一个节点。只放一个点时，各节点在环上分到的弧长差别很大；虚拟节点让每台物理节点在环上放很多点，弧长趋于平均，键数也就更均衡，加减节点时也只搬动一小部分键。第 110 课已经统计过迁移比例，本课只看均衡与热点。

需要先说明：Redis 规范**没有**讲一致性哈希或虚拟节点。Redis Cluster 用固定的 16384 个槽，再由运维或工具把槽分给节点，可以看成「槽就是固定数量的虚拟分区」，但它不是哈希环。本节的环是教学实现，用 MD5 放置虚拟节点。

实验 `hotkey`：4 台节点、4000 个标题键，模拟 10000 次访问，其中一半打在爆款 `article:00042:title` 上（实际 `4980` 次），另一半在所有键上均匀分布。

| 虚拟节点数 | 键数最大份额 | 访问最大份额 | 热点键所在节点 |
|---:|---:|---:|---|
| 1 | 0.6158 | 0.6084 | `n2` |
| 16 | 0.4163 | 0.5856 | `n4` |
| 128 | 0.2988 | 0.6460 | `n3` |

虚拟节点从 1 加到 128，键数的最大份额从 `0.6158` 降到 `0.2988`，接近理想的 0.25；但访问的最大份额一直在 `0.58`–`0.65` 之间，128 个虚拟节点时反而是 `0.646`。原因很直接：热点键只有一个，哈希把它映射到环上的一个点，它的 4980 次访问全部由那一台节点承担，再加上它分到的普通访问。虚拟节点改变的是键在哪里，改变不了一个键被访问多少次。

再加一台 `n5`（同样 128 个虚拟节点），键数最大份额降到 `0.2265`，但热点键仍在 `n3`，`n3` 的访问份额仍是 `0.6046`。加机器分走的是其他键，热点键并没有被分走。

真正能分散热点的是改数据模型。教学实验把爆款标题的读请求随机打到 N 个副本键 `article:00042:title#0` … `#N-1` 上（写入时要写全部 N 份，这里只模拟读）。N=8 时，8 个副本键里有 6 个落在 `n1`，访问最大份额只降到 `0.5016`；N=32 时，副本键分布为 `n1` 14 个、`n2` / `n3` / `n4` 各 6 个，访问最大份额降到 `0.3469`。拆分本身也要经过哈希，副本数少时一样会撞到同一台节点。这不是 Redis 的功能，也不是副本提升，只是演示：热点必须从键的设计上处理，靠路由层是消除不了的。

### 3. 迁移期间双写和转发

Redis 规范的 Live reconfiguration 一节把加节点、删节点和再平衡归结为同一件事：把哈希槽从一个节点移到另一个节点，而移动一个槽就是移动所有落在这个槽里的键。它的做法是：向目标 B 发 `CLUSTER SETSLOT 8 IMPORTING A`，向源 A 发 `CLUSTER SETSLOT 8 MIGRATING B`。之后，已有的键仍由 A 处理；A 上不存在的键通过 `-ASK` 交给 B，「这样就不会再在 A 上创建新键」。迁移工具用 `CLUSTER GETKEYSINSLOT` 取键，再用 `MIGRATE` 把键原子地从 A 搬到 B：B 回 OK 之后，A 删除旧键，所以从外部客户端看，一个键在任一时刻要么在 A，要么在 B。全部搬完后，对两台节点发 `SETSLOT <slot> NODE <node-id>`，通常也发给所有其他节点，不必等配置自然传播。

ASK redirection 一节解释了为什么不能只用 MOVED：MOVED 表示这个槽已经永久由另一个节点服务，后续请求都应发到那里；ASK 只表示「把下一条请求发过去」，因为下一条请求的键可能还在 A 上。客户端收到 ASK 时只重发这一条请求，先发 `ASKING`，不更新本地槽表；目标节点只有在请求前带了 `ASKING` 时，才会处理处于 IMPORTING 的槽，否则用 MOVED 把客户端打回真正的所有者。槽迁移完成后，A 会回 MOVED，客户端才把槽永久映射到新节点。Multi-keys operations 一节补充：迁移期间，所有键都存在且仍在同一节点上的多键操作照常可用；键不存在，或者分散在源和目标两边的多键操作，会返回 `-TRYAGAIN`。配置传播部分还写到：导入节点完成一个槽的导入后，会把自己的配置纪元（configEpoch）加一，让这次变更传播到整个集群；所有节点最终会认定，声明该槽的节点里 configEpoch 最大的那个是所有者。

这套机制的核心是两件事：**路由有版本**（configEpoch 决定谁说了算），**数据在源和目标之间有明确的读写规则**（MIGRATING / IMPORTING / ASK）。应用自己做分片路由时（例如在业务层或代理层维护路由表），一般没有 `MIGRATE` 这种逐键原子搬迁和 ASK 协议，常见做法是：

1. **路由表带版本**：配置服务维护 `route_version`，客户端缓存路由表，每个请求带上自己缓存的版本。节点发现分片不归自己时，回一个「路由过期」错误，客户端刷新路由后重试。
2. **拷贝存量**：目标节点进入导入状态，源节点按批把这个分片的存量键拷过去。拷贝期间写入仍由源节点处理。
3. **追平增量**：拷贝期间的新写有两种处理方式。**双写转发**：源节点写本地之后，同步把同一个版本转发给目标，再回复客户端；**变更日志**：源节点只写本地并追加变更日志，拷完存量后分几轮重放日志，直到剩下的条目足够少。
4. **短暂冻结并切换**：冻结这个分片的写（客户端收到「稍后重试」），把最后剩下的日志重放完，发布新版本路由，让目标成为所有者。冻结开始到新路由生效，就是**切换窗口**。
5. **清理源节点**：确认新路由已生效后，删除源节点上这个分片的数据。

每一步都依赖「每个键有单调版本号，目标只接受更新的版本」：存量拷贝可能拷到旧值，双写转发可能比拷贝先到，日志重放可能晚于转发，只要目标节点按版本取较大者，乱序就不会把新值覆盖成旧值。

## 常见误区

节点给出的误区是：**仅修改哈希环就认为完成无损迁移**。`flip_only` 对照在完全相同的写压测下，`0.1` 开始迁移、`0.101` 直接把路由表改成 `route_version=2`、分片 0 归 `n4`，不搬任何数据；`0.121` 清理源节点，删除 `n1` 上分片 0 的 `500` 个键。结果：

- 读请求有 `27` 次读不到已经确认写入的键，`reads_missing=27`。
- 已确认写入的键应有 `4060` 个，所有者节点上只有 `3715` 个，`missing_keys=345`，`total_key_count_ok=false`。
- `n4` 上分片 0 只有 `165` 个键，都是切换之后写进来的。
- 有 `14` 个已有键在 `n4` 上被重新从版本 `1` 开始计数，版本比之前确认过的更小，`version_regressions=14`。

改路由只是改了「请求去哪」，数据还留在原来的地方。路由表、数据和版本三者必须一起迁移，不能只看哈希环。

**额外误区（本课实验发现）：拷完存量就切换，不追增量。** `copy_then_flip` 照样拷了 10 批共 `500` 个键，`0.2` 拷完，`0.201` 切换路由，`0.221` 清理源节点。但拷贝期间源节点上发生的写没有同步给目标：在某个键所在批次已经拷完之后才写入的更新，以及拷贝开始后才插入的新文章，都留在了源节点上，随清理一起删除。最终 `missing_keys=2`（2 篇拷贝期间插入的新文章丢失），`wrong_version_keys=13`（13 个键回到了旧版本），已确认写入共丢 `15` 次，读到旧版本 `2` 次。总键数看上去只差 2 个，`4058` 对 `4060`，很容易被当成「基本没问题」；只有逐键核对版本才能发现另外 13 处回退。这也是验收要同时看总键数和版本的原因。

**第二个误区：以为一致性哈希或虚拟节点能消除热点。** 上一节的数字已经说明：虚拟节点从 1 到 128，键数最大份额从 `0.6158` 降到 `0.2988`，访问最大份额却始终在 `0.58`–`0.65`；加一台节点后，热点节点的访问份额仍是 `0.6046`。

**第三个误区：只看总键数就算验收通过。** `copy_then_flip` 少了 2 个键，13 个键版本回退；如果某次迁移恰好没有插入新键，总键数会完全一致，但版本依旧错。验收要逐键比较「最后一次确认的值和版本」。

## 设计权衡

节点给出的权衡是：**范围分片利于扫描，哈希分片更容易均匀分布**。`range_vs_hash` 的数字：扫描 100 个连续 id，范围分片碰 `1` 个分片、哈希分片碰 `8` 个；插入 400 个递增 id，范围分片 `100%` 落在最后一段，哈希分片最大份额 `0.13`。按文章 id 顺序翻页、按时间做归档扫描的场景偏向范围分片，但要预先切分最后一段，或者给 id 加随机前缀，以免新写入集中到一处；以单键读写为主、要求负载均匀的场景偏向哈希分片，代价是范围查询要扇出，或者另建索引。Redis Cluster 选择了哈希槽，并用 hash tag 给需要放在一起的键留了一个出口。

第二笔权衡是**双写转发和变更日志**，它们用不同的代价换取同样的正确结果。两次迁移的验收完全相同：`4060` 个键、版本全对。

| 指标 | `dual_write` | `change_log` |
|---|---:|---:|
| 存量拷贝 | 10 批 / 500 个键，`0.1`–`0.2` | 10 批 / 500 个键，`0.1`–`0.2` |
| 增量处理 | 同步转发 `36` 次 | `0.2` 一轮重放 `36` 条，冻结时剩 `3` 条 |
| 冻结开始 → 新路由生效 | `0.200` → `0.201` | `0.207` → `0.209` |
| 切换窗口 | `0.001` 秒 | `0.002` 秒 |
| 迁移期间分片 0 写延迟 p50 | `0.004` 秒（迁移前 `0.002`） | `0.002` 秒（不变） |
| 收到 `RETRY` 的写 | 1 | 0 |

双写转发让每次写多等一次源到目标的往返，迁移期间分片 0 的写延迟 p50 从 `0.002` 翻倍到 `0.004`；但目标始终与源同步，冻结时没有剩余日志，切换窗口最短。变更日志不增加写延迟，代价是要多一轮重放、冻结时还要把尾巴补完，切换窗口更长，实现也更复杂（日志要有界、要处理重放跟不上写入的情况）。这些都是教学虚拟时钟上的数字，只说明方向：双写把成本摊到迁移期间的每次写，日志追赶把成本集中到切换前后。

第三笔权衡是**冻结窗口的长短与可用性**。冻结期间分片 0 的写会收到 `RETRY`，客户端要退避重试；`dual_write` 里有 `1` 次写撞上了 `0.001` 秒的窗口。Redis 对单键操作没有冻结窗口：逐键 `MIGRATE` 是原子的，键要么在 A、要么在 B，配合 ASK 就能持续服务；代价是迁移期间部分多键操作会返回 `TRYAGAIN`，而且规范提醒，存在大键时在线重分片并不明智，因为 MIGRATE 要锁住两端搬迁整个值。应用层迁移用一个短冻结换取更简单的读写规则，Redis 用逐键原子搬迁和 ASK 协议换取不冻结。

- 本课主要读了 Key distribution model、Hash tags、MOVED Redirection、Live reconfiguration、ASK redirection、Multi-keys operations，以及配置纪元（Cluster current epoch、Configuration epoch、configEpoch conflicts resolution）里与重分片相关的段落。
- 规范**没有**讲一致性哈希、虚拟节点、范围分片或热点键。核心知识点第 1、2 节里这几部分的实验，是教学实现与通用设计讨论，不是对规范的转述。

规范里的定义与结论，本课按以下方式使用。

键分布：16384 个槽，`HASH_SLOT = CRC16(key) mod 16384`，CRC16 为 XMODEM，`"123456789"` 的输出为 `31C3`；集群稳定时，一个槽只由一个节点服务（该节点可以有副本）。Hash tag：键里有 `{`，且其右边有 `}`，两者之间至少有一个字符时，只对花括号之间的子串算槽。

MOVED：节点收到不属于自己的槽的请求时，回 `-MOVED <slot> <endpoint:port>`；客户端应记住这个映射，或者用 `CLUSTER SHARDS`（或已弃用的 `CLUSTER SLOTS`）刷新整张表，因为很可能不止一个槽变了。

Live reconfiguration：加节点、删节点、再平衡都是移动槽；`SETSLOT IMPORTING` / `MIGRATING`、`GETKEYSINSLOT`、原子的 `MIGRATE`，最后 `SETSLOT NODE`。MIGRATING 状态下，源节点只处理已存在的键，其余用 ASK 交给目标，因此不再在源上创建新键。

ASK：只重定向下一条请求，先发 `ASKING`，不更新槽表；IMPORTING 节点没有收到 `ASKING` 就回 MOVED。多键操作在迁移期间可能 `-TRYAGAIN`。

配置纪元：导入节点完成导入后递增 configEpoch，好让变更传播；重分片时，工具会强制目标把配置纪元提升到集群里最大的值加一，不需要其他节点同意，规范说这是出于性能考虑，因为真实的重分片往往要搬几百个槽。

教学实验与 Redis 实现的差异如下。

- **迁移单位**：Redis 按单个槽迁移；教学引擎把每 2048 个槽合成一个分片，一次搬一个分片。
- **数据搬迁**：Redis 逐键 `MIGRATE`，原子地把键从 A 移到 B，任一时刻一个键只存在于一边；教学引擎先批量**复制**（源上仍保留），再用双写或日志追平，切换后才清理源，所以迁移期间同一个键在两边各有一份，靠版本号保证目标不会回退。
- **新键**：Redis 在 MIGRATING 期间把源上不存在的键用 ASK 交给 B，新键直接建在目标上；教学引擎在切换前所有写都由源处理，新键先建在源上，再随双写或日志进入目标。
- **重定向**：Redis 有 MOVED 和 ASK 两种语义；教学引擎只有 `STALE_ROUTE`（相当于「请刷新路由」）和冻结期间的 `RETRY`，没有「只重定向一次」的 ASK。
- **路由版本**：Redis 用每个节点的 configEpoch 在 gossip 中竞争，最终取最大者；教学引擎用一个全知配置服务的全局 `route_version`，没有 gossip、UPDATE 消息或纪元冲突处理。
- **冻结窗口**：Redis 对单键操作没有冻结；教学引擎在切换前冻结整个分片 `0.001`–`0.002` 秒（虚拟时钟）。
- **其他**：没有副本、故障切换、持久化、`nodes.conf` 与 fsync，也没有 TCP。所有时间都是虚拟时钟上的教学数字。

## 自测题

**题 1.** 迁移完成后，怎样判断「总键数与版本正确」？请用 `dual_write` 和 `copy_then_flip` 的数字说明，为什么只看总键数不够。

<details>
<summary>答案</summary>

要维护一张「最后一次确认写入」的对照表：每次写得到确认时，记下这个键的值和版本。迁移完成后，对每个键查当前路由下的所有者节点，比较它保存的值和版本是否与对照表一致；同时统计所有者节点上的键总数，确认非所有者节点上不再有残留。

`dual_write`：对照表里有 `4060` 个键（4000 个初始键加 60 篇新文章），所有者节点上正好 `4060` 个，`missing_keys=0`、`wrong_version_keys=0`、`keys_on_non_owners=0`，`route_version=2`，分片 0 在 `n4` 上有 `510` 个键、在 `n1` 上为 `0`。总键数和版本都正确。

`copy_then_flip`：所有者节点上有 `4058` 个键，只比应有的少 2 个（拷贝开始后插入的 2 篇新文章），但逐键比较时还有 `13` 个键的版本比最后一次确认的旧，共丢失 `15` 次已确认写入。如果这次迁移期间恰好没有插入新键，总键数会完全一致，而那 13 处版本回退依然存在。所以验收必须同时看总键数和每个键的版本。

</details>

**题 2.** 为什么一致性哈希（以及更多虚拟节点、加机器）不能自动消除热点键？用 `hotkey` 的数字说明，并指出什么办法有效。

<details>
<summary>答案</summary>

一致性哈希和虚拟节点调整的是「每个键落在哪台节点」，目标是让**键数**均衡。热点是**单个键**的访问量过大，而这个键无论怎么哈希，都只映射到环上的一个位置，由一台节点承担它的全部访问。

10000 次访问里有 `4980` 次打在 `article:00042:title` 上。虚拟节点 1 / 16 / 128 时，键数最大份额从 `0.6158` 降到 `0.4163`，再降到 `0.2988`，但访问最大份额是 `0.6084` / `0.5856` / `0.6460`，并没有下降。再加一台 `n5`，键数最大份额降到 `0.2265`，热点键仍在 `n3`，`n3` 的访问份额仍是 `0.6046`。

有效的办法是改数据模型，把一个热点键拆成多个键，让访问分散到多个副本键上。拆成 8 个副本键时，有 6 个落在同一台节点，访问最大份额只降到 `0.5016`；拆成 32 个时降到 `0.3469`。拆分后的键也要经过哈希，副本数太少时一样会撞到一起。实际系统还可以用本地缓存或读副本，但那属于缓存与复制的手段，不是路由层自动完成的。

</details>

**题 3.** 只把路由表（或哈希环）上的分片 0 改到 `n4`，为什么不是无损迁移？双写转发和变更日志分别怎样补上缺口，代价有什么不同？

<summary>答案</summary>

路由只决定请求发往哪里，数据并不会随之移动。`flip_only` 在 `0.101` 把分片 0 改到 `n4`，`n4` 上一个存量键都没有；`0.121` 清理 `n1` 后，原来的 500 个键彻底消失。结果是读请求 `27` 次读不到已确认写入的键，所有者节点上只有 `3715` 个键、应有 `4060` 个，`missing_keys=345`，另有 `14` 个键在 `n4` 上从版本 `1` 重新计数，版本回退。

正确的迁移是：先拷贝存量，再追平增量，最后在短冻结里切换路由，然后才清理源节点。`dual_write` 让源节点在每次写入后同步转发给目标：同期转发 `36` 次，冻结时没有剩余，`0.200` 冻结、`0.201` 切换，窗口 `0.001` 秒；代价是迁移期间分片 0 的写延迟 p50 从 `0.002` 变成 `0.004`。`change_log` 只写本地并记日志：`0.2` 重放 `36` 条，`0.207` 剩 `3` 条时冻结，`0.209` 切换，窗口 `0.002` 秒；写延迟 p50 不变，代价是窗口更长、实现更复杂。两者的验收都是 `4060` 个键、版本全对、读不到和读到旧版本都是 `0`。Redis 用的是第三种做法：逐键原子 `MIGRATE` 加 ASK 重定向，键在任一时刻只在一边，单键操作不需要冻结窗口。

## 本课小结

- 范围分片利于扫描，哈希分片更容易均匀分布。扫描 100 个连续 id，范围碰 `1` 个分片、哈希碰 `8` 个；递增插入 400 个 id，范围 `100%` 落在最后一段，哈希最大份额 `0.13`。Redis Cluster 是哈希槽：`CRC16(key) mod 16384`，`crc16("123456789")=31C3` 已核对。
- 虚拟节点改善键数均衡，不消除热点键。虚拟节点 1 → 128，键数最大份额 `0.6158` → `0.2988`，访问最大份额始终在 `0.58`–`0.65`；加一台节点后热点节点仍有 `0.6046`。把热点键拆成 32 个副本键，访问最大份额降到 `0.3469`。
- 在线迁移要同时迁移路由、数据和版本：路由表带版本，先拷存量，再用双写或日志追平增量，短冻结后切换，最后清理源节点。`dual_write` 和 `change_log` 都得到 `4060` 个键、版本全对，切换窗口分别为 `0.001` 秒和 `0.002` 秒；双写让迁移期间的写延迟 p50 从 `0.002` 变成 `0.004`。
- 只改路由丢数据：`flip_only` 少了 `345` 个键，`27` 次读不到，`14` 个键版本回退。拷完存量不追增量也丢写：`copy_then_flip` 少 `2` 个键、`13` 个键版本回退，总键数只差 2，必须逐键核对版本才能发现。
- Redis 用逐键原子 `MIGRATE`、MIGRATING / IMPORTING 与 ASK / MOVED 实现不冻结的在线迁移，用 configEpoch 决定槽的所有者；教学引擎用全局 `route_version`、批量复制加双写或日志，以及短冻结窗口。两者都是为了保证一个已确认的写在迁移后仍然存在。
- 这些时间都是教学虚拟时钟上的数字，不是生产 RTT。`ShardMigrationEngine` 不是 Redis，也不是 Redis Cluster 客户端；它没有副本、故障切换、gossip 和 TCP，8 个分片是对 16384 个槽的教学归并。
