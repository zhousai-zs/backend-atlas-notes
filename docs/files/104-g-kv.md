## 导读

### 一个直觉：set / get 不是一份完整契约

想象内容后台把「文章 42 的标题」「是否已发布」「这篇稿此刻的阅读计数」放进一套 KV。编辑点保存，实例回了 OK；列表页再读一次，按理该看到完整的新标题。可如果这次写入是按字节往槽里填的，并发读就可能看到半截字符串。如果「键不存在」被当成一次故障而不是一种正常状态，监控会被空键刷爆。如果内存预算只按 value 的字节来算，一百个短标题就会把上限用穿。如果压测报告只写「每秒三十万次」，却不写键有多长、命中率多少、读写各占多少，下一次换了访问模式，这个数字就不能再用。

KV 对外看起来是 `set` / `get` / `del` / `exists` 四件事，真正要验收的是契约：键空间和值上限、不存在时返回什么、并发覆盖谁赢、写成功之后下一次读从哪个点开始可见、TTL 到期后还能否读到、容量满了是拒绝还是淘汰。节点把这件事写成：为高性能 KV 项目建立可验收契约。

### 接上前置

`a-hash` 讲过哈希如何把键映射到槽位，点查询可以做到与键数量近似无关，范围扫描却往往要另做结构。`e-lock` 讲过互斥、持锁范围和死锁。`g-cache` 讲过旁路缓存、TTL 与容量；`g-redis` 和 `g-persistence` 则已经从命令成本和持久化窗口靠近了同一类存储。本课把镜头拉回单机内核本身：先把 set / get / del / exists 的语义、线性化点和容量约定写清楚，再谈索引与锁怎么撑起这些约定。持久化会重新作为权衡出现，但本课不再重复 RDB / AOF 的恢复窗口。

### 一次写入走进 KV 之后

在教学引擎里，一次 `set` 大致走这样一条路径：

1. 用哈希把键映射到某一个分片，只持有这一片的锁（全局锁模式下则持有同一把大锁）。
2. 在锁内分配一个单调递增的序号，这就是本次操作的**线性化点**：序号更晚的读，必须看到这次写，或看到比它更晚的写。
3. 若这把键已经到期，按过期模式决定是立刻删除，还是先打标记、等压缩再删。
4. 按「键字节 + 值字节 + 每条固定开销」计费；超过容量则按约定拒绝或淘汰。
5. 把完整的新值一次性放进哈希槽，更新版本号，然后释放锁。可选的预写日志在这之后才落到文件。

RocksDB 的生产路径不同：写入通常先进入 MemTable，并可选择写 WAL；`Get` 找不到键时返回 `NotFound` 状态，而不是把它当成一次崩溃；删除一个本来就不存在的键也不是错误。默认写是异步的，调用返回只表示数据已经交给操作系统，`WriteOptions.sync = true` 才会等到持久介质。这些句子来自官方 Basic Operations 与 FAQ，本课用教学内核去对齐「可见性、失败语义、容量约定」，而不是去复刻 LSM。

### 教学场景（教学假设）

下面把内容后台的三样东西当作例子：文章标题（会被覆盖、会被读到半截就不合格）、阅读计数（不能在并发下丢更新）、编辑会话令牌（带 TTL，到期后的可见性必须说清）。它们只用于把契约落到一次可运行的实验上。

### 本课三条主线

1. **CRUD 与不存在状态**：空键是正常结果，删除空键要幂等，并发覆盖要定义谁赢，读写要有明确的线性化点。
2. **哈希索引和分片锁**：点查询走哈希槽；不同键可以并行，同一把键必须串行；不要把教学引擎的锁写成 RocksDB 的默认实现。
3. **TTL、容量上限和内存计费**：计费要包含键和元数据；满了是拒绝还是淘汰必须事先写清；TTL 到期后是否立即对读不可见，也是契约的一部分。

## 学习目标

- 能解释 CRUD 与不存在状态：空键返回的是「未找到」而不是一次故障，删除空键仍然成功，覆盖写从哪一个线性化点开始对后续读可见，以及并发下最后写入为何必须是完整值。
- 能独立完成：实现单机 KV 内核，支持 set / get / del / exists，并定义并发覆盖行为；在容量达到上限时按约定拒绝或淘汰，压测数字旁边写清键值大小、命中率和读写比例。

## 为什么后端要懂

内容后台里，标题、发布标记和计数会被高频读写。接口看起来只是「写进去、读出来」，可一旦把空键当成故障、把「回了 OK」理解成「任何并发读都已经看到完整新值」、或把内存预算理解成「value 有多少字节」，线上就会在很普通的访问模式里出错：监控被空键刷掉，读者看到半截标题，或者短键把实例的内存打满。节点把「为什么要懂」写成一句话：为高性能 KV 项目建立可验收契约。后端要先能说出这套存储在不存在、并发、过期和失败时保证什么，才能决定标题路径能不能直接覆盖、计数路径该用比较并交换还是原子递增，以及会话令牌到期后还准不准被读到。

另一面是把压测数字当成契约本身。同一套内核，键从 64 字节换成 1 KiB、命中率从 80% 降到 20%、读多写少换成各一半，数字都会变。官方文档和本课实验都在强调：报告一次性能，必须同时写下键值大小、命中率和读写比例。没有这三项，ops/s 不能在两个场景之间搬用。

## 核心知识点

### 1. CRUD 与不存在状态

先把四件事的返回值写死，再谈并发。RocksDB 的 Basic Operations 把键和值都定义成任意字节数组，`Put` 在键已存在时覆盖旧值，值的大小必须小于 4GB。`Get` 找不到键时返回 `NotFound`——这是一种正常状态，不是异常崩溃。`Delete` 的注释写得很明确：键本来就不存在，也不是错误。FAQ 还确认 `Put` / `Write` / `Get` / `NewIterator` 是线程安全的。多键要一起成功或一起失败，应走 `WriteBatch`，而不是先 `Put` 再 `Delete`、指望两次调用之间进程不会倒下。

教学引擎按同一组语义实现，并用文章标题跑通：

| 操作 | 结果（practice104） |
|---|---|
| 对还不存在的 `article:42:title` 做 `get` / `exists` | 状态是 `not_found`，`exists` 为假 |
| 删除这把还不存在的键 | 状态是 `ok`，`found` 为假（幂等） |
| 第一次 `set` 为 `Weekly digest` | 成功，版本 1，随后 `get` 读到该标题 |
| 再 `set` 为 `Weekly digest (revised)` | 仍成功，但是一次覆盖（`created` 为假），版本 2 |
| 删除后再 `get` / `exists` | 又是 `not_found`，`exists` 为假 |
| 再删一次 | 仍然是 `ok` |

对调用方来说，「从未写过」和「已经被删掉」在接口上可以是同一种 `not_found`。内部若要保留墓碑，那是实现细节，不应泄露成「删除失败」。把空键当异常抛出，是本课首先要挡住的误用。

并发覆盖必须再补两条约定。第一，同一把键上的两个 `set`，后一个线性化点覆盖前一个，并且读到的必须是完整值，不能是前缀。第二，`get` 加 `set` 并不是一次线性化操作：中间的缝隙里，别人可以插进来。

无锁、按字符慢慢写入的对照实现里，80 字节的标题在并发读下被看到 158 次撕裂，样本是 `"A"`、`"AA"`、`"AAA"` 这样的前缀；写完之后最终值是完整的，但过程不合格。换成 `KVEngine` 之后，15 个读线程加上两个写线程（各写 80 次 `A*80` 或 `B*80`）看到的只有这两个完整值，撕裂次数是 0，最终版本是 160，也就是两次写入次数之和。线性化点用序号表示：先 `set` 成 `draft` 的序号是 1，紧接着的 `get` 是 2，读到 `draft`；另一个线程在 `set` 返回之后再 `get`，序号 3 然后 4，读到的是 `published`。

阅读计数把「覆盖语义」和「计数语义」分开。4 个线程各做 100 次「先 `get` 再 `set(+1)`」，期望是 400，naive 路径只剩 100，其余更新被盖掉。同样的 400 次增加，比较并交换（失败就重试，这次重试了 596 次）和锁内 `incr` 都得到 400。标题可以直接 last-writer-wins，计数不行，这就是要把并发覆盖行为写进契约的原因。

### 2. 哈希索引和分片锁

点查询走哈希：键被映射到固定数量的分片，再在该分片的表里查找。优点是单次定位成本低，适合标题、令牌这类按键点读的路径；代价是跨分片的范围扫描要另做结构，教学引擎没有实现按标题排序的全表扫描。

锁也按分片切。不同键若落到不同分片，可以并行改；同一把键必须在同一把锁上排队，这样线性化点和「完整值」才站得住。8 个线程去写同一把热键 1600 次，最终版本正好是 1600，说明同一槽上的覆盖被完全串行化了。

是不是分片一定更快，要看临界区里有没有实际工作。这次实验用 8 个线程写 800 把不同的键（键形如 `article:{i}:title`，约 15 到 17 字节，值 16 字节）：

| 锁模式 | 临界区额外工作 | 耗时 | ops/s |
|---|---|---|---|
| 16 分片 | 无 | 0.0052 秒 | 152809.0 |
| 一把全局锁 | 无 | 0.0056 秒 | 143708.0 |
| 16 分片 | 每次持锁 0.0002 秒 | 0.039 秒 | 20528.8 |
| 一把全局锁 | 每次持锁 0.0002 秒 | 0.2128 秒 | 3760.2 |

在这个 Python 教学内核里，临界区几乎只是改一个字典时，分片锁和全局锁的吞吐非常接近（分片还要多付哈希和多把锁的开销）。一旦每次写入在锁内多做 0.2 毫秒的工作，分片把 800 次写入从 0.2128 秒降到 0.039 秒，大约是全局锁的 5.5 倍吞吐。这是教学对照，用来解释「为什么要分片」，不是生产环境的绝对数字。

RocksDB 默认的 MemTable 是跳表，不是「一张大哈希表加分片锁」。它也提供 `HashSkipList` / `HashLinkList`：先按前缀哈希到桶，桶内再跳表或链表。官方 MemTable 文档写明，这两类哈希 memtable **不支持**并发插入，并发插入只在 skiplist 上默认开启。不要把本课引擎的分片锁，说成 RocksDB 源码里的默认写路径。官方为了保持线性化，并发写入会等到本次插入完成并且序号推进；这与本课「锁内分配序号再改槽」是同一类可见性约定，实现完全不同。

### 3. TTL、容量上限和内存计费

内存不能只按 value 计费。100 个短标题，键 5 字节、值 10 字节，若只数 value，总共 1000 字节；教学引擎每条再加 32 字节的元数据开销，单条 47 字节，一共 **4700** 字节，是只数 value 的 4.7 倍。RocksDB 的内存页面把这件事说得更细：Block cache、索引和 Bloom filter、MemTable、迭代器钉住的 block，都占内存。尤其容易漏的是：索引和过滤器默认不一定计入你给 block cache 设的那个上限，于是「我给了 10GB cache」并不能解释进程为什么用了 15GB。Write Buffer Manager 可以把 MemTable 记进同一份预算，但要显式打开。

容量满了必须先有约定。教学引擎支持两种：

**拒绝。** 单条计费 53 字节，预算 159 字节，正好放下 3 个标题。前三个 `set` 都是 `ok`，第四个状态是 `rejected`，原因是 `capacity`；前三把键还在，第四把不存在。同样大小的覆盖写仍然成功；把已有标题改长以致超出预算，这次覆盖被拒绝，槽里仍是原来的 `hello`。

**淘汰。** 同样的 3 个名额，先写入 1、2、3，再访问 1，于是最久未用的是 2。写入第 4 个标题时淘汰了 `article:02:title`，1、3、4 还在，计费仍是 159。一个比整个预算还大的值会被直接拒绝，原因是 `item_too_large`，**并且不会为了给它腾地方而把已有键删掉**——否则「拒绝」就会附带一次意外的数据丢失。这是契约里要写明的失败语义。

RocksDB 达到内部压力时，更常见的是写停顿或写停止，而不是简单地 evict 一条用户键：immutable memtable 太多、Level-0 文件太多、或待压缩字节太多，都会让写线程入睡甚至无限期堵住。`WriteOptions.no_slowdown = true` 时，写不进去就立刻返回 `Status::Incomplete()`。这是另一份「满了怎么办」的约定，和本课的拒绝 / LRU 淘汰都合法，但不能混着宣传。

TTL 也要写清「到期后读还能不能看到」。教学引擎默认是访问时惰性删除：会话令牌 `draft-token` 的 TTL 是 2.0 秒，1.0 秒时仍读得到，再过 1.5 秒（总共 2.5 秒）`get` 变成 `not_found`，`exists` 为假，计费回到 0。另一种 `compact_lazy` 用来对照 RocksDB `DBWithTTL` 的懒删除：到期后 `get` 仍然返回 `draft-token`，原因记为 `expired_pending`，内存仍占 57 字节（键 14、值 11、开销 32）；调用一次教学版 `compact()` 之后，才变成 `not_found`，内存归零。官方 TTL 的语义是：插入的数据至少保留 ttl 秒，过期条目在 compaction 时删除，**在此之前 Get / Iterator 仍可能返回它们**。不要把「TTL=2 秒」理解成「2 秒后任何读都一定看不到」。

节点的权衡是：内存索引快，但容量受内存限制；加上持久化能在进程退出后找回数据，同时提高写入成本。400 次写入，键 16 字节、值 64 字节：

| 路径 | 耗时 | 单次 | 恢复 |
|---|---|---|---|
| 只改内存 | 0.0012 秒 | 3.0 微秒 | 进程一退就没有 |
| 追加 WAL，只 `flush` 不 `fsync` | 0.0028 秒 | 6.9 微秒 | 这次重放了 400 条、36800 字节，首尾都正确 |
| 每次 `fsync` | 0.0553 秒 | 138.2 微秒 | 同样找回 400 条，耗时约是只改内存的 46.1 倍 |

这些数字只描述这次教学日志，不是 RocksDB WAL 的官方延迟。上一课已经讲过：`flush` 不等于掉电后还在。本课只借用这条对照，说明「要恢复，就要付写入成本」。

最后是压测契约。节点的误区写得很硬：性能测试必须明确键值大小、命中率和读写比例。同一套教学内核上的五组对照：

| 工作负载 | 键 / 值 | 声明命中率 | 读写 | 其它 | ops/s |
|---|---|---|---|---|---|
| A | 16 / 64 | 80% | 90% 读 / 10% 写 | 无额外未命中代价，20000 次 | 298042.2 |
| B | 16 / 1024 | 80% | 同 A | 只把值改成 1 KiB | 290017.5 |
| C | 16 / 64 | 80% | 50% / 50% | 写更多 | 205236.6 |
| D | 16 / 64 | 80% | 同 A | 未命中额外停 0.2 毫秒，8000 次 | 49676.3 |
| E | 16 / 64 | **20%** | 同 A | 同样的 0.2 毫秒未命中代价 | 19357.3 |

A 和 B 在纯内存、且未命中也不额外停顿时几乎一样快，可它们不是同一份契约：值已经从 64 字节变成 1 KiB。一旦未命中要付出 0.2 毫秒（用来模拟一次轻量 IO），声明命中率从 80% 降到 20%，吞吐就从 49676.3 降到 19357.3。E 的实际 `get` 命中率是 0.308，高于声明的 0.20，因为一部分本来按「未命中键」去写的请求，后来又被读到了——这正好说明，报告里既要写声明的工作负载，也要写实际观察到的命中率。没有这些参数，就不要把「大约三十万 ops/s」单独拿去比较。

### 把三条主线串在同一次发布上

编辑保存文章 42：`set` 标题是一次覆盖写，线性化点之后列表页必须读到完整的新标题，而不是半截字符串。阅读计数走 `incr` 或比较并交换，而不是 `get` 再 `set`。若这是一枚 2 秒过期的编辑令牌，还要写清到期后 `get` 是立即 `not_found`，还是等到压缩才消失。内存预算按键 + 值 + 开销来计，满了按事先选好的拒绝或淘汰处理；任何一张「有多快」的表，旁边都要写键有多长、命中率多少、读写各占多少。

### 三条主线的收束

- CRUD：空键是 `not_found`，删除空键是 `ok`，覆盖从明确的序号开始可见，完整值、比较并交换和原子递增，是三种不同的并发约定。
- 索引与锁：哈希服务点查询；分片锁在临界区有实际工作时拉开差距；同一把键仍然串行。RocksDB 默认不是这样实现的。
- 计费、容量、TTL 和压测参数，决定这套内核在满载、到期和被别人引用数字时还能否对上契约。

## 常见误区

- 把 `get` 的空键当成一次故障，或把删除空键当成失败。官方语义里它们都是正常结果。
- 认为「`set` 返回了」就等于任何并发读都已经看到完整新值，或认为 `get` 再 `set` 可以拿来做计数。前者要靠线性化点，后者在这次实验里把 400 次增加做成了 100。
- 只按 value 字节做内存预算，或默认「满了会自动淘汰」却没写淘汰谁。只数 value 会把 4700 看成 1000；超大写入若先淘汰再拒绝，会把已经在线的标题一并删掉。
- 以为 TTL 到期后读一定看不到。RocksDB 的 TTL 在 compaction 之前仍可能返回过期条目；本课的 `compact_lazy` 对照里，到期后读到的仍是 `draft-token`。
- 性能测试只报一个 ops/s，不写键值大小、命中率和读写比例。A 和 B 数字接近，并不表示 64 字节和 1 KiB 是同一类负载；D 和 E 才把命中率的差别打出来。
- 把教学引擎的分片锁或惰性 TTL，直接说成 RocksDB 的默认行为。

## 设计权衡

- **覆盖写 vs 比较并交换 / 原子递增。** 标题这类「最后一版即真相」可以用 last-writer-wins，实现简单、吞吐也好说。计数和「只有版本匹配才许改」必须把读改写收成一次线性化操作，否则会丢更新。代价是重试次数（这次是 596）或把逻辑放进锁内。
- **全局锁 vs 分片锁。** 全局锁容易推理；分片锁在临界区有工作时能拉开吞吐（0.2128 秒对 0.039 秒），但要约定锁顺序，淘汰路径还可能触及多把分片锁。临界区很短时，收益可能被哈希和锁开销吃掉。
- **拒绝 vs 淘汰。** 拒绝保住已有数据、让调用方立刻收到失败，适合不能悄悄丢掉已发布标题的路径。淘汰能让新写入继续，但必须定义谁被踢掉，以及「一条放不进去的超大值」可不许附带误删。RocksDB 还有第三种：写停顿或返回 `Incomplete`。
- **访问时删除 vs 压缩时删除。** 前者读路径更干净，到期后内存也可以马上回来；后者把清理成本移到后台，但读可能看到过期值，内存也不会立刻下降。
- **内存索引 vs 持久化。** 只改内存时一次写入 3.0 微秒，加每次 `fsync` 的日志就变成 138.2 微秒，并且仍要面对上一课已经讲过的掉电窗口。需要恢复，就要把这份成本写进延迟预算。

9. 五组写明参数的工作负载，加上只改内存 / 写 WAL / 每次 `fsync` 的成本。

### 步骤 4：对照验收标准

```

# set 成 draft 的序号是 1，随后 get 是 2，读到 draft。
# 另一个线程在 set 返回之后再 get，序号 3 然后 4，读到 published。
# 同一把键上 160 次完整覆盖没有撕裂；热键 1600 次写入的最终版本是 1600。

# 改长超出预算同样被拒绝，槽里仍是 hello。

```

### 步骤 6：和生产引擎的对应关系（不要记错边界）

| 本课教学概念 | 可对照的官方路径 | 不要说成 |
|---|---|---|
| `not_found` / 删除空键为 `ok` | `Get` 的 `NotFound`；`Delete` 在键不存在时仍成功 | 空键等于一次 IO 错误或进程故障 |
| 锁内分配序号再改槽 | 写入推进 sequence number、保持线性化 | 本课实现了 RocksDB 的 write thread / WAL 组提交 |
| 哈希分片 + 分片锁 | HashSkipList / HashLinkList 按前缀分桶；默认 skiplist 才支持并发插入 | 分片锁就是 RocksDB 默认写路径 |
| 访问时删除的 TTL | 一种常见的内存 KV 约定 | RocksDB `DBWithTTL` 的默认行为 |
| `compact_lazy` | TTL 文档：过期项在 compaction 时删除，此前 Get 仍可能读到 | 本课的 `compact()` 等于生产里的 leveled compaction |
| 拒绝 / LRU 淘汰 | 应用层容量约定；RocksDB 更常见的是写停顿或 `Incomplete` | 「RocksDB 满了会 LRU 掉用户键」 |
| 每条 32 字节开销 | 官方内存组成：cache、index/filter、memtable、pinned blocks | 32 就是 RocksDB 每条记录的真实开销 |
| WAL + `fsync` 的 138.2 微秒 | Basic Operations 里 `WriteOptions.sync` | 这是生产 WAL 的官方延迟 |

## 源码与文档阅读

节点指定的资料是 [KV语义、索引与并发：参考文档 / 原始资料](https://rocksdb.org/docs/)（rocksdb.org，英文文档）。2026-11-12 访问该 URL 返回 200，页面会跳转到 [Getting started](https://rocksdb.org/docs/getting-started.html)；该页写明完整文档在 [GitHub wiki](https://github.com/facebook/rocksdb/wiki)。阅读时按页面上实际出现的内容来，不要把本课实践里的 158 次撕裂、4700 字节或 298042.2 ops/s 写成这些文档里的原句。

与本课直接对应、且已核对过的要点：

1. **CRUD 和不存在状态。** [Basic Operations](https://github.com/facebook/rocksdb/wiki/Basic-Operations) 把键和值定义为任意字节数组，`Put` 覆盖已有值，`Get` 用状态表示成功或 `NotFound`，值必须小于 4GB。头文件对 `Delete` 的说明是：键不存在也不是错误。[FAQ](https://github.com/facebook/rocksdb/wiki/RocksDB-FAQ) 确认基本读写是线程安全的。多键原子更新走 `WriteBatch`。默认写是异步的，`WriteOptions.sync = true` 才会等到持久介质。
2. **索引与并发。** [MemTable](https://github.com/facebook/rocksdb/wiki/MemTable) 写明默认结构是 skiplist，哈希 memtable 用前缀哈希降低比较次数，但跨前缀扫描很贵，且哈希 memtable 不支持并发插入。不要把「哈希索引」理解成「一定配分片锁」，也不要把本课的锁写成官方默认实现。
3. **TTL、内存计费与容量。** RocksDB 的 TTL 保证数据至少保留 ttl 秒，过期删除发生在 compaction，此前读仍可能看到旧条目。[Memory usage in RocksDB](https://github.com/facebook/rocksdb/wiki/Memory-usage-in-RocksDB) 把内存拆成 block cache、索引和过滤器、MemTable、迭代器钉住的块，并提醒索引过滤器默认未必计入 cache 上限。[Write Stalls](https://github.com/facebook/rocksdb/wiki/Write-Stalls) 描述 memtable、Level-0 和待压缩字节触发的减速或停写，以及 `no_slowdown` 立刻返回 `Incomplete`。

建议的阅读方法：先打开 docs 入口和 Getting started，再读 Basic Operations 里 `Get` / `Put` / `Delete` / `WriteBatch` / `sync` 那几节，用手写出「空键、覆盖、删除空键、写成功后的可见性」四行约定。然后读 MemTable 的类型对照表，标出「谁支持并发插入、谁适合点查询」。最后读内存组成和写停顿，把「预算里到底包含什么」和「满了是停住、拒绝还是淘汰」写成可验收的句子。对照 `bash test.sh` 的输出，看哪一组数字在模拟哪一条。记录：访问日期 2026-11-12、实际打开的 URL，以及你亲自跑过的实验输出。

阅读时还应注意这些页面写了、但本课实验没有用数字去覆盖的边界，避免把「没做」当成「文档没说」。文档还谈到 `PinnableSlice`、`SingleDelete` 的使用限制、列族、快照读、Merge 操作符、unordered_write，以及 Write Buffer Manager 跨列族共享预算。这些都是官方路径，本课既没有在教学引擎里实现它们，也没有在 `results.json` 里给出对应数字。

边界：教学实验只模拟已核对、并且已经跑出数字的那一部分语义。不确定的地方，应写「文档未覆盖」或「本课未实验」，而不是用教学输出去填空。

## 自测题

下面三道题都可以用 practice104 里的数字来回答，不必默写定义。若某一问只能说出「KV 就是 set/get」，却对不上 `not_found` 与删除空键的 `ok`、158 与 0、100 与 400，或 4700 与 1000，说明还要回到对应的对照表。

**题 1**：对还不存在的 `article:42:title` 做 `get`、`exists` 和 `delete`，教学引擎各返回什么？覆盖写成 `Weekly digest (revised)` 之后版本是多少？为什么空键不应当成故障？无锁慢写为什么会被读到 `"A"`、`"AA"` 这样的前缀，而 `KVEngine` 的撕裂次数是 0？`set` 返回之后再 `get`，序号 3 和 4 说明了什么？为什么 4 个线程各加 100 次，`get`+`set` 只剩 100，比较并交换和 `incr` 却是 400？

<details><summary>答案</summary>

- `get` 的状态是 `not_found`，`exists` 为假；`delete` 的状态是 `ok`，`found` 为假。第一次写入后版本是 1，覆盖后版本是 2，标题变成 `Weekly digest (revised)`。再删除又回到 `not_found`，再删一次仍是 `ok`。
- RocksDB 把 `NotFound` 写成一种正常状态，删除不存在的键也不是错误。把空键当故障，会把正常的未命中记成事故。
- 无锁实现按字符填写 80 字节标题，并发读看到了 158 次撕裂，样本就是这些前缀。`KVEngine` 在分片锁内一次性放入完整字符串，读到的只有完整的 `A*80` 或 `B*80`，撕裂 0 次，最终版本 160。
- 序号是线性化点：`set` 在序号 3 返回后，后续 `get` 的序号是 4，必须读到 `published`（或更晚的值），不能再回到这次写之前。
- `get` 和 `set` 是两次线性化操作，中间会丢更新，400 次增加只留下 100。比较并交换失败就重试（这次 596 次），`incr` 在锁内完成读改写，两种都得到 400。标题可以用 last-writer-wins，计数不行。

</details>

**题 2**：哈希分片解决的是哪类访问？8 个线程写 800 把不同的键时，为什么「临界区几乎无工作」和「每次持锁 0.2 毫秒」两张表不能得出同一个结论？同一把热键写 1600 次，为什么最终版本正好是 1600？为什么不能把这套分片锁说成 RocksDB 的默认实现？

<details><summary>答案</summary>

- 哈希分片服务的是点查询：先由键定位到分片，再在该表里找。它不自动提供有序的范围扫描。
- 临界区几乎无工作时，分片是 152809.0 ops/s、0.0052 秒，全局锁是 143708.0 ops/s、0.0056 秒，二者接近，分片还要付哈希和多把锁的开销。每次持锁再做 0.2 毫秒工作后，分片是 0.039 秒、20528.8 ops/s，全局锁是 0.2128 秒、3760.2 ops/s。分片的收益出现在锁内有实际工作、且不同键能并行的时候，不能用第一张表宣称「分片一定更快」。
- 同一把键落到同一分片，1600 次写入完全串行，版本累加到 1600，没有把两次覆盖合成一个撕裂值。
- RocksDB 默认 MemTable 是 skiplist，哈希 memtable 不支持并发插入。本课的分片锁是教学模型，用来把「不同键并行、同一键串行、锁内分配序号」跑出数字，不是官方默认写路径。

</details>

**题 3**：100 个短标题如果只按 value 计费会得到多少，教学引擎实际记了多少？预算 159 字节时，拒绝策略下第四个标题和「改长」各发生什么？淘汰策略淘汰了哪一把键，超大值被拒绝时工作集为什么还在？TTL 设为 2.0 秒后，访问时删除和 `compact_lazy` 对 `draft-token` 的可见性有什么差别？为什么 A 和 B 的 ops/s 接近，仍然不能省略键值大小，D 和 E 又说明了命中率什么？只改内存 3.0 微秒、每次 `fsync` 138.2 微秒，对应哪一条权衡？

<details><summary>答案</summary>

- 只数 value 是 1000 字节；计入 5 字节键和 32 字节开销后，单条 47、一共 4700，是前者的 4.7 倍。
- 拒绝策略下第四个 `set` 是 `rejected`，已有三把键仍在；同样大小的覆盖成功，改长超出预算被拒绝，标题仍是 `hello`。淘汰策略在写入第四把时淘汰了最久未用的 `article:02:title`，1、3、4 还在，计费 159。超大值先按「单条已超过预算」拒绝，原因是 `item_too_large`，计费仍是 159，不会先清空工作集再失败。
- 访问时删除：到期后再读是 `not_found`，内存回到 0。`compact_lazy`：到期后 `get` 仍返回 `draft-token`，占 57 字节，`compact()` 删掉 1 条之后才变成 `not_found`。这与官方 TTL「compaction 前仍可能读到过期值」是同一类约定。
- A 是 16/64、80% 命中、90% 读，298042.2 ops/s；B 只把值改成 1 KiB，290017.5 ops/s。纯内存且未命中也不额外停顿时，二者接近，但契约已经变了，报告必须写明值长度。加上 0.2 毫秒未命中代价后，命中率 80% 的 D 是 49676.3 ops/s，20% 的 E 是 19357.3 ops/s，命中率会改写结论。
- 内存索引快，但进程一退数据就没有；要恢复就要付写入成本。400 条日志、36800 字节可以重放找回，每次 `fsync` 的耗时大约是只改内存的 46.1 倍。

</details>

## 本课小结

- KV 不只是 set / get。空键是 `not_found` 而不是故障，删除空键是 `ok`，覆盖从明确的线性化点对后续读可见。无锁慢写撕开了 158 次标题，教学内核撕裂 0 次；`get`+`set` 把 400 次计数做成 100，比较并交换和 `incr` 都是 400。
- 哈希索引服务点查询，分片锁让不同键在临界区有工作时并行（0.039 秒对 0.2128 秒），同一把键仍然串行到版本 1600。这是教学模型，不是 RocksDB 默认的 skiplist 写路径。
- 计费要包含键和开销（4700 对 1000）。满了就按约定拒绝或淘汰：第四把键被拒绝，或淘汰 `article:02:title`；超大值不得顺手清空工作集。TTL 到期后是否还能读到 `draft-token`，取决于惰性删除还是等到压缩。压测必须写明键值大小、命中率和读写比例（A 298042.2，命中率降到 20% 且未命中有代价时是 19357.3）。内存索引快（3.0 微秒），每次 `fsync` 的日志是 138.2 微秒，才能在重放后找回 400 条。

学完后可以用三句话自检：空键和删除空键返回什么，线性化点之后读到的是不是完整新值，为什么计数不能用 `get`+`set`；分片锁在什么条件下比全局锁快，为什么不能把它说成 RocksDB 默认实现；4700 和 1000 差在哪里，拒绝和淘汰各怎样处理第四把键和超大值，TTL 的两种可见性以及 A 到 E 为什么必须带上工作负载参数。三句都能答上来，并且能指出 practice104 里对应的那组数字，这一课就算过关。

如果有一句答不上来，先回到对应的实验表，再回到官方文档里关于 `NotFound`、删除空键、MemTable 类型、TTL 在 compaction 前仍可能可见、内存组成和写停顿的那几句，不要只把「KV 就是 set/get 很快」这句话背下来。

写作笔记时顺便记下三件事：你核对文档的日期和实际打开的页面，这套存储的空键、并发覆盖、TTL 和满容约定有没有写成可验收的句子，以及压测数字旁边是否写了键值大小、命中率和读写比例。这三件事能把本课的边界说明带进后面的 KV 与存储引擎课，而不是只留下一串 ops/s。
