## 学习目标

1. 说明时间窗口、采样间隔和缺口的含义，以及如何与变更事件对齐。
2. 独立完成实践：提供 CPU、在途、延迟等指标，让 Agent 选择下一项验证（本次选择 `lock_wait_ms`）。
3. 结论明确区分观察和推断；不把缺采样当作零负载。

## 为什么后端要懂

一张图上两条线一起涨，最省事的说法是「所以 A 导致了 B」。缺了一个点看起来像「这一分钟负载掉到 0」，也会把自动告警带跑。诊断要先把观察写对，再单独写下假设和还需要的验证。

## 核心知识点

### 1. 缺采样不是 0，观察不是推断

**直觉。** 没有点，就没有测量；不要用 0 去填。

**原理。** 序列步长 60 秒。16:00–16:02、16:04–16:05 有点，**16:03 没有点**。若按「缺口填 0」来画，p99 会在 16:03 变成 0——这是反例，不是本课采用的序列。诚实的 `query_range` 把 `2026-11-15T16:03:00Z` 放进 `missing_ts`，点列里没有这个时间戳。报告的 observations 写明：「这是缺失采样，不是测到的零负载」。

观察与推断分开写。观察包括：p99 从 12ms 升到 110ms、in_flight 从 3 升到 21、cpu 在 18–22%、`lock_wait_ms` 从 1ms 升到 55ms、15:59 有一次 kv 2.0 发布、16:05:30 有回滚。推断单独成段，并带 `not_causation=true`：这些现象**与锁竞争相符，但不是证明**；发布在时间上对齐，只是候选因素。

### 2. 下一项验证由证据选择，而不是一次讲完根因

**直觉。** 先看 p99，下一步应该去验证哪个假说，而不是直接结案。

**原理。** 脚本化 Agent 在看到延迟和在途上升后，下一步查询 `lock_wait_ms`（而不是先给 CPU 或发布下结论）。CPU 峰值低于 40%，不支持「计算热循环已经打满」的说法。若要继续，应在 16:01–16:04 附近看追踪或锁剖析——那是建议的下一步，本课没有运行真实 profiler。

Prometheus 的查询基础文档强调区间、步长与无数据时的行为。本课用本地 JSON 复现「步长」和「缺口」，没有连接 Prometheus 服务器。

## 常见误区

- 单张图上的同时上涨就判定因果。
- 把缺失点当成 0，引出「负载突然掉光又恢复」的假故事。
- 只展示与假设相符的指标，不写还需要什么验证。
- 把本机脚本耗时或合成曲线当成生产容量结论。

## 设计权衡

自动相关和异常检测能节省时间，但必须保留不确定性，并给人（或下一个工具）留下反证路径。合成数据适合练习流程，不能代替线上指标。

## 自测题

**1. 16:03 没有点，能不能在图上画成 0 并说「那一分钟没有负载」？**

答：不能。那是缺采样。本次 `missing_ts` 含该时刻，点列中没有 0 值填充；「填 0」只作为反例计算。

**2. p99、在途和 lock_wait 一起上升，为什么还不能写「根因就是锁」？**

答：这是相符的观察，不是因果证明。发布事件也在邻近时间。报告把该判断放在 inference，并要求下一步做追踪或锁剖析。

**3. 为什么下一步选 `lock_wait_ms` 而不是直接怪 CPU？**

答：CPU 只在 18–22%。在延迟和在途上升之后，更应对锁等待做验证，而不是把最常见的「CPU 打满」故事套上去。

## 本课小结
