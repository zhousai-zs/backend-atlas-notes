# 第 155/208 课：灰度发布与回滚

> 序号 155/208 · id `j-release` · 领域 J · 阶段 4 · 难度 深入 · 子类 交付与安全
> 前置：[`j-kubernetes`](https://zhousai-zs.github.io/backend-atlas-notes/lessons/154.html) 和 [`j-metrics`](https://zhousai-zs.github.io/backend-atlas-notes/lessons/150.html)
> 节点摘要：小流量灰度通过指标与版本对照控制变更风险；数据库和协议变化必须支持回退窗口。

## 导读

上一课在滚动替换时统计了请求失败。灰度更进一步：只让一小部分流量看到新版本，用对照指标决定继续还是回滚，并且回滚后还要找得到旧产物。应用进程可以退回去，并不意味着数据迁移也能撤销。

教学假设：一次配置变更以 5% 流量进入金丝雀实例，并被注入延迟退化。以下路由、指标阈值和产物命名均为教学设计，不代表腾讯或微信内部实现。没有使用生产流量。`is_live_prod_traffic=false`。

## 学习目标

1. 解释金丝雀指标及适用边界
2. 独立完成实践：为配置变更设置 5% 流量灰度，注入延迟退化触发回滚。

## 为什么后端要懂

节点给出的理由是「把故障影响限制在可控范围。」若新版本直接接到全部流量，发现问题再撤，影响面已经铺开；小流量对照可以在更低成本下得到「要不要继续」的证据。

## 核心知识点

### 1. 金丝雀指标

**原理。** Google SRE Workbook 第 16 章把 canarying 定义为：把一次变更做部分、有时限的部署并加以评估，再决定是否继续放量。接受变更的部分称为 canary，其余称为 control。其逻辑是金丝雀通常只覆盖生产中小得多的一部分。该章示例按应用版本查看 HTTP 响应码，并在金丝雀指标相对对照组偏离过大时自动反应。

**直觉。** 要比较的是同一指标在两个版本上的差异，而不是只看全站平均数——全站会被 95% 的旧流量稀释。

**实践对照。** 200 次请求中 10 次进入 v2（观察份额 0.05）。教学 p99：v1 为 6.619 毫秒，v2 为 130.082 毫秒，阈值 50 毫秒，决策为 rollback。这些 p99 是本机短时样本，使用与第 150 课相同的教学分位算法，不是生产 SLO 测量。

### 2. 自动停止条件

**原理。** 工作手册指出，可以把部署调成根据版本错误率等指标自动反应。停止条件必须预先写清：用哪项指标、对照谁、阈值多少、以及触发后做什么。

**实践对照。** 本课停止条件是金丝雀 p99 高于 50 毫秒即回滚到 v1，并停止向 v2 派发。回滚后另发 40 次请求，全部由 v1 处理。阈值和 5% 份额都是教学参数。

### 3. 向后兼容迁移

**原理。** 应用回滚恢复的是可执行文件或配置，不自动撤销已经发生的数据写入。节点陷阱也提醒：不能认为应用回滚能撤销所有数据迁移。因此迁移需要向后兼容窗口，或单独的数据回退方案。

**实践对照。** v2 在处理请求时写入 `reports/migration.dat`（`schema=v2-migrated`）。应用回滚后该文件仍在。旧版本产物 `artifacts/v1-f77f0c83ccd13890.json` 可按路径和 SHA-256 `f77f0c83ccd138902e35ede298d15d9ef14dafe9e5855ccf15ad290f609ff2a4` 定位；灰度期间 v1 与 v2 同时运行。

## 常见误区

1. **认为应用回滚能撤销所有数据迁移。** 节点原句即此。本课迁移文件在回滚后仍然存在。若新版本已经改写存储格式，只把进程换回 v1 可能无法读取或留下半迁移状态。
2. **把全站延迟当作金丝雀指标。** 5% 的高延迟会被 95% 的对照组稀释；必须按版本切开，如本次分别计算 v1 与 v2 的 p99。

## 设计权衡

节点原句是「小流量更安全，但低频故障可能需要更长观察。」5% 降低了爆破半径，但对于只在特定用户或特定键上出现的缺陷，短窗口可能看不见。拉长观察会增加并行运行两个版本的成本，也拉长了不确定期。

## 动手实践

实践目录为 `practice155/`，需要 Python 3。本次为 CPython 3.13.5。

```bash
cd practice155
bash test.sh
cat results.json
ls artifacts
cat reports/migration.dat
```

脚本同时启动 v1 与注入延迟的 v2，按 5% 分流，计算分位并在超阈值时回滚。成功最后一行为 `ALL_CHECKS_PASSED`。延迟数字依赖本机调度，读者应以自己的 `results.json` 为准。

两项验收是「回滚产物可定位」以及「新旧版本可同时运行」。前者对应 `artifacts/v1-…json` 及其摘要；后者对应灰度期间两份进程同时提供服务。

## 自测题

1. **为什么金丝雀指标要按版本切开？** 小份额异常会被对照组稀释。本课若只看全站平均，130 毫秒的金丝雀会被 95% 的 6.6 毫秒流量掩盖。
2. **回滚后为什么还要保留旧产物摘要？** 验收要求回滚产物可定位，才能确认退回去的是哪一份已知配置，而不是「现在机器上碰巧还在的文件」。
3. **迁移文件还在，是否说明回滚失败？** 不说明。应用回滚已经停止把流量打到 v2，但数据侧效果需要单独处理。
