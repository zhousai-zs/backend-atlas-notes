# 第 4/208 课：操作系统的资源抽象

> 节点：`a-os` · 域：A · 子类：硬件与操作系统 · 难度：入门 · 前置：`a-machine`
>
> 一句话：操作系统把 CPU、内存与设备抽象成进程、地址空间和文件，并保护不同程序。

## 1. 学习目标与为什么后端要懂

完成本课后，你应该能够：

1. 解释用户态与内核态的区别，以及程序为什么需要系统调用。
2. 用进程查看器观察两个程序，追踪它们的文件和内存映射。
3. 说明系统调用与普通函数的区别。
4. 描述进程隔离的目标，以及这种隔离为什么不是“零成本”的。

后端工程师每天写的代码，最终都要落到进程、地址空间和文件描述符上。以微信公众号后台服务为例：

- **进程崩溃隔离**：某个 worker 进程因为空指针或未捕获异常退出时，其他 worker 仍应能继续服务。这依赖操作系统为每个进程提供独立的地址空间和故障边界。
- **文件描述符耗尽**：每个客户端连接、日志文件、管道和数据库连接都会占用文件描述符。泄漏到上限后，`accept()` 可能失败，表现为“服务还在，但新连接进不来”。
- **系统调用开销**：高并发路径上频繁 `read`、`write`、`epoll_wait`、`futex`，会把大量时间花在用户态与内核态之间。理解边界，才知道何时该批量化、缓冲或减少无谓调用。
- **资源受限**：CPU、内存、文件描述符、进程数都不是无限的。操作系统既提供抽象，也负责执行限额和保护。

本节不要求你背内核源码，而是建立一张“程序如何被操作系统托管”的 mental model，并能用 Linux 工具验证它。

## 2. 先建立直觉：操作系统是资源抽象层，也是保护者

裸机上只有 CPU、内存和各类设备。如果每个程序都直接操作硬件，会立刻遇到三个问题：

1. **程序怎么写**：不同磁盘、网卡、终端的操作方式不同，业务代码不可能逐一适配。
2. **资源怎么分**：多个程序同时运行，谁拿 CPU、谁用哪段内存？
3. **程序怎么互相保护**：一个程序写坏内存，不能把另一个程序或内核一起写坏。

操作系统的做法是“抽象 + 保护”：

| 硬件资源 | 操作系统抽象 | 典型接口 | 观察方式 |
| --- | --- | --- | --- |
| CPU | 进程 / 线程 | 调度、阻塞、唤醒 | `ps`、`top` |
| 内存 | 虚拟地址空间 | `brk`、`mmap`、页表 | `/proc/<pid>/maps` |
| 磁盘、网络、终端等设备 | 文件 / 文件描述符 | `open`、`read`、`write`、`close` | `/proc/<pid>/fd`、`lsof` |

可以把操作系统想成一个既提供“标准插座”，又负责“门禁和配电”的平台：业务程序通过统一接口使用资源，但不能绕过规则直接操纵硬件。

## 3. 用户态与内核态

### 3.1 直觉：两种权限级别

CPU 通常提供不同的特权级别。简化地说：

- **用户态**：普通应用程序运行的状态。不能直接执行特权指令，不能随意访问内核内存或设备寄存器。
- **内核态**：操作系统内核运行的状态。可以管理页表、中断、设备和进程调度。

程序想读文件、发网络包、申请内存、创建进程时，不能自己在用户态“硬来”，而要通过**系统调用**请求内核代办。

### 3.2 原理：一次系统调用发生了什么

以 `read(fd, buf, len)` 为例，简化路径是：

1. 用户程序调用 C 库或其他运行时提供的包装函数。
2. 包装函数准备系统调用号与参数，执行专门的陷入指令，CPU 从用户态进入内核态。
3. 内核检查文件描述符是否有效、缓冲区地址是否属于该进程、长度是否合法，然后执行实际读取。
4. 内核把结果放回用户缓冲区，恢复用户态继续执行；失败时通常返回 `-1` 并设置 `errno`。

伪代码：

```c
ssize_t n = read(fd, buf, len);
if (n < 0) {
    perror("read");
}
```

这里的关键不是“`read` 是一个函数名”，而是它背后跨越了保护边界。**普通函数调用发生在同一特权级、同一地址空间内；系统调用则要进入内核，由内核代表进程完成受保护操作。**

### 3.3 节点关键提醒：进入内核态不等于进程切换

这是本节点明确指出的误区：

> 用户态切换到内核态不必然发生进程切换。

同一个进程调用 `read` 进入内核，读完文件后可以继续返回该进程执行。此时发生了“特权级切换”，但没有发生“换另一个进程上 CPU”。进程切换需要调度器决定让另一个任务运行，可能由时间片中断、阻塞的系统调用或更高优先级任务触发，但它不是每次系统调用的必然结果。

可以用下面的命令建立初步观察：

```bash
ps -eo pid,ppid,stat,rss,cmd --sort=-rss | head
top -p <pid>
strace -c -f <program>
```

- `ps` 看进程身份、父子关系、状态和内存占用。
- `top` 动态看 CPU 与内存，并观察进程是否在睡眠或运行。
- `strace -c` 汇总系统调用次数和耗时，适合判断“时间花在哪些内核接口上”。

`strace` 会带来额外开销，适合短时间诊断，不应长期挂在高流量生产进程上。

## 4. 虚拟化、并发和持久化

操作系统的三大抽象可以对应三个问题：CPU 怎么被“独占”，内存怎么被“独占”，数据怎么在进程退出后仍然存在。

### 4.1 CPU 虚拟化：进程以为自己独占 CPU

**直觉**：一台机器同时运行很多进程，但每个进程都像是自己有一块 CPU。

**原理**：操作系统通过调度器在可运行任务之间切换，给每个任务分配时间片。进程有运行、可运行、睡眠等状态；发生阻塞系统调用时，进程让出 CPU；时间片用完时可能被抢占。切换任务需要保存和恢复寄存器、栈指针等上下文，这就是上下文切换成本。

**后端例子**：一个服务用多个 worker 进程处理请求，可以让多核并行；但如果 worker 数量远超 CPU 核数，大量时间会耗在调度和切换上。线程池大小、进程数量和阻塞行为要一起看，不能只看“并发数”。

### 4.2 内存虚拟化：每个进程看到自己的地址空间

**直觉**：两个程序都可以使用看似相同的地址，却互不干扰。

**原理**：程序使用的是虚拟地址，CPU 通过页表把虚拟地址翻译成物理地址。操作系统为每个进程维护独立的地址空间，并设置读、写、执行权限。虚拟内存还允许按需装入页面，因此“虚拟大小”不等于“已经占用的物理内存”。

查看某个进程的映射：

```bash
cat /proc/<pid>/maps
```

输出中的每一行通常包含地址范围、权限、偏移、设备、inode 和路径。下面是结构示意，真实地址和文件会变化：

```text
<start>-<end> r-xp 00000000 fd:01 12345 /usr/bin/python3
<start>-<end> rw-p 00000000 00:00 0      [heap]
<start>-<end> rw-p 00000000 00:00 0      [stack]
<start>-<end> r-xp 00000000 00:00 0      [vdso]
```

可以重点看：

- `r-xp`、`rw-p`：可读、可写、可执行、私有映射等权限。
- 文件路径：哪些代码和共享库是文件映射进来的。
- `[heap]`、`[stack]`：堆和栈区域。
- 同一共享库可能以只读代码段形式映射到多个进程，物理页可由内核共享；但每个进程的虚拟地址空间仍然是独立的。

**后端例子**：`ps` 中的 `VSZ` 很大不一定代表马上耗尽物理内存，`RSS` 才更接近当前驻留的物理页规模。排查内存问题时，两者要结合 `/proc/<pid>/maps`、实际分配行为和系统内存压力一起看。

### 4.3 并发：抽象制造“独享”，真实资源仍然共享

每个进程有独立地址空间，但所有进程仍然共享同一批 CPU、内存、磁盘和网络设备。操作系统调度这些访问，形成并发执行的效果。

并发带来的核心事实是：**多个执行流可能交错推进**。即使每个进程内部逻辑正确，只要它们共享外部资源，就可能出现竞争、排队和相互影响。进程隔离能阻止一个进程直接改写另一个进程的内存，但不能阻止它占满 CPU、耗尽文件描述符或把磁盘写满。

**后端例子**：一个 worker 进程泄漏文件描述符，其他 worker 可能仍能工作，但整个进程组最终可能因为共享的上限或下游连接池耗尽而一起受影响。隔离降低故障传播范围，不等于消除共享资源风险。

### 4.4 持久化：文件描述符是进程访问持久资源的句柄

**直觉**：程序把文件当作一串可读写的数据，不必关心磁盘块怎么摆放。

**原理**：操作系统用文件系统把设备上的数据组织成文件和目录。进程通过文件描述符访问已打开的文件、管道、终端和套接字。文件描述符本质上是进程文件描述符表中的索引，它指向内核中的打开文件描述，而不是“文件本身”。

查看进程打开了什么：

```bash
ls -l /proc/<pid>/fd
lsof -p <pid>
```

- `/proc/<pid>/fd` 展示该进程的文件描述符及其指向对象。
- `lsof -p <pid>` 可以进一步看到文件类型、路径、套接字等线索。

一个后台服务可能同时持有：

- 标准输入、标准输出、标准错误；
- 日志文件；
- 监听套接字和已建立连接的套接字；
- 与数据库、缓存、消息队列的连接；
- 管道、事件通知描述符等。

**文件描述符耗尽的典型链路**：代码在异常路径忘记关闭连接 → 进程 fd 数量持续上升 → 达到 `ulimit -n` 等限制 → 新建连接或打开日志失败 → 服务表现为拒绝新请求或报错。排查时应观察 fd 数量趋势，而不只是看 CPU。

**持久化还要注意写入语义**：`write` 成功通常只表示数据进入了内核页缓存或相关缓冲，不必然意味着已经落盘。对持久性有要求时，需要结合 `fsync` 等机制并理解其代价。缓冲提升吞吐，但也改变了“何时真正持久化”的语义。

## 5. 保护边界与系统调用

### 5.1 保护边界保护什么

用户态程序不能直接改页表、关中断、访问任意物理内存或设备寄存器。需要这些能力时，必须通过系统调用让内核检查后执行。这条边界带来几个直接结果：

- **隔离**：一个普通进程不能随意读写另一个进程的地址空间。
- **权限控制**：文件访问、网络绑定、进程操作都要经过内核检查。
- **统一接口**：设备差异被文件接口或专门系统调用封装。
- **可管理性**：内核可以记账、限流、调度和审计资源使用。

### 5.2 系统调用与普通函数的区别

| 维度 | 普通函数调用 | 系统调用 |
| --- | --- | --- |
| 执行位置 | 通常在同一进程、同一特权级 | 从用户态进入内核态 |
| 地址空间 | 仍使用当前进程地址空间 | 内核代表进程执行，访问受控 |
| 开销 | 主要是调用与返回 | 有特权级切换、参数检查、可能的阻塞和调度 |
| 错误返回 | 语言级异常或返回值 | 常见为 `-1` 加 `errno` |
| 典型例子 | 业务函数、字符串处理 | `open`、`read`、`write`、`mmap`、`clone` |

注意：C 库函数不一定是系统调用。`printf` 可能先写入用户态缓冲区，之后再调用 `write`；`malloc` 可能复用已有堆空间，只在需要时通过 `brk` 或 `mmap` 向内核申请。判断时要看实际调用路径，必要时用 `strace` 观察。

### 5.3 用 `strace` 看系统调用成本

汇总模式：

```bash
strace -c -f <program>
```

如果程序已经在运行，并且你有足够权限，也可以短时间附加：

```bash
strace -c -p <pid>
```

观察要点：

- 哪些系统调用次数最多？
- 哪些调用耗时占比高？是计算慢，还是在等 I/O、锁或网络？
- 是否有大量失败调用，例如反复 `EAGAIN`、`ENOENT` 或 `EMFILE`？
- `-f` 是否显示子进程/线程也贡献了大量调用？

不要简单把 `strace -c` 的耗时全部当成“系统调用本身的开销”：阻塞型调用的时间可能包含等待 I/O 或等待事件的时间。它更适合定位调用结构和热点，而不是替代完整的性能分析。

## 6. 常见误区与设计权衡

### 6.1 常见误区

1. **“进入内核态就是发生了进程切换。”**  
   这是本节点的核心误区。进入内核只是特权级变化；是否切换进程由调度器决定。一个进程可以进入内核读完文件后继续运行。

2. **“系统调用就是普通函数，只是名字特殊。”**  
   系统调用跨越保护边界，参数和指针要由内核校验，可能阻塞，错误约定也不同。

3. **“虚拟内存大，所以物理内存已经被占用。”**  
   虚拟地址空间可以大于物理内存；按需分页意味着映射存在不等于页面已驻留。应区分 `VSZ` 与 `RSS`。

4. **“文件描述符就是文件。”**  
   fd 是进程侧句柄，可以指向普通文件，也可以指向套接字、管道、终端等。同一个底层对象可能被多个 fd 或进程引用。

5. **“进程隔离了，所以一个进程出问题完全不会影响别人。”**  
   地址空间隔离能阻止直接内存破坏，但 CPU、内存、fd、磁盘、网络和下游依赖仍然共享。隔离缩小故障面，不消灭资源竞争。

6. **“`strace -c` 里时间最长的一定是应用逻辑最该优化的地方。”**  
   阻塞等待也会计入调用时间。要结合调用次数、错误码、I/O 模式和业务路径判断。

### 6.2 设计权衡

本节点的 tradeoff 是：

> 保护与抽象带来开销，也让服务故障可隔离。

展开来看：

- **进程 vs 线程**：多进程地址空间独立，崩溃隔离更好，但创建、切换、IPC 和内存使用成本更高；多线程共享内存、通信快，但一个线程的严重错误可能拖垮整个进程。微信公众号后台的 worker 模型、连接处理和任务拆分，本质上都在权衡“隔离性”和“共享效率”。
- **缓冲 vs 持久性**：缓冲和批量写入减少系统调用、提升吞吐，但数据在缓冲中时并未持久化；强持久化通常要付出同步写入的延迟成本。
- **连接池 vs 资源上限**：复用连接减少频繁创建和系统调用，但池子也是有限的 fd 和内存预算。池越大不一定越好，还要考虑下游承载能力和故障时的排队。
- **系统调用批量化 vs 代码复杂度**：批量读写、批量事件处理能降低切换次数，但会增加缓冲管理和错误处理复杂度。优化应建立在测量之上。
- **隔离边界 vs 运维复杂度**：拆成更多进程或服务能限制爆炸半径，但部署、监控、IPC 和资源核算都会更复杂。

一个实用的判断原则是：**先明确故障域和资源预算，再选择抽象边界；不要为了“看起来高并发”而无限增加进程、线程、连接或缓冲区。**

## 7. 动手实践：观察两个程序的文件与内存映射

本节点的实践是：**用进程查看器观察两个程序，追踪它们的文件和内存映射。**

下面给出可执行步骤。请在本地或隔离的实验环境完成，不要对生产进程做附加调试；示例端口使用 `18080`，避免与常见服务冲突。

### 步骤 1：启动两个可观察的程序

一个只睡眠的程序，一个简单的 HTTP 服务：

```bash
sleep 600 &
SLEEP_PID=$!

python3 -m http.server 18080 --bind 127.0.0.1 &
WEB_PID=$!

printf 'SLEEP_PID=%s WEB_PID=%s\n' "$SLEEP_PID" "$WEB_PID"
```

记录两个 PID。它们就是接下来观察的对象。

### 步骤 2：用 `ps` 和 `top` 看进程状态

```bash
ps -o pid,ppid,stat,vsz,rss,cmd -p "$SLEEP_PID","$WEB_PID"
top -p "$SLEEP_PID"
```

观察 `STAT`、`VSZ`、`RSS` 和命令行的差异。按 `q` 退出 `top` 后，再观察另一个 PID：

```bash
top -p "$WEB_PID"
```

思考：为什么两个进程的虚拟内存大小和驻留内存可能差很多？它们当前是在运行，还是在等待事件？

### 步骤 3：追踪内存映射

```bash
cat /proc/"$SLEEP_PID"/maps
cat /proc/"$WEB_PID"/maps
```

分别记录：

- 哪些区域是文件映射，路径是什么；
- 是否存在 `[heap]`、`[stack]`、`[vdso]`；
- 两个进程共同映射了哪些运行时或共享库；
- 哪些区域可写，哪些区域可执行。

比较后写出结论：**两个程序看到的地址空间是各自独立的，但可以共享同一批底层文件映射。**

### 步骤 4：追踪文件描述符

```bash
ls -l /proc/"$SLEEP_PID"/fd
ls -l /proc/"$WEB_PID"/fd
lsof -p "$WEB_PID"
```

重点观察：

- `sleep` 的 0、1、2 指向什么；
- HTTP 服务是否多出监听套接字；
- 启动服务后，是否出现了新的日志或临时文件；
- `lsof` 中能否看到套接字和文件路径。

如果方便，再建立一次连接：

```bash
curl -s http://127.0.0.1:18080/ >/dev/null
```

然后重新查看 `WEB_PID` 的 fd 和 `lsof`，观察连接建立前后是否有变化。

### 步骤 5：汇总系统调用

优先使用“启动即跟踪”的方式，避免权限限制：

```bash
strace -c -f python3 -m http.server 18081 --bind 127.0.0.1
```

在另一个终端发起请求：

```bash
curl -s http://127.0.0.1:18081/ >/dev/null
```

回到 `strace` 所在终端，按 `Ctrl-C`，读取汇总结果。观察 `accept`、`read`、`write`、`close`、`epoll_wait` 等调用的次数和耗时。

如果只是观察已经启动的 `WEB_PID`，并且环境允许附加，也可以使用：

```bash
strace -c -p "$WEB_PID"
```

附加后发起一次请求，再按 `Ctrl-C`。若出现权限错误，不要修改生产机器的安全策略，改用启动时跟踪的方式即可。

### 步骤 6：清理实验进程

```bash
kill "$SLEEP_PID" "$WEB_PID"
```

如果当前 shell 记录了这两个后台任务，也可以等待它们退出：

```bash
wait "$SLEEP_PID" "$WEB_PID" 2>/dev/null || true
```

## 9. 自测题与答案

### 题目 1

普通函数调用和系统调用有什么本质区别？程序进入内核态后，是否一定发生了进程切换？为什么？

**答案**：普通函数调用通常在同一进程、同一特权级和同一地址空间内完成；系统调用要跨越用户态与内核态的保护边界，由内核校验参数并代表进程执行受保护操作，失败时常返回 `-1` 并设置 `errno`。进入内核态不必然发生进程切换。进程可以因 `read` 等系统调用进入内核，完成操作后继续返回原进程运行；只有调度器选择另一个任务上 CPU 时，才发生进程切换。

### 题目 2

`/proc/<pid>/maps` 和 `/proc/<pid>/fd` 分别帮助你观察哪类资源抽象？为什么文件描述符泄漏可能拖垮一个后台服务？

**答案**：`maps` 展示进程的虚拟地址空间布局和内存映射，包括文件映射、堆、栈和权限；`fd` 展示进程打开的文件描述符，可能指向普通文件、套接字、管道或终端。文件描述符是有限资源，连接、日志文件等如果没有在异常路径关闭，数量会持续增长；达到进程或系统上限后，新的 `open`、`accept` 等操作可能失败，服务就会表现为拒绝新连接或无法写日志。

### 题目 3

两个 worker 进程中一个崩溃、另一个继续服务，体现了操作系统的什么目标？这种隔离的代价是什么？

**答案**：体现了进程隔离和故障边界：每个进程有独立地址空间，一个进程的非法内存访问通常不会直接改写另一个进程的地址空间，因此故障可以被限制在较小范围。代价包括进程创建和上下文切换开销、地址空间不共享带来的 IPC 成本、内存占用增加，以及运维和监控复杂度上升。此外，CPU、文件描述符、磁盘和下游服务仍然共享，隔离并不能消除资源耗尽和级联故障。
