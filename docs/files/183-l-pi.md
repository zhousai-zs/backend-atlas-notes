> 节点摘要：通过真实可运行的精简 Harness 理解框架装配，并能把已有 C++ 构建与诊断能力接入自己的 Agent 工具。最小核心便于定制，但业务状态、评测和隔离仍需自行装配。

## 导读

第 174 课用手写状态机说明 Harness。本课改用当前官方 Pi coding agent SDK，把「Agent 核心、Coding Agent 应用、宿主扩展」三层接到可运行的会话上：进程内 `createAgentSession`、权威的 `SessionManager`，以及子进程 `RpcClient`。

教学假设：一个本地诊断宿主只允许读取构建日志摘要，不提供任意 shell。这是为讲解 SDK 边界构造的场景，不代表腾讯或微信的内部编码助手，也不等于第三方多 Agent 编排已经内置。实践锁定 `@earendil-works/pi-coding-agent@1.5.2`，使用官方 `@earendil-works/pi-ai` 的 `fauxProvider` 脚本化回复，`is_live_model=false`。测试进程删除环境中的模型密钥（不读取、不打印其值），也不调用付费接口。

## 学习目标

1. 说明 Agent 核心、Coding Agent 应用和宿主扩展的分层及其适用边界。
2. 独立完成实践：官方 SDK 与 RPC 示例都可运行，安装包名和接口来自当日文档，而不是旧的 `pi-mono` 或 `@mariozechner/pi-coding-agent`。
3. 用负例确认：重启后读到正确活动历史且不同工作目录不串会话；工具权限在宿主执行器中校验；取消与 dispose 后不再收到旧会话事件；直接改 `session.agent` 内存消息不能替换持久历史。

## 为什么后端要懂

把已有构建日志、诊断脚本接到 Agent，首先要分清「框架替你做的」和「宿主必须自己保证的」。会话存档、工作目录隔离、工具授权和子进程生命周期都不是提示词能替代的。

## 核心知识点

### 1. 三层分工，不要把扩展说明当成沙箱

**直觉。** 核心负责模型与消息循环，Coding Agent 应用负责会话、工具装载和资源发现，扩展只是注册额外能力的入口。

**原理。** 本课用 `createAgentSession` 装配 `ModelRuntime`、`SessionManager`、`SettingsManager.inMemory` 和 `customTools`。`noTools: "builtin"` 后活动工具只剩宿主注册的 `summarize_build_log`，`bash` 不在装载表里。官方扩展可以 `registerTool`，但权限检查必须写在工具的 `execute()` 里：本次把 `logs/../../secret.env` 解析到工作区外时返回 `ERROR: unauthorized path`，秘密内容从未进入工具结果。扩展文档或工具 description 不能当作执行器。

**边界。** Pi 提供循环、持久化和 RPC 协议，不默认提供多 Agent 编排、评测或业务事务。第三方编排框架不是本包装箱即用的内置能力。

### 2. SessionManager 是持久上下文的权威来源

**直觉。** 会话文件才是重启后还在的历史，内存赋值不是。

**原理。** 默认会话目录按工作目录编码：`agentDir/sessions/--<cwd 路径>--/`。本次 `projA` 与 `projB` 的 `sessionFile` 不在同一目录；`SessionManager.list(cwdB)` 不含 A 的 session id，B 的历史里也没有 A 的提示词或 `kv.cpp` 日志。重启时用 `SessionManager.open(sessionFile)` 再建会话，同一 `sessionId` 下仍能读到用户提示和 `src/kv.cpp:41` 的诊断。

官方 `sdk.md` 写明：`SessionManager` 对已定稿的模型上下文具有权威性；要把外部历史接回来，应在构造会话时提供包含这些条目的 manager。**直接赋值 `session.agent.state.messages` 不会替换持久上下文。** 本次把内存改成 `PLANTED_MEMORY_SHOULD_NOT_PERSIST` 后，会话文件没有被改写；再次 `open` 仍是真实历史，没有植入句子。

### 3. 官方 fauxProvider，而不是自写固定输出模型

**直觉。** 要验证 SDK 管道，就走官方离线 provider，而不是自己 `return "ok"`。

**原理。** `@earendil-works/pi-ai` 导出 `fauxProvider`、`fauxAssistantMessage`、`fauxToolCall`。需要把它注册为 `ModelRuntime.registerNativeProvider(faux.provider)`：只调用 `registerProvider` 并手写 `streamSimple` 时，宿主仍会报 `No API key found for faux`。faux 的 `auth.resolve` 返回空认证对象，不发起网络。本次脚本先调用 `summarize_build_log({relpath:"logs/build.log"})`，再给出最终文本 `Build failed: undefined reference to exists at src/kv.cpp:41.`。这证明工具循环和事件（`tool_execution_start/end`）走的是官方管道，不能写成「已经测过真实模型」。

脚本还让模型尝试调用未装载的 `bash`：最终文本是「I cannot run bash」，秘密文件未被读取。

### 4. SDK 与 RPC：命令响应不是事件流，子进程必须收干净

**直觉。** 进程内 SDK 简单；RPC 把 Agent 放到子进程，换来隔离，也换来协议和生命周期。

**原理。** 官方 `RpcClient` 用 `node <cliPath> --mode rpc` 启动，本课显式传入包装箱入口 `dist/bundle/cli.js`（也存在 `dist/cli.js`）。`getState()` 返回带 `sessionId`、`isStreaming` 等字段的命令响应；会话事件走 `onEvent`。本次在隔离的 `HOME` 与 `PI_CODING_AGENT_DIR` 下 `start()`，`getState()` 成功；对子进程 `prompt()` 得到官方错误「No API key found for the selected model」，因为官方 faux API 是进程内注册，不是 CLI 的 `--provider faux`。随后 `abort()`、`stop()`，子进程 pid 不再存活。

SDK 侧对一个会等待 8 秒的工具调用 `abort()`，再 `dispose()`。dispose 之后订阅者没有再收到旧会话事件；再对已 dispose 的会话 `prompt()` 也没有新的 turn/tool 事件。

## 常见误区

- 继续用 `https://github.com/badlogic/pi-mono` 或 npm 包 `@mariozechner/pi-coding-agent`（当日仍可能查到旧 0.73.1），而不跟随重定向核对当前包名 `@earendil-works/pi-coding-agent`。
- 把 `session.agent.state.messages` 或 `session.state.messages` 改掉，就以为持久历史已经换了。
- 把扩展回调、工具说明或「模型说自己没调用 bash」当成权限系统。
- 把第三方多 Agent 编排写成 Pi 的默认内置能力。
- 用自写固定字符串冒充模型能力，或把 `ALL_CHECKS_PASSED` 四个字当成质量本身。

## 设计权衡

进程内 SDK 便于单测和注入官方 fauxProvider；RPC 进程隔离更清晰，但要把模型、扩展和认证再注入子进程，并负责子进程退出。最小核心能看懂装配，但评测、业务库和沙箱仍要自己接。

实践包在 `practice183/`。需要 Node.js（本次为 24.22.1）与已锁定的 `1.5.2`。若没有 `node_modules`，`test.sh` 会执行 `npm install --ignore-scripts --no-fund --no-audit`。不要把真实密钥传进进程：

```bash
# 干净目录不含 node_modules 时由 test.sh 安装

```

`run.log` 末行应为 `ALL_CHECKS_PASSED`，并有 `POSTCHECK_OK`。本次验证了：官方 SDK 工具循环、SessionManager 恢复、cwd 隔离、宿主路径授权、内存赋值不能替换持久历史、dispose 后无旧事件、官方 `RpcClient.getState/abort/stop` 且子进程退出。`results.json` 中 `is_live_model=false`，`package=@earendil-works/pi-coding-agent`，`package_version=1.5.2`。

## 自测题

**1. 为什么要用官方 fauxProvider，而不是在测试里 `return "Build failed"`？**

答：验收要证明的是 Pi 的会话、工具循环和事件管道，而不是自己的桩。本次 `registerNativeProvider(faux.provider)` 后出现了官方 `tool_execution_*` 事件和最终文本；`is_live_model` 仍为 false，不能外推到真实模型。

**2. 把 `session.agent.state.messages` 改成一段新历史，重启后会怎样？**

答：持久历史仍以 SessionManager 的会话文件为准。本次植入的 `PLANTED_MEMORY_SHOULD_NOT_PERSIST` 既没有写入 jsonl，也没有出现在再次 `open` 的消息里。

**3. 为什么 RPC 的 `getState()` 能成功，而 `prompt()` 报没有 API key，却仍然算「RPC 示例可运行」？**

答：官方 RpcClient 对协议和生命周期的验收是 start、命令响应、abort、stop 以及子进程退出。fauxProvider 是进程内 API，不是 CLI provider。本次没有编造一次「RPC 已用离线模型完成 prompt」，而是记下官方缺密钥错误，并把真实模型 prompt 列为未实测。
