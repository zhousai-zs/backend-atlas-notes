# 第 9/208 课：哈希表与冲突处理

> 节点：`a-hash` · 域：A · 子类：数据结构与算法 · 难度：基础 · 前置：`a-sequence`
>
> 一句话：哈希表用哈希函数缩小查找范围，通过链地址或开放寻址处理冲突。平均常数时间依赖哈希分布与装载因子，扩容及恶意碰撞可能造成长尾。

## 1. 学习目标与为什么后端要懂

### 1.1 学习目标

完成本课后，你应该能够：

1. 解释哈希函数与相等关系各自负责什么，以及为什么查找必须同时依赖两者。
2. 说清楚“平均 O(1)”背后的假设：哈希分布、装载因子、哈希与比较的成本，以及为什么它不等于最坏情况有界。
3. 区分链地址与开放寻址的存储布局、冲突处理、删除方式和引用稳定性。
4. 独立实现一个字符串哈希表，构造碰撞，并用装载因子变化解释探测次数的变化。
5. 正确描述 rehash 之后旧指针、旧引用、旧迭代器和旧桶索引的边界。
6. 在微信公众号后台这类读多写多、存在恶意输入的系统中，做出可解释的容量与安全取舍。

### 1.2 验收标准

节点给出的验收标准有两条，本课会反复回扣：

- **能解释平均 O(1) 的假设。** 不是“哈希表永远快”，而是在“哈希函数把键较均匀地散布到桶里、装载因子被 rehash 控制在常数上界、键的哈希与比较成本可视为常数”这些前提下，期望查找成本是常数。若哈希退化、装载因子失控或输入由攻击者构造，最坏情况会退化为 O(n)。
- **rehash 后旧引用的边界描述正确。** 不同实现差别很大：常见节点式 `std::unordered_map` 在 rehash 后元素地址不变，指向元素的指针和引用仍然有效，但迭代器失效；开放寻址或把元素连续存放在数组里的实现，rehash 会搬动元素，指针、引用、迭代器通常全部失效。不能笼统地说“rehash 后所有引用都失效”，也不能反过来说“都没事”。

### 1.3 为什么微信公众号后台要懂哈希表

节点对“为什么”的说明很直接：**理解 KV 索引、去重及攻击输入下的退化。** 放到微信公众号后台，哈希表几乎无处不在：

- **openid → 用户会话缓存。** 用户进入公众号、点击菜单、打开网页授权，后端都要根据 openid 找到对应的会话、权限、最近一次交互状态。哈希表把“在百万级用户里找一个人”变成“先算一个桶号，再在很短的链里比较 openid”。
- **消息去重。** 微信服务器可能重试推送，业务侧也可能重复消费。用消息 id、FromUserName、CreateTime 等字段组成去重键，放进哈希集合，可以快速判断“这条消息是不是已经处理过”。如果只比较哈希值而不比较完整键，两个不同消息可能被误判为重复，造成丢消息。
- **access_token 缓存。** access_token 数量不多，但访问频率极高，而且刷新时有并发问题。哈希表适合做 `appid → token` 的内存索引；如果表很小，启动时预留容量，避免在请求路径上触发扩容。
- **粉丝列表索引。** 按 openid 查粉丝资料、标签、分组，本质上是高基数 KV 索引。键的数量大，装载因子和每个元素的内存开销都会直接影响单机容量。
- **恶意碰撞攻击。** 如果接口接受用户可控的字符串作为键，而哈希函数固定且分布可预测，攻击者可以构造大量落入同一个桶的键。链地址表会退化成一条长链表，开放寻址表会退化成连续探测，CPU 被打满，正常请求的 p99 延迟急剧上升。
- **扩容毛刺。** 活动开始、批量导入粉丝、缓存预热时，短时间插入大量新键，可能触发一次 O(n) 的 rehash。平均吞吐看起来没问题，但单个请求可能正好撞上这次扩容，形成尾延迟。

所以本课的目标不是背“哈希表增删改查 O(1)”，而是建立一套能验证的模型：**键怎样变成桶号、冲突怎样被解决、装载因子怎样影响成本、扩容后哪些旧引用还能用。**

## 2. 从直觉到原理：三个核心要点

### 2.1 哈希函数与相等关系

#### 直觉：先分类，再确认

想象一个图书馆。你要找《深入理解计算机系统》，不会从第一排第一本开始逐本翻。你先根据分类号走到“计算机”书架，再在那一排里比较书名。哈希函数就是“分类号”，相等关系就是“确认书名是否完全一致”。

哈希表也是这样：

1. 用哈希函数 `h(key)` 把任意键映射到 `0..m-1` 的桶号。
2. 到对应的桶里找。
3. 对桶里的候选键，用相等比较 `key == candidate` 确认是不是同一个键。

只有哈希不够，因为不同的键可能得到同一个哈希值，这叫**冲突**。只有相等也不够，因为那就退化成从头到尾的线性扫描。**哈希负责缩小范围，相等负责最终判定。**

#### 原理：查找 = 哈希定位 + 相等比较

形式化地，一个哈希表至少需要两个部件：

- 哈希函数 `h: K → {0, 1, ..., m-1}`，`m` 是桶的数量。
- 相等谓词 `eq(a, b)`，判断两个键是否表示同一个键。

查找 `get(k)` 的过程是：

```text
i = h(k) % m
for candidate in bucket[i]:
    if eq(k, candidate.key):
        return candidate.value
return NOT_FOUND
```

这里有两个容易忽略的成本：

- `h(k)` 本身可能不是 O(1)。对字符串来说，哈希要遍历字节，成本是 O(键长度)。openid 长度通常固定且很短，可以近似常数；如果把整段消息体当键，哈希成本就会随消息长度增长。
- `eq(k, candidate)` 也可能不是 O(1)。字符串比较在最坏情况下要看完整个字符串。哈希表只是减少了需要比较的次数，并没有让单次比较免费。

#### 契约：哈希与相等必须一致

一个正确的哈希表依赖下面几条契约：

1. **同一个键，在它作为键期间，哈希值必须稳定。** 如果键对象被修改，导致哈希值变化，之前插入的位置就找不到了。
2. **若 `a == b`，则必须有 `h(a) == h(b)`。** 这是最重要的一条。反过来不成立：`h(a) == h(b)` 只说明冲突，不说明 `a == b`。
3. **相等比较和哈希必须覆盖同一组字段。** 如果相等比较忽略大小写，哈希也必须忽略大小写；如果相等比较忽略某个字段，哈希也不能把该字段算进去。否则会出现“逻辑上相等，但哈希到不同桶”的情况，查找失败。
4. **哈希函数应尽量均匀、快速，并让相近输入产生不相近的输出。** 这不是正确性的硬性要求，但直接决定平均性能。

用 C++ 自定义一个 openid 键，需要同时提供哈希和相等：

```cpp
#include <functional>
#include <string>
#include <unordered_map>

struct OpenId {
    std::string value;

    bool operator==(const OpenId& other) const {
        return value == other.value;
    }
};

struct OpenIdHash {
    std::size_t operator()(const OpenId& key) const {
        return std::hash<std::string>{}(key.value);
    }
};

std::unordered_map<OpenId, Session, OpenIdHash> sessions;
```

`std::unordered_map` 默认用 `std::equal_to<Key>` 做相等比较，用 `std::hash<Key>` 做哈希。自定义类型如果既没有 `operator==` 也没有可用的 `std::hash` 特化，就无法直接作为键。这里的 `OpenIdHash` 复用了标准库对字符串的哈希，保证“相等则同哈希”。

Python 的 `dict` 也是同一套契约：

```python
class OpenId:
    __slots__ = ("value",)

    def __init__(self, value: str) -> None:
        self.value = value

    def __hash__(self) -> int:
        return hash(self.value)

    def __eq__(self, other: object) -> bool:
        return isinstance(other, OpenId) and self.value == other.value
```

Python 有一个保护机制：如果你只定义了 `__eq__` 而没有定义 `__hash__`，这个类会变成不可哈希，避免你无意中破坏契约。但如果你定义了 `__hash__`，又允许对象在插入后修改参与哈希的字段，问题仍然会发生：

```python
key = OpenId("openid_A")
cache = {key: "session-A"}
key.value = "openid_B"
print(cache.get(key))   # 很可能输出 None
```

插入时字典记录的是 `hash("openid_A")` 对应的位置；修改后查找用的是 `hash("openid_B")`，自然找不到旧条目。更糟的是，这个对象还留在字典里，却很难再被正常访问。**结论：作为键的对象应当视为不可变；需要修改时，先删除旧键，再插入新键。**

#### 字符串哈希函数长什么样

一个简单、常见的字符串哈希是 FNV-1a：

```python
def fnv1a(s: str) -> int:
    h = 14695981039346656037
    for b in s.encode("utf-8"):
        h ^= b
        h = (h * 1099511628211) & 0xFFFFFFFFFFFFFFFF
    return h
```

它逐字节做“异或再乘一个奇数”，让每个字节都影响最终结果。实际使用时再对桶数取模：

```python
bucket = fnv1a(key) % bucket_count
```

对比一个故意写坏的哈希：

```python
def first_char(s: str) -> int:
    return ord(s[0]) if s else 0
```

如果所有 openid 都以 `u` 开头，这个函数会把所有键都送到同一个桶。它不是“偶尔冲突”，而是**确定性地构造了最坏情况**。这正是恶意碰撞攻击的入口：攻击者不需要破解哈希，只需要知道哈希只看首字符，就能批量制造同桶键。

哈希函数的质量通常看三点：

- **均匀性**：输出是否大致均匀落在各个桶里。
- **雪崩效应**：输入改一个字节，输出应有大量位变化。
- **速度**：哈希在每次查找都要算，不能比比较本身还贵太多。

`std::hash` 适合一般用途，但标准并不保证它在不同实现、不同版本、不同进程中产生相同结果，也不保证它能抵抗碰撞攻击。**不要把 `std::hash` 的结果持久化到数据库，也不要用它当全局唯一 ID。** 对不可信输入，应使用带随机种子的键控哈希（例如 SipHash 这一类设计），让攻击者无法离线构造碰撞。

#### 后端场景：哈希值不能代替相等

假设消息去重表只存 64 位哈希：

```python
seen = set()
digest = fnv1a(msg_id) & 0xFFFFFFFFFFFFFFFF
if digest in seen:
    drop_message()
else:
    seen.add(digest)
    process_message()
```

两个不同的 `msg_id` 可能得到同一个 64 位值。随着消息量增加，碰撞概率会上升；一旦碰撞，第二条不同消息会被当成重复消息丢掉。正确做法是：**哈希表内部可以用哈希缩小候选范围，但最终必须比较完整键（或足够强的唯一 ID）。** 如果业务上必须只存摘要，就要接受碰撞概率并做额外校验，而不是把哈希值当成“不会重复的键”。

### 2.2 负载因子和 rehash

#### 直觉：桶不能无限挤

设哈希表里有 `n` 个元素，桶的数量是 `m`，定义**装载因子**：

```text
α = n / m
```

`α` 衡量平均每个桶要装多少个元素。链地址中，如果哈希足够均匀，平均链长就是 `α`；开放寻址中，`α` 越接近 1，空槽越少，探测越长。

例如：

- 100 万个会话，200 万个桶，`α = 0.5`。
- 100 万个会话，100 万个桶，`α = 1.0`。
- 100 万个会话，50 万个桶，`α = 2.0`。

链地址可以容忍 `α > 1`，但平均链长会继续增长；开放寻址必须保证至少有一个空槽，通常要把 `α` 控制在 0.5 到 0.75 之间。

#### 平均 O(1) 到底假设了什么

在“简单均匀哈希”的假设下，链地址的期望查找成本是：

```text
成功查找：约 1 + α/2 次比较
失败查找：约 α 次比较
```

开放寻址的线性探测在均匀哈希近似下：

```text
成功查找：约 1/2 * (1 + 1/(1-α))
失败查找：约 1/2 * (1 + 1/(1-α)^2)
```

代入数字就能看出为什么不能把装载因子推到 1：

| α | 链地址成功/失败 | 线性探测成功 | 线性探测失败 |
| --- | --- | --- | --- |
| 0.25 | 1.125 / 0.25 | 1.17 | 1.39 |
| 0.50 | 1.25 / 0.50 | 1.50 | 2.50 |
| 0.75 | 1.375 / 0.75 | 2.50 | 8.50 |
| 0.90 | 1.45 / 0.90 | 5.50 | 50.50 |
| 0.99 | 1.495 / 0.99 | 50.50 | 5000.50 |

这些公式成立的前提是：

1. 哈希函数把键均匀、独立地散布到桶里。
2. `α = n/m` 被 rehash 控制在一个常数上界内，不随 `n` 增长。
3. 哈希计算和相等比较可以看作 O(1)（或键长度有界）。
4. 输入不是攻击者专门构造的碰撞集合。

满足这些前提，期望成本才是 O(1)。如果桶数固定而元素无限增长，`α` 会随 `n` 增长，平均链长也随之增长，整体就退化为 O(n)。所以“哈希表 O(1)”不是一个无条件的承诺，而是“**均匀哈希 + 有界装载因子**”下的期望结论。

还要区分三个词：

- **期望 O(1)**：对哈希函数的随机性和键分布取平均。
- **均摊 O(1)**：把偶尔一次 O(n) 的 rehash 成本摊到很多次插入上。
- **最坏 O(n)**：所有键落到同一个桶，或 rehash 正好发生在这一次操作里。

后端更关心尾延迟，而“平均”和“均摊”都不能自动推出“最坏有界”。这一点在第 3 节会展开。

#### rehash 做了什么

当 `α` 超过阈值，哈希表需要**扩容并重新分布**：

1. 分配一个更大的桶数组（常见做法是翻倍，或取下一个质数）。
2. 遍历旧表中的所有元素。
3. 用新的桶数重新计算每个元素的桶号，插入新表。
4. 释放旧桶数组。

重新计算桶号是必要的，因为 `h(key) % m` 依赖 `m`。即使哈希值不变，桶号也会变。

成本分析：

- 一次 rehash 要搬运 `n` 个元素，成本是 O(n + m)。
- 如果每次扩容按几何级数增长（例如 2 倍），从空表插入 `n` 个元素的总搬运成本是 O(n)，所以**均摊**每次插入 O(1)。
- 但单次插入仍可能是 O(n)。对有严格延迟目标的服务，这一次 O(n) 就是尾延迟毛刺。
- 如果每次只增加一个桶，扩容次数太多，总成本会退化到 Θ(n²)。

因此，工程上通常选择几何扩容，并在可预期的大批量写入前预留容量。

#### C++ 标准库里的控制手段

`std::unordered_map` 暴露了几个关键接口：

```cpp
#include <string>
#include <unordered_map>

std::unordered_map<std::string, Session> cache;

cache.max_load_factor(0.75f);  // 超过 0.75 时倾向于扩容
cache.reserve(1'000'000);      // 为约 100 万个元素预留桶，尽量避免请求路径上 rehash
```

几个接口的含义：

- `load_factor()`：当前 `size() / bucket_count()`。
- `bucket_count()`：当前桶数。
- `max_load_factor()`：装载因子上限提示，默认通常是 1.0。调低它会增加桶数、减少冲突，但更费内存。
- `rehash(n)`：让桶数至少为 `n`，可能触发重排。
- `reserve(n)`：按当前 `max_load_factor` 预留足够容纳 `n` 个元素的桶数，可能触发重排。

注意：`reserve` 和 `rehash` 都可能分配内存并抛异常；在服务启动阶段预留，比在请求处理中途扩容更可控。`max_load_factor` 是提示而不是精确保证，具体行为以你使用的标准库实现和版本文档为准。

Python 的 `dict` 不暴露桶数和装载因子，扩容阈值属于实现细节。CPython 会在内部装载因子达到阈值时扩容，不同版本的具体阈值可能变化。**不要把某个版本的内部阈值写死到容量规划里**；需要控制内存和延迟时，应通过压测和版本核对来确认。

#### rehash 后旧引用到底还能不能用

这是本课最重要的边界之一。先看一段 C++：

```cpp
#include <iostream>
#include <string>
#include <unordered_map>

int main() {
    std::unordered_map<std::string, int> cache;
    cache["openid_A"] = 1;

    int* p = &cache["openid_A"];
    auto it = cache.find("openid_A");

    std::cout << "before buckets=" << cache.bucket_count()
              << " it_value=" << it->second << "\n";

    cache.rehash(1024);

    std::cout << "after buckets=" << cache.bucket_count()
              << " same_address=" << (p == &cache.at("openid_A")) << "\n";
    std::cout << "value_via_pointer=" << *p << "\n";

    // 不要解引用 it：rehash 之后迭代器已经失效。
}
```

对常见的节点式 `std::unordered_map` 实现，标准保证：

- **rehash 会使迭代器失效。**
- **rehash 不使指向元素的指针和引用失效。** 因为元素节点本身没有被搬走，只是桶数组中的链接关系变了。
- **`end()` 迭代器始终不应长期缓存。**
- **`erase` 只使被删除元素的迭代器、指针和引用失效。**
- **桶号会改变**，所以缓存 `bucket(key)` 的结果或自己算出的 `h(key) % m` 在 rehash 后不能继续用。

但这条“指针和引用仍有效”的结论不能推广到所有哈希表：

| 场景 | rehash 后旧引用/指针 | 旧迭代器 |
| --- | --- | --- |
| 常见节点式 `std::unordered_map` | 指向元素的指针/引用仍有效 | 失效 |
| 自定义链地址，元素存在 `std::vector` 里 | 元素被搬移，通常失效 | 失效 |
| 开放寻址 / 连续槽数组 | 元素被搬移，通常全部失效 | 失效 |
| 缓存了桶索引或 `h(key) % m` | 桶号改变，不能再用 | 不适用 |
| 已 `erase` 的元素 | 失效 | 失效 |
| Python `dict` 的键对象 | 键对象本身不会被字典搬走 | 字典大小变化时，迭代中会报错，不能依赖 |

所以正确表述不是“rehash 后引用都失效”，也不是“rehash 后引用都安全”，而是：**要看容器是否把元素节点单独分配、rehash 是否搬动元素、以及你持有的是指针/引用还是迭代器/桶索引。** 对 `std::unordered_map`，记住“迭代器失效、元素指针和引用通常仍有效”；对开放寻址实现，默认按“全部失效”处理，除非文档明确保证。

#### 后端场景：把扩容移出请求路径

假设公众号后台有一个 `openid → Session` 的缓存，活动开始瞬间涌入大量新用户。如果表没有预留，插入到某个阈值时会触发 rehash，正好命中的那个请求要等待整个桶数组重建。平均 QPS 可能只下降一点，但 p99 会明显抬头。

可选做法：

- 服务启动时按预估在线用户数 `reserve`，或分片成多个小表，降低单次 rehash 的规模。
- 对批量导入、缓存预热，先扩容再灌数据。
- 监控 `load_factor`、最大链长和 rehash 次数；不要只看平均响应时间。
- 对延迟极敏感的场景，考虑增量 rehash：把一次大搬迁拆成多次小步骤。Redis 的字典就采用这种思路，但那是实现层面的设计，不是所有标准库容器都提供。

### 2.3 开放寻址与链地址

冲突不可避免，关键是冲突发生后把元素放在哪里。最常见的两类方案是**链地址**和**开放寻址**。

#### 链地址：每个桶挂一条链

链地址的布局是：桶数组的每个槽保存一个链表（或节点链）的头指针。哈希到同一个桶的元素，都挂在同一条链上。

```text
buckets:
[0] -> ("openid_A", session) -> ("openid_Z", session) -> null
[1] -> null
[2] -> ("openid_B", session) -> null
[3] -> ("openid_C", session) -> null
```

查找时：

1. 算出桶号。
2. 沿链逐个比较键。
3. 找到相等键就返回；走到链尾就说明不存在。

插入时可以在链头插入，也可以在链尾追加；删除时从链上摘掉节点。链地址的删除很直接：**找到节点，修改前驱的指针即可**，不需要墓碑。

链地址的优缺点：

- 优点：删除简单；可以容忍 `α > 1`；如果节点单独分配，rehash 只改桶指针，元素地址可以保持不变（常见 `std::unordered_map` 就是这种思路）。
- 缺点：每个元素额外带指针，内存开销更大；节点分散在堆上，缓存局部性差；冲突严重时退化成链表，查找 O(n)。

很多语言的标准库哈希表采用链地址或其变体。Java 的 `HashMap` 在链过长时还会把链表转成红黑树，把最坏查找从 O(n) 降为 O(log n)，这是工程上对抗退化的一个例子。C++ 标准不规定 `unordered_map` 必须用链地址，但常见实现采用节点式链地址。

#### 开放寻址：所有元素都放在槽数组里

开放寻址不建链表，所有元素都直接放在一个槽数组里。发生冲突时，按某种**探测序列**寻找下一个空槽：

- 线性探测：`i, i+1, i+2, ...`
- 二次探测：`i, i+1², i+2², ...`
- 双重哈希：用第二个哈希函数决定步长。

查找时沿着同样的探测序列走：

- 遇到空槽：说明键不存在，停止。
- 遇到已使用且键相等：找到了。
- 遇到已使用但键不等：继续探测。
- 遇到墓碑（已删除标记）：不能停，必须继续。

线性探测的查找骨架：

```python
EMPTY, USED, DELETED = 0, 1, 2

def lookup(slots, key):
    i = hash(key) % len(slots)
    for _ in range(len(slots)):
        slot = slots[i]
        if slot.state == EMPTY:
            return None
        if slot.state == USED and slot.key == key:
            return slot.value
        i = (i + 1) % len(slots)
    return None
```

插入时找到第一个 `EMPTY` 或 `DELETED` 槽放入；如果表里没有空槽，必须先扩容，否则探测会绕圈。

开放寻址的优缺点：

- 优点：元素连续存放，缓存局部性好；不需要每个元素额外挂指针，内存更紧凑；线性探测的顺序访问对 CPU 缓存和预取友好。
- 缺点：装载因子必须严格小于 1，通常要控制在 0.5 到 0.75；线性探测容易产生**一次聚集**，冲突会连成一片；删除复杂；rehash 会搬动元素，引用不稳定。

#### 删除为什么需要墓碑

开放寻址最容易踩的坑是删除。假设线性探测插入顺序如下：

```text
槽位:   0     1     2     3
内容:  K1    K2    K3    EMPTY
```

如果 `K1` 和 `K2` 冲突，`K2` 被放到 1；`K3` 又冲突，被放到 2。现在删除 `K2`：

- 如果直接把槽 1 设为 `EMPTY`，查找 `K3` 时，探测从槽 0 开始，走到槽 1 看到 `EMPTY` 就停止，误判 `K3` 不存在。
- 正确做法是把槽 1 标记为 `DELETED`（墓碑）。查找 `K3` 时遇到墓碑会继续探测，最终在槽 2 找到。

所以：

```python
slots[i].state = DELETED   # 不能直接设为 EMPTY
```

墓碑会被查找路径经过，但可以被后续插入复用。如果删除很多而插入很少，墓碑会越积越多，表看起来“很空”，实际探测却很长。这时需要 rehash 清理墓碑。另一种实现是删除后把后面的元素回移（backward-shift），避免墓碑，但实现更复杂，也需要仔细处理探测链。

#### 链地址与开放寻址的对比

| 维度 | 链地址 | 开放寻址 |
| --- | --- | --- |
| 存储 | 桶数组 + 独立节点/链 | 一个连续槽数组 |
| 冲突处理 | 挂到同桶的链上 | 按探测序列找下一个槽 |
| 装载因子 | 可以大于 1，但链会变长 | 必须小于 1，通常 ≤ 0.75 |
| 删除 | 摘链即可 | 墓碑或回移，复杂 |
| 缓存局部性 | 指针跳转，通常较差 | 连续访问，通常较好 |
| 引用稳定性 | 节点式实现 rehash 后元素地址可不变 | rehash 搬动元素，通常全部失效 |
| 最坏情况 | 所有键同桶，O(n) | 探测整个表/墓碑堆积，O(n) |
| 适合场景 | 删除频繁、需要稳定引用、实现简单 | 读多写少、内存紧凑、缓存友好 |

选择时不要只看“哪个更快”，而要看负载：

- 会话缓存、access_token 缓存这类读多、删除少、键值较小的场景，开放寻址的局部性优势明显。
- 消息去重、粉丝索引这类插入删除都频繁、可能需要持有元素引用的场景，链地址的删除和引用稳定性更省心。
- 如果输入不可信，两种方案都可能被碰撞攻击打退；必须配合键控哈希、输入限制和监控。
- 如果团队自己实现，必须明确墓碑策略、扩容策略、装载因子上限和并发模型；直接用成熟标准库通常更安全。

## 3. 常见误区与设计权衡

### 3.1 平均常数时间不等于最坏有界延迟

这是本节点明确列出的陷阱，也是后端最容易吃亏的地方。

“平均 O(1)”至少隐藏了四层假设：

1. 键的哈希值均匀分布。
2. 装载因子被控制在常数上界。
3. 哈希和相等比较的成本可视为常数。
4. 输入不是攻击者专门构造的。

真实系统里，这四条都可能被打破：

- **弱哈希。** 例如只看首字符、只看长度、或者对某些字段不敏感，攻击者可以批量制造同桶键。
- **固定种子。** 如果哈希函数完全确定且公开，攻击者可以离线计算出大量碰撞键，再通过接口提交。
- **突发写入。** 活动、批量导入、缓存预热会让装载因子快速上升，触发 rehash。
- **长键。** 如果把长字符串甚至整个请求体作为键，单次哈希就是 O(长度)，不是 O(1)。

一个典型的退化过程是：接口接受用户可控的 `msg_id`，后端用弱哈希做去重集合。攻击者提交 20 万个都落在同一个桶的键。链地址表的那个桶变成一条长度 20 万的链表；每次插入或查询都要走完整条链，单次操作从微秒级变成毫秒级甚至更差。正常用户的请求排在后面，p99 延迟飙升，严重时线程池被占满。**平均负载可能并不高，但尾延迟已经被打穿。**

应对思路不是承诺“最坏 O(1)”（哈希表一般做不到），而是降低退化的概率和影响：

- 对不可信输入使用带随机种子的键控哈希，让攻击者无法稳定构造碰撞。
- 限制单个键的长度和单次请求的键数量，对异常输入限流。
- 预分配容量，避免在请求路径上触发大 rehash；或采用增量 rehash。
- 监控装载因子、最大链长、探测长度和 rehash 次数，而不是只看平均 QPS。
- 对延迟目标严格的接口，用压测覆盖“最坏分布”，测 p99/p999，不只看均值。
- 必要时使用树化桶、分片哈希表或其他混合结构，把最坏情况从 O(n) 降下来。

结论：**哈希表的“常数时间”是期望值，不是延迟上界。** 设计 SLA 时，必须把碰撞、扩容和恶意输入纳入最坏情况预算。

### 3.2 其他常见误区

- **只比较哈希值。** 哈希相等只说明可能相等，必须再比较完整键。把哈希值当唯一 ID 会造成误判去重或错误命中。
- **修改作为键的对象。** 插入后修改参与哈希的字段，会导致旧条目无法查找。键应视为不可变。
- **哈希与相等覆盖的字段不一致。** 例如相等比较忽略大小写，哈希却区分大小写，逻辑上相等的键会落到不同桶。
- **假设迭代顺序稳定。** `unordered_map` 的遍历顺序不保证；rehash 后顺序会变。不要依赖它做分页、排序或幂等输出。
- **认为 rehash 只影响性能。** 如果你缓存了迭代器、桶号或指向元素的引用，rehash 可能直接造成未定义行为或错误结果。
- **在开放寻址中把装载因子推到 1。** 没有空槽时探测可能死循环；删除后的墓碑也会让有效装载因子高于表面值。
- **忽略线程安全。** `std::unordered_map` 和 Python `dict` 都不是为多线程无锁并发读写设计的。读多写少也要用合适的锁或并发容器；一边扩容一边读是数据竞争。
- **只看桶数，不看分布。** 桶很多但哈希很差，仍然会集中冲突；桶数合适但键分布偏斜，也会长尾。
- **把 `std::hash` 当稳定标识。** 标准不保证跨实现、跨版本、跨进程一致；不要持久化哈希值，也不要用它做跨服务 ID。

### 3.3 设计权衡：开放寻址局部性好，删除及引用稳定性更复杂

节点给出的取舍是：**开放寻址局部性好，删除及引用稳定性更复杂。** 这句话可以拆成两半：

- **局部性好**：开放寻址把元素放在连续数组里，线性探测通常访问相邻槽位，能吃到缓存行和硬件预取的好处。链地址要沿着堆上的节点指针跳转，每次跳转都可能是一次缓存缺失。对读多、键值小、装载因子可控的缓存，开放寻址往往有更好的常数。
- **删除及引用稳定性更复杂**：开放寻址不能简单地把槽清空，否则会截断探测链，所以需要墓碑或回移；墓碑积累会拖慢查找，需要定期 rehash。rehash 会搬动元素，之前持有的指针、引用、迭代器都可能失效。链地址删除只需摘链，节点式实现还能在 rehash 后保持元素地址不变，引用更稳定。

实际选择可以用下面的问题清单：

1. **删除频繁吗？** 频繁删除且不想处理墓碑，优先链地址。
2. **需要长期持有元素引用吗？** 需要的话，确认容器在 rehash 后是否保持元素地址；不要假设所有链地址都稳定。
3. **读是否远多于写？** 读多写少、键值小，开放寻址的缓存局部性更有价值。
4. **内存是否紧张？** 开放寻址没有每元素指针开销，通常更紧凑；但为了低装载因子要多留空槽。
5. **输入是否不可信？** 两种结构都需要键控哈希和限流；开放寻址在碰撞下可能出现聚集，链地址会退化成链表。
6. **延迟目标是否严格？** 需要预分配、分片、增量 rehash 或监控，不能只依赖均摊 O(1)。

没有一种结构在所有维度都赢。**结构选择应该由访问模式、删除比例、引用稳定性要求、内存预算和安全模型共同决定。**

### 步骤 2：写入哈希表与基准脚本

把下面的内容保存为 `/tmp/atlas-hash/hash_bench.py`：

```python
import sys


def fnv1a(s, mod):
    h = 14695981039346656037
    for b in s.encode("utf-8"):
        h ^= b
        h = (h * 1099511628211) & 0xFFFFFFFFFFFFFFFF
    return h % mod


def first_char(s, mod):
    return (ord(s[0]) if s else 0) % mod


class ChainTable:
    def __init__(self, buckets, hash_fn):
        self.buckets = [[] for _ in range(buckets)]
        self.hash_fn = hash_fn
        self.size = 0

    def insert(self, key):
        chain = self.buckets[self.hash_fn(key, len(self.buckets))]
        for existing in chain:
            if existing == key:
                return False
        chain.append(key)
        self.size += 1
        return True

    def contains(self, key):
        chain = self.buckets[self.hash_fn(key, len(self.buckets))]
        probes = 0
        for existing in chain:
            probes += 1
            if existing == key:
                return True, probes
        return False, probes

    def stats(self):
        lengths = [len(c) for c in self.buckets]
        n = self.size
        m = len(self.buckets)
        nonempty = sum(1 for length in lengths if length)
        success = (
            sum(length * (length + 1) / 2 for length in lengths) / n
            if n else 0
        )
        return {
            "alpha": n / m,
            "max_chain": max(lengths),
            "avg_nonempty": n / nonempty if nonempty else 0,
            "exp_succ": success,
            "exp_fail": n / m,
        }


def key(i):
    return f"user:openid:{i}"


def main():
    m = int(sys.argv[1]) if len(sys.argv) > 1 else 4096
    fixed_n = int(sys.argv[2]) if len(sys.argv) > 2 else None
    targets = (
        (fixed_n,) if fixed_n is not None
        else (m // 4, m // 2, m * 3 // 4, m * 9 // 10)
    )
    for name, hash_fn in [
        ("FNV-1a", fnv1a),
        ("FirstCharHash (weak)", first_char),
    ]:
        print(f"== {name}, buckets={m} ==")
        for n in targets:
            table = ChainTable(m, hash_fn)
            for i in range(n):
                table.insert(key(i))

            s = table.stats()
            hit, hit_probes = table.contains(key(n // 2))

            miss_total = 0
            for j in range(1000):
                miss, probes = table.contains(f"user:openid:absent-{j}")
                assert not miss
                miss_total += probes
            miss_avg = miss_total / 1000

            print(
                f"n={n:5d} alpha={s['alpha']:.3f} "
                f"max_chain={s['max_chain']:5d} "
                f"avg_nonempty={s['avg_nonempty']:.3f} "
                f"exp_succ={s['exp_succ']:.3f} "
                f"exp_fail={s['exp_fail']:.3f} "
                f"hit={int(hit)}/{hit_probes} "
                f"miss_avg={miss_avg:.3f}"
            )


if __name__ == "__main__":
    main()
```

这个脚本做了几件事：

- `ChainTable` 是链地址哈希表，每个桶是一个 Python 列表。
- `fnv1a` 是一个分布较好的字符串哈希。
- `first_char` 是故意写弱的哈希：所有以 `u` 开头的键都会落到同一个桶，用来构造碰撞。
- `stats()` 计算装载因子、最大链长、非空桶平均长度、成功查找的期望探测次数，以及失败查找的理论值 `n/m`。
- 默认情况下，主程序在 `α = 0.25, 0.5, 0.75, 0.9` 四档分别建表，并对 1000 个不存在的键测量实际探测次数；第二个命令行参数可以固定元素数量，便于单独改变桶数。

### 步骤 4：解读 FNV-1a 的结果

先看正常哈希：

- `alpha` 从 0.25 升到 0.9，`max_chain` 从 3 升到 6，`exp_succ` 从约 1.11 升到约 1.50。这与链地址的期望公式 `1 + α/2` 很接近。
- `exp_fail = n/m = α`，这是“查询哈希均匀分布”时的理论失败成本。
- `miss_avg` 是实际测得的 1000 个不存在键的平均探测次数，量级也随着装载因子上升而增加。它不一定精确等于 `α`，因为具体键的落点、空桶比例和哈希分布都会影响样本均值。
- `hit` 列是某个存在键的实测探测次数，通常很小，说明在桶内很快能比较到。

关键结论：**在哈希分布正常时，装载因子上升会让链变长、探测次数增加，但只要 α 有上界，平均成本仍然是常数级。**

### 步骤 5：观察弱哈希下的碰撞

再看 `FirstCharHash`：

- 所有键都以 `u` 开头，所以全部落在同一个桶。
- `max_chain = n`，`avg_nonempty = n`，`exp_succ ≈ n/2`，实际查找一个键平均要走半条链，失败查找要走完整条链。
- `exp_fail` 仍然显示 `n/m`，但这是理论列，它假设查询哈希均匀分布；弱哈希显然违反了这个假设。实际 `miss_avg = n`，说明**只看装载因子不能预测最坏情况**。
- `alpha` 从 0.25 到 0.9，`max_chain` 始终等于 `n`，因为冲突不是由装载因子造成的，而是由哈希函数把键集中在一起造成的。

这就是恶意碰撞攻击的缩小版：攻击者不需要让 `α` 变大，只要让所有键落到同一个桶，就能让单次操作退化为 O(n)。

### 步骤 6：改变桶数，隔离装载因子的影响

固定元素数量，改变桶数，观察 `α` 和探测次数的关系。脚本的第二个参数可以指定固定元素数：

```bash
python3 hash_bench.py 1024 1024
python3 hash_bench.py 4096 1024
python3 hash_bench.py 8192 1024
```

例如，当 `n = 1024` 时：

- `m = 1024`，`α ≈ 1.0`，链更长。
- `m = 4096`，`α = 0.25`，链更短。
- `m = 8192`，`α = 0.125`，链更短，但空桶更多、内存占用更大。

记录每组 `(m, n, α, max_chain, exp_succ, miss_avg)`，你应该能观察到：

- 正常哈希下，`α` 越低，平均链长和探测次数越小。
- 但 `α` 过低会浪费桶数组内存，形成“空间换时间”的权衡。
- 弱哈希下，改变 `m` 不能解决集中冲突，因为所有键仍然落在同一个桶；这再次说明**哈希质量与装载因子是两个独立因素**。

### 步骤 7：验证 rehash 后的引用边界

如果你有 C++ 环境，可以编译第 2.2 节的 `unordered_map` 示例，确认：

- `rehash` 后 `bucket_count` 改变。
- 指向元素的指针地址不变，`*p` 仍可读。
- 旧迭代器不能再用。

如果没有 C++ 环境，可以用 Python 验证“迭代期间改变字典大小”的边界：

```bash
python3 - <<'PY'
d = {"a": 1, "b": 2}
try:
    for k in d:
        d["c"] = 3
except RuntimeError as e:
    print("RuntimeError:", e)
PY
```

预期会看到类似 `dictionary changed size during iteration` 的错误。这说明：字典内部结构变化时，正在进行的迭代不能继续依赖。**不要一边遍历哈希表一边插入或删除；需要修改时先收集键，再统一处理，或使用显式的快照。**

## 5. 自测题（3 道，附答案）

### 题 1：为什么“平均 O(1)”需要假设？在什么情况下会退化？

**答案：** 哈希表的平均 O(1) 不是无条件成立的。它假设哈希函数把键较均匀、独立地散布到桶中，装载因子 `α = n/m` 被 rehash 控制在常数上界，键的哈希和相等比较成本可视为常数，并且输入不是攻击者刻意构造的碰撞集合。满足这些条件时，链地址的期望查找成本约为 `1 + α/2`（成功）或 `α`（失败），是常数级。

退化的情况包括：

- 哈希函数很弱或固定可预测，大量键落入同一个桶，链地址退化为长链表，开放寻址退化为长探测，最坏 O(n)。
- 桶数固定而元素持续增长，`α` 随 `n` 增长，平均链长也随之增长。
- 单次 rehash 需要搬运 `n` 个元素，虽然均摊 O(1)，但这次操作本身是 O(n)，会造成尾延迟。
- 键很长，哈希和比较本身是 O(键长度)，不再是 O(1)。

所以“平均 O(1)”描述的是期望和均摊，不是最坏延迟上界。

### 题 2：`std::unordered_map` rehash 后，指向元素的指针、引用和迭代器分别怎样？

**答案：** 对常见的节点式 `std::unordered_map` 实现，标准保证 rehash 会使迭代器失效，但不使指向元素的指针和引用失效，因为元素节点本身没有被搬走，只是桶数组和链接关系重建了。`end()` 迭代器不应长期缓存；`erase` 只使被删除元素的迭代器、指针和引用失效。桶号会改变，所以缓存的 `bucket(key)` 结果或自己算的 `h(key) % m` 不能继续使用。

要注意，这个结论不能推广到所有哈希表。开放寻址或把元素连续存放在数组里的实现，rehash 会搬动元素，指针、引用、迭代器通常全部失效；自定义链地址如果元素存在 `std::vector` 里，也会因搬移而失效。正确做法是查具体容器的文档，并区分“元素地址是否稳定”和“迭代器是否有效”这两件事。

### 题 3：开放寻址删除为什么需要墓碑？链地址为什么不需要？

**答案：** 开放寻址的查找依赖探测序列，遇到空槽就认为键不存在。如果删除时直接把槽设为 `EMPTY`，会截断探测链：某个键可能被放在更后面的槽里，但查找在删除位置就提前停止，误判不存在。墓碑 `DELETED` 表示“这里曾经有元素，但已删除”，查找遇到墓碑会继续探测，插入则可以复用墓碑。墓碑积累过多会拖慢查找，需要 rehash 清理。

链地址的每个桶是一条独立的链，删除时只要找到节点并修改前驱指针，把节点从链上摘掉即可。查找其他元素不依赖“空槽”作为终止条件，而是走到链尾，所以不需要墓碑。代价是链地址需要额外的节点和指针，缓存局部性通常不如开放寻址。

## 7. 小结与前后置关系

哈希表的核心可以压缩成一句话：**用哈希函数把键缩小到一个桶，用相等关系在桶内确认，用 rehash 把装载因子维持在可控范围，用链地址或开放寻址处理冲突。**

三个要点分别对应三个工程问题：

- **哈希函数与相等关系**决定“能不能找对”。哈希负责定位，相等负责判定；两者覆盖的字段必须一致，键在插入后不能随便修改。
- **负载因子和 rehash**决定“平均快不快、扩容时抖不抖”。`α` 有上界时期望成本才是常数；rehash 均摊 O(1)，但单次 O(n)，并且会改变桶号和迭代器有效性。
- **开放寻址与链地址**决定“空间、缓存、删除、引用稳定性怎么取舍”。开放寻址局部性好，但删除和引用稳定性更复杂；链地址删除简单，但指针跳转和额外内存有代价。

与本课的前置节点 `a-sequence` 的关系也很直接：顺序表/动态数组提供了连续存储和按索引 O(1) 访问，哈希表的桶数组本身就是一个序列；链地址的每个桶也常用序列存放冲突元素；rehash 时的扩容和搬移，与动态数组扩容在“均摊 O(1)、单次 O(n)、旧引用可能失效”这些问题上是相通的。区别在于：序列用整数下标直接定位，哈希表先把任意键映射成桶号，因此还要额外处理哈希分布、冲突和恶意输入。理解顺序表的扩容边界，再来看哈希表的 rehash，会更容易把“均摊成本”和“引用失效”这两件事分清。
