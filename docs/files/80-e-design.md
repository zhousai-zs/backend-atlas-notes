## 导读

先看本节点的 summary，后面所有内容都围绕它展开：

> 并发模型应围绕状态归属、任务生命周期与过载策略选择，而非只比较锁或协程的单次开销。

这句话把“选并发模型”从性能微比拉回到了架构判断。它至少包含三层意思。

第一层是**状态归属**：哪块可变状态归谁所有、由谁修改、通过什么方式访问。是多个线程靠锁轮流修改同一张表，还是每个分片只有一个执行者，其他代码只能发消息？状态归属决定了你需不需要锁、锁的粒度有多粗、以及一次跨分片操作要付多少协调成本。

第二层是**任务生命周期**：一个请求从进入系统、排队、被执行、被取消，到最后完成或超时，中间经过哪些阶段；每个阶段由谁负责推进；关闭服务时，已经在队列里的任务、正在执行的任务、已经发出但还没确认的任务分别怎么处理。生命周期不清，模型再快也会在停机时丢数据。

第三层是**过载策略**：当到达速率超过处理能力时，系统是让队列无限增长、把延迟推高，还是有界队列加拒绝，还是降级、丢弃低优先级请求，还是把压力反压给上游。过载策略不是“性能优化”，而是模型的一部分，因为它决定了尾延迟和故障时的行为。

这三层都稳定之后，才轮到“锁和协程单次谁更便宜”这种局部问题。单次开销当然要看，但它解释不了为什么一个吞吐更高的方案在 p99 上更差，也解释不了一个基准里更快的方案在停机时更难写对。本节点的 pitfalls 正是这句话的反面：**吞吐最高不必然是延迟或运维成本最优。**

本课沿着三个节点要点推进：

- **Actor 与线程封闭**：把状态关进一个执行者里，用“只有它能碰”代替“大家加锁轮流碰”；线程封闭则是这条思路在对象层面的约束。
- **共享状态与消息传递**：两种协调风格各自的代价。消息传递减少了共享可变状态，但引入了排队、跨分片操作和复制成本。
- **工作窃取、公平性和隔离**：任务怎样分配到执行者，怎样避免某个分片或某个租户把别人饿死，以及隔离边界画在哪里。

三个要点最终服务于同一个目标，也就是本节点的 why：**为复杂服务选择可维护、可观测的执行架构。**

## 学习目标

### goals

- 能解释 Actor 与线程封闭。
- 能独立完成：对同一 KV 负载比较分片锁、每分片事件循环与任务队列，写 ADR。

### acceptance

- 报告包含正确性、尾延迟和停机行为。
- 说明选择在何种负载下失效。

### 把验收翻译成可检查产物

“能解释”和“能独立完成”都太容易被“我看懂了”糊弄过去。把两条 acceptance 翻译成看得见、摸得着的东西：

- **“报告包含正确性、尾延迟和停机行为”**：你的报告不能只有一张吞吐柱状图。正确性部分要写清楚每个模型保证什么、不保证什么，例如“单 key 读改写线性化”“多 key 操作不原子”“重复提交需要幂等键”；并用至少一个并发正确性测试去验证它，而不是只靠肉眼读代码。尾延迟部分要给出 p50、p99、p999，最好把排队时间和执行时间分开，并说明测试是开环还是闭环、键分布是均匀还是倾斜。停机行为部分要写清楚收到停止信号后：是否停止接收新请求、队列里剩多少、正在执行的任务如何收尾、是否取消、最长排水时间、有没有已确认的写丢失、进程退出码是什么。三块缺一不可。
- **“说明选择在何种负载下失效”**：你的 ADR 必须有一段“失效模式与重访条件”。不是泛泛写“高负载可能有问题”，而是写出可观测的触发条件，例如“当单分片 QPS 超过某个量级、或 p99 排队时间超过预算、或热 key 占比超过某个比例时，每分片事件循环会出现队头阻塞，此时应改为……”。这一段是 acceptance 第二条，也是把“选择”从个人偏好变成工程决策的关键。

### 先修自检

- e-cancel：能说清一个任务在提交、排队、执行、取消、完成之间有哪些状态；能解释为什么取消不是“把线程杀掉”，而是协作式的状态检查；能说出关闭时为什么必须先停止接收、再排水、最后 join。
- d-threadpool：能写出一个固定线程池的基本结构——任务队列、工作线程循环、提交接口、停止标志；能解释队列有界和无界在过载时的行为差异；能说出为什么关闭时要把队列里的任务处理完或明确丢弃。
- e-lockfree：能解释原子读改写与内存序的基本作用；能说出无锁不等于无等待，也不等于更快；能理解为什么无锁结构仍然需要仔细设计对象回收和生命周期。

如果这三条里有任何一条说不清，先回去补。本课不会重新讲线程池怎么起线程，也不会重新讲原子操作怎么写；它假设你已经知道这些零件，重点是把零件装成一套能论证边界的架构。

## 为什么后端要懂

本节点 why 的原话是：**为复杂服务选择可维护、可观测的执行架构。** 在真实后端里，这句话对应的不是“哪种并发库更酷”，而是几类会直接影响 SLO 和故障处理的决策。

### 场景一：KV 缓存的三种写法，三种深夜告警

假设你负责一个进程内 KV 缓存，键是业务对象 ID，值是序列化后的记录或指针。团队里同时存在三种写法：

- 一张全局 `unordered_map`，外面一把大锁；
- 按 key 哈希成 64 个分片，每个分片一把锁；
- 每个分片一个事件循环，分片内的所有读写都在该分片的执行线程上完成。

这三种写法在“单次 get 要多少纳秒”上可能差不多，甚至在低并发基准里全局大锁还更快，因为代码简单、缓存局部性好。但线上出问题时，它们表现完全不同：全局大锁在热点 key 上会把所有线程排成一队，p99 直接抬升；分片锁在跨分片批量读时可能死锁，或者因为加锁顺序不一致而卡住；每分片事件循环遇到一个慢 handler，整个分片的请求都排在它后面，形成队头阻塞。选型时只比较单次开销，等于只看了最容易看的那一项。

### 场景二：任务队列把过载藏起来

另一个常见场景是：前端把每个请求包装成任务，提交到一个共享队列，后端用固定大小的线程池消费。低负载时一切正常，压测数字也漂亮。但队列是无界的，过载时任务不会消失，只会堆积；延迟从几十毫秒涨到几秒，内存也跟着涨，最后触发 OOM 或者被上游超时重试放大。

从“吞吐”看，这个模型在过载前可能最高；从“尾延迟”和“运维成本”看，它可能最差。这正是节点 pitfalls 说的事情：吞吐最高不必然是延迟或运维成本最优。模型选择必须把过载策略一起选进去，而不是事后补一个“队列太长就告警”。

### 场景三：停机时才发现生命周期没设计

还有一个更隐蔽的场景：服务收到 SIGTERM，线程池开始关闭。有的任务已经写入了下游，有的任务还在队列里，有的任务正卡在等待跨分片响应。如果没有明确的生命周期和停机协议，常见结果是：已确认的写丢了、同一个任务被执行两次、关闭时间超过编排系统给的 grace period，最后被 SIGKILL。

这类问题在功能测试里几乎发现不了，因为功能测试不会在持续写入的同时发停止信号。它属于 acceptance 里的“停机行为”，必须在选型阶段就写进模型，而不是上线后补。

### 场景四：消息传递看起来优雅，跨分片却很贵

Actor 风格很吸引人：每个对象只被一个执行者拥有，大家发消息，不共享内存。但真实 KV 负载里经常有“批量读多个 key”“按前缀扫描”“事务性更新两个 key”这类操作。如果每个 key 归一个 actor，跨 key 操作就变成跨 actor 协调：要么做两阶段提交，要么接受最终一致，要么把相关 key 放到同一个分片里。消息传递简化了共享状态，但排队、跨分片操作和复制成本会增加，这是节点 tradeoffs 的原话。选型时必须把这些成本算进去。

这些场景的共同点是：它们都不是“锁快还是协程快”能回答的。它们问的是状态归谁、任务活多久、过载怎么办、停机怎么收尾。这就是本课要建立的判断框架。

## 从直觉到原理

下面三个要点不是并列的知识点，而是一条设计流水线：先把状态收进一个所有者（要点一），再决定所有者之间怎么通信、共享状态还剩下多少（要点二），最后决定任务如何在多个所有者之间分配、怎样保证公平和隔离（要点三）。走完这三步，你才有资格写“可证明边界”。

### 要点一：Actor 与线程封闭

#### 直觉：与其让所有人小心地共享，不如让一个人独占

先问一个朴素的问题：为什么共享内存并发这么难写？

因为共享可变状态把两件事耦合在了一起：**数据放在哪里**和**谁有权修改它**。只要一块内存可以被多个线程直接读写，你就必须为每一种访问路径证明同步正确：读的人有没有持锁、写的人有没有持锁、锁是不是同一把、临界区有没有遗漏、对象生命周期有没有跨越解锁。访问路径越多，证明义务越多。

Actor 模型换了一个思路：把“谁有权修改”收窄到一个执行者。每个 actor 拥有自己的状态，状态不对外暴露可变引用；外部想读或改，只能发消息。actor 内部通常单线程地处理消息，因此对自身状态的所有访问天然是串行的，不需要为每个字段再加锁。这里的“单线程”不一定是绑定某个 OS 线程，而是“同一时刻只有一个消息在处理”。

线程封闭（thread confinement）是同一思想在对象层面的说法：某个对象只允许被一个线程访问。它可以靠约定、靠封装、靠运行时断言来维持。典型形式包括：

- 把对象放在某个分片结构里，分片的执行线程是唯一访问者；
- 用 `thread_local` 保存只属于当前线程的缓存或缓冲区；
- 用队列把对象的所有权转移给下一个执行者，转移后原线程不再触碰；
- 用类型或接口把“可变访问”限制在所有者内部，外部只能拿到快照或消息句柄。

一句话概括：**Actor 是“状态 + 邮箱 + 单线程处理”的组合；线程封闭是“这个对象只归这个执行者碰”的约束。**

#### Actor 的四个组成部分

把 Actor 拆开看，通常会看到四样东西：

1. **私有状态**：只有 actor 自己的处理逻辑能直接读写。它可以是几个字段，也可以是一整张 map。
2. **邮箱 / 消息队列**：外部把消息放进来，actor 按某种顺序取出处理。邮箱可以是无界的，也可以是有界的；可以 FIFO，也可以带优先级。
3. **处理循环**：从邮箱取消息、执行、产生新消息或副作用、回到取消息。这个循环在任一时刻只处理一条消息，因此对私有状态是串行的。
4. **地址 / 句柄**：外部通过它发送消息，而不是通过它拿到状态指针。地址可以是对象 ID、分片 ID、队列句柄，或者是 Asio 里的 strand 加 executor。

用伪代码表示，一个极简 actor 长这样：

```cpp
class CounterActor {
public:
    void send(Increment msg) {
        {
            std::lock_guard<std::mutex> lk(mu_);
            mailbox_.push_back(msg);
        }
        cv_.notify_one();
    }

    void run() {
        for (;;) {
            Increment msg;
            {
                std::unique_lock<std::mutex> lk(mu_);
                cv_.wait(lk, [&] { return stop_ || !mailbox_.empty(); });
                if (stop_ && mailbox_.empty()) return;
                msg = mailbox_.front();
                mailbox_.pop_front();
            }
            value_ += msg.delta;   // 只有本循环访问 value_
        }
    }

private:
    std::mutex mu_;
    std::condition_variable cv_;
    std::deque<Increment> mailbox_;
    bool stop_ = false;
    long long value_ = 0;      // 私有状态
};
```

注意这个例子里仍然有一把锁，但它保护的是**邮箱**，不是业务状态。业务状态 `value_` 只被 `run()` 所在线程访问，所以不需要锁。这是 Actor 风格最容易被误解的地方：Actor 不是“完全没有同步”，而是把同步集中到消息边界，把业务状态的并发访问消掉。

#### 线程封闭的边界在哪里

线程封闭听起来很安全，但它有一个前提：**不能有逃逸**。只要有人拿到了 actor 私有状态的可变引用，或者把对象的所有权转移出去却继续使用，封闭就破了。

常见的逃逸路径有这些：

- **回调捕获了 `this` 或成员引用**：actor 把 `&value_` 传给一个异步回调，回调在另一个线程执行，封闭失效。
- **返回内部容器的引用**：`const std::unordered_map&` 看起来是只读，但如果调用方把它转成非 const，或者容器本身在别处被修改，仍然会出问题。
- **共享 `shared_ptr`**：两个 actor 都持有同一个可变对象的 `shared_ptr`，就等于共享状态又回来了。
- **全局缓存 / 单例**：actor 内部顺手访问了一个全局 map，这个 map 不受 actor 的串行保护。
- **析构发生在错误的线程**：对象在 actor A 的线程创建，却在 actor B 的线程销毁；如果析构访问了线程局部资源或依赖所有者线程，就会出问题。
- **跨分片直接调用**：为了“省一次消息”，在分片 A 的 handler 里直接调用分片 B 的对象方法。

所以线程封闭不是一个可以声明一次就永久成立的属性，而是一条需要**持续维护的约束**。工程上常见的加固手段是：

- 在对象里记录 `owner_thread_id`，在每个公开方法入口断言当前线程等于所有者；调试构建开启，生产构建可采样。
- 把可变状态放在私有实现里，公开接口只暴露值语义的查询和消息发送。
- 用所有权转移代替共享：消息里放 `std::unique_ptr` 或值，而不是共享引用。
- 用静态检查或代码审查规则禁止跨分片直接调用；所有跨分片路径必须经过消息层。
- 用 TSan/ASan 跑并发回归，至少能抓到一部分逃逸导致的竞争和生命周期错误。

#### “串行执行”不等于“绑定线程”

Actor 和每分片事件循环经常被描述成“单线程”，但更准确的说法是**串行执行**。这两者的区别很重要：

- **绑定线程**：对象只能在一个固定的 OS 线程上访问。线程封闭最严格的形式。
- **串行执行**：同一时刻只有一个执行上下文在处理该对象，但不同的消息可能在不同线程上执行。只要前一条处理完、后一条才开始，并且中间有正确的同步，状态仍然是安全的。

Boost.Asio 的 strand 就是后者的典型：handlers 关联到同一个 strand 后，不会并发执行；但它们可能由线程池里的不同线程执行。strand 不保证“永远是同一个线程”，它保证的是“不会同时有两个 handler 在跑”。这也意味着：如果你在 handler 里把 `this` 泄漏给外部线程，或者从外部线程直接调用对象方法而不经过 strand，串行保证就被绕过了。sourceStudy 要你读的正是这层约束。

#### 为什么这个要点能服务“可证明边界”

一旦状态被收进一个所有者，很多证明义务会变得清晰：

- **数据竞争**：只要没有逃逸，所有者内部的状态不存在跨线程并发访问，数据竞争的可能性被结构性消除。
- **顺序**：同一 actor 的消息按邮箱顺序处理，单 key 的读改写天然串行；跨 actor 的顺序则需要额外协议。
- **生命周期**：actor 的创建、运行、停止可以写成一个状态机；消息的所有权转移也让对象的销毁时机更容易界定。
- **可观测性**：每个 actor / 分片可以独立统计邮箱深度、处理耗时、拒绝数，故障定位的粒度更细。

代价是：所有跨 actor 的交互都变成消息，消息要排队、要序列化、要处理跨分片语义。这就是下一个要点要展开的内容。

### 要点二：共享状态与消息传递

#### 两种协调风格，不是两个阵营

共享状态和消息传递经常被讲成对立的两派：一派说锁是万恶之源，一派说消息传递只是把锁藏起来。更准确的说法是：它们解决的是同一个问题的两种成本分布。

- **共享状态**：多个执行者直接访问同一块内存，用锁、原子操作、读写锁等建立同步。优点是读写路径短、没有消息复制、跨线程可见性直接；缺点是把正确性责任分散到每一个访问点，需要证明每一处都同步正确，锁竞争还会直接影响尾延迟。
- **消息传递**：执行者不直接共享可变内存，而是把值或所有权传给另一个执行者，由对方在自己的串行上下文里处理。优点是状态归属清晰、单所有者内部不需要锁、消息边界天然是可观测点；缺点是排队、复制/序列化、跨分片协调，以及“消息发出去之后什么时候算完成”的语义更复杂。

节点 tradeoffs 说得很准确：**消息传递简化共享状态，但排队、跨分片操作和复制成本增加。** 这句话不是否定消息传递，而是提醒你：简化不会凭空发生，它把复杂度从“锁的正确性”转移到了“排队和协调”。

#### 消息传递的四种成本

##### 成本一：排队

消息不会凭空被处理，它要进邮箱或队列。队列一旦形成，就有三个问题：

1. **延迟**：消息在队列里等待的时间会计入端到端延迟。低负载时队列接近空，这项成本看不出来；高负载时它会迅速主导 p99。
2. **内存**：无界队列在过载时会把内存吃光；有界队列则会拒绝或阻塞，拒绝策略又会影响上游。
3. **顺序**：同一发送者到同一接收者的消息通常保持顺序，但不同发送者之间、跨多个接收者之间，不保证全局顺序。如果你的业务依赖“先写后读”，必须把这两条消息路由到同一个 actor / 分片，或者携带版本号。

一个常见的错误是：看到 actor 模型“无锁”，就默认它低延迟。实际上，如果邮箱是无界 FIFO，过载时它的尾延迟可能比一把分片锁更差，因为请求在前面排了很长的队，而分片锁至少会让部分线程继续推进。

##### 成本二：跨分片操作

单 key 操作很容易映射到一个 actor；但真实负载里常有：

- 批量读：`MGET k1 k2 ... kn`，这些 key 可能落在不同分片。
- 条件更新：读 key A，根据结果写 key B。
- 事务：要么两个 key 都更新，要么都不更新。
- 扫描：按前缀或范围遍历，天然跨分片。

跨分片操作需要协调，常见方案各有代价：

- **串行扇出**：向多个 actor 发请求，等所有回复。延迟由最慢的分片决定，任何一个分片过载都会拖慢整体。
- **两阶段提交**：先准备、再提交，需要额外的日志、超时和恢复逻辑；参与者故障时可能阻塞。
- **Saga / 补偿**：每个分片本地提交，失败后补偿。实现简单一些，但中间状态对外可见，业务要能接受。
- **共分片**：把需要一起操作的 key 设计成落在同一个分片。这能恢复本地性，但会限制数据模型，还可能制造热点。

所以“每个 key 一个 actor”在单 key 场景很优雅，在跨 key 场景可能非常贵。选型时要把负载里的跨分片比例作为一个一阶参数，而不是事后才发现。

##### 成本三：复制

如果 actor 的状态需要复制到多个节点或线程以提高可用性，就会引入复制成本：写要传播、读可能读到旧值、故障切换要选主、网络分区要处理一致性。复制不是 Actor 模型独有的，但 Actor 的“状态私有”会让复制边界更清晰：你复制的是 actor 的状态快照或消息日志，而不是随意共享的内存。清晰不等于便宜，共识、日志、快照传输都是实打实的开销。

##### 成本四：语义与生命周期

消息传递把“调用”变成了“发送 + 等待回复”或“发送后不管”。这会带来新的语义问题：

- 消息丢了怎么办？需要超时、重试、幂等键。
- 回复晚了，调用方已经取消，结果还要不要应用？需要取消协议和版本检查。
- 接收者崩溃，邮箱里的消息怎么办？需要持久化或明确丢弃。
- 关闭时邮箱里还有消息，算已接受还是未接受？需要停机协议。

这些都不是“加个队列”能自动解决的，它们属于任务生命周期设计。

#### 共享状态并没有消失

即使采用消息传递，共享状态通常也没有完全消失，只是被压缩到了几个地方：

- **队列本身**：多个生产者往同一个邮箱投递，邮箱的内部结构仍然是共享的，需要同步。
- **路由表**：key 到分片的映射是共享只读的，但扩容、迁移时会变。
- **全局资源**：内存分配器、日志、指标、连接池仍然是进程级共享。
- **跨分片索引**：二级索引、聚合统计往往需要跨 actor 共享或汇总。

所以正确的说法不是“消息传递消灭了共享状态”，而是“消息传递把共享状态收敛到少数边界，并让业务状态的所有权变得明确”。这些边界仍然需要并发正确性证明，只是数量少了、位置集中了。

#### 三种候选模型：同一 KV 负载的三条路

节点 practice 要求对同一 KV 负载比较三种模型。为了避免抽象讨论，先把三条路摆清楚。

##### 模型 A：分片锁

把 key 哈希到 N 个分片，每个分片一张 map 加一把锁。工作线程直接调用 KV 接口，进入分片时加锁，离开时解锁。

```cpp
struct Shard {
    mutable std::mutex mu;
    std::unordered_map<std::string, std::string> map;
};

class ShardedKV {
public:
    explicit ShardedKV(size_t n) : shards_(n) {}

    std::optional<std::string> get(const std::string& key) {
        Shard& s = shard_for(key);
        std::lock_guard<std::mutex> lk(s.mu);
        auto it = s.map.find(key);
        if (it == s.map.end()) return std::nullopt;
        return it->second;
    }

    void put(const std::string& key, std::string value) {
        Shard& s = shard_for(key);
        std::lock_guard<std::mutex> lk(s.mu);
        s.map[key] = std::move(value);
    }

private:
    Shard& shard_for(const std::string& key) {
        return shards_[std::hash<std::string>{}(key) % shards_.size()];
    }

    std::vector<Shard> shards_;
};
```

- **状态归属**：状态仍然共享，访问权由锁临时授予。
- **生命周期**：请求就是一次函数调用，栈上完成；停机时停止接收、等待在途调用返回、销毁 map。
- **过载**：没有队列，压力直接表现为线程阻塞和锁竞争；上游超时或线程池队列会承接溢出。
- **优点**：实现简单、单 key 延迟低、没有消息复制、调试直观。
- **缺点**：热点 key 会让单个分片的锁成为串行点；跨分片操作要同时持多把锁，容易死锁；锁竞争会直接抬高尾延迟。

##### 模型 B：每分片事件循环

每个分片绑定一个执行者（一个线程或一个串行 executor），分片内的所有操作都提交到该执行者，由它串行处理。分片状态只被这个执行者访问，因此不需要锁。

```cpp
struct Op {
    enum class Kind { Get, Put } kind;
    std::string key;
    std::string value;
    std::promise<std::optional<std::string>> done;
};

class ShardLoop {
public:
    void submit(Op op) {
        {
            std::lock_guard<std::mutex> lk(mu_);
            queue_.push_back(std::move(op));
        }
        cv_.notify_one();
    }

    void run() {
        for (;;) {
            Op op;
            {
                std::unique_lock<std::mutex> lk(mu_);
                cv_.wait(lk, [&] { return stop_ || !queue_.empty(); });
                if (stop_ && queue_.empty()) return;
                op = std::move(queue_.front());
                queue_.pop_front();
            }
            execute(op);   // 只在本线程访问 map_
        }
    }

private:
    void execute(Op& op) {
        if (op.kind == Op::Kind::Get) {
            auto it = map_.find(op.key);
            op.done.set_value(it == map_.end()
                ? std::nullopt
                : std::optional<std::string>(it->second));
        } else {
            map_[op.key] = std::move(op.value);
            op.done.set_value(std::nullopt);
        }
    }

    std::mutex mu_;
    std::condition_variable cv_;
    std::deque<Op> queue_;
    bool stop_ = false;
    std::unordered_map<std::string, std::string> map_;  // 只被 run() 线程访问
};
```

- **状态归属**：分片状态归该分片的执行者独占，外部只能通过 `submit` 发消息。
- **生命周期**：操作作为消息进入队列；停机时先停止接收，再让执行者把队列处理完或按策略丢弃。
- **过载**：每个分片有自己的队列；队列长度就是该分片的压力信号。慢操作会阻塞整个分片。
- **优点**：分片内无锁、单 key 顺序天然成立、每分片指标清晰、状态归属最容易证明。
- **缺点**：队头阻塞；热点分片会成为瓶颈；跨分片操作需要扇出和等待；执行者一旦阻塞（例如同步 I/O），整片停摆。

##### 模型 C：任务队列

前端把每个请求包装成任务，提交到一个共享的有界队列，固定数量的工作线程从队列取任务执行。KV 状态的正确性由任务内部的同步策略保证，例如按 key 分片的锁，或者按 key 路由到固定工作线程。

```cpp
class TaskQueueKV {
public:
    TaskQueueKV(size_t workers, size_t capacity)
        : queue_(capacity), kv_(64) {
        for (size_t i = 0; i < workers; ++i) {
            threads_.emplace_back([this] { worker_loop(); });
        }
    }

    bool submit(std::function<void()> task) {
        return queue_.try_push(std::move(task));   // 有界：满了就拒绝
    }

private:
    void worker_loop() {
        for (;;) {
            std::function<void()> task;
            if (!queue_.pop(task)) return;          // 关闭且队列空
            task();
        }
    }

    BoundedQueue<std::function<void()>> queue_;
    ShardedKV kv_;                                   // 任务内部再处理同步
    std::vector<std::thread> threads_;
};
```

- **状态归属**：任务本身不拥有 KV 状态；状态仍由 `ShardedKV` 的锁保护。任务队列负责调度，锁负责正确性。
- **生命周期**：任务从提交到执行之间有一段排队期；关闭时要区分“已入队未执行”“执行中”“已完成”。
- **过载**：有界队列 + 拒绝是显式策略；无界队列则会把过载变成延迟和内存问题。
- **优点**：任务粒度灵活、容易做优先级和限流、工作线程利用率高、可以接工作窃取。
- **缺点**：队列本身是竞争点；任务粒度过细会增加调度开销；如果没有按 key 串行化，读改写仍可能丢失更新；关闭和取消语义更复杂。

三种模型不是互斥的：模型 C 可以用模型 A 做状态保护，模型 B 可以看成“每个分片一个单线程任务队列”。把它们并列，是为了逼你回答：状态归谁、任务活多久、过载怎么处理。

#### 选择的第一原则：先写契约，再选模型

在比较性能之前，先写下这个 KV 服务的契约：

- 单 key 的 `get` 和 `put` 是否要求线性化？读改写是否要求原子？
- 跨 key 的批量操作是否要求原子？如果不要求，允许看到什么中间状态？
- 同一个 key 的多次写是否要求按提交顺序生效？
- 重复提交同一个请求是否要求幂等？幂等键是什么？
- 过载时允许拒绝吗？拒绝后客户端看到什么错误？
- 停机时已确认的写是否必须保留？未确认的写允许丢吗？
- 尾延迟预算是什么？p99 还是 p999？预算是端到端还是服务端？

这些问题的答案会直接排除一些模型。例如：如果要求跨 key 原子，模型 B 的每 key 一个 actor 就很难做；如果要求严格单 key 顺序，模型 C 必须加按 key 串行化；如果停机零丢失，三种模型都需要持久化和确认协议，而不只是内存队列。

#### 可证明边界的第一层：把“保证”写成命题

“可证明边界”不是要求你写形式化证明，而是要求你把保证写成可以被检验的命题。例如：

- **命题 1（单 key 线性化）**：对任意 key，所有成功的 `put` 和 `get` 可以排成一个全序，且每个 `get` 返回它之前最近一次 `put` 的值。
- **命题 2（跨 key 非原子）**：`MGET` 不保证快照一致性，可能观察到部分新值、部分旧值。
- **命题 3（停机有界）**：收到停止信号后，最多 T 毫秒内停止接收新请求；已确认的写不丢失；未执行的排队任务返回明确错误。
- **命题 4（过载有界）**：队列长度不超过 C；超过时拒绝新请求；拒绝不会导致已接受请求被丢弃。

只有命题清楚，你才能设计测试去验证，也才能在 ADR 里写“这个选择在什么条件下失效”。如果契约本身是模糊的，任何模型都可以声称自己正确。

#### 可证明边界的第二层：为每个命题找到证据

证据可以分层：

- **代码结构**：状态私有、接口不暴露可变引用、跨分片调用必须经过消息层。这是“按构造正确”的部分。
- **并发测试**：多线程对同一 key 做读改写，检查最终计数；用 barrier 放大交错；用 TSan 检查数据竞争。
- **模型检查 / 线性化检查**：记录操作历史，用离线检查器判断是否可线性化；适合核心数据结构，不一定适合整个服务。
- **故障注入**：在负载中发停止信号、注入超时、让某个分片变慢，观察是否满足停机与过载命题。
- **观测数据**：队列深度、拒绝数、p99、排水时间。它们不能证明正确性，但能证明边界在何时被逼近。

这就是为什么 acceptance 要求报告同时包含正确性、尾延迟和停机行为：三者分别对应“逻辑对不对”“边界有多近”“退出干不干净”。

### 要点三：工作窃取、公平性和隔离

#### 任务分配不是细节，它会改变模型的性质

一旦有多个执行者，就必须回答：任务怎么分配到执行者？常见策略有：

- **静态分片**：按 key 哈希固定到某个执行者。模型 B 就是这种。
- **共享队列**：所有工作线程从同一个队列取。模型 C 的简单形式。
- **每工作线程队列 + 工作窃取**：每个线程有自己的队列，空闲时从别的线程“偷”任务。
- **路由到 key 的所属执行者**：为了保证单 key 顺序，任务必须回到该 key 的分片。

策略不同，正确性、尾延迟和隔离性都不同。节点把“工作窃取、公平性和隔离”放在同一个要点里，是因为它们经常一起出现：窃取提高利用率，但可能破坏局部性和公平性；隔离限制干扰，但可能降低利用率。

#### 工作窃取：用局部性换利用率

工作窃取的基本结构是：

- 每个工作线程有一个双端队列（deque）。
- 线程自己产生的任务压入自己的队列，通常从一端取（LIFO），这样最近的任务还在缓存里，局部性好。
- 空闲线程从其他线程的另一端“偷”任务（FIFO），这样偷到的是较老的任务，减少与所有者的冲突。
- 窃取需要原子操作或锁来协调 deque 的两端，成本比本地取任务高得多。

它解决的问题是**负载不均**：静态分配时，有的线程早早干完，有的线程还在排队；工作窃取让空闲线程去帮忙，从而提高 CPU 利用率、降低平均延迟。

但它带来几个新问题：

- **局部性丢失**：被偷走的任务可能在另一个 CPU 上执行，缓存和 NUMA 局部性变差。
- **顺序破坏**：如果同一个 key 的任务被偷到不同线程，单 key 的串行保证就没了；所以工作窃取通常用于“任务之间无顺序依赖”的场景，或者窃取后仍然路由回 key 的所有者。
- **窃取开销**：高竞争时，窃取本身会成为开销；deque 的实现要非常小心。
- **尾延迟不一定改善**：如果任务粒度太粗，一个长任务仍然会卡住；如果粒度太细，调度开销又会上升。

所以“用了工作窃取”不等于“尾延迟就好了”。它主要改善的是**平均利用率和负载不均**，对单点长任务、锁竞争、下游阻塞无能为力。

#### 公平性：谁在排队，谁会被饿死

公平性问的是：在所有等待的任务中，调度器是否会给每个任务合理的执行机会，还是某些任务会被无限期推迟。

在 KV 服务里，不公平的常见来源有：

- **热点 key**：同一个 key 的请求都排到同一个分片，其他 key 的请求被堵在后面。
- **大请求**：一个批量扫描占用分片很久，小请求只能等。
- **租户 / 优先级**：高优先级请求持续到达，低优先级请求永远排不上。
- **工作窃取偏向**：某些队列总被优先偷，另一些队列长期得不到帮助。
- **锁的不公平**：某些 mutex 不保证先来先得，等待线程可能被反复插队。

公平性不是“绝对平均”，而是与业务契约匹配。你可以选择：

- **FIFO**：简单、可预测，但大请求会阻塞小请求。
- **优先级队列**：保护关键请求，但低优先级可能饿死，需要老化机制。
- **每个租户独立队列 / 配额**：隔离干扰，但会降低全局利用率。
- **轮转 / 加权公平队列**：在吞吐和公平之间折中，实现更复杂。

关键是把公平性写成可观测的指标：每个分片的队列深度、每个租户的等待时间、拒绝率、p99 按租户拆分。没有这些指标，“公平”只是口号。

#### 隔离：把故障和压力关在笼子里

隔离（bulkhead）的思路是：不要让一个故障或一个热点影响整个系统。常见隔离维度包括：

- **分片隔离**：每个分片独立队列、独立执行者。一个分片过载，不影响其他分片。
- **租户隔离**：每个租户独立配额或独立线程池，防止一个租户打满全局。
- **资源隔离**：CPU 亲和性、cgroup、独立内存池，防止一个组件拖垮整机。
- **故障隔离**：一个 actor / 分片崩溃或卡住，不传播到其他分片；但同进程内仍然共享地址空间，隔离是有限的。
- **部署隔离**：把不同负载类型的服务拆成不同进程或不同机器。

隔离的代价是资源利用率下降：每个隔离单元都要预留容量，空闲时不能完全共享。所以隔离不是越多越好，而是按故障域和 SLO 来画边界。

在三种模型里的体现：

- **模型 A（分片锁）**：锁本身不提供隔离。一个热点分片会把线程池里的线程都吸过去，其他分片的请求可能没有线程可用；除非你给分片独立的线程池或限流。
- **模型 B（每分片事件循环）**：天然按分片隔离，一个分片慢只影响自己；但分片之间不共享线程，CPU 利用率可能不均衡。
- **模型 C（任务队列）**：队列是全局共享的，一个慢任务会占住工作线程；需要靠优先级、租户队列、独立线程池来做隔离。工作窃取可以缓解空闲，但也可能把热点传播到更多线程。

#### 隔离与可观测性是一体两面

你无法隔离你看不见的东西。每个隔离单元至少要有：

- 队列深度 / 邮箱长度；
- 当前正在处理的任务数和耗时；
- 拒绝数、超时数、取消数；
- p50 / p99 / p999 延迟；
- 错误率和重试率；
- 停机时的剩余任务数和排水时间。

如果所有分片共用一个全局指标，热点分片会被平均值掩盖。模型 B 的一个实际优势就是指标天然按分片拆分；模型 A 和 C 需要额外按分片 / 租户打标签，否则观测不到隔离边界。

#### 可证明边界的第三层：把失效条件写成可触发的事件

到这里，可以把“可证明边界”收束成一个工程写法。对每个模型，回答四个问题：

1. **状态归属命题**：哪些状态是单所有者？哪些仍然是共享的？共享的那些由什么保护？
2. **顺序命题**：哪些操作有顺序保证？是单 key、单分片，还是全局？跨分片看到什么中间状态？
3. **资源命题**：队列 / 邮箱的容量是多少？满了以后发生什么？内存上限是多少？
4. **生命周期命题**：取消、超时、停机分别怎么处理？哪些状态是终态？排水时间上界是多少？

然后为每个命题写出**失效条件**。例如：

- 模型 A：当单分片 QPS 超过锁能承载的上限，或临界区内出现慢操作时，锁竞争会让 p99 超标；跨分片操作在加锁顺序不一致时会死锁。
- 模型 B：当某个分片的队列持续增长，或单个 handler 执行时间超过尾延迟预算时，队头阻塞会让该分片所有请求超时；当 key 分布倾斜时，热点分片先饱和。
- 模型 C：当到达速率持续超过消费速率且队列无界时，排队延迟和内存会同时失控；当任务缺少按 key 串行化时，读改写会丢失更新；当关闭时没有排水协议时，已确认的写可能丢。

这些句子就是 acceptance 第二条要的内容：不是“高负载可能有问题”，而是“在什么负载特征下、哪个指标先坏、为什么”。

## 常见误区与设计权衡

前面的原理部分给出了三条设计轴。这一节把实际选型时最容易犯的错误集中列出来，并逐条对应到节点的 pitfalls 与 tradeoffs。

### 误区一：只拿单次操作开销做决定

**错误做法**：写一个单线程微基准，测 `lock/unlock` 和“发一条消息”的纳秒数，然后得出“消息传递更慢”或“锁更慢”的结论。

**为什么不对**：单次操作开销只是模型成本的一小项。真正的差异在竞争、排队、缓存局部性、尾延迟和停机复杂度上。一个在无竞争时 20ns 的锁，在热点分片上可能让 p99 从 1ms 涨到 50ms；一个单次 200ns 的消息投递，在队列空时看起来慢，但它可能让你完全省掉跨分片的锁和死锁风险。节点 pitfalls 说“吞吐最高不必然是延迟或运维成本最优”，就是提醒你不要用单一维度的微基准替代架构判断。

**正确做法**：先写契约和失效条件，再做端到端负载测试，至少同时看正确性、p50/p99/p999、吞吐、内存、拒绝率、停机排水时间。单次开销可以作为解释现象的辅助数据，不能作为决策的唯一依据。

### 误区二：把“无锁”当成“无等待”或“更快”

**错误做法**：看到某个模型内部没有 mutex，就认为它一定延迟低、不会阻塞。

**为什么不对**：无锁（lock-free）通常只保证系统整体有进展，不保证每个线程有进展；无等待（wait-free）才是每个操作都有界步数。更重要的是，Actor 的“业务状态无锁”往往伴随“邮箱有锁”或“队列有原子操作”；锁只是被移到了消息边界，并没有消失。高竞争下，邮箱的入队/出队、条件变量唤醒、缓存行 bouncing 都可能成为瓶颈。

**正确做法**：问清楚“哪把锁被消掉了、哪把锁被移到了哪里、竞争点转移到了谁身上”。如果竞争点从业务 map 转移到了单个邮箱，热点 key 的尾延迟可能并没有改善。

### 误区三：忽略排队，只测执行时间

**错误做法**：压测时只统计 handler 内部耗时，看到 p99 很低，就认为模型没问题。

**为什么不对**：端到端延迟 = 排队时间 + 执行时间 + 传输/序列化时间。模型 B 和 C 都有显式队列，过载时排队时间会主导 p99。如果你只测执行时间，等于把模型最昂贵的部分排除在观测之外。更隐蔽的是“协调遗漏”（coordinated omission）：闭环压测中，客户端因为服务变慢而降低发送速率，导致你测不到真实用户会经历的等待。

**正确做法**：用开环负载或至少记录“请求进入系统的时间”，把排队时间和执行时间分开统计；在过载区间多取几个点，而不是只测容量以内的漂亮数字。队列深度、拒绝数、超时数要一起看。

### 误区四：把“消息传递”当成“没有共享状态”

**错误做法**：采用 Actor 后，认为再也不会出现数据竞争，于是跨 actor 传递 `shared_ptr`、在 handler 里直接调用别的 actor、或者共享一个全局缓存。

**为什么不对**：消息传递只保证“通过消息边界传递的值/所有权”不共享；一旦你把可变引用、共享指针或全局对象带进来，共享状态就回来了，而且更隐蔽——因为它披着“我们在用 Actor”的外衣。Asio strand 也是同理：它只序列化通过该 strand 调度的 handler，不保护你从别处直接调用的对象。

**正确做法**：把“禁止逃逸”写成代码规则：消息只传值或 `unique_ptr`；公开接口不返回可变引用；跨分片只能发消息；全局缓存要么改成每分片，要么明确加锁并记录在案；在调试构建里断言所有者线程。

### 误区五：没有过载策略，只靠“队列应该不会满”

**错误做法**：使用无界队列，认为“正常流量不会堆积”；或者使用有界队列但不定义满了以后的行为。

**为什么不对**：过载不是异常，是分布式系统的常态：上游重试、热点事件、依赖变慢都会让到达速率超过处理能力。无界队列会把过载转化为延迟和内存增长，最终 OOM；有界队列如果不定义拒绝语义，调用方可能收到模糊错误、无限重试，反而放大压力。

**正确做法**：在 ADR 里明确：队列容量、拒绝条件、拒绝错误码、是否重试、是否降级、是否反压、是否丢低优先级。模型 B 要定义每分片邮箱容量；模型 C 要定义全局队列容量和任务优先级；模型 A 要定义线程池队列和上游超时。没有过载策略的模型不算完成。

### 误区六：把公平性留给“操作系统应该会处理”

**错误做法**：不设计优先级和配额，认为线程调度器会“公平地”分配 CPU。

**为什么不对**：OS 调度器保证的是线程之间的 CPU 时间公平，不是你的业务请求之间的公平。一个热点分片可能占满所有工作线程；一个批量任务可能长时间占住执行者；一个租户可能用大量小请求挤掉另一个租户。这些都不是 OS 能替你解决的。

**正确做法**：按业务契约选择公平性策略：FIFO、优先级、租户配额、轮转。把公平性指标（按分片/租户的等待时间、拒绝率）纳入监控。模型 B 的分片隔离是天然优势，但分片内部仍然需要防止单个大请求阻塞小请求；模型 C 需要额外的调度策略。

### 误区七：忽略停机，把“进程退出”当成“任务结束”

**错误做法**：关闭时直接 `std::terminate`、`detach` 线程，或者只设置一个 `stop` 标志就退出，不等待队列和正在执行的任务。

**为什么不对**：停机会暴露所有生命周期设计的漏洞：已确认的写可能还没落盘、任务可能执行到一半、回调可能引用已销毁的对象、队列里的任务可能永远不执行。`detach` 尤其危险：线程还在访问对象，对象已经析构。节点 acceptance 明确要求报告包含停机行为，就是因为这是模型正确性的一部分。

**正确做法**：设计明确的状态机：`Running → Draining → Stopped`。停止接收新任务；对已入队任务选择“处理完”或“明确拒绝/取消”；给排水设上限；等待工作线程 join；释放资源；记录排水时间、剩余任务数、丢失/重复数。用故障注入在负载中发停止信号，验证这些数字。

### 误区八：把隔离当成免费的

**错误做法**：为每个租户、每个分片、每种请求都开独立线程池，认为隔离越多越安全。

**为什么不对**：隔离需要预留资源，会降低利用率；线程/队列越多，调度和内存开销越大；隔离边界过多还会让全局观测和容量规划变难。隔离应该按故障域和 SLO 来画，而不是按组织结构或代码模块来画。

**正确做法**：先识别真正的故障域：热点 key、慢依赖、大租户、批处理。为这些画边界；其他部分共享资源以提高利用率。每个隔离单元要有独立指标和容量上限，否则只是把问题藏起来。

### 权衡总表

把节点 tradeoffs 展开成一张对照表，方便在 ADR 里引用：

| 维度 | 共享状态（锁） | 消息传递（Actor / 队列） |
| --- | --- | --- |
| 状态归属 | 共享，靠锁临时授权 | 单所有者，边界清晰 |
| 单次延迟 | 无竞争时短 | 多一次入队/出队和调度 |
| 竞争点 | 每个共享对象/分片 | 邮箱、队列、路由 |
| 跨分片操作 | 多锁、需顺序、可能死锁 | 扇出/事务/Saga，延迟由最慢者决定 |
| 顺序保证 | 由锁和临界区决定 | 单 actor 内自然串行，跨 actor 需协议 |
| 过载表现 | 线程阻塞、锁竞争、上游超时 | 队列增长、延迟上升、拒绝 |
| 停机 | 等待在途调用、销毁状态 | 停止接收、排水、处理未完成消息 |
| 可观测性 | 需按分片打点 | 邮箱/队列天然是观测点 |
| 运维复杂度 | 较低，但死锁和锁粒度难调 | 较高，需管理队列、路由、重试、幂等 |

这张表不是让你选一边站，而是让你在 ADR 里逐项写清楚：我选了什么、为什么、代价是什么、在什么条件下代价会变成故障。

## 动手实践：对同一 KV 负载比较三种模型，写 ADR

本节点的 practice 是：**对同一 KV 负载比较分片锁、每分片事件循环与任务队列，写 ADR。** 这一节给出一套可执行的做法。重点不是写出三个“能跑”的 demo，而是让三者面对同一份负载、同一套指标、同一组故障注入，最后产出一份能支撑决策的 ADR。

### 第一步：固定负载与契约

先写一份 `workload.md`，把变量固定下来，避免“每个模型测的其实不是同一件事”。

**负载参数**：

- key 空间：例如 100 万个 key；
- 分布：先测均匀分布，再测 Zipf / 热点分布（例如 1% 的 key 承担 50% 的请求）；
- 读写比：例如 95% get、5% put；
- 值大小：例如 256B 和 4KB 两档；
- 并发客户端：例如 64 或 256；
- 是否包含跨分片操作：例如 1% 的 `MGET`，每次 8 个 key；
- 是否包含慢操作：例如 0.1% 的请求执行 10ms 的模拟 I/O；
- 过载测试：把到达速率逐步提高到超过容量，观察 p99、队列、拒绝；
- 测试时长：每档至少几分钟，避免只测到预热阶段；
- 重复次数：至少 5 次，报告中位数和尾部，不只报最好的一次。

**契约参数**：

- 单 key 读写要求线性化；
- 跨 key `MGET` 不要求快照一致，但要说明可能看到部分新值；
- 同一 key 的写按提交顺序生效；
- 重复提交使用幂等键，服务端去重窗口为 10 分钟；
- 过载时允许拒绝，返回明确的可重试错误；
- 停机时已确认的写不能丢，未确认的写可以失败；
- 尾延迟预算：p99 ≤ 20ms，p999 ≤ 100ms（示例，按实际 SLO 替换）。

把这些写下来，后面每个模型的正确性测试和 ADR 都引用它。没有契约，就没有“正确性”可谈，也没有“在何种负载下失效”可写。

### 第二步：实现三个模型的统一接口

为了让比较公平，三个模型实现同一个接口：

```cpp
class KV {
public:
    virtual ~KV() = default;

    virtual std::optional<std::string> get(const std::string& key) = 0;
    virtual bool put(const std::string& key, std::string value) = 0;
    virtual std::vector<std::optional<std::string>>
        mget(const std::vector<std::string>& keys) = 0;

    // 停止接收新请求；返回前完成或取消已接受的任务。
    virtual void shutdown(std::chrono::milliseconds drain_limit) = 0;
};
```

接口里有两个容易忽略但很关键的点：

1. **`put` 返回 `bool`**：过载时可能被拒绝；调用方必须能区分“成功”“失败”“可重试”。
2. **`shutdown` 带排水上限**：停机不是无限等待；超过上限要有明确行为，并记录剩余任务。

三个模型分别实现：

- `ShardedLockKV`：分片 mutex + map；`mget` 按分片分组，必要时按固定顺序加锁，或者干脆逐 key 读取并接受非原子。
- `ShardLoopKV`：每分片一个执行者 + 邮箱；`get/put` 封装成消息并等待 future；`mget` 向多个分片发请求后汇总。
- `TaskQueueKV`：有界任务队列 + 工作线程；任务内部调用 `ShardedLockKV` 或按 key 路由；`shutdown` 先关闭队列再 join。

注意：模型 C 如果内部直接用 `ShardedLockKV`，它和模型 A 的差异就主要在“排队与调度”上，这是合理的对比——它回答的是“加一层任务队列是否改善尾延迟/隔离/停机”。在 ADR 里要明确这一点，避免读者误以为两者状态保护完全不同。

### 第三步：正确性测试

正确性测试要比“跑一遍没崩”强。至少做四类：

##### 测试一：单 key 读改写

多个线程对同一个 key 执行“读 → 加一 → 写”，每个线程做固定次数，最终值必须等于总次数。这能抓到丢失更新。

```cpp
void test_read_modify_write(KV& kv, int threads, int per_thread) {
    kv.put("counter", "0");
    std::vector<std::thread> ts;
    std::atomic<bool> start{false};
    for (int t = 0; t < threads; ++t) {
        ts.emplace_back([&] {
            while (!start.load(std::memory_order_acquire)) {}
            for (int i = 0; i < per_thread; ++i) {
                for (;;) {
                    auto old = kv.get("counter");
                    long v = std::stol(*old);
                    if (kv.put("counter", std::to_string(v + 1))) break;
                }
            }
        });
    }
    start.store(true, std::memory_order_release);
    for (auto& t : ts) t.join();
    auto final = kv.get("counter");
    assert(std::stol(*final) == 1LL * threads * per_thread);
}
```

这个测试对模型 A 和 C 有意义，因为它们的 `get` 和 `put` 是两次独立调用，中间可能被别的线程插入。模型 B 如果提供原子的“读改写消息”，则应该直接测那个消息，而不是用两次调用模拟。这个差异本身就要写进 ADR：**模型的接口语义不同，测试要按契约调整，不能用一个测试假装三者等价。**

##### 测试二：单 key 顺序

一个线程依次 `put(k, "1")`、`put(k, "2")`、`put(k, "3")`，另一个线程在每次 `put` 返回后立即 `get(k)`，必须能看到刚写入的值（read-your-writes）。这能抓到消息乱序、异步写回、以及“put 返回了但实际还没生效”的问题。

##### 测试三：跨分片非原子性

对多个 key 并发写，同时执行 `mget`，记录是否观察到部分新值、部分旧值。如果契约允许，测试应该断言“不会崩溃、不会返回不存在于任何版本的值”；如果契约要求快照一致，则这个测试应该失败，说明模型不满足契约。重点是让中间状态**可见**，而不是假装它不存在。

##### 测试四：并发回归与 TSan

用 TSan 构建跑上述测试；用 ASan 跑停机测试，检查 use-after-free。对模型 B，重点检查对象是否逃逸出分片线程；对模型 C，重点检查任务捕获的引用是否比任务活得短；对模型 A，重点检查跨分片加锁顺序。

### 第四步：尾延迟测试

尾延迟测试的关键是“开环”和“分段统计”。

一个简化的开环压测骨架：

```cpp
struct Sample {
    std::chrono::steady_clock::time_point enqueued;
    std::chrono::steady_clock::time_point started;
    std::chrono::steady_clock::time_point finished;
    bool rejected;
};

void report(const std::vector<Sample>& samples) {
    std::vector<double> queue_ms, service_ms, total_ms;
    size_t rejected = 0;
    for (const auto& s : samples) {
        if (s.rejected) { ++rejected; continue; }
        queue_ms.push_back(ms(s.started - s.enqueued));
        service_ms.push_back(ms(s.finished - s.started));
        total_ms.push_back(ms(s.finished - s.enqueued));
    }
    // 对 queue_ms / service_ms / total_ms 分别排序，输出 p50/p99/p999
    // 同时输出 rejected / samples.size()
}
```

报告里至少要有：

- 吞吐（成功请求/秒）与拒绝率；
- 排队时间 p50/p99/p999；
- 执行时间 p50/p99/p999；
- 端到端时间 p50/p99/p999；
- 每个分片的队列深度最大值和平均值；
- CPU 利用率、RSS、上下文切换次数（可用 `pidstat` / `perf`）；
- 过载区间的曲线，而不是单点。

跑三组负载：

1. **容量以内**：到达速率约为实测容量的 70%，看基线延迟和公平性。
2. **临界点**：逐步提高速率，找到 p99 开始非线性上升的拐点。
3. **过载**：超过容量 1.5 倍，观察队列、拒绝、内存和恢复行为。

每组的结论要写成“模型 X 在 Y 负载下 p99 为 Z，拐点在 W”，而不是“模型 X 更快”。

### 第五步：停机测试

停机测试必须在**有负载**的时候做，否则测不到问题。步骤：

1. 启动压测，稳定运行一段时间；
2. 发送停止信号（或调用 `shutdown`）；
3. 记录停止信号时间、停止接收时间、最后一个任务完成时间、进程退出时间；
4. 统计：已确认的写有多少、停机后读不到的有多少、重复执行的有多少、队列剩余多少、拒绝多少；
5. 检查退出码、是否有崩溃、是否有 TSan/ASan 报告；
6. 对每个模型重复，至少覆盖“空闲停机”“轻载停机”“过载停机”三种状态。

停机报告至少要回答：

- 停止接收是否立即生效？有没有新请求在停止后仍被接受？
- 已入队但未执行的任务：是处理完、取消，还是丢弃？调用方看到什么？
- 正在执行的任务：是否给它完成窗口？超时后怎么处理？
- 已确认的写：是否全部可见？如果用了异步写回，是否 flush？
- 排水时间是否在上限内？超过上限时进程如何退出？
- 资源是否释放？线程是否 join？有没有 detached 线程？

这一节直接对应 acceptance 第一条的“停机行为”。

### 第六步：把实验结果写成 ADR

ADR（Architecture Decision Record）不是会议纪要，也不是 benchmark 报告。它要回答的是：在什么背景下、做了哪个决定、考虑过哪些选项、付出了什么代价、什么条件下需要重新考虑。

一个适合本 practice 的 ADR 模板如下：

```markdown
# ADR-0007：KV 服务并发模型选择

## 状态
Proposed / Accepted / Superseded

## 背景与约束
- 业务负载：读写比、key 分布、值大小、跨分片比例、峰值倍率
- SLO：p99、p999、可用性、停机排水上限
- 团队与运维约束：语言、现成组件、排障能力、发布方式
- 明确不做什么：例如暂不支持跨 key 事务

## 决策
选择模型 X，因为……

## 备选方案
- 模型 A：分片锁
- 模型 B：每分片事件循环
- 模型 C：任务队列
每个方案给出：状态归属、顺序保证、过载策略、停机方式、实测数据

## 正确性论证
- 命题与证据：单 key 线性化、跨 key 非原子、幂等、停机
- 测试结果：读改写、顺序、跨分片、TSan/ASan

## 尾延迟与容量
- 三组负载下的 p50/p99/p999、排队时间、拒绝率
- 拐点与容量余量

## 停机行为
- 状态机、排水上限、已确认写的处理、实测排水时间

## 后果
- 正面：……
- 负面：……
- 运维成本：……

## 失效模式与重访条件
- 在什么负载特征下会失效
- 触发重访的指标阈值
- 届时候选方案
```

一份填好的核心段落可以长这样（数字是示例，必须用你自己的实验替换）：

```markdown
## 决策
选择“每分片事件循环 + 有界邮箱”，分片数 64，每分片一个执行线程。
单 key 读写在该分片内串行执行；跨分片 MGET 采用扇出 + 超时，不保证快照一致。
过载时每分片邮箱上限 4096，满则拒绝并返回 RETRY_LATER。
停机采用 Draining：停止接收 → 处理已入队消息 → 最多等待 5s → join。

## 正确性论证
- 单 key 读改写：模型 B 将读改写实现为单条消息，10 万次并发递增结果正确。
- 单 key 顺序：put 返回前已完成内存更新，read-your-writes 测试通过。
- 跨分片：MGET 允许部分新值；测试确认不会返回撕裂值。
- TSan/ASan：并发回归与停机注入均无报告。

## 尾延迟
- 均匀分布、70% 容量：p99 8ms，p999 20ms，排队时间占比 < 5%。
- Zipf 热点、90% 容量：热点分片 p99 45ms，超过预算；拐点出现在单分片 QPS 约 12k。
- 过载 1.5x：拒绝率 18%，未拒绝请求 p99 120ms，热点分片队列达到上限。

## 停机
- 空闲：排水 < 50ms。
- 轻载：排水 300ms，已确认写 0 丢失。
- 过载：排水 5s 触顶，剩余 1200 条未执行消息被拒绝，调用方收到明确错误；无重复执行。

## 失效模式与重访条件
- 当热点 key 使单分片 QPS 持续超过 12k，或热点分片 p99 超过 30ms 时，队头阻塞会扩散到该分片所有请求。
- 当跨分片 MGET 比例超过 20%，扇出延迟会主导端到端 p99。
- 触发重访的条件：连续一周热点分片 p99 > 30ms，或跨分片流量占比 > 20%，或分片间负载比 > 4:1。
- 届时候选：热点 key 拆分 + 请求合并；或改为模型 C 的任务队列 + 按 key 路由，以便对热点 key 做单独限流。
```

这份 ADR 满足 acceptance 的两个要求：正确性、尾延迟、停机行为都有具体内容；失效条件是可观测、可触发重访的，而不是“高负载可能有问题”。

### 第七步：横向比较，给出“为什么不选另外两个”

ADR 最容易写薄弱的地方，是只论证自己选的模型，不认真对待被否掉的模型。评审时最常问的问题是：“如果另一个模型在你的负载下更好，你怎么知道？”

所以比较表至少要包含：

| 维度 | 模型 A 分片锁 | 模型 B 每分片事件循环 | 模型 C 任务队列 |
| --- | --- | --- | --- |
| 单 key 顺序 | 锁保护，但读改写需额外协议 | 分片内天然串行 | 取决于任务路由 |
| 热点 key | 单分片锁竞争 | 单分片队头阻塞 | 全局队列/线程被占 |
| 跨分片 | 多锁，需固定顺序 | 扇出，延迟取最慢 | 任务内协调，易阻塞线程 |
| 过载 | 线程阻塞、上游超时 | 每分片邮箱满则拒绝 | 有界队列满则拒绝 |
| 隔离 | 弱，需额外限流 | 强，按分片天然隔离 | 中，需租户/优先级 |
| 停机 | 等在途调用 | 停止接收 + 排水 | 关闭队列 + join |
| 实现复杂度 | 低 | 中 | 中到高 |
| 可观测性 | 需按分片打点 | 每分片天然可观测 | 队列指标集中，分片需额外打点 |

然后对每个未选方案写一句“在什么条件下它会反过来胜出”。例如：

- 如果负载以单 key 为主、跨分片很少、团队希望最少代码，模型 A 可能更合适；它的单次延迟最低，停机也最简单。
- 如果任务种类多、需要优先级和弹性伸缩，模型 C 可能更合适；它把调度和状态保护解耦，便于做限流和批处理。
- 如果热点均匀、每分片负载稳定、追求可观测和隔离，模型 B 更合适；它把状态归属和指标边界都画得很清楚。

这不是“和稀泥”，而是把决策的适用条件写清楚。未来负载变化时，团队能根据这些条件判断是否需要重访，而不是凭感觉推翻。

### 第八步：把结论变成可执行的检查

最后，把 ADR 里的关键命题变成 CI 或发布检查项：

- 正确性回归：单 key 读改写、顺序、跨分片中间状态、幂等去重。
- 并发检查：TSan 构建跑核心路径；ASan 跑停机测试。
- 尾延迟门禁：在固定负载下 p99 不超过预算；超过则阻断发布或要求说明。
- 停机演练：定期在预发环境做“负载中停机”，检查排水时间、丢失/重复、退出码。
- 过载演练：定期把到达速率推到容量以上，检查拒绝语义和恢复时间。
- 指标看板：每分片队列深度、p99、拒绝数、排水时间；设置与失效条件对应的告警阈值。

这样，ADR 不是一份写完就归档的文档，而是和测试、监控、发布流程连在一起的决策记录。

## 延伸阅读：sourceStudy

本节点的 sourceStudy 是：**阅读 Boost.Asio strands 的串行执行保证，识别对象访问与 handler 调度之间的约束。**

推荐资源里的链接是 Boost.Asio 官方文档的 strands 概览页。阅读时不要只记住“strand 可以避免锁”这一句，而要抓住下面几层约束。

### 第一层：strand 保证的是什么

Asio 的 strand 提供的是**handler 调用的串行化**：关联到同一个 strand 的 handlers 不会并发执行。它不保证这些 handler 永远在同一个 OS 线程上运行，也不保证你从 strand 外部直接调用的代码会被串行化。文档里的关键词是 “strictly sequential invocation”，不是 “thread affinity”。

这正好对应本课的区分：串行执行不等于绑定线程。你可以把 strand 看成“逻辑上的单线程执行者”，它可能在线程池的多个线程之间迁移。对象的状态只要只通过该 strand 上的 handlers 访问，就不需要为每次访问加锁；但一旦有外部线程直接访问，串行保证就被绕过。

### 第二层：对象访问必须和 handler 调度对齐

读文档时重点看它如何把 handler 与 executor / strand 绑定。常见的绑定方式包括：

- 构造 `boost::asio::strand<Executor>`，或在较新接口里用 `boost::asio::make_strand(io_context)`；
- 用 `boost::asio::bind_executor(strand, handler)` 把 handler 关联到 strand；
- 在异步操作的完成 handler 上绑定同一个 strand；
- 对 composed operation 的每一个中间 handler 都保持相同的 strand 关联。

这里的约束是：**对象的每一次访问，都必须发生在与该对象所有者相同的 strand 上。** 只在“入口 handler”上绑定 strand，而后面的回调忘了绑定，就会出现两个 handler 并发访问同一对象的情况。文档里对 composed operations 的说明尤其值得读：一个组合操作由多个中间 handler 组成，如果其中任何一个跑到了 strand 外，串行性就断了。

### 第三层：post、dispatch、defer 的语义差异

Asio 提供几种把 handler 交给 executor 的方式，它们的执行时机不同。阅读时要区分：

- **post**：把 handler 排入队列，不会在当前调用栈内立即执行；
- **dispatch**：如果当前上下文已经在目标 executor / strand 上，可能立即执行；否则排队；
- **defer**：类似延迟提交，具体语义以文档为准。

对设计的含义是：

- `dispatch` 可能导致**重入**：你以为只是“提交一个任务”，结果它在当前栈上直接跑了，对象的中间状态可能被自己再次进入。对持有锁或处于半更新状态的对象，这很危险。
- `post` 更接近“消息传递”，它保证不在当前栈上执行，但会增加一次排队。
- 无论哪种方式，**handler 捕获的对象生命周期**都必须覆盖执行时刻。如果对象在 handler 执行前被销毁，strand 不会救你。

### 第四层：strand 不保护生命周期和取消

strand 只解决“不会并发调用”，不解决：

- handler 捕获的 `this` 是否还有效；
- 异步操作取消后，完成 handler 是否仍会被调用；
- 对象在哪个线程析构；
- 多个 strand 之间的顺序和死锁。

这些要结合 e-cancel 的生命周期设计和对象所有权设计。一个常见模式是：用 `enable_shared_from_this` 让 handler 持有对象的 shared_ptr，确保执行期间对象存活；同时用取消令牌/停止标志让 handler 在被取消后快速返回。strand 保证串行，shared_ptr 保证存活，取消协议保证不会做无用功，三者缺一不可。

### 第五层：把文档结论映射回本课模型

读完 strands 文档后，你应该能把模型 B 的约束写得更精确：

- 每个分片对应一个 strand（或一个单线程 executor）；
- 分片状态只能在该 strand 的 handler 中访问；
- 所有跨分片调用都通过 `post` 到目标 strand，而不是直接调用；
- 组合操作的所有中间 handler 都绑定同一 strand；
- 外部线程不能直接调用分片对象的方法；
- 停机时先停止提交，再让 strand 处理完队列，最后销毁对象；
- 对 `dispatch` 的重入风险做专门检查。

如果你能把这几条写进 ADR 的“正确性论证”和“失效模式”，sourceStudy 的目的就达到了：不是记住 API，而是识别“串行执行保证”与“对象访问、handler 调度、生命周期”之间的约束。

## 自测题

先别看答案。能对着三个要点和 practice 讲清楚，再对照答案检查。

### 题 1：Actor、线程封闭与 strand

**问题**：你的同事说：“我们用 Actor 模型，每个 key 一个 actor，所以完全不需要锁，也不会有数据竞争。”请回答：

1. 这句话哪里对、哪里不完整？
2. Actor 的私有状态在什么情况下会“逃逸”，逃逸后会发生什么？
3. “串行执行”和“绑定线程”有什么区别？Boost.Asio 的 strand 属于哪一种？
4. 如果所有访问都通过 strand，是否就自动保证了对象生命周期安全？

**答案**：

1. “每个 key 一个 actor，actor 内部状态只被一个执行者访问”这部分是对的：如果状态确实没有逃逸，单 actor 内部不需要为业务状态加锁，数据竞争的可能性被结构性消除。不完整的地方在于：邮箱/队列本身仍然是共享的，入队出队需要同步；跨 actor 操作需要消息和协调；全局资源（分配器、日志、指标、连接池）仍然共享；而且“不会数据竞争”依赖于“没有逃逸”这个前提，不是自动成立的。
2. 逃逸的常见路径：把成员的可变引用或 `this` 交给异步回调；返回内部容器的非 const 引用；跨 actor 共享可变对象的 `shared_ptr`；访问不受 actor 保护的全局缓存；把对象所有权转移后又继续使用；在错误的线程析构对象；为了省一次消息而直接调用别的 actor。逃逸后，两个执行者可能同时读写同一块状态，数据竞争和生命周期错误就回来了，而且因为“我们在用 Actor”而更隐蔽。
3. 绑定线程是对象只能在一个固定 OS 线程上访问；串行执行是同一时刻只有一个执行上下文处理该对象，但不同消息可能在不同线程上执行。strand 属于后者：它保证关联的 handlers 不并发执行，但不保证线程亲和。因此对象访问必须始终通过同一个 strand，不能从外部线程直接调用。
4. 不保证。strand 只序列化调用，不延长对象寿命。如果 handler 捕获的 `this` 在 handler 执行前被销毁，strand 不会阻止 use-after-free。需要额外的所有权设计（例如 `shared_from_this` 让 handler 持有对象）和取消协议，确保对象在执行期间存活，并在取消后安全退出。

### 题 2：三种模型与失效条件

**问题**：一个 KV 服务，95% get / 5% put，单 key 读改写要求线性化，1% 的请求是 8 个 key 的 `MGET`（不要求快照一致），存在明显热点 key。团队在分片锁、每分片事件循环、任务队列之间选择。请回答：

1. 三个模型分别怎样保证单 key 读改写的正确性？
2. 热点 key 分别会对三个模型造成什么影响？
3. 如果选择每分片事件循环，ADR 里应写哪些失效条件？
4. 任务队列模型为什么可能“吞吐最高但尾延迟最差”？

**答案**：

1. 分片锁：读改写需要在同一临界区内完成，或者用版本号/CAS 重试；如果 `get` 和 `put` 各自加锁，中间会被插入，必须靠外层协议保证原子。每分片事件循环：把“读改写”实现成一条消息，在分片执行者内一次处理完，天然串行。任务队列：需要按 key 路由到固定执行者，或者任务内部使用分片锁 + 版本检查；如果只是把 `get` 和 `put` 各包一个任务，仍然会丢失更新。
2. 分片锁：热点 key 落在单个分片，该分片的 mutex 成为串行点，竞争导致 p99 上升，严重时线程都堵在这把锁上。每分片事件循环：热点分片的消息队列持续增长，单个慢请求会造成队头阻塞，该分片所有 key 的延迟一起上升。任务队列：热点任务会占满工作线程，全局队列可能被热点请求填满，导致其他 key 的请求也排在后面；如果有按 key 路由，则退化为该 key 的串行瓶颈。
3. 至少写：当热点分片 QPS 超过某个实测拐点，或该分片 p99 超过预算时，队头阻塞会让该分片所有请求超时；当分片间负载比超过某个比例（例如 4:1）时，静态分片的容量利用率下降；当跨分片 `MGET` 比例上升时，扇出延迟由最慢分片决定，可能主导端到端 p99；当单个 handler 执行时间超过尾延迟预算时，整片停摆。还要写触发重访的指标阈值和届时候选方案（热点 key 拆分、请求合并、改任务队列 + 按 key 限流等）。
4. 因为吞吐和尾延迟不是一回事。无界队列在过载前可以维持很高的吞吐，但请求在队列里排队的时间会迅速增长；闭环压测还可能因为客户端变慢而低估真实等待（协调遗漏）。当到达速率超过消费速率时，队列把过载转成延迟和内存，p99/p999 先坏，随后可能 OOM 或触发上游重试放大。节点 pitfalls 说的“吞吐最高不必然是延迟或运维成本最优”就是这个意思。

### 题 3：ADR、验收与权衡

**问题**：你要为上面的 KV 服务写 ADR。请回答：

1. acceptance 要求报告包含哪三块？每块至少给出两个具体内容。
2. 怎样证明“这个选择在何种负载下失效”，而不是写一句“高负载可能有问题”？
3. 消息传递简化了共享状态，但节点指出它增加了哪些成本？请各举一个 KV 场景。
4. 为什么说“可证明边界”不等于“形式化证明”？

**答案**：

1. 三块是正确性、尾延迟、停机行为。正确性至少写：单 key 线性化的命题与测试、跨 key 非原子的语义、幂等/重复提交处理、TSan/ASan 结果。尾延迟至少写：p50/p99/p999、排队时间与执行时间分开、开环还是闭环、键分布（均匀/倾斜）、过载区间的拐点。停机行为至少写：停止接收是否立即生效、已入队/执行中任务的处理、排水时间上限与实测值、已确认写是否丢失、重复执行数、退出码。
2. 把失效条件写成“负载特征 + 指标阈值 + 后果 + 重访动作”。例如：“当热点分片 QPS 持续超过 12k，或分片间负载比超过 4:1，导致该分片 p99 超过 30ms 时，队头阻塞会扩散到该分片所有 key；连续一周触发则重访，候选方案是热点 key 拆分或任务队列 + 按 key 限流。”这比“高负载可能有问题”可检查得多，也能直接映射到监控告警。
3. 节点 tradeoffs 指出的三项成本是排队、跨分片操作和复制。排队：每个 key 一个 actor，热点 key 的邮箱会堆积，消息等待时间计入 p99。跨分片：`MGET` 8 个 key 落在不同 actor，需要扇出并等待最慢者，或做事务/ Saga，延迟和复杂度都上升。复制：actor 状态要跨节点复制以提高可用性时，需要传播写、处理读旧值、故障切换和一致性，成本和单机共享内存完全不是一个量级。
4. 因为“可证明”在这里指的是：把保证写成明确命题，并用代码结构、并发测试、线性化检查、故障注入和观测数据去支撑，让你知道边界在哪里、何时会被突破。它不要求像形式化方法那样对全部状态空间做机器证明（那当然更严格，但成本很高，通常只用于核心算法）。ADR 里的“正确性论证 + 失效条件”就是工程意义上的可证明边界：不是“我觉得没问题”，而是“我证明了这些、没证明那些、这些条件下会坏”。

## 本课小结

1. **选模型先看三件事：状态归属、任务生命周期、过载策略。** 这是本节点 summary，也是全课的总纲。锁或协程的单次开销只是局部数据，解释不了尾延迟、停机和运维复杂度。
2. **Actor = 私有状态 + 邮箱 + 串行处理 + 地址。** 它把同步集中到消息边界，让业务状态不再被多线程直接访问；但邮箱仍然需要同步，跨 actor 交互仍然需要协议。
3. **线程封闭靠“不逃逸”维持。** 回调捕获 `this`、返回内部可变引用、共享 `shared_ptr`、全局缓存、跨分片直接调用、错误线程析构，都会破坏封闭。要用封装、所有者断言、所有权转移和并发检测持续加固。
4. **串行执行不等于绑定线程。** strand 保证关联 handlers 不并发执行，但可能在不同线程上运行；对象访问必须始终经过同一个 strand，否则保证失效。
5. **消息传递简化共享状态，但增加三类成本。** 排队（延迟、内存、顺序）、跨分片操作（扇出、事务、Saga、共分片）、复制（一致性、故障切换、日志/快照）。这是节点 tradeoffs。
6. **工作窃取改善负载不均和利用率，但不自动改善尾延迟。** 它可能破坏局部性和单 key 顺序；长任务、锁竞争、下游阻塞仍然会拖尾。任务要路由回 key 的所有者，才能同时保住顺序和弹性。
7. **公平性和隔离要按业务契约设计。** FIFO、优先级、租户配额、轮转各有代价；隔离按故障域画，不是越多越好；每个隔离单元都要有独立指标，否则热点会被平均值掩盖。
8. **可证明边界 = 明确命题 + 证据 + 失效条件。** 命题覆盖状态归属、顺序、资源上限、生命周期；证据来自代码结构、并发测试、TSan/ASan、线性化检查、故障注入和观测数据；失效条件要写成可触发的指标阈值。
9. **三种模型各有适用面。** 分片锁简单、单次延迟低，但热点和跨分片是难点；每分片事件循环隔离好、状态归属清晰，但队头阻塞和分片倾斜是难点；任务队列调度灵活、易做过载策略，但队列竞争、按 key 顺序和停机语义更复杂。
10. **吞吐最高不必然是延迟或运维成本最优。** 这是节点 pitfalls。无界队列、热点分片、闭环压测都可能制造“吞吐漂亮、尾延迟很差”的假象；必须同时看正确性、p99/p999、拒绝率、内存和停机。
11. **停机是模型的一部分，不是收尾工作。** 停止接收、排水、取消、join、释放资源要有状态机和上限；已确认的写不能丢，未执行的任务要有明确结果，重复执行要能识别。acceptance 要求报告包含停机行为，原因就在这里。
12. **ADR 要写“为什么不选另外两个”。** 对每个备选方案写清适用条件和反向胜出条件；把结论变成测试门禁、停机演练、过载演练和监控阈值，决策才可执行、可重访。
13. **为什么后端要懂：为复杂服务选择可维护、可观测的执行架构。** 真实故障往往不是“锁慢了 20ns”，而是热点分片把 p99 拖垮、无界队列把过载藏成延迟、停机时丢了已确认的写、跨分片操作在高峰期卡住。把这些边界提前写进模型和 ADR，才能在负载变化时有依据地重访，而不是靠猜。

本课的主线可以压缩成一句话：**先把状态收进明确的所有者，再把任务生命周期和过载策略写成命题，最后用同一份 KV 负载和同一组指标去比较分片锁、每分片事件循环与任务队列，把“为什么选、何时失效”写进 ADR。** 下一步可以继续沿着这个方向深入：如何为热点 key 设计拆分与请求合并，如何在多分片之间做可观测的追踪，以及如何把停机演练和过载演练纳入常态化的发布流程。
