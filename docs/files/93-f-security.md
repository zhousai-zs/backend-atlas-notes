## 导读

### 一个直觉例子：写字楼

把一次 RPC 调用想成一次跨楼送件：A 楼的人要把一个箱子送到 B 楼，箱子里装的是业务数据，收件方要确认来的人靠不靠谱。现实里的写字楼通常同时用了几道不同的措施，每一道只解决一个问题。

- **密封封条**：包裹从 A 楼送到 B 楼，路上可能被人拆开看内容，甚至被调包。封条不能阻止别人碰包裹，但能让你在收件时发现"被动过"。这对应传输加密与完整性：链路上的内容被窃听或篡改，接收方能够发现。
- **门禁刷工牌**：闸机确认"你是登记过的人"，而不是随便一个自称访客的人。工牌也可能被伪造，所以闸机要能识别真伪。这对应**对端认证**：客户端要验证服务端是不是真的那台服务；在 mTLS 下，服务端也要验证客户端证书，从而确认调用方是谁。
- **工牌能进哪几层**：即使你是公司员工，也未必能进机房。身份是真的，不代表权限无限。这对应**授权**：服务端拿到可信身份后，把它映射成角色/权限，再判断这个身份能不能调用某个具体方法。
- **前台与监控**：前台会限制一次搬入的箱子尺寸和同时进入的人数；机房门口有监控，记录谁在什么时候进了机房。这对应**消息大小、并发/速率限制与审计日志**：防止单个请求或某个调用方把资源耗尽，并留下可追溯的操作记录。

对照回 RPC：封条约等于 TLS，工牌约等于认证，楼层权限约等于授权，箱子尺寸/人数/监控约等于资源限制与审计。四者解决的是不同问题，不能互相替代——封条再结实，也管不了你拿工牌能进哪一层。

### 接上前置知识

前面已经学过 gRPC 的调用模型，以及请求上下文如何在调用链中传递。上下文里经常携带 user-id、tenant、trace-id、角色等字段，下游服务往往直接读这些字段做判断。

这里的关键区别是：**上下文只是一个容器，不是证据**。任何能构造请求的人，都可以往元数据里塞一个 `role: admin`。如果服务端直接把上下文里的角色当真，等于让调用方自己给自己发权限。因此本课关心的不是"上下文里有没有身份字段"，而是"这个身份是不是由可信来源建立、验证之后才被使用"。TLS/mTLS 负责把身份可信地建立起来，授权负责把这个身份翻译成"能做什么"。

### 一条教学时间线

假设（教学假设）某内容后台有一个内部 KV 配置服务，早期为了省事，明文跑在内网，只靠 IP 白名单做访问控制。调用方包括图文发布服务、内部运营工具和一些批处理脚本。

1. **早期**：大家觉得"内网就是可信的"，没有 TLS，也没有调用方身份，只要来源 IP 在白名单里就放行。
2. **事故**：一个运营脚本在批量清理测试 key 时，误调用了 Delete 接口。因为脚本所在机器在网段白名单里，请求被直接接受，清空了一批线上配置。
3. **排查**：服务日志为了"方便调试"，把调用方请求头里的完整令牌原样打印了出来；令牌又随着日志被转发到多个系统，排查过程本身变成了二次泄漏。
4. **反思**：传输、认证、授权、审计被混成了一件事——"能连上"被误当成"身份可信"，又被误当成"有权做任何操作"。

### 错误做法与正确做法

| 环节 | 错误做法 | 正确做法 |
| --- | --- | --- |
| 传输 | 内网明文，认为"内网天然可信" | 至少启用 TLS 加密链路，客户端验证服务端证书 |
| 对端 | 只靠 IP 白名单识别调用方 | 使用 mTLS 或可信令牌，由服务端验证调用方身份 |
| 授权 | 只要能连上就能调用所有方法 | 身份映射角色/权限，对每个方法单独判断 |
| 资源 | 不限制消息大小、并发与速率 | 设置最大消息大小、并发上限与速率限制 |
| 审计 | 日志打印完整令牌、私钥等凭证 | 记录操作者、动作、对象、结果，并对凭证脱敏 |

### 本课三条主线

1. **TLS 与 mTLS**：先解决"链路是否加密、对端是否可信"。TLS 提供传输加密与完整性，并通过证书让客户端验证服务端身份；mTLS 下服务端也要求并验证客户端证书，从而认证调用方身份。
2. **身份和权限映射**：身份可信之后，还要把它映射成角色/权限，在服务端按方法做授权判断。认证回答"你是谁"，授权回答"你能做什么"。
3. **消息大小、速率与审计**：服务端要限制输入规模与资源使用，并对敏感操作记录审计日志，同时保证日志里不出现令牌、私钥等凭证。

## 学习目标

学完本课，你应该能够：

- 能解释TLS与mTLS。
- 能独立完成：为KV服务加入TLS和只读角色，验证无证书与越权写入被拒绝。
- 能区分传输加密、对端认证、操作授权三者各自解决的问题，以及只做其中一项会留下什么漏洞。
- 能说明 TLS 握手中客户端如何验证服务端证书，以及 mTLS 下服务端如何验证客户端证书（具体凭证 API 与配置方式以所读文档版本为准）。
- 能把调用方身份映射为角色，并在服务端按方法/资源做授权判断，而不是只凭"能连上"放行。
- 能为服务端设置最大消息大小、并发与速率上限，并对超限请求返回明确错误。
- 能设计不泄露令牌、私钥等凭证的审计日志，覆盖敏感操作的操作者、动作、对象与结果。
- 能把"加密链路可用"与"业务授权生效"拆成两组独立测试来验证，而不是用一次成功调用代替全部结论。

## 为什么后端要懂

> 为内部工具和Agent提供可控服务边界。

即将入职腾讯微信公众号后台开发的后端工程师，会同时面对通用内容后台、图文发布服务、内部运营工具、配置/KV 服务，以及网关到多级 RPC 的调用链（教学假设）。这些系统看起来"都在内网"，但调用方非常杂：网页后台、批处理脚本、定时任务、其他微服务，以及会自主发起调用的 Agent。任何一个调用方配置错误、凭证泄漏或被误用，都可能越过你本来以为存在的服务边界。服务边界不是靠"它在内网"自动成立的，而是靠传输、身份、授权和资源限制一层层落实的。

### 三件事分别解决什么问题

摘要说"传输加密、对端认证与操作授权分别解决不同问题"，值得逐句拆开：它们不是同一个安全措施的三种叫法，也不是做了前一个就不需要后一个。

| 机制 | 主要防什么 | 只做它会留下什么 |
| --- | --- | --- |
| 传输加密（TLS） | 链路被窃听、篡改；客户端可通过证书验证服务端身份 | 只加密不认证调用方：任何能连上端口的人和程序都能发起调用，服务端不知道对面是谁 |
| 对端认证（mTLS，服务端验证客户端证书） | 冒充调用方、未授权客户端接入 | 只认证不授权：任何持证服务都能调用所有方法，包括写入和删除 |
| 操作授权（身份→角色→方法级判断） | 越权读写、横向移动、误操作影响扩大 | 只授权不加密：凭证与业务数据在链路上明文暴露，身份信息也可能被中间人截获 |

用一个具体场景说明：KV 服务只做 TLS，客户端能确认"我连的是真的 KV 服务"，但 KV 服务并不知道调用方是谁；此时任何能访问该端口的程序都可以尝试调用 Delete。反过来，如果只做 mTLS 不做授权，所有持证服务都被一视同仁，一个只该读配置的运营工具仍然可以执行写入甚至删除。再退一步，如果只在业务层判断角色却不加密链路，令牌在网络上是明文的，攻击者拿到令牌后可以冒充合法调用方，授权判断再严格也只是在验证一个被偷来的身份。

所以正确的组合是：TLS 保证链路可信，mTLS 或可信令牌让服务端确认调用方身份，授权把身份映射为权限并逐方法判断，最后由资源限制与审计兜住误用和事故。内网只是网络位置，不是身份，也不等于授权——处于内网不等于可以跳过身份与授权检查。

### 限制输入规模与资源使用

摘要的最后一句是"服务端还需限制输入规模与资源使用"。这句话容易被忽略，因为加密和授权听起来更像"安全"，而大小与限流听起来像"性能"。但在真实后台里，一个不限制输入的服务，往往先被正常但失控的调用方拖垮，而不是先被攻击者攻破。

算一笔账（教学假设）：假设某个 RPC 方法没有设置最大消息大小，一个客户端发送 100MB 的请求体，服务端同时处理 50 个这样的请求。如果每个请求体在反序列化前后都需要驻留内存，仅请求体本身就约 `100MB × 50 = 5GB`。再叠加反序列化后的对象、缓冲区拷贝和框架自身开销，实际占用会更高，单进程很容易 OOM，并连带影响同机部署的其他服务。这还没有计算请求排队、线程或协程堆积，以及向下游服务放大请求带来的连锁压力。

因此服务端至少要做四类约束：

- **最大消息大小**：为请求和响应设置合理上限，超过上限直接拒绝，避免单个请求撑爆内存。
- **并发上限**：限制同时在处理的请求数量，超出后排队或快速失败，防止雪崩。
- **速率限制**：按调用方或身份限制单位时间内的请求量，避免脚本失控或重试风暴。
- **明确错误**：超限时返回可识别的错误码与说明，让调用方能够退避，而不是静默丢弃。

在这些约束之上，敏感操作（例如删除配置、修改权限、批量发布）还应该记录审计日志。审计日志要回答"谁、在什么时候、对什么对象、做了什么、结果如何"，但**不得写入令牌、私钥等凭证**；日志往往会被采集、转发和长期保存，一旦写入凭证，泄漏面会比原始请求大得多。日志中的调用方标识应该是身份或主体 ID，而不是原始密钥材料。

回到本课的定位：加密链路、对端认证、操作授权、资源限制与审计，共同构成"可控的服务边界"。只做其中一两项，边界就是漏的；全部做了但测试只测"能调通"，也无法证明越权会被拒绝。后面的练习会围绕一个 KV 服务，把 TLS、只读角色和越权写入的验证拆开来做。

### 在多级 RPC 中，身份如何一路可信

再把视角拉远一点。通用内容后台的一次请求，往往不是"客户端直连一个服务"，而是"网关 → 业务服务 → 配置/KV 服务"这样的多级调用（教学假设）。每一跳都需要回答两个不同的问题：这一跳的对方是谁？它代表谁在操作？

- **网关到内部服务**：网关先完成用户侧认证，得到经过验证的用户主体；网关与内部服务之间再用 mTLS 确认"调用方确实是这个网关/这个服务"，而不是某个能连上端口的程序。
- **服务到服务**：下游服务通过 mTLS 验证上游服务身份；上游把已经验证过的用户主体、租户、请求 ID 放进上下文继续传递，而不是把用户原始令牌原样透传。
- **下游的信任边界**：下游只能信任"来自已认证对端、且由可信环节写入"的身份字段。随便一个 header 里写的 `user-id` 不能直接当真，否则任何一个能发请求的进程都能冒充别人。
- **令牌的作用范围**：如果使用令牌作为调用凭证，应关注它的受众、有效期与权限范围；具体令牌格式、传播协议和各语言实现，以所读文档版本为准。

这条链上最容易出现的问题，是把"网关注入的身份"和"任意调用方可写的元数据"混为一谈。前者有认证作为前提，后者没有；下游如果不区分来源，前面做的 mTLS 就白做了。

### 授权判断应该落在哪里

认证与授权是两件事：认证回答"你是谁"，授权回答"你能做什么"。即使 mTLS 已经证明对方是一个合法服务，也不代表它可以调用所有方法。

一个常见的落地方式是"主体 → 角色 → 权限 → 方法"：

1. 从可信身份中得到主体（服务身份或用户主体）。
2. 把主体映射到角色，例如只读、读写、管理员；KV 服务可以有一个只读角色。
3. 为角色定义权限集合，例如只读角色允许 `Get`/`List`，不允许 `Put`/`Delete`。
4. 在服务端对每个方法做判断，默认拒绝；新增方法时必须显式授权，而不是因为"忘了加检查"而默认放行。
5. 必要时再细化到资源级，例如按租户或命名空间判断，避免 A 租户的只读身份读到 B 租户的数据。

授权必须发生在服务端。客户端的按钮置灰、脚本里的参数校验都只是体验或防误操作，不能作为安全边界。验证时也要把两件事分开：无证书的调用应该在握手/连接阶段失败；持只读证书执行写入应该在业务授权阶段被拒绝。两者失败的位置和日志含义不同，混在一起测就无法判断究竟哪一层生效。

### 排障时如何区分 TLS 失败与授权失败

mTLS 加强身份管理，也增加证书签发、轮换和排障成本。排障时先分清失败发生在哪一层，能少走很多弯路：

- **握手/连接阶段失败**：常见原因包括证书过期、信任链不匹配、主机名或 SAN 不匹配、客户端未提供证书等；具体校验规则与错误信息以所读文档版本和实现为准。
- **请求已到达业务层但被拒绝**：说明对端认证可能已经通过，问题在令牌校验、角色映射或方法级授权；典型表现是明确的权限错误，而不是连接建立失败。
- **不要用关闭 TLS 的方式排障**：临时降级容易变成永久降级，也会掩盖证书配置问题；更稳妥的做法是查看握手日志、证书有效期和主体映射，并确保日志中不出现私钥、令牌等敏感材料。
- **把审计与排障日志分开看**：审计关注"谁做了什么、结果如何"，排障日志关注链路与错误原因；两者都不应记录凭证原文。

把这几层合起来看，"可控服务边界"不是某一个开关，而是一组互相配合的约束：链路可信、对端可认证、身份可映射、操作可授权、资源可限制、行为可追溯。任何一层缺失，其他层都无法单独兜底。

还有两个常见的疑问值得展开：既然服务都在内网，为什么还要这么麻烦？mTLS 的成本是否值得？

### "内网可信"忽略了什么

- **内网不是单一信任域**：办公网、测试网、生产网、第三方接入和临时机器可能互相可达；一台被入侵的跳板机，往往就处在"白名单"里面。
- **IP 白名单认证的是位置，不是身份**：NAT、代理和共享出口会让多个调用方共用一个 IP，IP 本身也会变化；它无法回答"你是谁"。
- **横向移动**：攻击者拿到一台内网机器后，可以继续扫描并调用白名单内的其他服务；没有 mTLS 和授权，每个服务都可能成为下一个入口。
- **误操作不分内外**：运营脚本、定时任务、Agent 都可能是合法调用方，但权限过大时同样会造成事故，内网身份并不能降低这种风险。
- **审计与追责**：出事后要回答"是谁做的"，仅靠 IP 往往定位不到具体主体，也无法判断是一次误操作还是越权行为。

所以"内网"应该被当作一层网络位置和隔离手段，而不是身份或授权。它可以作为额外防线，但不能替代 TLS、认证和授权。

### 成本与取舍

mTLS 不是免费的：证书签发、分发、轮换、吊销，以及握手失败时的排障，都需要流程和工具支持。对调用方少、风险低的内部只读服务，也可以先用 TLS 加可信令牌完成认证，再配合服务端授权；当服务身份本身需要强认证，或调用链跨越多个信任域时，mTLS 的价值会更明显。具体选择没有唯一答案，取决于调用方数量、数据敏感度、运维能力和合规要求。无论选哪种组合，授权与资源限制都不能省。

### 四个概念的最小对照

| 概念 | 回答的问题 | 典型失败表现 |
| --- | --- | --- |
| 传输加密 | 链路上的内容会不会被看见或篡改 | 明文可被抓包、内容可被修改 |
| 对端认证 | 对面是不是它声称的那个服务/客户端 | 任意客户端可连接、无法确认调用方 |
| 操作授权 | 这个身份能不能做这个操作 | 只读身份能写入、普通服务能删除 |
| 审计与限制 | 出了事能否追溯、资源会不会被耗尽 | 日志无主体、单个请求打爆内存 |

这四行也可以当作排查时的提问顺序：先看链路，再看对端，再看权限，最后看资源与记录。把顺序固定下来，就不容易用"能调通"掩盖某一层的缺失。

### 一个权限映射的例子（教学假设）

仍以 KV 配置服务为例，角色可以先粗分为三档：

| 角色 | 允许的方法 | 不允许的方法 |
| --- | --- | --- |
| 只读（reader） | `Get`、`List` | `Put`、`Delete` |
| 读写（writer） | `Get`、`List`、`Put` | `Delete` |
| 管理（admin） | `Get`、`List`、`Put`、`Delete` | 无（但仍需审计） |

几个容易忽略的点：

- 角色应该由可信身份映射得到，而不是按调用方自报的名字硬编码；同一个服务在不同环境下也可能拥有不同角色。
- 只读角色的价值在于把"日常查询"和"修改配置"分开。报表、巡检、运营看板大多只需要读，不应顺手拿到写权限。
- 如果有多租户，还要在方法级权限之上加资源级判断，避免只读身份跨租户读取。
- 没有证书、没有可信令牌的调用不应被映射到任何角色，默认拒绝；新增方法时也要显式决定它属于哪个权限集合。
- 写入和删除最好分开授权，因为删除的破坏半径通常更大；权限变更本身也应进入审计范围。

### 把检查点放进请求生命周期

把上面的概念按一次请求的顺序串起来，会更容易记住每一层的位置：

1. **建立连接**：TLS 握手，客户端验证服务端证书；mTLS 下服务端验证客户端证书，确认对端身份。
2. **接收请求**：检查消息大小等输入约束，超限直接拒绝，避免把压力带到后续阶段。
3. **提取身份**：只使用来自已认证对端或可信凭证的身份信息，不信任任意调用方可写的元数据。
4. **执行授权**：把身份映射为角色/权限，按方法和资源判断；不通过则返回明确的权限错误。
5. **处理业务**：在并发和速率限制下执行，避免单个调用方耗尽资源。
6. **记录审计**：记录主体、动作、对象和结果，但对令牌、私钥等凭证做脱敏或不记录。

这个顺序也解释了为什么"只测一次成功调用"不够：成功调用只能证明某一层没有挡住你，不能证明其他层会在该拒绝的时候拒绝。

## 核心知识点

这一节把 RPC 安全拆成三个相互独立、又必须组合使用的问题：链路是否加密、对端是谁、这个身份能做什么。以下场景均为教学假设：一个内部配置/KV 服务，前面是网关，后面可能还有多级 RPC；它同时被运营工具和自动化任务调用。

### 1. TLS与mTLS

**直觉。** TLS 先解决“说的内容别人看不到、改不了”，再通过证书解决“我连上的确实是那个服务”。握手时可以粗略理解为：

1. 客户端发出支持的协议版本、密码套件和随机数。
2. 服务端返回自己的证书链，并给出协商结果。
3. 客户端用本地信任的 CA 校验证书链、有效期和主机名（SAN/CN），确认对端身份。
4. 双方完成密钥交换，之后用会话密钥加密应用数据。

mTLS 在此基础上多一步：服务端在握手时发出 `CertificateRequest`，要求客户端也出示证书；客户端提交后，服务端用自己信任的 CA 校验。这样服务端不仅“被客户端认证”，也能认证“调用方是谁”。

| 模式 | 客户端验证服务端 | 服务端验证客户端 | 典型用途 |
|---|---|---|---|
| 明文 TCP | 否 | 否 | 仅本地调试，不应承载敏感数据 |
| TLS | 是 | 否 | 浏览器/外部客户端访问服务 |
| mTLS | 是 | 是 | 服务间调用、内部工具访问敏感接口 |

**用 openssl 造一套实验证书。** 下面命令只用于实验，证书和私钥不要提交到仓库。

```bash
mkdir -p /tmp/rpc-tls && cd /tmp/rpc-tls

# 1) 自签 CA
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout ca.key -out ca.crt \
  -subj "/CN=Atlas Lesson CA" \
  -addext "basicConstraints=critical,CA:TRUE" -addext "keyUsage=critical,keyCertSign,cRLSign"
# 注：较新的 Python（如 3.13）默认开启严格证书校验，CA 缺少 keyUsage 会报
# "CA cert does not include key usage extension"；叶子证书最好也带 authorityKeyIdentifier，见 practice93/test.sh

# 2) 服务端证书：SAN 必须包含客户端实际连接使用的主机名
openssl req -newkey rsa:2048 -nodes \
  -keyout server.key -out server.csr \
  -subj "/CN=kv.internal.atlas.test"
cat > server.ext <<'EOF'
subjectAltName=DNS:kv.internal.atlas.test,IP:127.0.0.1
extendedKeyUsage=serverAuth
EOF
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key \
  -CAcreateserial -days 365 -out server.crt -extfile server.ext

# 3) 客户端证书：CN 用作实验中的调用方身份
openssl req -newkey rsa:2048 -nodes \
  -keyout client.key -out client.csr \
  -subj "/CN=ops-reader"
cat > client.ext <<'EOF'
extendedKeyUsage=clientAuth
EOF
openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key \
  -CAserial ca.srl -days 365 -out client.crt -extfile client.ext
```

检查证书内容和链：

```bash
openssl verify -CAfile ca.crt server.crt client.crt
openssl x509 -in server.crt -noout -subject -issuer -enddate
openssl x509 -in server.crt -noout -ext subjectAltName
```

**连接验证。** 先用普通 TLS 连接，确认客户端能验证服务端；再用 `-cert/-key` 发起 mTLS 连接，观察服务端是否要求客户端证书：

```bash
# 只验证服务端
openssl s_client -connect 127.0.0.1:8443 \
  -servername kv.internal.atlas.test -CAfile ca.crt

# 携带客户端证书，用于 mTLS
openssl s_client -connect 127.0.0.1:8443 \
  -servername kv.internal.atlas.test -CAfile ca.crt \
  -cert client.crt -key client.key
```

生产环境还应检查协议版本、密码套件和证书轮换策略；具体默认值与推荐配置以所读 OpenSSL/运行环境文档版本为准。

**Python 服务端开启 mTLS。** 关键是加载服务端证书、加载信任的客户端 CA，并把 `verify_mode` 设为 `CERT_REQUIRED`：

```python
import socket
import ssl

ctx = ssl.create_default_context(ssl.Purpose.CLIENT_AUTH)
ctx.load_cert_chain("server.crt", "server.key")
ctx.load_verify_locations("ca.crt")
ctx.verify_mode = ssl.CERT_REQUIRED  # 没有客户端证书则握手失败

with socket.socket() as s:
    s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    s.bind(("127.0.0.1", 8443))
    s.listen(5)
    print("listening on 127.0.0.1:8443")
    conn, _ = s.accept()
    with ctx.wrap_socket(conn, server_side=True) as tls:
        peer = tls.getpeercert()
        subject = dict(x[0] for x in peer["subject"])
        print("client CN =", subject.get("commonName"))
        tls.sendall(b"OK\n")
```

客户端不提供证书时，服务端会在握手阶段失败；这正是“无证书被拒绝”的第一层。真正的业务授权还要在握手之后按身份判断，不能把“握手成功”当成“可以写数据”。

**常见失败对照。**

| 现象/报错关键词 | 常见原因 | 排查动作 |
|---|---|---|
| `certificate has expired` | 证书过期 | 用 `openssl x509 -enddate` 查看有效期并轮换 |
| `hostname mismatch` / `IP address mismatch` | SAN 不含实际访问的主机名或 IP | 用 `-servername` 对齐，重签带正确 SAN 的证书 |
| `unable to get local issuer certificate` | 客户端不信任签发 CA，或链不完整 | 检查 `-CAfile`、服务端是否发送中间证书 |
| `certificate required` / 握手直接断开 | 服务端要求 mTLS，客户端未带 `-cert/-key` | 补客户端证书，并确认其 EKU 适合客户端认证 |
| `tlsv1 alert unknown ca` | 服务端不信任客户端证书的签发者 | 把客户端 CA 加入服务端信任库 |

gRPC 中对应的通常是“通道凭证”：服务端配置证书与私钥，客户端配置信任的 CA；需要 mTLS 时再要求并校验客户端证书。各语言的具体凭证 API 名称与参数以所读 gRPC 文档版本为准。

### 2. 身份和权限映射

**认证不等于授权。** 认证回答“你是谁”，授权回答“你能做什么”。mTLS 握手成功只说明客户端持有某张受信任证书；它不自动说明这个身份可以写配置。反过来，只有令牌校验、没有方法级权限表，也会让一个只读工具意外获得删除能力。

身份来源可以是：

- mTLS 客户端证书的 subject（常见取 CN，或取 SAN 中的 URI/DNS 标识；选用哪个字段要团队统一，并防止同名冲突）。
- 网关/服务端校验过的令牌所对应的主体。
- 服务自身签发的短期身份。

无论来源是什么，服务端都应在入口处完成验证，把结果写入请求上下文，再供下游使用。接上 `f-context` 的原则：只信任本进程验证过的身份，不信任外部传入的 `X-User`、`X-Role` 等请求头；如果网关已经验证并转发身份，服务边界仍需确认“这些头只能来自可信网关”，否则调用方可自行伪造。

| 身份/角色 | Get | List | Put | Delete | 说明（教学假设） |
|---|---|---|---|---|---|
| `ops-reader` | 允许 | 允许 | 拒绝 | 拒绝 | 运营只读工具 |
| `config-writer` | 允许 | 允许 | 允许 | 拒绝 | 配置发布服务 |
| `admin` | 允许 | 允许 | 允许 | 允许 | 受控的人工运维入口 |
| 未认证 | 拒绝 | 拒绝 | 拒绝 | 拒绝 | 默认拒绝 |

**默认拒绝。** 权限表应是白名单：没有明确允许的组合一律拒绝。这样新增方法时不会因为“忘了配置”而默认放开。角色到权限的映射可以集中配置，但判断必须在服务端每个 RPC 方法入口执行，不能只靠客户端隐藏按钮。

```python
ROLE_PERMISSIONS = {
    "ops-reader": {"Get", "List"},
    "config-writer": {"Get", "List", "Put"},
    "admin": {"Get", "List", "Put", "Delete"},
}

IDENTITY_ROLES = {
    "ops-reader": "ops-reader",
    "config-writer": "config-writer",
    "oncall-admin": "admin",
}

class PermissionDenied(Exception):
    pass

def authorize(identity: str | None, method: str) -> None:
    if not identity:
        raise PermissionDenied("unauthenticated")
    role = IDENTITY_ROLES.get(identity)
    allowed = ROLE_PERMISSIONS.get(role, set())
    if method not in allowed:
        raise PermissionDenied(f"{identity} cannot call {method}")

# 演示：只读身份调用写方法
try:
    authorize("ops-reader", "Put")
except PermissionDenied as e:
    print("denied:", e)   # denied: ops-reader cannot call Put
```

真实实现中，`identity` 必须来自刚完成的证书/令牌校验结果，而不是请求体或可伪造的头部。授权判断应尽量靠近方法实现，并在进入业务逻辑、访问存储之前完成。

**错误码要区分。** 未认证表示“没有可信身份或凭证无效”，无权限表示“身份有效但该操作不允许”。两者混用会让客户端错误重试，也会让审计失真。gRPC 中常见的映射是 `UNAUTHENTICATED` 与 `PERMISSION_DENIED`，具体状态码语义与各语言写法以所读文档版本为准。

| 场景 | 建议返回 | 客户端动作 |
|---|---|---|
| 没有客户端证书，或证书不受信任 | `UNAUTHENTICATED` | 修复凭证，不要盲目重试 |
| 令牌过期/签名无效 | `UNAUTHENTICATED` | 重新获取令牌 |
| 身份有效但角色不允许该方法 | `PERMISSION_DENIED` | 不要重试，提示申请权限 |
| 目标 key 不存在 | `NOT_FOUND` | 按业务处理 |
| 请求超过大小/速率限制 | `RESOURCE_EXHAUSTED`（以文档为准） | 降低批量或退避重试 |

授权通过后，才进入存储访问。对于“读某个 key”这类操作，还要注意对象级权限：角色允许 `Get` 不等于允许读取所有命名空间。教学假设中可以把 key 前缀映射到租户或环境，再在授权层检查，而不是只检查方法名。

### 3. 消息大小、速率与审计

**为什么认证过的调用方也要限制。** 可信身份不代表行为可控：有 bug 的脚本可能一次发送巨大 payload，失控的自动化任务可能在循环里重试，网关抖动会造成重试风暴。服务端如果不设边界，单个调用方就能耗尽内存、连接数和下游容量。

| 控制点 | 目的 | 常见做法 |
|---|---|---|
| 最大消息大小 | 防止超大请求拖垮内存 | 先读长度头，超过上限立即拒绝，不继续读包体 |
| 每身份速率 | 限制突发与持续调用量 | 令牌桶/漏桶，按身份或身份+方法分桶 |
| 并发上限 | 防止连接和线程/协程被占满 | 信号量、工作池、队列上限 |
| 超时与截止时间 | 防止慢请求长期占用资源 | 入口设置 deadline，逐跳传递并留余量 |
| 审计 | 事后追责与排障 | 记录身份、方法、key、结果、trace_id |

大小限制要在解析层做，而不是等整个消息读进内存后再判断。教学假设的 KV 请求有长度前缀时，可以先读头部：超过 `MAX_MESSAGE_BYTES` 就直接返回错误并关闭该请求；对于流式 RPC，还要限制累计字节数，不能只限制单帧。

下面是一个可直接运行的单进程令牌桶示例，按身份限速：

```python
import time

class TokenBucket:
    def __init__(self, rate_per_sec: float, burst: int):
        self.rate = rate_per_sec
        self.burst = burst
        self.tokens = float(burst)
        self.updated = time.monotonic()

    def allow(self, cost: float = 1.0) -> bool:
        now = time.monotonic()
        self.tokens = min(self.burst, self.tokens + (now - self.updated) * self.rate)
        self.updated = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True
        return False

buckets: dict[str, TokenBucket] = {}

def allow_request(identity: str) -> bool:
    bucket = buckets.setdefault(identity, TokenBucket(rate_per_sec=5, burst=10))
    return bucket.allow()

for i in range(12):
    print(i, allow_request("ops-reader"))
```

单机令牌桶只解决单进程问题；多副本部署时，通常要结合网关限流、集中式配额或一致性要求较低的分片限流。具体实现取决于所读框架/网关文档版本。并发上限同样重要：认证通过、限速通过，但下游已经过载时，应快速失败或排队，而不是无限创建连接。

**审计日志。** 审计的目标是回答“谁在什么时候对什么做了什么，结果如何”。建议至少记录时间、经过验证的身份、方法、目标 key/资源、结果、trace_id；不要记录令牌、私钥、密码，也不要记录完整请求体中的敏感内容。

| 应记录 | 不应记录 |
|---|---|
| 时间、身份、方法、key、结果、trace_id | 令牌、私钥、密码、证书私钥内容 |
| 拒绝原因（如 `PERMISSION_DENIED`） | 完整的敏感请求体或响应体 |
| 目标命名空间/环境等必要维度 | 可被用来重放的认证材料 |

错误示例（把凭证写进日志）：

```text
2026-11-10T10:00:00Z INFO auth token=Bearer eyJhbGciOi... method=Put key=prod/db/password result=ok
```

正确示例（只记录身份与结果）：

```text
2026-11-10T10:00:00Z INFO audit identity=config-writer method=Put key=prod/db/timeout result=OK trace_id=7f3c...
2026-11-10T10:00:01Z WARN audit identity=ops-reader method=Put key=prod/db/timeout result=PERMISSION_DENIED trace_id=8a1d...
```

一个简单的脱敏函数可以在写日志前兜底：

```python
import re

SENSITIVE_KEYS = {"token", "authorization", "password", "secret", "private_key"}

def redact(value):
    if isinstance(value, dict):
        return {
            k: ("***" if k.lower() in SENSITIVE_KEYS else redact(v))
            for k, v in value.items()
        }
    if isinstance(value, list):
        return [redact(v) for v in value]
    if isinstance(value, str):
        return re.sub(r"(Bearer|Basic)\s+[A-Za-z0-9._~+/=-]+", r"\1 ***", value)
    return value

print(redact({"method": "Put", "token": "abc", "note": "Bearer xyz.123"}))
```

脱敏是最后一道防线，不是第一道：日志字段应采用白名单式构造，避免把整个请求对象直接序列化。

收束一下：TLS 保护链路并让客户端验证服务端，mTLS 进一步让服务端认证调用方；认证得到的身份要在请求上下文中传递，再通过服务端权限表做默认拒绝的授权；即使身份可信，也要用大小、速率、并发和审计约束资源使用。三者分别测试：先验证无证书/错误证书被拒绝，再验证只读身份越权写入被拒绝，最后检查日志中没有凭证。

## 常见误区

这一节把实现中最容易出问题的判断集中列出。先回到节点给出的前提，再逐条看误区。以下场景均为教学假设，用于说明通用后台问题，不代表任何公司内部实现。

### 前提：内网不是信任边界

节点已经写明：

> 处于内网不等于可以跳过身份与授权检查。

很多团队的真实假设是「能连上就是自己人」：服务部署在同一 VPC，调用方来源 IP 固定，于是认证和授权都被省掉。这个假设在三种情况下会直接失效。

- **内网横向移动**：任何一台被攻破的机器、任何一个被拿到的运营工具凭据，都可以沿内网可达性直接调用 KV 写入、配置变更、图文发布等接口。攻击者不需要突破边界，只需要找到一个跳板。
- **误操作脚本**：内部定时任务、批量修复脚本、运营后台的一次性工具，只要参数写错或环境选错，在没有身份与授权约束时就能覆盖配置、批量改文章状态。这类事故往往不是恶意攻击，但破坏力相同。
- **共享网段**：办公网、测试环境、容器网络常常路由互通，仅凭来源 IP 段无法区分调用方是谁、以什么身份调用、该不该允许。IP 只能说明「从哪里来」，不能说明「谁在调用」。

所以，内网可以降低一部分网络暴露面，但不能替代身份认证和授权决策。下面的误区大多源于把这几件事混为一谈。

### 误区一：只校验证书，不做授权

**误区**：TLS 握手成功、客户端证书校验通过，就认为调用方「可信」，于是放开所有方法。

**后果**：证书只回答「你是谁」，不回答「你能做什么」。任何持有合法证书的服务，或配置错误的客户端，都能写 KV、改配置、发布文章。在 mTLS 下这个问题更隐蔽：调用方身份是明确的，但权限没有收口。

**正确做法**：把认证和授权分成两层。认证层确认调用方身份（证书主体、令牌对应的服务账号等），授权层在服务端按身份映射角色/权限，并对每个方法单独判断，例如 KV 的读、写、删除命名空间分别对应不同权限。授权决策必须在服务端完成，不能因为链路已加密就跳过。

### 误区二：在客户端做权限判断

**误区**：运营工具在前端隐藏「删除」「发布」按钮，或由客户端根据角色决定要不要发起某个 RPC，就认为权限已经控制住了。

**后果**：客户端可以被替换、被脚本直接调用，隐藏按钮不等于服务端拒绝。只要 RPC 端点可达，构造一个请求就能绕过所有 UI 判断。

**正确做法**：客户端判断只作为体验优化，服务端才是唯一的授权决策点。每个方法入口都要检查调用方身份与所需权限，越权请求返回明确的拒绝结果，并记录审计日志。

### 误区三：把令牌、证书私钥打进日志或错误信息

**误区**：为了排障打印完整请求头、把令牌拼进日志、在异常信息里回显证书私钥或完整 PEM 内容。

**后果**：凭证会扩散到日志平台、告警群、工单系统和本地终端，等同于泄露。即使后来删掉日志，副本往往已经流转出去。

**正确做法**：日志只记录调用方身份标识、方法名、结果码、耗时和必要的资源标识；令牌、私钥、完整证书内容一律不记录，确需关联时使用不可逆的摘要或内部 ID。错误信息只说明失败原因，不回显凭证。（对应 acceptance「日志不暴露凭证」。）

### 误区四：关闭证书校验图省事

**误区**：联调时为了快点跑通，使用 `verify=False`、`InsecureSkipVerify` 之类的开关，或对自签证书直接跳过校验，并把它带进了测试甚至生产配置。

**后果**：中间人可以冒充服务端，TLS 只剩下「看起来加密」，完整性校验也失去意义。更麻烦的是这类开关常常藏在配置里，很难被 code review 发现。

**正确做法**：正确配置 CA 和证书链；测试环境使用独立 CA，并把测试 CA 纳入测试客户端的信任库；确需临时绕过时必须限定环境、有明确到期时间并纳入检查清单。具体配置项名称、TLS 版本与套件选择以所读文档版本为准。

### 误区五：证书过期无监控，导致全站故障

**误区**：证书只在首次上线时签发，没有到期告警，也没有轮换流程。

**后果**：到期瞬间所有 RPC 握手失败，网关到多级 RPC 的整条链路一起不可用；mTLS 下客户端证书过期还会让服务端拒绝调用方，故障面更大。

**正确做法**：为所有证书配置到期告警（提前数周），定期做轮换演练，把签发和轮换纳入发布流程；mTLS 要同时覆盖服务端证书和客户端证书，并确保轮换期间新旧证书有重叠窗口。

### 误区六：把加密和授权放进同一个测试

**误区**：一个用例同时验证「能连上」和「能写入」，失败了再看是哪一步。

**后果**：失败时无法区分是 TLS 配置、证书链、证书过期，还是授权规则写错，回归定位慢，也容易在修一个问题时掩盖另一个问题。

**正确做法**：分层测试。第一层只测加密链路：无证书、错误证书被拒绝，正确证书可以建立连接；第二层在已认证的前提下，用一个「有身份但无权限」的调用方验证越权写入被拒。两层分别有独立断言，出错时能直接定位。（对应 acceptance「加密链路与业务授权分别测试」。）

## 设计权衡

节点对 mTLS 的成本有一句准确的概括：

> mTLS加强身份管理，也增加证书签发轮换和排障成本。

这句话的重点不是「不要用 mTLS」，而是「身份强度和运维成本要一起算」。提升安全性的方案很多，差别通常不在能不能做，而在团队是否愿意长期承担它的运维复杂度。

### 几种常见组合的对比

下表是一般经验，不是绝对结论；具体行为以所读文档版本和实际部署为准。

| 方案 | 身份强度 | 运维成本 | 排障难度 | 适用场景 |
| --- | --- | --- | --- | --- |
| mTLS | 强：双向证书，调用方身份明确 | 高：CA、签发、轮换、吊销都要管 | 高：握手失败原因多，证书链问题不直观 | 服务间强身份、合规要求高的内部 RPC |
| 服务端 TLS + 令牌 | 中：强度取决于令牌签发与保管 | 中：令牌签发、过期、撤销 | 中：认证失败与授权失败需分开看 | 大多数内部服务，已有统一令牌体系时更顺 |
| 网关统一鉴权 | 取决于网关到后端是否透传身份 | 中低：入口集中管理 | 中：问题可能在网关或后端 | 边界入口统一收口；后端仍需方法级授权 |
| 服务网格 sidecar | 强：平台可自动做 mTLS | 中高：依赖平台能力 | 高：链路长，可观测性依赖平台 | 平台化程度高、愿意统一托管证书的团队 |

一个一般经验是：网关做第一道认证，服务间按敏感度选择 mTLS 或令牌，业务服务保留方法级授权。不要把「入口认证」当成「全部授权」。

### 证书有效期：短与长的取舍

短有效期缩小私钥泄露后的可用窗口，但轮换频率更高，对自动化和监控的要求也更高；长有效期省运维，但泄露和吊销的风险更大，出问题时影响时间也更长。一般经验是先把自动轮换和到期告警做扎实，再逐步缩短有效期，而不是一上来就追求很短的有效期。

### 授权粒度：服务级、方法级、资源级

- **服务级**：一个服务一个权限，最省事，但服务内所有方法同权，适合早期或低敏感服务。
- **方法级**：按读、写、管理等操作区分，是内部 RPC 常见做法，KV 服务的读配置、写配置、删除命名空间可以分别授权。
- **资源级**：还要判断「对哪个资源」，例如只能改自己负责的命名空间或某类配置。粒度最细，但需要业务数据参与判断，成本和出错面都更高。

一般经验是从方法级起步，对高风险资源再加资源级判断，避免一开始就设计过细的权限模型。

### 限流放在网关还是服务内

网关适合做粗粒度、统一入口的限流，挡住洪峰、保护后端整体；服务内适合按方法、租户或资源做更细的控制，并能保护单个实例。两者并不冲突：网关挡外部压力，服务内保自身稳定。只做其中一层，通常会在另一层留下缺口。

### 审计日志的量与存储成本

审计日志要能回答「谁在什么时间对哪个资源做了什么、结果如何」，但不要记录令牌、私钥等凭证。高 QPS 下全量记录成本很高，一般经验是按敏感操作分级：写配置、删除、发布等敏感操作完整记录，普通读可以采样或只记聚合指标；同时设定保留期和冷热分层存储，避免审计日志本身成为成本和隐私负担。

### 一个组合示例：KV 服务与图文发布链路（教学假设）

假设有一条链路：运营工具 → 网关 → 图文发布服务 → KV 服务。可以按敏感度分层：

- 运营工具到网关：服务端 TLS + 登录令牌，网关完成第一道认证，并把身份（操作者或服务账号）写入受控的调用上下文。
- 网关到图文发布服务：服务端 TLS + 调用令牌，网关只放行已认证的入口流量；图文发布服务对「创建草稿」「发布」「下线」分别做方法级授权。
- 图文发布服务到 KV 服务：根据 KV 中存放的是普通配置还是敏感开关，选择 mTLS 或服务端 TLS + 令牌；写配置和删除命名空间单独授权。
- 所有写操作记录审计日志：调用方身份、资源标识、操作类型、结果；日志中不出现令牌和私钥。

这个示例的重点不是照抄，而是每跳都回答两个问题：调用方是谁，它能做什么。加密只解决链路问题，不替代这两个回答。

### 权衡检查清单

在选方案前，可以先回答下面几个问题：

1. 威胁模型是什么？是防外部攻击、防内网横向移动，还是满足合规审计？不同目标对身份强度的要求不同。
2. 团队能否长期维护 CA、签发、轮换和吊销？如果答案是否定的，mTLS 的隐性成本会很高。
3. 身份能否透传到后端？如果网关终止了认证但后端拿不到身份，方法级授权就无从谈起。
4. 证书和令牌的到期告警、轮换演练是否已经自动化？没有监控的 mTLS 比不做 mTLS 更危险。
5. 授权粒度是否与业务风险匹配？低敏感读接口不必过度设计资源级权限。
6. 审计日志的保留期、存储成本和访问权限是否明确？审计数据本身也需要保护。

### 取舍的底线

无论选择哪种组合，有几条底线不变：

- 服务端必须做授权决策，客户端判断不能作为安全边界。
- 凭证不进日志、不进错误信息、不进工单。
- 加密链路测试与授权测试分开，失败时能定位到具体层。
- 内网流量同样经过身份与授权检查，不能因为「都在内网」而放行。

### 误区与权衡的对应关系

- 「只校验证书不做授权」对应权限映射的粒度选择：认证强不等于授权细。
- 「客户端做权限判断」对应授权决策点：放在服务端才能统一。
- 「关闭证书校验」对应 TLS/mTLS 的运维能力：做不好校验，不如先把 CA 和轮换流程建好。
- 「证书过期无监控」对应有效期取舍：自动化不到位时，长有效期只是延迟故障，不是消除故障。
- 「加密与授权一起测」对应排障成本：分层测试是控制 mTLS 复杂度的必要手段。

### 本节小结

- 内网不是信任边界，认证与授权必须在服务端做。
- 加密链路与业务授权分层测试，日志不出现凭证。
- mTLS 的身份强度更高，但要连证书签发、轮换和排障成本一起评估。

评估方案时，把身份强度、运维成本和排障难度放在一起看，而不是只比较加密强度。

## 动手实践：为 KV 服务加入 TLS 和只读角色

> 节点 practice 原文：「为KV服务加入TLS和只读角色，验证无证书与越权写入被拒绝。」
> 验收标准（acceptance 原文）：「加密链路与业务授权分别测试」「日志不暴露凭证」。

本课附带的 `practice93/` 是一份可直接运行的教学实现（Python 标准库 `ssl` + `openssl` 命令，不依赖 gRPC 包），结构与 gRPC 的「通道凭证 + 服务端按身份授权」思路对应，但协议是自定义的「4 字节长度头 + JSON」，只用于教学。

| 文件 | 作用 |
|---|---|
| `kvserver.py` | mTLS 服务端：`CERT_REQUIRED` 校验客户端证书；从证书 CN 取身份，映射角色 `reader`/`writer`，默认拒绝；最大消息 64KB；每身份令牌桶（5/s，突发 10）；JSON 审计日志并把 `token/password/authorization` 脱敏为 `***` |
| `client.py` | 客户端：校验服务端证书链与主机名，可选携带客户端证书、伪造令牌、超大包体、明文连接、连发 N 次 |
| `test.sh` | 一键生成 CA/证书，按 A 加密链路层、B 业务授权层、C 输入规模与速率、D 审计与凭证 四组分别验证 |

### 步骤 1：签发证书（test.sh 自动完成，建议手动跑一遍理解）

```bash
# 自签 CA（Python 3.13 默认的严格校验要求 CA 带 basicConstraints 和 keyUsage）
openssl req -x509 -newkey rsa:2048 -nodes -days 30 -subj "/CN=ca" \
  -keyout certs/ca.key -out certs/ca.crt \
  -addext "basicConstraints=critical,CA:TRUE" -addext "keyUsage=critical,keyCertSign,cRLSign"
# 服务端证书：SAN 必须包含客户端连接用的主机名
openssl req -newkey rsa:2048 -nodes -subj "/CN=kv-server" -keyout certs/server.key -out certs/server.csr
openssl x509 -req -in certs/server.csr -CA certs/ca.crt -CAkey certs/ca.key -CAcreateserial \
  -days 30 -extfile certs/server.ext -out certs/server.crt   # server.ext 含 subjectAltName=DNS:localhost,IP:127.0.0.1
# 客户端证书：CN 就是身份，reader-cli / writer-cli；另用 rogue-ca 签一张 CN=writer-cli 的冒名证书
openssl x509 -in certs/reader-cli.crt -noout -subject -issuer -enddate
```

身份与权限映射写在服务端，而不是让客户端自报角色：

```python
ROLE_OF = {"reader-cli": "reader", "writer-cli": "writer"}      # 身份 -> 角色
PERMS = {"reader": {"GET"}, "writer": {"GET", "PUT", "DELETE"}}  # 角色 -> 方法；没列的一律拒绝
```

### 步骤 2：运行

```bash
tar xzf practice93.tar.gz && cd practice93 && ./test.sh
```

### 步骤 3：对照实测输出（本课在 Linux 上实际运行的结果）

**A. 加密链路层**——这一组都只看握手，与业务权限无关：

| 用例 | 实测结果 | 说明 |
|---|---|---|
| A1 明文客户端连 TLS 端口 | `ConnectionResetError` | 服务端握手失败直接断开 |
| A2 不带客户端证书 | `ConnectionResetError`，服务端记 `HANDSHAKE_REJECTED` | TLS 1.3 下客户端往往只看到连接被重置，原因要看服务端日志 |
| A3 非受信 CA 签发、CN 冒充 `writer-cli` | `TLSV1_ALERT_UNKNOWN_CA` | 证书里写什么 CN 都没用，签发者不受信 |
| A4 用 `evil.example` 作主机名 | `Hostname mismatch, certificate is not valid for 'evil.example'` | 客户端侧对服务端的认证 |
| A5 正常 mTLS | `TLS TLSv1.3 {"code": "OK", "value": "hello"}` | `openssl s_client` 复核：`Protocol: TLSv1.3`，`Verify return code: 0 (ok)` |

**B. 业务授权层**——双方都持合法证书，只测权限：

```text
reader PUT: {"code": "PERMISSION_DENIED", "msg": "reader-cli (reader) cannot PUT"}
PASS B1 只读角色越权写入被拒绝
PASS B2 只读角色删除被拒绝
越权后值: {"code": "OK", "value": "hello"}      # B3 值没有被改动
PASS B4 writer 写入成功 / PASS B5 reader 读到新值
```

**C. 输入规模与速率**：

```text
200KB 请求: {"code": "RESOURCE_EXHAUSTED", "msg": "message 200040 > 65536"}   # 只读了 4 字节长度头就拒绝
reader 连发 30 次: CODES OK=10 RESOURCE_EXHAUSTED=20                         # 突发 10 个后被限速
PASS C3 其他身份不受影响                                                       # 令牌桶按身份隔离
```

**D. 审计与凭证**——请求里故意带了令牌 `tok-SECRET-9f3a`：

```json
{"identity": "reader-cli", "op": "PUT", "key": "cfg/banner", "result": "PERMISSION_DENIED",
 "req": {"op": "PUT", "key": "cfg/banner", "token": "***"}}
```

`grep` 确认 `audit.log` 和服务端输出里都没有令牌原文和 `PRIVATE KEY`，最后打印 `ALL_CHECKS_PASSED`。

### 步骤 4：自己动手改，观察变化

1. 把 `kvserver.py` 里 `verify_mode = ssl.CERT_REQUIRED` 改成 `CERT_NONE`：A2、A3 会变成能连上，而且 `getpeercert()` 拿不到身份，所有请求都会因 `role is None` 被拒绝——这正说明「加密」和「认证」是两层。
2. 在 `PERMS` 里给 `reader` 加上 `"PUT"`：A 组全部照常通过，只有 B1 失败——分层测试让你一眼看出是授权层出了问题。
3. 把 `redact()` 换成直接 `json.dumps(req)`：D2 立刻失败，令牌原文进了日志。
4. 把 `-days 30` 改成很短的有效期并等它过期（或用 `faketime` 之类工具），观察握手报错，体会 tradeoffs 里说的「证书签发轮换和排障成本」。

### 后台场景迁移（教学假设）

一个内部配置 KV 服务给多个运营工具和自动化脚本用：给只读看板发 reader 身份的证书，给发布系统发 writer 身份；每个身份单独限速，Delete 只留给少数身份并且必记审计。真实的 gRPC 项目里，这些分别对应通道 TLS 凭证、服务端拦截器里的鉴权、最大接收消息大小配置和审计日志，具体 API 以所读 gRPC 语言版本文档为准。

## 自测题

### 题 1：已开启 TLS，为什么仍能被任意进程调用 Put？

**题干：** 某配置/KV 服务已开启 TLS，客户端需要信任服务端证书才能连接。但测试发现，任何能连上服务端口的进程都可以调用 `Put` 写入数据。缺了什么？应如何补？

**答案：** 缺的是**调用方身份认证**和**服务端授权**。单向 TLS 只解决传输加密、完整性以及"客户端验证服务端身份"，并不证明调用方是谁。需要补充：用 mTLS 让服务端要求并验证客户端证书，或用调用凭证（例如令牌）标识调用方；然后在服务端把身份映射到角色/权限，并在每个方法（例如 `Put`）执行前做授权判断。网络位置（例如"处于内网"）不能替代这两步。

**解析：** TLS 与 mTLS 解决不同问题：TLS 主要保护链路并让客户端确认服务端；mTLS 增加服务端对客户端证书的要求与验证，从而认证调用方。认证之后还要授权。两者应分别测试：先验证"无证书或无令牌被拒绝"，再验证"有身份但越权被拒绝"。不要把"能建立加密连接"误认为"已授权"，也不要把网关已经终止 TLS 当作下游服务可以跳过身份检查的理由。

### 题 2：只读脚本调用 Delete，服务端应如何拒绝与记录？

**题干：** 一个持有合法客户端证书的只读运营脚本调用了 `Delete`。服务端应返回什么？在哪一层判断？审计日志应如何记录？给出一行不含凭证的示例日志。

**答案：** 服务端应在**业务授权层**（例如拦截器、中间件或方法入口的权限检查）判断，而不是在 TLS 握手层判断；TLS 只负责确认对端身份。授权失败应返回表示"已认证但无权限"的 RPC 错误，常见为 `PERMISSION_DENIED`，具体状态码与语言 API 以所读版本文档为准，并拒绝执行删除。审计日志记录时间、主体标识、角色、方法、资源、结果与原因，但**不得记录令牌、私钥、证书私钥或完整凭证**。

示例（单行，字段可按团队规范调整）：

`2026-11-10T12:00:00Z outcome=denied reason=rbac principal=svc-ops-readonly role=viewer method=/kv.KV/Delete resource=kv:config/app`

**解析：** 授权判断的位置决定了错误语义：证书校验失败通常发生在连接建立阶段；身份合法但权限不足属于业务层拒绝。日志中的主体标识应是经过映射的服务身份或角色标签，而不是原始证书内容或令牌。若日志系统需要关联请求，可使用请求 ID，但同样不得写入凭证。审计日志应能回答"谁、在何时、对什么、做了什么、结果如何"，并能在不暴露敏感材料的前提下支持追查。

### 题 3：不限制消息大小时，50 个并发 100MB 请求会怎样？

**题干：** 服务端未限制最大消息大小。50 个并发客户端各发送 100MB 请求，可能出现什么问题？至少给出两种服务端限制手段，并说明取舍。

**答案：** 50 × 100MB 的请求体在服务端会产生约 5GB 的原始负载，叠加反序列化、缓冲区复制、框架内部队列和并发处理，内存占用会进一步放大，可能导致 OOM、频繁 GC、CPU 饱和、请求延迟上升，甚至进程崩溃，影响同实例上的其他调用方。至少两种限制手段：

1. **限制最大接收消息大小**（服务端与客户端分别配置合理上限），超限直接拒绝。取舍：上限过小会误伤合法的大批量请求，需要按业务峰值和真实报文分布评估。

2. **限制并发与速率**（最大并发调用/流、QPS 限流、准入控制），并配合请求超时与截止时间。取舍：限流过紧会降低吞吐并可能触发客户端重试，超时设置不当会造成重试风暴；阈值需要压测和线上观测后调整。

还可以结合应用层校验（例如业务字段大小、批量条数上限）以及分页/分片设计。具体配置项名称、默认值与行为以所读文档版本和框架版本为准。

**解析：** 这与本课 `summary` 一致：传输加密、对端认证与操作授权分别解决不同问题，服务端还需要限制输入规模与资源使用。限制消息大小、并发和速率属于服务边界的一部分；审计日志用于事后追查敏感操作，但日志本身不能成为新的泄漏点。取舍上，mTLS 加强身份管理的同时会增加证书签发、轮换和排障成本；资源限制提高稳定性，但需要持续调参并观察误杀与重试情况。

## 本课小结

- TLS 提供传输加密与完整性，并让客户端验证服务端身份；它本身不等于"调用方已认证"。

- mTLS 下服务端要求并验证客户端证书，从而认证调用方；mTLS 加强身份管理，也增加证书签发、轮换与排障成本。

- 认证回答"你是谁"，授权回答"你能做什么"；授权通常在服务端按身份映射角色/权限，再逐方法判断每个调用是否允许。

- 通道凭证绑定连接、调用凭证绑定每次调用，二者可以组合；具体 API 名称、组合方式与错误表现以所读文档版本为准。

- 服务端应限制最大消息大小、并发与速率，避免大请求和高并发耗尽内存与 CPU；阈值需要结合业务、压测和线上观测调整。

- 敏感操作要记审计日志，日志中不得写入令牌、私钥等凭证；日志应能回答谁在何时对什么做了什么、结果如何。

- 处于内网不等于可以跳过身份与授权检查；加密链路与业务授权应分别测试：无证书或无令牌被拒绝，有身份但越权也被拒绝。

- 公开文档只能支撑通用机制的理解，不能推断任何企业内部实现；角色映射等文档未充分展开的部分属于本课扩展。
