# 第 165/208 课：向量检索与混合召回

> 序号 165/208 · id `k-vector` · 领域 K · 阶段 3 · 难度 进阶 · 子类 检索增强
> 前置：[`k-rag`](https://zhousai-zs.github.io/backend-atlas-notes/lessons/164.html)
> 节点摘要：近似近邻索引在召回率、内存和查询延迟间权衡；混合检索把语义与精确匹配结合。

## 导读

有了向量之后，下一个工程问题是：怎么在可接受的延迟里找到近邻，以及过滤之后还剩不剩候选。近似索引（HNSW 一类）会漏掉真实近邻；过滤可能把正确答案直接剔出候选集。参数不能靠几个好看的例子来定。

## 学习目标

1. 解释 HNSW 及适用边界。
2. 独立完成实践：构建精确错误码和自然语言两类查询，比较向量与混合检索的 recall@k。

## 为什么后端要懂

线上查询同时包含 `E_CONN_RESET` 这种符号和「就绪探针失败会不会重启容器」这种自然语言。只信一种检索，会在另一类查询上静默失败。过滤条件写错时，索引再准也找不到已被排除的文档。

## 核心知识点

### 1. 精确近邻与近似近邻（HNSW）

**直觉。** 在已经算好的向量上，把查询向量与所有文档做内积，得到的是该空间里的精确 k 近邻。HNSW 之类的图索引用有限的边和有限的探测去逼近它，换速度、换内存，也换掉「一定找得到真正的近邻」。

**官方口径。** pgvector README（2026-11-15 同批抓取）：默认是精确近邻，提供完全召回；加上 HNSW 等近似索引后，用召回换速度，并且「加索引后查询结果可能与之前不同」。参数 `m`、`ef_construction`、`hnsw.ef_search` 越高，通常召回越好、构建或查询越慢。本机没有 Postgres，也没有安装成 `hnswlib`（该库此前在本环境因编译器不支持而安装失败），因此**不能**把本课结果写成 pgvector / hnswlib 的实测。

**实践对照。** `ann.py` 实现的是教学用 NSW：每个点只连 `m=2` 条随机边，搜索从「与查询最远」的点出发，只走 3 跳。这不是 pgvector 的 HNSW。在本课 16 条标注查询上，它在错误码集合上的文档级 recall@5 为 0.0，自然语言集合为 0.5，并且在绝大多数查询上错过了 MiniLM 空间里的精确最近邻。这是在演示「近似 + 差参数会漏掉真实近邻」，不是在推荐这组参数，更不是在说「语义检索不如 BM25」。

### 2. 报告查询集与召回口径

**口径（写进 `results.json`）。** Recall@k 是：查询的 gold **文档** ID 是否出现在 top-k **段落** 所所属的文档中。这是文档级召回，不是段落级，更不是「生成答案是否正确」。k=5。查询集分两族，各 8 条：错误码/符号（`E_CONN_RESET`、`ENOSPC`、`OOM_KILL`、`cl100k_base`、`call_id` 等）与自然语言（为何杀进程、就绪探针会不会重启、哈希是不是 Sentence Transformer、Evals 还能不能开新项目等）。

**本机数字（MiniLM 精确检索 / BM25 / 混合，均对应该标注集）。**

| 查询族 | minilm_exact | bm25 | hybrid | teaching_nsw |
| --- | ---: | ---: | ---: | ---: |
| 错误码（8） | 1.0 | 1.0 | 1.0 | 0.0 |
| 自然语言（8） | 1.0 | 1.0 | 1.0 | 0.5 |

**边界。** 16 条查询上得到 1.0，不能用来选定生产 HNSW 参数——这正是官方误区「只凭几个好看的例子选索引参数」。集合小、文档短、gold 与用词重叠明显时，BM25 和精确向量都很容易打满。要用更大、更难的集，并且把近似索引的召回相对**精确近邻**单独报告。

本课未使用哈希向量充当语义索引。

### 3. 过滤后候选不足

**直觉。** 元数据过滤发生在「谁有资格进入候选」这一层。过滤之后，即使集合里存在正确答案，检索也找不到它。

**实践对照。** 查询「写入失败是因为卷满了」，gold 是 D03（标签 `storage`）。加上 `tag=network` 后，候选里仍有网络类文档，但 D03 不在其中，过滤后命中为假。`results.json` 明确写出：`gold_present_unfiltered=true`，`gold_present_after_filter=false`，原因是过滤把金标排除了，而不是模型「语义不好」。

## 常见误区

- 只凭几个好看的例子选索引参数。
- 把教学 NSW 或哈希向量称为 pgvector HNSW / 语义索引。
- 过滤后找不到文档，却去调 embedding 模型。
- 不声明 recall 是文档级还是段落级，也不声明 k。

## 设计权衡

近似索引更快但可能漏掉真实近邻。提高 `ef_search` / `m` 通常能补回召回，代价是延迟和内存。混合检索（本课为 z-score 后相加）能同时照顾符号和句子，但融合权重需要在独立测试集上调，本课没有做权重搜索。

## 自测题

**1. 为什么必须先写清 recall 的口径再比较方法？**

答案：文档级、段落级、答案正确率是三件事。本课是「gold 文档是否出现在 top-5 段落所属文档中」。口径不清，1.0 和 0.5 无法解释。

**2. 过滤后找不到 D03，是不是向量模型失败了？**

答案：不是。D03 的标签是 storage，过滤条件是 network，金标根本不在候选里。应先检查过滤是否过窄。

**3. 教学 NSW 在错误码上 recall@5=0，能说明「不要用 HNSW」吗？**

答案：不能。它只说明在 m=2、从最远点起步、只走 3 跳时，近似搜索会错过精确近邻。官方 HNSW 的 `m` / `ef_search` 默认值比这大得多，需要在真实索引上另测。
