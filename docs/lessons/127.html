边界说明：本课里的「内容后台」「文章键 article:01:title」「标题家族 Weekly digest / Weekly digest (revised) / Weekly digest (hotfix)」「节点 n1 / n2 / n3」「日志格式 v1 / v2」都是教学假设，用来让读写版本兼容、特性开关和半数升级再回滚变得可观察，不代表腾讯/微信或任何企业的内部实现。配套代码是 Python 3 标准库写的教学引擎 EvolutionEngine，不是 Redis，不是 etcd，不是真实的协议或产品，也不是网络服务。它是单进程离散事件仿真，没有 Raft，没有 WAL，没有 TCP，也没有真实的滚动发布工具。持久化是教学用 dict flush，不是 fsync。Clock 是虚拟时钟。write_s=0.05、upgrade_s=0.10、snapshot_s=0.05、restore_s=0.10 和 negotiate_s=0.05 都是教学延迟，不是生产 RTT。v1 / v2 是教学日志格式，不是 etcd 的 WAL 或 mvcc db。本课把节点里的 feature gate 落实为「只有集群版本升到 v2 才允许写出 v2 记录」，把迁移状态机落实为 all_v1 / mixed / all_v2；升级指南本身使用的是 mixed versions、lowest common version、supported features 和 enabled capabilities，并不定义这两个教学名字。本课所有时间都来自 /workspace/atlas/lessons/practice127/results.json，是教学虚拟时钟上的数字。

导读

上一课留下的缺口

上一课的 VerificationEngine 解决的是「一致性承诺怎样留下独立证据」：把并发操作记成 invoke / ok / fail / info 历史，注入分区或丢失应答，再用寄存器模型去核对，并保存能复现反例的种子。那一课的边界停在已经固定的协议和日志格式，没有回答另一件同样会破坏集群安全的事：滚动升级期间，旧二进制、新二进制和新的持久化格式会同时存在，旧节点会不会把一条新记录误读成错误的标题，集群版本一旦抬上去还能不能退回来。

找出一条陈旧读的反例，并不能代替「为新旧格式写兼容矩阵，并在半数升级后再试一次回滚」。节点把摘要写成：升级期间新旧节点、持久化格式和消息模式同时存在，需要兼容窗口与可回滚边界。

接上前置

前置 第 126 课 h-verification 留下的结论是：没有记下来的历史就没有可复查的证据；超时要记成不确定结果；测试能发现错误，但不能穷尽状态空间。把这条结论搬到升级上，就会看到对称的风险。如果只在「已经全部换成新二进制」的集群上跑通读写，就等于没测过混合版本窗口，也测不到「旧节点碰到新记录该拒绝还是误读」。本课不再生成 Jepsen 式的并发历史，而是给同一组标题加上 v1 / v2 两种日志格式，并让三个教学节点逐个更换二进制。

升级指南把滚动升级写成：一个接一个地把旧进程换成新进程；在全体更换完成之前，集群按最低共同版本的协议运行；新特性要等全部成员升级后才可用；一旦集群版本抬上去，就不能再靠换回旧二进制来降级，只能依靠事先保存的 snapshot。本课的兼容矩阵、特性开关和半数回滚，就是把这几句话落到可测量的步骤上，而不是复现 etcd 3.4 到 3.5 的发布流程。

教学场景（教学假设）

假设内容后台把文章 article:01:title 放在三个教学节点 n1、n2、n3 上，一开始三边都是 v1 二进制，日志里只有格式 v1 的 Weekly digest。一次写入花费 write_s=0.05，一次升级或回降花费 upgrade_s=0.10，随后用 negotiate_s=0.05 重算集群版本：只要还有一个 v1 成员，集群版本就是 v1，v2 日志格式的特性开关保持关闭，v2 二进制也只能继续写 v1 记录。三个成员都换成 v2 之后，集群版本升到 v2，开关打开，新写入带上教学字段 editor=desk。拍快照花费 snapshot_s=0.05，从快照恢复花费 restore_s=0.10。所有时间都是教学虚拟时钟上的值，不是线上滚动升级的墙钟时间，也不是生产 RTT。

本课三条主线

  1. 读写版本兼容：列出 v1 / v2 读写与记录格式的矩阵。新二进制必须能读旧记录；集群版本未抬升时，新二进制仍写旧格式；旧二进制碰到新记录必须拒绝，不能误读成一个错误标题。
  2. feature gate：v2 记录能不能写出，不取决于某台机器的二进制，而取决于集群版本。开关关闭时，半数成员已经是 v2，写出的仍是 v1。
  3. 迁移状态机：状态在 all_v1、mixed、all_v2 之间移动。处于 mixed 时可以回滚；进入 all_v2 之后二进制回降被拒绝，恢复策略是从升级前的快照还原。

学习目标

  • 能解释读写版本兼容及适用边界：兼容窗口靠「读得了旧格式、新格式被开关拦住」来维持；窗口只在集群版本尚未抬升时存在。指南里与 auth 相关的 WAL 格式变更不支持滚动升级，说明并不是所有格式变化都有这样的窗口。
  • 独立完成实践：为日志格式 v1/v2 写兼容矩阵，模拟半数升级再回滚。能指出半数升级时集群版本为什么仍是 v1，以及全体升级后为什么不能再换回旧二进制。
  • 验收上要做到：旧版本不会误读新记录；明确不可逆迁移后的恢复策略。

为什么后端要懂

节点给出的理由是：避免滚动升级破坏集群安全性。 升级很少是「三台机器在同一瞬间同时换成新版本」。只要中间有一段时间新旧并存，一条新格式记录就可能被旧进程看到。如果旧进程把它当成旧格式解析，标题可能被读错，集群的安全性在一次看起来正常的滚动中被破坏。指南要求先在预发环境验证、先拍 snapshot、按最低共同版本运行，并且写清「全部升级完成之后不能再降级」。本课用同一组标题把兼容窗口、特性开关和回滚边界写成可核对的数字，就是为了让「可回滚」不再只写在发布说明里。

核心知识点

1. 读写版本兼容

兼容矩阵要按「谁在写、集群版本是什么、谁在读、记录是哪种格式」逐格填写，而不是只看新集群能不能工作。本课得到的格子如下。

写入方 / 集群版本 写出格式 读取方 结果 时刻
v1 / v1 v1 v1 读到 Weekly digest (revised) 0.10
v1 / v1 v1 v2 同样读到 revised（新二进制能读旧记录） 0.30
v2 / v1（开关关闭） 仍是 v1 v1 读到 revised，特性 log_format_v2 为假 0.30
v2 / v2（开关打开） v2，并带 editor=desk v2 读到 revised 0.55
v2 / v2 v2 v1 拒绝，原因 unsupported_format，v1 节点仍保留 revised，并不把 hotfix 当成自己的标题 0.60

最后一格是验收要求的那句：旧版本不会误读新记录。 集群已是 v2 之后，进程在 n1 写出 Weekly digest (hotfix) 的 v2 记录，n1 / n2 应用成功，仍为 v1 二进制的 n3 拒绝这条记录，标题留在升级前已经共同持有的 Weekly digest (revised)。若忽略 fmt 字段直接取 value，不安全的解码会得到 hotfix——那才叫误读。正确的 v1 实现必须拒绝，而不是猜。

适用边界也在这张表里。兼容窗口成立，是因为 v2 二进制在集群仍为 v1 时继续写 v1 记录，旧节点根本不会碰到新格式。指南同时写明：若集群启用了 auth，3.5 更改了与 auth 相关的 WAL 条目格式，从 3.4 滚动升级不受支持。那种格式变化没有「先写旧格式」的窗口，不能用本课这张矩阵去硬套。

2. feature gate

节点所说的 feature gate，在本课里就是集群版本对「能否写出 v2 记录」的开关。指南的原话是：全体换成新进程之后，新特性才对集群可用；混合期间集群按最低共同版本的协议运行，成员协商出的 cluster version 控制所支持的特性。升级过程的日志里则出现 enabled capabilities for version。本课不把 feature gate 写成书中的正式接口名。

开关的效果可以从半数升级那条线上直接读出来。t=0.00 拍下快照，标题仍是 Weekly digest，校验和为 efe1be83bdea6938。0.10 到 0.15 写入 revised，格式是 v1。0.20 开始把 n1 升到 v2，0.35 协商结束，状态是 mixed，集群版本仍是 v1，开关为假。0.50 再升 n2，0.65 协商结束，两台已经是 v2、n3 仍是 v1，集群版本还是 v1。随后在 0.70 到 0.75 写入 Weekly digest (hotfix)，格式仍然是 v1，三个节点全部应用成功。新二进制已经占了半数，但没有被允许写出旧节点读不懂的记录。

3. 迁移状态机

状态按成员二进制和集群版本移动：全部为 v1 时是 all_v1；只要新旧并存就是 mixed；三台都换成 v2 并且集群版本抬升后是 all_v2。这是教学状态名，用来落实指南里「只有全体升级后才视为升级完成，混合时仍按旧协议运行」这句话。

mixed 是可回滚窗口。半数升级之后，0.80 把 n2 降回 v1，0.95 协商结束时状态仍是 mixed（n1 还是 v2），集群版本仍是 v1；接着把 n1 也降回，1.10 回到 all_v1。1.15 从 n3 读到的仍是格式 v1 的 Weekly digest (hotfix)。因为混合期间从未写出 v2 记录，回滚不需要动日志，只需要把二进制换回去。

窗口在最后一名成员升级时关上。对照路径里，n1、n2、n3 分别在 0.35、0.50、0.65 完成协商：前两次集群仍是 v1，第三次集群变成 v2，开关打开，状态成为 all_v2。随后 0.70 写出格式 v2 的 hotfix。此时再把 n1 降回 v1，会在 0.80 被拒绝，原因是 cluster_already_v2_and_log_has_v2_records，给出的恢复策略是 restore_from_pre_upgrade_snapshot。按这条策略从 0.05 的快照恢复，0.95 结束时标题回到 Weekly digest，校验和仍是 efe1be83bdea6938，集群版本回到 v1，三台二进制都是 v1。这就是验收要求的「明确不可逆迁移后的恢复策略」：不能再靠换回旧二进制，只能回到升级前拍下的快照。快照里没有后来的 revised 和 hotfix，这是正确的，说明恢复回到的是拍摄点。

常见误区

第一个误区是节点写明的那句：只测试全量新版本集群。 对照路径里，三台都已是 v2 时写入 revised，格式为 v2，读取成功，看起来一切正常，结束于 0.55。可是同一条 v2 写入若碰到一个仍为 v1 的 n3，就会被 unsupported_format 拒绝。全量新集群上的通过，测不到混合窗口，也测不到回滚边界。

第二个误区是把「已经有两台换成新二进制」当成「可以启用新格式」。半数升级之后开关仍是关的，hotfix 仍以 v1 写出并被 n3 接受。若在 mixed 里强行写出 v2，旧节点就会进入上一节那一格拒绝路径；兼容代码的意义，正是先把这种写出拦住。

第三个误区是以为全体升级之后还能靠换回旧二进制来撤。指南写得清楚：全部成员升级、集群版本抬升之后，降级不可用；事先下载的 snapshot 才是退路。本课在 0.80 拒绝回降，并在 0.95 用快照把标题恢复到 Weekly digest，就是把这句话跑通一遍。

设计权衡

节点给出的权衡是：兼容代码增加复杂度，但缩小升级爆炸半径。 为了让 v2 二进制在集群仍为 v1 时继续写 v1、让 v2 读者能读 v1、让 v1 读者拒绝而不是误读 v2，引擎里要同时理解两种记录，还要在每次成员变更后重算集群版本。这些分支就是增加的复杂度。

换来的是可回滚的混合窗口：两台升到 v2 之后，集群仍按 v1 运行，0.75 的 hotfix 仍是旧格式，随后可以在 1.10 把两台都降回去，爆炸半径停在「尚未启用新格式」这一侧。若没有这层兼容，第一次把新二进制加入集群就可能写出旧节点读不懂或误读的记录，一次滚动就会把错误标题扩散出去。指南用最低共同版本和「新特性等全部升级后再开放」来收紧同一半径；本课的开关和矩阵是它的教学对照，不是一份更短的升级脚本。

自测题

题 1. 为什么旧版本不能误读新记录？请用兼容矩阵里 v2 记录碰到 v1 读取方的那一格，说明拒绝和「直接取 value」有什么不同。

答案 误读指的是旧二进制把一条它并不理解的记录当成合法标题用掉。矩阵的前四格都是合法路径：v1 写 v1、v2 读 v1、开关关闭时 v2 二进制仍写 v1，以及开关打开后 v2 读写 v2，读到的都是 `Weekly digest (revised)`。真正要防的是第五格。 集群已经是 v2 之后，`n1` 写出格式 v2 的 `Weekly digest (hotfix)`，`n1` 和 `n2` 应用成功，仍为 v1 的 `n3` 返回 `unsupported_format`，标题留在原来的 `Weekly digest (revised)`，完成于 `0.60`。它没有把 hotfix 写进自己的存储。若忽略 `fmt`、直接取 `value`，不安全的解码会得到 hotfix，看起来像是一次成功的读取，实际上是把旧进程不能理解的字段当成了标题。验收要求的「旧版本不会误读新记录」，指的就是拒绝这条路径，而不是猜一个值。 这格能出现，前提往往是集群版本已经抬升，或有人绕过开关。兼容窗口里，开关关闭时根本不会写出 v2，旧节点也就不会走到这一格。

题 2. 为日志格式 v1/v2 做完兼容矩阵之后，半数升级再回滚，集群版本和写出格式会怎样变？为什么这时可以回滚？

答案 先拍快照：`t=0.05`，标题是 `Weekly digest`，校验和 `efe1be83bdea6938`。`0.15` 写入 revised，格式 v1。然后只升两台：`n1` 在 `0.35` 协商结束，`n2` 在 `0.65` 协商结束，状态都是 `mixed`，集群版本仍是 v1，特性开关为假。随后 `0.70` 到 `0.75` 写入 `Weekly digest (hotfix)`，格式仍是 v1，三个节点都应用成功，包括尚未升级的 `n3`。 这时可以回滚，是因为集群版本还没有抬升，日志里也没有 v2 记录。`0.80` 起把 `n2`、`n1` 依次降回 v1，`0.95` 时状态仍是 `mixed`，`1.10` 回到 `all_v1`。`1.15` 从 `n3` 读到的还是格式 v1 的 hotfix。指南把这一阶段写成：只要仍有一名成员停留在旧版本，集群就仍按旧协议运行，可以把全部成员退回旧二进制。本课的半数升级对应的就是这个窗口，而不是已经完成的升级。

题 3. 全体升级之后为什么不能再换回旧二进制？不可逆迁移后的恢复策略是什么？若只在全量新集群上做测试，会漏掉什么？

答案 最后一名成员升级时，集群版本会被抬起来。对照路径里，`n3` 在 `0.65` 完成协商后，集群版本变成 v2，开关打开，状态成为 `all_v2`。`0.70` 写出格式 v2 的 hotfix。此后在 `0.80` 尝试把 `n1` 降回 v1，结果是 `ok=false`，原因 `cluster_already_v2_and_log_has_v2_records`。指南的原话是：全部成员升到新版本后，集群将升到新版本，从这一完成状态降级是不可能的。 恢复策略在拒绝记录里写明为 `restore_from_pre_upgrade_snapshot`。按 `0.05` 拍摄、校验和为 `efe1be83bdea6938` 的快照恢复，`0.95` 结束时标题回到 `Weekly digest`，集群版本回到 v1，三台都是 v1 二进制。恢复不会保留后来的 revised 和 hotfix，因为它回到的是拍摄点。这就是「明确不可逆迁移后的恢复策略」：退路是升级前的快照，不是换回旧二进制。 若只在全量新集群上测试，三台都是 v2 时写入 revised 会在 `0.55` 成功，格式为 v2，看起来没有问题。同一条 v2 写入碰到仍为 v1 的 `n3` 时，才会出现 `unsupported_format`。只测全量新版本，既看不到混合窗口，也看不到回滚在何时失效。

本课小结

  • 升级期间新旧节点、持久化格式和消息模式会同时存在，需要兼容窗口和可回滚边界，以免滚动升级破坏集群安全。
  • 读写兼容要写成矩阵。新二进制能读 v1；开关关闭时 v2 二进制仍写 v1；开关打开后 v2 读写带 editor=desk 的 v2 记录。v1 碰到 v2 记录必须拒绝：n3 在 0.60 以 unsupported_format 留下 revised，而不会把 hotfix 误读进来。
  • 特性开关跟的是集群版本，不是某一台机器的二进制。半数升级在 0.35 和 0.65 之后集群仍为 v1，0.75 的 hotfix 仍是格式 v1，三个节点都能应用。
  • mixed 可以回滚：1.10 回到 all_v1，1.15 读到 hotfix。一旦 0.65 把集群抬到 v2，0.80 的二进制回降会被拒绝；不可逆之后只能从 0.05 的快照恢复，0.95 标题回到 Weekly digest，校验和 efe1be83bdea6938。
  • 不要只测试全量新版本集群。全部为 v2 时读写可以在 0.55 通过，却测不到旧节点拒绝新记录、也测不到回滚窗口。兼容代码增加了分支，但把爆炸半径留在集群版本抬升之前。
  • 这些是教学虚拟时钟上的数字，不是生产 RTT。EvolutionEngine 不是 Redis，也不是 etcd。指南不定义 feature gate 或 v1/v2 教学格式；本课用它们落实最低共同协议、特性开关和 snapshot 退路。并不是所有格式变化都有滚动窗口。

如果有一句答不上来，先回到 results.json 里对应的字段，再回到指南里「按最低共同版本运行」「新特性等全部升级后再开放」以及「集群版本抬升后只能靠事先保存的 snapshot 回退」这几段，不要把「已经有一半换成新二进制」当成「可以启用新格式」，也不要把「全量新集群测试通过」当成升级安全。
