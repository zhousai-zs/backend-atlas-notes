第 14/208 课：测试思维与问题分解

节点：a-testing · 域：A · 子类：基础工程认知 · 难度：入门 · 前置：a-compile

一句话：把需求拆成可观察的输入输出契约，用正常、边界和错误输入反复验证，而不是「跑通一次就算对」。

1. 学习目标与为什么后端要懂

1.1 学习目标

完成本课后，你应该能够：

  1. 解释输入输出契约：说清「合法输入长什么样、输出必须满足什么、非法输入如何失败」，而不是只描述「这段代码在干嘛」。
  2. 用边界值与等价类设计用例：不只测「看起来正常」的一条路径，还覆盖空值、超长、损坏等类别。
  3. 写出可重复、能缩小失败输入的测试：失败时能稳定复现，并把触发 bug 的输入压到尽量短。
  4. 独立完成节点实践：为字符串解析器设计合法、空值、超长和损坏输入案例；测试能发现植入的边界错误。
  5. 在微信公众号后台场景里，能把「回调参数、配置行、openid 校验」想成契约 + 用例，而不是靠手工点一次接口。

1.2 验收标准

节点给出的验收标准有两条，本课会反复回扣：

  • 能复现失败并缩小最小输入。 测试失败时不是「偶发红一下」，而是固定输入、固定断言；必要时把输入一点点裁短，定位到真正触发条件。
  • 测试能发现植入的边界错误。 实践里会故意留下一处「超长边界差一」的 bug；你的用例必须把它抓出来，而不是只测 happy path。

1.3 为什么微信公众号后台要懂测试思维

节点对「为什么」写得很干脆：让功能有明确完成定义，减少只凭运行一次判断正确。 放到即将入职的腾讯微信公众号后台，几乎每天都会碰到「字符串进来 → 解析 → 写库/回包」：

  • 服务器 URL 验证 / 事件回调。 echostr、签名、openid、事件类型都是字符串。只拿一条合法样例测通，生产上一个空 openid、超长 EventKey 或半截 XML 就可能 NPE、脏写或 500。
  • 配置与灰度开关。 运维或配置中心常给 key=value 行。缺 =、键超长、值含控制字符——若不先验契约，启动期静默吞错，线上行为难查。
  • 模板消息 / 客服消息字段。 用户昵称、跳转 URL、模板占位符都有长度与字符集边界。等价类想清楚，比「测一个中文昵称」稳得多。
  • 完成定义（Definition of Done）。 「解析配置行」完成 = 合法行出正确 dict、非法行抛约定异常、边界长度行为写死——而不是「我本地跑过一次」。

所以本课要建立的肌肉是：先写契约，再按等价类填用例，让失败可复现、可缩小；覆盖率只是辅助信号，不是正确性证明。

2. 从直觉到原理：三个核心要点

2.1 输入输出契约

直觉：快递面单

寄件人地址、收件人手机、重量上限——面单就是契约。司机不管「你心里想寄什么」，只按面单字段验收。程序也一样：调用方与被调用方先约定输入形状和输出承诺。

原理：契约 = 前置条件 + 后置条件 + 失败语义

对一个函数 parse_kv_line(line: str) -> dict，契约至少要写清：

维度 要约定什么 例子
前置（合法输入） 类型、编码、长度、格式 单行 UTF-8；恰好一个 =；key 为 [A-Za-z_][A-Za-z0-9_]{0,31}
后置（成功时） 返回值结构与不变量 {"key": ..., "value": ...}；value 长度 ≤ 256
失败语义 非法时抛什么、是否修改外部状态 ValueError 且消息分类；无副作用

GoogleTest Primer（见资源）强调的也是：断言描述「期望的可观察行为」，而不是「实现细节碰巧如此」。单元测试里的 EXPECT_* / ASSERT_* 就是在检查契约条款。

例子：公众号配置行

合法：  reply_timeout_ms=3000
非法：  =3000          （空 key）
非法：  reply_timeout_ms  （缺 =）
非法：  k=<257 个 a>   （value 超长）

契约写清后，「完成」才可判定：合法样例全绿，非法样例全按约定失败。

2.2 边界值与等价类

直觉：安检不是穷举每个人

不能测「世界上所有字符串」。把输入空间划成几类，每类抽代表；边界（刚好合法 / 刚好非法）最容易藏 off-by-one。

原理：等价类划分 + 边界加强

对 value 最大长度 256：

等价类 代表输入 期望
正常非空 name=alice 成功
空 value name= 按契约：允许或拒绝（本课允许空 value）
空整行 / 空白 ""、" " ValueError
超长 value 257 个字符 ValueError
边界合法 恰好 256 成功
损坏格式 无 =、多个 =、非法 key 字符 ValueError

边界值：长度 0、1、max、max+1；首尾字符；刚好缺字段。微信后台里 openid 常见 28 字符——测 0、28、29、含空格，比只测一条真实 openid 有用。

例子：四类实践输入（对应节点 practice）

  1. 合法：app_id=wx123、flag=1
  2. 空值：""、"\n"、只有空格
  3. 超长：key 33 字符、value 257 字符
  4. 损坏：no_eq、=onlyvalue、bad-key=1（含连字符）、a=b=c

2.3 可重复测试与失败定位

直觉：故障单要「步骤可复现」

「刚才红了一下」没法修。测试必须：固定输入 → 固定断言 → 任意机器同结果。失败后优先缩小输入（delta debugging 思想）：删字符直到再删就不失败——那就是最小触发器。

原理：确定性 + 隔离 + 最小复现

  • 可重复：不依赖当前时间、随机数、未 mock 的网络、执行顺序。
  • 失败定位：断言消息写清期望与实际；一个用例测一个行为，避免「大红一片不知哪条契约破了」。
  • 缩小输入：若 key=<200 个 x>=y 失败，试更短 key，直到最短仍失败的串——常能直接指向「长度判断用了 < 而不是 <=」。

例子：Linux 下快速复现

cd /workspace/atlas/lessons/practice14
python3 -m pytest parse_kv_test.py -q    # 或直接 python3 parse_kv_test.py
# 单条复现
python3 -c "from parse_kv import parse_kv_line; parse_kv_line('a=' + 'x'*257)"

3. 常见误区与设计权衡

3.1 误区：覆盖率不是正确性的充分证明

节点 pitfalls：覆盖率不是正确性的充分证明。

行覆盖 100% 仍可能漏掉「value 长度上界」。分支走过去了，不代表边界值断言对了。覆盖率是「有没有测到这行」的信号，不是「行为符合契约」的证明。优先补能证伪的边界用例，而不是为了百分比去测 getter。

3.2 权衡：单元测试 vs 系统测试

节点 tradeoffs：单元测试快且定位清楚，系统测试验证真实组合行为。

单元测试 系统 / 集成测试
速度 毫秒级，可大量跑 慢，依赖进程/网络/DB
定位 直接指向函数契约 失败链路长
覆盖 边界、错误注入容易 真实组合、配置、部署差异

公众号后台建议：解析、签名校验、状态机用单元测试钉死契约；回调 HTTP → 业务 → 回包用少量系统测试防组装错误。两者互补，不是二选一。

4. 动手实践：字符串解析器的四类用例

节点实践原文：为字符串解析器设计合法、空值、超长和损坏输入案例。

本课落地一个 parse_kv_line：解析单行 key=value（公众号配置 / 简单查询串的缩影）。

4.1 契约（写进代码前先冻结）

  • 合法：恰好一个 =；key 匹配 ^[A-Za-z_][A-Za-z0-9_]{0,31}$（1～32 字符）；value 为不含 \n/\r 的字符串，长度 0～256。
  • 成功返回：{"key": key, "value": value}。
  • 非法：抛 ValueError（空行、缺 =、多 =、非法 key、超长等）。

4.2 植入的边界错误（供测试发现）

目录里有两份实现：

  • parse_kv.py：正确实现（value 上限 256）。
  • parse_kv_buggy.py：故意把上限写成 257，会错误接受长度为 257 的 value。

parse_kv_test.py 对正确实现跑全套合法/空值/超长/损坏用例，并检查 buggy 版是否「错误地接受 257」——若接受，打印 PLANTED_BUG_DETECTED，即满足验收「测试能发现植入的边界错误」。你可以自己把 buggy 的 _MAX_VALUE 改回 256，再观察这条检测如何从「发现 bug」变成「buggy 行为消失」。

4.3 可执行步骤

cd /workspace/atlas/lessons/practice14
python3 parse_kv_test.py

期望：正确实现对全部合法/空值/超长/损坏用例通过；针对 buggy 实现的检查报告「已发现边界错误」。

4.4 缩小失败输入（验收点练习）

若某次你改坏了 key 正则，用二分/逐字删除找到最短失败串，例如从 app_id=1 改到 a=1 仍失败 → 问题在「单字符 key」规则，而不是 value。

5. 自测题（附答案）

Q1. 什么是「输入输出契约」？举一个公众号回调相关的例子。

答案 契约是对函数/接口前置条件、成功后置条件与失败语义的明确约定。例如验证 URL：输入须含 `signature/timestamp/nonce/echostr`；签名校验通过则原样返回 `echostr`；失败返回 401 或空——而不是「好像能通」。

Q2. 为何「覆盖率 100%」仍可能漏掉超长 value 的 bug？

答案 覆盖率只说明某行/分支执行过，不说明用了临界输入。若测试 value 长度只有 3，检查 `len(value) <= 256` 的那一行虽被执行，错误的 `<= 257` 或 `< 256` 仍不会被揭穿。必须有 max 与 max+1 的边界用例。

Q3. 单元测试与系统测试如何分工？节点的权衡结论是什么？

答案 单元测试快、定位清，适合钉死解析与纯逻辑契约；系统测试验证真实组合（HTTP、DB、配置）。节点原文：单元测试快且定位清楚，系统测试验证真实组合行为——两者互补。

7. 小结

  • 契约先行：合法输入、成功输出、失败方式写清，功能才有完成定义。
  • 等价类 + 边界：合法 / 空值 / 超长 / 损坏四类是字符串入口的基本盘。
  • 可复现 + 可缩小：失败输入要稳定、能压到最小。
  • 覆盖率≠正确性；单元与系统测试分工合作。
