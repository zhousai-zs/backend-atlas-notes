第 12/208 课：网络分层、地址与路由

节点：a-network · 域：A · 子类：基础工程认知 · 难度：入门 · 前置：a-os

一句话：网络协议分层把应用消息逐层封装，IP负责寻址转发，传输层提供端到端通信语义。

1. 学习目标与为什么后端要懂

1.1 学习目标

完成本课后，你应该能够：

  1. 解释链路、IP 与传输层：说清「帧 / 包 / 段」大致落在哪一层，各自解决什么问题。
  2. 说清 IPv4/IPv6 与子网：地址长什么样、前缀（CIDR）如何划网段、主机位与网络位怎么分。
  3. 理解路由、MTU 与分片：包怎么被转发到下一跳；为什么应用消息大小可以远大于链路 MTU。
  4. 独立完成实践：追踪一次 HTTP 请求，记录 DNS 结果、本机路由提示，以及 TCP 端口与连接两端。
  5. 在微信公众号后台场景里，能把「域名 / IP / 端口 / 应用协议」拆开排障，而不是只会说「网络不行」。

1.2 验收标准

节点给出的验收标准有两条，本课会反复回扣：

  • 能解释 MAC 地址与 IP 的作用范围。 MAC 是链路层、同广播域/同链路上的硬件（或虚拟）地址；跨过路由器后，下一跳的 MAC 会变，端到端通信不靠「目的主机的 MAC 一路不变」。IP 是网络层标识，用于跨网寻址与路由转发（有 NAT 时语义会变复杂，但排障仍先问：这是域名问题、IP 可达问题，还是端口/应用协议问题）。
  • 能说明 MTU 与应用消息大小不同。 MTU 约束的是「这一跳链路上，一个 IP 包大概能装多大」；你的 JSON、素材文件、模板消息体可以是几十 KB 甚至更大——靠 TCP 分段（或偶发的 IP 分片）切开传输。把「接口 MTU=1500」理解成「HTTP body 不能超过 1500」是错的。

1.3 为什么微信公众号后台要懂网络分层

节点对「为什么」写得很干脆：能够区分域名、IP、端口和应用协议的故障。 放到即将入职的腾讯微信公众号后台，几乎每天都会碰到这类拆分：

  • 回调 URL。 用户消息推到你的公网域名 → DNS 解析到负载均衡 / 机器 IP → 落到 443（或内网端口）→ 应用层是微信约定的 HTTP(S) 验签与 XML/JSON。挂了要先问：域名解析错了？IP 不通？端口没开？还是 HTTP 状态码/验签失败？
  • access_token 拉取。 你的服务访问微信开放平台域名：又是 DNS → 出网路由 / 代理 → TCP 443 → HTTPS + 业务 JSON。超时可能是 DNS、路由 ACL、TLS，或对端限流——分层才能缩小范围。
  • 素材 CDN。 图片/音频上传后，粉丝侧往往走 CDN 域名。你要分清「源站 IP」「CDN 边缘节点」「客户端到边缘的路径」；MAC 只在每一跳本地有意义。
  • 模板消息下发。 你的后台连微信网关：端口、TLS、HTTP 路径、业务 errcode 是不同层的故障信号。不会分层，就会在日志里把「连接被 RST」和「errcode=40001」混成一句话。

所以本课要建立的排障肌肉是：先定层，再定对象（域名 / IP / 端口 / 应用协议），最后才猜业务。

2. 从直觉到原理：三个核心要点

2.1 链路、IP 与传输层

直觉：寄快递的三张标签

把一次「公众号服务器把模板消息发到微信网关」想成寄快递：

  1. 应用层：信纸上写的是 JSON——业务内容（touser、template_id、data）。
  2. 传输层（常见 TCP）：保证「这封信」在两端进程之间按序、可靠地送达；两端用 端口 区分「哪一个进程/服务」在收（例如 443）。
  3. 网络层（IP）：信封上的「城市门牌」——跨很多路由器也能找到目的主机（或 NAT 后的下一跳目标）。
  4. 链路层：每一段公路上的「当前这辆车要开进哪个车道/对接哪台交换机」——用 MAC 在本链路内投递；到下一个路由器，会换一辆车、换一张本地标签。

分层的核心收益：上面的层不用关心下面怎么换「本地标签」；下面的层不用解析业务 JSON。

原理：封装与解封装

发送端大致是「自上而下封装」：

应用数据 (HTTP body / 业务 JSON)
  → 加上传输头（TCP：源端口、目的端口、序号…）      → 段 (segment)
  → 加上 IP 头（源 IP、目的 IP、协议号…）            → 包 (packet)
  → 加上链路头（源 MAC、目的 MAC…）                  → 帧 (frame)

接收端反过来逐层剥头。你在 curl -v 里看到的是应用层对话；ss -ti / Wireshark 才能同时看到传输与 IP；同网段抓包才能直接看到以太网头里的 MAC。

端口在哪一层？ 端口是传输层的概念：同一台机器上的 IP 只能说明「哪台主机」，端口才说明「哪个套接字/服务」。微信回调打到 https://api.example.com/wx/callback，对系统而言首先是：解析域名得到 IP，再对 IP:443 建 TCP，再在 TLS 之上发 HTTP。

短命令：看见端口与连接

# 本机谁在听 443 / 80（需按实际环境调整）
ss -lntp | head
# 或
ss -ltn

# 看本机到某主机的 TCP 连接（示例）
ss -tn | head

# 一次带细节的 HTTPS 请求（会打印 DNS、连接、TLS、HTTP 头）
curl -v --max-time 10 https://httpbin.org/get -o /dev/null

在 curl -v 输出里，试着标出：解析到的 IP、connect 到的端口、HTTP 状态行——这三项分别贴近「IP / 传输 / 应用」。

微信公众号例子

粉丝发消息 → 微信服务器 POST 你的回调：

你看到的现象 更可能卡在哪一层
域名都 ping/解析不到 DNS 或根本无网（偏「名字→IP」与连通）
解析到了 IP，TCP 超时 路由、防火墙、安全组、端口未监听
TCP 通了，TLS 握手失败 证书、SNI、中间盒（仍偏传输之上、应用之下）
HTTP 200 但业务验签失败 应用协议 / 业务逻辑

验收回扣（MAC vs IP）： 回调路径上每一跳交换机/路由器改写的是「本段的 MAC」；你的公网 IP（或 LB IP）才是跨网转发要盯的标识。不要指望「抓到微信源站 MAC」来做公网排障——你通常根本不在同一链路。

2.2 IPv4/IPv6 和子网

直觉：门牌号与小区围墙

  • IPv4：大约 A.B.C.D，32 位，常写成点分十进制。公网地址紧缺，所以到处是 NAT。
  • IPv6：128 位，写成冒号十六进制；地址空间大，设计上减少「全家共用一个公网 IP」的压力（现实部署仍因环境而异）。
  • 子网 / 前缀：用 CIDR 如 192.168.1.0/24 表示「前 24 位是网络号，后 8 位是主机号」——相当于小区围墙：墙内二层广播/邻居发现更近，出墙必须走网关（路由）。

原理：前缀长度决定「谁算邻居」

对 IPv4：

  • /32：只有一个地址（常常是「主机路由」）。
  • /24：256 个地址（可用主机数要去掉网络号/广播等细节，入门先建立「前缀越长，子网越小」的直觉）。
  • /16：更大网段。

判断「两个 IP 是否同子网」：看在给定前缀长度下，网络前缀是否相同。同子网 → 往往直接链路投递（ARP/ND 解析 MAC）；不同子网 → 交给默认网关或更具体的路由条目。

IPv6 常见前缀如 /64 作为局域网默认划分（细节留给后续课，本课抓住「前缀 = 子网边界」）。

短命令与短代码

# 看本机地址与前缀（Linux）
ip -br addr
ip route

import ipaddress

net = ipaddress.ip_network("10.0.0.0/24")
print(net.network_address, net.broadcast_address, net.num_addresses)
print(ipaddress.ip_address("10.0.0.50") in net)   # True
print(ipaddress.ip_address("10.0.1.50") in net)   # False

微信公众号例子

  • 开发机在公司 10.x 网段，微信回调却要求公网可达：你要分清 内网 IP 与 公网入口 IP（LB/NAT），别把内网地址配进公众号后台的 URL。
  • 容器/云主机安全组放行的是「某网段到某端口」——本质是基于 IP 前缀 + 端口的策略；不会写 MAC 白名单做公网回调。

2.3 路由、MTU 与分片

直觉：下一跳，而不是「一步飞到终点」

路由不是魔法：每台路由器只决定 下一跳是谁。你的包可能经过：本机 → 网关 → 运营商 → … → 对端机房。traceroute / mtr 看的是路径上的线索（ICMP 相关，可能被过滤，结果要会读也要会怀疑）。

MTU（Maximum Transmission Unit）：这一跳链路愿意承载的最大帧/包相关上限。以太网常见 IP MTU 1500 字节量级。你的素材文件 2MB，不可能也不需要「一个 IP 包打完」——通常由 TCP 把字节流切成多个段，每个段再装进合适大小的 IP 包。

分片： 若某跳 MTU 更小且包不可分片（IPv4 DF 位、或 IPv6 本就强调端到端避免中间分片），可能触发 Path MTU Discovery；配置不当会出现「小包通、大包挂」的经典故障。

原理：应用消息大小 ≠ MTU

概念 大致含义 典型数量级
应用消息 一次业务含义完整的数据（一份 JSON、一张图） KB～MB+
TCP 段 传输层一次提交给 IP 的一块 受拥塞窗口、MSS 等约束
IP 包 网络层转发单位 常受路径 MTU 约束（如 ~1500）
链路帧 本跳介质上的封装 MTU 直接相关

验收回扣（MTU vs 应用消息）： 接口 mtu 1500 不阻止你 POST 20KB 的模板消息；它只约束「每个 IP 包在这条链路上别太大」。应用层可以很大，下面自动切。

短命令

# 本机路由表
ip route

# 问内核：去某个 IP 准备怎么走（示例 IP 换成你 DNS 得到的）
ip route get 1.1.1.1

# 路径线索（可能被中间设备限速/过滤）
traceroute -n -w 2 -q 1 1.1.1.1 | head
# 或
mtr -rwzbc 10 1.1.1.1

# 看网卡 MTU
ip link | sed -n '1,20p'

微信公众号例子

  • 上传大素材失败、但 ping 通：可能是代理缓冲、超时、或 Path MTU 问题，而不是「公网 IP 写错」这一种原因。
  • 内网机器经 HTTP 代理出网：路由表仍指向网关，但 应用层 被指到代理；排障时别只看 ip route，也要看环境变量与客户端代理配置——这正是节点 tradeoffs 说的：分层便于组合，但排障要沿完整路径定位。

3. 常见误区与设计权衡

3.1 误区：TCP/IP 分层模型不必机械对应 OSI 每一层

节点 pitfalls：TCP/IP 分层模型不必机械对应 OSI 每一层。

考试题喜欢把「会话层、表示层」背得很细；工程排障里更常用的是 大致四层心智模型（链路 / 网络 / 传输 / 应用），并把 TLS、HTTP、DNS、RPC 框架放回「偏应用或应用辅助」的位置。不要因为对不上 OSI 第七层的某个名字，就不敢判断「这是端口问题还是 JSON 问题」。

实践建议：

  • 能画：DNS → IP → TCP/UDP 端口 → TLS? → HTTP/RPC。
  • 不必强行：每个库调用对应 OSI 某一层编号。

3.2 权衡：分层便于组合，但排障需沿完整路径定位

节点 tradeoffs：分层便于组合，但排障需沿完整路径定位。

分层的好处：换网卡驱动不用改业务 JSON；换域名不用改 TCP 状态机。坏处是：故障会在层与层之间「折射」。

完整路径清单（公众号回调一例）：

  1. 公众号后台配置的 URL 字符串是否正确（应用配置）
  2. DNS 是否解析到你期望的入口
  3. 公网到 LB/机器的路由与安全组
  4. 端口是否在听、TLS 证书是否匹配
  5. HTTP 路径、验签、业务逻辑

只盯着一层，会误判。分层是设计工具，也是排障地图——地图要整张用。

4. 动手实践：追踪一次 HTTP 请求

实践目标（节点原文）：追踪一次 HTTP 请求，记录 DNS 结果、路由及端口。

本课在仓库里准备了脚本：/workspace/atlas/practice12/trace_http.py。它会：

  1. 打印目标 URL / 域名 / 约定端口
  2. 用 DNS（getaddrinfo）列出 IP
  3. 调用 ip route get <ip> 给出本机转发提示
  4. 对 IP:443（或 80）做一次 TCP connect，打印本地端口与对端
  5. 发起 HTTP(S) GET，打印状态码与少量响应头
  6. 打印验收口述提示（MAC vs IP、MTU vs 应用消息）

步骤 1：进入目录并查看脚本

cd /workspace/atlas/practice12
sed -n '1,40p' trace_http.py

步骤 2：跑通默认追踪

python3 trace_http.py httpbin.org /get --scheme https

期望：

  • DNS 至少打出一条 IPv4 或 IPv6
  • 路由提示含 via / dev / src 之一（环境缺 ip 命令时会打印跳过原因，仍算可解释）
  • TCP connect 为 OK，并看到 本地端口（临时端口）与 对端 443
  • HTTP status 为 200（依赖外网；若环境无网，把失败点记录在「哪一步」——正是分层练习）

  2. Trying ...:443 / Connected
  3. HTTP 状态行

与脚本第 2、4、5 步对照，确认你能独立口述同一条路径。

  • [ ] 能说明：MAC 作用范围在链路/邻接，IP 用于跨网寻址与路由
  • [ ] 能说明：MTU 限制单包大小，不限制应用消息可以很大

5. 自测题（3 道，附答案）

题 1：MAC 与 IP 的作用范围

题： 粉丝消息经微信服务器 POST 到你的公网回调 https://wx.example.com/cb。有人说：「把微信服务器的 MAC 地址加白名单就能防伪。」这对吗？请用作用范围反驳或限定。

答案：

  • 不对（至少对公网场景基本不可行/无意义）。MAC 只在同一链路/广播域有意义；跨过路由器后，帧的源/目的 MAC 变成「本跳」的地址，你在机房网卡上看到的源 MAC 是上一跳设备，不是「微信源站主机的 MAC 一路漂过来」。
  • 防伪应靠 TLS、验签 Token/签名、IP 允许列表（若微信公布出口网段） 等网络层/应用层手段。
  • 回扣验收：能解释 MAC 地址与 IP 的作用范围。

题 2：MTU 与应用消息大小

题： 网卡 mtu 1500。产品经理要发 80KB 的图文 JSON 给内部渲染服务。有人说必须先把 JSON 拆成 ≤1500 字节的多次 HTTP 请求。是否必须？正确理解是什么？

答案：

  • 不是必须。 MTU 约束的是链路/IP 包大小；HTTP 请求体可以是 80KB，由 TCP 分段（以及路径上的包大小选择）完成。
  • 你要担心的是超时、网关 body limit、内存，而不是「MTU=1500 ⇒ HTTP body≤1500」。
  • 回扣验收：能说明 MTU 与应用消息大小不同。

题 3：分层排障

题： 模板消息发送客户端日志依次为：DNS 正常；connect 到 IP:443 超时；从未出现 HTTP 状态码。故障更可能卡在哪一层？下一步查什么？若换成「TCP 通但 HTTP 返回 401/业务 errcode」，判断如何变？

答案：

  • 前者卡在 传输连通或更下层路径（路由、安全组、端口未听、中间防火墙），还没到应用协议语义。下一步：ip route get、安全组、对端 ss -lntp、换路径/代理对比。
  • 后者说明 传输已通，问题在 应用层鉴权/业务（token、权限、参数）。
  • 这正是 why：区分域名、IP、端口和应用协议的故障；也回扣 tradeoffs——要沿完整路径定位。

7. 小结与前后置关系

7.1 本课要点回顾

  1. 分层封装：应用消息被传输层、IP、链路层逐层加上头部；排障先定层。
  2. IP 与子网：地址 + 前缀决定「邻居还是走网关」；IPv4/IPv6 是同一思想的不同宽度。
  3. 路由 / MTU / 分片：转发看下一跳；MTU 管单包，不管「业务消息能不能大于 1500」。
  4. 误区与权衡：不必机械抠 OSI；分层好组合，排障要走完整路径。
  5. 实践：对一次 HTTP 请求记下 DNS、路由提示、端口与 HTTP 结果。

7.2 验收回扣

  • MAC vs IP： 自测题 1 + 实践步骤 4/5。
  • MTU vs 应用消息： 自测题 2 + 实践口述提示。

7.3 前后置

  • 前置： a-os（进程、系统调用、本机环境——否则端口监听与网卡命令会很飘）。

域名、IP、端口、应用协议是四件不同的事；MAC 管本跳，MTU 管单包，别用它们去限制你对业务消息的想象。
