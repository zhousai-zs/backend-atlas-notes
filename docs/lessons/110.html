摘要 分片把键空间划到多个实例，路由、迁移和热点控制比简单取模更决定系统可演进性。

边界说明：本课中的「内容后台」「文章标题」「阅读计数」「爆款 Weekly digest」都是教学假设，用来让分片、迁移和热点变得可观察，不代表腾讯/微信或任何企业的内部实现。配套代码是 Python 3 标准库写的教学引擎，模块包括 ConsistentHashRouter / ModuloRouter / RangeRouter / HashSlotCluster / ClusterClient（统称 ShardingEngine），不是 Redis，不是 redis-py，也不是网络服务。它没有 TCP 协议、cluster bus、gossip、CLUSTER 命令解析器，也没有槽位所有权的集群传播。一致性哈希环用 MD5 放置虚拟节点，这不是 Redis Cluster 的路由方式——Redis Cluster 用的是 16384 个哈希槽，公式是 HASH_SLOT = CRC16(key) mod 16384（实现里是 CRC16 & 0x3FFF），不是 Ketama / 一致性哈希环。教学 MIGRATE 是进程内字典搬迁，不是 Redis 的 TCP MIGRATE 命令。官方文档已于 2026-11-12 用 curl 核对（见下文）。文中的官方机制只写到核对过的页面和源码能够支撑的范围；教学实验里的迁移条数、比例、槽位和标题都来自 /workspace/atlas/lessons/practice110/results.json，不是生产 Redis 的基准数字。

导读

一个直觉：分片不是「把数据切开」，而是「给每个键一个可解释的归属，并准备它在节点变化时搬家」

内容后台的一篇文章至少有两类数据：标题和阅读计数。单机 KV 还能装下时，所有键都在一个实例上；容量或吞吐逼近上限时，就要把键分到多个实例。最直接的做法是 hash(key) % N：键算出哈希，对节点数取模，落在哪个余数就去哪个实例。3 个节点时它工作得很好，加到第 4 个节点时问题立刻出现：同一个键对 4 取模的结果和原来对 3 取模的结果大多不同，于是大量键要换位置。换位置本身不是灾难，灾难是「换位置」和「数据已经搬过去」被混为一谈。

节点把这条机制概括为：分片把键空间划到多个实例，路由、迁移和热点控制比简单取模更决定系统可演进性。这里要同时看三件事。第一，路由规则决定一个键平时去哪个实例；第二，重分布机制决定加节点、删节点时哪些键要搬、怎么搬、搬的过程中读写怎么处理；第三，访问分布决定即使键分得很均匀，会不会有一个键或一段键把某个实例打爆。三件事分别对应本课的三条主线，不能用「哈希看起来很随机」一把带过。

接上前置

g-kv 给了单机键值存储的基本读写模型：键定位、值存取、容量与吞吐的边界。g-replication 讲的是同一份数据在多个节点上的副本、确认和故障切换；分片与复制是正交的两件事——复制解决「同一份数据有几份」，分片解决「不同键由谁来服务」。一个键可以在一个分片里有多个副本，也可以只有一个副本；分片数量增加不等于副本数量增加。

f-discovery 讲的是服务实例的发现与成员变化。分片系统必须知道「当前有哪些节点」「哪个节点负责哪段键空间」；节点加入、离开、故障都会改变这张表。本课不展开服务发现协议，只把「节点成员变化会触发路由变化」当作前提。

因此本课要补的不是「再讲一遍哈希」，而是三个新边界：取模为什么在节点数变化时代价大；一致性哈希和虚拟节点改变了哪一部分；槽位所有权和迁移协议如何把「搬家」拆成可观察的读写阶段。

教学场景（教学假设）

教学数据主要是 10000 个文章标题键：article:00000:title 到 article:09999:title。默认 3 个教学节点 n1 / n2 / n3，某些实验再加一个空节点 n4。另有一篇爆款文章 article:00042:title，值 Weekly digest，用来观察「键分布均匀但访问量不均匀」。阅读计数的键是 article:NNNNN:views，多键操作实验里会把它和标题放在一起。槽位实验使用与规范 CLUSTER SLOTS 示例同一组分界：n1 负责 0–5460，n2 负责 5461–10922，n3 负责 10923–16383。

这些都是教学假设。真实内容后台还会有审核状态、版本号、缓存层、冷热分离和跨地域部署；本课只保留能观察「路由、迁移、热点」的最小字段。

本课三条主线

  1. 哈希与范围分片：取模、一致性哈希、连续范围各自把键空间切成什么形状；范围扫描和「新文章都是大 id」分别偏爱哪一种。
  2. 虚拟节点和迁移：虚拟节点如何改善键在节点间的均衡；加删节点时哪些键要动；槽位所有权、MIGRATING / IMPORTING、ASK / MOVED 如何定义迁移期间的读写。
  3. 热点拆分与跨分片操作：均匀的键分布为什么不等于均匀的访问量；热 key 拆分能做什么、不能做什么；hash tag 如何把多键放进同一槽，以及迁移中为什么会遇到 TRYAGAIN。

学习目标

  • 能解释哈希分片与范围分片：取模在节点数变化时为什么迁移比例高，一致性哈希为什么只重映射一部分键，范围分片为什么利于扫描但容易被连续 id 的写入打出热点；能说清 Redis Cluster 的 16384 槽与一致性哈希环不是同一种机制。
  • 能独立完成：实现一致性哈希路由，模拟增删节点并统计迁移比例与热点分布；能说明迁移期间源节点、目标节点和客户端各自遵循什么读写策略；能用实验数字证明「均匀键分布不等于均匀访问量」，并区分热 key 拆分、槽位迁移和副本提升。

为什么后端要懂

内容后台的标题和阅读计数不会永远装在一台机器上。发布量增长时，单机 KV 的容量先到上限；爆款文章出现时，单机吞吐先到上限。分片是最常见的扩展手段，但它的代价不在「写一个哈希函数」，而在节点变化时的数据搬迁和访问倾斜。如果路由只用 hash % N，从 3 个节点扩到 4 个节点，大部分键都会换归属；如果只改路由不搬数据，读请求会落到没有这份数据的节点上，写请求会在新旧两个位置各留一份。迁移期间客户端读到什么、写到哪里，必须有明确规则，否则「扩容」会变成一次数据事故。

热点是另一条独立的风险。10000 个标题键可以很均匀地分到 4 个节点，每个节点大约四分之一；但只要 10000 次读里有 9000 次打在同一篇爆款上，持有这个键的节点就会承担 92.34%（0.9234）的读流量。此时「键分布很均匀」是真的，「访问分布很均匀」是假的。后端工程师如果只看键数或哈希环的均衡度，就会在容量规划里漏掉最关键的变量。

多键操作还会把分片边界暴露给业务。标题和阅读计数如果落在不同槽，MSET 会返回 CROSSSLOT；用 hash tag 把它们放到同一槽后，迁移期间又可能出现 TRYAGAIN。这些错误不是实现瑕疵，而是分片系统在告诉客户端：跨分片的原子性和同分片的原子性不是一回事。

核心知识点

1. 哈希与范围分片

先看最朴素的哈希分片：node = hash(key) % N。它把键空间按哈希值对节点数取余切成 N 份，路由计算是 O(1)，实现也简单。3 个节点时，10000 个标题键大致分成三千多、三千多、三千多。问题是 N 从 3 变成 4 时，同一个键的余数几乎必然改变。教学实验 modulo_vs_consistent 里，3 个节点加 n4 后，取模路由搬走 7458 个键、留下 2542 个，migration_ratio=0.7458；被搬走的键分散到 n4 / n3 / n2 / n1 的数量分别是 2410 / 1650 / 1703 / 1695。也就是说，加一个节点会让约四分之三的键重新映射，而且旧节点之间也在互相搬。删掉 n4 时同样搬走 7458 个，比例还是 0.7458。

一致性哈希换了一种切法。它把节点（更准确地说，是节点的虚拟节点）放在一个哈希环上，键也哈希到环上，然后顺时针找第一个节点。加一个新节点时，只有落在新节点「接管区间」里的键需要改归属，其他键不动。教学实现用 MD5 把每个物理节点的 150 个虚拟节点放到环上；实验里 3 个节点加 n4，只搬走 2399 个、留下 7601 个，migration_ratio=0.2399，并且 moved_to 只有 n4，consistent_hash_moved_only_to_new_node=true。删掉 n4 时同样搬走 2399 个、比例 0.2399，迁回 n2 / n1 / n3 的数量是 890 / 786 / 723。

这组对照说明的是重映射范围，不是数据一致性。取模在 3→4 时约迁移 3/4，一致性哈希约迁移 1/4，而且一致性哈希只把键迁到新节点。这个结论成立的前提是环上的虚拟节点足够多、哈希分布足够均匀；虚拟节点数量不足时，环上的区间大小会很不均，迁移比例和负载都会偏。

范围分片按连续区间切键空间。例如按文章 id 把 0–2499 给 n1、2500–4999 给 n2、5000–7499 给 n3、7500–9999 给 n4。它的优点是范围查询只碰少数分片：扫描 2000–2199 这 200 个连续 id，范围分片只打到 n1 一个分片（range_shard_count=1）；同样这 200 个键走一致性哈希，会打到 n1 / n2 / n3 / n4 四个分片，计数是 53 / 46 / 49 / 52（hash_shard_count=4）。如果业务经常按 id 区间导出、批量审核或做时间范围扫描，范围分片能省掉大量跨分片请求。

但范围分片把「连续 id」的写入集中到同一个分片。实验 range_vs_hash_scan 里，5000 次写中有 4000 次落在 id 9800–9999 这段「新文章尾部」。范围分片下 n4 拿到 4000 次、n1 拿到另外 1000 次，n2 和 n3 都是 0，range_hot_share=0.8；一致性哈希下写量是 1134 / 1555 / 1275 / 1036，max_share=0.311。这不是说哈希一定更好，而是说：范围分片优化了扫描，代价是连续热点；哈希分片打散了尾部写入，代价是范围查询要 fan-out 到多个分片。

Redis Cluster 用的是第三种切法：固定 16384 个哈希槽，每个主节点负责一部分槽。规范给出的基本算法是 HASH_SLOT = CRC16(key) mod 16384，实现里用 CRC16 的低 14 位，也就是 crc16(...) & 0x3FFF。CRC16 的参数是 XMODEM（文档也写作 ZMODEM / CRC-16/ACORN）：Width 16，Poly 1021，Init 0000，输入输出都不反射，输出异或 0000，对 "123456789" 的输出是 31C3。教学引擎实测 CRC16("123456789")=12739=0x31C3，matches_spec_31C3=true，与规范附录一致。文档还写到，CRC16 在把不同种类的键均匀分到 16384 个槽上表现很好；建议集群规模大约最多 ~1000 个节点，上限是 16384 个主节点。稳定时一个槽由一个节点服务，可以有副本，副本在可接受陈旧的前提下可以分担只读。

这里必须把术语分开：Redis Cluster 是固定槽位所有权，不是一致性哈希环。规范里没有 Ketama，没有按节点做哈希环，也没有「虚拟节点」这个术语。16384 个槽提供了类似「一次只搬一部分键空间」的迁移粒度，但机制是槽的归属和搬迁，不是环上顺时针找节点。把 Redis Cluster 讲成一致性哈希，会导致后面读 CLUSTER SETSLOT、MOVED、ASK 时全部对不上。

Redis 还有一个让多键操作能落在同一槽的规则：hash tag。若键中有 {，且其右侧有 }，且两者之间至少有一个字符，则只哈希 { 与第一个 } 之间的子串；否则哈希整个键。教学实验给出的槽位是：{user1000}.following 与 {user1000}.followers 都只哈希 user1000，都在槽 3443；{article:00042}:title 与 {article:00042}:views 都哈希 article:00042，都在槽 9458；未加标签的 article:00042:title 哈希整个键，在槽 10587，和加标签的不同。边界例子也要按文档记：foo{}{bar} 中间没有字符，哈希整个键，payload 是 foo{}{bar}，槽 8363；foo{{bar}}zap 只取到第一个 }，payload 是 {bar，槽 4015；foo{bar}{zap} 只取第一个 { 到第一个 }，payload 是 bar，槽 5061；以 {} 开头（如 {}whole）同样哈希整个键。这些 payload 是教学 hash_tag_payload 的返回值，规则与规范一致。

文档还提到，Redis 8.0 起，含 hashtag 且满足条件的 glob 模式（KEYS/SCAN/SORT）可以只扫一个槽。本课实验没有实现这条优化，只作为文档阅读，不编造实验数字。

2. 虚拟节点和迁移

一致性哈希的第一个问题不是迁移，而是均衡。如果每个物理节点只在环上放 1 个点，节点之间的区间大小由哈希值决定，可能相差很大。实验 vnode_balance 用同样的 10000 个标题、3 个节点做对照：1 个虚拟节点时，n1 / n2 / n3 的键数是 1786 / 3257 / 4957，份额 0.1786 / 0.3257 / 0.4957，max_min_ratio=2.775475923852184，最大份额 0.4957；每个节点放 150 个虚拟节点后，键数变成 3215 / 3361 / 3424，份额 0.3215 / 0.3361 / 0.3424，max_min_ratio=1.0650077760497667，最大份额 0.3424。虚拟节点把每个物理节点切成许多小段散落在环上，键落到各段的概率更接近均等，于是节点间的键数更接近。

虚拟节点改善的是键的均匀程度，它们自己不会搬数据。加节点时仍然要迁移「新节点接管区间」里的键，只是这个区间由许多虚拟节点组成，大小更可控。把虚拟节点数量从 1 提到 150，不会自动把已有数据重新分布；它改变的是路由表，数据迁移仍然要单独执行。实验里 vnodes_do_not_move_data_by_themselves=true 就是提醒这一点。

迁移的核心问题是：在键从源节点搬到目标节点的过程中，客户端读写应该发生什么？ 教学实验先演示一个错误做法。naive_vs_protocol_migration 有 2000 个标题，槽位按 0–5460 / 5461–10922 / 10923–16383 分给 3 个节点，然后把槽 0–199 交给 n4。这 200 个槽里有 28 个键。天真做法是先把槽表改成 n4、不搬数据：28 次读全部 missing，reads_ok=0、missing_ratio=1.0；对 article:00014:title（槽 192）写入 Weekly digest (revised) 后，n1 仍是 Weekly digest，n4 是 Weekly digest (revised)，split_brain=true。客户端以为数据已经在 n4，实际上旧数据还在 n1，新写入又在 n4 造了第二份。

协议做法把迁移拆成可观察的阶段。官方规范里，增删节点、再均衡，本质都是把哈希槽从一个节点搬到另一个节点；搬槽就是搬这个槽里的键。相关子命令包括 CLUSTER ADDSLOTS / DELSLOTS / ADDSLOTSRANGE / DELSLOTSRANGE，以及 CLUSTER SETSLOT slot NODE / MIGRATING / IMPORTING。MIGRATING 表示源节点仍接受该槽的请求，但仅当键存在；键不存在时返回 -ASK，指向迁移目标。IMPORTING 表示目标节点只在请求前有 ASKING 时才接受该槽的请求，否则对真正的槽所有者返回 -MOVED。

规范给了槽 8 从 A 迁到 B 的例子：先对 B 发 CLUSTER SETSLOT 8 IMPORTING A，再对 A 发 CLUSTER SETSLOT 8 MIGRATING B。已有键仍由 A 处理，A 上不存在的键由 B 处理（A 会把客户端重定向到 B），因此不会再在 A 上创建新键。然后用 CLUSTER GETKEYSINSLOT 取出键，对 A 发 MIGRATE，原子地把键从 A 迁到 B（两端短暂加锁）；对外看来一个键在任意时刻只存在于 A 或 B。迁完后对相关节点发 SETSLOT NODE。文档提醒：大 key 在有延迟约束时不适合这样迁。

ASK 与 MOVED 的区别必须记清。MOVED 表示该槽此后由另一个节点永久服务，客户端应更新槽表；ASK 只把下一条查询发到指定节点，不要改槽表，因为同一槽里其他键可能还在源节点。客户端收到 ASK 后，先发 ASKING，再发被重定向的那条命令，并且后续查询仍先打到旧节点。ASKING 在目标节点上设置一次性标志，让 IMPORTING 槽的请求被接受。若错误的客户端过早把槽映射到 B 且没发 ASKING，B 会用 MOVED 把请求打回 A。教学 ClusterClient 就是按这个规则实现的：遇到 ask 只把这一次请求发到目标并带 asking=True，遇到 moved 才更新 slot_map。

回到实验 naive_vs_protocol_migration 的协议路径。迁移中 28 个已有键全部读成功，仍由 n1 服务（mid_migration_existing_ok=28、mid_migration_existing_total=28、mid_migration_served_by=["n1"]）。新键 article:new:133:title（槽 195）经 ASK 写到 n4，值为 Weekly digest (revised)，ask_count_after_new_write=1。迁完 28 个键并 finish 后，28 个旧键全部可读且由 n4 服务（after_finish_ok=28、after_finish_served_by=["n4"]），新键仍在。教学客户端在 after 阶段的 moved_count=20、ask_count=1：moved_count 是客户端收到 MOVED 后更新槽表时累计的重定向次数（按槽首次更新计数），不是 28 个旧键各算一次；ask_count=1 是先前新键走 ASK 的次数。读写策略可以压缩成一句话：迁移期间源节点服务已有键，源上没有的键 ASK 到目标，目标只在 ASKING 时服务，新键建在目标；迁完 SETSLOT NODE，客户端靠 MOVED 更新槽表。

Redis 式的「搬一部分槽」也能把迁移量控制住。实验 slot_add_node_migration_ratio 用 10000 个标题、3 节点上述槽范围，把每隔 4 个槽（共 4096 个槽）迁到 n4。迁前键数是 3333 / 3344 / 3323 / 0，迁后是 2503 / 2505 / 2492 / 2500；迁前槽数是 5461 / 5462 / 5461 / 0，迁后是 4095 / 4097 / 4096 / 4096。keys_moved=2500，key_migration_ratio=0.25，总和仍是 10000，没有丢键。这个结果说明：目标与一致性哈希相近（都约 1/4），但手段是槽所有权，不是哈希环。迁移量的可控性来自「只搬一部分槽」，不是来自「一致性哈希」这个名字。

3. 热点拆分与跨分片操作

均匀的键分布不等于均匀的访问量。实验 hotspot 用 4 个节点、每节点 150 个虚拟节点，把 10000 个标题键分到 n1 / n2 / n3 / n4，键数是 2429 / 2471 / 2701 / 2399，份额 0.2429 / 0.2471 / 0.2701 / 0.2399，max_share=0.2701，看起来相当均匀。但 10000 次读里有 9000 次打在爆款键 article:00042:title（Weekly digest）上，该键在 n2。访问量变成 234 / 9234 / 295 / 237，份额 0.0234 / 0.9234 / 0.0295 / 0.0237。n2 的键份额只有 0.2471，访问份额却是 0.9234，uniform_keys_are_not_uniform_access=true。

这就是分片系统里最容易被忽略的偏差：哈希只保证键在节点间大致均匀，不保证请求在节点间均匀。一个爆款键的全部读请求都会落到它所在的节点，虚拟节点再多也不会把这个键拆开。容量规划如果只看键数、磁盘占用或哈希环的均衡度，就会低估这个节点的 CPU、连接数和网络出口。

热 key 拆分的教学做法是把 article:00042:title 拆成 8 个分区键 article:00042:title#0 到 article:00042:title#7，按 user id 取模选分区。8 个分区分别落到 n3 / n2 / n1 / n3 / n4 / n2 / n4 / n4，四个节点都有分区。9000 次热读的访问量变成 1125 / 2250 / 2250 / 3375，份额 0.125 / 0.25 / 0.25 / 0.375，最大份额从 0.9234 降到 0.375。必须写明：这是教学上的热 key 拆分，不是 Redis Cluster 命令，也不是副本提升。 它把「一个键的读」变成「一组键的读」，分散的是访问压力，不是数据所有权；读取方要能根据 user id 选分区，写入方要维护多个分区的值，跨分区的聚合和一致性都要额外处理。如果业务不能接受「读到的分区值可能不同步」，热 key 拆分就不是免费的。

跨分片操作是另一条边界。多键操作要求所有键落在同一个槽，否则 Redis Cluster 返回 CROSSSLOT Keys in request don't hash to the same slot。教学实验 hashtag_and_tryagain 里，article:00001:title 与 article:00001:views 的槽位是 16052 与 8986，MSET 返回 crossslot。用 hash tag 后，{article:00001}:title 与 {article:00001}:views 都在槽 6229，MSET 成功，落在 n2。规范也给了同样的多键示例：MSET {user:1000}.name Angela {user:1000}.surname White，用 hash tag 把多个键放到同一槽。

同一槽也不代表迁移期间永远可用。实验继续：开始把槽 6229 迁往 n4，只迁走 title 后，再 MSET 两个键，得到 tryagain。原因是这两个键此时被拆在源和目标两边：title 在 n4，views 还在 n2 的源侧。规范对此的说明是：重分片进行中，若这些键都还在同一侧（源或目标）且都存在，多键操作仍可用；若键不存在，或在重分片期间被拆到源和目标两边，则返回 -TRYAGAIN。迁完后该槽的多键操作恢复。实验里两个键都迁到 n4 后，带 ASKING 的 MSET 成功，final_owner=n4。TRYAGAIN 的正确反应是重试，而不是把错误当成永久失败；但重试要有退避和上限，否则迁移窗口内会放大压力。

这里还有两个容易混淆的点。第一，hash tag 只解决「多键是否同槽」，不解决「这个槽是否过热」。把标题和计数放进 {article:00001} 只会让它们同槽，爆款文章的这个槽仍然可能被打爆。第二，跨分片操作不只是 MSET：跨槽事务、跨槽 Lua、跨槽范围查询都要么被拒绝，要么需要客户端自己聚合。范围分片的扫描优势在哈希分片里会变成 fan-out 成本，这是第 1 节已经量化过的权衡。

常见误区

「一致性哈希解决重分布，所以数据一致性问题也解决了。」 一致性哈希只减少加删节点时需要重映射的键数，它不搬值，也不决定哪份副本是新的。实验 consistent_hash_is_not_consistency 用 400 个标题、3 节点加 n4，migration_ratio=0.25（搬走 100，全部到 n4）；如果不搬值、只改路由，naive_reads_found=300，naive_reads_missing=100，100 个被重映射的键在新家都读不到。对 article:00001:title 在新家 n4 写入 Weekly digest (revised)，旧家 n2 仍是 Weekly digest，two_copies_diverge=true。一致性哈希只减少了要重映射的键数，不搬数据，也不决定哪份是新的。

「键分布均匀，访问就均匀。」 实验 hotspot 里四个节点的键份额是 0.2429 / 0.2471 / 0.2701 / 0.2399，最大只有 0.2701；但 9000 次热读打在一个键上，持有该键的 n2 访问份额达到 0.9234。uniform_keys_are_not_uniform_access=true。容量规划必须同时看键分布和访问分布，不能用一个哈希环的均衡度代替。

「虚拟节点会帮我搬数据。」 虚拟节点只改变环上的路由区间，让键更均匀地落到各物理节点。实验 vnode_balance 里，1 个虚拟节点的 max_min_ratio=2.775475923852184，150 个虚拟节点降到 1.0650077760497667；但加节点后的迁移仍然要单独执行，vnodes_do_not_move_data_by_themselves=true。把虚拟节点数调大不是迁移方案。

「Redis Cluster 就是一致性哈希。」 Redis Cluster 是 16384 个固定哈希槽，公式 HASH_SLOT = CRC16(key) mod 16384，实现是 CRC16 & 0x3FFF；它没有 Ketama 环，也没有「虚拟节点」这个术语。本课的一致性哈希环用 MD5 放虚拟节点，是教学对照，不是 Redis 的路由实现。把两者混为一谈，会误以为 Redis 加节点只影响环上相邻区间，也会误读 CLUSTER SETSLOT 和槽表。

「迁移就是先改槽表，再慢慢补数据。」 实验 naive_vs_protocol_migration 的天真做法先改槽表不搬数据：28 次读全部 missing（reads_ok=0、missing_ratio=1.0），对 article:00014:title 写入修订标题后，n1 仍是 Weekly digest，n4 是 Weekly digest (revised)，split_brain=true。正确顺序是先用 MIGRATING / IMPORTING 定义迁移窗口，已有键由源节点服务，源上没有的键 ASK 到目标，迁完键后再 SETSLOT NODE。槽表是结果，不是起点。

「ASK 和 MOVED 都是重定向，客户端随便更新槽表就行。」 MOVED 表示槽的归属永久改变，客户端应更新槽表；ASK 只对下一条查询生效，不能改槽表，因为同一槽的其他键可能还在源节点。教学客户端在协议实验里 ask_count=1、之后 moved_count=20，两者的计数口径和用途不同。收到 ASK 后先发 ASKING 再发命令；过早把槽映射到目标又没有 ASKING，目标会把请求 MOVED 回源节点。

「加了 hash tag，多键操作在迁移期间也一定成功。」 hash tag 只保证键落在同一槽。实验 hashtag_and_tryagain 里，两个带标签的键都成功 MSET 到槽 6229；但只把 title 迁到 n4、views 还留在源侧时，再 MSET 得到 tryagain。规范说得很清楚：重分片期间键被拆到源和目标两边，或键不存在，就返回 -TRYAGAIN；迁完后才恢复。

「热 key 拆分就是加副本。」 教学里的热 key 拆分是把一个键拆成 8 个分区键，按 user id 选分区，访问份额从 0.9234 降到 0.375；这不是 Redis Cluster 命令，也不是副本提升。副本提升改变的是「谁来服务同一份数据」，热 key 拆分改变的是「数据分成几份、请求怎么选份」。两者解决的不是同一个问题。

「教学 MIGRATE 就是 Redis 的 MIGRATE 命令。」 教学 migrate_key 是进程内字典的复制加删除，HashSlotCluster 的槽表也是本地表；Redis 的 MIGRATE 是跨节点的 TCP 命令，迁移期间两端短暂加锁，大 key 在有延迟约束时不适合这样迁。本课不实现 TCP、cluster bus 或槽位所有权的集群传播。

设计权衡

节点的权衡是：范围分片利于扫描，哈希分片较易均衡但跨分片范围查询昂贵。实验 range_vs_hash_scan 把这条权衡量化得很直接。扫描 2000–2199 这 200 个连续 id，范围分片只打到 n1 一个分片；一致性哈希打到四个分片，计数 53 / 46 / 49 / 52。如果每次扫描都要 fan-out 到四个分片再聚合，尾延迟、网络请求数和失败重试都会增加；如果业务能按 id 区间定位，范围分片就省掉了这部分成本。

反过来，连续 id 的写入会集中。5000 次写里 4000 次落在 id 9800–9999，范围分片下 n4 拿到 4000、n1 拿到 1000，n2 / n3 为 0，range_hot_share=0.8；一致性哈希下写量是 1134 / 1555 / 1275 / 1036，max_share=0.311。范围分片适合「按范围读多、写入分散」的负载，哈希分片适合「写新 id 集中、按单键读多」的负载。没有一种切法同时最优，选择取决于查询模式和写入模式。

重分布的权衡在「迁移量」和「迁移期间的正确性」之间。取模 3→4 搬走 7458 个键（0.7458），一致性哈希搬走 2399 个（0.2399），Redis 式搬 1/4 的槽搬走 2500 个键（0.25）。迁移量越小，扩容窗口越短、网络和磁盘压力越小；但迁移量小不等于迁移简单。实验里的协议做法要维护 MIGRATING / IMPORTING 状态、处理 ASK / MOVED、在迁移完成后 SETSLOT NODE，而天真做法虽然「瞬间完成」，却让 28 个键全部读不到并制造了 split_brain=true。减少迁移量和保证迁移正确性是两条独立的工程任务。

虚拟节点的数量也是权衡。1 个虚拟节点时 max_min_ratio=2.775475923852184，150 个时降到 1.0650077760497667；虚拟节点越多，键分布越均匀，但环上的元数据、查找和重建成本也越高。150 是本课教学实现的选择，不是所有系统的最优值。节点数、键数、哈希函数和虚拟节点数要一起评估。

热 key 拆分同样有代价。实验把最大访问份额从 0.9234 降到 0.375，但代价是：读取方要按 user id 选分区，写入方要维护 8 份值，跨分区的聚合、缓存失效和一致性都变复杂。8 个分区落在 n3 / n2 / n1 / n3 / n4 / n2 / n4 / n4，并没有做到四个节点完全均分；分区数量、分区键设计和路由规则都会影响最终分布。热 key 拆分不是「拆了就均匀」，而是「把单点压力换成可控的多点压力」。

跨分片操作则是「原子性」和「可扩展性」的权衡。hash tag 让多个键同槽，换来同槽多键操作的原子性，但把相关键绑在同一个节点上，热点和故障域也更集中；不用 hash tag，多键操作会 CROSSSLOT，但键可以自由分散。迁移期间 TRYAGAIN 的存在，说明系统宁愿让客户端重试，也不愿在源和目标两边做跨节点的隐式事务。这个取舍要和业务对一致性、延迟和重试成本的要求一起看。

7. 和生产引擎的对应关系（不要记错边界）

  • 教学 ShardingEngine 是 Python 3 标准库模型，不是 Redis。没有 TCP、cluster bus、gossip、CLUSTER 命令解析器，也没有槽位所有权的集群传播；槽表是 HashSlotCluster 的本地列表，节点加入和迁移由测试代码直接调用。
  • 教学一致性哈希环用 MD5 放置虚拟节点，每个物理节点默认 150 个；Redis Cluster 用 16384 个槽，路由公式是 CRC16(key) & 0x3FFF，没有 Ketama 环，也没有「虚拟节点」这个术语。两者都可以「只搬一部分键空间」，但机制不同。
  • 教学 key_hash_slot 与规范一致：先按花括号规则取 payload，再 crc16(payload) & 0x3FFF；hash_tag_payload 返回的 payload 会用于槽位计算。Redis 8.4 的 keyHashSlot 也做同样的低 14 位截断和 hash tag 处理。
  • 教学 MIGRATE 是 HashSlotCluster.migrate_key 的进程内复制加删除，键在任意时刻只在一个字典里；Redis 的 MIGRATE 是跨节点 TCP 命令，迁移期间两端短暂加锁。教学实现没有网络、没有序列化协议、没有 RESTORE。
  • 教学 ASK / MOVED 只在 ClusterClient 和本地槽表之间传递；ASKING 是 asking=True 参数，不是 Redis 的 CLIENT_ASKING 标志位。语义对齐，实现不同。
  • 教学 TRYAGAIN 由 mset 在「同槽但键被拆到源和目标两边或缺失」时返回；Redis 的 CROSSSLOT / TRYAGAIN 文本和错误路径见 src/cluster.c，本课不声称教学实现覆盖了 Redis 的全部多键命令和错误分支。
  • 教学实验没有实现 Redis 8.0 的单槽 glob 模式优化（patternHashSlot），也没有实现副本、故障切换、cluster bus 或 gossip；热 key 拆分是教学手段，不是 Redis Cluster 命令，也不是副本提升。

页面还写了 hash tag 规则：若键中有 {，且其右侧有 }，且两者之间至少有一个字符，则只哈希 { 与第一个 } 之间的子串；例子是 {user1000}.following 与 {user1000}.followers 只哈希 user1000，同槽；foo{}{bar} 哈希整个键；foo{{bar}}zap 哈希 {bar；foo{bar}{zap} 哈希 bar；以 {} 开头则哈希整个键。Redis 8.0 起，含 hashtag 且满足条件的 glob 模式（KEYS/SCAN/SORT）可只扫一个槽；本课实验没有实现这条优化，只作为文档阅读，不编造实验数字。

实时重配置部分，页面写到增删节点、再均衡本质都是把哈希槽从一个节点搬到另一个节点，搬槽就是搬这个槽里的键；相关子命令包括 CLUSTER ADDSLOTS / DELSLOTS / ADDSLOTSRANGE / DELSLOTSRANGE，以及 CLUSTER SETSLOT slot NODE / MIGRATING / IMPORTING。MIGRATING：源节点接受该槽的请求，但仅当键存在；否则返回 -ASK，指向迁移目标。IMPORTING：目标节点只在请求前有 ASKING 时才接受该槽的请求，否则对真正的槽所有者返回 -MOVED。文档的槽 8 例子是：先对 B 发 CLUSTER SETSLOT 8 IMPORTING A，再对 A 发 CLUSTER SETSLOT 8 MIGRATING B；已有键仍由 A 处理，A 上不存在的键由 B 处理，因此不会再在 A 上创建新键；然后用 CLUSTER GETKEYSINSLOT 取出键，对 A 发 MIGRATE，原子地把键从 A 迁到 B（两端短暂加锁）；迁完后对相关节点发 SETSLOT NODE。文档提醒：大 key 在有延迟约束时不适合这样迁。

页面还区分了 ASK 与 MOVED：MOVED 表示该槽此后由另一个节点永久服务，客户端应更新槽表；ASK 只把下一条查询发到指定节点，不要改槽表，因为同一槽里其他键可能还在源节点。客户端收到 ASK 后，先发 ASKING，再发被重定向的那条命令，并且后续查询仍先打到旧节点。ASKING 在目标节点上设置一次性标志，让 IMPORTING 槽的请求被接受。若错误的客户端过早把槽映射到 B 且没发 ASKING，B 会用 MOVED 把请求打回 A。多键操作部分，页面用 hash tag 把多个键放到同一槽，例如 MSET {user:1000}.name Angela {user:1000}.surname White；重分片进行中，若这些键都还在同一侧（源或目标）且都存在，多键操作仍可用；若键不存在，或在重分片期间被拆到源和目标两边，则返回 -TRYAGAIN；迁完后该槽的多键操作恢复。这份规范讲的是固定 16384 槽的所有权与搬迁，没有 Ketama、没有按节点做哈希环，也没有「虚拟节点」这个术语；虚拟节点是本课一致性哈希实验里的教学机制，不能和 Redis 的槽位机制混为一谈。

自测题

1. 为什么 hash(key) % N 在 3→4 扩容时会搬走大部分键，而一致性哈希只搬一小部分？虚拟节点在这件事里起了什么作用，又没有起什么作用？

答案： 取模的归属是「哈希值对节点数取余」，N 从 3 变成 4 后，同一个键的余数大多改变，所以大部分键要换节点。实验 modulo_vs_consistent 里 3→4 搬走 7458 个、migration_ratio=0.7458；一致性哈希把节点和键放在环上，加节点只影响新节点接管的区间，搬走 2399 个、migration_ratio=0.2399，而且 moved_to 只有 n4。虚拟节点把每个物理节点的区间切成许多小段散在环上，让键在节点间更均匀：1 个虚拟节点时 max_min_ratio=2.775475923852184，150 个时降到 1.0650077760497667。但虚拟节点只改变路由区间，不搬数据；vnodes_do_not_move_data_by_themselves=true。加节点后的迁移仍然要单独执行。

2. 迁移期间只改槽表不搬数据会发生什么？协议做法里 MIGRATING / IMPORTING、ASK、MOVED 各自负责哪一段？为什么 ASK 不能更新槽表？

答案： 只改槽表不搬数据时，客户端以为键在 n4，实际数据还在 n1。实验 naive_vs_protocol_migration 里 28 次读全部 missing（reads_ok=0、missing_ratio=1.0）；对 article:00014:title 写入修订标题后，n1 仍是 Weekly digest，n4 是 Weekly digest (revised)，split_brain=true。协议做法里，MIGRATING 让源节点继续服务已有键、源上没有的键返回 ASK；IMPORTING 让目标节点只在收到 ASKING 时服务；ASK 只重定向下一条查询，MOVED 才表示槽的归属永久改变、客户端应更新槽表；迁完后 SETSLOT NODE。实验里迁移中 28/28 已有键由 n1 服务，新键 article:new:133:title（槽 195）经 ASK 写到 n4，ask_count_after_new_write=1；after 阶段 28/28 由 n4 服务，moved_count=20、ask_count=1。ASK 不能更新槽表，因为同一槽的其他键可能还在源节点；如果客户端过早把槽映射到目标又没有 ASKING，目标会用 MOVED 把请求打回源节点。

3. 10000 个标题键在 4 个节点上分布得很均匀，为什么仍然可能有一个节点被打爆？热 key 拆分和 hash tag 分别解决了什么，又没有解决什么？

答案： 哈希只保证键在节点间大致均匀，不保证请求均匀。实验 hotspot 里四个节点的键份额是 0.2429 / 0.2471 / 0.2701 / 0.2399，最大 0.2701；但 10000 次读里有 9000 次打在 article:00042:title，该键在 n2，于是访问份额变成 234 / 9234 / 295 / 237，n2 的键份额只有 0.2471、访问份额却是 0.9234，uniform_keys_are_not_uniform_access=true。热 key 拆分成 8 个分区后，9000 次热读的份额是 0.125 / 0.25 / 0.25 / 0.375，max_share 从 0.9234 降到 0.375；但这是教学热 key 拆分，不是 Redis Cluster 命令，也不是副本提升，读取方要按 user id 选分区，写入方要维护多份值。hash tag 解决的是多键同槽：{article:00001}:title 与 {article:00001}:views 都在槽 6229，MSET 成功；不带 tag 的 article:00001:title 与 article:00001:views 在槽 16052 与 8986，返回 crossslot。但 hash tag 不解决单槽过热，也不保证迁移期间多键操作一定成功：只迁走 title 后 MSET 返回 tryagain，两个键都迁到 n4 后才恢复。

本课小结

  • 分片先要回答「键归谁」，再回答「节点变了怎么搬」。取模在 3→4 时搬走 7458 个键（0.7458），一致性哈希（每节点 150 个虚拟节点）只搬 2399 个（0.2399）且只搬到 n4；Redis Cluster 则是 16384 个固定槽、CRC16(key) & 0x3FFF，靠槽所有权搬迁，不是一致性哈希环。三者都能把键分到多个实例，但路由和迁移机制不同。
  • 虚拟节点改善键的均匀程度，不搬数据。1 个虚拟节点时 max_min_ratio=2.775475923852184、max_share=0.4957；150 个时 max_min_ratio=1.0650077760497667、max_share=0.3424。加节点后的迁移仍要单独执行；迁移量可以被控制在约 1/4，但正确性要靠 MIGRATING / IMPORTING、ASK / MOVED 和 SETSLOT NODE 这一套读写策略，而不是先改槽表再补数据。
