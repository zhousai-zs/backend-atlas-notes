第 15/208 课：字符编码、字节序与数据表示

节点：a-encoding · 域：A · 子类：工具与程序执行 · 难度：基础 · 前置：a-binary、a-network

一句话：字节序规定多字节整数排列，字符编码规定字符到字节的映射，两者是不同层面。

1. 学习目标与为什么后端要懂

1.1 学习目标

完成本课后，你应该能够：

  1. 解释大端与小端：说清多字节整数在内存/线上「高位字节在前还是低位字节在前」，以及为什么网络协议统一用网络字节序（大端）。
  2. 理解 UTF-8 变长编码：能从首字节判断 1～4 字节字符边界，知道「字符数 ≠ 字节数」。
  3. 分清长度单位与边界：协议头里的 length 到底是字节、字符还是码点；截断时绝不能劈开多字节字符。
  4. 独立完成节点实践：编写网络序整数编解码及 UTF-8 边界检查工具。
  5. 在微信公众号后台场景里，能把「回调 XML/JSON、openid、模板消息中文、TCP 二进制协议头长度字段」正确按字节处理。

1.2 验收标准

节点给出的验收标准有两条，本课会反复回扣：

  • 能解释字符数不等于字节数。 「微信」是 2 个字符，UTF-8 下是 6 个字节；按「字符数」截库字段却按「字节数」分配缓冲，就会截断或越界。
  • 跨端序测试结果一致。 同一整数用网络序（大端）打包后，在任意主机上 unpack 得到相同数值；与小端布局对比能看出字节顺序差异。

1.3 为什么微信公众号后台要懂编码与字节序

节点对「为什么」写得很干脆：避免网络跨平台解析错误和中文截断。 放到即将入职的腾讯微信公众号后台，几乎每天都会碰到字节与字符混用：

  • 服务器回调 XML / JSON。 消息体是 UTF-8。按「最多 64 字符」截昵称时，若用 buf[64] 当字节上限，可能把「微」劈成 E5 BE 半截，下游 decode 失败或乱码。
  • openid / 模板消息中文。 openid 多为 ASCII；模板里的用户昵称、门店名是中文。日志、DB 列宽、Kafka 消息大小——单位是字节还是字符必须写清。
  • TCP / 自研二进制协议头。 常见 uint32 length + payload。若不按网络序（大端）读写，x86 小端机器上「长度 256」会变成 0x00010000 量级，直接撑爆缓冲或解错包。
  • 跨语言互操作。 Go / C++ / Python 服务混部时，只有显式约定编码与端序，联调才不会「我这边看着是对的」。

所以本课要建立的肌肉是：整数走网络序；文本走明确字符编码；长度字段写明单位；截断只落在字符边界上。

2. 从直觉到原理：三个核心要点

2.1 大端与小端

直觉：写信地址的顺序

门牌「1 号楼 2 单元 3 层 4 室」——你先写楼号还是先写室号？大端（big-endian）像人读写数字：高位在前；小端（little-endian）把最低字节放在最低地址，对 CPU 取低位算术有时更方便。对同一数值 0x01020304：

端序 内存 / 线上 4 字节（低地址 → 高地址）
大端（网络序） 01 02 03 04
小端（x86 主机常见） 04 03 02 01

原理：字节序只管「多字节整数如何拆成字节」

  • 字节序（endianness）：多字节整数的字节排列约定。与「字符怎么变成字节」无关——那是下一节的字符编码。
  • 网络字节序 = 大端。 POSIX / 套接字约定：htons / htonl / ntohs / ntohl 在主机与网络序之间转换。见 byteorder(3)。
  • 主机字节序：看 CPU。x86/x86_64 是小端；有些嵌入式/老架构是大端。协议里不要假设对端和你一样。

例子：Python struct 与 Linux 工具

import struct
n = 0x01020304
print(struct.pack("!I", n).hex(" "))  # 网络序大端 → 01 02 03 04
print(struct.pack("<I", n).hex(" "))  # 小端       → 04 03 02 01
print(struct.unpack("!I", b"\x01\x02\x03\x04")[0])  # → 16909060

# 本机端序（Linux）
lscpu | grep -i 'byte order'
# 或
python3 -c "import sys; print(sys.byteorder)"  # little / big

公众号后台若手写二进制帧：length、msg_type、crc 一律 !（network）打包，跨语言、跨机器结果一致——这就是验收里的「跨端序测试结果一致」。

2.2 UTF-8 变长编码

直觉：汉字比字母「更宽」

电报时代每个字符等宽；UTF-8 为了兼容 ASCII 并覆盖 Unicode，常用字符短、生僻字符长：

范围 首字节形态 字节数 例子
ASCII 0xxxxxxx 1 A → 41
拉丁扩展等 110xxxxx 2 é
基本汉字等 1110xxxx 3 微 → E5 BE AE
补充平面 11110xxx 4 emoji

续字节一律 10xxxxxx。看到首字节就能知道本字符要吃几字节——边界检查的基础。

原理：字符编码 = 码点 → 字节序列的映射

  • 码点（code point）：Unicode 抽象编号，如 U+5FAE（微）。
  • 编码（encoding）：把码点序列化成字节。UTF-8 / UTF-16 / GBK 是不同映射。
  • 字符数 ≠ 字节数 ≠ 显示宽度。 Python 里 len("微信") == 2，但 len("微信".encode("utf-8")) == 6。

例子：公众号昵称截断

nick = "微信用户ABC"
raw = nick.encode("utf-8")
print(len(nick), len(raw))  # 字符数 vs 字节数

# 错误：按字节硬切
bad = raw[:4]               # 可能劈开「微」
# bad.decode("utf-8")       # UnicodeDecodeError

# 正确：只在字符边界截断（见实践 utf8_safe_truncate）

printf '微' | xxd           # e5 be ae
python3 -c "print(list(map(hex, '微'.encode())))"

2.3 长度单位、边界与二进制数据

直觉：量杯刻度必须统一

菜谱写「加水 200」——是毫升还是克？协议写 length=16——是 16 字节、16 字符，还是 16 个 UTF-16 code unit？单位没写清，比端序错了更隐蔽。

原理：三件事分开记

  1. 长度单位：协议 / DB / API 文档必须写明 byte / char / rune。HTTP Content-Length 是字节；「昵称最多 16 个字」通常是字符。
  2. 边界：变长编码下，合法截断点 = 某字符结束后的偏移。半截续字节既不是合法 UTF-8，也不能当「差不多的中文」。
  3. 二进制 vs 文本：签名、protobuf、自定义帧是原始字节，不要 .decode("utf-8") 再当字符串处理；文本字段则相反，入库前要明确编码。

例子：帧头 length 字段

| magic(2B) | msg_type(2B) | body_len(4B, 网络序) | body |
  • body_len 用 !I 编解码；单位是 body 的字节数。
  • 若 body 是 UTF-8 JSON，先按字节读满 body_len，再 decode；不要按「字符数」去 recv。
  • 截断展示用文案时，对已 decode 的 str 按字符切，或对 bytes 用安全截断——两者不要混。

3. 常见误区与设计权衡

3.1 误区：char 是否有符号由实现决定，不能盲目位移

节点 pitfalls：char是否有符号由实现决定，不能盲目位移。

C/C++ 里 char 可能是 signed 或 unsigned，取决于编译器与平台。对可能 ≥ 0x80 的字节做算术右移或符号扩展，会把 0xE5 变成 0xFFFFFFE5，边界判断全错。正确做法：

  • 当字节处理时用 unsigned char / uint8_t；
  • 位移前先 & 0xFF；
  • 或直接用语言提供的编解码库，避免手搓位移。

Python 的 bytes 元素已是 0～255 的 int，无此坑；但写 C 扩展或读 C 协议文档时务必警惕。

3.2 权衡：显式编码提高互操作性，也要求验证输入长度

节点 tradeoffs：显式编码提高互操作性，也要求验证输入长度。

隐式 / 随主机 显式约定
互操作 换机器、换语言易翻车 协议写死 UTF-8 + 网络序，联调稳
成本 少写几行 必须校验长度、编码合法性、截断边界
失败模式 静默错数、偶发乱码 非法输入早失败，需定义错误语义

公众号后台建议：对外协议与存储一律显式 UTF-8 + 网络序整数；入口处验证字节长度与 UTF-8 完整性，拒绝半截序列，而不是「尽量 decode」。

5. 自测题（附答案）

Q1. 大端与小端分别如何排列 0x01020304？网络字节序是哪一种？为何公众号二进制协议头必须统一？

答案 大端：`01 02 03 04`（高位在前）；小端：`04 03 02 01`。网络字节序是大端。若不统一，小端机器把长度字段按主机序写出，对端会解出错误长度，导致粘包/超读/拒绝服务。微信后台多语言、多机器互打，必须显式网络序。

Q2. 为什么「字符数不等于字节数」？「微信」在 UTF-8 下各是多少？截昵称时按字节硬切会怎样？

答案 UTF-8 是变长编码：ASCII 1 字节，常用汉字 3 字节。「微信」= 2 字符 = 6 字节。按字节硬切（如 `raw[:4]`）可能得到半个「微」（`E5 BE`），`decode` 失败或产生替换字符，模板消息/日志出现乱码。

Q3. 节点 pitfalls 与 tradeoffs 各说了什么？写 C 扩展读字节时要注意什么？

答案 Pitfalls：char 是否有符号由实现决定，不能盲目位移——应用 `unsigned char`/`uint8_t` 或先 `& 0xFF`。Tradeoffs：显式编码提高互操作性，也要求验证输入长度——协议写死 UTF-8/网络序的同时，入口必须校验长度与完整性。

7. 小结

  • 字节序 ≠ 字符编码：前者排多字节整数，后者映射字符到字节。
  • 网络序 = 大端；跨机器整数必须显式转换或用 ! 打包。
  • UTF-8 变长：字符数 ≠ 字节数；截断只落在字符边界。
  • 长度写明单位；char 有符号性不可假设；显式编码换互操作，代价是校验长度。
