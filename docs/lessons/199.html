第 199/208 课：容量规划与成本治理

序号 199/208 · id n-planning · 领域 N · 阶段 4 · 难度 深入 · 子类 架构决策 前置：n-slo、i-capacity 节点摘要：以请求结构、增长、冗余和故障场景估算容量，持续对照真实资源消耗与单位业务成本。

导读

第 198 课给出了错误预算，第 141 课讨论过容量。本课为一套三副本 KV 估算「一台故障后还剩多少」，并用压测核对误差。教学假设：每个副本是本机上的一个 OS 进程，不是机房里的三台物理机。is_live_model=false。本机没有 wrk/hey，但有 Python 与多进程；不把「没有 wrk」写成无法压测。

节点资源标题写的是 Capacity Calculations，URL 指向 Non-Abstract Large System Design。2026-11-16 核对该 URL 仍为 200；/workbook/capacity-planning/ 返回 404，因此不以失效路径为准，而把容量计算作为 NALSD 的一部分阅读。

学习目标

  1. 说明峰值与突发及适用边界：不能按平均负载采购。
  2. 独立完成实践：为三副本 KV 估算一台故障时剩余容量，并与压测验证。
  3. 验收：包含复制与备份成本，给出误差和扩容触发点。

为什么后端要懂

只按平均值买机器，峰值和 N-1 会把服务打穿。估算若不对照一次真实负载，误差会一直藏在表格里。

核心知识点

1. 用单机测量估算 N-1，再用压测核对

直觉。 「三副本还剩三分之二」只在副本真正隔离时近似成立。

原理。 实践为每个副本启动一个监听进程，先测 1 进程、3 进程，再杀掉其中一个测 2 进程。干净复跑与正式树刷新中，单机、两机（N-1）与三机吞吐量都被真实测到，且两机明显高于单机、不高于三机。估算采用 2 × 单机，相对误差落在 ±35% 门限内（例如一次约 +3.5%，另一次约 −4.4%）。若天真地用三副本总量的 2/3，同机 CPU 往往使误差更大，报告里两种算法都保留。两种算法都写入报告，不以较差的那个充作「验证通过」。

边界。 这是本机教学压测，不是多机器或 wrk 官方套件。绝对值不能搬到生产。美元成本也未测，只用相对成本单位。

2. 成本要计入复制和备份，触发点要写明

直觉。 三副本不是三倍读容量那么便宜，因为写要放大，备份还要占一份。

原理。 成本表计入 3 个副本加上 15% 备份，写放大为 3，并给出相对的单位读成本。扩容触发点取实测 N-1 容量的 70%：计划峰值超过它就该扩，而不是等平均值看起来还很空。仅按平均值（例如峰值的 40%）采购的方案在本课被明确拒绝。

常见误区

  • 只按平均负载采购容量。
  • 用共享进程里的 2/3 比例代替隔离副本的 N-1，还不报告误差。
  • 成本表只算「提供读服务的机器」，忽略复制写放大和备份。

设计权衡

成本压缩与故障余量需要共同评审。保留 N-1 意味着平时有空闲；把空闲卖光则等于没有故障余量。

自测题

1. 为什么估算用 2×单机，而不是三副本总量的 2/3？

答：N-1 问的是「还剩两台时的能力」。应用单机测量外推，再用两台的压测核对。以当次 reports/capacity.json 为准，两份算法都保留。

2. 平均负载看起来只有峰值的 40%，为什么不能按这个买？

答：故障时要在峰值下仍留 N-1。按平均采购会在突发或一台失败时不够。

3. 「包含复制与备份成本」指什么？

答：写要打到三个副本，备份另占一份相对成本。本次相对集群成本为 3.45 个单位，而不是 3。
