第 159/208 课：Token、窗口与生成预算

序号 159/208 · id k-tokens · 领域 K · 阶段 1 · 难度 基础 · 子类 模型能力与表示 前置：k-transformer 节点摘要：Tokenizer 把文本编码为模型词元，中文、代码和标点的 token 数与字符数不相等。

导读

上一课说明上下文越长计算越重。真正进模型的不是字符数，而是 tokenizer 切出的词元。中文日志和 C++ 源文件用同一套字符预算去估不同模型，会得到错误的余量；截断时还可能删掉错误栈或任务约束。

教学假设：统计一份中文 KV 日志和一段教学 C++ 代码的词元数，并按策略截断。以下文本均为教学样本，不代表腾讯或微信内部日志。使用 PyPI 当日稳定版 tiktoken==0.14.0 的本地编码器，is_live_model=false，没有调用 OpenAI 或其他付费 API。

学习目标

  1. 解释编码器差异及适用边界
  2. 独立完成实践：统计中文日志和 C++ 文件的 token 数，制定截断与摘要策略。

为什么后端要懂

节点给出的理由是「控制长日志与代码任务的输入预算。」预算按词元计费和截断；用字符数去猜，会在一种模型上浪费窗口，在另一种模型上悄悄截掉关键证据。

核心知识点

1. 编码器差异

原理。 tiktoken README 写明：它是用于 OpenAI 模型的快速 BPE tokenizer，并示范 get_encoding("o200k_base") 与 encoding_for_model("gpt-4o")。不同编码表把同一段字节切成不同数量的词元。2026-11-15 抓取 PyPI，当前稳定版为 tiktoken 0.14.0（requires_python >=3.9，未 yank）。

直觉。 「这段有 529 个字符」不能告诉你某种模型还能塞多少词元。换编码表，数字就会变。

实践对照。 同一份日志 529 字符、669 字节，在 cl100k_base / o200k_base / p50k_base 下分别是 291、267、377 个词元；同一段 C++ 413 字符则是 129、131、167。字符到词元的比率在日志与代码之间也不同（例如 cl100k 上为 0.5501 对 0.3123）。因此不能用字符数直接估算所有模型预算。

2. 输入/输出预算

原理。 上下文窗口同时覆盖输入和预留给输出的词元。本课只统计输入侧，没有调用任何会返回 usage 的远程模型，也没有测量输出预算。

实践对照。 结果记录三种编码的输入词元，不把这些数字写成某张账单。官方 encoding_for_model 需要模型名称；本课直接按编码名计数，避免把编码表误说成已经绑定某个未核验的在线模型快照。

3. 截断与上下文上限

原理。 超过窗口必须删减。策略应先保住错误栈和任务约束，再丢可替代的心跳或周期性指标。若必保内容已经超过软预算，也不应先砍栈。

实践对照。 在 cl100k_base、软预算 80 时，必保内容本身是 112 个词元，仍全部保留；心跳与定期指标被删，共丢掉 4 行。截断后仍含「调用栈」「service.cpp:7」「任务约束」。

常见误区

  1. 以为所有模型共享同一种 tokenizer。 节点原句即此。三种编码对同一日志给出三个词元数。
  2. 按字符比例一刀切。 中文日志和 C++ 的词元/字符比不同，先按字符删可能在一种文本上砍得太狠，在另一种上留下大量噪音。

设计权衡

节点原句是「截断节省成本，但可能删除决定性证据。」把预算压到 80 以下确实更便宜，若误删调用栈就不能再定位空指针。本课选择让必保行突破软预算，代价是实际输入变成 112 个词元。

自测题

  1. 为什么 529 个字符不是通用预算？ 三种编码分别给出 291、267、377 个词元，预算单位是词元。
