第 2/208 课：CPU与指令执行

节点：a-machine（CPU Execution）
领域：A / 硬件与操作系统
阶段：0
前置节点：a-binary
本课关键词：寄存器、程序计数器、指令、数据通路、流水线、分支预测、乱序执行、指令集、微架构

0. 这个节点在学什么

节点的核心结论是：

CPU 按照指令集执行加载、计算、分支和存储；流水线与乱序执行属于具体微架构实现。

这句话可以拆成两层：

  1. 软件看到的契约：CPU 能执行哪些指令、能用哪些寄存器、如何寻址、函数如何调用。这一层主要由指令集架构（ISA）和ABI描述。
  2. 硬件内部的实现：同一条指令在芯片里怎样被拆分、排队、预测、并行执行。这一层是微架构，不同型号的 CPU 可以完全不同。

本课的目标不是让你背会某款 CPU 的框图，而是建立一条稳定的心智链路：

C 代码 -> 编译器生成的指令 -> CPU 取指/译码/执行 -> 真实运行时间

后端工程师平时写的是 C/C++、Go、Java 等高层代码，但性能问题最终会落到这条链路上。尤其是即将进入腾讯微信公众号后台开发的同学，面对消息收发、权限校验、限流、路由、存储访问等高并发路径，理解这条链路能帮助你：

  • 看懂编译器优化和汇编，知道源码里的一个 if 不一定是机器里的一条分支；
  • 用 perf stat 解释“为什么同样的代码，换数据分布后变慢了”；
  • 理解函数调用、栈帧和调用约定，为后续排查栈溢出、崩溃、协程切换打基础；
  • 知道“主频高”不等于“业务快”，容量评估必须用真实负载测量；
  • 为后面的缓存、并发、操作系统调度课程建立硬件直觉。

1. 学习目标与为什么后端要懂

1.1 本课学习目标

学完本课后，你应该能够：

  1. 解释寄存器与程序计数器：知道它们分别保存什么，程序计数器如何驱动“下一条指令”。
  2. 解释指令与数据通路：能说清一条加载、加法、比较、分支、存储指令在 CPU 中大致经过哪些部件。
  3. 区分指令集与微架构：知道 x86-64、ARM64、RISC-V 是 ISA，而流水线深度、分支预测器、乱序执行窗口是微架构。
  4. 解释一次函数调用的基本过程：call/ret、返回地址、栈帧、参数寄存器、返回值寄存器、调用约定。
  5. 完成动手实践：把循环编译成汇编；用排序后数据与随机数据对比条件分支的运行时间；用 perf stat 观察分支预测失败。
  6. 建立正确的性能观：主频不能单独决定程序速度；抽象模型便于理解，但优化决策必须回到真实硬件测量。

1.2 为什么后端要懂 CPU 执行

后端服务不是“把请求交给数据库”这么简单。一个微信公众号后台的典型请求可能包含：

接入层 -> 鉴权 -> 限流 -> 消息解析 -> 业务路由 -> 存储/缓存 -> 组装响应

其中每一段都可能有大量分支、函数调用、内存访问和循环：

  • 解析 JSON/Protobuf 时，字段是否存在、类型是否匹配，都是条件分支；
  • 鉴权和限流时，命中缓存还是回源，是典型的热路径分支；
  • 消息分发时，不同消息类型走不同处理器，可能形成间接跳转；
  • 批量任务中，数据是否有序、是否集中，会影响分支预测和缓存命中；
  • 排查 p99 延迟时，cycles、instructions、branch-misses 往往比“CPU 使用率”更有解释力。

更重要的是，源码不等于机器指令。编译器可能：

  • 把循环展开；
  • 把条件分支转换成 cmov；
  • 自动向量化；
  • 内联函数，消除 call/ret；
  • 把变量长期放在寄存器里，而不是内存里。

如果你只看 C 代码，很容易对真实执行情况做出错误判断。理解 CPU 执行，就是学会在“源码”和“硬件”之间来回翻译。

2. 从直觉到原理

2.1 先建立直觉：CPU 在重复一个很小的循环

把 CPU 想成一个极其勤奋、但只会执行简单动作的工人。它不断重复：

  1. 取指（Fetch）：根据程序计数器，从内存中取出下一条指令。
  2. 译码（Decode）：识别这是什么指令，需要哪些寄存器，做什么运算。
  3. 执行（Execute）：算术逻辑单元做加减、比较、位运算；或计算内存地址。
  4. 访存（Memory）：需要时读写数据。
  5. 写回（Write Back）：把结果写回寄存器。

这叫指令周期。真实的现代 CPU 比这复杂得多，会并行、乱序、预测，但这个五步模型是理解一切的起点。

一个很短的 C 循环：

long sum(const long *a, long n) {
    long s = 0;
    for (long i = 0; i < n; i++) {
        s += a[i];
    }
    return s;
}

它做的事情可以抽象成：

s = 0
i = 0
判断 i < n，不成立就结束
读取 a[i]
s = s + a[i]
i = i + 1
跳回判断

这就是“加载、计算、分支、存储”的雏形。CPU 的工作不是理解“求和”，而是执行一条条更小的指令。

2.2 寄存器与程序计数器

寄存器是什么

寄存器是 CPU 内部数量很少、速度极快的存储单元。它们不像内存那样有地址总线访问延迟，通常可以在一个时钟周期内被读写（具体取决于微架构和指令）。

常见寄存器可以分为几类：

类型 作用 x86-64 例子
通用寄存器 整数、指针、临时值 rax、rbx、rcx、rdx、rsi、rdi、r8–r15
栈指针 指向当前栈顶 rsp
帧指针 指向当前栈帧基址 rbp
指令指针/程序计数器 指向下一条要执行的指令 rip
标志寄存器 保存比较结果、溢出、零标志等 rflags
向量寄存器 SIMD/浮点运算 xmm、ymm、zmm

寄存器非常宝贵。编译器会尽量把循环变量、指针、累加器放在寄存器里；寄存器不够时，才会“溢出”到栈上。你在 -O0 汇编里看到大量 -8(%rbp)、-16(%rbp)，通常就是变量被放在栈上。

程序计数器是什么

程序计数器（Program Counter，PC）保存“下一条指令的地址”。在 x86-64 中，它叫 rip（Instruction Pointer）。CPU 每取一条指令，PC 通常增加这条指令的长度；遇到跳转、调用、返回、中断时，PC 被改成目标地址。

可以把 PC 想成书签：

  • 顺序执行：书签往后翻一页；
  • jmp：直接翻到某一页；
  • call：记住当前页，翻到函数那一页；
  • ret：回到刚才记住的那一页；
  • 中断/异常：硬件把现场保存好，跳到处理程序。

关键点：PC 是控制流的源头。CPU 先要知道下一条指令在哪里，才能取指。分支预测之所以重要，就是因为 CPU 不想等 PC 确定后才继续工作。

用 gdb 看寄存器

编译一个带调试信息的程序后，可以用 gdb 观察：

gcc -O0 -g -fno-omit-frame-pointer -o call call.c
gdb -q ./call

在 gdb 中：

(gdb) break add
(gdb) run
(gdb) info registers rip rsp rbp rdi rsi rax
(gdb) x/4gx $rsp
(gdb) disassemble /r

你会看到：

  • rip 指向当前即将执行的指令；
  • rsp 指向栈顶；
  • rdi、rsi 往往是前两个整数参数；
  • rax 往往是返回值或临时结果；
  • x/4gx $rsp 可以查看栈上的返回地址、保存的 rbp 等内容。

这比只看源码更能建立“机器正在做什么”的直觉。

2.3 指令与数据通路

指令是什么

一条机器指令通常包含：

  • 操作码（opcode）：要做什么，例如加、加载、跳转；
  • 操作数：对谁做，可能是寄存器、立即数、内存地址；
  • 寻址方式：如何算出内存地址；
  • 下一条指令的位置：顺序下一条，或某个跳转目标。

以 x86-64 为例，几类常见指令：

指令 含义
movq (%rdi), %rax 从 rdi 指向的内存读取 8 字节到 rax
addq %rax, %rbx rbx = rbx + rax
cmpq %rdx, %rdi 比较 rdi 与 rdx，设置标志位
jne .L3 若不相等，跳到 .L3
call add 调用函数 add
ret 从当前函数返回

注意：不同汇编语法看起来不同。GCC 在 Linux 上默认常用 AT&T 语法，objdump -M intel 可以切换成 Intel 语法。学习时不必死记语法，重点是看懂“数据从哪里来、到哪里去、控制流是否改变”。

数据通路是什么

“数据通路”是数据在 CPU 内部流动的路径，通常包括：

程序计数器
   |
   v
取指单元 ---> 指令译码 ---> 寄存器堆
                              |
                              v
                        算术逻辑单元 ALU
                        地址生成单元 AGU
                              |
                              v
                          数据缓存/内存
                              |
                              v
                          写回寄存器

控制单元则负责根据指令产生控制信号：什么时候读寄存器、ALU 做什么运算、是否写内存、下一条 PC 取哪里。

把 C 循环翻译成汇编

把前面的求和函数保存为 sum.c：

long sum(const long *a, long n) {
    long s = 0;
    for (long i = 0; i < n; i++) {
        s += a[i];
    }
    return s;
}

用 GCC 生成汇编：

gcc -O2 -S -o sum.s sum.c

在 x86-64 上，-O2 通常会得到类似下面的结果（不同 GCC 版本和平台可能略有差异）：

sum:
    testq   %rsi, %rsi
    jle     .L4
    leaq    (%rdi,%rsi,8), %rdx
    xorl    %eax, %eax
.L3:
    addq    (%rdi), %rax
    addq    $8, %rdi
    cmpq    %rdx, %rdi
    jne     .L3
    ret
.L4:
    xorl    %eax, %eax
    ret

逐行理解：

汇编 作用
testq %rsi, %rsi 测试 n 是否为 0 或负数
jle .L4 若 n <= 0，跳到返回 0 的分支
leaq (%rdi,%rsi,8), %rdx 计算结束地址：a + n * 8
xorl %eax, %eax 把累加器 rax 清零
addq (%rdi), %rax 读取 a[i] 并加到 rax
addq $8, %rdi 指针前进 8 字节，指向下一个 long
cmpq %rdx, %rdi 比较当前指针和结束地址
jne .L3 不相等就继续循环
ret 返回，返回值在 rax

这段汇编里已经能看到本节点的几个关键词：

  • 寄存器：rax 是累加器，rdi 是数组指针，rsi 是长度，rdx 是结束地址；
  • 程序计数器：jne 会改变下一条指令的位置；
  • 指令与数据通路：addq (%rdi), %rax 同时完成“访存”和“计算”；
  • 分支：循环末尾的条件跳转；
  • 编译器优化：-O2 把循环变量 i 变成了指针递增，减少了一次乘法和比较。

如果你用 -O0 编译，会看到更多栈访问和更“笨”的代码：

gcc -O0 -S -o sum_O0.s sum.c

这正好说明：源码到机器码之间隔着一层编译器。学习汇编不是要手写汇编，而是为了知道编译器把你的代码变成了什么。

用 objdump 看机器码

gcc -S 看的是汇编文本；objdump 看的是已经编译好的可执行文件中的机器码：

gcc -O2 -g -o sum sum.c
objdump -d -M intel sum | sed -n '/<sum>:/,/^$/p'

你会看到地址、机器码字节和汇编指令。例如：

0000000000001139 <sum>:
    1139: f3 0f 1e fa          endbr64
    113d: 48 85 f6             test   rsi,rsi
    1140: 7e 15                jle    1157 <sum+0x1e>
    ...

objdump 的价值在于：

  • 确认编译器到底生成了哪些指令；
  • 确认某个 if 是否变成了条件跳转，还是 cmov；
  • 确认函数有没有被内联；
  • 对照源码和机器码，理解性能差异。

2.4 指令集与微架构：软件契约 vs 硬件实现

这是本节点最重要的概念之一。

指令集架构（ISA）

ISA 是软件和 CPU 之间的契约，规定：

  • 有哪些指令；
  • 指令如何编码；
  • 有哪些寄存器；
  • 有哪些寻址方式；
  • 特权级、异常、内存模型等。

常见 ISA：

  • x86-64：Intel/AMD 服务器和 PC 常见；
  • ARM64/AArch64：手机、部分服务器常见；
  • RISC-V：开放指令集，教学和研究常见。

编译器面向 ISA 生成代码。只要 ISA 兼容，同一个二进制程序通常可以在不同实现上运行。

微架构

微架构是某个具体 CPU 核心如何实现这个 ISA，包括：

  • 流水线多少级；
  • 每周期能取多少条、发射多少条指令；
  • 分支预测器有多复杂；
  • 乱序执行窗口多大；
  • 缓存多大、几路组相联；
  • 有没有 SMT（超线程）；
  • 主频、功耗、散热策略。

例如，同样是 x86-64，不同代际的 Intel、AMD 处理器，流水线深度、预测器、缓存层次都可能不同。同一段二进制代码在它们上面都能跑，但性能可能差很多。

一张表区分

维度 指令集 ISA 微架构
是什么 软件可见的契约 硬件内部的实现
例子 x86-64、ARM64、RISC-V 某款 Intel/AMD/ARM 核心
决定什么 指令编码、寄存器、寻址、特权级 流水线、预测器、缓存、乱序窗口、频率
对后端的意义 二进制兼容、编译器目标 性能、功耗、成本、调优空间
是否会变 很稳定，演进较慢 每代产品都可能变化

还要注意：ABI 不是 ISA。函数参数放在哪些寄存器、栈如何对齐、哪些寄存器由调用者保存，这些属于调用约定/ABI。x86-64 在 Linux 上常用 System V ABI，在 Windows 上调用约定不同。后端服务通常部署在 Linux 上，所以本课以 System V AMD64 ABI 为例。

节点验收要求“能区分指令集和微架构”，你可以用一句话回答：

指令集是“CPU 承诺能听懂哪些指令”，微架构是“CPU 内部如何把这些指令执行得快”；同一指令集可以有不同微架构，性能不能只看指令集或主频。

2.5 流水线：让多条指令同时在路上

从“做完一条再做下一条”到流水线

如果没有流水线，CPU 执行一条指令要经过取指、译码、执行、访存、写回，做完才做下一条。这样吞吐量很低。

流水线像工厂装配线：把一条指令的处理拆成多个阶段，不同指令处在不同阶段，同时推进。

经典五级流水线：

时间 ->
指令1:  IF  ID  EX  MEM  WB
指令2:      IF  ID  EX   MEM  WB
指令3:          IF  ID   EX   MEM  WB
指令4:              IF   ID   EX   MEM  WB

理想情况下，虽然一条指令仍需 5 个周期完成（延迟），但每个周期都能完成一条指令（吞吐量）。这就是“延迟”和“吞吐量”的区别。

流水线冒险

流水线不是免费的，常见冒险有三类：

  1. 数据冒险：后一条指令需要前一条指令的结果。
  2. 控制冒险：遇到分支，不知道下一条该取哪里。
  3. 结构冒险：多条指令争用同一个硬件资源。

数据冒险的例子：

addq %rax, %rbx
addq %rbx, %rcx

第二条指令需要 rbx，而第一条还没写回。现代 CPU 常用转发/旁路（forwarding/bypass），把结果从执行阶段直接送给下一条指令，减少等待。

加载后立即使用则更麻烦：

movq (%rdi), %rax
addq %rax, %rbx

rax 要等访存阶段结束才可用，可能产生一个“气泡”（bubble），流水线暂停一个周期。这就是为什么“指针追逐”和“链表遍历”常常比数组遍历慢：不是指令多，而是依赖链和访存延迟限制了并行。

控制冒险就是分支问题：CPU 取到一条条件跳转时，条件可能还没算出来，但它不想停，于是先猜一个方向继续取指。这就是分支预测。

2.6 分支预测：CPU 的“猜下一步”

为什么需要预测

考虑循环：

for (int i = 0; i < n; i++) {
    s += a[i];
}

循环末尾的条件跳转，前 n-1 次都“跳回循环开头”，最后一次“不跳，继续往下”。如果 CPU 每次都等条件算完再取指，流水线会经常空转。

现代 CPU 会在分支结果出来之前，根据历史信息预测：

  • 这个分支以前跳过吗？
  • 最近几次是跳还是不跳？
  • 这个分支和之前哪些分支有关？
  • 目标地址在哪里？

常见机制包括：

  • 静态预测：例如“向后跳通常 taken，向前跳通常 not taken”；
  • 两位饱和计数器：连续两次猜错才改变强预测；
  • BTB（Branch Target Buffer）：缓存分支目标地址；
  • 全局历史/局部历史：利用分支之间的相关性；
  • 返回地址栈（RAS）：预测 ret 的返回地址；
  • 间接分支预测：用于虚函数调用、switch、函数指针等。

预测失败的成本

如果猜错，CPU 必须：

  1. 丢弃已经取入的错误路径指令；
  2. 恢复寄存器状态；
  3. 从正确地址重新取指；
  4. 重新填满流水线。

这叫流水线冲刷（flush）。代价通常是十几个到几十个周期，流水线越深，代价往往越大。

排序数据为什么可能更快

经典例子：

if (data[i] >= 128) {
    sum += data[i];
}
  • 如果 data 是随机的，条件大约一半真一半假，历史预测很难稳定，分支预测失败多。
  • 如果 data 已经排序，前一半几乎全为假，后一半几乎全为真；除了中间一次转变，预测器很容易学会，失败少。

注意：这里变快的不是“加法变少了”，而是控制流变得可预测。排序本身要花时间，所以只有在“同一批数据被反复处理很多次”或“排序对后续逻辑也有价值”时才可能划算。这个权衡会在动手实践里量化。

一个重要的现实：编译器可能把分支消掉

源码里的 if 不一定对应机器里的条件跳转。编译器可能把它变成：

  • cmov（条件传送）：没有控制流分支，但仍有数据依赖；
  • 向量化指令：一次处理多个元素；
  • 查表或无分支计算。

所以做实验时，必须用 objdump 确认循环里到底有没有条件跳转。如果没有，排序前后没有差异是正常现象，不是实验失败，而是编译器优化在起作用。

2.7 乱序执行：在不改变结果的前提下重叠工作

什么是有序、什么是乱序

程序在软件层面有一个顺序。CPU 为了填满流水线，可能把后面不依赖前面结果的指令提前执行，这叫乱序执行（Out-of-Order Execution，OoO）。

例如：

long x = a[i];
long y = b[i];
long z = x + y;

两个加载 a[i]、b[i] 互不依赖，CPU 可以让它们并行发出，不必等第一个加载完成再发第二个。等数据都到齐后，再做加法。

现代乱序 CPU 通常包含：

  • 重排序缓冲区（ROB）：记录指令原始顺序，保证按序提交；
  • 保留站/调度器：等待操作数就绪，选择可执行的指令；
  • 寄存器重命名：消除假依赖，让更多指令并行；
  • 加载/存储队列：管理内存访问顺序和冲突。

关键点：乱序执行不等于结果乱序。CPU 可以乱序执行，但通常按程序顺序“退休/提交”（retire/commit），以保证异常和内存语义正确。你在软件层看到的仍然是顺序语义。

乱序执行的边界

乱序执行不是无限的，受限于：

  • ROB 大小；
  • 物理寄存器数量；
  • 加载/存储队列大小；
  • 执行单元数量；
  • 缓存和内存延迟；
  • 依赖链长度。

如果循环里有一条很长的依赖链，例如：

s = s + a[i];

每次加法都依赖上一次的 s，那么即使 CPU 能乱序，也很难让多次迭代的加法同时进行。反过来，如果有多个独立累加器，编译器或程序员可以制造更多指令级并行（ILP）。

乱序执行与安全

乱序和推测执行也带来了侧信道安全问题（例如 Spectre 类问题）。CPU 可能提前执行本不该执行的路径，留下缓存痕迹。现代 CPU 和编译器会加入各种缓解措施，这些措施可能带来性能开销。这里先建立概念，后续安全与操作系统课程会展开。

2.8 一次函数调用的基本过程

这是本节点的验收点之一。我们用一个最小例子：

__attribute__((noinline))
long add(long a, long b) {
    return a + b;
}

long caller(void) {
    return add(7, 5) + 1;
}

int main(void) {
    return (int)caller();
}

保存为 call.c，用 -O0 和帧指针编译，方便观察：

gcc -O0 -fno-omit-frame-pointer -g -o call call.c
objdump -d -M intel call | sed -n '/<caller>:/,/^$/p'

在 x86-64 System V ABI 下，调用过程大致如下。

第一步：调用者准备参数

前六个整数/指针参数依次放入：

rdi, rsi, rdx, rcx, r8, r9

所以 add(7, 5) 会变成：

movl $7, %edi
movl $5, %esi

超过六个的整数参数，或者较大的结构体，可能通过栈传递。浮点参数使用 xmm0–xmm7。具体规则属于 ABI，不同平台不同。

第二步：调用者执行 call

call add

call 做两件事：

  1. 把返回地址压入栈。返回地址是 call 后面那条指令的地址；
  2. 把程序计数器 rip 设置为 add 的入口地址。

此时栈顶保存着“函数执行完后回到哪里”。

第三步：被调用者建立栈帧

典型的函数序言（prologue）：

pushq %rbp
movq %rsp, %rbp
subq $N, %rsp

含义：

  • 保存调用者的 rbp；
  • 让 rbp 指向当前栈帧基址；
  • 为局部变量、临时值、保存的寄存器腾出空间。

如果函数使用了 rbx、r12–r15 等被调用者保存寄存器，还要先把它们压栈，返回前恢复。

第四步：执行函数体

add 可能被编译成：

add:
    leaq (%rdi,%rsi), %rax
    ret

rdi 和 rsi 是参数，结果放入 rax。rax 是整数/指针返回值寄存器。

第五步：函数返回

典型尾声（epilogue）：

leave
ret

leave 等价于：

movq %rbp, %rsp
popq %rbp

它恢复栈指针和调用者的帧指针。然后 ret 从栈顶弹出返回地址，写回 rip，控制流回到调用者。

第六步：调用者继续

调用者从 call 的下一条指令继续执行。返回值在 rax 中。调用者需要注意：

  • rax、rcx、rdx、rsi、rdi、r8–r11 等是调用者保存寄存器，被调用者可以随意修改；
  • rbx、rbp、r12–r15 是被调用者保存寄存器，被调用者必须恢复；
  • 栈在 call 前要满足 ABI 的对齐要求（x86-64 System V 通常要求调用前 rsp 16 字节对齐）。

栈帧示意

高地址
+----------------------+
| 调用者的栈帧          |
+----------------------+
| 第 7 个及以后参数      |  <- 调用者准备
+----------------------+
| 返回地址              |  <- call 压入
+----------------------+
| 保存的 %rbp           |  <- 被调用者序言
+----------------------+
| 局部变量/临时空间      |  <- sub $N, %rsp
+----------------------+
| 对齐填充/出参空间      |
+----------------------+
低地址                  <- %rsp

这就是“一次函数调用”的完整骨架。很多后端问题都能从这里找到线索：

  • 递归太深导致栈溢出；
  • 协程切换需要保存/恢复寄存器上下文；
  • 崩溃栈回溯依赖帧指针或 DWARF 信息；
  • 回调、虚函数、函数指针会带来间接分支，影响分支预测；
  • 不同 ABI 的库混用可能导致参数错位或栈损坏。

3. 常见误区与设计权衡

3.1 常见误区

误区一：主频越高，程序一定越快

不对。粗略的性能关系是：

运行时间 ≈ 指令数 × 平均每指令周期数（CPI） ÷ 主频

主频只是分母中的一个因素。程序还可能受限于：

  • 指令数太多；
  • CPI 太高（缓存未命中、分支预测失败、依赖链）；
  • 内存带宽；
  • I/O 和锁竞争；
  • 多核利用率；
  • 功耗和散热导致的降频。

一款 3.0 GHz 的 CPU 可能因为缓存小、分支预测差，跑得比 2.5 GHz 但 IPC 更高的 CPU 慢。服务器选型不能只看主频，必须跑真实业务基准。

误区二：一条 C 语句就是一条指令

不对。一行 C 可能变成多条指令，也可能被完全优化掉。循环可能被展开、向量化；函数可能被内联；条件分支可能变成 cmov。必须看编译器和汇编。

误区三：分支预测就是“随机猜”

现代预测器会利用历史、目标地址、相关性，准确率可以很高。但面对真正随机、无规律的数据，准确率会下降。排序数据之所以快，是因为分支模式变得高度可预测。

误区四：乱序执行会让程序结果乱序

不对。乱序执行是硬件内部的调度方式，软件可见的结果和异常顺序通常仍按程序顺序提交。不要把“乱序执行”理解成“程序语义可以乱”。

误区五：排序一定能让程序更快

不一定。排序本身有 O(N log N) 的成本；如果只处理一次，排序可能得不偿失。而且编译器可能把分支优化成 cmov 或向量化，排序带来的分支预测收益就消失了。正确做法是测量。

误区六：汇编指令越少越快

不一定。指令少但依赖链长、缓存不友好，可能更慢；指令多但能并行、访问局部性好，可能更快。性能取决于指令数、CPI、访存、并行度和预测等多个因素。

误区七：指令集就是微架构

不对。x86-64 是 ISA；某款具体 CPU 的流水线、缓存、预测器才是微架构。同一份二进制可以在不同微架构上运行，性能不同。

误区八：函数调用只是跳转

不对。函数调用涉及参数传递、返回地址、栈帧、寄存器保存、栈对齐、返回值等一整套 ABI 约定。call/ret 只是其中最显眼的两个指令。

3.2 设计权衡

权衡 说明
抽象 vs 真实 五级流水线是教学模型，真实 CPU 更复杂；理解模型有助于推理，但优化必须实测
流水线深度 深流水线可能提高主频，但分支预测失败和异常恢复的代价更大
乱序窗口 窗口越大，越能隐藏延迟，但功耗、面积、复杂度更高
分支预测 预测越准，流水线越满；但预测器占用芯片面积和功耗，且推测执行有安全风险
排序 vs 不排序 排序可能让分支更可预测，但有 upfront 成本；只在重复处理或后续也受益时考虑
编译器优化 向量化、内联、cmov 可能提升吞吐，也可能改变分支行为；需要看汇编和测量
可移植 vs 极致优化 针对某款微架构调优可能很快，但换 CPU 或编译器后收益可能消失

节点特别强调：

抽象模型便于理解，优化决策仍需要真实硬件测量。

这句话应该成为你以后做性能优化的默认原则。不要凭“看起来应该更快”下结论，要用 perf、基准测试和真实负载说话。

4. 动手实践

本实践对应节点任务：

编译循环为汇编，对比顺序与随机分支的运行时间。

建议在 Linux x86-64 环境完成。需要：

  • gcc；
  • binutils（提供 objdump）；
  • 可选：perf、gdb、taskset。

先记录环境，便于解释结果差异：

uname -m
gcc --version
lscpu

把 CPU 型号、GCC 版本、编译选项记在实验笔记里。不同机器上的绝对时间不可直接比较，但同一台机器上的相对趋势有意义。

4.1 第一步：把循环编译成汇编

创建 sum.c：

long sum(const long *a, long n) {
    long s = 0;
    for (long i = 0; i < n; i++) {
        s += a[i];
    }
    return s;
}

生成 -O0 和 -O2 汇编：

gcc -O0 -S -o sum_O0.s sum.c
gcc -O2 -S -o sum_O2.s sum.c

对比两个文件：

diff -u sum_O0.s sum_O2.s

观察并回答：

  1. -O0 是否把 i、s、n、a 放在栈上？
  2. -O2 是否把循环变量变成了指针递增？
  3. 循环条件对应哪条比较指令和哪条跳转指令？
  4. 哪条指令负责读取数组元素？哪条负责累加？
  5. 返回值放在哪个寄存器？

再用 objdump 看可执行文件：

gcc -O2 -g -o sum sum.c
objdump -d -M intel sum | sed -n '/<sum>:/,/^$/p'

你应该能在输出中找到类似 add rax,QWORD PTR [rdi]、add rdi,0x8、cmp rdi,rdx、jne 的指令。不同编译器版本可能不同，但“加载、加法、指针递增、比较、条件跳转”这条链是稳定的。

4.2 第二步：观察一次函数调用

创建 call.c：

__attribute__((noinline))
long add(long a, long b) {
    return a + b;
}

long caller(void) {
    return add(7, 5) + 1;
}

int main(void) {
    return (int)caller();
}

编译并反汇编：

gcc -O0 -fno-omit-frame-pointer -g -o call call.c
objdump -d -M intel call | sed -n '/<caller>:/,/^$/p'
objdump -d -M intel call | sed -n '/<add>:/,/^$/p'

在 caller 中找：

  • mov edi,0x7、mov esi,0x5：参数放入寄存器；
  • call add：调用；
  • add rax,0x1：使用返回值；
  • leave、ret：返回。

在 add 中找：

  • 函数序言；
  • 参数如何被使用；
  • 返回值是否在 rax；
  • ret 如何返回。

如果装了 gdb，可以单步执行并在 add 入口查看：

(gdb) break add
(gdb) run
(gdb) info registers rip rsp rbp rdi rsi
(gdb) x/4gx $rsp
(gdb) stepi

重点确认：rsp 指向的栈顶是不是返回地址，rdi/rsi 是不是 7 和 5。

4.3 第三步：排序数据与随机数据的分支对比

下面是一份完整可运行的 C 基准程序，它依次做这几件事：

  1. 生成随机数组；
  2. 复制并排序一份；
  3. 对同一段带条件分支的求和逻辑，分别用随机数据和排序数据重复执行；
  4. 输出耗时和校验和。

创建 branch_bench.c：

#define _POSIX_C_SOURCE 200809L
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <string.h>
#include <time.h>

#define N 32768
#define PASSES 2000

static int cmp_int(const void *pa, const void *pb) {
    int a = *(const int *)pa;
    int b = *(const int *)pb;
    return (a > b) - (a < b);
}

__attribute__((noinline))
static uint64_t sum_branch(const int *a, size_t n) {
    uint64_t s = 0;
    for (size_t i = 0; i < n; ++i) {
        if (a[i] >= 128) {
            s += (uint64_t)a[i];
        }
    }
    return s;
}

static double now_sec(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (double)ts.tv_sec + (double)ts.tv_nsec / 1e9;
}

int main(int argc, char **argv) {
    int use_sorted = (argc > 1 && strcmp(argv[1], "sorted") == 0);
    int *random_data = malloc(N * sizeof(*random_data));
    int *sorted_data = malloc(N * sizeof(*sorted_data));
    if (!random_data || !sorted_data) {
        perror("malloc");
        return 1;
    }

    srand(42);
    for (size_t i = 0; i < N; ++i) {
        random_data[i] = rand() & 255;
    }
    memcpy(sorted_data, random_data, N * sizeof(*random_data));
    qsort(sorted_data, N, sizeof(*sorted_data), cmp_int);

    const int *data = use_sorted ? sorted_data : random_data;
    uint64_t acc = 0;

    acc += sum_branch(data, N);

    double t0 = now_sec();
    for (int p = 0; p < PASSES; ++p) {
        __asm__ volatile("" ::: "memory");
        acc += sum_branch(data, N);
    }
    double t1 = now_sec();

    volatile uint64_t sink = acc;
    (void)sink;

    printf("%-6s N=%d PASSES=%d time=%.3f s checksum=%llu\n",
           use_sorted ? "sorted" : "random",
           N, PASSES, t1 - t0,
           (unsigned long long)acc);

    free(random_data);
    free(sorted_data);
    return 0;
}

编译。这里使用 GCC 选项尽量阻止编译器把条件分支转换成 cmov 或自动向量化：

gcc -std=c11 -O2 -g -fno-tree-vectorize -fno-if-conversion -fno-if-conversion2 -o branch_bench branch_bench.c

说明：

  • -O2：常用优化级别；
  • -fno-tree-vectorize：关闭自动向量化；
  • -fno-if-conversion、-fno-if-conversion2：尽量阻止把 if 转成无分支的 cmov；
  • 这些是 GCC 选项。不同编译器或版本可能不支持，若报错可去掉不支持的选项，但必须用 objdump 确认循环中仍有条件跳转。

运行：

./branch_bench random
./branch_bench sorted

为了减少调度抖动，可以绑定到一个 CPU 核心，并重复几次：

taskset -c 0 ./branch_bench random
taskset -c 0 ./branch_bench sorted
taskset -c 0 ./branch_bench random
taskset -c 0 ./branch_bench sorted

建议每种模式跑 3–5 次，记录时间，取中位数。不要只跑一次就下结论。

4.4 第四步：确认机器码里真的有分支

先确认 sum_branch 中没有被优化成 cmov：

objdump -d -M intel branch_bench | sed -n '/<sum_branch>:/,/^$/p'

你希望看到类似：

cmp    DWORD PTR [rdi+rax*4],0x7f
jle    ...

或者：

cmp    ...
jl     ...

如果看到的是 cmov，说明编译器已经把它变成条件传送，排序前后可能没有明显差异。这时可以：

  1. 检查编译选项是否生效；
  2. 换一个 GCC 版本；
  3. 接受这个结果，并把它作为“源码分支不等于机器分支”的例证。

4.5 第五步：用 perf stat 看分支预测失败

如果系统允许使用 perf，运行：

perf stat -e cycles,instructions,branches,branch-misses -r 3 -- taskset -c 0 ./branch_bench random
perf stat -e cycles,instructions,branches,branch-misses -r 3 -- taskset -c 0 ./branch_bench sorted

重点关注：

  • branches：执行了多少条分支；
  • branch-misses：其中有多少次预测失败；
  • cycles、instructions：周期数和指令数；
  • branch-misses / branches：分支失败率。

典型预期是：

  • random 的 branch-misses 明显更多；
  • sorted 的 branch-misses 更少；
  • 如果编译器消除了分支，两者可能接近。

如果 perf 提示权限不足，可以尝试：

sudo sysctl kernel.perf_event_paranoid

或者在有权限的开发机上完成实验。不要为了实验随意修改生产机器内核参数。

4.6 第六步：记录结论

建议在实验笔记中写清楚：

项目 记录
CPU 型号 lscpu 输出
GCC 版本 gcc --version
编译选项 完整命令
random 中位耗时 3–5 次结果
sorted 中位耗时 3–5 次结果
random 分支失败率 perf stat 结果
sorted 分支失败率 perf stat 结果
汇编中是否有条件跳转 objdump 结果
结论 是否支持“可预测分支更快”

然后回答三个问题：

  1. 排序后变快，是因为指令数变少了吗？
  2. 如果不是，那是 CPU 的哪一部分在起作用？
  3. 如果业务只处理一次数据，排序还值得吗？

完成本实践后，检查自己是否能做到：

5. 自测题

题 1：程序计数器与函数调用

请解释：

  1. 程序计数器保存什么？
  2. 执行 call 时，返回地址被放在哪里？
  3. 执行 ret 时，CPU 如何知道回到哪里？
  4. 栈帧里通常包含哪些内容？

参考答案：

  1. 程序计数器保存下一条要执行指令的地址；在 x86-64 中叫 rip。顺序执行时它指向下一条指令，遇到跳转、调用、返回、中断时被修改。
  2. call 会把 call 后面那条指令的地址（返回地址）压入栈，然后把 rip 设置为被调用函数的入口地址。
  3. ret 从栈顶弹出返回地址，写入 rip，从而回到调用者继续执行。
  4. 典型栈帧包括：返回地址、保存的调用者帧指针 rbp、局部变量、临时空间、保存的被调用者保存寄存器、栈对齐填充，以及可能通过栈传递的参数。具体布局取决于 ABI 和编译器。

题 2：主频与性能

两款 CPU 都执行同一套 x86-64 指令，A 的主频是 3.0 GHz，B 的主频是 2.5 GHz。为什么 B 可能运行同一个程序更快？请至少说出三个原因。

参考答案：

  • B 的微架构 IPC 更高：每周期能执行更多指令，或流水线/执行单元更宽；
  • B 的缓存更大、命中率更高，减少了内存等待；
  • B 的分支预测器更准，流水线冲刷更少；
  • A 可能存在功耗/散热降频，实际频率达不到标称值；
  • A 的乱序执行窗口更小，难以隐藏延迟；
  • 程序可能受内存带宽、I/O、锁竞争限制，主频不是瓶颈。

核心公式是：运行时间 ≈ 指令数 × CPI ÷ 主频。主频只是其中一个因素。

题 3：排序数据与随机数据

在“排序后数据 vs 随机数据”的分支实验中，为什么排序后可能更快？为什么有时候两者又没有明显差异？做这个实验时应该怎样验证？

参考答案：

排序后，if (data[i] >= 128) 的条件模式变成“前面几乎全假、后面几乎全真”，分支预测器容易学习，预测失败少；随机数据的条件模式无规律，预测失败多，流水线冲刷成本高，所以更慢。

两者没有明显差异，可能是因为编译器把条件分支优化成了 cmov、进行了向量化，或者瓶颈不在分支而在内存、循环开销等。验证方法：

  1. 用 objdump -d -M intel 查看 sum_branch 中是否还有条件跳转；
  2. 用 perf stat -e branches,branch-misses 对比两种数据的失败率；
  3. 多种编译选项、多次运行，取中位数；
  4. 注意排序本身的成本，不能只看循环阶段。

7. 一页总结

CPU 执行的核心链路：
PC 指向指令 -> 取指 -> 译码 -> 读寄存器/算地址 -> 执行/访存 -> 写回

寄存器：
  数量少、速度快；保存操作数、指针、临时结果、栈指针、返回地址等。

程序计数器：
  保存下一条指令地址；jmp/call/ret/中断都会改变它。

指令与数据通路：
  加载、计算、比较、分支、存储；数据在寄存器、ALU、缓存/内存之间流动。

流水线：
  多条指令重叠执行；有数据冒险、控制冒险、结构冒险；分支预测失败会冲刷。

分支预测：
  利用历史预测跳转方向；随机分支难预测，排序后分支模式更稳定。

乱序执行：
  不改变软件可见结果，提前执行就绪指令；受 ROB、寄存器、队列和依赖链限制。

ISA vs 微架构：
  ISA 是软件契约；微架构是硬件实现。同一 ISA 性能可以差很多。

函数调用：
  参数入寄存器 -> call 压返回地址 -> 被调用者建栈帧 -> 返回值放 rax
  -> ret 弹出返回地址 -> 调用者继续。

性能观：
  时间 ≈ 指令数 × CPI ÷ 主频；主频不是唯一因素，优化必须实测。

下一课可以继续沿着“二进制 -> CPU 执行 -> 缓存/存储层次 -> 操作系统”的路径推进。学习本课时，最重要的不是记住某个汇编片段，而是养成一个习惯：看到性能现象时，先问“机器实际在执行什么”，再用工具验证。
