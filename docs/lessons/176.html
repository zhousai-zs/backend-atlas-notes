第 176/208 课：短期状态与长期记忆

序号 176/208 · id l-memory · 领域 L · 阶段 3 · 难度 进阶 · 子类 上下文与持久运行 前置：l-context 节点摘要：对话历史、任务状态和长期知识是三类对象，正确性、权限和删除要求不同，不能塞进同一份无限增长的聊天记录。

导读

第 175 课解决窗口里放什么。本课解决窗口之外还要存什么：会话怎么续，任务走到哪一步，哪些事实可以跨任务复用——以及这些事实什么时候必须消失。

教学假设：一个运维助手要记住不同用户各自的副本延迟和配置。这是为讲解隔离、TTL 与撤销设计的场景，不代表腾讯或微信的内部配置中心。实践用 SQLite 分表，不用向量库，也不把词法匹配写成语义检索或授权。

学习目标

  1. 说明会话、任务状态与长期知识为何要分表或分命名空间。
  2. 独立完成实践：两个用户用相同查询不能召回对方记录；过期、撤销、删除的事实不再进入上下文。
  3. 用负例确认：每条被引用事实都有来源和有效期，模型推断与已确认事实可区分；恢复任务时不能把历史推断当成已完成步骤。

为什么后端要懂

节点给出的理由是「为长任务建立可靠连续性，同时减少陈旧信息、跨用户污染和无法删除的历史」。记忆如果只是把上次模型说过的话再写回去，连续性会变成串租户、过期配置和删不掉的隐私数据。

核心知识点

1. 三类对象分表存放

直觉。 聊天记录帮你把话说下去，任务状态记录哪一步已经执行，长期知识是可以跨任务引用的事实。它们不是同一张表的三个字段。

原理。 实践建立 sessions、tasks、facts 三张表。会话只记谁在聊；任务行记 state 和已经执行的 step（例如 retrieved_logs）；事实行记文本、来源、类型、有效期和撤销/删除标记。2026-11-15 23:52:58（UTC+8）抓取的 Sessions（Last-Modified 2026-11-10 16:04:28，UTC+8）把会话定义为对话历史存储；同日 Persistence（Last-Modified 2026-11-15 03:43:40，UTC+8）则把 checkpointer 与长期 store 分开。本课先在业务表上把这三类分开，不把 SDK 会话当成任务事务。

2. 租户隔离发生在检索时，而不是“写入时碰巧分开”

直觉。 两个用户问同一句“staging replica lag”，不能因为文本像就共用一条记忆。

原理。 recall(user_id, query) 先按 user_id 过滤，再做简单词法匹配。Alice 命中 f1（以及一条也提到 lag 的推断 f-inf），Bob 只命中 f2；f1 不会出现在 Bob 的结果里。向量相似度在这里故意没有出场——节点把“用向量相似度代替授权”列为陷阱。

3. 来源、TTL、置信状态

直觉。 一条能被引用的事实，必须说得清从哪来、何时失效、是不是已确认。

原理。 每条命中都带 source 与 expires_at；kind 只能是 confirmed 或 inference，并且 confirmed 标志与 kind 一致。Alice 的推断“the lag is probably caused by a lock”来源是 model:session-s-alice，与 runbook 里已确认的 40ms 延迟分开展示。

4. 写入、合并与冲突

直觉。 长期记忆的写入是一次带来源的登记，不是把模型刚说的话默认为事实。

原理。 实践不做复杂的冲突合并，但要求新事实必须声明 kind 与 source。若把上次模型结论无来源地永久写入，就会违反节点陷阱。冲突处理可以在后续课扩展为按时间或按来源优先级合并；本课先保证“没有来源的推断进不了 confirmed”。

5. 检索时重新做权限和有效期校验

直觉。 写入时合法，不等于召回时仍然合法。

原理。 recall 每次都丢弃 deleted=1、revoked=1 以及 expires_at <= now 的行。Alice 过期的 canary 比例、已撤销的 pager 号码，以及 Carol 删除后的 wifi 密码，都不会再进入上下文。只删“主视图”却保留检索行，是节点点名的漏洞；本课的删除是给事实行打删除标记，检索直接跳过。

6. 任务恢复读执行状态，不读历史推断

直觉。 “模型曾经猜过锁竞争”不是“检索步骤已经做完”。

原理。 resume_task 返回 step=retrieved_logs、state=running。断言明确禁止把推断文本当成 step。恢复会话更不等于恢复后台事务，这一点会在第 177 课展开。

常见误区

用向量相似度代替授权，相似问题会把别人的事实召回来。只删除主表而保留检索索引，用户以为删掉的数据仍会被搜到。把上次模型生成的结论无来源地写入事实库，推断会在后续任务里变成“已确认”。这三条都是节点陷阱，实践分别用 user_id 过滤、删除标记和 kind 字段对应。

设计权衡

长期记忆改善连续性，但增加失效、隐私和维护成本。对一次性任务，短期会话加可靠任务状态可能已经足够。本课把事实表做小，是为了把隔离和 TTL 变成断言，而不是演示一套生产级记忆中台。

动手实践

实践包是 practice176.tar.gz：

tmp_dir=$(mktemp -d)
tar -xzf practice176.tar.gz -C "$tmp_dir"
cd "$tmp_dir/practice176"

源码与文档阅读

2026-11-15（UTC+8）抓取 Agents SDK Sessions（23:52:58，Last-Modified 2026-11-10 16:04:28）与 LangGraph Persistence（23:52:59，Last-Modified 2026-11-15 03:43:40）。前者管对话历史，后者把 checkpointer 和 store 分开。本实践用三张业务表对应这三类对象，不把任一篇文档的 API 直接当成“已经实现了官方记忆产品”。

自测题

1. 两个用户问了同一句话，为什么不能靠“文本很像”共用记忆？

答：隔离键是 user_id，不是文本相似度。本次相同查询下 Alice 与 Bob 的命中集合不相交。用向量相似度代替授权，会把别人的事实召回来。

2. 用户要求删除数据之后，为什么还必须在检索路径上拦截？

答：只改主视图、不改检索行，删除就是假的。本次对 Carol 做 deleted=1 后，再按她的身份检索 wifi 密码得到空列表。

3. 为什么不能把“大概是锁导致的延迟”写成已完成的任务步骤？

答：那是 kind=inference 的事实，不是执行器做过的动作。本次恢复读取的是 step=retrieved_logs，明确与那条推断文本区分。

推荐资源

  • Sessions · 跨轮会话存储：核对会话历史与业务任务存储的区别。
  • Persistence · Checkpointer 与 Store：对照框架里短期检查点与长期存储的分工。

本课小结

记忆要分会话、任务状态和长期事实；召回时重新检查租户、TTL、撤销和删除；推断与确认必须分栏。本课用 SQLite 验证了隔离与失效，没有使用向量库或托管会话。下一课是第 177 课 l-durable（持久状态与任务恢复）。
