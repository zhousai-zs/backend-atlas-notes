导读

一个快递的比喻

想象一个包裹从仓库发往收件人，中间要经过多个中转站。

  • 快递单号：包裹每到一站，扫描一次，就留下一条“某站、某时刻、经手人”的记录。只要单号一致，事后就能把分散在各个中转站的记录按顺序串成一条完整轨迹。这就是 trace（追踪） 的直觉：用同一个标识把一次请求经过的所有服务、所有 span 关联起来。
  • 随件附言：比如“易碎”“请放前台”“工作日送达”。它跟着包裹走，每一站都能看到，也会继续往下一站传。这就是 baggage 的直觉：一组随上下文传播的键值对。正因为它每一站都能看到，所以绝不能写银行卡密码、身份证号、令牌这类敏感信息。
  • 派送截止时间：包裹上写着“请在周五 18:00 前送达”。每一站都能看到剩余时间，若已经来不及，就不必再安排后续中转。这就是 deadline（截止时间） 的直觉：它随请求传播，让下游知道“还有多少时间可用”，并在超时或取消时停止工作。

接上前两课

前面已经学过两件事：

  1. 截止时间（f-deadline）：调用方设置一个 deadline，被调用方读取剩余时间；一旦超时或取消，就应停止无意义的工作。
  2. TLS（e-tls）：它解决传输加密和对端身份可信的问题，让“我连的是谁”有基本保障。

但这两件事都留下同一个问题：这些信息怎样沿着调用链继续往下传？ 网关知道请求的 deadline，发布服务知道吗？发布服务再调审核服务时，审核服务知道吗？如果中间经过线程池、异步队列、协程切换，信息还在吗？

本课要讲的，就是“请求上下文（Context）”如何显式携带 trace、baggage、deadline 和身份信息，跨过函数、线程、进程和协议的边界，并且不串请求。

教学时间线：一次“发布图文”的排障事故

以下场景为教学假设。

  1. 作者在后台点击“发布图文”，请求先到网关。网关生成或接收一个 trace 标识，并设置本次请求的 deadline，然后调用发布服务。
  2. 发布服务校验参数、落库草稿，再调用审核服务；审核服务可能还要调用内容安全能力或存储服务。
  3. 发布服务同时可能调用评论/阅读数服务做初始化，调用消息推送通知关注者。
  4. 为了不阻塞主线程，发布服务把“写操作日志”“发通知”等任务提交到线程池，线程池里的任务需要知道“我属于哪一个请求”。

事故版本是这样的：代码用一个全局变量（或进程级单例）保存 trace_id，线程池任务启动时直接读这个全局变量。

  • 高并发下，A 请求刚把 trace_id 写成 A-001，线程被调度去处理 B 请求，全局变量被改成 B-002；A 的异步任务随后读到的却是 B-002。
  • 于是 A 请求的日志里出现了 B 的 trace 标识，排障时按 A-001 过滤，发现链路缺了一段；按 B-002 过滤，又混进了不属于它的记录。
  • 更糟的是，deadline 也没传进线程池：上游网关在 800ms 后已经超时返回，线程池里的任务仍在慢慢调用下游，占用连接和 CPU。
  • 如果再把“用户身份”也从全局变量里读，异步任务甚至可能拿着另一个用户的身份去访问数据，形成越权风险。

错误做法与正确做法对照

场景 错误做法 正确做法
在线程池里取 trace 读全局变量或“当前线程”的隐式状态 在提交任务时把 Context 作为参数显式传入，任务内部从该 Context 读取
跨服务传递 trace 只在本服务日志里打印一个自造 ID，不放进请求头 按所选传播规范把上下文注入跨进程请求（如 HTTP 头），对端再提取；具体头名以文档版本为准
传递截止时间 下游重新给一个很长的默认超时 从上游 Context 读取剩余时间，据此设置下游调用 deadline；已超时就不要再发起
传递用户身份 把完整令牌、手机号塞进 baggage baggage 只放非敏感的、可跨服务可见的少量键值；身份凭据走专门的认证通道并校验
信任外部字段 直接把外部传入的 trace_id 或“用户 ID”当授权依据 外部字段只用于观测和关联；授权必须由服务端基于可信凭据重新判定
记录日志 每条日志各自拼字符串，字段命名不统一 统一从 Context 取 trace 标识等字段，结构化输出，保证可过滤、可关联

本课三条主线

  1. trace 与 baggage：trace 让一次请求的调用链可关联；baggage 让少量业务键值随链路传播，但必须守住敏感数据边界。
  2. deadline 与取消：截止时间要沿调用链传下去，下游要能读取剩余时间，并在超时或取消时及时停止工作。
  3. 身份信息与敏感数据边界：身份信息可以随上下文传递，但“传过来”不等于“可信”，更不能把外部传入的字段直接当授权依据。

这三条主线共同指向一个结论：上下文应当是显式的、有可信来源、有生命周期的，而不是散落在全局变量里的隐式状态。

学习目标

学完本课，你应当能够：

  1. 能解释 trace 与 baggage：说清 trace 解决“同一次请求的记录如何串起来”，baggage 解决“少量键值如何随链路传播”，以及二者在敏感数据上的不同风险。
  2. 能独立完成：为跨线程 RPC 传播 trace 和 deadline，验证并发请求互不覆盖。 也就是在提交异步任务、发起下游 RPC 时显式携带上下文，并用并发测试证明 A 请求不会读到 B 请求的 trace 或 deadline。
  3. 解释 OpenTelemetry 中 Context 的作用：它用于跨 API 边界和逻辑执行单元携带值；Propagation 负责把上下文注入跨进程请求并在对端提取（具体 API 名称以所读文档版本为准）。
  4. 说明常见传播格式的定位：默认常用的 W3C Trace Context 使用 traceparent 头，其形态为 version-traceid-parentid-flags；字段细节以所读规范版本为准。
  5. 在代码中正确使用 deadline：调用方设置，服务端读取剩余时间，超时或取消时停止后续工作，而不是继续“无主”地消耗资源。
  6. 划清身份信息与敏感数据边界：baggage 对下游可见且会跨服务传播，不放令牌和隐私数据；外部传入的 trace 或身份字段不能直接当授权依据。
  7. 让日志可关联：日志中稳定输出 trace 标识等上下文字段，能够按一次请求过滤出完整调用链。
  8. 认识显式上下文的取舍：显式传递比全局变量冗长，但依赖清晰、便于测试，也更容易在异步边界上做对。

为什么后端要懂

节点给出的理由是：

让异步和多服务链路可诊断且不串请求。

这句话看起来简单，但它同时点出了两个目标：可诊断（出了问题能查）和不串请求（A 的数据不能跑到 B 身上）。下面把它展开。

1. “当前请求”不再等于“当前线程”

在最小的同步程序里，一个请求从头到尾占用一个线程，“当前线程”差不多就是“当前请求”。但真实后端很快会引入：

  • 线程池：请求处理到一半，把任务丢给另一个线程；
  • 异步回调 / future：任务完成时才继续，执行时机与提交时机分离；
  • 协程：同一个线程上交错执行多个逻辑执行单元；
  • 消息队列：请求的后续处理甚至发生在另一个进程、另一台机器。

一旦发生这些切换，用全局变量或线程局部变量保存“当前请求的信息”就会出问题：全局变量会被并发覆盖，线程局部变量在切换到另一个线程时丢失，协程场景下还可能被同一线程上的其他任务看到。结果就是串请求或丢上下文。显式 Context 的意义，是把“这段逻辑属于哪个请求”变成调用参数的一部分，跟着逻辑执行单元走，而不是跟着碰巧执行它的线程走。

2. 多服务链路没有 trace，日志就拼不起来

一个请求经过网关、发布服务、审核服务、存储、消息推送，每个服务都会打日志。没有统一 trace 标识时，你只能靠时间戳、用户 ID、请求参数去猜哪些日志属于同一次请求。请求量一上来，日志交错，猜错几乎是必然的。

有了 trace，日志里带上同一个 trace 标识，过滤一次就能得到整条链路；再结合 span 的父子关系，还能看出时间花在哪个下游、哪次重试上。trace 不是“多打一行日志”，而是把可观测性从“按服务各看各的”变成“按请求串起来看”。

3. deadline 不传下去，上游放弃了，下游还在干活

假设网关给本次请求设置了 800ms 的 deadline，发布服务调审核服务时却不传这个信息，而是用了一个默认 5 秒超时。网关在 800ms 时已经超时返回，用户看到失败；发布服务还在等审核服务，审核服务还在调更下游，连接、线程、CPU 都被一个“已经没人要的结果”占着。

deadline 随请求传播后，下游能读到“只剩 200ms”，就可以：

  • 不再发起明显来不及的调用；
  • 给下游设置更短的超时；
  • 在收到取消信号时尽快释放资源。

这类浪费在高峰期会放大：越忙，越多“无主请求”占资源，形成恶性循环。

4. 身份信息传错边界，会造成越权

身份信息和 trace 一样会随上下文流动，但它的安全含义完全不同。trace 标识主要用于观测，泄露通常影响的是隐私和排障；身份信息一旦被错误地跨请求复用，或者把外部传入的“用户 ID”直接当成已认证身份，就可能让一个用户读到另一个用户的数据。

因此要区分两件事：

  • 传递：把“这次调用代表谁”作为上下文的一部分带下去，方便下游做审计和权限判断；
  • 信任：下游必须知道这个身份是谁认证的、经过什么边界、是否可被外部伪造。来自网关的、经过认证的内部字段，和来自公网请求、可被客户端随意填写的字段，可信度完全不同。

外部传入的 trace 或身份字段，只能用于关联和参考，不能直接当授权依据。授权必须基于可信凭据在服务端重新判定。

一个算例：20 个 span 的人工拼接有多难

假设一次“发布图文”请求扇出到 5 个下游服务，每个下游再调用 3 个更下游，整条链路约 20 个 span。每个服务只打印自己的日志，没有统一 trace 标识：

  • 5 个下游可能在同一毫秒内都有日志，时间戳无法区分谁属于 A 请求、谁属于 B 请求；
  • 同一个下游会被不同请求复用，日志里出现大量同名方法，只能靠参数猜；
  • 重试会让同一下游出现多次调用，缺少父子关系时看不出哪次是重试；
  • 线程池和异步任务让日志顺序与逻辑顺序不一致，人工排序容易出错；
  • 一旦某个服务日志缺少用户 ID，整条线索就断了。

如果 20 个 span 各自只属于一次请求，但请求量是每秒上千次，那么“人工拼接”实际上是不可完成的任务。反过来，只要每个 span 都带上同一个 trace 标识和正确的父子关系，过滤、排序、聚合都可以自动完成。这就是“可诊断”的具体含义。

逐词拆解 summary

节点摘要说：

上下文携带追踪、截止时间和身份等跨调用信息，应明确可信来源和生命周期而非依赖隐式全局变量。

  • 上下文：不是某个具体变量，而是伴随一次逻辑执行的一组信息的集合；它需要被显式创建、传递和结束。
  • 携带：上下文本身不产生业务价值，它的作用是“带着走”，让跨函数、跨线程、跨进程的调用仍能拿到同一组信息。
  • 追踪、截止时间和身份等：这是三类典型内容。追踪用于关联调用链，截止时间用于控制资源，身份用于审计和权限判断；它们的敏感级别和可信要求并不相同。
  • 跨调用信息：强调边界。信息要跨过的不只是函数调用，还包括线程池、异步回调、协程、RPC、消息队列等边界。
  • 应明确可信来源：每个字段都要能回答“谁写入的、经过哪些边界、是否可能被外部伪造”。外部传入的 trace 或身份字段不能直接当授权依据。
  • 和生命周期：上下文从哪开始、在哪结束、异步任务持有它多久、请求结束后是否还应继续使用，都要有明确约定，避免悬挂引用和跨请求复用。
  • 而非依赖隐式全局变量：全局变量看似省事，却把“当前请求”绑定到进程状态上；并发、线程池和协程会让它串请求或丢数据。显式传递虽然冗长，但依赖清晰、便于测试，也更容易在异步边界上做对。

理解了这些，后面的实践才有意义：我们要做的不是“多打几个日志字段”，而是让 trace、deadline 和身份信息在跨线程 RPC 时跟着请求走，并用并发验证证明它们不会互相覆盖。

5. 把四个问题收束成一张检查清单

以后写任何跨边界代码时，可以先问四个问题：

  1. “这段逻辑属于哪个请求？”——如果答案依赖“当前线程碰巧在处理谁”，就存在串请求风险。应当从显式传入的 Context 取 trace 标识，而不是从全局变量取。
  2. “这段逻辑还有多少时间？”——如果下游调用使用固定的长超时，而不看上游剩余时间，就可能在上游已经放弃后继续消耗资源。deadline 应随 Context 传递，并在每次发起下游调用前重新评估。
  3. “这段逻辑代表谁？”——身份信息是否已经过可信边界？它来自网关注入并校验过的字段，还是来自公网请求里可以随意填写的字段？两者不能混用。
  4. “这些字段能放到哪里？”——trace 标识可以进日志和传播头；deadline 可以进调用选项；身份凭据要走专门的认证通道；baggage 只放非敏感、下游可见也无妨的少量键值。

这四个问题不需要复杂工具才能回答，但它们能挡住大部分“看起来能跑、出事查不了”的上下文问题。

6. 显式上下文的代价与收益

节点给出的取舍是：

显式上下文较冗长，但依赖清晰且便于测试。

“冗长”体现在：

  • 函数签名要多一个 Context 参数，或者调用下游时要显式传入传播信息；
  • 线程池任务、异步回调、定时任务在提交时都要把 Context 一起带走；
  • 代码评审时要多看一眼“这个字段是从哪来的”，不能靠“全局里应该有人设置过”。

“依赖清晰”体现在：

  • 读代码时能顺着参数看到上下文从哪里进入、在哪里被使用；
  • 不需要猜测某个全局变量在某个时刻被谁改过；
  • 异步任务的行为不依赖它碰巧运行在哪个线程上。

“便于测试”体现在：

  • 可以构造一个带有指定 trace 标识和 deadline 的 Context，直接传给被测函数；
  • 可以并发提交多个带不同 Context 的任务，断言它们互不覆盖；
  • 可以模拟“剩余时间已经不足”的 Context，验证代码是否正确放弃下游调用。

反过来，隐式全局变量在单线程小脚本里确实省事，但一旦进入线程池、协程和多服务链路，省下的参数会以排障成本和越权风险的形式还回来。对后端工程师来说，显式上下文是更值得长期维护的选择。

把上面这些串起来看：异步和并发让“当前线程”不再可靠，多服务让日志必须靠 trace 关联，deadline 决定资源是否被浪费，身份边界决定是否越权；而显式 Context 正是把这些信息从“碰巧存在的全局状态”变成“可传递、可验证、可结束的请求属性”的机制。这就是本课要建立的直觉。

核心概念

在通用内容后台中，一次「打开图文详情」可能经过网关、图文服务、评论服务、计数服务等多级调用。为了在日志、指标和故障排查中把同一次用户请求串起来，也为了让每一跳都知道还剩多少时间、当前是谁在调用，我们需要请求上下文（request context）及其跨进程传播。下面以教学假设的公众号后台为例，说明 trace、baggage、deadline 与身份边界。

教学假设：文中网关、图文发布、评论/阅读数、消息推送等场景只用于说明通用后台模式，不代表任何公司内部实现。

1. trace与baggage

trace、span 与父子关系。 一次完整的请求链路称为一个 trace；trace 内的每个工作单元称为 span。每个 trace 有全局标识 trace_id，每个 span 有自己的 span_id，并记录 parent_span_id 指向直接上游。多个 span 通过相同的 trace_id 和父子关系组成调用树。

trace_id = 4bf92f3577b34da6a3ce929d0e0e4736
└─ span A  gateway              (parent = 无)
   ├─ span B  article-api       (parent = A)
   │  └─ span C  article-db     (parent = B)
   └─ span D  comment-rpc       (parent = A)
      └─ span E  comment-cache  (parent = D)

排查「某篇图文详情为什么慢」时，可以用 trace_id 找到整棵树，再用 span_id / parent_span_id 看清时间花在哪一跳。日志中至少带 trace_id 与当前 span_id，需要时再带 parent_span_id，不要把整棵树都塞进每条日志。

进程内 Context 与跨进程 Propagation。 进程内 Context 解决「当前这次执行到底属于哪个请求」：在线程、协程、异步回调之间传递 trace 信息和 baggage。跨进程 Propagation 解决「把哪些上下文写进网络请求，又在对端还原」：发送方 inject（注入）到 HTTP 头或 RPC metadata，接收方 extract（提取）后建立本进程的 Context。两者不是一回事：Context 是内存中的执行作用域，Propagation 是线协议上的序列化与还原。

W3C Trace Context。 常用默认传播格式是 W3C Trace Context，核心是 traceparent 头。一个常见示例：

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01

按常见格式拆解：

段 示例值 含义
version 00 协议版本；不同版本的处理规则以所读 W3C 文档为准
trace-id 4bf92f3577b34da6a3ce929d0e0e4736 32 个十六进制字符，标识整条 trace
parent-id / span-id 00f067aa0ba902b7 16 个十六进制字符，标识当前调用方的 span
trace-flags 01 采样等标志；具体位含义以所读文档版本为准

接收方应校验长度、字符集和版本；无法识别时按团队约定决定拒绝、丢弃还是新建 trace。不要把 traceparent 当作可信身份或权限凭据，它只用于关联调用链。

baggage。 Baggage 是随上下文一起传播的键值对，通常放非敏感的业务标签，例如教学假设中的 tenant=t-42、experiment=detail_v2、channel=oa。它的关键特点是：会跨服务传播，并且下游可以读取；它可能被中间件、日志、APM 记录。因此绝不能把访问令牌、会话 Cookie、手机号、身份证号等敏感数据放进去。Baggage 的编码、大小限制和是否允许修改，以所读 OpenTelemetry / W3C Baggage 文档及团队规范为准。

trace 与 baggage 对照。

维度 trace（traceparent 等） baggage
主要目的 串联调用链、定位耗时与错误 携带非敏感业务标签
核心内容 trace_id、span_id、采样标志 业务键值对，如租户、实验组、渠道
是否描述调用树 是，配合 parent span 形成树 否，只是伴随传播的标签
下游可见性 下游用于继续建 span 下游可读取，也可能继续传下去
安全定位 关联信息，不是授权凭据 不可信输入，不能放秘密或隐私
常见载体 HTTP traceparent、RPC metadata HTTP baggage、RPC metadata（以版本为准）

最小可运行示例。 下面的代码只用 Python 标准库 contextvars，演示进程内 Context、父子 span、inject/extract 以及 baggage 传播。

from __future__ import annotations

from contextlib import contextmanager
from contextvars import ContextVar
from dataclasses import dataclass, field
from typing import Iterator, Mapping
import secrets


@dataclass(frozen=True)
class Ctx:
    trace_id: str
    span_id: str
    parent_span_id: str | None = None
    baggage: Mapping[str, str] = field(default_factory=dict)


current: ContextVar[Ctx | None] = ContextVar("ctx", default=None)


@contextmanager
def use(ctx: Ctx) -> Iterator[Ctx]:
    token = current.set(ctx)
    try:
        yield ctx
    finally:
        current.reset(token)


def start(parent: Ctx | None = None, baggage: Mapping[str, str] | None = None) -> Ctx:
    parent = current.get() if parent is None else parent
    return Ctx(
        trace_id=parent.trace_id if parent else secrets.token_hex(16),
        span_id=secrets.token_hex(8),
        parent_span_id=parent.span_id if parent else None,
        baggage=dict(parent.baggage) if parent else dict(baggage or {}),
    )


def inject(ctx: Ctx) -> dict[str, str]:
    headers = {"traceparent": f"00-{ctx.trace_id}-{ctx.span_id}-01"}
    if ctx.baggage:
        headers["baggage"] = ",".join(f"{k}={v}" for k, v in ctx.baggage.items())
    return headers


def extract(headers: Mapping[str, str]) -> Ctx:
    version, trace_id, span_id, _ = headers["traceparent"].split("-")
    if version != "00" or len(trace_id) != 32 or len(span_id) != 16:
        raise ValueError("unsupported traceparent")
    baggage = {}
    for item in headers.get("baggage", "").split(","):
        if item.strip():
            key, _, value = item.strip().partition("=")
            baggage[key] = value
    return Ctx(trace_id, span_id, None, baggage)


def show(label: str, ctx: Ctx) -> None:
    print(f"{label:8s} trace={ctx.trace_id[:8]} span={ctx.span_id} "
          f"parent={ctx.parent_span_id} baggage={dict(ctx.baggage)}")


root = start(baggage={"tenant": "t-42", "channel": "oa"})
show("root", root)
with use(root):
    gateway = start()
    show("gateway", gateway)
    with use(gateway):
        headers = inject(gateway)
        print("headers:", headers)
        with use(extract(headers)):
            article = start()
            show("article", article)

运行后可以看到 gateway 的父 span 是 root，article 的父 span 是网关传下来的 span；tenant、channel 随 baggage 到达下游。这里的 extract 只演示协议还原，生产代码还必须做长度限制、字符校验、异常处理和头过滤。

2. deadline和取消

deadline（绝对时间）与 timeout（相对时长）。 deadline 是「最晚什么时候必须完成」的绝对时间点；timeout 是「最多允许等多久」的相对时长。入口常配置相对超时，例如教学假设中网关给图文详情设 800ms；进程内应立刻换算成绝对 deadline（now + 800ms）保存在 Context 里，之后每一跳都从这个时间点算剩余，而不是每一跳重新拿到 800ms，否则链路越深总耗时越长。

概念 含义 在链路中的处理
timeout 相对时长，例如 800ms 只在入口配置；进入进程后换算为绝对 deadline
deadline 绝对时间点，例如本机单调时钟上的「现在 + 800ms」 进程内沿 Context 传递同一个上限
剩余预算 deadline - now 跨进程时传这个相对值，接收方用自己的时钟换算回本地 deadline

为什么跨进程传「剩余预算」。 两台机器的时钟不完全一致，直接传绝对时间戳会被时钟偏差放大或缩小；所以常见做法是在发出请求的那一刻计算剩余时长写进请求（gRPC 在线协议里用相对的超时值表达 deadline，具体头名与格式以所读文档版本为准），接收方收到后立即换算成本地的绝对 deadline。网络传输、序列化、排队、数据库访问都会消耗预算，因此每往下一跳，剩余值都会自然变小；若还要给本跳收尾留余量，可以在剩余时间上再减去本跳预估开销。剩余时间过小就应快速失败，而不是继续发起注定超时的子调用。

取消要向下传播。 上游用户断开、网关超时或调用方主动取消时，取消信号应沿调用链向下传：服务端停止无意义的计算，关闭数据库查询，取消下游 RPC，释放连接和线程。否则会出现「上游已经返回 504，下游还在写数据」的僵尸工作。gRPC 客户端设置的 deadline 会随请求传到服务端，服务端可读取剩余时间并在超时或取消时停止工作；具体 API 名称和可读取的字段以所读 gRPC 文档版本为准。

线程池与协程中的上下文丢失。 contextvars 的值绑定在当前线程/任务的执行上下文中。把函数提交给 ThreadPoolExecutor 时，框架不会自动把提交方的 Context 复制到工作线程，所以工作线程里的 ContextVar.get() 往往拿到默认值。需要显式用 contextvars.copy_context() 捕获当前上下文，再调用 ctx.run(fn, ...)。协程场景也要注意：asyncio.create_task 会复制创建时的上下文，但任务内的 set 不会反向写回父任务；跨任务共享可变状态应使用明确的数据结构，而不是依赖 Context 自动同步。

可运行示例。 对比直接提交与复制上下文，并演示 deadline 已过期时提前放弃。

from concurrent.futures import ThreadPoolExecutor
from contextvars import ContextVar, copy_context
from dataclasses import dataclass
from time import monotonic


@dataclass(frozen=True)
class Ctx:
    trace_id: str
    deadline: float


ctx_var: ContextVar[Ctx | None] = ContextVar("ctx", default=None)


def work(label: str) -> str:
    ctx = ctx_var.get()
    if ctx is None:
        return f"{label}: 无上下文，无法关联 trace/deadline"
    remaining = ctx.deadline - monotonic()
    if remaining <= 0:
        return f"{label}: trace={ctx.trace_id} 已过期，放弃下游调用"
    return f"{label}: trace={ctx.trace_id} 剩余={remaining:.0f}s"


def expired_job() -> str:
    ctx_var.set(Ctx("trace-expired", monotonic() - 1))
    return work("过期任务")


ctx_var.set(Ctx("trace-92", monotonic() + 2))
print(work("主线程"))

with ThreadPoolExecutor(max_workers=2) as pool:
    lost = pool.submit(work, "直接提交").result()
    carried = pool.submit(copy_context().run, work, "复制上下文").result()
    expired = pool.submit(copy_context().run, expired_job).result()

print(lost)
print(carried)
print(expired)

预期现象：直接提交 拿不到 trace-92；复制上下文 能拿到 trace_id 和剩余 deadline；过期任务 在调用下游前就返回。生产环境还要把取消信号接入 RPC/数据库客户端，并在 finally 中释放资源。

3. 身份信息与敏感数据边界

身份必须来自可信来源。 用户 ID、租户 ID、调用方服务身份不能由客户端随便写在头里。正确做法是：入口先验证令牌、会话或 mTLS 证书（例如经过前置 e-tls），验证通过后由服务端代码把身份写进 Context；下游只信任「由可信入口写入」的上下文，或通过 mTLS/服务网格再次验证调用方服务身份。教学假设：网关校验登录态后写入内部用户主键，图文服务据此判断作者权限，评论服务据此判断能否删除评论，消息推送服务据此确定消息归属。

外部请求
  │  令牌 / 外部请求头（均不可信）
  ▼
边界网关
  │  校验令牌/mTLS；剥离外部内部身份头；写入可信身份
  ▼
图文服务 ──► 评论服务 ──► 计数服务
        trace 头继续传播，仅用于关联

为什么不能直接信外部头。 常见反例是攻击者构造：

GET /api/articles/123 HTTP/1.1
Host: example.internal
x-user-id: 10001
traceparent: 00-aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa-bbbbbbbbbbbbbbbb-01

如果服务直接读取 x-user-id 当作用户身份，攻击者就能冒充 10001。因此节点 pitfalls 明确写的是：「外部传入trace或身份字段不能直接当授权依据。」 正确边界是：边界网关剥离客户端带来的内部身份头（如 x-user-id、x-tenant-id、x-internal-service 等，具体名单按团队规范），验证令牌后重新生成这些头；下游不得把原始外部值当授权依据。

trace 头可以接收，但只用于关联。 外部传入的 traceparent 可以接受，用于把外部请求接入同一条链路；但要校验格式、限制长度，必要时重新生成 trace_id 或强制采样，避免被恶意值污染日志和采样。即使接受了 trace 头，它也不能参与鉴权。baggage 同理：外部 baggage 只能作为不可信标签，入口应做白名单过滤，不能凭 role=admin 或某个租户标签直接放行。

敏感数据边界。 Baggage 会传到所有下游，可能进入访问日志、APM、消息队列和第三方系统；它的完整性和机密性不能作为安全假设。因此验收要求是「不在baggage中放令牌和隐私数据」。令牌、Cookie、API Key、密码、验证码、手机号、身份证号、精确位置、完整请求体等都不应放进去。日志关联所需的 trace 信息可以放，但日志本身也要脱敏。

数据 放进程内 Context 放跨进程 baggage 说明
trace_id / span_id / 采样标志 可以 可以，走 trace 头 仅用于关联调用链
已鉴权用户内部主键 可以，按最小权限控制 不建议 属于个人数据，下游按需读取或只传引用
租户、实验组、来源渠道 可以 可以 非敏感标签，且入口应校验来源
访问令牌、Cookie、API Key 不放 绝不 泄露后可直接冒用身份
手机号、身份证号、精确位置 不放 绝不 隐私数据，可能进入日志或第三方
is_admin=true、role=admin 不放 绝不 授权结论应在服务端实时计算
原始请求体、带查询参数的完整 URL 不放 不放 可能包含秘密参数或个人信息

验收与取舍。 两个可检查点：

  • 日志可关联完整调用链：每条关键日志至少带 trace_id（建议再带 span_id），能从入口查到下游。
  • 不在baggage中放令牌和隐私数据：代码审查和日志采样中不应出现此类值。

显式上下文较冗长，但依赖清晰且便于测试。团队需要约定哪些键允许进入 Context、哪些只在本进程使用、哪些可以跨进程传播；把规则写进基础库和网关配置，比在每个业务函数里临时拼头更可靠。对于教学假设中的评论删除场景，尤其要把「身份来自网关校验结果」和「评论归属来自数据库查询」分开，不能用一个可伪造的头同时完成身份与授权。

把身份写入上下文的推荐顺序。 实现时可以固定顺序，让「不可信输入」和「可信身份」不混在一起：

  1. 在边界完成令牌或 mTLS 校验，失败立即拒绝，不进入业务服务。
  2. 剥离客户端伪造的内部身份头；只保留允许透传的 trace 头和经白名单过滤的 baggage。
  3. 用校验结果构造身份对象并写入当前请求 Context，后续业务代码只读取这个对象。
  4. 调用下游时由基础库重新注入内部身份头，同时继续传递 trace 头与 deadline。
  5. 记录日志时只打印必要的身份标识和 trace 信息，敏感字段脱敏。

同步与异步场景的差异。 教学假设中的评论删除是同步 RPC，消息推送则可能由异步消费者触发。同步场景可以在入口建立 Context 后沿调用链传；异步场景要把已鉴权的身份、trace 信息和 deadline（或消息的过期时间）写入消息属性或任务参数，不能假设消费者线程自动拥有生产者的 Context。消息体里只放内部引用和必要标签，令牌等秘密应通过服务身份或短期凭据获取，不随消息长期保存。

场景 可信身份从哪里来 需要传播什么
HTTP 同步请求 网关校验令牌后的结果 trace、deadline、内部身份引用
服务间 RPC mTLS/服务网格验证的调用方身份，或上游可信 Context trace、deadline、租户/实验标签
异步消息/定时任务 生产者的已鉴权上下文 + 消息系统的服务身份 trace、消息过期时间、内部业务引用
外部 webhook 签名校验或令牌校验结果 新 trace（或受控关联）、处理时限

上下文对象的生命周期。 一个请求的 Context 应在入口创建、在请求结束时释放；不要在全局变量里缓存某个用户的 Context，也不要把 Context 传给无关的线程长期持有。对线程池任务，复制上下文后尽快执行；对协程任务，注意父任务取消时子任务也要收到取消信号。上下文对象应尽量小，只放标识和轻量标签，避免把大对象、数据库连接或请求体塞进去。

出错时的边界。 如果 trace 头格式非法，可以丢弃该头并新建 trace；如果身份头缺失或校验失败，应返回未认证/无权限，而不是回退到某个默认用户；如果 deadline 已过期，应在入口或下游调用前直接失败。所有回退策略都应显式记录，不要让「默认值」悄悄变成越权或无限等待。

不要把「关联」和「授权」混为一谈。 即使网关已经校验过身份，业务服务仍要针对具体资源做权限判断。例如用户 10001 已登录，不代表他有权删除别人的评论；Context 里的用户 ID 只说明「是谁」，资源归属和操作权限需要业务服务根据数据库状态判断。把两者分开，才能避免「只要能传上下文就被信任」的错误。

可观测性检查。 上线前可以确认：入口日志只记录 trace_id 与认证结果，不记录令牌；下游日志能带 trace_id/span_id 与内部身份引用；网关会覆盖客户端伪造的内部身份头；采样日志中搜索 baggage 键，确认没有令牌和隐私字段。

采样与重新生成策略。 外部 trace 头可能是旧版本、超长或被构造的。入口可以按策略选择「接受并校验」「丢弃后新建」「保留 trace_id 但更换当前 span」；如果团队要求外部请求单独成链，就重新生成 trace_id。无论哪种，采样标志只影响是否记录详细 span，不影响鉴权，也不影响 deadline。

一个请求上下文的推荐内容。 可以把上下文分成三层：

层 例子 是否跨进程
调用链标识 trace_id、span_id、采样标志 是，通常走 trace 头
请求约束 deadline、剩余预算、取消信号 是，通过 RPC/HTTP 元数据传递
业务标签与身份 租户、实验组、已鉴权用户引用 视场景而定，敏感字段不进入 baggage

三层不要互相替代：trace 不能证明身份，租户标签不能代替资源归属查询，deadline 也不能代替业务超时策略。

日志关联的边界。 「日志可关联完整调用链」不等于把所有上下文都打进日志。推荐只记录 trace_id、span_id、服务名、关键状态和脱敏后的业务标识；baggage 中的标签按白名单记录，避免把用户输入或隐私字段原样落盘。

收束。 第一，trace 负责「串起来」：用 trace_id 和父子 span 还原调用链，跨进程靠 inject/extract。第二，deadline 负责「来得及」：进程内保存绝对截止时间，跨进程传剩余预算，取消信号要向下传，线程池/协程要显式携带 Context。第三，身份和敏感数据负责「别越界」：身份只来自可信鉴权，trace 只用于关联，baggage 不放令牌和隐私数据。

  • 这里的 traceparent 只是按 W3C Trace Context 的格式拼字符串，没有实现采样标志的完整语义；生产中应使用 OpenTelemetry SDK 自带的 propagator（具体 API 以所读文档版本为准）。

常见误区与设计权衡

请求上下文（Context）的价值，不是“多打一行日志”，而是让一次请求在跨线程、跨队列、跨服务之后仍然可被解释：它从哪里来、经过了谁、还剩多少时间、为什么被取消。上下文既要携带观测信息，也可能携带调用预算、取消信号和已经过校验的内部主体信息；但它不是“什么都能装”的袋子。

以教学假设的“网关 → 图文发布服务 → 内容处理与消息推送 → 评论/阅读数服务”为例：网关负责入口校验和边界决策，后面每一跳消费已经验证过的上下文，并把自己的处理结果继续向下传递。以下场景均为教学假设，不代表任何公司的真实架构。

上下文传播通常包含两件事：进程内携带值，以及跨进程序列化与提取。OpenTelemetry 将前者描述为跨 API 边界和逻辑执行单元携带值的机制，把后者描述为 Propagation：把上下文写入 HTTP 头等载体，在对端再提取出来。常见默认是 W3C Trace Context，traceparent 的基本形状可理解为 version-traceid-parentid-flags；具体字段校验、大小写和版本兼容规则以所读文档版本为准。

教学假设中，一次“发布图文”的链路可能这样走：网关解析外部请求，创建或接续 trace，并设置总 deadline；图文发布服务写草稿后调用内容处理；内容处理成功后调用消息推送；评论或阅读数服务在另一个写路径上被调用。每增加一跳，父 span 与子 span 的关系都应保留，日志、指标和异常才能落到同一条调用链上，而不是只留下一个孤立的请求号。

下面先列出常见误区，再逐类解释它们为什么危险，以及更稳妥的替代做法。表中的“纠正”不是唯一实现，具体 API 和组件能力以所读文档版本为准。

误区 典型表现 后果与纠正
把外部传入的 trace 或身份字段直接当授权依据 网关把 trace 标识、用户标识或租户标识透传给下游，下游据此放行或判断数据归属 外部字段可能被伪造、篡改或重放；trace 只用于关联观测，身份与权限必须由可信边界完成认证和校验。pitfalls：外部传入trace或身份字段不能直接当授权依据。
用全局变量或单例保存当前请求的 trace_id 为了少传参数，在模块级维护“当前 trace_id”，处理函数随用随取 并发请求会相互覆盖，异步切换和线程复用时尤其明显；测试之间也会互相污染。应使用每次请求独立创建的上下文对象，或由框架管理的上下文机制，并明确其生命周期。
以为 threading.local 或 contextvars 会自动进入线程池任务 把任务提交给线程池后，直接读取调用线程里的上下文 新线程或复用的 worker 不保证自动继承调用方上下文，结果可能是空值、旧值或错配值。不要默认“提交即传播”；是否自动复制、如何复制，以所读运行时和框架文档版本为准，并在任务边界显式捕获和恢复需要的上下文。
把 access token、手机号放进 baggage，或把 baggage 当成业务参数通道 为了方便下游直接读取令牌、手机号、租户白名单，甚至把业务状态塞进 baggage Baggage 会随上下文跨服务传播，对下游可见，容易进入日志、调试页面和第三方系统；它不适合承载秘密和隐私数据，也不应替代明确的接口参数。纠正：不在 baggage 中放令牌和隐私数据，只保留最少、非敏感、确有跨服务需要的标记。
每一跳重新生成 trace_id，导致链路断开 每个服务入口都新建一个“请求编号”，或只在最外层日志里打一个自增号 父子关系丢失，跨服务排障只能靠时间猜测；应接续可信上游的 trace 上下文，在必要边界做校验和补全，而不是逐跳重置。若必须重新生成，应保留关联字段并在文档中说明断点。
下游使用固定超时，而不是继承剩余 deadline 上游只剩 200ms，下游仍然按固定的 3s 去调用数据库或另一个服务 上游已经放弃，下游还在占用连接和资源；gRPC 客户端设置的 deadline 会随请求传到服务端，服务端可读取剩余时间并在超时或取消时停止工作，具体 metadata 键名与 API 以所读文档版本为准。更稳妥的是基于剩余预算设置下游超时，并保留少量收尾余量。
上游取消后，下游继续写库或继续推送 收到取消信号后只停止返回响应，后台任务仍完成“最后一步” 会产生用户已离开但消息已发、请求已失败但计数已加等不一致；取消应沿调用链传递，写操作要有幂等、补偿或事务边界，异步任务应在真正执行前再次检查上下文和截止时间。
日志只打 trace_id，不打 span_id，无法还原父子关系 所有日志都带同一个请求号，但没有当前操作、父操作或调用阶段的信息 只能知道“属于同一请求”，不能知道“谁调用了谁、慢在哪一段”；应同时记录当前 span 标识和父子关系，或至少记录阶段名与上下游服务名，具体字段命名以团队规范和所读文档版本为准。

这些误区的共同点，是把“上下文可用”误认为“上下文可信”，或者把“进程内能读到”误认为“跨边界一定会传播”。前者首先是安全问题，后者是观测与可靠性问题。通用内容后台往往同时存在 HTTP 入口、消息队列、定时任务和多级 RPC，任何一处默认“自动传播”，都可能在故障时变成盲区。

一、外部字段不等于可信身份。 traceparent 这类头适合做链路关联，但它不是身份凭证；即使格式合法，也只说明“某个调用方声称自己属于某条链路”。身份字段同理：网关注入的用户标识、租户标识，只有在网关完成签名、会话或令牌校验后，才能作为内部可信主体的一部分传给下游。

下游仍应按最小权限校验资源归属，不能因为“头里有管理员标识”就跳过授权。对于评论、阅读数、消息推送这类会改变状态或影响他人的操作，尤其要把“观测关联”和“业务授权”分开：前者可以来自请求头，后者必须来自可信认证、服务端会话或内部授权服务。

二、进程内保存要明确归属。 全局变量和单例的风险不只是并发覆盖，还包括请求结束后忘记清理、后台任务复用了上一个请求的值、测试并行时相互干扰。显式上下文对象或由框架管理的上下文，能让“这个值属于哪次请求”变得清楚。

如果使用 contextvars 或线程局部存储，必须把创建、复制、清理和跨线程提交视为设计的一部分，而不是顺手使用。提交任务时，调用方应在提交点捕获当前上下文，在 worker 侧恢复它，并在任务结束后清理；至于框架是否已经替你完成这一步，以所读文档版本为准。

三、跨进程传播要保留因果链。 trace 的任务是保持因果链，不是保证业务正确。每一跳都应记录“我收到了什么、我是否接受、我生成或沿用了什么”，但不要把未经校验的外部值直接写进授权判断。对消息推送和评论/阅读数这类异步或旁路服务，尤其要区分“观测上的关联”与“业务上的命令”：消息里可以带关联标识，但消费方仍要按消息本身和业务状态做幂等与权限判断。

在 HTTP、消息队列和 RPC 之间传播时，载体可能不同：HTTP 常用头，消息系统常用消息属性，gRPC 常用 metadata。不要假设每种载体的键名和默认行为完全一致；具体键名、大小写和注入方式以所读文档版本为准。跨语言服务之间更要先确认双方使用同一套传播约定，否则会出现“每段都有 trace，但拼不起来”的情况。

四、超时与取消是上下文的一部分。 教学假设的网关到多级 RPC 链路中，入口设置总预算，后面每一跳根据剩余时间决定是否继续；这样上游放弃时，下游不会继续做无意义的工作。固定超时看似简单，但它会把“上游已经失败”的请求继续拖在系统里，尤其在下游排队严重时更明显。

继承剩余 deadline 不等于每一层都机械地减一个常数。中间服务要扣除自身处理、序列化和网络开销，并给收尾日志、补偿和响应预留余量；如果剩余时间已经不足以完成关键步骤，应尽早失败并返回可识别的超时原因。具体如何从请求中读取 deadline，以所读文档和框架版本为准。

取消不是“少返回一个响应”，而是“停止继续产生副作用”。写库、发消息、加计数都需要考虑幂等和补偿，避免半成功状态。比如发布图文已经写入草稿，但消息推送被取消时，后续重试要能识别“这次推送是否已经发生”；评论计数写入后请求超时，也不能简单再叠加一次。

五、日志要能还原调用树。 只有 trace_id 时，你能把日志串起来，却很难解释调用树；只有 span_id 时，又缺少全局关联。两者配合阶段名、服务名和结果状态，才能回答“慢在哪一跳、错在哪一跳、是谁调用了谁”。字段名和采集方式以团队规范及所读文档版本为准。

一个实用的检查方法是：从入口日志出发，能否找到每一次下游调用的父操作、子操作和结束状态；从一条错误日志出发，能否回到入口请求和受影响的业务对象。如果只能看到同一个 trace_id 却看不到父子关系，说明上下文只传播了“编号”，没有传播“结构”。

六、baggage 要克制。 Baggage 是随上下文传播的键值对，会跨服务传播且对下游可见，因此它适合放少量非敏感的传播标记，比如教学假设中的灰度分组或调用来源；不适合放令牌、手机号、完整用户资料或业务对象。字段越少，越容易审计，也越不容易在日志和调试工具中泄露。

还要注意，baggage 不是隐藏参数。把它当成跨服务的业务参数通道，会让接口契约变得不可见：调用方以为只是传了一个上下文值，下游却把它当成必需输入，最终难以测试、难以演进，也难以判断谁应该为字段的语义负责。

设计权衡

权衡 倾向 选它的条件
显式参数传递 vs 隐式 contextvars/线程局部 核心链路优先显式；横切关注点可用受控的隐式上下文。tradeoffs：显式上下文较冗长，但依赖清晰且便于测试。 选择显式：调用关系需要被单测、跨团队接口需要稳定契约、调用栈虽然深但结构明确。选择隐式：同一类横切信息需要穿过大量中间层，框架已有统一注入和清理机制，并且测试能够构造和检查完整上下文。
接受外部 trace 头 vs 在边界重新生成 可信入口接受并校验后沿用；不可信入口重新生成并保留关联。 接受外部：有可信网关能校验格式、长度、采样标志和来源，且希望与前端或上游系统打通链路。重新生成：外部来源不可控、格式混乱或存在伪造风险；此时可把经过校验的外部值作为关联属性，而不是直接作为父子关系。
baggage 多放字段 vs 最小化 默认最小化。 最小化：字段非敏感、跨服务确实需要、命名稳定、生命周期可解释，并且不会成为隐式业务契约。多放：仅在短期排障、受控环境和明确审计下考虑；不能以“下游方便”为理由放入令牌、隐私数据或会频繁变化的业务状态。
全量采样 vs 采样 常规流量采样；关键故障窗口再提高采样率。 采样：流量大、存储和查询成本敏感，且采样决策能沿链路一致传播，不会只留下半条调用链。全量：低流量关键链路、短时故障排查或必须完整审计的场景；同时要评估敏感字段进入日志和追踪系统的风险。

权衡不是“选一个永远正确的答案”，而是把代价放到能被看见的位置。显式传递会让签名和调用点变长，但阅读代码时不必猜“这个值从哪里来”；隐式机制让业务代码更短，却要求团队把生命周期、清理和跨线程复制讲清楚。二者可以组合：业务依赖显式，观测与预算等横切信息由框架携带，但组合方式必须可测试。

接受外部 trace 头能打通前后端和上下游，却把外部输入的校验责任带进边界；在边界重新生成更安全、更可控，却会失去与上游的直接关联。选择前者时，要能校验格式并限制其影响范围；选择后者时，要保留经过校验的关联信息，避免排障时从零开始。

baggage 的取舍同样不是“多放一点更方便”。每增加一个字段，就多一份跨服务可见性和泄露面，也多一条隐式契约；最小化不是教条，而是让每个字段都能回答“谁写入、谁读取、何时清理、为何必须跨服务”。如果回答不了，就不应该放进 baggage。

采样则要在“看得见”和“付得起”之间取平衡。全量采样最容易解释单次请求，但成本高、敏感数据暴露面也大；采样能控制成本，却要求采样标记在链路中一致传播，否则会出现父链路被采样、子链路没被采样，排障时只看到半条调用链。

把选择写进代码结构，而不是只写进约定。

上下文设计最容易停留在“大家都知道要传 trace”的口号里，真正落地时却依赖某个人记得复制、某个框架默认帮忙、某个中间件碰巧注入。只要这些前提有一个不成立，链路就会在故障时断开。因此，团队需要把关键动作固定到边界和抽象上：入口统一校验与接续，进程内统一创建与清理，出口统一注入，异步任务统一捕获与恢复。

这样做会增加一些样板代码，但它把隐式假设变成了可检查的结构。显式上下文较冗长，但依赖清晰且便于测试；隐式机制则适合承载那些确实横切、且框架能够保证生命周期的信息。关键不是二选一，而是不要把业务依赖藏进隐式上下文。

边界处要做三件事。

第一，判断外部输入是否可信，并完成认证、签名或会话校验；不能因为请求带了 trace 或身份字段就直接授权。第二，校验传播载体的格式和大小，拒绝异常值，避免把不可控内容原样写入日志或继续传播。第三，决定是接续外部链路还是在边界重新生成，并记录这个决定，保证后续排障时知道链路在哪里开始或断开。

这里还要区分“入口”与“可信边界”。教学假设中，网关可能是统一入口，但真正的身份校验可能由认证服务完成；在认证完成之前，下游不能把上游传来的主体字段当成已授权。若链路跨越不同信任域，边界服务应重新建立内部上下文，而不是简单透传外部所有字段。

进程内要做三件事。

第一，为每次请求创建独立的上下文对象，并明确哪些字段是请求级、哪些是进程级配置。第二，在提交线程池任务、定时任务或异步回调时，捕获需要的上下文并显式恢复；不要假设 worker 会自动继承提交线程的值。第三，在请求结束、异常退出和取消路径上清理上下文，避免复用线程时串值。

如果使用框架提供的上下文机制，应确认它的作用域和复制规则，而不是只看 API 是否方便。contextvars、线程局部存储和异步任务调度各自有边界；具体行为以所读运行时与框架文档版本为准。测试里可以构造两个并发请求，分别检查它们的 trace、deadline 和内部主体不会互相污染。

下游与异步任务要做三件事。

第一，基于剩余 deadline 计算下游超时，而不是每层写死一个更大的固定值；剩余预算不足时尽早失败。第二，把取消信号继续传给真正执行工作的层，并在产生副作用之前再次检查是否已经取消。第三，为写库、发消息、加计数设计幂等键或补偿逻辑，让“上游失败、下游半成功”可以被修复。

消息推送和评论/阅读数这类场景尤其需要这种意识。教学假设中，发布图文成功后可能触发推送，阅读数可能在另一个写路径上累加；如果上游取消而消费者继续执行，用户会看到与请求结果不一致的状态。解决方式不是简单地“不要取消”，而是让每个副作用都能被识别、重试或补偿。

日志与隐私要做三件事。

第一，日志同时保留 trace 与 span 的关联，至少能看出当前阶段和上下游关系；只打一个请求号不足以还原调用树。第二，对进入日志、baggage 和追踪系统的字段做分级，令牌、手机号等敏感信息不进入传播上下文。第三，给上下文字段设定大小和数量上限，避免把大对象或不可控输入带进每一跳。

这些动作看起来分散，实际都指向同一个原则：上下文只承载“跨边界仍然有意义、且可以被治理”的信息。观测标识用于关联，deadline 用于预算，取消用于停止工作，已校验的主体用于授权；业务参数应留在明确接口里，敏感数据应留在受控存储和授权路径里。

需要避免的“看似省事”。

  • 为了少改接口，把用户身份塞进 baggage，让下游自己取。
  • 为了日志好看，在每一跳重新生成 trace_id，导致父子关系消失。
  • 为了代码短，把当前请求放进全局单例，默认并发不会出问题。
  • 为了统一，给所有下游设置同一个固定超时，不读剩余 deadline。
  • 为了“保证成功”，上游取消后仍继续写库或发消息。
  • 为了省字段，日志只打 trace_id，不打阶段和 span 关系。

这些做法在单请求、低并发、无故障的演示里往往能工作，但在真实后台里会把问题推迟到最难的时刻暴露。上下文设计的目标不是让代码看起来更短，而是让并发、超时、取消和跨服务调用仍然可解释、可测试、可治理。

一个可复用的判断顺序。

  1. 这个字段是观测关联，还是业务契约？观测关联可以进上下文，业务契约应显式建模。
  2. 这个字段会跨服务传播吗？会传播就对下游可见，必须按可见数据治理。
  3. 这个字段是否敏感？令牌、手机号、隐私资料不进入 baggage 和日志。
  4. 这个值是否已被可信边界校验？未校验的外部 trace 或身份字段不能直接授权。
  5. 这个调用还有多少剩余预算？下游超时应基于剩余 deadline，而不是固定值。
  6. 取消后还会不会产生副作用？会，就补幂等、补偿或事务边界。
  7. 日志能否还原父子关系？至少保留 trace、span、阶段和上下游服务。
  8. 这个隐式依赖能否被测试？不能构造和检查的上下文设计，通常不可靠。

回到本课的两个验收点：日志可关联完整调用链；不在 baggage 中放令牌和隐私数据。前者要求 trace 与 span 的结构被保留，后者要求对“会传播且对下游可见”的字段保持克制。做到这两点，再叠加明确的 deadline 与取消处理，上下文才真正成为后台系统的基础设施，而不是日志里的一串编号。

自测题

题 1：线程池里串了 trace_id

题干：某服务用线程池处理下游调用。压测时发现 A 请求的日志里出现了 B 请求的 trace_id。为什么会这样？应该怎么改？

答案：常见原因是把当前请求上下文放在线程本地变量或隐式全局状态里，而线程池会复用线程；提交任务时没有把 A 的上下文随任务一起捕获，执行时读到的是该线程上一次或另一个任务留下的上下文。

修改方式是显式传递上下文：在提交任务时捕获当前 Context，在执行任务时恢复它，任务结束后清理；或者让任务对象携带上下文参数，避免依赖线程本地状态。在 Python 里就是 pool.submit(contextvars.copy_context().run, fn, ...)；practice92 的场景 1 用全局变量时 40 个并发请求里有 38 个在下游看到了别人的 trace_id，改成 copy_context 后串请求数为 0。

不同语言和框架的上下文 API 名称不同，以所读文档版本为准。关键不是记住某个函数，而是确保“捕获—传递—恢复—清理”四步都发生在正确的生命周期里。

解析：这题考的是“可信来源”和“生命周期”。上下文不是越全局越方便，而是要有明确的创建、复制、恢复和销毁边界。

日志里的 trace_id 只是表象，真正的问题是并发任务之间共享了可变状态。修复后应能用并发测试证明：每个任务的日志只包含自己的追踪标识，线程复用不会造成串扰。

教学假设场景：评论服务把“写阅读数”的任务丢进线程池，任务里直接读取当前线程的追踪上下文；高并发下线程被反复复用，于是评论区日志可能挂到另一篇图文的链路上。排查时应先看任务提交点，而不是先怀疑日志组件。

题 2：300ms deadline 被下游写死成 1s

题干：上游给网关 300ms deadline。网关耗时 20ms，业务服务本地处理 50ms 后调用存储服务。存储服务把超时写死为 1s。会出什么问题？正确做法和数值是多少？

答案：存储服务不应该重新获得 1s 的预算。到业务服务发起存储调用时，整条链路大约只剩 300 - 20 - 50 = 230ms；存储服务应继承上游 deadline，取剩余时间作为自己的上限，并在继续调用更下游时再扣除本地开销后继续传递。

如果存储调用前还有序列化、排队、连接建立等本地开销，实际可用时间应小于 230ms。正确做法是“继承剩余预算，再扣本地下游开销”，而不是“每个服务按自己的配置重新计时”。

具体 API 和“剩余时间”的读取方式以所读 gRPC 文档版本为准；不要凭记忆写字段名或 metadata 键名。

解析：写死 1s 会让下游在整条请求已经超时后继续工作，浪费资源，还可能出现“上游已取消、下游仍在写”的不一致。

deadline 应沿调用链传播，取消信号也应尽早向下传递。验收时可以构造慢存储实验：上游 300ms 超时后，业务服务和存储服务都应在预算耗尽时停止，而不是各自按本地配置继续跑满 1s。

教学假设场景：网关收到“发布图文”请求后调用发布服务，发布服务写完元数据再调用评论/阅读数服务初始化计数。若最底层把超时写死，前端早已收到超时，后台仍在补写数据，重试时就容易出现重复计数或覆盖。

题 3：请求头身份与 baggage 里的手机号

题干：某内部服务直接读取请求头 x-user-id 判断是否允许删除文章；另一个团队提议把用户手机号放进 baggage，方便下游展示。分别有什么问题？

答案：第一，外部传入的 x-user-id 不能直接当作授权依据：请求头可能被伪造、被网关错误透传，或者缺少签名与来源校验。

身份应来自可信的认证/鉴权边界，例如经过校验的会话或令牌，再由该边界把“已认证主体”写入内部上下文；x-user-id 最多作为提示，不能单独决定删除权限。

第二，手机号属于隐私数据。baggage 会跨服务传播且对下游可见，可能进入日志、监控或第三方组件，不应放入；这与本节点 acceptance 中的“不在 baggage 中放令牌和隐私数据”一致。

解析：这题同时对应 pitfalls 与 acceptance。要点不是“头部一定不能用”，而是“不能把不可信输入直接升级为授权结论”。

追踪字段、身份字段、授权结论是三类不同信息：追踪字段用于关联日志，身份字段用于标识主体，授权结论必须由可信策略计算。

下游确实需要用户信息时，可以传不敏感的稳定标识，再由下游按权限读取，并遵循最小必要原则；不要把“方便展示”当成扩大敏感数据传播范围的理由。

教学假设场景：内容后台的删除入口若只看 x-user-id，外部伪造请求头就可能越权；而把手机号塞进 baggage 后，消息推送、审计日志等下游都可能无意间记录它，排查时很难彻底清理。

本课小结

  • 上下文携带追踪、截止时间和身份等跨调用信息，应明确可信来源和生命周期，而不是依赖隐式全局变量。
  • trace 与 baggage 是两件事：trace 用于串联调用链，baggage 是随上下文传播的键值对；二者都不等于授权依据。
  • deadline 与取消要沿调用链传递；下游应读取剩余时间并在超时/取消时停止工作，而不是各自写死超时。
  • 身份信息必须来自可信边界，敏感数据要设边界；外部传入的 trace 或身份字段不能直接当授权依据。
  • acceptance 回顾：日志可关联完整调用链；不在 baggage 中放令牌和隐私数据。
  • pitfalls 回顾：外部传入 trace 或身份字段不能直接当授权依据；追踪字段可以来自外部，但只能用于观测，不能用于授权。
  • tradeoffs 回顾：显式上下文较冗长，但依赖清晰且便于测试；相比之下，隐式全局状态短期省事，长期容易产生并发串扰和不可复现问题。
  • 边界提醒：公开文档不能推断任何企业内部实现；OpenTelemetry API 名称、W3C 头部细节、gRPC metadata 键名等，以所读文档版本为准。

把这八条压缩成一句话：让每一次跨调用都带着“可追踪、可截止、可审计但不越权”的上下文，并让它的来源和生命周期在代码里看得见。
