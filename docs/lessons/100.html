摘要 MVCC保留多个版本实现一致性读取，版本可见性、锁和垃圾回收共同决定并发行为。

边界说明：本课中出现的「内容后台」「审稿中的文章」「编辑预览旧稿」「阅读数递增」「发布状态」等场景都是教学假设，用来让概念落地，不代表腾讯/微信或任何企业的内部实现。配套代码是 Python 3 标准库写的教学服务，核心是一个名为 MVCCEngine 的教学 MVCC 引擎：它用行上的版本链、提交时间戳近似的快照、行锁和一次显式的 purge()，按脚本化的交错和带阈值的计时去演示快照可见性、一致性读与当前读、长事务阻碍清理，以及「按快照里的旧值写回」造成的丢失更新。它不是 InnoDB，不是 PostgreSQL，也不是 SQLite 内核。本课没有用 sqlite3 做对照，因为 SQLite 的隔离和 WAL 快照语义与 InnoDB 不同，绝不能把某一边的现象直接说成另一边的行为。本课出现的状态、阅读数、版本条数和等待时间只来自这次教学实验。InnoDB 的多版本、一致性读、加锁读和 purge 语义，以 MySQL 8.4 官方文档为准（本文已核对，访问日期 2026-11-11）：17.3 InnoDB Multi-Versioning、17.7.2.3 Consistent Nonlocking Reads、17.7.2.4 Locking Reads，以及文档链到的 17.8.9 Purge Configuration。教学模型用提交时间戳近似文档所说的「某个时间点的快照」；InnoDB 源码里的 ReadView（活跃事务 ID 列表等字段）在上述 8.4 手册页面中并未展开，因此不把那些字段写成官方定义。也不要把 PostgreSQL 的 SI / xmin / xmax，或 SQLite 的 WAL，说成 InnoDB 的语义。

导读

一个直觉：阅览室墙上的那张照片

想象内容后台有一间阅览室，专门给编辑预览稿件。楼下放着正在改的那一版：草稿、阅读数、发布状态，随时可能被另一位同事改掉。编辑走进阅览室的时候，管理员不会让他直接站到活页旁边看——那样一改，他眼前的字就会跳。管理员做的是：在他第一次翻开这篇文章时，给当时的页面拍一张照片，钉在阅览室墙上。接下来他再看，看的都是这张照片。楼下已经把稿件发布、把阅读数改成 120 了，这张照片上却还是 draft、阅读数 100。后来进门的同事会拿到一张新拍的照片，上面已经是发布后的页面。

这张照片就是快照。楼下每次改页，不会把旧的那一版烧掉，而是把旧版沿一条链子存进地下室——这就是版本链，对应 InnoDB 文档里用 rollback segment / undo 重建旧行的办法。打扫地下室的人只能扔掉「已经没有任何墙上照片还用得着」的旧版；如果有一位编辑整个下午都坐在阅览室里不走，那张旧照片就一直要求地下室把通向它的整串旧版留下来。这就是长事务对清理的拖累。

还有一件事照片解决不了。如果这位编辑不只是看照片，而是走下楼，把手按在活页上说「我要改这一行」，活页就被锁住了。此时再想改同一行的人必须等他离开。普通的预览（一致性读）看的是照片，不加这把锁；SELECT FOR UPDATE、UPDATE、DELETE 这种当前读，看的是楼下最新已提交的那一版，并且会下手去锁。所以 MVCC 并不是「有了版本就完全不加锁」。

接上前置

  • g-transaction：事务把若干操作收成原子单元，隔离级别决定并发下能观察到什么；先读后写会丢失更新，失败之后要重试整个事务。本课不再重复「交割袋」和隔离级别对照表，而是问引擎靠什么让一个读者在别人改同一行时，仍然看到稳定的一页，以及这件事在什么时候仍然要加锁。上一课里，读已提交下两次 SELECT 可能看到 100 再看到 70，可重复读则两次都是 100——那些现象的背后，正是「快照何时建立、读的是哪一个版本」。
  • g-index：聚簇索引和二级索引决定一行怎么被找到，覆盖索引能否避免回表。本课不改索引结构，但要记住：InnoDB 的多版本信息是加在聚簇索引行上的隐藏字段，旧版本往往并不单独再存一棵 B+ 树，而是沿着 roll pointer 到 undo 里重建。教学引擎只用一条版本链来演示可见性，没有实现二级索引上的 delete-mark 与回表。把结论带回 InnoDB 时，索引那一课的访问路径和本课的版本可见性要合在一起看。

前面单独看都学过：会用事务和隔离级别解释丢失更新，也知道一行是怎么被索引找到的。本课把它们组装成「预览为什么还能看到旧稿、发布为什么不必等预览结束、阅读数为什么不能按照片上的数字加一写回、一个不提交的只读事务为什么会把旧版本堆在那里」。组装之后才会出现的问题是：每条 SELECT 都成功了，编辑看到的却是已经过时的草稿；阅读数每次都「加了一」，总数却对不上；看板为了「看最新」而加锁，结果把发布堵在门外。

和上一课的丢失更新对照一下，有助于分清「应用把旧值写回去」和「引擎在快照里给你看旧值」不是同一件事。上一课两个会话各扣 30，naive 路径先 SELECT 到 100 再写成 70，最终 70 而不是 40——那是应用层的先读后写，发生在已经提交的绝对值更新上。本课 naive 路径按快照里的 100 写回 101，期望却是 120，机制是同一类：新值在应用里用一份过时的读数算出来，再按绝对值盖回去。

不一样的是背景。上一课要强调的是：即便引擎在连接之间不脏读，先读后写仍会丢更新；本课要强调的是：即便引擎用版本链给了你一份稳定的旧照片，你也不能把照片上的数字当成写回的依据，更不能因为「可重复读看见了旧值」就以为随后的 UPDATE 会自动被拒绝。InnoDB 文档允许 DML 作用在快照之后才提交的行上，教学引擎按这一条得到了静默的 101。上一课 PostgreSQL 可重复读路径上的中止与整段重试，到这里不能直接拿来当结论。

    RR：本事务第一次一致性读时建立快照，之后一直用这一份
    RC：每条一致性读建立一份新快照
    沿版本链找到对该快照可见的版本
    不加行锁；其他会话可以同时修改这些行
        │
        ├─► 当前读（SELECT FOR UPDATE / FOR SHARE，以及 UPDATE / DELETE）
        │      读最新已提交版本（外加本事务自己写过的行）
        │      加行锁：FOR UPDATE / UPDATE 为排它，FOR SHARE 为共享
        │      若行被未提交事务持锁，则等待对方结束，再使用最新值
        │      已经存在于自己读视图里的记录，一致性读会忽略这些行锁，
        │      继续按快照走版本链（旧版本不能被锁，要靠 undo 重建）
        │
        ├─► 写者提交
        │      新版本成为当前行，旧版本留在链上（update undo）
        │      在此之后建立的快照能看见新版本
        │      仍被某个活跃快照需要的旧版，不能被 purge 丢掉
        │
        └─► COMMIT / ROLLBACK
               释放本事务加过的行锁
               若这是最后一个还握着旧快照的事务，purge 才可以回收旧版本

  长事务（哪怕只做一致性读、迟迟不提交）：
        快照一直活着 → update undo 不能丢 → 版本链变长

正常路径看起来只是「开一个事务，SELECT 两次，或者再 UPDATE 一次」。本课真正要讲的是图上那几处分叉：快照建立的时机决定第二次一致性读还能不能看到旧稿；普通 SELECT 和 SELECT FOR UPDATE 走的不是同一条路，一个不加锁、一个要等最新并加锁；写者留下的旧版本，要等所有还可能用到它们的快照结束，才能被清理。

教学场景（教学假设）

内容后台有一篇正在审稿的文章，初始是 status=draft、views=100。灰度期间出现了几件「每条语句都成功，看到的页和数对不上」的事：

  1. 编辑 A 在可重复读下预览这篇草稿。同事 B 把文章发布，并把阅读数改成 120 后提交。A 再预览，仍看到 draft、100；新开的会话 C 已经看到 published、120。如果 A 用的是读已提交，他的第二次一致性读就会直接看到新值。
  2. 同一事务里，A 的快照读仍是旧稿，接着做一次 SELECT FOR UPDATE，却读到了最新已提交的发布稿，并且握住了行锁。A 只做快照读时，B 的 UPDATE 几乎不等待；A 做当前读并持锁 0.20 秒时，B 要明显地等。
  3. A 开了一个长事务，第一次一致性读钉住了草稿快照，之后有 50 次已提交的更新。A 仍活跃时，版本链上保留 51 个版本，purge 清不掉；A 提交后再 purge，只剩当前 1 个版本。
  4. 阅读数要从 100 累加到 120。naive 路径按快照里读到的 100 加一，写回 101，把并发的 19 次递增丢掉了。safe 路径按最新版本做 views = views + 1，最终是 120。另外，若看板预览也走加锁读，写者会被堵在门外；改回快照读后，写者不再等待。

这些数字都来自本课的 practice100，可以用 bash test.sh 再跑出来。它们证明的是教学代码的行为，不是某家生产内容库的事故报告，也不是 InnoDB 内核自己打出来的日志。

本课三条主线

  1. 快照可见性：快照决定你能看见哪一个已提交版本；可重复读在本事务第一次一致性读时建立并保持快照，读已提交则每条一致性读建立新快照。
  2. 一致性读与当前读：一致性读走版本链、不加行锁；当前读（加锁读和 UPDATE / DELETE）读最新已提交版本并加锁，必要时等待。
  3. undo、长事务和清理：写者把旧版本留在链上；还被活跃快照需要的旧版不能回收；长事务会阻碍清理，增加空间成本。

三条主线对应三个很容易分开记、合在一起才出问题的点。只记住「MVCC 可以读写并存」，可能以为预览看到的永远是最新稿，或以为有了版本就不必加锁；只记住「可重复读能避免不可重复读」，可能在同一事务里用 SELECT FOR UPDATE 时，对「为什么突然看到新值」感到意外；只记住「旧版本会清理」，可能忽略一个迟迟不提交的只读事务正在把 undo 堆起来。下面按这个顺序展开。

学习目标

学完本课，你应该能够：

  1. 能解释快照可见性（goals 原文）；
  2. 能独立完成：观察长事务下更新产生的版本与锁等待，对比事务隔离设置。（goals 原文）；
  3. 面对一篇「编辑预览时同事已经发布」的记录，指出可重复读下为什么两次快照读都是 draft、100，读已提交下第二次为什么变成 published、120，新事务为什么看到新值；
  4. 区分快照读与加锁读：同一事务里快照读仍看旧版，SELECT FOR UPDATE 看到最新已提交版并加锁；只做快照读时写者几乎不等待，当前读持锁时写者要等（本次持锁 0.20 秒，等待约 0.20 秒）；
  5. 说明长事务对版本回收的影响：50 次更新后，活跃快照下保留 51 个版本，事务结束后 purge 只剩 1 个；并能指出「按快照旧值写回」会把应是 120 的阅读数写成 101，当前读上的相对更新才能得到 120。

为什么后端要懂

节点的 why 原文是：「分析长事务、旧版本积压和读写互相影响。」拆开看，至少有三层。

预览看到旧稿，不一定是 bug。 内容后台几乎每天都有「编辑打开一篇稿、同事同时在改状态和阅读数」这种并发。可重复读下，A 第一次一致性读钉住快照之后，B 把文章发布并提交，A 再读仍是 draft、100——这正是快照在做它该做的事。新开的会话 C 看到 published、120，也不是 C「更正确」，只是 C 的快照建立得更晚。如果产品要的是「打开预览之后画面不再跳」，可重复读的这份快照就是所需的语义；如果要的是「每次刷新都看最新已发布稿」，提高隔离级别并不解决问题，应该换读已提交，或者结束当前事务再读。入职后排「两个页面数字不一样」，先问这两次读是不是同一个事务、用的是哪一级、是不是一致性读，而不是先认定其中一次读错了。

读写能不能彼此躲开，取决于你走的是哪一种读。 一致性读不加行锁，所以 A 只做快照预览时，B 的发布不必等——本次实验里等待是 0.0 秒。一旦预览改成 SELECT FOR UPDATE，或者更新阅读数时去抢同一把行锁，写者就要排队：本次持锁睡眠 0.20 秒，发布等待约 0.20 秒。文档写得很清楚：如果你先普通 SELECT 再改相关行，别的事务可以在中间把你刚读到的行改掉；计数器这类更新，不要用一致性读或共享读去取当前值再写回。实践里，A 按快照里的 100 加一写回 101，并发行了 19 次递增，本该是 120，最终却是 101。入职后写阅读数、点赞、库存，优先看新值到底是按「照片上的数字」算的，还是按「当前行上的相对更新」算的，以及看板读有没有去挣写者的锁。

一个不提交的只读事务，也会把旧版本拖住。 InnoDB 把旧版本放在 undo 里，不只是为了回滚，也是为了给一致性读重建更早的行。官方多版本一节写明：update undo 只有在「已经没有任何被赋予快照的事务，还可能用这些信息重建旧行」之后才能丢弃，并建议连只做一致性读的事务也要定期提交，否则 rollback segment 会增长，甚至撑满 undo 表空间。实践里，A 钉住草稿快照后发生 50 次已提交更新，活跃时链路保留 51 个版本，调用 purge 也清掉 0 个；A 结束后再 purge，一次收掉 50 个旧版，只剩当前行。入职后看磁盘涨、历史链表变长、查询变慢，除了写流量本身，也要查有没有会话长时间开着事务——包括那个「只是查了一眼、忘了提交」的连接。

把「单独看都像对的、合在一起才出问题」的情况列成表，入职后可以当排查清单用：

失败情况 谁先发现 若处理不当会怎样 本次实践中的对照

  • 「编辑一直看到旧稿，新会话却是新稿」，先看是不是可重复读下同一事务的一致性读，快照建立在第一次 SELECT；
  • 「发布被一个只读页面堵住」，先看那次读是不是加锁读，而不是普通的一致性读；
  • 「阅读数少加了」，先看是不是把快照里的旧值拿去绝对写回，有没有改成基于最新版的相对更新或条件更新；
  • 「undo 或历史链表一直涨」，先查有没有长时间未提交的事务，包括只做一致性读的那些。

核心知识点

1. 快照可见性

先把「看见」从「锁住」里分开。一致性读要回答的不是「现在楼下那一页写了什么」，而是「对某个时间点来说，哪一个已提交版本是可见的」。MySQL 8.4 的一致性读文档把这件事说成：InnoDB 用多版本，向一次查询出示数据库在某个时间点的快照；查询看得到在该时间点之前已经提交的改动，看不到之后或尚未提交的改动。例外是：查询看得到同一事务里更早语句自己做的改动。

快照何时建立，取决于隔离级别。同一页文档写明：在可重复读（InnoDB 默认级别）下，同一事务里的所有一致性读，都去读该事务第一次一致性读时所建立的那份快照；想要更新的快照，需要提交当前事务，然后再发新的查询。在读已提交下，事务里的每一次一致性读都会建立并读取一份新的快照。教学引擎用「当时已经发生的最后一次提交时间戳」来近似这个时间点：可重复读把这份 ReadView 留在事务上，读已提交则每次一致性读换一份。

可见性规则在教学模型里被收成一句：只看快照之前已经提交、并且尚未被快照之前的删除或覆盖所隐藏的版本；本事务自己尚未提交的改动除外。沿版本链从新往旧走，跳过别人未提交的版本，跳过快照之后才出生的版本，直到找到那个「出生不晚于快照、消失晚于快照」的节点。这是对文档「时间点之前已提交」这句话的教学近似，不是把 InnoDB 源码里的活跃事务 ID 列表重写了一遍。

实践里这条路径是这样走的。文章初始是草稿、阅读数 100。事务 A 先做一次一致性读，然后事务 B 把稿件改成 published、views=120 并提交，A 再读一次，最后新开事务 C 再读：

a = engine.begin("REPEATABLE READ")
first = engine.consistent_read(a, "articles", 1)   # draft, 100
# 事务 B 发布并提交：published, 120
second = engine.consistent_read(a, "articles", 1)  # 仍是 draft, 100
c = engine.begin("READ COMMITTED")
c_sees = engine.consistent_read(c, "articles", 1)  # published, 120

可重复读下，A 的两次读都是 draft、100，C 看到 published、120。把 A 的隔离级别换成读已提交，第一次仍是 draft、100，第二次一致性读则已经是 published、120。第二次读的「变」或「不变」，不是随机刷新，而是快照建立时机不同。

把这一组对照放到教学模型的版本链上看，会更清楚「可见」到底判的是哪两个时间戳。种子行是提交时间戳 0 的那一版；A 第一次一致性读时，库里最后一次提交仍是 0，于是 RR 快照的 view_ts=0（这也是后来 purge 结果里记下的 min_active_snapshot_ts）。B 提交发布之后，链上变成两节：

  当前：v1  trx_id=B  begin_ts=1  end_ts=空     data={published, 120}
  更早：v0  trx_id=0  begin_ts=0  end_ts=1     data={draft, 100}

A 再做一致性读时，仍拿着 view_ts=0：v1 的 begin_ts=1 晚于快照，还不可见；v0 的 begin_ts=0 不晚于快照，且 end_ts=1 晚于快照，尚未被这份快照之前的覆盖所隐藏，所以 A 看到 draft、100。C 的快照建立在 B 提交之后，view_ts=1，v1 已经出生且尚未结束，所以 C 看到 published、120。读已提交的 A 在第二次一致性读时换了一份新快照，判断方式和 C 相同，于是也看到新值。

这张图是教学模型里的提交时间戳，用来把文档「某个时间点之前已提交、之后或未提交不可见」这句话走一遍，不是 InnoDB 页里的 DB_TRX_ID 原样打印。InnoDB 重建旧行时，是顺着 DB_ROLL_PTR 到 undo 里还原，而不是在用户表里并排存着 v0、v1 两行给应用程序直接点选。但可见性要回答的问题是一样的：对这份快照而言，哪一版算「已经出生、尚未被当时的删除或覆盖藏起来」。

这里有一条和上一课 PostgreSQL 路径不同、但必须按 MySQL 文档来记的边界：快照约束的是一致性读，不一定约束后续的 DML。一致性读文档写明，快照适用于事务里的 SELECT，不一定适用于 DML；一个可重复读事务可能 UPDATE / DELETE 到别的事务刚刚提交、自己的 SELECT 还看不见的行，一旦它改了这些行，这些改动就会对本事务可见。教学引擎遵循这条已核对的规则：当前读和 UPDATE 走最新已提交版本，而不是走自己那份旧快照。不要把 PostgreSQL 可重复读里「行在本事务开始之后被别人改过则提交失败」的行为，直接说成 InnoDB 的语义。

同一页还写了一条值得单独记住的异常，本课实验没有用数字去演示，只按文档转述：如果你在一个事务里更新了某些行，随后的 SELECT 会看到这些被自己改过的行的最新版本，但对那些自己没改过的行，仍可能看到更早的版本；若此时别的会话也在改同一张表，你有可能看到一个数据库里从未作为整体存在过的组合。

文档把推进时间点的办法写得很具体：提交当前事务，然后再做一次 SELECT，或者使用 START TRANSACTION WITH CONSISTENT SNAPSHOT。想看「最新已提交」又不必结束事务时，则应改用读已提交，或改走加锁读。文档也提到一致性读越过 DROP TABLE，以及某些会重建表的 ALTER TABLE 时会失效；后一种情况下再次一致性读可能报到 ER_TABLE_DEF_CHANGED。这些边界本课教学引擎都没有实现，课文也不编造对应的实验结果。

2. 一致性读与当前读

一致性读是 InnoDB 在读已提交和可重复读下处理普通 SELECT 的默认方式。同一页文档接着写：一致性读不会在它访问的表上加锁，因此其他会话可以在这次一致性读进行的同时修改这些表。这正是「阅览室看照片、楼下仍可改活页」那一层。

当前读是另一条路。加锁读文档指出：如果你在同一事务里先查询、再插入或更新相关数据，普通 SELECT 给不了足够保护，别的事务可以更新或删除你刚刚读到的行。InnoDB 提供两种加锁读：SELECT ... FOR SHARE 对读到的行加共享锁，其他会话仍可读，但在你提交之前不能改；若这些行正被另一个未提交事务改过，你的查询会等到那个事务结束，然后使用最新值。SELECT ... FOR UPDATE 则对搜索遇到的索引记录加锁，效果和你对这些行发一条 UPDATE 相似。

文档原句还写了两件关键的事：SELECT ... FOR UPDATE 读的是最新可用数据，并在读到的每一行上加排它锁；一致性读会忽略那些已经存在于读视图中的记录上的锁——旧版本不能被锁住，它们是对内存中的行副本应用 undo 重建出来的。

所以「看最新」和「加锁」是绑在一起的。想看最新又不一定要改行，文档给的办法是改用读已提交，或者做一次加锁读（页上的例子是 SELECT * FROM t FOR SHARE）。计数器这类更新，文档明确劝你：不要用一致性读，也不要用共享锁读去取当前值，因为两个会话可能读到同一个数字；示例写法是先 SELECT ... FOR UPDATE 再加一，并随即给出更好的单句相对更新（UPDATE child_codes SET counter_field = LAST_INSERT_ID(counter_field + 1)）。加锁读只在关闭了自动提交、真正处于事务中时才有意义，锁在提交或回滚时释放。

两种加锁读的差别，决定了谁还会被放进阅览室、谁必须在楼下排队。FOR SHARE 允许其他会话继续普通地读，但不允许它们在你提交前修改这些行，也不允许另一个 FOR UPDATE 同时握住同一行；若行上已有未提交的修改，你要等到对方结束，再用最新值。FOR UPDATE 则像一条搜寻型 UPDATE 那样加排它锁：其他事务不能改这些行，不能对它们做 FOR SHARE，在某些隔离级别下连读都会被挡住。一致性读不在此列——它忽略已经存在于读视图中的那些行锁。

文档还提醒：外层语句上的加锁读，不会自动锁住子查询里那张表的行，除非子查询自己也写了 FOR SHARE 或 FOR UPDATE；NOWAIT 和 SKIP LOCKED 用来避免死等，前者遇到锁立即报错，后者把已锁的行从结果里拿掉，并注明跳过已锁行得到的是不一致视图，不适合一般事务工作。教学引擎实现了共享锁与排它锁的互斥和等待，没有实现 NOWAIT / SKIP LOCKED，也没有实现间隙锁。手册加锁读这一页没有把间隙锁、next-key lock 展开，本课不把它们写成已经核对过的定义。

把官方的计数器例子对到本课的阅读数上，路径就清楚了。文档要你保护的是「先读出一个数字、再按这个数字写回去」这一段窗口。实践里的 naive 路径正好踩进窗口：A 用一致性读看到 100，中间 19 个会话各自在最新版本上加一，行已经到了 119，A 仍按照片上的数字写回 101。safe 路径相当于文档随后给出的那条相对更新：在当前读锁住的最新行上做 views = views + 1，最终 120。FOR SHARE 在这里不够用——文档自己也说，两个会话若同时用共享读去看计数器，至少一方在随后更新时会走进死锁。

实践把同一事务里的两种读并排放在一起。A 在可重复读下先快照读到草稿 100，B 发布为 published、120 并提交之后：

snap = engine.consistent_read(a, "articles", 1)
# snap 仍是 draft, 100
cur = engine.locking_read(a, "articles", 1, mode="FOR UPDATE")
# cur 是 published, 120，并且 A 持有行锁

快照读还停在旧版，当前读已经看到最新已提交版。这不是引擎前后不一致，而是两条读路径本来就不同。

锁等待用 0.20 秒的持有来量。A 只做快照读并保持事务 0.20 秒时，B 的 UPDATE 等待 0.0 秒，不被阻塞。A 改做 SELECT FOR UPDATE 并持锁 0.20 秒时，B 的 UPDATE 等待 0.2003 秒，明显不短于持锁时间。断言并不要求这个等待精确到毫秒，只要求它跨过「几乎为零」和「接近持锁时间」这条界限：快照路径小于 0.05 秒，加锁路径不小于 0.15 秒。这就是 pitfalls 要提前打的那一针：MVCC 让一致性读可以不挡写者，但当前读仍然加锁，写者仍会等。

3. undo、长事务和清理

写者提交之后，新版本成为当前行，旧版本并不会立刻消失。InnoDB 多版本一节把旧版本信息放在 undo 表空间里的 rollback segment 中：它既用来回滚，也用来为一致性读重建更早的行。每行有隐藏字段 DB_TRX_ID（最近一次插入或更新该行的事务）、DB_ROLL_PTR（指向 undo 记录的 roll pointer）和 DB_ROW_ID。删除在内部被当成一次更新，并在行上打删除标记。

insert undo 只为回滚服务，事务一提交就可以丢；update undo 还要给一致性读用，只有当已经不存在「InnoDB 曾赋予快照、而该快照的一致性读还可能需要这些信息来重建旧行」的事务时，才能丢弃。行被 DELETE 之后，也要等到这条删除对应的 update undo 被丢弃，才会物理清除，这个操作叫 purge。

同一节建议：即使事务只做了一致性读，也应当定期提交。否则 InnoDB 不能从 update undo 里丢数据，rollback segment 可能变得过大，撑满它所在的 undo 表空间。Purge 配置一节把原因说得更直白：在可重复读这类一致性读隔离级别下，事务必须返回与读视图创建时相同的结果，因此 MVCC 必须把数据保留在 undo 里，直到所有依赖这些数据的事务结束。哪怕是只读事务，也可能让 History list length 增长。文档举的例子包括：mysqldump --single-transaction 碰上大量并发 DML，以及关闭了自动提交、执行了 SELECT 却忘了 COMMIT / ROLLBACK。

教学引擎把这条规则收成：purge() 只能丢掉「对当前所有活跃快照来说都不再需要」的旧版本；若还存在一份快照，就必须从当前版本一直保留到该快照可见的那一版，因为重建旧行要沿着整条链走。实践里，A 在只有 1 个版本时做第一次一致性读，钉住 draft、100；随后 50 次已提交更新把阅读数一路改到 150，并且稿件已发布。A 仍活跃时，版本数是 51，此时调用 purge，清掉 0 个，仍然剩余 51；A 再读，看到的还是 draft、100。A 提交后，没有活跃快照了，再 purge，一次收掉 50 个旧版，剩余 1 个，新会话读到 published、150。

long_tx = engine.begin("REPEATABLE READ")
engine.consistent_read(long_tx, "articles", 1)  # 钉住 draft, 100
# 50 次已提交更新之后：
engine.version_count("articles", 1)  # 51
engine.purge()                       # purged=0, remaining=51
engine.commit(long_tx)
engine.purge()                       # purged=50, remaining=1

这组数字要和「快照还在，旧链就不能拆」写在一起看。长事务的代价不只是自己占一个连接，而是把别人已经提交的旧版本也留在台上。

再把 insert undo 和 update undo 分开，避免把「事务一提交，undo 就该清空」记成一句笼统的话。多版本一节写明：rollback segment 里的 undo 分成 insert 和 update 两类。insert undo 只为回滚服务，事务提交后就可以丢弃；update undo 还要给一致性读重建旧行，必须等到没有任何被赋予快照的事务还可能用到它。本课 50 次更新留下的是后一类：它们改的是已有文章的状态和阅读数，不是插入后立刻可以忘掉的新行。教学引擎没有单独模拟 insert undo，实践里的 51 个版本对应的是「当前行加上一条仍可能被旧快照走一遍的更新链」。

多版本一节还有一段关于二级索引的说明，教学引擎没有实现，但读文档时不应跳过。InnoDB 的 MVCC 对待二级索引和聚簇索引并不相同：聚簇索引记录就地更新，隐藏的系统列指向 undo，旧版本从那里重建；二级索引记录没有这些隐藏列，也不就地更新。二级索引列被更新时，旧的二级索引记录会被打上删除标记、再插入新记录，删除标记最终由 purge 清掉。

若二级索引记录已被标记删除，或该页被更新的事务改过，就不能再走覆盖索引，而要回聚簇索引，检查 DB_TRX_ID，必要时再从 undo 取正确版本。第 98 课里「覆盖索引避免回表、写放大随二级索引条数上升」的数字，到了这里要补一句：在多版本仍然活着的二级索引上，覆盖路径可能会被关掉。本课实验没有测量这一条，不把任何回表次数写进 results.json。

Purge 配置一节把生产里能直接盯的信号写成了 History list length：它通常不高，但写得多或事务开得久——哪怕只是只读——都会让它涨起来。官方举的两个例子都很日常：一次带着 --single-transaction 的 mysqldump 碰上大量并发 DML，以及某个会话关了自动提交、查完却忘了提交。内容后台若有「导出当前稿库」「打开预览后去开会」这类操作，对照的就是这两类长事务，而不是必须先出现一条失败的 UPDATE。教学模型用「活跃快照的最小 view_ts」来决定能不能砍链，没有实现历史链表长度这个计数器，因此课文只引用文档的定性描述，不用教学数字去冒充 SHOW ENGINE INNODB STATUS 的输出。

把三条主线串在同一篇稿上

到这里，三条主线已经分别对照过数字。把它们按时间顺序放回同一篇 autumn-review 上，可以看出版本链、快照和锁是怎样共用一行的。下面的时间顺序是教学实验里实际发生过的交错，不是生产日志。

  1. 库里只有种子这一版：draft、100，版本数 1。编辑 A 以可重复读打开预览，第一次一致性读建立快照，view_ts=0，看到草稿。这次读不加行锁。
  2. 同事 B 把稿件改成 published、120 并提交。链上现在有两节，旧版留着给 A 的快照。A 再做一致性读，仍是 draft、100；新事务 C 看到 published、120。若 A 用的是读已提交，他的第二次一致性读会和 C 一样看到新值。到这一步，还没有人在行上加锁。
  3. 若 A 接着在同一事务里做 SELECT FOR UPDATE，他离开照片、去看楼下最新已提交的那一版，读到 published、120，并握住排它锁。此时再有人想更新这一行，就要等 A。实践里 A 持锁 0.20 秒，发布等待 0.2003 秒。若 A 始终只看照片，同样持有事务 0.20 秒，发布等待是 0.0 秒。一致性读忽略行锁，当前读才会让写者排队。
  4. 阅读数若还要继续加，不能再按照片上的 100 写回。A 若把 100+1 写成 101，中间那 19 次已经成功的递增会被盖掉，最终 101，而不是期望的 120。在当前读上对最新版做 views = views + 1，才能得到 120。这一步用的是文档所说的 DML / 当前读路径：它看最新已提交版本，并不被 A 那份旧快照挡住，但也不会自动帮你把「照片上的旧数字」改成相对更新。
  5. 若 A 一直不提交，只是把那份 draft、100 的快照握在手里，后面即使又发生 50 次已提交更新（阅读数走到 150），版本链也会留在 51。此时调用 purge，清掉 0 个。A 结束之后再 purge，一次收掉 50 个旧版，剩余 1 个，新会话看到 published、150。

五步里没有一步是「有了 MVCC 就什么都不必管」。快照解释了为什么预览还停在旧稿，当前读解释了为什么同一事务里又能看到新稿并挡住写者，purge 解释了为什么一个只读预览也能把旧版本堆到 51。下一节的误区，就是把其中一件误当成另外两件的替代品。

三条主线的收束

快照决定一致性读看见哪一版，当前读决定何时看最新并加锁，purge 决定旧版本能活多久。三件事共用同一条版本链：可见性沿着它往回走，锁加在当前行上而不是加在旧版本上，清理则必须先问还有没有快照要沿着它重建旧行。把上一小节的五步对照回三条主线：第 1、2 步是快照可见性，第 3、4 步是一致性读与当前读，第 5 步是 undo、长事务和清理。少记任何一步，都容易把「看到旧稿」「写者被堵」或「版本收不掉」当成互不相关的三件故障。

常见误区

节点的 pitfalls 原文是：「MVCC不是完全不加锁。」这件事在文档和实验里都可以直接核对，不必写成口号。

最常见的误会是：既然一致性读不加行锁，读写就不会互相等待，于是预览、报表、后台看板都可以随便写 SELECT ... FOR UPDATE，或者「为了看到最新」把所有读都改成加锁读。一致性读文档确实说，普通 SELECT 在读已提交和可重复读下默认是一致性读，不加锁，其他会话可以同时改。可一旦你写成加锁读，走的就是另一条路径：读最新已提交版本，并且加锁；行被未提交事务握着时要等待。实践里，同一把 0.20 秒的「编辑还没离开」，快照预览让发布等待 0.0 秒，加锁预览让发布等待 0.2003 秒；看板那一组同样是 0.0 秒对 0.2004 秒。读者并没有改一行字，却把写者堵在门外。

第二个误会是反过来的：既然当前读能看到最新，快照也就「没那么重要」，更新阅读数时可以先一致性读出一个数字，在应用里加一，再按绝对值写回。加锁读文档用计数器警告过这条路。实践里，A 的快照读到 100，中间 19 个会话各自按最新版本加一，行已经到了 119，A 仍把 101 写回去，最终 101 而不是 120。更值得注意的是：按 InnoDB 文档，这个 UPDATE 作为 DML 会作用在最新行上，并不会因为快照里还是 100 就被自动拒绝。教学引擎按这一条来，所以 naive 路径是静默丢失，不是序列化失败。上一课 PostgreSQL 可重复读里「行被并发更新则中止、再整段重试」的处理，不能原样搬到这里来解释 InnoDB。

第三个误会是：只读事务很安全，迟迟不提交也无所谓。官方多版本和 purge 两节都把只做一致性读的长事务算进无法丢弃 update undo 的原因里。实践里 51 降不到 1，靠的不是又一次更新，而是那个钉住草稿的长事务终于结束。内容后台里这往往看起来不像事故：预览页还开着，导出还没跑完，连接也没报错，只是 undo 在悄悄变长。

第四个误会来自把「自己改过的行」和「自己没改过的行」用同一种直觉去理解。一致性读文档提醒：事务里更早语句的改动对后续 SELECT 可见，于是你可能在一次查询里同时看到自己刚更新的新值，以及另一些行上仍属于旧快照的旧值，组合出数据库里从未作为整体出现过的状态。本课没有为这条异常单独跑一组数字，但它足以说明：不要因为「这是可重复读」就假定一次 SELECT 看到的整张表，都对应某一个曾经提交过的全局状态。尤其不要在刚 UPDATE 过若干行之后，用同一事务里的一致性读去做跨行对账，却以为自己看到的是发布那一刻的完整页面。

MVCC 减少的是一致性读对写者的阻塞，不是把锁、空间和清理从设计里取消，也不是保证你在同一事务里任意混用快照读和当前写之后，仍能把整张表理解成「某一刻的照片」。

设计权衡

节点的 tradeoffs 原文是：「版本读取减少读写阻塞，但增加空间与清理成本。」

一边是并发形态。一致性读让预览不必挡住发布：本次快照路径等待 0.0 秒，写者可以在读者仍握着旧照片时把稿件改成 published、120。对内容后台这种「读多、偶尔发布、阅读数持续加」的负载，少阻塞往往是 MVCC 被采用的首要理由。另一边是空间和清理。每一次已提交更新都留下可供重建的旧版；50 次更新在长快照下把链路从 1 拉到 51，清理被挡住。生产里这表现为 undo 表空间、历史链表和重建旧行时多出来的工作，而不是教学模型里一个整数那么轻。

锁并没有从权衡里消失，它只是被用在更窄的地方。真正要保护「我接着要改这一行」的路径，仍然需要当前读；真正要累加的计数，应当在最新版本上做相对更新，而不是把快照里的旧值写回去。隔离级别则是在「同一事务里画面稳不稳」和「第二次读能不能看到刚提交的发布」之间选：可重复读把预览钉在第一次一致性读，读已提交让每次一致性读换新快照。读已提交不会让同一个预览事务把 50 次更新全钉在最初那一版上——它每次一致性读都换新快照，对「必须看见第一次打开时的旧稿」不友好，但对「尽快让旧版能被 purge」更友善。这并不是说读已提交就没有 undo：只要一份快照还活着，它看见的那一截链就不能拆；只是它不再把整个长事务期间的所有旧版都钉死在同一份 view_ts 上。

把三件事放在一张选择表里，入职后写预览、计数和导出时可以对照：

你更在意的 更靠近哪条路 这次实验里能看见的代价
同一预览事务里画面不要跳 可重复读 + 一致性读 B 发布后 A 仍看 draft/100；若事务很久不提交，50 次更新会把链路留在 51
每次刷新都看最新已提交稿 读已提交的一致性读，或结束事务再读 A 的第二次一致性读变为 published/120；不再用第一份快照去挡住整段旧链
累加阅读数不能丢 当前读上的相对更新，而不是快照绝对值 safe 得到 120；naive 写回 101
预览不要堵住发布 看板走一致性读，不要走 FOR UPDATE 快照路径等待 0.0 秒；加锁路径等待约 0.20 秒

选哪一边之前，先写出要守的语义：预览是否允许跳变，计数是否允许丢失，以及一个只读会话最长可以开多久。更「新」的读、更少的阻塞和更少的旧版本，很难在同一条路径上同时拿到。

动手实践：观察长事务下更新产生的版本与锁等待，对比事务隔离设置

节点要求的实践是：「观察长事务下更新产生的版本与锁等待，对比事务隔离设置。」下面的步骤全部可以在 practice100 里重跑。运行环境是本机 Python 3.13.5；数字来自本次 bash test.sh 写入的 results.json。

步骤 1：准备数据与目标操作

教学库里只有一篇文章：id=1，标题 autumn-review，初始 status=draft、views=100。要观察的操作是：

  • 编辑 A 打开预览（一致性读），同事 B 发布为 published、views=120 并提交，再比较 A 的第二次一致性读和新事务 C 的读；
  • 同一事务里先快照读、再 SELECT FOR UPDATE；以及 A 持有快照或持有行锁 0.20 秒时，B 的 UPDATE 分别等了多久；
  • A 钉住快照后发生 50 次已提交更新，观察 purge 在 A 结束前后的版本数；
  • 阅读数从 100 累加到 120：naive 按快照旧值写回，safe 在最新版本上 views = views + 1。

步骤 2：两条执行路径

naive 路径把「看见」和「写回」都建立在快照上：预览用快照读是对的，但把快照里的阅读数拿到应用里加一，再按绝对值 update(..., {"views": 101})；看板若再写成加锁读，读者就会去抢写者的行锁。

snap = engine.consistent_read(a, "articles", 1)   # views == 100
engine.update(a, "articles", 1, {**snap, "views": snap["views"] + 1})
# 写回 101，中间那 19 次递增被盖掉

safe 路径把两种读用在它们该在的地方：看板和预览走一致性读，不持行锁；累加走当前读，在最新已提交版本上做相对更新。

engine.update_current(
    a, "articles", 1,
    lambda d: {**d, "views": d["views"] + 1},   # 119 + 1 = 120
)

隔离级别的对照发生在预览路径上：可重复读把 A 的两次一致性读钉在同一份快照，读已提交让第二次读换新快照。这不是又一种「写回姿势」，而是同一条一致性读在两种官方规则下的不同结果。

步骤 2.1：两个会话怎样交错

可见性和丢失递增都不是靠运气撞车。B 的发布被放在 A 第一次一致性读之后、第二次之前；19 次并发递增被放在 A 已经读到 100、但还没有写回之间。锁等待则用线程：A 先进入快照读或 FOR UPDATE，发出「已就绪」信号后再睡眠 0.20 秒，B 从这一刻开始计时并试图 UPDATE。读结果时不要把 0.2003 秒当成生产里的锁等待基准，它只说明在这次教学引擎里，写者确实在等那把被持有 0.20 秒的行锁。

源码与文档阅读

节点指定的资料是 MySQL 8.4 参考手册 17.3 InnoDB Multi-Versioning（dev.mysql.com，英文文档，访问日期 2026-11-11，页面标明为 MySQL 8.4）。节点在资源说明里希望重点核对「快照可见性」与「一致性读与当前读」。需要如实记录的是：这一页的主题是多版本如何把旧行放进 undo、隐藏字段、insert / update undo 的丢弃条件和 purge；快照建立时机、一致性读不加锁、以及当前读如何看待最新行，要到手册链接出去的一致性读、加锁读两页里才能读全。阅读时按页面上实际出现的内容来，不要把本课实践里的 51、101、0.2003 写成这篇文档里的原句。

这几页里与本课直接对应、且已核对过的要点：

  1. InnoDB 是多版本存储引擎。 旧版本信息存在 undo 表空间的 rollback segment 里，既用于回滚，也用于为一致性读重建更早的行。行上有 DB_TRX_ID、DB_ROLL_PTR、DB_ROW_ID；删除在内部是带删除标记的更新。
  2. 一致性读是某个时间点的快照。 查询看见该时间点之前已提交的改动，看不见之后或未提交的改动，但看得见同一事务更早语句的改动。可重复读下，同一事务的所有一致性读共用第一次一致性读建立的快照；读已提交下，每次一致性读建立新快照。一致性读不加锁，其他会话可以同时修改这些表。
  3. 当前读读最新并加锁。 FOR SHARE / FOR UPDATE 在行被未提交事务改过时等待，然后使用最新值；FOR UPDATE 读最新可用数据并加排它锁，加的锁与一条搜寻型 UPDATE 相同。一致性读忽略已在读视图中的那些行锁，旧版本靠 undo 重建，不能被锁住。普通 SELECT 不足以保护「先读再改」；计数器不要用一致性读或共享读取当前值再写回。
  4. 快照主要约束 SELECT，不一定约束 DML。 可重复读事务的 UPDATE / DELETE 可能作用到别的事务刚提交、自己的一致性读还看不见的行；一旦改了，这些改动对本事务可见。这是 InnoDB 与上一课 PostgreSQL 可重复读写冲突处理的重要差别。
  5. update undo 的丢弃条件和长事务。 update undo 只有在已不存在「被赋予的快照还可能需要它来重建旧行」的事务时才能丢；只做一致性读的事务也应当定期提交。purge 在行不再为 MVCC 或回滚所需要之后，才物理删除。长事务（包括只读）会让历史链表增长。

自测题

下面三道题都可以用 practice100 里的数字来回答，不必默写定义。若某一问只能说出「MVCC 用了多个版本」却对不上 draft/100 与 published/120、51 与 1，或 101 与 120，说明还要回到对应的对照表。

题 1：一篇文章初始是 draft、阅读数 100。事务 A 先做了一次一致性读，事务 B 把它改成 published、120 并提交。为什么在可重复读下 A 再读仍是 draft、100，而新事务 C 已经看到新值？如果 A 用的是读已提交，第二次一致性读会看到什么？这能说明教学引擎在模拟脏读吗？

答案 - 可重复读下，同一事务的所有一致性读共用第一次一致性读建立的快照。A 第一次读时稿件还是草稿 100，这份快照被钉住；B 随后提交的发布对这份快照不可见，所以 A 第二次仍是 `draft`、100。C 是新事务，快照建立在 B 提交之后，看到 `published`、120。实践里这组数字是稳定的。 - 读已提交下，每次一致性读建立新快照。A 第一次仍是 `draft`、100，第二次已经是 `published`、120。这是隔离级别改变了快照建立时机，不是文章被「读错了」。 - 不能说这是脏读。脏读是读到尚未提交的修改。B 在 A 第二次读之前已经提交；A 在可重复读下看到的是更早的已提交版本，C 看到的是更晚的已提交版本。MySQL 8.4 一致性读文档把可见范围写成「该时间点之前已提交，不含之后或未提交」。

题 2：为什么同一事务里，快照读仍看到 draft、100，接着的 SELECT FOR UPDATE 却看到 published、120？A 只做快照读时，B 的 UPDATE 为什么等待 0.0 秒，A 做当前读持锁 0.20 秒时又为什么等到 0.2003 秒？「MVCC 不是完全不加锁」在这组数字里应当怎么说？

答案 - 快照读走一致性读路径，继续使用 A 第一次建立的快照，所以仍是旧稿。`SELECT FOR UPDATE` 是当前读，文档写明它读最新可用数据并加排它锁，因此看到 B 已经提交的 `published`、120。两条路径本来就不同。 - 一致性读不加行锁，其他会话可以同时修改这些表，所以 A 只预览时，B 的更新等待 0.0 秒。当前读持有行锁，B 必须等 A 结束；本次 A 持锁睡眠 0.20 秒，B 等到 0.2003 秒。看板那一组同样是快照路径 0.0 秒、加锁路径 0.2004 秒。 - 这正好说明 MVCC 不是完全不加锁。版本链让一致性读可以不挡写者，但加锁读和 `UPDATE` 仍然加锁，写者仍会等待。把预览改成 `FOR UPDATE`，就会让读者挤占写者。

题 3：A 开一个可重复读长事务并钉住草稿快照之后，发生了 50 次已提交更新。为什么此时 purge 之后仍有 51 个版本，A 结束再 purge 只剩 1 个？如果 A 还按快照里的 100 给阅读数加一写回，为什么最终是 101 而不是 120？MySQL 8.4 文档对只读长事务和计数器更新分别怎么说？

答案 - 一开始有 1 个版本，再加 50 次已提交更新，链路上共 51 个版本。A 的快照仍需要最初那一版，重建它要沿着整条链走，所以活跃时 `purge` 清掉 0 个、剩余 51。A 提交后不再有活跃快照，`purge` 一次收掉 50 个旧版，只留当前行。A 在更新期间再读，仍是 `draft`、100；结束后新会话读到 `published`、150。 - naive 路径把快照里的 100 加一写成 101。中间 19 次递增已经把行推到 119，期望是 100+19+1=120，绝对写回把它们盖掉了。safe 路径在最新版本上做 `views = views + 1`，得到 120。按文档，InnoDB 的 `UPDATE` 作为 DML 可以作用在快照之后才提交的行上，所以这条 naive 路径是静默丢失，不会自动变成序列化失败。 - 多版本一节和 purge 配置一节都要求：只做一致性读的事务也要定期提交，否则 update undo 不能丢，长事务（包括只读）会让历史链表增长。加锁读一节则提醒：不要用一致性读或共享读去取计数器再写回。两组忠告分别对应本课的 51→1 和 101→120。

本课小结

  • MVCC 保留多个版本实现一致性读取，版本可见性、锁和垃圾回收共同决定并发行为。
  • 快照可见性：可重复读在第一次一致性读时建立并保持快照，读已提交每次一致性读换新快照。实践里，B 把稿件从 draft、100 发布为 published、120 之后，RR 下 A 两次都是 draft、100，新事务 C 看到新值；RC 下 A 的第二次一致性读已经是 published、120。
  • 一致性读与当前读：一致性读走版本链、不加行锁；当前读读最新已提交版本并加锁。同一事务里快照读仍是 draft、100，FOR UPDATE 看到 published、120。A 只做快照读时，B 的更新等待 0.0 秒；A 当前读持锁 0.20 秒时，B 等待 0.2003 秒。看板加锁读同样让写者等 0.2004 秒，改回快照读则是 0.0 秒。
  • undo、长事务和清理：50 次已提交更新在长快照下把版本链留在 51，purge 清掉 0 个；长事务结束后 purge 清掉 50 个，剩余 1 个，最新值为 published、150。按快照旧值写回阅读数得到 101，基于最新版的相对更新得到 120。
  • 验收：能区分快照读与加锁读；能说明长事务对版本回收的影响。实践里 0.0 / 0.2003 秒的等待，和 51 / 1 的版本数，必须和「MVCC 不是完全不加锁」写在同一份报告里。
  • 误区：MVCC 不是完全不加锁。不要把预览写成加锁读去挡发布，也不要按快照里的旧计数写回，更不要让一个只读事务长时间不提交。
  • 权衡：版本读取减少读写阻塞，但增加空间与清理成本。选隔离级别、快照读还是当前读之前，先写出预览能不能跳变、计数能不能丢、只读会话最长开多久。

学完后可以用三句话自检：同一事务里两次一致性读，以及一次当前读，分别看到了哪一版，这和 RR / RC 的快照规则是不是一致；只做快照读和做了加锁读时，写者分别等了多久；一个长事务在 50 次更新期间把版本链留在了多少，结束之后又能收回多少，按快照旧值写回的计数少了什么。三句都能答上来，并且能指出 practice100 里对应的那组数字，这一课就算过关。

如果有一句答不上来，先回到对应的实验表，再回到 MySQL 8.4 文档里关于快照建立时机、一致性读不加锁、当前读等待最新、以及 update undo 何时能丢的那几句，不要只把「MVCC 就是多版本」这句话背下来。
