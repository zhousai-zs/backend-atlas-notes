参考资料 Redis数据结构与命令成本：参考文档 / 原始资料（redis.io，文档）
摘要 Redis按数据类型提供原子命令，复杂度、键大小与命令执行时间会影响整个实例响应。

边界说明：本课中出现的「内容后台」「文章日榜」「窗口阅读计数」「热门稿件统计」等场景都是教学假设，用来让概念落地，不代表腾讯/微信或任何企业的内部实现。配套代码是 Python 3 标准库写的教学服务，核心是一个名为 RedisEngine 的教学引擎：它实现了 string、hash、sorted set 的一组常用命令，把一条命令当作互斥的原子单元来执行，并用「检查了多少项」以及可选的按项计时，来演示命令复杂度、无界扫描和大键如何挡住后面一条便宜的 INCR。它不是 Redis，不是 redis-py，也不是一个对外提供网络协议的服务器。有序集合用字典加二分插入的有序列表近似官方文档所说的「跳表 + 哈希表」双结构，没有实现 ziplist / listpack、紧缩哈希、字段级过期或集群槽。本课出现的检查项数、等待时间和计数结果只来自这次教学实验。string、hash、sorted set 的语义与命令复杂度，以及 KEYS / SCAN 的生产约束，以 Redis 官方文档为准（本文已核对，访问日期 2026-11-11）：Redis data types、Redis Strings、Redis hashes、Redis sorted sets、KEYS、SCAN。也不要把本课的按项睡眠，说成 Redis 源码里的实际耗时。

导读

一个直觉：只有一个窗口的柜台

想象内容后台的数据柜台只有一个窗口。编辑要给一篇稿加一次阅读，窗口很快就能办完。可如果有人把整本会员档案都摊在柜台上——一份有 2000 个字段的统计表，或者把日榜上全部文章从头抄到尾——窗口就被占住了。后面只想做 INCR 的人不能插队，只能等这份大活做完。

Redis 把数据做成几种现成的类型，每种类型配一组原子命令。便宜的命令检查的项很少：GET、INCR、HGET、ZSCORE 都是常数时间。贵的命令检查的项随输入变大：HGETALL 和 KEYS 会走完整份集合或整个键空间，ZRANGE 0 -1 会把有序集合里的成员都返回。贵的不是「Redis 慢」，而是这条命令的复杂度和输入规模已经写在文档里。窗口只有一个，一条慢命令会让整个实例上的其他请求一起等。

接上前置

  • a-hash：哈希表用键直接定位到桶，均摊后读写是常数时间，但要处理冲突，也要分清「找一个键」和「把整张表扫一遍」不是同一件事。本课里的 Redis hash 把一篇文章的字段做成一张小表，HGET 只取一个字段，HGETALL 则把字段全部倒出来；后者的成本跟字段数成正比。
  • a-db：关系模型里，一行、一列、一条 SQL 的扫描范围决定了代价。Redis 不是关系数据库，但「先选对结构，再看这条命令会碰多少项」这一条是通的。本课不再设计表和索引，而是问：计数、对象字段和排行榜该用哪种类型，以及一条命令会检查多大的输入。

前面单独看都学过：会用哈希表做点查，也知道扫描范围会改变一次查询的代价。本课把它们组装成「阅读数为什么必须用一条 INCR，日榜为什么不要一次拉回全部成员，运维为什么不能在生产路径上跑 KEYS」。组装之后才会出现的问题是：每个命令都成功了，阅读数却对不上；窗口计数在高峰过后还占着键；一次「查一下有哪些文章键」把加阅读的请求堵住了将近 0.2 秒。

一条命令走进实例之后

  客户端发出一条命令
        │
        ▼
  进入命令执行路径（教学引擎用一把互斥锁模拟：同一时刻只跑一条）
        │
        ├─ SET / GET / INCR / ZSCORE / HGET / HSET / HINCRBY
        │      文档复杂度 O(1)；本课实践里 examined = 1
        │
        ├─ HMGET
        │      O(N)，N 是这次请求的字段数
        │
        ├─ HGETALL / HKEYS / HVALS
        │      O(N)，N 是这个 hash 里的全部字段
        │
        ├─ ZADD / ZINCRBY / ZRANK / ZREVRANK
        │      O(log N)，N 是有序集合的成员数
        │
        ├─ ZRANGE / ZREVRANGE
        │      O(log N + M)，M 是这次返回的成员数
        │      只要前 10 名，M=10；写 0 -1 把整份集合倒出来，M=N
        │
        ├─ KEYS pattern
        │      O(N)，N 是整个键空间，不是匹配到的条数
        │      官方文档写明：不要用在常规应用代码里
        │
        └─ SCAN / HSCAN / ZSCAN
               单次调用 O(1)，完整迭代 O(N)
               一次只走一小段，游标回到 0 才算走完

  本条命令结束，下一条才能开始
  一条检查了很多项的命令，会让后面再便宜的 INCR 也排队

正常路径看起来只是「选一种类型，发一条命令」。本课真正要讲的是图上那几处分叉：同一份数据用 string、hash 还是 sorted set，决定了你能做哪种原子操作；一条命令内部是原子的，并不等于客户端连续发的两步也是原子的；复杂度公式里的 N 和 M 一旦变大，挡住的就不是这一个调用，而是整个窗口。

教学场景（教学假设）

内容后台要同时做三件事：保存文章的标题和状态、累加阅读数、维护一份当日阅读排行榜。灰度期间出现了几件「每条命令都成功，数字和延迟却对不上」的事：

  1. 文章元信息放在 hash 里，阅读数放在 string 里，日榜放在 sorted set 里。文章 42 经过一波集中阅读后，日榜分数是 82，倒序名次是第 0 名。只要前 10 名，教学引擎检查了 15 项；把 21 个成员全部倒出来，检查了 26 项。
  2. 200 个请求同时给同一篇阅读数加一。客户端先 GET 再 SET 的路径，最终只有 3；改成一条 INCR，得到 200。日榜上先 ZSCORE 再 ZADD 得到 2，一条 ZINCRBY 得到 200。窗口计数若在第一次 INCR 之后、EXPIRE 之前崩溃，60 秒窗口走完后键还在，值是 10，TTL 仍是 -1；安全路径用带 NX 和 EX 的一条 SET 创建键，窗口结束后键消失，TTL 是 -2。
  3. 键空间里有 4051 个键。一次 KEYS article:* 虽然只匹配 2000 个，却检查了全部 4051 个键，后面一条 INCR 等了 0.1924 秒。一次 SCAN（COUNT 20）只检查 20 个键，INCR 只等 0.0001 秒。2000 个字段的 HGETALL 让后面的 INCR 等 0.0901 秒，HGET 一个字段则是 0.0001 秒。2000 个成员的 ZRANGE 0 -1 让 INCR 等 0.0907 秒，只要前 10 名则是 0.0001 秒。100 次读取里有 80 次打在那份大 hash 上，一共检查了 160000 项；另外 20 次只取一个字段，一共检查了 20 项。

本课三条主线

  1. string、hash 和 sorted set：按要做的操作选类型，而不是先把对象序列化成一个大字符串再自己解析。
  2. 单命令原子性：一条 INCR / ZINCRBY / HINCRBY 在执行期间不会跟其他命令交错；客户端把读和写拆成两步，就不能再享受这个保证。
  3. 大 key、热 key 与复杂度：先写出这条命令的 N 和 M，再决定要不要全量返回、要不要在生产路径上扫描键空间。热门键如果再叠上一次昂贵的全量读取，检查项数会被放大。

学习目标

  • 能解释 string、hash 和 sorted set 各自适合什么操作，并能指出常用命令的复杂度是相对于哪个输入规模。
  • 能独立完成：实现排行榜与过期计数，评估扫描和大成员集合操作。
  • 验收时能做到：不在生产路径使用无界 KEYS 扫描；能指出命令复杂度与输入规模。

为什么后端要懂

后台服务里，缓存、计数和排行榜经常会落到 Redis 上。选错类型，应用层就要自己拆字段、自己排序；选对了类型却用错命令，一次「把全部成员拿回来再在进程里排」就会把实例卡住。节点的 why 写得很短：把缓存、计数与队列建模成合适的数据操作。本课先把计数、对象字段和排行榜这三件最常见的事做对，队列和更复杂的集合运算不在这次实验里展开。

对即将做公众号后台的人来说，这三件事几乎天天会碰到：一篇稿的标题和状态要按字段读改，阅读数要在并发下加得准，日榜只要前几名却不能把全站稿件倒进接口。命令的成本会穿过这条业务线，变成接口超时、实例 CPU 打满、以及其他本来毫不相关的计数请求一起变慢。实践里一次 KEYS 就能让后面的 INCR 等到 0.1924 秒，一次 2000 字段的 HGETALL 也能让它等到 0.0901 秒——被拖慢的并不是那条扫描自己的调用方，而是整个窗口后面排队的人。先能指着复杂度公式说出「这次检查了多少项」，再谈集群、持久化和缓存失效，才不会把后面那些手段用在一个本身就不该全量扫描的命令上。

核心知识点

1. string、hash 和 sorted set

官方概览把 Redis 叫作数据结构服务器：键的值不是只能当不透明的字节，而是带一组针对该类型的命令。本课只展开节点点名的三种。

string 是最基本的值，一份字节序列。SET / GET / INCR 都是 O(1)。文档把 INCR 写成：把字符串解析成整数，加一，再写回去；若键不存在就从 0 起算。它特别强调「原子」的含义：多个客户端同时对同一个键做 INCR，不会出现大家都读到 10、都写成 11 的竞态，最终一定是每个人加一次之后的值。string 也常被用来缓存整页或一段 HTML，但文档提醒：如果存的是结构化数据，应考虑改用 hash 或 JSON。单个 string 的默认上限是 512 MB，本课没有去碰这条上限。

hash 是字段到值的集合，用来表示一个对象，或一组相关计数。HSET / HGET / HINCRBY 都是 O(1)，HMGET 是 O(N)（N 为本次要取的字段数），HGETALL、HKEYS、HVALS 是 O(N)（N 为这个 hash 的全部字段）。文档写得很直白：大多数 hash 命令是 O(1)，这几条全量命令和多数字段过期命令是 O(n)。教学场景里，article:42 用 hash 存放 title、status、author，需要标题时只 HGET，不要为了看一个状态就把全部字段搬回来。

sorted set 是带分数的唯一成员集合，按分数排序，分数相同再按成员的字典序。官方实现说明是跳表加哈希表，因而加入或更新一个成员是 O(log N)，排好序这件事在写入时已经做完，读取时不必再排序。ZADD / ZINCRBY / ZRANK / ZREVRANK 是 O(log N)，ZSCORE 是 O(1)，ZRANGE / ZREVRANGE 是 O(log N + M)。文档把排行榜当作典型用法：既能按分数更新，又能取前 N 名，还能查一名成员的名次。教学里日榜键是 rank:daily，成员是文章 ID，分数是阅读数。

用一组接近官方教程风格的命令把这三种类型走一遍，有助于把「类型」和「命令」对上号。下面是教学引擎里实际发生过的操作，写法按 Redis 命令来，方便对照文档；运行仍以 bash test.sh 为准：

HSET article:42 title "Weekly digest" status published author editor-a
INCR views:42
INCR views:42
ZADD rank:daily 2 42

# 随后文章 42 又被集中阅读 80 次
INCR views:42          # 每次 +1，最终 82
ZINCRBY rank:daily 1 42

HGET article:42 title          # Weekly digest
GET views:42                   # 82
ZSCORE rank:daily 42           # 82
ZREVRANK rank:daily 42         # 0
ZREVRANGE rank:daily 0 9 WITHSCORES
# 前 10 名：42/82、20/60、19/57、…、12/36，检查 15 项
ZRANGE rank:daily 0 -1 WITHSCORES
# 21 个成员全部返回，检查 26 项

ZRANGE 的 0 和 -1 与列表里的 LRANGE 一样，表示从第一个到最后一个。这在成员很少时看起来无害，成员涨到 2000 时，M 就变成了 2000。官方文档把排行榜的日常更新写成 ZADD 或 ZINCRBY，把取榜写成有界范围，而不是先把整份集合拉回进程再排一次。

实践里这三种类型同时出现在同一篇文章上：

article:42     hash     title=Weekly digest  status=published
views:42       string   82
rank:daily     zset     成员 42 的分数 82，倒序名次 0

21 篇文章进入日榜后，文章 42 以 82 分排在第一，第二名是文章 20（60 分）。ZREVRANGE 0 9 取出前 10 名，教学引擎检查了 15 项（1 + floor(log2(21)) + 10）；ZRANGE 0 -1 取出全部 21 个成员，检查了 26 项。同一份集合，只要前 10 名和全量倒出，检查项数已经不一样。后面把成员数放大到 2000 时，这个差距会变得很刺眼。

2. 单命令原子性

文档在讲 INCR 时说得很清楚：原子意味着这条命令在执行时，其他客户端不会插进来做同一件事。教学引擎用一把互斥锁来模拟这一点——一条命令从进到出，中间不会换成另一条命令。

这并不等于「你在客户端写的两行 Redis 调用加在一起也是原子的」。200 个线程同时给同一个阅读数加一，得到的是这样一组对照：

路径 最终值 期望
先 GET 再 SET（中间隔 2 毫秒的本地加一） 3 200
一条 INCR 200 200
先 ZSCORE 再 ZADD 2 200
一条 ZINCRBY 200 200

GET 和 SET 各自都是原子的，但两个客户端可以都读到同一个旧值，再分别写回「旧值加一」。日榜上同样的拆法会把分数写丢。节点的 pitfalls 就是这句话：单命令原子不意味着客户端多步操作整体原子。

过期计数是同一个误区的另一种样子。常见写法是：

n = INCR win:naive
if n == 1:
    EXPIRE win:naive 60

只有第一次请求会去设 TTL。若第一次在 INCR 之后、EXPIRE 之前崩溃，这个键就没有过期时间；后面的请求看到的已经是 2、3、4，不会再走 EXPIRE。实践里，崩溃后 TTL 是 -1（键还在，但没有过期时间）；再累加到 10，把时钟推进 61 秒之后，键仍然在，值仍是 10，TTL 还是 -1。

安全路径把「创建键」和「设过期」放进同一条命令：SET win:safe 1 EX 60 NX。成功则这是本窗口的第一次；失败说明键已经在，再 INCR。实践里，创建时 TTL 是 60，10 次命中后值是 10；窗口结束后键消失，GET 得到空，TTL 是 -2；下一次命中会重新创建，TTL 再次是 60。官方 string 文档还列有 SETEX、SET 的 EX 选项，以及较新版本里把递增和过期合并到一条命令的路径；本课实验覆盖的是 SET NX EX 这一种，没有去跑那些变体。

3. 大 key、热 key 与复杂度

复杂度公式要和输入规模放在一起读。KEYS 的文档写的是 O(N)，并警告：生产环境要格外小心，它的本意是调试和特殊操作，例如改键空间布局；不要把它写进常规应用代码，若只是想找一类键，应考虑 SCAN 或用集合把这些键自己维护起来。SCAN 的文档写的是：单次调用 O(1)，完整迭代 O(N)；因为它每次只返回一小批，所以可以在生产里用，而不必承担 KEYS 或 SMEMBERS 那种对着大集合长时间堵住服务器的代价。完整遍历的保证是有限的：迭代期间集合若被改过，可能重复或错过中间变化的元素。本课没有做「边 SCAN 边增删」的实验，不把教学引擎的扫描结果说成并发修改下的官方保证。

实践里键空间有 4051 个键，其中文章 hash 2000 个。KEYS article:* 匹配 2000 个，但检查了全部 4051 个键——成本跟键空间走，不跟匹配数走。SCAN MATCH article:* COUNT 20 走完整遍同样检查 4051 个键，却拆成 203 次调用；其中一次调用只检查 20 个键。两种办法最终找到的文章键是同一批。

大键是同一个公式换了一个 N。2000 个字段的 hash 上，HGET 检查 1 项，HMGET 三个字段检查 3 项，HGETALL 检查 2000 项。2000 个成员的有序集合上，ZREVRANGE 0 9 检查 21 项（1 + floor(log2(2000)) + 10），ZRANGE 0 -1 检查 2011 项。官方 sorted set 文档也提醒：对返回值很大的 ZRANGE 要当心，复杂度是 O(log N + M)，M 是返回的成员数。

教学引擎给每一项加上 50 微秒的持锁成本，用来观察「一条命令挡住后面一条 INCR」的数量级，不是用来测量真实 Redis 的延迟：

挡在前面的命令 检查项 该命令持锁 后面 INCR 等待
KEYS *（4052 个键，含探测键） 4052 0.204283 秒 0.1924 秒
一次 SCAN COUNT 20 20 0.001458 秒 0.0001 秒
HGETALL（2000 个字段） 2000 0.100272 秒 0.0901 秒
HGET 一个字段 1 0.000120 秒 0.0001 秒
ZRANGE 0 -1（2000 个成员） 2011 0.100787 秒 0.0907 秒
ZREVRANGE 0 9 21 0.001136 秒 0.0001 秒

无界扫描和大键会把一次本该是常数时间的计数，变成十分之一秒到接近 0.2 秒的等待。改成游标扫描、单字段读取和有界的前 10 名，等待都回到 0.0001 秒。

热 key 是访问集中在少数键上。若这把热键还是大键，检查项数会被请求次数放大。实践里 100 次读取：80 次 HGETALL 打在那份 2000 字段的热 hash 上，共检查 160000 项；20 次 HGET 打在一份冷的小 hash 上，共检查 20 项。热键占了请求的 0.8，却占了几乎全部的检查工作。分片帮不上这种键的忙：官方性能实践也指出，对着超大键做扫描时，拆分到多个分片并不能把这一个键变小。本课没有做集群实验，这条只作为阅读提示，不写入 results.json 的断言。

把三条主线串在同一篇稿上

文章 42 的标题在 hash 里，阅读数在 string 里，名次在 sorted set 里——这是选对类型。200 个并发加一只能靠 INCR 和 ZINCRBY，不能靠客户端自己读改写——这是单命令原子性。日榜只要前 10 名、统计只要一个字段、键空间只能用 SCAN 分段走——这是把复杂度和输入规模写进路径里。三件事任意一件做错，表现都可能是「命令返回了成功」：阅读数丢了、窗口键删不掉、或一次运维查询把加阅读堵住了 0.1924 秒。

三条主线的收束

选类型时先写清要做的原子操作：加一个数、改一个字段、更新分数并取前 N 名。写客户端时，凡是「先读后写」，都问自己这两步之间会不会插进别人。评估一条命令时，把文档里的 N 和 M 换成自己的键数量、字段数、返回条数；只要这个数字在生产路径上可能增长，就不要用无界的 KEYS、HGETALL 或 ZRANGE 0 -1。

常见误区

  • 把每条命令的原子性当成一段业务的原子性。 GET 再 SET、ZSCORE 再 ZADD、INCR 再 EXPIRE，每一步都可能成功，拼起来却会丢更新或留下永不过期的键。实践里前一种落到 3 和 2，后一种在窗口结束后还留着值 10、TTL -1。
  • 以为 KEYS 的成本等于匹配到的条数。 匹配 2000 个文章键时，它仍然检查了全部 4051 个键。官方文档把这条命令留给调试和特殊操作，生产路径应使用 SCAN，或在写入时就把这类键记进一个集合。
  • 把「类型灵活」理解成「一次把整个值搬回来再在应用里算」。 hash 和 sorted set 的价值，正是字段点和有界范围可以走 O(1) 或 O(log N + M)。2000 字段的 HGETALL 和 2000 成员的全量 ZRANGE，会把后面一条 INCR 拖到约 0.09 秒；改成 HGET 或前 10 名，等待回到 0.0001 秒。

设计权衡

节点给出的权衡是：灵活类型减少应用代码，但需控制键数量、大小和热度。用 hash 存对象、用 sorted set 做榜，应用就不必自己拆 JSON、自己排序；代价是键会变多，单个键也可能因为字段或成员不断追加而变成大键，热门文章还会把访问集中到同一把键上。

选择时先写出三件事：单个键预计会有多少字段或成员，一次读取真正需要多少，以及是不是会有远高于平均值的访问打在同一把键上。需要整份对象且字段很少时，一次 HGETALL 是合理的；字段可能涨到几千时，应只取用到的字段，或把大统计拆到按时间分片的键上。日榜如果只展示前 10 名，就不要在接口里写 ZRANGE 0 -1。键的命名和过期也要一起设计，避免靠生产路径上的 KEYS 去「找一找有哪些键」。

本课没有覆盖 Lua 脚本、MULTI/EXEC、集群槽和持久化。这些手段可以在需要跨键原子性、分片或重启恢复时再引入，但不能用来给一条本来就不该全量扫描的命令善后。持久化是下一课之后的节点，本课的数字只说明命令执行期间的成本和原子性。

步骤 1：准备数据与目标操作

教学场景里要同时支持：

  • 文章元信息：HSET / HGET 读写 title、status
  • 阅读计数：INCR，以及带 60 秒窗口的过期计数
  • 日榜：ZADD / ZINCRBY 更新分数，ZREVRANGE 取前 10 名，ZREVRANK / ZSCORE 查名次和分数
  • 运维与巡检：比较 KEYS article:* 和 SCAN，比较 HGETALL 与 HGET，比较全量 ZRANGE 与前 10 名

不要在实验一开始就调用 KEYS * 或对日榜做 ZRANGE 0 -1 当默认读取路径。

步骤 2：两条执行路径

计数和日榜都准备了 naive / safe 两条路：

# naive：每一步都是原子命令，拼起来不是
raw = r.get("views:naive")
n = int(raw or "0") + 1
r.set("views:naive", str(n))

score = r.zscore("rank:daily", "42") or 0.0
r.zadd("rank:daily", "42", score + 1)

n = r.incr("win:naive")
if n == 1:
    r.expire("win:naive", 60)   # 若第一次崩溃，后面再也不会走这里

# safe：把「读改写」收成一条命令；创建与过期也收成一条
r.incr("views:safe")
r.zincrby("rank:daily", 1, "42")
created = r.set("win:safe", "1", ex=60, nx=True)
if not created:
    r.incr("win:safe")

扫描和大键同样对照：KEYS 对 SCAN 的一次调用，HGETALL 对 HGET，ZRANGE 0 -1 对 ZREVRANGE 0 9。

步骤 2.1：并发和挡住是怎样交错的

200 个线程先在栅栏上对齐，再同时走 naive 或 safe 路径。naive 路径在读和写之间故意留了 2 毫秒，让「大家都读到旧值」稳定出现；这是为了演示竞态，不是 Redis 协议的一部分。挡住实验则是：先把键种进去，再打开按项计时，一条重命令持锁时，另一条线程去发 INCR，记录它等了多久。

步骤 6：和生产引擎的对应关系（不要记错边界）

  • 教学引擎跑在一个进程里，用互斥锁和按项睡眠模拟「一条命令挡住另一条」。它用来说明检查项数和等待的数量级对比，不用来测量 Redis 的事件循环、过期抽样、LRU、持久化 fork 或集群跳转。
  • 有序集合的检查项数采用 1 + floor(log2(N)) + M 这一教学近似，对应文档里的 O(log N + M)，并不是源码里跳表的比较次数。
  • SCAN 的实现是按排序后的键名、以游标为下标、每次最多走 COUNT 个键。真实 Redis 的 COUNT 是提示，单次返回数量不保证落在固定区间，也可能一次返回 0 个元素；只要游标还不是 0，迭代就不能结束。本课没有覆盖这些边界。
  • Python 3.13.5 只是本次跑实验的解释器版本。教学引擎不依赖第三方包，也不连接外部 Redis。换一台机器重跑，整数断言应当相同；等待时间允许在阈值内波动，但重命令路径仍应明显长于短命令路径。

源码与文档阅读

节点指定的资料是 Redis data types（redis.io，英文文档，访问日期 2026-11-11）。节点在资源说明里希望重点阅读 string、hash 和 sorted set 与单命令原子性，用于核对本节点实验的语义和边界。需要如实记录的是：这一页是类型总览，具体命令、复杂度、INCR 的原子含义、hash 全量命令的 O(n)、sorted set 的 O(log N + M)，以及 KEYS / SCAN 的生产约束，要到类型分页和命令页里才能读全。阅读时按页面上实际出现的内容来，不要把本课实践里的 3、200、0.1924 写成这些文档里的原句。

这几页里与本课直接对应、且已核对过的要点：

  1. Redis 按类型提供命令。 string 是字节序列，可做缓存和原子计数，SET / GET / INCR 为 O(1)，默认上限 512 MB。hash 是字段到值的记录，HSET / HGET / HINCRBY 为 O(1)，HGETALL / HKEYS / HVALS 为 O(N)。sorted set 是带分数的唯一成员集合，写入时保持有序，实现是跳表加哈希表；ZADD / ZINCRBY 为 O(log N)，ZRANGE 为 O(log N + M)，排行榜是文档给出的典型用途。
  2. 单条命令的原子性有明确含义。 string 文档用 INCR 说明：多个客户端同时加一，不会大家都读到 10 再都写成 11。它没有把「客户端连续发的两条命令」说成一条事务。MSET / MGET 是单条命令里操作多个键，仍然是这一条命令的原子性。
  3. 无界扫描和大范围读取要按 N、M 来看。 KEYS 是 O(N)，文档警告不要写进常规应用代码，应考虑 SCAN 或用集合维护子集。SCAN 单次 O(1)、完整迭代 O(N)，可在生产使用，但对迭代期间发生变化的集合只提供有限保证。sorted set 文档提醒不要让 ZRANGE 返回过大的 M；hash 文档把 HGETALL 标成 O(n)。

建议的阅读方法：先读类型总览，再分别打开 string、hash、sorted set 三页，用手写下 INCR、HGET、HGETALL、ZINCRBY、ZRANGE 的复杂度，以及公式里的 N、M 各指什么。然后再读 KEYS 和 SCAN 的警告与保证。回到本课实践，看哪一组数字在模拟其中哪一条。记录：访问日期 2026-11-11、实际打开的 URL，以及你亲自跑过的 bash test.sh 输出。

阅读时还应注意这几页写了、但本课实验没有用数字去覆盖的边界，避免把「没做」当成「文档没说」。string 页有 SET 的 NX / XX / IFEQ、MSET、GETRANGE 等，以及较新版本里把递增与过期合并的命令；hash 页有字段级过期（7.4 起）和紧缩哈希（8.10 起）；sorted set 页有按分数范围、按字典序范围，以及并交差运算。SCAN 页写了迭代期间集合变化时的有限保证，以及单次调用可能返回 0 个元素。这些都是官方原文里的路径，本课既没有在教学引擎里实现完整集合，也没有在 results.json 里给出对应数字。

边界：教学实验只模拟已核对、并且已经跑出数字的那一部分语义，不代表 Redis 的内存编码、过期淘汰、多线程 I/O、持久化或集群槽。不确定的地方，应写「文档未覆盖」或「本课未实验」，而不是用教学输出去填空。

自测题

下面三道题都可以用 practice101 里的数字来回答，不必默写定义。若某一问只能说出「Redis 很快」却对不上 3 与 200、4051 与 20，或 0.1924 与 0.0001，说明还要回到对应的对照表。

题 1：为什么给同一篇文章加阅读、改标题、更新日榜，要分别用 string、hash 和 sorted set，而不是把整篇文章序列化成一个 string？文章 42 的分数是 82、倒序名次是 0 时，取前 10 名为什么检查 15 项，倒出全部 21 个成员却检查 26 项？把成员数放到 2000 时，这两个数字分别变成了什么？

答案 - string 适合原子计数，`INCR` 是 O(1)，文档保证多个客户端同时加一不会写丢。hash 适合按字段读写一篇稿的标题和状态，`HGET` 是 O(1)，不必为了一个字段把整份对象反序列化。sorted set 在写入时就按分数保持顺序，`ZINCRBY` 更新分数，`ZREVRANGE` 取前 N 名，`ZREVRANK` 查名次，都不必在应用里再排序。 - 有序范围的成本是 O(log N + M)。21 个成员时，教学近似是 `1 + floor(log2(21)) + M`，所以前 10 名是 15，全量 21 个成员是 26。成员数到 2000 时，前 10 名检查 21，全量检查 2011。差的不是「排行榜这个类型慢」，而是 M 从 10 变成了整个集合。

题 2：200 个请求同时加一时，为什么先 GET 再 SET 最终是 3，一条 INCR 却是 200？日榜上先 ZSCORE 再 ZADD 为什么是 2？窗口计数在第一次 INCR 之后崩溃，60 秒之后为什么键还在、值是 10、TTL 是 -1，而 SET NX EX 那条路径在窗口结束后 TTL 是 -2？

答案 - `GET` 和 `SET` 各自原子，并不使「读到旧值、本地加一、写回」整段原子。200 个线程可以对齐后读到同一个旧值，再互相覆盖，实践里最终是 3。`INCR` 把读改写收在一条命令里，最终是 200。日榜上的 `ZSCORE`+`ZADD` 是同一类拆法，最终是 2，`ZINCRBY` 是 200。 - 常见过期计数只在 `INCR` 返回 1 时调用 `EXPIRE`。第一次若在两条命令之间崩溃，键被创建却没有 TTL（-1）；后续命中看到的已经不是 1，也不会再设过期。窗口走完后值仍是 10，TTL 仍是 -1。安全路径用一条 `SET NX EX` 同时创建键并设定 60 秒过期，窗口结束后键消失，TTL 是 -2，新窗口可以重新从 1 开始。

题 3：KEYS article:* 只匹配到 2000 个键，为什么还检查了 4051 项，并把后面的 INCR 挡住 0.1924 秒？为什么改成一次 SCAN COUNT 20、或把 HGETALL / 全量 ZRANGE 改成 HGET / 前 10 名，等待都会回到 0.0001 秒？80 次热键全量读取检查 160000 项，说明大 key 和热 key 叠在一起时应该先改什么？

答案 - `KEYS` 的复杂度是 O(N)，N 是整个键空间，不是匹配条数。实践里键空间 4051，匹配 2000，检查的仍是 4051；加上探测键后这次 `KEYS` 检查 4052 项，持锁约 0.204283 秒，后面的 `INCR` 等到 0.1924 秒。官方文档明确要求：不要把 `KEYS` 写进常规应用代码。 - 一次 `SCAN COUNT 20` 只检查 20 项，持锁约 0.001458 秒，`INCR` 等待 0.0001 秒。`HGETALL` 2000 字段对应 0.0901 秒，`HGET` 一个字段是 0.0001 秒；全量 `ZRANGE` 是 0.0907 秒，前 10 名是 0.0001 秒。短命令并没有变快，是前面那条命令不再按整个集合的规模持锁。 - 热键本身只说明访问集中；若每次访问还做全量读取，检查项数会被次数放大：80 × 2000 = 160000，而 20 次单字段只有 20。应先把热路径改成点查或有界范围，必要时再拆键；不要指望用分片把「这一把已经很大的键」变小。本课没有跑集群，后半句以官方性能实践和本课的检查项数为限。

本课小结

  • Redis 按数据类型提供原子命令，复杂度、键大小与命令执行时间会影响整个实例响应。
  • string、hash 和 sorted set：计数用 INCR，对象字段用 HGET / HSET，排行榜用 ZINCRBY 和有界的 ZREVRANGE。实践里文章 42 的阅读数和日榜都是 82，倒序名次 0；21 个成员时前 10 名检查 15 项，全量检查 26 项。
  • 单命令原子性：200 次并发下，GET+SET 落到 3，INCR 得到 200；ZSCORE+ZADD 落到 2，ZINCRBY 得到 200。窗口计数若把 INCR 和 EXPIRE 拆开，第一次崩溃后 TTL 一直是 -1，窗口结束后值仍是 10；SET NX EX 在窗口结束后键消失，TTL 是 -2。
  • 大 key、热 key 与复杂度：KEYS article:* 匹配 2000，检查 4051，挡住 INCR 0.1924 秒；一次 SCAN COUNT 20 检查 20，等待 0.0001 秒。HGETALL 2000 字段等待 0.0901 秒，HGET 为 0.0001 秒；2000 成员的全量 ZRANGE 等待 0.0907 秒，前 10 名为 0.0001 秒。80 次热键全量读取检查 160000 项，20 次冷键点查检查 20 项。
  • 验收：不在生产路径使用无界 KEYS 扫描；能指出命令复杂度与输入规模。实践里 4051 / 20 的检查项，和 0.1924 / 0.0001 秒的等待，必须和「单命令原子不是多步业务原子」写在同一份报告里。
  • 误区：不要把两条成功的命令当成一段原子更新，也不要按匹配条数去估计 KEYS 的成本，更不要默认把整个 hash 或整个有序集合搬回应用再算。
  • 权衡：灵活类型减少应用代码，但需控制键数量、大小和热度。先写出一个键会涨到多大、一次读取真正需要多少、热路径会不会打在同一把大键上。

学完后可以用三句话自检：同一篇文章的字段、计数和名次分别用了哪种类型，取前 10 名和全量倒出的检查项数差在哪里；200 次并发下拆成两步和收成一条命令的结果各是多少，窗口计数在崩溃后为什么删不掉；KEYS、HGETALL、全量 ZRANGE 各检查了多少项、挡住后面的 INCR 多久，改成 SCAN、HGET、前 10 名之后又变成多少。三句都能答上来，并且能指出 practice101 里对应的那组数字，这一课就算过关。
