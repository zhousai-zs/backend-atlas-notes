承接说明：前置节点 d-pool 讨论连接这类稀缺资源的复用与生命周期管理，提醒我们一次远程调用背后往往复用了连接、线程和缓冲，调用失败并不等于底层资源一定健康。前置节点 f-protobuf 讨论 Protobuf 的模式、字段编号与代码生成，解决了“消息长什么样、字段身份怎样固定”的问题。本课把这两条线接到调用语义上：请求发出去以后，客户端到底能知道什么、不能知道什么；成功、失败和“结果未知”为什么是三种状态；流式调用为什么不能当成一次普通函数返回；截止时间为什么只是本地的预算，而不是服务端没执行的证明。本节点 summary 是：RPC 把远端调用包装为接口，但网络使成功、失败和结果未知成为不同状态，远端调用不等同本地函数。

导读

先看本节点的 summary，后面所有内容都围绕它展开：

RPC 把远端调用包装为接口，但网络使成功、失败和结果未知成为不同状态，远端调用不等同本地函数。

这句话至少包含三层意思。

第一层是接口看起来像本地函数，但它只是一个包装。生成代码把参数序列化、把请求发到某个地址、等待响应、把响应反序列化，最后返回一个对象或抛出一个错误。调用点的写法可能和本地函数几乎一样，但底层经历了编解码、连接复用、排队、网络传输、服务端调度、业务执行和响应回传。包装降低了使用成本，也容易让人误以为“调用返回了，事情就一定有确定结论”。节点 tradeoffs 说得很直接：透明封装提高使用便利，但必须暴露失败与时间预算。

第二层是远端调用有三种结果状态，而不是两种。本地函数通常只有“正常返回”和“抛出异常”两种出口；远程调用还多出一种“结果未知”：请求可能已经到达服务端，服务端可能已经提交，但响应在回程丢失，或者客户端在等待时超时。此时客户端既不能断言成功，也不能断言失败。节点 summary 把“成功、失败和结果未知”并列，就是要打破“非成即败”的二元直觉。

第三层是失败要分层，时间要预算。网络错误、框架错误和业务错误不是同一层的东西；把“连接被重置”和“余额不足”压成同一个布尔值，会让重试策略和排障都失去依据。同时，任何一次调用都必须带时间预算：客户端等多久、服务端还剩多少时间、重试要不要重新计时、流式调用空闲多久算超时。节点 points 把“传输错误与业务错误”和“结果未知和截止时间”单独列出，正是因为它们决定了接口能否被安全地重试、能否被观测、能否在故障时给出确定行为。

本课沿着三个节点要点推进：

  • 请求响应和流式调用：调用模型决定了消息有几个、完成信号在哪里、错误在什么时候出现，以及“已经收到的部分数据”算不算结果。
  • 传输错误与业务错误：错误必须分层表达，传输层回答“这次调用有没有完成”，业务层回答“这个操作决定怎么做”。
  • 结果未知和截止时间：超时只是客户端停止等待，不代表服务端没有执行；要解决未知，只能靠幂等、去重、查询或对账，而不是靠猜。

三个要点最终服务于本节点的 why：设计能处理部分故障的服务 API。

学习目标

goals

  • 能解释请求响应和流式调用。
  • 能独立完成：画出服务器提交后响应丢失的时序，给接口定义可观察结果。

acceptance

  • 能解释超时不代表服务端未执行。
  • 业务错误与网络状态分层。

把验收翻译成可检查产物

“能解释”和“能独立完成”都太容易被“我看懂了”糊弄过去。把两条 acceptance 翻译成看得见、摸得着的东西：

  • “能解释超时不代表服务端未执行”：你要能画出一张时序图，把一次调用拆成至少这些时刻：客户端发出请求、请求到达服务端、服务端开始处理、服务端完成提交、服务端发出响应、响应丢失或迟到、客户端截止时间到达。图上要标出哪些时刻客户端能观察到，哪些只能由服务端知道。还要配一张状态表，分别写“客户端认为的状态”和“服务端实际的状态”，并列出在超时发生后，客户端有哪些合法动作：直接失败、带幂等键重试、按请求 ID 查询、进入人工对账。只背一句“超时可能已经执行”不算完成，能把时刻和动作写清楚才算。
  • “业务错误与网络状态分层”：你要给出一个错误分类表，至少区分传输/框架层和业务层，并说明每一类错误的可观察信号、是否可重试、重试是否需要幂等保护、应该记录什么日志。接口定义中，业务错误不能只返回一个布尔值或一句字符串，而要有稳定的错误码、可读消息和必要的上下文；传输错误也不能伪装成业务失败。验收时要能拿着这张表，对任意一个错误判断它属于哪一层、该不该重试、重试会不会产生重复副作用。

先修自检

  • d-pool：能说清连接复用的基本动机，知道连接有建立、空闲、使用中、失效等状态；知道连接池借出和归还的不是“调用”，而是底层连接资源；能解释连接断开为什么会让正在进行的调用失败，但不会自动撤销服务端已经完成的操作。
  • f-protobuf：能说清消息模式、字段编号和序列化的关系；知道请求和响应都是先变成字节再上线；知道模式演进要遵守字段编号兼容规则；知道反序列化失败和业务处理失败是两件不同的事。
  • C++ 基础：能写结构体、枚举、std::optional、std::variant 或简单的结果类型；知道怎样用 std::chrono 表示时间点和时长；能读懂回调、future/promise 或同步等待的基本写法。
  • 网络常识：知道客户端和服务端是两个独立进程；知道请求可能丢失、响应可能丢失、连接可能中途断开；知道“发出去了”不等于“对方收到了”，更不等于“对方处理完了”。

如果前两条里有任何一条说不清，先回去补。本课不会再展开连接池的实现细节，也不会重新讲 Protobuf 的线格式；它假设你已经知道“调用要经过序列化和网络”，重点放在“调用结果到底意味着什么”。

为什么后端要懂

本节点 why 的原话是：设计能处理部分故障的服务 API。 在真实后端里，这句话对应的不是抽象的分布式理论，而是几类会直接造成资金损失、数据重复和排障困难的工程问题。

场景一：下单接口超时后自动重试

客户端调用下单接口，等待 2 秒没有响应，于是判定失败并自动重试一次。第一次请求其实已经到达服务端，订单已经写入数据库，只是响应在回程丢失。第二次请求又创建了一笔订单。用户看到两个订单，库存被扣了两次。节点 pitfalls 说的正是这件事：重试一次远程写可能产生重复副作用。 如果接口没有幂等键和去重机制，客户端根本无法安全地区分“第一次真的失败了”和“第一次成功了但响应丢了”。

场景二：流式订阅中途断开

一个日志订阅接口用服务端流式调用持续推送日志。客户端已经收到了 1000 条，连接在第 1001 条时断开。客户端能说“这次订阅成功了 1000 条”吗？不能。流可能只是被中断，服务端可能还会继续产生数据；客户端也不知道最后一条是否完整、服务端是否已经把游标推进。流式调用把“完成”从“收到第一条数据”推迟到了“收到终止状态”，而中途失败会留下部分结果。接口必须定义：部分结果是否可观察、断线后从哪里续传、重复数据是否允许。

场景三：网关把错误压成一个布尔值

网关把下游的 gRPC 调用结果转成 HTTP 响应。为了省事，只要调用没有拿到正常响应，就返回 500 和一句“系统错误”。于是“参数非法”“订单不存在”“库存不足”“连接被拒绝”“截止时间已到”全都被压成同一种错误。客户端看到 500 不知道该不该重试；监控也分不清是业务拒绝多还是网络故障多。节点 acceptance 要求“业务错误与网络状态分层”，就是因为这种压缩会让重试策略、告警和用户体验一起失真。

场景四：截止时间预算被重试吃光

一个请求的端到端预算是 500 毫秒。客户端第一次尝试用了 400 毫秒后超时，然后立刻重试，又给了自己 500 毫秒。结果整个请求耗时 900 毫秒，早就超过了上游给它定的预算。更糟的是，服务端可能仍在处理第一次请求，第二次请求又叠加进来，形成重试放大。截止时间必须是端到端预算，重试要消耗剩余预算，而不是每次尝试都重新获得一份完整预算。

场景五：容量规划只看成功 QPS

监控面板上只统计“成功请求数”和“平均延迟”。当大量请求超时、结果未知时，这些请求没有出现在成功计数里，但服务端可能已经执行了业务逻辑，数据库写入和下游调用都真实发生了。只看成功 QPS，会低估服务端的实际负载，也会漏掉重复副作用。结果未知的请求必须单独计数，重试次数、去重命中数和超时后查询次数也要有指标。

核心概念：从调用点到结果

2.1 本地调用与远程调用的状态差

先看本地函数调用。它有几个默认前提：

  • 调用者和被调用者在同一个地址空间里；
  • 参数传递不经过序列化，通常只是一次寄存器或栈上的复制；
  • 调用要么正常返回一个值，要么抛出异常；
  • 如果进程没有崩溃，返回就意味着函数体已经执行完；
  • 调用没有“在途中”的状态，调用栈本身就是执行状态的记录；
  • 重试一次本地函数，通常只是再执行一遍，副作用是否重复由函数自己决定，至少没有网络这一层不确定性。

远程调用把这些前提逐个打破。一次 RPC 至少经过下面这些阶段：

客户端业务代码
    │  构造请求对象
    ▼
序列化 / 编码
    │
    ▼
连接复用与发送队列
    │
    ▼
内核网络栈  ──────────────►  服务端内核网络栈
                                  │
                                  ▼
                             反序列化 / 分发
                                  │
                                  ▼
                             业务处理
                                  │
                                  ▼
                             提交（写库、扣款、发消息）
                                  │
                                  ▼
                             序列化响应
                                  │
                                  ▼
客户端内核  ◄──────────────  服务端发送
    │
    ▼
反序列化响应
    │
    ▼
返回业务代码

客户端能直接观察到的，只是这条链路两端的几个点：

  • 本地调用是否成功发出；
  • 是否在截止时间之前收到一个完整的响应；
  • 收到的响应里，传输状态是什么；
  • 响应中的业务结果是什么。

客户端观察不到中间发生了什么。请求可能还在发送队列里，可能已经到达服务端但还没开始处理，可能业务已经提交但响应还没发出，也可能响应已经发出但在回程丢失。节点 summary 说“远端调用不等同本地函数”，核心就在这里：本地调用能看到执行，远程调用只能看到消息。

一个常见的错误写法是把远程调用包成“返回值或抛异常”：

Order CreateOrder(const CreateOrderRequest& req) {
    // 看起来像本地函数：成功返回订单，失败抛异常
    auto resp = stub.CreateOrder(req);
    if (!resp.ok()) {
        throw std::runtime_error(resp.error_message());
    }
    return resp.order();
}

这段代码把“传输失败”“业务拒绝”“结果未知”全都塞进异常里。调用者捕获异常后，无法判断该不该重试，也无法知道订单是否已经创建。正确做法是先定义清楚结果类型，再决定每一层怎样映射到异常或错误码。

2.2 请求响应调用

请求响应（很多文档里叫 unary RPC）是最常见的调用模型：

  • 客户端发送一个请求消息；
  • 服务端处理这个请求；
  • 服务端返回一个响应消息；
  • 一次调用在收到响应或收到终止状态时结束。

它的完成点很明确：客户端收到完整的终止状态。 在 gRPC 里，这个终止状态由 status code、status message 和 trailing metadata 组成；响应消息本身只是结果的一部分，不是全部。很多实现把“响应”和“状态”分开传输，就是为了让服务端在返回数据之后还能报告业务结果或错误。

一个请求响应调用可以用下面的时序表示：

客户端                                        服务端
  │                                             │
  │  ── 请求（可能带 deadline）──────────────►  │
  │                                             │  反序列化
  │                                             │  业务处理
  │                                             │  提交
  │  ◄──────────── 响应 + 终止状态 ───────────  │
  │                                             │
  │  反序列化，检查状态                          │
  ▼                                             ▼

请求响应模型有三个容易忽略的细节。

第一，响应消息和终止状态可能不是同一个东西。 有的框架允许服务端先返回响应，再在 trailers 里报告错误；也有的框架把错误放在响应体里。接口定义必须明确：调用者应该先看什么、后看什么，业务错误放在哪里。

第二，响应完整到达之前，调用没有完成。 如果响应传到一半连接断了，客户端可能已经解析出部分字段，但不能把它当成完整结果。反序列化应该等消息完整后再交给业务层，或者明确标记“部分结果不可用”。

第三，请求响应不等于强同步。 客户端在等待响应，服务端可能在异步处理；客户端的线程被阻塞，不代表服务端的执行也在同一个时间线上。超时只影响客户端等待，不会自动停止服务端。

一个更接近真实语义的 C++ 结果类型可以这样定义：

enum class TransportStatus {
    kOk,              // 收到了完整的终止状态
    kUnavailable,     // 连接失败、服务不可达
    kDeadlineExceeded,// 本地等待超时
    kCancelled,       // 调用被取消
    kInternal,        // 框架或对端内部错误
    kUnknown          // 无法归类的传输层失败
};

enum class BusinessCode {
    kOk,
    kInvalidArgument,
    kNotFound,
    kAlreadyExists,
    kFailedPrecondition,
    kPermissionDenied
};

struct CallResult {
    TransportStatus transport;
    BusinessCode business;
    std::string message;
    std::optional<Order> order;
};

这里故意把 transport 和 business 分成两个字段。它们回答的是不同问题：

  • transport：这次调用有没有完成？请求有没有得到对端的明确答复？
  • business：如果完成了，业务操作决定怎么做？

把两者合成一个 bool ok，就会丢掉“结果未知”和“错误属于哪一层”这两类关键信息。

2.3 流式调用

流式调用把“一次请求、一次响应”扩展成“多次消息”。常见有四类：

  • 服务端流式：客户端发一个请求，服务端返回多条响应消息，最后给一个终止状态；
  • 客户端流式：客户端发送多条请求消息，服务端最后返回一个响应；
  • 双向流式：两个方向都可以独立发送多条消息；
  • 半双工式的批量流：客户端发完再半关闭，服务端再陆续返回，语义上仍属于双向流的一种用法。

流式调用的关键不在于“消息多”，而在于完成点被推迟了。在请求响应模型里，收到响应基本就接近完成；在流式模型里，收到第一条消息只说明流建立成功，收到最后一条消息也不一定说明业务成功，必须等终止状态。

服务端流式

服务端流式最常见，例如日志订阅、变更推送、大结果集分页。

客户端                                        服务端
  │  ── 请求 ───────────────────────────────►  │
  │  ◄──────────── 消息 1 ───────────────────  │
  │  ◄──────────── 消息 2 ───────────────────  │
  │  ◄──────────── 消息 3 ───────────────────  │
  │  ◄──────────── 终止状态（OK / 错误）─────  │
  ▼                                             ▼

它有三个语义要点：

  1. 部分结果是可观察的。 客户端可能在收到 3 条消息后遇到错误。这 3 条消息是否有效、能否提交给业务，必须由接口定义。不要假设“流失败 = 所有消息都无效”，也不要假设“已经收到的消息一定完整”。
  2. 终止状态才是最终结论。 一条消息的到达只代表这条消息被传输了，不代表整个操作成功。服务端可能在发完若干条后才发现数据库错误，然后用非 OK 状态终止流。
  3. 流不是原子的。 不能把服务端流式调用当成“返回一个数组”的普通调用。中途失败会留下部分结果，消费方需要有游标、检查点或幂等处理。

客户端流式

客户端流式适合上传、批量写入、聚合计算。客户端可以连续发送多条消息，最后半关闭发送方向，等待服务端返回一个汇总响应。

它的风险点在于提交时机。服务端可能在收完最后一条消息后才提交，也可能边收边写。如果客户端在发送过程中超时或断线，服务端是否已经写入了一部分？答案取决于实现和接口约定，不能靠猜。

节点 practice 要求“画出服务器提交后响应丢失的时序”，这个场景在客户端流式里同样成立，而且更复杂：服务端可能已经提交了前几批数据，最后一条响应却丢了。接口必须能通过请求 ID、批次号或幂等键查询已提交的范围。

双向流式

双向流式两个方向独立，常见于实时协作、双向同步、长连接会话。

它的语义要点是：

  • 两个方向的消息顺序分别在各自的流内保持，但跨方向没有全局顺序；
  • 一方可以半关闭发送方向，仍然继续接收；
  • 任何一方都可以用终止状态结束整个流；
  • 连接中断时，两个方向都可能留下部分已发送、部分已处理的状态；
  • 流量控制是双向的，接收慢会反压发送方。

双向流最容易被误用成“一个永不结束的通道”。设计时必须定义：空闲多久算超时、断线后是否重连、重连后从哪里续传、重复消息如何识别、终止状态如何区分正常结束和故障。

流式调用的状态机

可以把自己的流式客户端简化成下面几个状态：

INIT
  │ 发送请求 / 建立流
  ▼
ACTIVE ──收到消息──► ACTIVE（继续接收）
  │                     │
  │ 收到终止状态         │ 发生传输错误
  ▼                     ▼
TERMINATED_OK       BROKEN（部分结果，状态未知）
  │                     │
  │                     │ 决定是否重连/续传
  ▼                     ▼
结束                  RECONNECTING

注意 BROKEN 不等于 TERMINATED_ERROR。前者表示“流没有正常走完”，后者表示“对端明确告诉你失败了”。两者的处理方式不同：前者可能需要查询或续传，后者至少知道对端的结论。

2.4 传输错误与业务错误

节点 points 的第二条是“传输错误与业务错误”。这不是命名问题，而是分层问题。

可以把一次调用的错误分成三层：

层次 典型例子 回答的问题 常见信号
传输/连接层 连接被拒绝、连接重置、DNS 失败、TLS 握手失败、网络超时 请求有没有到达对端？连接是否可用？ Unavailable、socket 错误、连接池借出失败
框架/协议层 消息格式错误、压缩算法不支持、流量超限、截止时间已到、调用被取消 这次调用有没有完整完成？框架是否拒绝或中止了它？ DeadlineExceeded、Cancelled、ResourceExhausted、Internal
业务层 参数非法、资源不存在、余额不足、状态冲突、权限不足 业务操作决定怎么做？结果是拒绝、冲突还是成功？ InvalidArgument、NotFound、FailedPrecondition、PermissionDenied

在 gRPC 里，这些信息通常通过 status code、status message 和 trailing metadata 表达。Google 的规范把 status code 大致分成几组：

  • 成功：OK；
  • 调用方错误：InvalidArgument、NotFound、AlreadyExists、PermissionDenied、Unauthenticated、FailedPrecondition、OutOfRange、Aborted；
  • 服务端错误：Internal、Unavailable、DataLoss、Unknown；
  • 控制类：DeadlineExceeded、Cancelled、ResourceExhausted、Unimplemented。

这里不要求你背全表，而要求你建立判断顺序：

  1. 先判断这是不是传输/框架层错误。如果是，业务代码通常不应该把它当成“业务拒绝”。
  2. 如果是业务层错误，判断它是否可重试。InvalidArgument 通常不该重试；Aborted 可能表示并发冲突，重试前要重新读取状态；AlreadyExists 在幂等创建场景下甚至可以被当成成功。
  3. 如果错误发生在“请求已发出、响应未收到”的窗口，先把它标成结果未知，再决定查询、重试还是人工处理。

业务错误和传输错误混在一起，会带来两个直接后果：

  • 重试策略失真：把“余额不足”当成网络错误重试，只会重复失败；把“连接重置”当成业务拒绝，则会漏掉本可恢复的调用。
  • 可观测性失真：监控无法区分“服务端拒绝了很多请求”和“网络出了故障”，告警会指向错误的方向。

一个分层的错误模型可以写成：

struct Error {
    enum class Layer { kTransport, kProtocol, kBusiness } layer;
    int code;                 // 传输码或业务码
    std::string message;      // 给人看的描述
    bool retryable;           // 是否允许在满足幂等条件下重试
    std::optional<std::string> retry_after; // 建议退避时间
    std::optional<std::string> request_id;  // 用于查询和对账
};

注意 retryable 不是由错误码单独决定的。即使 Unavailable 通常可重试，如果这次调用是一个非幂等的写操作，也不能直接重试；必须带上幂等键或先查询。这一点会在 2.5 和 2.6 展开。

业务错误放在哪里

业务错误有两种常见表达方式：

  • 带内（in-band）：放在正常响应的字段里，例如响应体中的 error_code；
  • 带外（out-of-band）：放在 RPC 的终止状态或 HTTP 状态码里，例如 gRPC 的 status、HTTP 的 4xx/5xx。

两种方式各有代价：

  • 带内错误让传输层始终保持 OK，客户端必须先解析响应才能知道业务失败；但如果业务错误很多，监控会看到“调用全部成功”，掩盖问题。
  • 带外错误让框架层直接表达失败，便于统一重试和告警；但业务错误和传输错误共用一套状态码时，容易混淆层次。

无论选哪种，接口文档都要明确：

  • 哪些状态码代表业务拒绝；
  • 哪些状态码代表传输/框架故障；
  • 业务错误的详细信息放在哪里；
  • 客户端遇到每一类错误时，允许做什么、不允许做什么。

只写“失败返回错误”是不够的。错误语义必须和调用模型一起设计，否则接口在故障时没有确定行为。

2.5 结果未知

结果未知是 RPC 语义里最容易被低估的状态。它不是“失败”，也不是“成功”，而是：

客户端不知道服务端是否执行了这次操作，也不知道执行到了哪一步。

产生结果未知的常见窗口有：

  • 请求发出后、响应到达前超时：客户端不再等待，但请求可能已经在服务端执行；
  • 连接在请求发出后断开：客户端只看到连接错误，无法确认对端是否收到；
  • 服务端处理完成后，响应在回程丢失：服务端已经提交，客户端什么都没收到；
  • 客户端进程崩溃或重启：内存里的等待状态消失，但服务端的操作可能已经生效；
  • 取消信号与提交发生竞争：客户端发出取消，服务端可能已经越过不可回滚的提交点；
  • 流式调用中途断开：已经传输了一部分消息，后续状态未知。

可以把一次调用的时间线切成几段，看看客户端在每个时刻知道什么：

时刻 客户端观察 服务端实际 客户端能否确定结果
刚构造请求 还没发送 什么都不知道 能确定：未执行
已写入发送缓冲 不知道是否到达 可能还没收到 不能确定
请求已到达服务端 通常不知道 可能开始处理 不能确定
服务端提交完成 通常不知道 已产生副作用 不能确定
响应已发出 还没收到 已提交并回包 不能确定
响应丢失 只看到超时/连接错误 已提交 不能确定
收到完整响应 能看到状态和结果 已提交 能确定

关键结论是：“没收到响应”跨越了多个完全不同的服务端状态。 客户端把超时当成“没执行”，是一种没有依据的推断。

三种投递语义

围绕结果未知，系统设计里常见三种语义：

  • 至多一次（at-most-once）：不重试，最多执行一次。可能失败，但不会因为重试产生重复副作用。适合非幂等写操作在没有幂等保护时的保守选择。
  • 至少一次（at-least-once）：允许重试，保证请求最终至少被处理一次，但可能重复。适合可重复执行的操作，或者消费端有去重的场景。
  • 有效一次（effectively-once）：通过幂等键、去重表或事务性消息，让重复请求产生与一次执行相同的可观察结果。注意这不是“网络上只传了一次”，而是“重复对结果没有额外影响”。

严格意义上的“端到端恰好一次”很难靠单次 RPC 实现，因为网络本身就会丢包、重传和超时。工程上更现实的目标是：允许重复传输，但通过幂等和去重让副作用只发生一次。

解决未知的四种手段

当客户端处于结果未知状态时，不能靠猜，只能靠外部信息收敛：

  1. 按请求 ID 查询：接口提供查询能力，客户端用调用时生成的唯一请求 ID 查询操作状态。
  2. 幂等重试：带上同一个幂等键重试，服务端通过去重表识别重复请求，返回第一次的结果。
  3. 对账：定期比对业务单据和下游记录，发现重复或缺失后修正。适合无法在线查询的场景。
  4. 人工介入：高风险操作在未知状态下转人工审核，不自动重试。

这四种手段都需要接口提前支持。如果接口既没有请求 ID，也没有幂等键，也没有查询能力，那么一旦响应丢失，客户端就永远无法可靠地判断结果。

2.6 截止时间

截止时间（deadline）是调用方愿意等待的最长时间预算。它通常以绝对时间点或剩余时长表示，并随请求传播到服务端。

需要区分两个概念：

  • 超时（timeout）：一个相对的时长，例如“等 2 秒”；
  • 截止时间（deadline）：一个绝对的时间点，例如“必须在 12:00:03.500 之前完成”。

在分布式调用里，截止时间更适合传播，因为每一跳都可以用同一个绝对时间点计算自己还剩多少预算。gRPC 的 deadline 就是这种语义：客户端设置一个时间点，框架把它编码进请求，服务端可以读取剩余时间。

截止时间有三个关键性质。

性质一：截止时间是客户端的等待上限，不是服务端的停止保证

客户端在截止时间到达后停止等待，并可能发送取消信号。但截止时间到达的那一刻，服务端可能：

  • 还没收到请求；
  • 正在处理；
  • 刚刚完成提交；
  • 已经提交但响应还在路上；
  • 已经收到取消信号，但取消发生在提交之后。

因此，超时不代表服务端未执行。这是本节点 acceptance 的第一条。

性质二：取消与提交存在竞争

取消信号是尽力而为的。服务端可能在收到取消之前就已经完成提交，也可能在提交过程中收到取消。接口设计不能假设“客户端取消 = 服务端回滚”。

如果业务需要“取消后一定不生效”，那就要在服务端设置明确的提交点和取消检查点，并使用事务或补偿机制。仅仅依赖 RPC 的取消语义是不够的。

性质三：截止时间要覆盖整条调用链和重试

一个请求的预算不是每次尝试都重新获得的。正确做法是：

总预算 500ms
  ├─ 第一次尝试：最多用 300ms
  ├─ 退避等待：20ms
  ├─ 第二次尝试：最多用剩余 180ms
  └─ 到达总截止时间：停止，返回结果未知或明确失败

如果每次重试都重新设置 500ms，端到端时间会被放大，还可能给服务端制造额外负载。重试次数、退避时间和单次超时都必须从同一个总预算里扣。

一个简单的预算检查可以写成：

using Clock = std::chrono::steady_clock;

struct Deadline {
    Clock::time_point expires_at;

    bool expired() const {
        return Clock::now() >= expires_at;
    }

    std::chrono::milliseconds remaining() const {
        auto left = expires_at - Clock::now();
        if (left <= Clock::duration::zero()) {
            return std::chrono::milliseconds(0);
        }
        return std::chrono::duration_cast<std::chrono::milliseconds>(left);
    }
};

调用前检查 expired()，调用时把 remaining() 传给框架；收到错误后先看剩余预算，再决定能不能重试。不要在重试循环里重新创建一个“完整预算”的 Deadline。

截止时间设多长

截止时间太短，正常请求也会被误判为超时，结果未知的比例上升；太长，故障时客户端会被长时间挂住，资源无法及时释放。合理的截止时间通常来自：

  • 上游给本服务的端到端预算；
  • 本服务各下游调用的预算之和，加上自身处理时间；
  • 真实延迟分布的高分位数，而不是平均值；
  • 故障时的降级策略。

截止时间不是拍脑袋的数字，而是接口契约的一部分。接口文档应该说明：调用方应该设置多长的截止时间，服务端在剩余时间不足时会怎样处理。

2.7 重试与幂等

节点 pitfalls 说：重试一次远程写可能产生重复副作用。 这句话值得单独展开。

重试本身不是坏事。对只读调用、幂等写调用和可去重的消息消费，重试能显著提高成功率。问题在于，很多团队把重试当成默认策略，却没有检查操作是否幂等。

一个非幂等的写操作，重试可能造成：

  • 重复下单、重复扣款、重复发消息；
  • 重复创建资源，返回两个不同的 ID；
  • 计数器被多加一次；
  • 审计日志出现两条相同记录；
  • 下游收到两次通知，产生两次副作用。

安全的写重试通常需要下面三者之一：

  1. 操作本身幂等：例如“把状态设置为已支付”比“给余额加 100”更容易做成幂等。
  2. 幂等键 + 去重表：客户端为每次逻辑操作生成唯一键，服务端记录键和第一次的结果；重复请求直接返回第一次的结果。
  3. 可查询的操作状态：客户端在未知时先查询，确认未执行后再重试。

幂等键的设计要点：

  • 键应该由客户端生成，并在重试时保持不变；
  • 键要能唯一标识一次逻辑操作，而不是一次网络尝试；
  • 服务端要在提交业务数据的同一个事务里写入去重记录，避免“业务成功、去重记录失败”；
  • 去重记录要设置合理的保留时间，太短会漏掉迟到的重试，太长会占用空间；
  • 同一个键的重复请求，如果参数不同，应该返回冲突错误，而不是默默接受。

一个简化的服务端去重逻辑：

struct DedupRecord {
    std::string idempotency_key;
    std::string request_hash;
    Order result;
    bool completed;
};

std::optional<Order> FindCompleted(const std::string& key);

Order CreateOrder(const CreateOrderRequest& req) {
    auto existing = FindCompleted(req.idempotency_key());
    if (existing) {
        if (Hash(req) != existing->request_hash) {
            throw BusinessError::Conflict("same key, different payload");
        }
        return *existing;  // 返回第一次的结果
    }

    auto order = CommitOrder(req);  // 与去重记录同一事务
    SaveDedupRecord(req.idempotency_key(), Hash(req), order);
    return order;
}

注意：真正的实现要把“提交订单”和“写去重记录”放在同一个原子操作里，或者使用事务消息/outbox 保证一致性。上面代码只是展示语义，不是可直接上线的实现。

重试还需要退避和抖动：

  • 固定间隔重试会让大量客户端同时冲击故障服务；
  • 指数退避能降低持续压力，但要有上限；
  • 抖动可以打散重试时间；
  • 重试次数和总预算要有限制，避免重试风暴；
  • 服务端返回 Retry-After 或类似提示时，应该尊重它。

2.8 把可观察结果写进接口

节点 practice 要求：画出服务器提交后响应丢失的时序，给接口定义可观察结果。

“可观察结果”的意思是：客户端在拿不到原始响应时，仍然有办法通过接口确认操作状态。常见设计有三种。

方案一：创建操作资源

写操作不直接返回最终对象，而是返回一个操作 ID：

POST /orders
  request_id = 客户端生成的唯一 ID
  -> 202 Accepted
     operation_id = ...

客户端随后用 operation_id 查询：

GET /operations/{operation_id}
  -> PENDING / SUCCEEDED / FAILED
     result = ...

这样即使创建响应丢失，客户端也能用 request_id 或 operation_id 查询最终状态。关键是 request_id 必须由客户端生成并在重试时复用。

方案二：按业务键查询

如果业务本身有唯一键，例如订单号、支付单号、消息 ID，可以让客户端用这个键查询：

CreateOrder(request_id, ...) -> Order
GetOrderByRequestId(request_id) -> Order | NotFound

当客户端超时后，先调用 GetOrderByRequestId：

  • 查到，说明第一次已经成功；
  • 查不到，并且确认查询本身可靠，才可以考虑重试；
  • 查询也失败，保持未知，进入对账。

要注意“查不到”并不总是等于“没执行”。如果查询走了只读副本，可能有复制延迟；如果查询本身超时，仍然未知。接口文档要说明查询的一致性级别。

方案三：幂等重试

客户端直接用同一个幂等键重试，服务端保证重复请求不产生新的副作用。这是最简单的使用方式，但要求服务端实现去重，并且去重记录与业务提交保持一致。

无论哪种方案，接口都应该明确列出可观察状态：

状态 含义 客户端动作
UNKNOWN 客户端没有拿到明确结论 查询、幂等重试或对账
PENDING 服务端已接受，尚未完成 轮询或等待通知
SUCCEEDED 操作已提交，结果可用 使用结果
FAILED 操作明确失败，未提交 按错误码处理
DUPLICATE 检测到重复请求，返回已有结果 使用第一次的结果

这张表比一句“成功/失败”更能指导调用方写代码。

2.9 流式调用里的失败处理

流式调用的失败处理要额外考虑“部分结果”。

服务端流式

  • 客户端收到部分消息后流中断：已收到的消息可能有效，也可能不完整；
  • 需要为消息设计序号或游标，便于判断缺口和续传；
  • 终止状态要区分“正常结束”和“异常中断”；
  • 如果业务要求原子性，流式本身不提供，需要在消费端做缓冲和提交点。

客户端流式

  • 客户端可能在发送到一半时断线，服务端已收到的部分数据可能已被处理；
  • 需要批次号、序号或幂等键，避免重连后重复提交；
  • 服务端要定义“收到多少才算一批”“什么时候提交”；
  • 最终响应要能告诉客户端哪些数据已接受、哪些需要重发。

双向流

  • 两个方向独立，任一方向出错都可能导致整个流终止；
  • 要定义半关闭语义：一方说“我不再发了”，另一方是否还能继续发；
  • 要定义空闲超时、心跳和重连策略；
  • 重连后要能续传，而不是从头再来；
  • 重复消息要有去重机制。

一个流式消费的伪代码：

Stream stream = stub.Subscribe(request);
std::string cursor = load_checkpoint();

while (stream.Receive(&msg)) {
    if (msg.sequence() <= cursor_sequence) {
        continue;  // 重复消息，跳过
    }
    if (msg.sequence() != cursor_sequence + 1) {
        // 发现缺口，不能假装连续
        request_resume(cursor_sequence);
        break;
    }
    process(msg);
    cursor_sequence = msg.sequence();
    save_checkpoint(cursor_sequence);  // 提交点
}

auto status = stream.Finish();
if (!status.ok()) {
    // 部分结果已处理，但流未正常结束
    mark_unknown_and_resume(cursor_sequence);
}

这段代码的重点不是 API 细节，而是三个原则：有序号、有检查点、终止状态单独判断。

常见误区与设计权衡

误区一：把远程调用当成有返回值的本地函数

auto order = client.CreateOrder(req);  // 看起来像本地调用

这行代码隐藏了序列化、网络、超时、重试和未知状态。调用者很容易写出“返回了就是成功，抛异常就是失败”的逻辑。

更准确的写法是把调用结果建模成显式的状态：

auto result = client.CreateOrder(req, deadline);
switch (result.transport) {
    case TransportStatus::kOk:
        // 已拿到明确终止状态，再看业务码
        break;
    case TransportStatus::kDeadlineExceeded:
        // 结果未知：不能断言失败，也不能断言成功
        break;
    case TransportStatus::kUnavailable:
        // 可能没到达，也可能到达了但回包失败；写操作要谨慎
        break;
    default:
        break;
}

透明封装本身没有错，错的是封装之后不暴露失败和时间预算。节点 tradeoffs 说“透明封装提高使用便利，但必须暴露失败与时间预算”，就是要求接口在便利和可判断之间取得平衡。

误区二：超时等于服务端没有执行

这是本课最重要的一条。超时只说明客户端等不下去了。服务端可能：

  • 还没开始处理；
  • 正在处理；
  • 已经提交；
  • 已经提交并发出响应，只是响应丢了。

如果业务代码在超时后直接重试非幂等写操作，就可能产生重复副作用。正确做法是先进入“结果未知”状态，再按接口提供的能力查询、幂等重试或对账。

误区三：收到响应就等于业务成功

响应消息只是传输层交付的内容。它可能包含业务错误字段，也可能服务端先返回数据、再用终止状态报告失败。调用者必须同时检查：

  • 传输是否完整；
  • 终止状态是否 OK；
  • 业务码是否表示成功；
  • 响应内容是否满足业务不变量。

只看“有响应”或只看 HTTP 200，都不够。

误区四：重试是提高可用性的万能药

重试对瞬时故障有效，但对下面这些情况没有帮助，甚至有害：

  • 参数非法、权限不足等确定性业务错误；
  • 服务端已经过载，重试会加剧拥塞；
  • 非幂等写操作，重试会产生重复副作用；
  • 截止时间已经耗尽，重试只会拖长整体延迟。

重试前要同时满足：错误可重试、操作幂等或有幂等键、剩余预算足够、重试次数未超限。

误区五：流式调用失败时，已收到的数据都可以直接用

流式调用不是原子的。已经收到的消息可能：

  • 是完整的，可以安全处理；
  • 只传输了一部分，反序列化后字段不完整；
  • 属于一个最终失败的操作，业务上不应提交；
  • 在断线重连后重复出现。

接口必须定义部分结果的处理规则。消费端要有检查点、序号和去重，不要假设“收到多少算多少”。

误区六：把业务错误和网络错误压成同一个状态

把“库存不足”和“连接超时”都返回 500，会让调用方无法决定是否重试。库存不足重试一万次也不会成功；连接超时则可能换个实例就能成功。

错误分层不是为了好看，而是为了让调用方做出正确动作。至少要把下面几类分开：

  • 调用方参数错误；
  • 业务状态冲突；
  • 权限/认证问题；
  • 对端暂时不可用；
  • 截止时间耗尽；
  • 结果未知。

权衡一：透明封装与显式失败

透明的客户端让业务代码写起来像本地调用，降低学习和接入成本。但过度透明会隐藏失败语义，让调用者误以为只有成功和失败两种结果。

更好的平衡是：

  • API 保持简单；
  • 结果类型显式区分传输状态和业务状态；
  • 截止时间作为显式参数；
  • 文档明确未知状态和重试规则；
  • 提供查询/幂等能力，而不是只提供一个裸调用。

权衡二：带内错误与带外错误

带内错误让传输层总是成功，响应结构统一，但监控和重试需要解析业务体；带外错误让框架直接表达失败，便于统一处理，但业务错误和传输错误容易混在同一套状态码里。

选择时要考虑：

  • 调用方是否统一由框架处理错误；
  • 业务错误是否需要携带复杂结构化详情；
  • 监控是否需要按错误层聚合；
  • 是否需要跨语言、跨协议映射。

没有绝对正确的选择，但必须保持一致，并在接口文档里写清楚。

权衡三：重试提高成功率与放大负载

重试能掩盖瞬时故障，提高成功率；但在故障期间，重试会放大流量，可能把“局部故障”变成“雪崩”。

控制手段包括：

  • 只对可重试错误重试；
  • 指数退避加抖动；
  • 限制重试次数和总预算；
  • 服务端提供重试提示；
  • 使用重试预算，而不是无限重试；
  • 对非幂等操作禁用自动重试。

权衡四：短截止时间与长截止时间

短截止时间能快速释放资源、降低尾延迟，但会增加误超时和结果未知；长截止时间能容忍慢请求，但故障时资源占用更久，用户体验更差。

截止时间应该由端到端预算决定，而不是每个服务各自拍脑袋。上游给下游的预算要逐跳扣减，重试也要从同一预算里扣。

权衡五：流式的实时性与可恢复性

流式调用能实时推送，但断线后恢复复杂。要支持续传，就需要：

  • 消息序号或游标；
  • 服务端保留一段时间的历史；
  • 客户端保存检查点；
  • 重复消息去重；
  • 过期游标的处理策略。

这些都会增加服务端存储和接口复杂度。如果业务可以接受“断线后从头再来”，设计会简单很多；如果不能，就必须为可恢复性付出成本。

动手实践：画出服务器提交后响应丢失的时序，给接口定义可观察结果

本节点的 practice 是：画出服务器提交后响应丢失的时序，给接口定义可观察结果。

这个实践不要求你搭一个完整的生产级 RPC 框架，但要求你把语义想清楚，并用可运行的小实验验证。最终产物应该包括：

  • 一张带时间戳的时序图；
  • 一张客户端/服务端状态对照表；
  • 一份接口定义，明确请求 ID、幂等键和查询能力；
  • 一段可运行的模拟代码，能复现“提交后响应丢失”；
  • 一组测试，证明有幂等保护时不会产生重复副作用；
  • 一张错误分层与重试决策表。

第一步：建立目录

cd /tmp/rpc-semantics

/tmp/rpc-semantics/

第二步：画提交后响应丢失的时序

假设客户端在 t0 发起 CreateOrder，服务端在 t4 完成数据库提交，在 t5 发出响应，响应在回程丢失，客户端在 t7 到达截止时间。

时间轴       客户端                         网络                          服务端
  t0   构造请求，生成 request_id
  t1   序列化并发送  ──────────────►
  t2                                     请求到达
  t3                                                     反序列化，开始处理
  t4                                                     提交订单（不可回滚点）
  t5                                     响应发出  ◄────── 序列化响应
  t6          ✗ 响应丢失（回程）
  t7   截止时间到达，停止等待
       客户端观察：DeadlineExceeded
       服务端实际：订单已提交
       客户端是否知道结果：不知道

图上要标出三个关键点：

  1. 提交点 t4：从这一刻起，服务端的副作用已经生效，即使客户端取消也不能自动撤销。
  2. 响应丢失点 t6：客户端没有收到任何业务数据，连接可能表现为超时或重置。
  3. 截止时间 t7：客户端放弃等待，但这只是客户端的动作，不是服务端的状态。

如果使用 gRPC，可以在图旁边标注：客户端最终拿到的是 DEADLINE_EXCEEDED，而服务端数据库里已经有一条订单。这正是“超时不代表服务端未执行”的具体形态。

第三步：写状态对照表

把每个时刻的“客户端认为”和“服务端实际”写下来：

时间 客户端认为 服务端实际 结果是否确定
t0 尚未发送 无 确定未执行
t1 已发送，等待 可能未收到 不确定
t3 等待响应 正在处理 不确定
t4 等待响应 已提交 不确定
t6 等待响应或已超时 已提交，响应丢失 不确定
t7 调用失败 已提交 客户端仍不知道

这张表是后面接口设计的依据：只要客户端处于“不确定”区间，接口就必须提供收敛未知状态的手段。

第四步：定义接口和可观察结果

一个只返回 Order 的接口是不够的。建议定义三个能力：

service OrderService {
  // 创建订单。request_id 和 idempotency_key 由客户端生成。
  rpc CreateOrder(CreateOrderRequest) returns (CreateOrderResponse);

  // 按客户端请求 ID 查询，用于超时后确认第一次是否成功。
  rpc GetOrderByRequestId(GetOrderByRequestIdRequest)
      returns (GetOrderByRequestIdResponse);
}

message CreateOrderRequest {
  string request_id = 1;        // 逻辑请求唯一 ID，重试时不变
  string idempotency_key = 2;   // 幂等键，重试时不变
  string user_id = 3;
  string sku = 4;
  int32 quantity = 5;
}

message CreateOrderResponse {
  string order_id = 1;
  string request_id = 2;
  OrderState state = 3;
}

message GetOrderByRequestIdRequest {
  string request_id = 1;
}

message GetOrderByRequestIdResponse {
  bool found = 1;
  string order_id = 2;
  OrderState state = 3;
}

enum OrderState {
  ORDER_UNKNOWN = 0;
  ORDER_PENDING = 1;
  ORDER_COMMITTED = 2;
  ORDER_FAILED = 3;
}

接口语义要写清楚：

  • CreateOrder 成功返回，表示订单已提交，order_id 可用；
  • 如果客户端收到 DEADLINE_EXCEEDED，不能推断订单未创建，应调用 GetOrderByRequestId；
  • 如果查询返回 found = true，说明第一次请求已经产生订单，客户端应使用该结果；
  • 如果查询返回 found = false，并且查询本身是成功的，才可以在幂等键保护下重试；
  • 如果查询也失败，保持 UNKNOWN，进入对账或告警；
  • 重复的 idempotency_key 必须返回第一次的结果，而不是创建新订单；
  • 同一个幂等键但参数不同，返回冲突错误。

这里的“可观察结果”不是一句口号，而是 GetOrderByRequestId 这个具体能力。没有它，客户端在响应丢失后只能盲目重试。

第五步：实现最小模拟器

下面是一个不依赖 gRPC 的模拟器骨架。它把服务端提交和响应丢失显式建模：

#include <chrono>
#include <iostream>
#include <map>
#include <optional>
#include <string>
#include <vector>

using Clock = std::chrono::steady_clock;

enum class TransportStatus {
    kOk,
    kUnavailable,
    kDeadlineExceeded,
    kCancelled
};

struct Order {
    std::string order_id;
    std::string request_id;
    std::string sku;
};

struct CreateOrderRequest {
    std::string request_id;
    std::string idempotency_key;
    std::string sku;
};

struct CreateOrderResponse {
    TransportStatus transport;
    std::string order_id;
    std::string message;
};

class OrderServer {
public:
    explicit OrderServer(bool dedup_enabled)
        : dedup_enabled_(dedup_enabled) {}

    CreateOrderResponse CreateOrder(const CreateOrderRequest& req) {
        if (dedup_enabled_) {
            auto it = by_key_.find(req.idempotency_key);
            if (it != by_key_.end()) {
                ++dedup_hits_;
                return {TransportStatus::kOk, it->second.order_id, "duplicate"};
            }
        }

        Order order;
        order.order_id = "order-" + std::to_string(next_id_++);
        order.request_id = req.request_id;
        order.sku = req.sku;

        orders_.push_back(order);          // 模拟提交
        by_request_[req.request_id] = order;
        if (dedup_enabled_) {
            by_key_[req.idempotency_key] = order;
        }
        return {TransportStatus::kOk, order.order_id, "created"};
    }

    std::optional<Order> GetByRequestId(const std::string& request_id) const {
        auto it = by_request_.find(request_id);
        if (it == by_request_.end()) {
            return std::nullopt;
        }
        return it->second;
    }

    int order_count() const { return static_cast<int>(orders_.size()); }
    int dedup_hits() const { return dedup_hits_; }

private:
    bool dedup_enabled_;
    int next_id_ = 1;
    int dedup_hits_ = 0;
    std::vector<Order> orders_;
    std::map<std::string, Order> by_request_;
    std::map<std::string, Order> by_key_;
};

客户端模拟：

CreateOrderResponse CallWithResponseLoss(OrderServer& server,
                                         const CreateOrderRequest& req,
                                         bool drop_response) {
    auto server_result = server.CreateOrder(req);
    if (drop_response) {
        // 服务端已经提交，但响应在回程丢失
        return {TransportStatus::kDeadlineExceeded, "", "response lost"};
    }
    return server_result;
}

这里的 CallWithResponseLoss 故意模拟“服务端执行成功、客户端只看到超时”。真实网络里，这个超时可能来自丢包、延迟、连接重置或框架等待超时，但对客户端的语义是一样的：结果未知。

第六步：复现重复副作用

先关闭去重，模拟客户端超时后自动重试一次：

int main() {
    const std::string request_id = "req-1001";

    {
        OrderServer server(/*dedup_enabled=*/false);
        CreateOrderRequest req{request_id, "key-1001", "sku-A"};

        auto first = CallWithResponseLoss(server, req, /*drop_response=*/true);
        std::cout << "first transport=" << static_cast<int>(first.transport)
                  << " orders=" << server.order_count() << "\n";

        // 客户端不知道第一次是否成功，直接重试
        auto second = CallWithResponseLoss(server, req, /*drop_response=*/false);
        std::cout << "second transport=" << static_cast<int>(second.transport)
                  << " order_id=" << second.order_id
                  << " orders=" << server.order_count() << "\n";
    }

    {
        OrderServer server(/*dedup_enabled=*/true);
        CreateOrderRequest req{request_id, "key-1001", "sku-A"};

        auto first = CallWithResponseLoss(server, req, /*drop_response=*/true);
        auto found = server.GetByRequestId(request_id);
        std::cout << "after loss found=" << (found ? "yes" : "no")
                  << " orders=" << server.order_count() << "\n";

        auto second = CallWithResponseLoss(server, req, /*drop_response=*/false);
        std::cout << "retry order_id=" << second.order_id
                  << " orders=" << server.order_count()
                  << " dedup_hits=" << server.dedup_hits() << "\n";
    }
}

预期输出类似：

first transport=2 orders=1
second transport=0 order_id=order-2 orders=2
after loss found=yes orders=1
retry order_id=order-1 orders=1 dedup_hits=1

第一组说明：客户端重试一次，服务端产生了两个订单，这就是节点 pitfalls 说的重复副作用。

第二组说明：带幂等键时，第一次虽然响应丢失，但订单已经存在；重试命中去重，返回同一个 order-1，订单数量仍然是 1。

注意第二组里客户端先用了 GetByRequestId 查询。实际系统可以查询后再决定，也可以直接用幂等键重试；两种方式都要求服务端有对应的能力。

第七步：加入截止时间和取消

现在模拟“服务端在截止时间之后才完成提交”：

struct Deadline {
    Clock::time_point expires_at;

    bool expired() const { return Clock::now() >= expires_at; }
};

CreateOrderResponse CallWithDeadline(OrderServer& server,
                                     const CreateOrderRequest& req,
                                     Deadline deadline,
                                     bool server_commits_after_deadline) {
    if (deadline.expired()) {
        return {TransportStatus::kDeadlineExceeded, "", "expired before send"};
    }

    if (server_commits_after_deadline) {
        // 模拟客户端已经超时，服务端仍然完成了提交
        auto result = server.CreateOrder(req);
        return {TransportStatus::kDeadlineExceeded, "", "committed after deadline"};
    }

    return server.CreateOrder(req);
}

测试时记录三件事：

  1. 客户端拿到的传输状态；
  2. 服务端实际订单数量；
  3. 用 request_id 查询是否能找到订单。

一个典型的结论表：

场景 客户端状态 服务端订单数 查询结果
正常完成 OK 1 找到
截止时间前未提交 DeadlineExceeded 0 未找到
截止时间后提交 DeadlineExceeded 1 找到
提交后响应丢失 DeadlineExceeded 1 找到

第三行和第四行是 acceptance 的核心证据：客户端看到的是超时，但服务端确实执行了。只有查询或幂等重试才能收敛状态。

题 1：流式调用的部分结果

问题：客户端调用一个服务端流式接口，收到 10 条消息后连接断开。请回答：

  1. 客户端能否断言这次调用成功？为什么？
  2. 已收到的 10 条消息是否一定可以提交给业务？
  3. 接口应该提供哪些信息，才能支持断线续传？
  4. 如果业务要求“要么全部生效、要么全部不生效”，流式调用本身能提供这个保证吗？

答案：

  1. 不能。收到消息只说明这些消息被传输了，调用还没有收到正常终止状态；连接断开意味着流没有正常走完，结果可能是部分成功或未知。
  2. 不一定。消息可能完整，也可能只是部分传输；即使完整，它们也可能属于一个最终失败的操作。接口必须定义部分结果是否有效。
  3. 至少要有消息序号或游标、服务端保留历史的能力、客户端检查点、重复消息去重规则，以及过期游标的处理方式。
  4. 不能。流式调用不是原子的，中途失败会留下部分结果。业务原子性要靠消费端缓冲、事务提交点或补偿机制实现，不能指望流本身。

题 2：超时与服务端提交

问题：客户端在 t1 发出 CreateOrder，服务端在 t4 提交，响应在 t5 丢失，客户端在 t7 超时。请回答：

  1. 客户端在 t7 能得出什么结论？
  2. 服务端在 t7 的实际状态是什么？
  3. 客户端直接重试一次，可能发生什么？
  4. 接口应该提供什么能力，才能让客户端安全处理这个局面？

答案：

  1. 只能得出“没有在截止时间前收到明确响应”。不能断言成功，也不能断言失败，应标记为结果未知。
  2. 订单已经提交。超时只是客户端的等待上限，不是服务端回滚。取消信号即使发出，也可能发生在提交之后。
  3. 如果是非幂等写操作，可能创建第二笔订单，产生重复副作用；如果服务端已经过载，还会放大负载。
  4. 提供客户端生成的请求 ID 和幂等键、按请求 ID 查询操作状态的能力，以及明确的重复请求处理规则。客户端应查询或幂等重试，而不是盲目重试。

题 3：业务错误与网络状态分层

问题：网关收到下游的四种结果：Unavailable、InvalidArgument、DeadlineExceeded、AlreadyExists。请回答：

  1. 它们分别属于哪一层？
  2. 哪些通常可以重试，哪些通常不应重试？
  3. AlreadyExists 在什么情况下可以被当成成功？
  4. 如果网关把它们全部映射成 HTTP 500，会有什么问题？

答案：

  1. Unavailable 属于传输/可用性层；InvalidArgument 属于业务层（调用方错误）；DeadlineExceeded 属于框架/控制层，且通常意味着结果未知；AlreadyExists 属于业务层。
  2. Unavailable 通常可重试，但写操作要有幂等保护；DeadlineExceeded 只能在剩余预算足够且操作幂等时重试，优先查询状态；InvalidArgument 不应重试；AlreadyExists 一般不应盲目重试，除非接口把它定义为幂等创建的成功结果。
  3. 在幂等创建场景下，如果客户端用同一个幂等键重试，而第一次已经创建成功，那么返回 AlreadyExists 或直接返回第一次的结果都可以被视为成功语义；但接口必须明确规定，不能让调用方猜。
  4. 调用方无法区分该不该重试，监控无法区分业务拒绝和网络故障，告警和容量规划都会失真；还可能把可恢复的瞬时故障误报成服务端崩溃。

题 4：重试、幂等与截止时间

问题：一个写接口的端到端预算是 500 毫秒。客户端第一次尝试 300 毫秒后超时，自动重试，又给了自己 500 毫秒。请回答：

  1. 这样设置截止时间有什么问题？
  2. 重试前应该检查什么？
  3. 幂等键应该由谁生成，重试时是否变化？
  4. 服务端去重记录和业务提交不一致，会有什么后果？

答案：

  1. 重试重新获得了完整预算，端到端时间可能变成 800 毫秒以上，超过上游预算；还会在服务端可能仍在处理第一次请求时叠加第二次请求。
  2. 检查错误是否可重试、操作是否幂等或有幂等键、总预算还剩多少、重试次数是否超限，以及第一次是否可能已经提交。
  3. 幂等键应由客户端生成，用来标识一次逻辑操作；重试时必须保持不变。每次网络尝试可以有不同 attempt ID，但逻辑请求 ID 和幂等键不变。
  4. 可能出现“业务已提交、去重记录没写”或“去重记录写了、业务没提交”的不一致：前者导致重试重复执行，后者导致重试拿到一个并不存在的结果。两者都应在同一事务或可靠 outbox 中处理。

本课小结

  1. RPC 是包装，不是本地函数。 它经过序列化、连接复用、网络、服务端调度和响应回传；调用点看起来简单，底层状态并不简单。这是本节点 summary 的核心。
  2. 远端调用有三种结果状态。 成功、失败之外还有结果未知；把“没收到响应”直接当成失败，是没有依据的推断。
  3. 请求响应的完成点是终止状态。 响应消息不等于全部结果，必须同时检查传输完整性、终止状态和业务码。
  4. 流式调用把完成点推迟到流结束。 部分结果可能有效，也可能属于最终失败的操作；接口必须定义部分结果、检查点、续传和去重。
  5. 传输错误与业务错误要分层。 传输层回答“调用有没有完成”，业务层回答“操作决定怎么做”；混成同一个布尔值会让重试和监控失真。
  6. 超时不代表服务端未执行。 提交可能发生在截止时间之前，取消也可能发生在提交之后。这是 acceptance 的第一条。
  7. 结果未知只能靠外部信息收敛。 请求 ID 查询、幂等重试、对账和人工介入，都需要接口提前支持。
  8. 重试远程写可能产生重复副作用。 这是节点 pitfalls。重试前必须确认操作幂等或有幂等键，并且剩余预算足够。
  9. 截止时间是端到端预算。 重试要从同一预算里扣，不能每次尝试都重新获得完整时间；截止时间还要传播到服务端。
  10. 可观察结果要写进接口。 practice 要求给接口定义可观察结果：请求 ID、幂等键、查询接口和明确的状态语义，缺一不可。
  11. 透明封装必须暴露失败和时间预算。 这是节点 tradeoffs。便利性不能以丢失失败语义为代价。
  12. 流式调用要按流设计。 序号、游标、检查点、终止状态和重复消息处理，是流式可靠性的基本要素。
  13. 观测要能区分层次和未知。 按状态码、重试、去重命中、超时后查询和流中断位置分别统计，才能定位问题。
  14. 本课服务于“设计能处理部分故障的服务 API”。 先承认远端调用有三种状态，再把错误分层、时间预算、幂等和查询写进接口，最后用模拟器验证响应丢失和重试的真实行为。

本课的主线可以压缩成一句话：请求响应和流式调用决定完成点，传输错误与业务错误决定分层，结果未知和截止时间决定重试与查询；接口只有把这三件事都写清楚，才能在部分故障下保持可判断。
