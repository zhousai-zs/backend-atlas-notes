边界说明

本课讨论的是通用的重试工程方法。文中涉及的内容后台、推送、素材拉取、图文发布、阅读计数等场景均为教学假设，用于帮助理解通用后台问题，不代表任何具体公司的真实架构或实现细节。

关于 gRPC 重试的具体字段名、默认值、上限和状态码判定，请以你所使用版本的官方文档和对应语言实现为准；本课只引用公开文档中的稳定要点，不猜测未公开行为，也不编造节点字段或验收标准。

本课不涉及具体框架的私有配置，也不提供可直接照抄的生产参数。所有数字都是为了说明放大效应而设定的教学示例。

导读

一个直觉例子：电话占线

你给客服打电话，听到“您拨打的电话正忙”。

  • 立刻狂拨：挂断、重拨、挂断、重拨……每秒钟拨十次。对方线路并没有因此更快空出来，反而可能因为你和其他人一起猛拨而更忙。
  • 隔一会儿再拨：等几秒，再试一次；如果还忙，就等更久一点。线路恢复后，你大概率能接通。
  • 一群人同时重拨：如果一万个人都采用“立刻狂拨”，交换机承受的呼叫量会在故障瞬间暴涨，本来只是短暂占线，可能演变成大面积打不通。

重试的直觉就在这里：失败后什么时候再试、试多少次、谁有资格试，比“要不要重试”更重要。没有节奏的重试，是把一次失败变成一场风暴。

一条教学调用链

假设一个通用内容后台的读路径：

客户端
  └─> API 网关
        └─> 图文服务
              └─> 阅读计数存储

某个时刻，计数存储出现约 2 秒的抖动，请求开始超时。如果链路上每一层都“失败就重试 3 次”，那么一次客户端请求在最坏情况下会变成：

1 次客户端请求
  × 3（网关重试）
  × 3（图文服务重试）
  × 3（计数存储客户端重试）
  = 27 次对计数存储的尝试

这还只是一个客户端。若入口有 10000 QPS，且大家都在同一时间重试，下游看到的瞬时尝试量可能是原来的数倍到数十倍。重试没有创造新的容量，只是把未来的请求提前堆到同一时刻。

错误做法与正确做法对照

场景 错误做法 正确做法
下游超时 立即原地重试，间隔为零 先判断错误是否可重试，再用退避加抖动拉开时间
写操作失败 不区分幂等性，直接重发 非幂等写默认不盲目重试，或先做去重 / 幂等键
多层调用 每一层都独立重试 3 次 明确重试归属层，限制总尝试次数和总时限
故障持续 无限重试直到成功 受整体 deadline 约束，预算耗尽就快速失败
大面积抖动 所有客户端同步重试 加入随机抖动，打散重试峰值
可观测性 只记录最终失败 记录尝试次数、退避时长、失败分类和重试预算

本课三条主线

  1. 可重试错误分类：哪些失败值得再试，哪些重试只会放大问题。
  2. 指数退避和抖动：如何让重试在时间上散开，而不是整齐地冲击下游。
  3. 重试预算与多层放大：如何给重试设总闸门，避免每层都重试造成乘法级放大。

学习目标

完成本课后，你应当能够：

  1. 能解释可重试错误分类，区分瞬态故障、永久错误和结果未知的写操作。
  2. 能独立完成：模拟下游短暂故障，对比立即重试与退避加抖动的请求峰值。
  3. 说明指数退避中“第 n 次重试前等待多久”的基本计算方式，并解释为什么必须加入随机抖动。
  4. 识别多层调用链中重试被乘法放大的路径，估算最坏情况下的尝试次数。
  5. 为一个具体接口写出重试策略：重试资格、最大尝试次数、退避上限、总时限和预算。
  6. 解释重试与 deadline 的关系，判断“剩余时间还够不够再试一次”。
  7. 说明为什么非幂等写不能盲目重试，以及可以用什么方式降低重复副作用。
  8. 设计重试相关的观测指标，能在故障复盘时说清放大来自哪一层。

提示：目标 1 和目标 2 是本节点的核心验收方向；其余目标用于把策略落到工程细节。

为什么后端要懂

防止故障时多层重试压垮服务。

这句话说的不是“重试不好”，而是：重试在正常情况下几乎不可见，在故障时却会决定系统是缓慢恢复还是彻底雪崩。

故障时流量为什么会反而上升

在没有重试的系统里，下游变慢，入口流量大致不变，压力是“平的”。

一旦加入重试，链路就多了一个正反馈：

下游变慢 / 超时
  -> 客户端认为失败，发起重试
  -> 下游收到更多请求，排队更长、超时更多
  -> 更多客户端认为失败，发起更多重试
  -> 负载继续上升

这就是重试风暴的典型形态。它不需要代码有 bug，只需要“失败就重试”这个看似合理的默认行为，再叠加一个已经过载的下游。

更麻烦的是亚稳态：系统可能在一个高负载、高重试、高错误率的区间里维持很久。即使最初的抖动只有 2 秒，重试带来的额外请求也可能让下游一直缓不过来；等抖动结束，积压和重试还在继续，恢复时间被显著拉长。

放大来自“乘法”，不是“加法”

单层重试的放大是线性的：最多尝试 maxAttempts 次。

多层重试的放大是乘法的：

入口尝试数 ≈ 客户端尝试 × 网关尝试 × 服务内尝试 × ...

教学假设：客户端、网关、图文服务、计数存储客户端各重试 3 次，那么一次入口请求在最坏情况下对应 3 × 3 × 3 × 3 = 81 次下游尝试（如果四层都独立重试）。即使只有三层，也是 27 次。

所以工程上必须回答一个问题：这个请求应该由哪一层负责重试？ 通常应尽量在靠近失败点、且掌握幂等语义的一层做有限重试，而不是每层都“顺手加一个重试”。

与上一课 deadline 的关系：重试花的是剩余预算

上一课讲 deadline：一个请求有整体截止时间，超过就必须放弃。

重试不是免费的，它消耗的正是这份剩余预算：

剩余时间 = deadline - 已经过去的时间
一次重试的成本 ≈ 退避等待 + 本次尝试的最长耗时

如果剩余时间不够“退避 + 一次有意义的尝试”，那么重试只会做两件坏事：

  1. 占用连接、线程或协程资源，挤占本可以成功的请求；
  2. 在客户端已经不再等待结果时，仍然向下游发送流量。

公开的 gRPC 文档也明确：重试受整体 deadline 约束。换句话说，deadline 是重试的上位规则，不是并列选项。设计重试策略时，先问“还剩多少时间”，再问“还值不值得试”。

一个教学时间线：2 秒抖动如何变成峰值翻倍

设定（全部为教学假设）：

  • 入口稳定在 10000 QPS；
  • 下游计数存储出现 2 秒 抖动，期间请求超时；
  • 客户端采用“失败立即重试一次”的策略，不考虑退避。

正常 2 秒内，入口本来会发出：

10000 QPS × 2 s = 20000 次请求

抖动发生后，这 20000 次请求失败并立即重试，于是下游在相近的时间窗口内看到：

原始 20000 次 + 重试 20000 次 = 40000 次尝试

瞬时尝试速率从约 10000 QPS 抬到约 20000 QPS，峰值翻倍。如果客户端重试 3 次，最坏情况下尝试量还会继续上升；如果网关和服务内也重试，放大会按层数相乘。

而如果采用“指数退避 + 抖动”，同样这批请求会被打散到更长的时间窗口里：

  • 第一次重试等待一个较小的随机区间；
  • 后续重试等待逐步变长，但有上限；
  • 不同客户端抽到不同的随机值，不会在同一毫秒一起冲进去。

结果不是“重试次数变少”，而是重试的瞬时密度变低，给下游留出恢复空间。这正是退避和抖动存在的意义。

重试是一项策略，不是一行 for 循环

很多事故的起点，是把重试写成这样一句直觉代码：

for (int i = 0; i < 3; ++i) {
  if (call()) return ok;
}
return failed;

这段代码只回答了“试几次”，却没有回答真正重要的问题：

  • 谁可以重试：这个错误是瞬态的，还是参数错误、权限错误这类重试也不会好的永久错误？
  • 写操作能不能重试：这次调用是否幂等？重复执行会不会多扣一次、多发一条、多记一次阅读？
  • 等多久：退避从多少开始，增长多快，上限多少？
  • 如何打散：有没有随机抖动，避免所有实例同步重试？
  • 总共试几次：最大尝试次数是否包含首次？多层之间如何避免乘法放大？
  • 什么时候必须停：整体 deadline 还剩多少？重试预算是否已经耗尽？
  • 失败后怎么观测：能否区分“首次失败”“重试成功”“重试耗尽”，并在复盘时定位放大层？

所以本课把重试视为一个策略对象：它至少包含重试资格、次数上限、退避与抖动、总时限、预算和可观测性。缺了任何一项，重试都可能在某个故障时刻从“救命”变成“加速器”。

下一节开始进入核心概念：我们先建立错误分类，再看退避与抖动的计算，最后讨论预算和多层放大如何一起约束。

把这些问题写清楚，比多写一个 for 循环更重要；它们也构成了本课后续实验的观察维度。

核心概念

重试不是“失败就再来一次”的默认动作，而是一套三问策略：这次失败值不值得重试？应该等多久再试？最多允许多少请求被放大？它们分别对应错误分类、退避抖动和重试预算。

教学假设：下文的公众号后台、推送、素材拉取、图文发布和阅读计数，都是通用后台场景的举例，不代表任何真实系统实现。gRPC 参数与行为以所用版本文档为准。

1. 可重试错误分类

重试只对“再试一次可能成功，且再试不会造成重复副作用”的失败有意义。要同时看两个维度：

  • 错误是否瞬态：网络抖动、短暂过载可能恢复；参数错误、权限错误通常不会。
  • 操作是否幂等：同一请求执行多次与执行一次的效果相同，才可以安全地重复发送。
错误/场景 是否可重试 理由 注意
连接拒绝、建连超时 是，谨慎 请求通常还没到达服务端应用逻辑，重试有机会成功 服务整体不可用时重试会加剧拥塞，必须有退避和预算
UNAVAILABLE 是，前提是操作安全 常见于连接抖动、实例切换等瞬态问题 也可能是过载信号；非幂等写先确认是否已提交
RESOURCE_EXHAUSTED / HTTP 429 限流 有条件 服务端明确表示容量不足 优先遵守服务端 Retry-After 或 gRPC pushback；没有提示的立即重试会放大限流
DEADLINE_EXCEEDED 有条件 若总 deadline 还有余量且操作幂等，仍可能成功 若总预算已耗尽，重试没有意义；若请求已发出且结果未知，非幂等写危险
INVALID_ARGUMENT / HTTP 400 否 请求本身不合法，重试不会改变结果 应修正参数或调用方式，属于契约或客户端问题
NOT_FOUND 一般否 资源不存在通常是确定性结果 如果读的是最终一致副本，是否短暂等待应由业务明确决定，不能默认重试
PERMISSION_DENIED 否 权限或凭证问题不会因重试消失 检查授权链路，避免把鉴权失败变成额外流量
INTERNAL / HTTP 500 有条件 可能是瞬时内部错误，也可能已经产生副作用 只对幂等操作重试，并保留错误上下文和 trace
请求已发出但响应丢失 未知 服务端可能已经执行，只是响应没有回来 非幂等写不能盲目重试，必须用幂等键或查询确认结果

一个关键分界是“请求有没有到达服务端应用逻辑”。请求尚未离开客户端，或明确未到达服务端应用时，重试通常几乎总是安全的；请求已经发出但结果未知时，风险取决于操作是否幂等。gRPC 的透明重试就属于前一种情况：请求还没有离开客户端，或没有到达服务端应用逻辑，因此可以安全地再发。相反，一旦客户端收到响应头，这次调用在语义上就被视为已提交（committed），不应再重试；具体行为以所用版本文档为准。

DEADLINE_EXCEEDED 要特别小心。它可能表示单次尝试超时，也可能表示整个调用预算已经耗尽。只有“整个 deadline 还有足够余量”时，重试才有意义；如果剩余时间连一次最小尝试都放不下，应该直接失败。重试始终受整体 deadline 约束。

幂等性决定了“能不能重发”

读请求、按主键覆盖的 PUT、带幂等键的写，通常可以重试。教学假设中的“素材列表查询”是读，“把素材标题覆盖为某个值”是幂等写，都可以在预算内重试。

但“阅读数 +1”“发送一条推送”“扣费”这类操作不是天然幂等的：同一个请求执行两次，副作用就发生两次。正确做法不是“绝不重试”，而是让它可以安全重试：

  • 客户端为一次业务操作生成稳定的幂等键，重试时复用同一个键。
  • 服务端用唯一索引、条件写或事务保存“键 → 已执行结果”，同一个键再次到来时返回第一次的结果。
  • 幂等键要和业务操作绑定，不能每次重试换一个新键。

下面是一个保守的分类示意。真实系统还要结合错误详情、操作语义和服务端能力调整。

from enum import Enum

class Op(Enum):
    READ = "read"
    IDEMPOTENT_WRITE = "idempotent_write"
    NON_IDEMPOTENT_WRITE = "non_idempotent_write"

FINAL_CODES = {"INVALID_ARGUMENT", "NOT_FOUND", "PERMISSION_DENIED"}
SAFE_CONNECT_CODES = {"CONNECT_REFUSED", "CONNECT_TIMEOUT"}

def is_retryable(err, op, deadline_left_s, min_try_s=0.05):
    if deadline_left_s <= min_try_s:
        return False
    code = getattr(err, "code", "")
    sent = getattr(err, "request_sent", True)
    if op is Op.NON_IDEMPOTENT_WRITE:
        if sent:
            return False
        return code in SAFE_CONNECT_CODES
    if code in FINAL_CODES:
        return False
    if code == "RESOURCE_EXHAUSTED":
        return getattr(err, "retry_after_s", None) is not None
    return code in SAFE_CONNECT_CODES | {
        "UNAVAILABLE", "DEADLINE_EXCEEDED", "INTERNAL"
    }

服务端去重的教学示意如下。生产实现必须保证“检查 + 写入结果”的原子性，通常依赖唯一索引、事务或条件更新，不能只用普通字典。

class DedupStore:
    def __init__(self):
        self._results = {}

    def execute_once(self, idem_key, fn):
        if idem_key in self._results:
            return self._results[idem_key]
        result = fn()
        self._results[idem_key] = result
        return result

gRPC 的 retryableStatusCodes 是一个显式白名单：只有配置中列出的状态码才允许重试。它不是“所有错误都自动重试”。maxAttempts 包括首次尝试，公开文档中该值上限被限制为 5；initialBackoff、maxBackoff、backoffMultiplier 和 retryableStatusCodes 要一起配置。再次强调，具体字段与上限以所用版本文档为准。

2. 指数退避和抖动

如果一次失败后立刻重试，所有同一时刻失败的客户端会在下一个瞬间再次同时打向下游。下游本来只是因为短暂过载而失败，却会被“整齐划一”的重试波峰再打一次。指数退避解决“越失败等越久”，抖动解决“大家不要在同一毫秒一起醒”。

把第 n 次重试的基准等待时间记为：

backoff_n = min(base × multiplier^(n-1), cap)

若把 n 从 0 开始编号，也可以写成 backoff_n = min(base × multiplier^n, cap)。两者只差一个下标。以 base=100ms、multiplier=2、cap=2s 为例：

第 n 次重试 计算 基准等待（不含抖动）
1 100ms × 2^0 100ms
2 100ms × 2^1 200ms
3 100ms × 2^2 400ms
4 100ms × 2^3 800ms
5 100ms × 2^4 1600ms
6 min(3200ms, 2000ms) 2000ms
7 min(6400ms, 2000ms) 2000ms

没有抖动时，同一批失败会共享同一条时间表。假设 1000 个客户端同时因为一次 200ms 的下游抖动失败，它们会在 100ms、200ms、400ms 等时刻形成整齐的请求波峰，波峰高度甚至可能接近原始流量。抖动把每个客户端的等待随机化，让重试流量摊平。

常见抖动方式：

方式 等待公式 特点
无抖动 backoff_n 简单，但同步失败时容易形成重试波峰
Full jitter（全抖动） random(0, backoff_n) 分布最分散，平均等待更短；gRPC 文档中的重试等待采用这种形式
Equal jitter（等量抖动） backoff_n/2 + random(0, backoff_n/2) 保留至少一半的退避时间，分散程度较小
Decorrelated jitter（去相关抖动） min(cap, random(base, prev × 3)) 带状态、相邻等待去相关，适合波动较大的场景；不是 gRPC 文档的默认形式

选择抖动方式时，不要只看“平均延迟”。更重要的是峰值流量、尾延迟和预算消耗。教学上可以先用 full jitter 做基线，再用压测数据比较 equal jitter 或 decorrelated jitter 是否更合适。随机数生成器应各自独立，避免所有实例使用同一个固定种子。

一个重要的细节是：抖动是在基准退避之上做随机化，不应把总时限也随机掉。等待时间必须和剩余 deadline 比较；如果剩余预算不足以“等待 + 再尝试一次最小请求”，应当直接放弃，而不是先睡完再发现已经超时。

下面是带“总尝试次数上限 + 总时限上限 + 服务端提示”的重试循环示意。fn(left) 应使用传入的剩余时间设置本次调用的 deadline；server_hint(err) 把服务端 pushback 或 Retry-After 统一换算成秒，负值表示服务端要求不要重试。

import random
import time
from dataclasses import dataclass

@dataclass
class RetryPolicy:
    max_attempts: int = 4
    base_s: float = 0.1
    multiplier: float = 2.0
    cap_s: float = 2.0
    min_try_s: float = 0.05

def backoff(policy, retry_no):
    nominal = min(
        policy.base_s * policy.multiplier ** (retry_no - 1),
        policy.cap_s,
    )
    return random.uniform(0, nominal)

def call_with_retry(fn, policy, deadline_s, should_retry, server_hint=None):
    started = time.monotonic()
    attempts = 0
    while True:
        attempts += 1
        left = deadline_s - (time.monotonic() - started)
        if left <= policy.min_try_s:
            raise TimeoutError("deadline budget exhausted")
        try:
            return fn(left)
        except Exception as err:
            left = deadline_s - (time.monotonic() - started)
            if attempts >= policy.max_attempts:
                raise
            if not should_retry(err, left):
                raise
            wait_s = backoff(policy, attempts)
            if server_hint is not None:
                hint_s = server_hint(err)
                if hint_s is not None:
                    if hint_s < 0:
                        raise
                    wait_s = hint_s
            if left <= wait_s + policy.min_try_s:
                raise
            time.sleep(wait_s)

这里的 attempts 包括首次尝试，因此 max_attempts=4 表示最多 1 次首发 + 3 次重试。deadline_s 是整次业务调用的总预算，不是单次尝试的超时。真实客户端还应把剩余 deadline 传给下游，避免在本地已经超时后，下游还在继续执行。

尊重服务端反馈能显著降低无效重试：HTTP 429 可带 Retry-After；gRPC 服务端可通过 grpc-retry-pushback-ms 告诉客户端延后重试，或表示不要再重试。客户端应把这类提示纳入等待计算，而不是机械执行自己的退避表。解析细节和边界行为以所用版本文档为准。 gRPC service config 中可以配置 retryPolicy。下面只是字段示意，字段名、默认值和上限以所用版本文档为准：

{
  "methodConfig": [{
    "name": [{"service": "content.PushService", "method": "Send"}],
    "retryPolicy": {
      "maxAttempts": 4,
      "initialBackoff": "0.1s",
      "maxBackoff": "2s",
      "backoffMultiplier": 2.0,
      "retryableStatusCodes": ["UNAVAILABLE", "RESOURCE_EXHAUSTED"]
    }
  }]
}

配置里有三点值得注意：maxAttempts 包括首次尝试；公开文档把该值上限限制为 5；retryableStatusCodes 是白名单，只列出真正希望重试的状态码。不要把非幂等写配置成可重试，也不要把所有 5xx 都无条件列入。整体 deadline 仍然是最终约束，重试不能突破它。

另有对冲（hedging）策略：它会在未收到响应时额外发出请求，用更多容量换尾延迟。它通常只适合幂等读，而且必须受整体预算约束；非幂等写不应使用。具体配置与行为以所用版本文档为准。

3. 重试预算与多层放大

教学假设：一个请求从网关进入内容服务，再调用素材服务，最后访问存储。如果这四层各自配置“最多尝试 3 次”，最坏放大如下：

串联层数 n 最坏尝试次数 3^n 直观含义
1 3 每个请求最多被本层放大 3 倍
2 9 上游一次请求可能变成 9 次下游尝试
3 27 放大继续按乘法增长
4 81 一次入口请求可能压出 81 次底层尝试

这是最坏上界，实际次数取决于失败发生在哪一层、哪些尝试被短路。但只要每层独立重试，放大就是乘法关系，而不是加法关系：每层都“只重试几次”，合起来就可能形成重试风暴。

处理原则是只在一层重试，并默认放在最外层，也就是直接面向业务语义的那一层。理由是最外层最了解操作是否幂等、用户可见的总 deadline 和业务降级策略；它可以统一施加最大尝试次数、总时限和重试预算，避免内层再次放大。若团队选择靠近故障的层重试，则必须关闭其他层的重试，并让该层拿到完整预算；不要“每层都稍微重试一下”。

其他层应快速失败，并把“不可重试”或“预算耗尽”的信号透传给上层。信号可以通过错误分类、错误详情或内部上下文约定表达，具体载体由团队协议决定；关键是不要让内层在不知情的情况下继续重试。

重试预算限制重试请求占总请求的比例。教学值：不超过 10%。它不是每个请求自己算，而是按下游服务或方法共享一个预算；否则每个请求都以为自己只占 10%，总体仍会放大。

一个简单的令牌桶实现是：正常成功请求补充 ratio 个令牌，ratio=0.1 表示 10 次成功供 1 次重试；每次重试消耗 1 个令牌；容量限制突发。预算不足时直接失败，不要换一层继续尝试。

class RetryBudget:
    def __init__(self, ratio=0.1, capacity=100.0):
        self.ratio = ratio
        self.capacity = capacity
        self.tokens = capacity

    def allow_retry(self):
        return self.tokens >= 1.0

    def on_retry(self):
        self.tokens = max(0.0, self.tokens - 1.0)

    def on_success(self):
        self.tokens = min(self.capacity, self.tokens + self.ratio)

初始容量带来一定的突发能力，生产上还可以叠加时间衰减或滑动窗口。这个教学实现只表达“成功补充、重试消耗、容量封顶”的核心思想，不代表任何特定框架的内置算法。 gRPC 还提供服务级重试限流 retryThrottling：maxTokens 是令牌上限，tokenRatio 是成功时补充的令牌数。公开文档语义是每次失败令牌减 1，每次成功加 tokenRatio，令牌数不高于 maxTokens/2 时停止重试；具体边界以所用版本文档为准。

设 maxTokens=10、tokenRatio=0.1，初始有 10 个令牌：

阶段 计算 令牌数 是否允许重试
初始 - 10 是
连续 5 次失败 10 - 5 5 否，达到一半阈值

另一段同样从 10 个令牌开始：

阶段 计算 令牌数 是否允许重试
先 4 次失败 10 - 4 6 是
再 10 次成功 6 + 10 × 0.1 7 是
再 3 次失败 7 - 3 4 否

这组数字说明：失败会让重试预算快速收缩，成功只会缓慢恢复。它和客户端的指数退避、抖动、单层重试是互补关系，而不是替代关系。预算耗尽时直接快速失败，比“再试一下”更符合整体利益。

重试前还应看下游健康度。熔断器在错误率或延迟超过阈值时进入 open，直接快速失败；冷却期后进入 half-open，只放少量探测流量。配合负载感知，下游返回 429 时主动降速，而不是继续加码。指标至少观察重试率、重试成功率、预算拒绝率和重试耗尽率；如果重试率很高但重试成功率很低，通常说明策略正在放大故障。

三点收束：错误分类回答“能不能重试”，退避与抖动回答“何时重试”，预算与单层约束回答“最多放大多少”。可重试不等于应该重试；非幂等写不盲目重试；总尝试次数和总时限都要有上限；只在选定的一层重试，并让预算随下游健康度收缩。做到这些，重试才是恢复手段，而不是故障放大器。

常见误区与设计权衡

所有层都重试会形成乘法级请求放大。

积极重试提高短暂故障成功率，也增加成本和恢复压力。

乘法级放大与恢复期亚稳态

重试不是“免费的成功率”。只要请求链路上有多个环节各自重试，尝试次数就会相乘，而不是相加。以教学假设的通用内容后台为例：接入层、业务服务、下游依赖各重试 3 次，那么一个用户请求在最坏情况下会变成 3 × 3 × 3 = 27 次下游尝试。故障越靠近底层，放大越明显；如果每层还把“重试次数”理解为“额外重试 3 次”，实际倍数还会更大。

更危险的是恢复阶段。下游刚从短暂故障中恢复时，容量往往还没有完全回到正常水平，而此时积压请求、超时请求和层层重试会同时涌入。第一波重试把刚恢复的下游再次打满，请求继续失败并继续重试，形成“恢复—过载—再失败”的亚稳态。系统看起来一直在恢复，实际却长时间回不到稳定状态。

因此，重试策略必须把“谁可以重试、重试几次、总共允许多少时间、失败如何记账”放在一起考虑，而不是在每个调用点各自写一个 for 循环。多层共享预算、限制总尝试次数，并给重试加上退避与抖动，才能避免把局部故障升级为全局过载。

积极重试与保守重试的权衡

维度 积极重试 保守重试
短暂故障成功率 较高，能覆盖更多瞬时抖动 较低，部分本可恢复的请求会失败
尾延迟 可能更高，失败请求占用更久 更可控，快速失败或有限等待
下游压力 更大，故障时放大明显 更小，给下游留出恢复空间
成本 更高，CPU、连接、日志和下游配额都被消耗 更低，但可能增加业务失败成本
恢复时间 故障初期看似更快，严重时可能延长整体恢复 单请求更慢，但整体恢复更稳

选择哪一侧，取决于接口是否幂等、业务是否能接受失败、下游容量和整体 deadline。读请求通常可以更积极；非幂等写、计数类操作和已经接近 deadline 的请求应更保守。积极与保守不是道德判断，而是对“成功率、尾延迟、下游压力、成本、恢复时间”的显式取舍。

高频误区（对错对照）

误区一：失败后在 for 循环里立即重试，不等待。 错。立即重试会在下游仍然故障时瞬间制造数倍流量，把一次短暂抖动变成持续过载。 对。至少加入有上限的指数退避，并用抖动打散重试时刻；重试之间要检查整体 deadline。

误区二：只要退避了，就不需要抖动。 错。所有客户端使用同样的 base 和倍数，会在同一时刻一起重试，形成周期性的“重试脉冲”。 对。使用 full jitter 或等效随机化，让重试到达时间分散开；抖动范围要可解释、可测试。

误区三：所有失败都可以重试，包括非幂等写。 错。教学假设中的“重复推送”“阅读数 +1”这类操作，如果响应丢失后盲目重试，可能造成重复推送或重复计数。 对。先判断操作是否幂等；非幂等写需要幂等键、去重表或业务侧唯一约束，无法保证时不要自动重试。

误区四：只限制重试次数，不限制总时限，超过 deadline 还在重试。 错。次数上限不能防止单次调用耗时过长；已经超过整体 deadline 的重试只会浪费资源，并让调用方更晚拿到失败。 对。同时设置 max attempts 和总 deadline，每次重试前检查剩余时间，剩余预算不足时直接放弃。

误区五：每一层都重试，而且各层不共享预算。 错。接入层、业务层、依赖层各自重试会形成乘法放大，故障时总尝试次数可能远超预期。 对。约定只在一层重试（本课默认放在掌握业务语义与总 deadline 的最外层），其余层快速失败并透传「不要重试」；或让各层共享重试预算/令牌。

误区六：把 4xx 参数错误也当成可重试错误。 错。参数错误、鉴权失败、资源不存在等通常不会因为重试而改变，重试只会放大无效请求。 对。只对明确的瞬态错误重试，例如 UNAVAILABLE、超时等；具体状态码分类以协议和所用框架文档为准。

本节使用配套练习 practice87（随课附 practice87.tar.gz）：单机 Python 3 标准库、离散时间模拟、无需网络、一秒内跑完。目标不是实现生产级重试库，而是把「策略差异」变成可重复观察的数字：在同样的短暂故障下，立即重试、无抖动退避、退避加抖动分别会把多少请求同时推到下游。

文件 作用

idem.py 「阅读数 +1」响应丢失场景：盲重试 / 分类拒绝 / 幂等键

实验模型

  • N = 1000 个在途请求在 t ∈ [0, 5ms) 内同时失败——模拟「下游实例突然挂掉，一批请求同时报 UNAVAILABLE」（教学假设：比如一次推送后大量用户同时打开文章，请求同一个计数服务）。
  • 下游在 [0, 0.8s) 故障，返回 UNAVAILABLE；0.8s 之后恢复。
  • 恢复后下游容量为每 10ms 桶 200 个请求；超出容量的请求同样失败（过载）。
  • 按 10ms 时间桶统计到达下游的请求数：retry_peak_per_10ms 只统计重试请求的峰值，after_recovery_peak 统计恢复后最拥挤的一个桶。
  • 三种策略都设置 max_attempts = 5（包含首次尝试）和总时限 deadline = 4s：下一次重试的时刻若会超过总时限，直接放弃。

步骤 2：读懂三种策略

def next_delay(strategy, attempt, rng, base=0.2, mult=2.0, cap=2.0):
    """attempt: 已经失败的次数(1 起)。返回下一次重试前的等待秒数。"""
    if strategy == "immediate":
        return 0.010                          # 失败后 10ms 立刻再打
    b = min(base * mult ** (attempt - 1), cap)  # 200ms, 400ms, 800ms, 1.6s, 2s...
    if strategy == "backoff":
        return b                              # 无抖动：所有人同一张时间表
    if strategy == "backoff_jitter":          # full jitter: random(0, b)
        return rng.uniform(0, b)
    raise ValueError(strategy)

模拟主循环用一个最小堆按时间顺序处理每一次尝试：

while events:
    t, cid, att = heapq.heappop(events)       # (时间, 客户端, 第几次尝试)
    k = int(t / BUCKET); buckets[k] = buckets.get(k, 0) + 1
    success = t >= outage_end and buckets[k] <= CAPACITY
    if success:
        ok += 1; continue
    if att >= max_attempts:                   # 上限 1：总尝试次数
        give_up += 1; continue
    nt = t + next_delay(strategy, att, rng)
    if nt >= deadline:                        # 上限 2：总时限
        give_up += 1; continue
    heapq.heappush(events, (nt, cid, att + 1))

注意两道闸：att >= max_attempts 和 nt >= deadline，分别对应验收「总尝试次数与总时限有上限」。

实测输出（固定种子 42，你的机器上应完全一致）：

immediate       retry_peak_per_10ms= 1000 @  10ms after_recovery_peak=   0 total= 5000 amp=5.00 success=0.000 give_up=1000 max_att=5 max_t=0.045s
backoff         retry_peak_per_10ms= 1000 @ 200ms after_recovery_peak=1000 total= 4800 amp=4.80 success=0.400 give_up= 600 max_att=5 max_t=3.005s
backoff_jitter  retry_peak_per_10ms=   86 @ 150ms after_recovery_peak=  28 total= 4619 amp=4.62 success=0.907 give_up=  93 max_att=5 max_t=2.372s

怎么读：

  1. immediate：5 次尝试在 45ms 内全部用完，每 10ms 桶都是 1000 个请求——下游故障期间流量放大 5 倍，而故障要 800ms 才结束，所以成功率为 0。立即重试既没救回请求，又把下游打得更狠。
  2. backoff（无抖动）：等待拉长了，但 1000 个请求在 200ms、600ms、1.4s、3.0s 整齐地成波到达，每波 1000 个。1.4s 那波下游已恢复，但容量只有 200/10ms，于是 800 个因过载再次失败——这就是「恢复时被重试波峰打回去」。
  3. backoff_jitter：同样的退避上限，只是每个客户端在 [0, b) 里随机取等待，重试峰值从 1000 降到 86，恢复后最拥挤的桶只有 28，成功率 0.907。
  4. amp（总尝试 / 请求数）三者接近：抖动不是靠「少试」，而是靠「错开」。

步骤 5：幂等实验

python3 idem.py

blind_retry      result=OK               attempts=2 server_calls=2 count=2
classify_no_key  result=FAILED_NO_RETRY  attempts=1 server_calls=1 count=1
idempotency_key  result=OK(dup)          attempts=2 server_calls=2 count=1
classify: {'UNAVAILABLE': False, 'INVALID_ARGUMENT': False, 'DEADLINE_EXCEEDED': False} unsent: True

服务端第一次已经 count += 1，但响应丢了（RESPONSE_LOST）：

  • blind_retry：盲目重试，阅读数被加了两次（count=2）——这就是要避免的事故。
  • classify_no_key：is_retryable 判定「已发出、结果未知、非幂等」→ 不重试，直接把失败交给上层（count=1）。
  • idempotency_key：同一业务操作复用同一个幂等键，服务端识别重复并返回 OK(dup)，可以安全重试（count=1）。
  • 最后一行：对非幂等写，已发出的 UNAVAILABLE / DEADLINE_EXCEEDED 都不重试；只有「请求从未发出」才安全。

迁移到 gRPC 时，用 service config 的 retryPolicy（maxAttempts、initialBackoff、maxBackoff、backoffMultiplier、retryableStatusCodes）表达本实验的 backoff_jitter，用 retryThrottling（maxTokens、tokenRatio）表达 budget.py 的令牌；只把幂等方法配置为可重试；所有重试仍受整体 deadline 约束。字段、默认值和可用性以所用版本文档为准。

把结论带回设计

  • 先判断接口是否幂等，再决定是否允许自动重试；非幂等写优先补幂等键，而不是用重试掩盖语义问题。
  • 再确定只在哪一层重试，避免每层各自重试。
  • 然后设置 max attempts 与总 deadline，二者缺一不可。
  • 最后选择退避参数与抖动方式，并用峰值、恢复后峰值、成功率和放弃数验证。

  7. 查找服务端 pushback 的响应元数据，确认延后与停止两种语义。
  8. 查找 retryThrottling 的令牌规则，写出失败、成功与停止重试三个分支。
  9. 查找 hedgingPolicy，核对它与 retryPolicy 能否同时出现，以所用版本文档为准。
  10. 回到 deadline/timeout 章节，确认重试与总时限的约束关系。
  11. 用本文“自测题”第 1、3 题检验自己是否真的读懂了放大与预算。

逐项核对清单

  • maxAttempts：包括首次尝试在内的总尝试次数上限；公开文档中该值被限制为 5。写配置时不要把它理解成“额外重试 4 次”。
  • initialBackoff、maxBackoff、backoffMultiplier：共同决定每次重试前的等待区间。
  • retryableStatusCodes：只对这些状态码重试；不在列表里的失败直接返回。
  • 退避公式：第 n 次重试前随机等待 random(0, min(initialBackoff * backoffMultiplier^(n-1), maxBackoff))，上限由 maxBackoff 截断。
  • 已提交（committed）：收到响应头后，这次调用视为已提交，不再重试。也就是说“请求可能已经被处理”之后不该再赌一次。
  • 透明重试：当请求尚未离开客户端，或尚未到达服务端应用逻辑时，gRPC 可以做透明重试；它与 maxAttempts、限流令牌如何计数，以所用版本文档为准。
  • pushback：服务端可用 grpc-retry-pushback-ms 告知客户端延后多久再重试，或不再重试。
  • retryThrottling：maxTokens 与 tokenRatio；每次失败令牌减 1，每次成功加 tokenRatio；令牌数不高于 maxTokens/2 时停止重试。
  • hedgingPolicy：对冲请求是另一套并发策略，与 retryPolicy 的关系以所用版本文档为准，不要凭记忆混用。
  • deadline：重试受整体 deadline 约束，退避等待也在这条时间线内消耗预算。

读文档时带着的四个问题

  • 这个错误是否保证请求尚未被处理？如果无法保证，重试就可能造成重复副作用。
  • 这次重试会不会被客户端库、框架拦截层或网关中的另一层再次放大？
  • 退避等待是否计入同一个 deadline？用户还能等多久？
  • 故障持续时由谁负责停止：令牌不足、预算耗尽，还是人工开关？

自测题

题 1：四层调用链的乘法放大

题干：一条调用链有 4 层，每层对下游最多尝试 3 次。下游完全故障时，假设每层都独立重试且不共享预算，最底层大约会收到多少次请求？应如何修改？

答案：3^4 = 81 次。修改方向是只保留一层重试，其余层把错误透传；同时叠加重试预算与总时限。

解析：第一层 3 次尝试，每次都会触发第二层的 3 次，再乘第三、第四层，得到 3×3×3×3=81。这就是 pitfalls 所说的“所有层都重试会形成乘法级请求放大”。更糟的是，下游越慢，放大持续越久，恢复期还要承受这批积压请求。可行做法：

  • 只在最外层或最靠近用户的一层重试，内层一律不重试；
  • 重试只针对可重试错误分类，且次数、退避、总时限都有上限；
  • 用重试预算或令牌桶限制故障期间的额外流量；
  • 通过请求头携带“已重试”标记，避免下游再次放大。

对应验收：总尝试次数与总时限有上限。

题 2：阅读数 +1 能否自动重试

题干：给“文章阅读数 +1”的接口在超时后自动重试是否安全？如果不安全，怎么改？

答案：不安全。超时只说明客户端没等到响应，不说明服务端没执行；自动重试可能重复计数。应使用幂等键/去重表，或改为可重放的计数事件。

解析：超时是典型的“结果未知”状态。首次请求可能已经写入成功，只是响应丢了；此时重试会再加 1。可选的工程手段：

  • 客户端生成幂等键（如 请求 ID + 文章 ID），服务端按键去重，重复请求返回首次结果；
  • 计数改为“事件 + 聚合”，用唯一事件 ID 保证同一阅读事件只计一次；
  • 对确实需要强一致的场景，先查询再写入并不可靠，仍要靠服务端去重；
  • 明确不可幂等写不盲目重试，只对可安全重放的读请求或幂等写重试。

对应验收：不可幂等写不盲目重试。

题 3：抖动与总时限

题干：为什么退避要加抖动？full jitter 的公式是什么？只设尝试次数、不设总时限会有什么问题？

答案：抖动把同时失败的大量客户端错开，避免同一时刻再次冲击下游。full jitter 可写为 sleep = random(0, min(initialBackoff * backoffMultiplier^(n-1), maxBackoff))。只设次数不设总时限，会让重试在用户早已超时后继续占用资源，并拖长故障恢复。

解析：

  • 没有抖动时，同一批请求会在相同退避点同时重试，形成新的尖峰，即“重试风暴”。
  • 抖动让等待时间落在区间内随机分布，把尖峰摊平；gRPC 公开文档给出的正是从 0 到当前退避上限的随机等待。
  • 次数上限只约束“每次调用最多试几次”，不约束一次调用在墙上时钟里待多久；若下游持续超时，退避会累积，请求可能远超用户可接受时延。
  • 因此需要同时设置单次调用 deadline、总尝试次数上限和可选的预算，并让重试等待计入 deadline。

对应验收：总尝试次数与总时限有上限。

本课小结

  • 重试能恢复部分瞬态故障，但每次重试都是额外的下游流量，收益与风险必须一起看。
  • 可重试错误分类是第一步：只对明确的瞬态失败重试，不可幂等写不盲目重试。
  • 指数退避要有上限和抖动；第 n 次重试前等待 random(0, min(initialBackoff * backoffMultiplier^(n-1), maxBackoff))。
  • 重试预算与多层放大是同一个问题的两面：层数越多，乘法放大越危险，通常只让一层重试。
  • 已提交（committed）之后不再重试；服务端可用 pushback 让客户端延后或停止重试。
  • retryThrottling 用令牌控制故障期间的额外流量：失败减 1，成功加 tokenRatio，令牌不高于 maxTokens/2 时停止重试。
  • 重试受整体 deadline 约束，总尝试次数与总时限都要有上限，这正是本课验收的核心。
  • 公开文档只描述协议与库的语义，不能据此推断任何企业内部 RPC 实现；字段与默认值以所用版本文档为准。
