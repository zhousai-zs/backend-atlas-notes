第 7/208 课：复杂度与实验分析

领域 A · 阶段 1 · 数据结构与算法 · 基础 · 前置：第 6 课「编译与链接」

一句话：渐近复杂度描述的是输入规模增长时资源消耗的趋势，不是延迟的预测。分析时要讲清输入分布、最坏情况和常数成本，再用实验验证。

一、学习目标和为什么后端要懂

学完这一课你应该能： 1. 解释时间复杂度和空间复杂度； 2. 独立完成实验：测量线性扫描、二分查找随输入规模增长的耗时曲线； 3. 推导嵌套循环的复杂度，并解释为什么小数据下的快慢会和大 O 不一致。

为什么后端要懂：在加机器之前，先识别出算法级的瓶颈。比如公众号后台要判断一个用户是否在某个号的粉丝集合里：粉丝从 1 万涨到 1000 万，O(n) 扫描的耗时会涨 1000 倍，加 10 台机器也追不上；换成 O(log n) 或 O(1) 的结构，问题直接消失。

二、核心要点：从直觉到原理

1. 时间和空间复杂度

直觉：别问"跑多少毫秒"，问"数据翻 10 倍，工作量翻几倍"。

复杂度 n 翻 10 倍时工作量 后台例子
O(1) 不变 哈希表按 openid 查用户
O(log n) 只多几步 有序数组二分、B+ 树索引
O(n) ×10 遍历整个粉丝列表
O(n log n) 约 ×13 对消息按时间排序
O(n²) ×100 两两比较做消息去重

原理：大 O 只保留增长最快的项，丢掉常数和低阶项：3n² + 100n + 7 记为 O(n²)。

推导嵌套循环（验收要求）：数清最内层语句执行了多少次。

for i in range(n):          # n 次
    for j in range(i, n):   # n-i 次
        work()              # 合计 n + (n-1) + ... + 1 = n(n+1)/2，所以是 O(n²)

i = 1
while i < n:                # i 每次翻倍，循环 log₂n 次
    for j in range(n):      # 每次 n 次
        work()              # 合计 n·log n，所以是 O(n log n)

空间复杂度同理，算的是额外用掉的内存。消息去重用 set 记已见的 msg_id：时间 O(n)，空间 O(n)；先排序再比较相邻项：空间可以做到 O(1)（原地排序），但时间变成 O(n log n)。

2. 最坏、平均与摊还

同一个算法，换个输入，代价可能完全不同，所以说复杂度时必须说是哪一种。

  • 最坏：线性查找目标在最后或者根本不存在，要比较 n 次。对延迟敏感的接口（看 P99）要关心最坏。
  • 平均：目标均匀随机分布时，平均比较约 n/2 次。前提是你说清楚了输入分布；真实流量往往不均匀，比如热门大号的请求远多于普通号。
  • 摊还：一串操作的总代价分摊到每次。Python list.append 偶尔扩容要拷贝全部元素（O(n)），但容量按比例增长，所以 n 次 append 总共 O(n)，摊还每次 O(1)。注意，摊还 O(1) 不等于每次都快：扩容的那一次就是一个延迟尖刺。

3. 常数、数据分布和规模

大 O 把常数丢了，但真实机器上常数很重要： - 常数：每一步的成本不同，比如 CPU 缓存命中与否（回顾第 3 课的内存层次）、解释执行还是 C 实现、有没有函数调用。 - 数据分布：二分查找要求数据有序；如果每次都得先排序，就要付 O(n log n)。哈希表在冲突严重时会退化。 - 规模：n 小时常数主导，n 大时增长趋势主导。

我在 box 上实测的纯 Python 版本，单次查找平均纳秒数如下：

n 线性扫描 纯 Python 二分
4 129 208
8 161 244
16 235 296
64 697 424

n ≤ 16 时 O(n) 反而更快，到 64 才反超。这就是"小数据下快慢与大 O 不一致"：二分每步要算中点、多做分支，常数更大。所以很多标准库的排序在小区间里会改用插入排序。

三、常见误区和设计权衡

误区 - ❌ 从一次小规模测试推断渐近行为。n=1000 跑一次、两者都是"零点几毫秒"，看不出任何趋势；必须扫多个数量级，并且重复测量。 - ❌ 把大 O 当延迟预测。O(log n) 只说明增长慢，不说明一定是多少毫秒。 - ❌ 只看平均。接口超时看的是最坏情况和尾延迟。 - ❌ 测量方法有错，比如计时只包住了一部分代码，或者把构造数据的时间也算进去。

权衡：降低复杂度可能增加内存和实现复杂度。 - 用哈希集合去重，查询 O(1)，但每个元素有额外的内存开销； - 维护有序数组可以二分，但插入是 O(n)，因为要挪元素； - 换成跳表或平衡树，查询和插入都是 O(log n)，但代码更复杂、常数更大。

在后台系统里，先估算 n 的量级和读写比例，再选结构，别为了 n=50 的场景上复杂结构。

四、动手实践：线性扫描与二分查找的耗时曲线

  1. 在 box 上建目录：mkdir -p ~/lab7 && cd ~/lab7
  2. 保存下面的脚本为 bench.py：
import bisect, random, timeit

def linear_search(arr, target):
    for i, x in enumerate(arr):
        if x == target:
            return i
    return -1

def binary_search(arr, target):
    i = bisect.bisect_left(arr, target)
    return i if i < len(arr) and arr[i] == target else -1

def bench(fn, arr, targets, repeat=5):
    # 每轮查一批随机目标，取多轮中最快的一次，减少噪声
    best = min(timeit.repeat(lambda: [fn(arr, t) for t in targets],
                             number=1, repeat=repeat))
    return best / len(targets) * 1e6  # 微秒/次

print(f"{'n':>10} {'linear(us)':>12} {'binary(us)':>12} {'ratio':>8}")
for n in [10, 100, 1_000, 10_000, 100_000, 1_000_000]:
    arr = list(range(n))                      # 已有序，两种方法都能用
    targets = [random.randrange(n) for _ in range(200)]
    lin = bench(linear_search, arr, targets[:50] if n >= 100_000 else targets)
    bi = bench(binary_search, arr, targets)
    print(f"{n:>10} {lin:>12.2f} {bi:>12.3f} {lin/bi:>8.1f}")
  1. 运行：python3 bench.py。我在 box 上的真实输出如下（你的机器数值会不同，趋势应该一致）：
         n   linear(us)   binary(us)    ratio
        10         0.17        0.099      1.7

六、自测题

1. 下面代码的时间复杂度是多少？

for i in range(n):
    j = 1
    while j < n:
        j *= 2
答案外层 n 次，内层 j 翻倍约 log₂n 次，所以是 O(n log n)。

2. 同事在 n=500 时测得 O(n²) 的去重比 O(n) 的 set 去重还快，于是说"大 O 没用"。你怎么回应？

答案小规模下常数主导：set 要算哈希、分配内存，常数更大。大 O 描述的是增长趋势，不预测某个规模下谁快。应该把 n 扫到 1e4、1e5、1e6 再比，O(n²) 很快就会被反超；同时也要看生产环境真实的 n 有多大。

3. list.append 说是 O(1)，但线上偶尔看到单次 append 耗时尖刺，为什么？这属于哪种复杂度分析？

答案这是摊还分析。容量满了要扩容并拷贝全部元素，那一次是 O(n)；因为容量按比例增长，n 次操作总共 O(n)，摊还到每次是 O(1)。摊还 O(1) 不保证每一次都快，对延迟敏感的场景可以预分配容量。
