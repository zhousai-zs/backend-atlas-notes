参考文档 负载均衡与热点倾斜：参考文档 / 原始资料（grpc.io）
摘要 负载均衡按端点、连接或请求分配流量，长连接和请求成本差异使轮询未必均衡。

边界说明：本课中的内容后台、图文发布服务、存储服务、热门文章读计数和长连接网关等场景，都是为讲解方便设置的教学假设，不代表任何企业内部实现。涉及 gRPC、Envoy、Nginx 等框架的具体行为时，以所读文档版本为准。

导读

先想象一家超市有三个收银台。门口有一位引导员，负责把顾客分配到不同的收银台。

  • 如果引导员让顾客严格按 1→2→3→1 的顺序轮流去收银台，这就是一种“轮询”：每个收银台拿到的顾客数量大致相同。
  • 如果引导员总让新顾客去当前排队人数最少的收银台，这就是一种“最少请求”或“最少活跃请求”思路：看的不只是已经分配了多少人，还要看现在还有多少人在排队。
  • 如果某位顾客推着满满一车商品，即使三个队的人数一样多，他所花的时间也可能远远超过别人。于是“每队人数差不多”并不等于“每队工作量差不多”。

把镜头拉回后端。上一课 f-discovery 解决的是“服务有哪些可用端点，地址列表从哪里来”；这一课要回答的是“拿到端点列表之后，每个连接或每个请求到底发给谁”。服务发现给的是候选集合，负载均衡做的是选择。

可以设一个教学时间线。假设通用内容后台有 3 个存储实例 A、B、C，图文发布服务通过它们读写文章元数据和正文索引：

时刻 变化 教学观察
t0 A、B、C 都健康，服务发现返回 3 个端点 请求量大致平均，三台机器 CPU 接近
t1 C 的磁盘开始变慢，单次读延迟从约 20ms 升到约 200ms C 上开始堆积在途请求，但端口仍然可连、健康检查可能仍通过
t2 客户端仍严格轮询，每个请求按 A→B→C 轮转 约 1/3 的请求落到慢实例；简化估算下平均延迟约 (20+20+200)/3≈80ms，p99 接近 200ms
t3 改为参考在途请求数或延迟的“最少活跃请求”策略 C 的在途数上升后，新请求更多转向 A、B；p99 通常先改善，但策略不是万能药

这张表里的数字是教学假设，不是任何线上系统的实测值。它想说明的是：只要有一个端点持续变慢，而分配逻辑只数“请求个数”，慢端点就会稳定吃掉一部分流量，并把这些请求的尾延迟带进整体 p99。

常见错误 可能出现的结果 更稳妥的做法
只按端点数量平均分配，不看请求成本和在途数量 慢实例排队越来越长，快实例反而闲着 同时观察在途请求、延迟和错误率，把“最少活跃请求”作为候选策略
把“连接级均衡”误当成“请求级均衡” 长连接建立后固定落在少数实例，新增流量仍压向热点 先明确均衡发生在哪一层；长连接场景考虑请求级再分配或可控的连接轮换
为缓存局部性使用固定哈希，却不处理热点 key 某个 key 或某类请求持续压向一个实例 监控分片倾斜，必要时加盐、拆 key、增加虚拟节点或限流
端点摘除时直接关闭连接 在途 RPC 被中断，客户端看到超时或错误 先停止新流量，等待在途请求排空，再摘除；以框架文档的优雅退出语义为准

以所读 gRPC 文档版本为准，客户端侧的 LB policy 会从 resolver 给出的地址列表中为每个 RPC 选择子通道（subchannel）；内置策略包括 pick_first 与 round_robin 等；可以通过 service config 选择策略，也可以实现并注册自定义 LB policy。LB policy 负责管理子通道状态，并产生 picker 为每次 RPC 选子通道。这里只借用这些公开语义做对照，具体 API 名称、配置字段和可用策略均以所读文档版本为准。

本课沿着三条主线展开：

  1. 轮询、最少请求与权重：它们分别假设了什么，什么时候会把“流量均匀”误当成“工作量均匀”。
  2. 连接级和请求级：均衡发生在建连时还是每次调用时，长连接为什么会让选择结果“粘住”。
  3. 一致性哈希与热点：哈希能带来缓存局部性，也可能把热点固定在一个分片上。

学习目标

完成本课后，你应当能够：

  • 能解释轮询、最少请求与权重。
  • 能独立完成：在异构延迟实例上比较轮询和最少活跃请求策略。
  • 能区分连接级均衡与请求级均衡，并说明长连接为什么会造成流量粘滞。
  • 能解释一致性哈希的缓存局部性与热点固化之间的取舍。
  • 能描述端点增删时避免丢失在途调用的基本步骤，并以所读文档版本核对优雅退出语义。
  • 能为一次异构延迟实验记录每实例负载与 p99，而不是只比较平均值。
  • 能用请求成本差异和连接分布举出“流量均匀但工作量不均匀”的反例。

为什么后端要懂

解决实例CPU倾斜与长尾放大。

这句话点出了两个彼此相关、但又不完全相同的问题。“CPU 倾斜”说的是实例之间的实际承压不均衡：有的机器忙到排队，有的机器却很闲。“长尾放大”说的是延迟分布的问题：少数慢请求或少数慢实例，会通过调用链和扇出把影响扩散到更大比例的请求上。负载均衡如果只盯着“请求个数”，很容易同时踩中这两个问题。

先看 CPU 倾斜。一个通用的内容后台里，负载均衡器能直接看到的信息通常很有限：连接数、请求数、字节数，或者一个静态配置的权重。它未必知道每个请求进来以后要做什么，也不知道某台实例当前的磁盘队列有多长。于是“分得均匀”往往只是分配动作均匀，不是处理成本均匀。教学假设中，图文发布服务调用存储服务时，读一条文章摘要、拉一页正文、刷新一篇热门文章的读计数，成本可能相差很大；如果这些请求被同等看待，机器之间的 CPU 使用率自然会分叉。

CPU 倾斜至少有四类常见来源，值得逐一建立直觉。

请求成本差异

同样是“一次请求”，背后的 CPU 和 IO 可能完全不同。一次按 ID 读取文章元数据，可能只查一次缓存；一次批量拉取历史图文，可能要扫描多个分片并做序列化；一次热门文章读计数更新，可能还要处理并发写和重试。轮询只保证每个实例收到的请求次数接近，却不知道每次请求有多重。

这类差异在平均值上不一定明显，在 p99 上却很容易暴露：轻请求很快返回，重请求在某个实例上排队，排队的请求又继续占着连接和内存，最后形成“请求数看起来差不多，CPU 和尾延迟差很多”的局面。

长连接粘住少数实例

长连接网关是一个典型场景。客户端与服务端建立连接后，后续很多请求都复用这条连接；如果均衡发生在建连时，那么连接一旦建立，流量路径就基本固定了。建连那一刻的偶然不均，会被后续的请求量放大并长期保留。

连接数均衡也不等于请求量均衡。一条连接可能非常活跃，另一条连接可能长期空闲；如果只按连接数分配，活跃连接所在的实例仍然可能先饱和。以具体框架的连接的复用、流控制和重连行为为准，不能把“连接数相等”直接当成“负载相等”。

热点 key 与分片

热门文章的读计数是另一个直观例子。假设文章按 key 做哈希分片，大部分文章的读写很分散，但某一篇爆款文章在短时间内被大量读取或计数。这个 key 仍然只会落在一个分片上，其他分片再空也帮不上忙。此时问题不是“机器数量不够”，而是“同一个 key 的流量无法靠增加机器自动摊开”。

一致性哈希可以减少节点增删时的重映射范围，让缓存局部性更稳定，但它不会把一个热点 key 拆成多个 key。它解决的是“节点变化时尽量少搬家”，不是“单个 key 的极端热度自动消失”。热点需要额外的手段来观察和处理，例如限流、局部聚合、拆分计数 key，或者为热点路径准备专门的容量；具体方案要结合业务语义，不能只看哈希算法。

异构机器与静态权重

真实集群里的机器往往不是同一代配置：CPU 核数、内存、磁盘类型、网络带宽、是否同时跑批处理任务，都可能不同。权重可以表达“这台机器应该多接一些”，但权重通常是静态意图，不是实时状态。某台高权重机器如果刚好磁盘变慢，它仍然会按权重继续接流量，直到监控和摘除机制介入。

所以，权重解决的是“容量不同”，最少活跃请求解决的是“当前积压不同”，轮询解决的是“分配动作简单可预测”。它们不是互相替代的关系，而是回答不同的问题。把它们混成一个“最均衡算法”的期待，通常会在异构和热点场景里失望。

长尾放大：一个扇出概率例子

扇出（fan-out）是指一个上游请求需要调用多个下游，再把结果聚合起来。内容后台的聚合页、批量查询、发布前校验，都可能出现这种结构。扇出会让尾延迟比单个实例的尾延迟更显眼。

做一个简化假设：一个聚合请求需要访问 100 个分片，每个分片独立地有 1% 的概率进入慢路径；只要其中任意一个分片慢，整个聚合请求就慢。

没有碰到慢分片的概率是：

0.99^100 ≈ 0.366

因此，至少碰到一个慢分片的概率是：

1 - 0.99^100 ≈ 0.634

也就是约 63.4%。单个分片的慢请求比例只有 1%，但到了用户请求这一层，超过一半的请求都可能被至少一次慢调用拖住。这个计算依赖“各分片独立”的假设；如果多个分片共享同一台慢实例、同一块磁盘或同一个热点 key，慢事件会相关，实际影响可能更集中，不能把这个概率当成线上承诺。

这就是长尾放大的直觉：平均值会稀释异常，扇出会把异常重新收集起来。一个实例的 p99 变差，不一定只影响它自己那 1/N 的流量；只要调用链路上有扇出，它就可能影响更大比例的用户请求。

对负载均衡来说，这意味着不能只看全局平均延迟，也不能只看“请求有没有发出去”。至少要按实例观察在途请求数、错误率和 p99，并关注慢实例是否被持续分配新流量。教学时间线里的 3 个存储实例只慢了 1 个，轮询却仍然把约 1/3 的新请求送给它；如果聚合请求需要访问所有分片，影响还会沿着调用链扩散。

两个数字例子：为什么轮询不够

轮询的优点是简单、可预测，而且在实例同构、请求成本接近时很有效。问题出在它默认“每个请求差不多重”。下面用两个教学假设把这个默认拆开。

例一：请求数相同，处理成本不同。

假设 3 个存储实例各收到 100 req/s，轮询把请求数分成完全相同的 100/100/100。三台机器处理一类请求的平均 CPU 成本分别是 2ms、10ms、40ms。下面的 CPU 工作量是简化后的等效值，不含并行、IO 等待和调度开销：

实例 请求数 平均单位成本 每秒 CPU 工作量
A 100 req/s 2ms 0.2 CPU
B 100 req/s 10ms 1.0 CPU
C 100 req/s 40ms 4.0 CPU

请求数完全一样，工作量却是 0.2 / 1.0 / 4.0，C 是 A 的 20 倍。最先饱和的是 C，而不是请求数最多的实例。C 饱和以后，排队时间继续上升，p99 被拉高；轮询仍然按顺序把新请求送过去，因为它看到的是“每个实例都收到了 100 个请求”，而不是“C 已经忙不过来了”。

这说明，最少请求策略之所以有意义，不是因为它比轮询“更高级”，而是因为它至少尝试参考当前未完成的请求数量。它仍然有盲点：如果每个请求的成本差异极大，或者新请求恰好都很重，单纯数在途请求也不够；还需要结合延迟、错误率和容量信号。具体指标如何采集、如何聚合，以所读框架和监控系统的文档版本为准。

例二：长连接分布不均。

假设长连接网关有 900 条长连接，建连后按连接级策略落在 A、B、C 三台实例上，数量分别是 500、250、150。再假设每条连接每秒产生 1 个请求：

实例 连接数 连接占比 请求量（每连接 1 req/s）
A 500 约 55.6% 约 500 req/s
B 250 约 27.8% 约 250 req/s
C 150 约 16.7% 约 150 req/s

连接级轮询只影响新连接。存量连接不会因为下一轮轮询自动搬家；除非连接断开重连，或者应用层主动做迁移。于是 A 承担了约 55.6% 的请求，B 和 C 分别只有约 27.8% 和 16.7%。每台机器看起来都“有连接”，但实际工作量并不接近。

如果连接级策略还使用了哈希或粘性，这个分布可能更稳定，也更难自动纠正。粘性本身不是错误：它有利于缓存局部性、会话状态和减少重连成本。但它会把“建连时的偶然”和“某个热点连接”固定下来，所以需要配套的监控、连接轮换或请求级再分配，而不是假设“连接数均衡”已经足够。

把两个例子放在一起，可以得到本课最重要的判断：流量均匀不等于工作量均匀。轮询优化的是分配次数，权重表达的是静态容量，最少活跃请求参考的是当前积压，一致性哈希优化的是节点变化时的映射稳定性。它们各自能看到的信息不同，也各自有看不到的部分。

因此，真正要问的不是“哪一个负载均衡算法最好”，而是“这个系统里，什么信号最能代表实例当前的承压，什么代价可以接受”。在请求同构、实例同构、连接短促的场景里，轮询可能已经足够；在长连接、异构延迟、热点 key 和扇出调用并存的场景里，只用轮询就很容易把慢实例的问题放大。

当你在内容后台看到 CPU 使用率长期倾斜、平均延迟还行但 p99 很高，或者某个长连接网关实例总是先排队，不要先假设“机器不够”。先看请求成本、连接分布、热点 key 和实例差异，再决定是调整策略、增加容量，还是处理某个具体的热点路径。这就是本课要建立的判断顺序。

把这句话再展开一点，所谓判断顺序可以落到几组具体问题上。

先分清“分派不均”还是“处理不均”

如果每个实例收到的请求数量相近，但 CPU 和 p99 差很多，问题更可能在请求成本、热点 key 或机器差异。这时继续微调轮询顺序通常收益有限，应该先找出哪类请求更重，以及这些请求是否集中在少数 key、少数连接或某台异构机器上。

反过来，如果某个实例的请求数明显更高，先看连接分布、静态权重、哈希规则和客户端连接池。这更像分派层的问题，调整选择策略或连接管理方式可能更直接。

把这两种情况分开，可以避免在错误的层面调参：分派不均时去优化单机代码，或者处理成本不均时反复更换轮询顺序，通常都只能得到短暂改善。

现象 优先怀疑 先补哪类观测
每实例请求数接近，CPU 和 p99 差很多 请求成本差异、热点 key、异构机器 按实例的耗时分布、热点 key、磁盘队列
连接数接近，请求量和 CPU 差很多 连接活跃度差异、请求级分配不均 每连接请求速率、在途 RPC 数
总请求量均衡，个别分片持续偏高 一致性哈希或其他分片规则固化了热点 分片流量、key 分布、节点变更记录
扩容后新实例很快过载 新实例未预热、权重或健康状态不准确 启动阶段延迟、错误率、权重与实际容量

再把“连接”与“请求”分开看

连接级均衡在建立连接时做选择，请求级均衡在每次调用时做选择。前者开销小、适合短连接或连接复用稳定的场景；后者更灵活，但需要更多状态和判断。一个系统可能同时存在两层选择，例如接入层按连接分配，服务间调用再按 RPC 分配；这时不能只看其中一层的指标就下结论。

对于长连接网关，连接数、活跃连接数、每连接请求速率是三个不同指标。只报连接数，会掩盖“少数活跃连接贡献大部分流量”的事实。对于图文发布服务调用存储服务，如果客户端使用固定大小的连接池，池大小均衡也不等于每个连接上的请求量均衡；具体连接复用和并发语义要以所读框架文档版本为准。

端点和故障态也要纳入

负载均衡不是一次性选择。端点会扩容、缩容、发布、故障摘除，客户端的视图也会随着服务发现更新而变化。新端点刚加入时缓存可能未热、连接池可能未建立，如果立刻按等权打满，它可能先被压垮；端点摘除时如果直接断开，在途调用又可能失败。因此，端点变更需要和健康检查、排空、重试预算一起考虑，具体行为以所读文档版本为准。

这也是为什么“端点增删时不丢失在途调用”不能只靠一句“支持优雅退出”来保证。选择策略、连接生命周期和退出流程必须对得上，否则流量虽然重新分配了，用户请求仍然可能在切换瞬间失败。

最后回到“为什么后端要懂”

因为负载均衡的选择发生在每个请求的路径上，策略里的假设会变成系统真实的负载形状。一个看似简单的轮询，可能让慢实例稳定吃掉三分之一的新流量；一个看似稳定的连接哈希，可能让热点 key 长期固定在一个分片；一次扇出调用，可能把单个分片 1% 的慢请求放大到约 63% 的用户请求。

理解这些，不是为了背出一个“最好的算法”，而是为了在看到 CPU 倾斜和长尾时，能判断该查分派、查成本、查连接还是查热点，并用实验数据验证判断。策略名称只是起点，真正决定效果的是它看到的信号、假设的负载，以及端点变化时是否仍然成立。

最后留三个问题，用来检验自己是否真的理解了负载均衡：

  • 当前的分派依据是什么：请求数、连接数、在途数、延迟，还是哈希？
  • 这个依据在长连接、热点 key 和异构实例上还准确吗？
  • 端点增删时，谁负责停止新流量、等待在途请求结束，失败又由谁兜底？

如果这三个问题答不清楚，再换一个策略名称，也只是把倾斜推迟到下一次故障。

核心概念

本节把“把流量分给谁”和“每个实例实际承担多少工作”分开看。负载均衡器看到的通常是连接数或请求数，而实例真正消耗的是 CPU、内存、下游等待时间；两者不一致时就会出现倾斜。以下场景为教学假设：通用内容后台的图文发布服务调用存储服务，网关维持大量长连接，热门文章读计数集中在少数 key 上。

1. 轮询、最少请求与权重

轮询（round robin） 按固定顺序依次选择端点，完全不做健康度以外的比较。它需要的状态最少，适合各实例同构、请求成本接近的情况；一旦某个实例变慢，轮询仍会按同样比例把新请求送过去，慢实例的排队会继续加深。

加权轮询 用权重表达容量差异。直接按权重展开成序列会产生突发，例如 5:1:1 若写成 AAAAA B C，B、C 很久才被选一次。平滑加权轮询（smooth weighted round robin）每轮给每个端点累加自身权重，选当前值最大者，再把被选者的当前值减去总权重。权重 5:1:1 时一种选择序列是：

A A B A C A A

七个位置中 A 出现 5 次、B 和 C 各 1 次，且分布比“连续五个 A”更均匀。

随机 每次独立抽取端点，实现简单，长期比例接近权重，但短期会有抖动，也不感知实例当前是否排队。

最少活跃请求（least request / least outstanding） 选择当前在途请求数最少的端点。它需要维护 inflight 计数：请求开始加一，结束减一，异常路径也必须在 finally 中减一。它比轮询更能适应慢实例，因为慢实例的 inflight 会自然堆积，从而被暂时避开。注意 inflight 只反映“还没完成”，不反映请求本身的重或轻。

P2C（power of two choices） 随机挑两个端点，比较二者的活跃数，选较小的那个。全量扫描在端点很多时要遍历所有候选，且所有客户端同时看到同一个“最空”端点时容易形成羊群效应；P2C 只用两次采样就把最大负载压到较低水平，代价是实现比纯随机多一点状态，比全量扫描更适合大规模集群。具体效果和证明以所读论文/文档版本为准。

策略 需要维护的状态 对慢实例的反应 实现复杂度
轮询 一个游标 无，继续按比例分配 低
平滑加权轮询 游标 + 每端点当前权重 无，除非调低权重或摘除 低到中
随机 端点列表 无，只能靠概率 低
最少活跃请求 每端点 inflight 快，inflight 堆积后自然避开 中
P2C 每端点 inflight + 随机源 较快，两次采样中避开较忙者 中

下面四个类可直接运行。LeastActive 和 P2C 用 acquire/release 模拟一次请求的生命周期，释放放在 finally 中；示例用固定数据打印选择序列，不依赖网络。

import random

class RoundRobin:
    def __init__(self, nodes):
        self.nodes = list(nodes)
        self.i = 0

    def pick(self):
        if not self.nodes:
            raise RuntimeError("no nodes")
        node = self.nodes[self.i % len(self.nodes)]
        self.i += 1
        return node

class SmoothWeighted:
    def __init__(self, weights):
        self.nodes = list(weights)
        self.weight = dict(weights)
        self.current = {n: 0 for n in self.nodes}
        self.total = sum(self.weight.values())

    def pick(self):
        for n in self.nodes:
            self.current[n] += self.weight[n]
        node = max(self.nodes, key=lambda n: self.current[n])
        self.current[node] -= self.total
        return node

class LeastActive:
    def __init__(self, nodes):
        self.nodes = list(nodes)
        self.inflight = {n: 0 for n in self.nodes}

    def acquire(self):
        node = min(self.nodes, key=lambda n: self.inflight[n])
        self.inflight[node] += 1
        return node

    def release(self, node):
        self.inflight[node] -= 1

    def run(self, node, work):
        try:
            return work(node)
        finally:
            self.release(node)

class P2C:
    def __init__(self, nodes, rng=None):
        self.nodes = list(nodes)
        self.inflight = {n: 0 for n in self.nodes}
        self.rng = rng or random.Random(7)

    def acquire(self):
        a, b = self.rng.sample(self.nodes, 2)
        node = a if self.inflight[a] <= self.inflight[b] else b
        self.inflight[node] += 1
        return node

    def release(self, node):
        self.inflight[node] -= 1

rr = RoundRobin(["A", "B", "C"])
print("round_robin:", [rr.pick() for _ in range(6)])

sw = SmoothWeighted({"A": 5, "B": 1, "C": 1})
print("smooth_5_1_1:", [sw.pick() for _ in range(7)])

la = LeastActive(["A", "B"])
print("least_active:")
la.inflight["A"] = 2
for _ in range(3):
    node = la.acquire()
    print(" ", node, dict(la.inflight))
    la.run(node, lambda n: None)

p2c = P2C(["A", "B", "C"])
print("p2c:")
p2c.inflight["B"] = 4
for _ in range(4):
    node = p2c.acquire()
    print(" ", node, dict(p2c.inflight))
    p2c.release(node)

这段代码只打印选择结果，用来说明“选择依据”而不是做性能结论。真实系统还要处理端点健康检查、摘除与恢复、权重更新；这些细节以所用实现和文档版本为准。

2. 连接级和请求级

连接级均衡工作在 L4，按 TCP 连接分配：连接建立时选中一个后端，此后该连接上的所有请求都走同一个实例。请求级均衡工作在 L7 或客户端：每个请求独立选择端点。HTTP/2 和 gRPC 在同一条连接上多路复用大量请求，连接级均衡的粒度会变得很粗。

维度 连接级均衡（L4） 请求级均衡（L7/客户端）
选择时机 建连时 每个请求
典型部署 四层代理、长连接入口 七层代理、客户端 LB
状态需求 连接表 端点列表 + 每请求/子通道状态
扩容后新实例 只能等新连接 新请求可立即进入
故障影响 一条连接上的请求一起受影响 可按请求重选
实现复杂度 较低 较高

教学假设：长连接网关到内容后端使用 gRPC 长连接。扩容新增一个后端实例后，如果网关只在建连时选一次，已有连接不会迁移，新实例可能长时间 0 流量；同时老实例的连接数和 CPU 继续偏高。这不是“算法选错”，而是均衡粒度太粗：连接数看起来没变，但每个连接背后的请求成本和排队时间可能完全不同。

缓解思路：

  • 客户端 LB 对解析器返回的每个端点建立子连接，再对每次 RPC 选择子通道，把均衡下沉到请求级；
  • 给连接设置最大寿命，到期后逐步重建；或定期重连，让新端点有机会被选中。具体开关、默认值和重连行为以所读代理/框架文档版本为准；
  • 不要把连接数当成工作量。长连接上一个热点请求的耗时可能远大于几十个轻请求，必须结合每实例的 inflight、CPU 和 p99 一起看。

在 gRPC 的公开说明中（以所读文档版本为准）：客户端由 LB policy 从 resolver 给出的地址列表中为每个 RPC 选择子通道；内置策略包括 pick_first 与 round_robin 等；可以通过 service config 选择策略，也可以实现并注册自定义 LB policy；LB policy 管理子通道状态并产生 picker，为每次 RPC 选子通道。pick_first 会优先使用第一个可用地址，通常不会把请求分散到多个子通道；round_robin 则在可用子通道之间轮转。连接失败、子通道进入暂时不可用状态时的具体行为，要以对应版本文档为准。

统计到各实例的已建立连接数，可以用：

ss -tn state established '( dport = :50051 )' \
  | awk 'NR>1 { n=split($5, a, ":"); host=a[n-1]; c[host]++ }
         END { for (h in c) printf "%s %d\n", h, c[h] }' \
  | sort

如果本机是 IPv6 或 ss 输出格式不同，需要按实际列调整字段。这个命令只能说明连接分布，不能说明每个实例处理了多少请求、排队多久；要判断倾斜，还要结合每实例的 QPS、inflight、CPU 和 p99 延迟。

还有一个容易忽略的点：连接级均衡下，“新实例 0 流量”并不等于新实例不可用。健康检查可能显示正常，但客户端没有新建连接，自然没有请求。排查时应先看连接建立时间分布和客户端重连策略，再看服务端指标。请求级均衡也不是免费午餐：每个 RPC 多一次选择、子通道需要维护健康状态，连接数也可能上升，需要根据实际负载和框架能力权衡。

3. 一致性哈希与热点

按 key 粘性常用于两类需求：缓存局部性，让同一对象的读写落在同一实例，减少缓存重复和跨节点回源；会话或有序处理，让同一会话的请求落在同一实例，避免状态分裂。教学假设：图文内容按 article_id 选择缓存节点，同一篇文章的读计数更新希望尽量落在同一处。

最直接的粘性是 hash(key) % N。N 从 4 变成 5 时，大量 key 的余数改变，缓存需要整体迁移；均匀随机下通常只有约 1/5 的 key 仍落在原编号，约 4/5 会移动。一致性哈希把节点和 key 都映射到一个哈希环，key 顺时针找到第一个节点；扩容时只有新节点接管的那一段 key 需要迁移，平均约 1/N。虚拟节点让每个物理节点在环上出现多次，改善负载均衡。

下面代码用 bisect 维护有序环，4 个节点扩到 5 个节点，统计 key 的迁移比例，并与取模方案对照：

import bisect
import hashlib


class HashRing:
    def __init__(self, nodes=(), vnodes=100):
        self.vnodes = vnodes
        self.ring = []
        self.owner = {}
        for node in nodes:
            self.add(node)

    @staticmethod
    def _hash(text):
        return int(hashlib.md5(text.encode("utf-8")).hexdigest()[:8], 16)

    def add(self, node):
        for i in range(self.vnodes):
            h = self._hash(f"{node}#{i}")
            self.ring.append(h)
            self.owner[h] = node
        self.ring.sort()

    def get(self, key):
        if not self.ring:
            raise RuntimeError("empty ring")
        h = self._hash(key)
        i = bisect.bisect_left(self.ring, h)
        if i == len(self.ring):
            i = 0
        return self.owner[self.ring[i]]


keys = [f"article:{i}" for i in range(20000)]
old_nodes = [f"n{i}" for i in range(4)]

ring = HashRing(old_nodes)
before = {k: ring.get(k) for k in keys}
ring.add("n4")
after = {k: ring.get(k) for k in keys}
moved = sum(before[k] != after[k] for k in keys)
print(f"consistent_hash 4->5 moved={moved / len(keys):.3f} (expect ~0.200)")

mod_before = {
    k: old_nodes[int(hashlib.md5(k.encode()).hexdigest(), 16) % 4] for k in keys
}
new_nodes = old_nodes + ["n4"]
mod_after = {
    k: new_nodes[int(hashlib.md5(k.encode()).hexdigest(), 16) % 5] for k in keys
}
mod_moved = sum(mod_before[k] != mod_after[k] for k in keys)
print(f"modulo          4->5 moved={mod_moved / len(keys):.3f} (expect ~0.800)")

一次运行的输出会接近 consistent_hash ... 0.200 与 modulo ... 0.800，具体数值受哈希函数和虚拟节点数影响；虚拟节点越多，环上分布越平滑，但元数据和构建成本也越高。这里用 MD5 只是演示，生产环境应选团队已审计、性能合适的哈希函数，并按实际节点数量评估环的大小。

粘性也会带来热点。教学假设：某篇爆款文章的 article_id 在短时间内成为热点 key，按 key 选择后所有更新都落到同一节点。若 5 个节点共 5 万次读，单个热点 key 占 40%，则该节点承担 2 万次，其余 3 万次才由另外 4 个节点分担，平均每节点 7500 次；请求按 key 看是“分散的”，按节点看却已经倾斜。这就是“流量均匀不等于工作量均匀”的典型形态：请求数量可能按 key 分布，但单篇爆款让某个 key 的工作量远超其他 key。

如果这个热点 key 还是读计数，问题会更明显：计数更新往往需要串行化或加锁，同一个 key 的并发更新集中到单实例后，CPU 可能不是瓶颈，锁竞争和队列等待才是。教学假设中的图文发布服务如果同步刷新计数，还会把存储服务的尾延迟放大到调用方。

tradeoffs 原文：「粘性利于缓存局部性，但可能固化热点与故障影响。」

缓解可以从三个方向考虑：

  • 热点探测加本地缓存：在调用方或网关侧按短窗口统计每个 key 的请求数，超过阈值就标记为热点；对只读内容做短 TTL 本地缓存，减少对同一后端节点的重复请求。阈值、窗口和 TTL 要按业务压测确定，并接受短时间的内容陈旧。
  • key 加后缀打散副本：把同一个热点对象的读请求映射到多个副本 key，例如按请求序号或客户端标识加后缀，写路径再合并或异步收敛；读吞吐上去了，但要接受副本之间的一致性代价和合并复杂度。
  • 有界负载一致性哈希（bounded load）：在一致性哈希选中的节点已超过平均负载上限时，继续沿环找下一个节点，把单点负载压住；上限通常用 (1 + ε) × 平均负载 表示。该方法的定义、参数和证明以所读论文/文档版本为准。
方案 扩容时迁移 热点控制 额外复杂度
取模哈希 大部分 key 需重映射，4→5 约 80% 差，热点集中 低
一致性哈希 约 1/N，4→5 约 20% 一般，取决于 key 分布 中
有界负载一致性哈希 约 1/N 较好，可限制单节点上限 中到高

三种方案不是互斥的。常见组合是：普通 key 走一致性哈希保证缓存局部性；对探测出的热点 key 做本地缓存或副本打散；当某个节点仍然过载时，再用有界负载把溢出请求沿环转发。组合会增加状态和排障难度，因此每加一层都要能回答“它解决了哪一个具体指标”。

还要看到粘性与故障的关系：同一 key 固定在某个节点，缓存命中率可能更高，但该节点故障时，这部分 key 的请求会一起受影响；如果客户端没有及时摘除故障节点并重新选择，恢复时间会被放大。反过来，完全打散虽然降低了单点影响，却牺牲了缓存局部性。选择哪一种，要看你更在意命中率、尾延迟还是故障隔离。

常见误区与设计权衡

负载均衡的讨论很容易停在“把请求分出去”这一层，但在真实后台里，分配动作和实际工作量往往不是一回事。下面用两张表把常见误区与选型条件放在一起看。示例场景均为教学假设：通用内容后台的图文发布服务调用存储服务、热门文章读计数、长连接网关等，只用于说明机制，不代表任何具体产品的内部实现。

误区的共同结构

  • 把手段当成目标：把“QPS 均匀”当成“负载均匀”，于是策略选对了形式，却没有选对观测指标。
  • 忽略状态生命周期：in-flight 计数、连接、缓存归属都有生命周期；只处理成功路径，异常路径就会留下偏差。
  • 忽略变更瞬间：扩容、下线、故障切换都是分布发生变化的时刻，稳态下的均匀不代表变更时也均匀。

可以优先观察的信号

  • 每实例 QPS、CPU、p99 是否同向变化；如果 QPS 接近而 p99 分化，先怀疑请求成本差异。
  • 每实例 in-flight 计数是否与实际并发相符；计数长期偏高或偏低都值得检查释放路径。
  • 连接数、连接上的请求速率、单连接队列是否同时均匀；只均匀一项不足以说明问题。
  • 新实例加入后的流量爬升曲线；长期贴底通常意味着连接未迁移或权重未生效。
  • 实例摘除窗口内的错误率与重试量；错误率尖峰往往说明在途请求没有被优雅处理。
  • 哈希类策略下扩容前后的缓存命中率；命中率骤降通常不是“容量不够”，而是映射重排。

热点倾斜的常见成因

  • 请求成本异质：有的调用只读缓存，有的要跨服务写多张表，按次数分配会天然偏离工作量。
  • 数据局部性：热门文章、热门账号或热点 key 会把读计数与缓存压力压到少数实例。
  • 连接复用：长连接把多次请求绑定在同一子通道上，连接级均衡无法看到连接内部的偏斜。
  • 实例异构：新老机型、不同规格、不同 JVM 或运行时状态，让相同请求数产生不同耗时。
  • 冷启动：新实例缓存未热、连接池未建立，一上来就满权重容易把长尾放大。
  • 客户端同质决策：所有客户端用同样的策略和同样的时钟做选择，容易形成同步摆动。
  • 变更过渡态：扩缩容、发布、摘除节点时，地址列表与连接状态并不同步更新。

这张表没有“永远正确”的一行。粘性在缓存局部性上占优，却可能把热点和故障影响一起固定下来；无状态均衡更利于替换与隔离，却要求请求本身可以任意路由。真正要做的是先写出约束，再选择代价可以接受的方案。

选择时的判断顺序

  1. 先问请求是否同质：如果单次调用成本差异很大，单纯轮询通常不是好起点。
  2. 再问实例是否同构：CPU、内存、网络与冷启动行为不同的实例，需要权重或预热来过渡。
  3. 再问粒度：长连接场景要明确连接级均衡是否足够，以及请求级是否可见。
  4. 再问状态：是否有缓存、会话或本地索引依赖特定实例；有状态会改变粘性的价值。
  5. 再问客户端能力：能否维护策略、计数与健康状态；不能时优先考虑代理 LB。
  6. 最后问变更路径：扩容、缩容、发布、故障时，是否有摘流、排空与重试预算。
  7. 用每实例 p99、CPU 与 in-flight 验证选择，而不是只看总 QPS。
  8. 把策略当成可回滚的配置，保留观测与灰度手段，避免一次性全量切换。

第 3 步：轮询（rr）

在本课的测试机上实测输出（你的数字会不同，但趋势一致）：

{"policy": "rr", "elapsed_s": 3.07, "errors": 0, "p99_ms": 80.7,

观察：请求数 400/400/400 完全均匀，但 C 的 p99 是 A 的 12 倍，总耗时 3 秒——工作线程大量时间卡在 C 上。这就是 pitfalls 说的「流量均匀不等于工作量均匀」。

第 4 步：最少活跃请求（least）与 P2C

python3 lb.py --policy least
python3 lb.py --policy p2c

实测：

策略 总耗时 整体 p99 A 请求数 B 请求数 C 请求数 C 的 p99
rr 3.07s 80.7ms 400 400 400 80.8ms
least 1.00s 52.4ms 561 563 76 52.8ms
p2c 1.08s 57.1ms 554 553 93 60.7ms

观察： - least 看的是每个端点的 inflight（在途请求数）。C 慢，在途请求堆着不走，自然被少选，只拿到 76 个；同样 1200 个请求，总耗时从 3.07s 降到 1.00s。 - 整体 p99 仍有 52ms，因为落到 C 上的那 6% 请求依然慢——负载均衡只能少用慢实例，不能把它变快；真要消掉这个尾巴，要靠摘除/降权或对冲请求（后续课程）。 - P2C 只随机看两个端点，效果接近 least，但每次选择是 O(1)，并且不会让所有客户端同时挤向"全局最空"的那台。

lb.py 里 least 的核心就几行，关键是计数一定在 finally 里减：

def pick(self):
    eps = self.snapshot                      # 不可变快照
    if not eps: raise RuntimeError("UNAVAILABLE: no endpoints")
    if self.policy == "least":
        return min(eps, key=lambda e: (e.inflight, random.random()))  # 打平时随机
    a, b = random.sample(eps, 2)             # p2c
    return a if a.inflight <= b.inflight else b

def call(bal):
    ep = bal.pick()
    with ep.lock: ep.inflight += 1
    try:
        ...  # 发请求、读回复
    finally:                                 # 异常也要减，否则计数泄漏，端点永远"很忙"
        with ep.lock: ep.inflight -= 1; ep.count += 1

第 5 步：运行中摘除端点，不丢在途调用

实测：

{"errors": 0, "per_instance": {"A": {"count": 580}, "B": {"count": 580}, "C": {"count": 40}},

3. 分清 resolver 与 LB policy 的分工

  • resolver 的职责是“发现并给出地址”，它回答“有哪些端点可用”。
  • LB policy 的职责是“在给定地址集合上做选择”，它回答“这一次 RPC 走哪个子通道”。
  • 二者通过地址列表与策略配置衔接；不要把“服务发现”和“流量分配”混成一层。

教学假设：在一个通用内容后台里，图文发布服务调用存储服务时，resolver 可能拿到一组存储网关地址；具体每一次上传或读取走哪个网关，则由 LB policy 决定。这里只借用通用后台形态说明分层，不代表任何企业内部实现。

4. 子通道与 picker 的概念核对

  • 子通道（subchannel）可以理解为“到某个端点的连接抽象”；一个地址可能对应一个或多个子通道，具体以文档与实现为准。

自测题

题 1：QPS 相同但 CPU 与 p99 差异明显

题干：三个实例的 QPS 完全相同，但其中一个实例 CPU 达到 90%，p99 是另外两个的 5 倍。请说明可能原因与修正方向。

答案：流量均匀不等于工作量均匀。轮询只保证“请求次数”大致相同，不保证每个请求的成本相同；慢请求、重查询、大对象、缓存未命中等都会让同一实例承担更高工作量。先按实例拆分请求成本与排队时间，再考虑最少活跃请求、P2C 或按能力加权，并检查是否存在连接级粘滞。

解析：对应本课 pitfalls“流量均匀不等于工作量均匀”。QPS 是到达速率，CPU 与 p99 反映的是服务时间与排队；只盯 QPS 会把倾斜误判为“机器性能问题”。

题 2：扩容后新实例几乎没流量

题干：gRPC 服务扩容 2 台新实例后，新实例几乎没流量，旧实例仍然很忙。为什么？怎么改？

答案：常见原因是长连接下的连接级均衡：客户端与已有实例建立了长连接，新实例没有被重新纳入选择；轮询发生在“已建立的子通道”之间，而不是每次 RPC 都重新建连。可改用请求级均衡策略（例如 round_robin 在子通道间轮转，或最少活跃请求/P2C），并确认 resolver 已把新地址推给客户端、策略已重建 picker。

解析：连接级与请求级的差别在于“选择发生的频率”。教学假设：长连接网关场景里，连接建立后流量会沿既有连接走；扩容是否生效，取决于客户端是否感知新地址并在每次 RPC 重新选子通道。

题 3：一致性哈希热点与节点摘除

题干：用一致性哈希按文章 ID 路由读计数，一篇爆款文章把一个节点打满；同时还需要在摘除节点时保证“端点增删时不丢失在途调用”。怎么缓解？

答案：热点缓解可分三层：一是给热点 key 增加隔离或拆分（例如探测到热点后在调用方加短 TTL 本地缓存，或把计数 key 加后缀拆成多个副本，读时合并）；二是用有界负载一致性哈希给每个节点设负载上限，超限的请求沿环溢出到下一个节点（注意：虚拟节点只能让 key 的整体分布更均匀，救不了单个热点 key）；三是对读计数采用本地聚合后异步上报，降低单次请求成本。节点摘除时先停止新流量、等待在途调用完成（或设置超时与重试边界），再移除地址，确保“端点增删时不丢失在途调用”。

解析：一致性哈希的优点是粘性与缓存局部性，缺点是热点会固化。对应本课 tradeoffs：粘性利于缓存局部性，但可能固化热点与故障影响。验收上要报告每实例负载与 p99，并验证端点增删时在途调用不丢失。

本课小结

  • 负载均衡按端点、连接或请求分配流量；长连接和请求成本差异使轮询未必均衡。
  • 轮询、最少请求与权重：轮询简单但忽略成本，最少请求关注在途工作量，权重用于表达异构能力。
  • 连接级和请求级：连接级选择发生在建连时，请求级选择发生在每次 RPC；长连接下扩容是否生效取决于客户端是否重新选路。
  • 一致性哈希与热点：按 key 路由带来粘性与缓存局部性，但爆款 key 会固化热点，需要隔离、拆分或限流。
  • 验收关注两点：报告包含每实例负载与 p99；端点增删时不丢失在途调用。
  • 最大的误区是“流量均匀不等于工作量均匀”；QPS 相同仍可能出现 CPU 与长尾差异。
