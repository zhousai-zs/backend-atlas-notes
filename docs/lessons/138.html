导读

上一课留下的缺口

上一课的 CacheEngine 已经说明：同一缓存行里的独立写入会争夺所有权，布局会改变 HITM 与吞吐。那一课的边界停在CPU 缓存行，没有回答另一件 I/O 上的事：把一份周报文件发给客户端时，数据是否还要在用户态和内核态之间走一个来回；把许多小请求合并成一次系统调用，又会引入怎样的等待。

节点把摘要写成：减少用户态与内核态复制或合并多次操作可降低固定成本，但缓冲区生命周期和排队等待变复杂。大文件传输和高频率的小请求，优化目标并不相同，却都会碰到复制次数和批大小。

接上前置

前置 第 131 课 i-perf 留下的结论是：要解释热点，先分清用户态和内核态的时间，并且采样本身也有代价。本课不再展开帧指针或丢样，只用到「CPU 时间要和吞吐一起读」这一条：用 sendfile 和 read/write 发送同一份教学文件，对比 CPU 与吞吐；再量化小请求为了凑批而等待的时间。

官方 sendfile(2) 把效率差写成：read/write 要把数据搬进再搬出用户空间，sendfile 把复制留在内核里。它同时要求，带 zero-copy 支持的套接字在对端消费完之前，输入文件不得修改。本课用教学引擎复现这两条口径，而不是在本机执行 sendfile。

教学场景（教学假设）

假设内容后台的教学 KV teachkv 要把周报文件 weekly-digest.bin（键为 article:01:title，标题为 Weekly digest）发给客户端。文件大小是 64 MiB（67108864 字节），低于 sendfile(2) 写出的单次上限 0x7ffff000。read/write 路径按 64 KiB 分块，每块两次系统调用，并在用户态各做一次读入与写出复制；sendfile 路径对整个文件做一次系统调用，只计内核内复制，用户态复制为 0。每次系统调用在教学虚拟时钟上花费 10000 纳秒，用户态复制每字节 2 纳秒，内核复制每字节 1 纳秒。窗口都是 30.00 秒。一组实验在 CPU 受限下尽量多发文件；另一组受教学线路限制，两边都只发出 44 份，专用来对比 CPU。另外用 64 字节的小标题响应，对比不批量与批量大小 16：高到达率 200000 次 / 秒，以及低到达率 10 次 / 秒（超时分别取教学 10 毫秒和 tcp(7) 记载的 Cork 上限 200 毫秒）。所有时间都是教学虚拟时钟上的值，不是线上探测间隔，也不是生产 RTT。

本课三条主线

  1. sendfile / splice：sendfile 把文件描述符之间的复制留在内核，避免用户态来回；splice 则要求其中一个描述符是管道，并且「通常避免真正拷贝」并不等于保证零拷贝。适用边界是：整条链路仍可能有内核复制、后续 DMA 或无法移动的页；输入也不能是套接字；带 zero-copy 支持时，文件在对端消费完之前不能改。
  2. 批量 syscall：把多次小的 write 合成一次，或用 TCP_CORK / SPLICE_F_MORE 提示还有后续数据，是为了摊掉每次系统调用和每个部分帧的固定成本。适用边界是：只有到达足够密时，合并才会提高吞吐。
  3. 批大小与延迟：批越大，高负载下系统调用越少，但低负载下请求要等批次凑齐或等到超时。适用边界是：批量能提升吞吐，也可能恶化低负载延迟；等待时间必须量化，而不是只看平均吞吐。

学习目标

  • 能解释 sendfile / splice 及适用边界：它们减少的是用户态与内核态之间的复制，并不等于整条链路零复制；文件在异步发送期间的所有权仍受官方约定约束。
  • 独立完成节点实践：用 sendfile 和 read/write 发送文件，对比 CPU 与吞吐。本课跑的是教学引擎，不是宿主 sendfile。
  • 能说明零拷贝并不意味着整个链路零复制，并能量化小请求的批量等待。

为什么后端要懂

节点对「为什么」写得很干脆：优化大包传输和高频小请求。放到本课的教学内容后台：同一份 64 MiB 的 weekly-digest.bin，在 CPU 受限的 30.00 秒里，read/write 只发出 103 份，吞吐 230.41 MB/s，CPU 利用率 0.9919，用户态复制了两倍载荷（13824425984 字节）；sendfile 发出 446 份，吞吐 997.69 MB/s，用户态复制为 0，但内核复制仍等于整份载荷 29930553344 字节。若两边都只发出教学线路允许的 44 份，吞吐同为 98.43 MB/s，read/write 的 CPU 是 0.4237，sendfile 只需 0.0984。大包路径的收益是少走用户态复制。另一侧，小请求到达 200000 次 / 秒时，不批量只能打到 100000.00 次 / 秒（CPU 已经 1.0000）；按 16 条一批，吞吐回到 200000.00，平均多等 37.50 微秒。到达只有 10 次 / 秒、再用 200 毫秒作为超时，吞吐仍是 10.00，平均却要等 100.00 毫秒。不把复制次数和批量等待分开看，就会在大文件上继续 read/write，或在低负载上为了吞吐去牺牲延迟。

核心知识点

1. sendfile / splice

sendfile(2) 的定义是在两个文件描述符之间复制数据。因为复制发生在内核里，它比 read(2) 加 write(2) 更高效——后者要把数据搬进用户空间再搬出去。in_fd 必须支持 mmap 一类操作，不能是套接字；自 2.6.33 起 out_fd 可以是任意文件，更早则必须是套接字。一次调用最多 0x7ffff000 字节，而且可能少写，调用方要准备重试。本课的 64 MiB 低于该上限，教学上一次 sendfile 发完整份文件。

这已经足够说明验收里的第一句：零拷贝并不意味着整个链路零复制。手册自己用的动词是 copy；它省掉的是用户态那一趟，不是内核里的复制，更不是网卡或对端之后的路径。本课在 sendfile 路径上把 kernel_copy_bytes 记为与载荷相同，user_copy_bytes 记为 0；read/write 则是用户态两倍载荷，另加一次内核侧计入。CPU 受限时，sendfile 的吞吐从 230.41 升到 997.69 MB/s；线路受限、吞吐同为 98.43 MB/s 时，CPU 从 0.4237 降到 0.0984。两组对比都来自同一套教学成本，不是宿主 sendfile 的墙钟。

splice(2) 是它点名的另一条路径：在两个描述符之间移动数据，而不在内核地址空间和用户地址空间之间复制，且其中一个必须是管道。NOTES 说「虽然我们谈论复制，实际复制通常被避免」，方法是管道缓冲里对内核页做引用计数，只复制指针。但 SPLICE_F_MOVE（尝试移动页而不是复制）只是提示，页仍可能被复制；自 Linux 2.6.21 起该标志还是空操作。因此本课没有把 splice 写成「已经测得内核复制为零」的第三条吞吐曲线。适用边界还包括：输入文件在对端消费之前必须保持未修改——这是 NOTES 对带 zero-copy 支持的套接字或管道写下的约定，也是缓冲区生命周期变复杂的地方。

2. 批量 syscall

节点写的批量 syscall，在 sendfile(2) 正文里并没有单独成节。它给出的抓手是 NOTES 里的 TCP_CORK：若要在文件内容前发送头部，可用这个选项减少分组、调节性能。splice(2) 的 SPLICE_F_MORE 也指向同一处，表示后面还有数据。tcp(7) 把 TCP_CORK 写成不要发出 partial frames，排队的部分帧在选项清除时再发送，用于 sendfile 前预置头部或作吞吐优化；tcp_autocorking 则在有前序分组仍在队列里时，尽量合并连续的 write / sendmsg。

本课把「合并多次操作以降低固定成本」落到小标题响应上。每次系统调用的教学成本是 10000 纳秒，不批量时每秒最多完成 100000 次调用。到达 200000 次 / 秒时，不批量只能完成 3000000 次（吞吐 100000.00，CPU 1.0000）；按 16 条一批，系统调用降到 375000 次，吞吐回到 200000.00，CPU 降到 0.125。适用边界是：固定成本足够高、到达足够密时，合并才会提高吞吐；到达稀疏时，只是把等待加到第一条请求上。

3. 批大小与延迟

tcp(7) 同时写明：按当前实现，TCP_CORK 有 200 毫秒的上限，到期会自动发出已排队数据。这是手册里的文档值，不是本课在宿主上测到的 cork 时间，但它已经把「为吞吐而等」写成了有上界的等待。

本课用同一上界量化小请求的批量等待。到达 200000 次 / 秒、批量 16、周期到达时，平均等待 37.50 微秒，最长 75.00 微秒——这是凑齐一批的时间，换来了吞吐翻倍。到达只有 10 次 / 秒时：不批量则等待为 0，系统调用 300 次，吞吐 10.00；把超时设成教学 10 毫秒（小于 100 毫秒的到达间隔），仍然是每次刷新 1 条，平均白等 10.00 毫秒，系统调用没有减少；把超时设成文档中的 200 毫秒，每次刷新 3 条，系统调用降到 100，平均等待却是 100.00 毫秒，最长 200.00 毫秒，吞吐仍是 10.00。高负载下批量抬吞吐，低负载下同样的批大小恶化延迟。批大小与超时必须和到达率一起写进结果，这就是验收要求的「量化小请求批量等待」。

常见误区

节点写出的误区是：忽略文件变化和异步发送的缓冲所有权。sendfile(2) NOTES 写得很硬：若 out_fd 是带 zero-copy 支持的套接字或管道，已交给对端路径的那部分输入文件，必须保持未修改，直到对端读完。教学实验在 sendfile 返回之后、对端尚未消费之前改写 weekly-digest.bin，标记为违反该约定。本课没有编造接收端会看到旧页、新页还是二者的混合——那不是这次教学计数能测量的东西。真正的风险是：调用已经返回，并不等于缓冲区所有权已经回到你手里；此时改文件、回收缓冲或覆盖 mmap 区，都可能让仍在飞行中的发送看到你不再期望的内容。异步发送把生命周期拉得比一次 write 更长，忽略这一点，就是把「更高效的复制路径」当成了「可以立刻改源文件」。

设计权衡

节点写出的权衡是：批量提升吞吐，可能恶化低负载延迟。高到达率下，批量 16 把吞吐从 100000.00 拉回被请求的 200000.00，代价是平均 37.50 微秒的凑批等待。低到达率下，200 毫秒超时把平均延迟抬了 100.00 毫秒，吞吐却还是 10.00。大文件的 sendfile 也有类似的「用约束换效率」：吞吐或 CPU 更好，但输入文件在对端消费前不能动，失败时还要准备退回 read/write（手册建议在 EINVAL / ENOSYS 时回退）。选择批量或零拷贝之前，要把到达率、等待、以及缓冲区所有权放在同一张表里，而不是只比较 MB/s。

自测题

题 1. sendfile 相对 read/write 省掉的是什么、没有省掉的是什么？在本课 CPU 受限和线路受限两组里，吞吐与 CPU 各是多少？为什么说零拷贝并不意味着整个链路零复制？

答案 sendfile(2) 写明：复制在内核中完成，因此比要在用户空间来回搬运的 read/write 更高效。省掉的是用户态那一趟复制和每块两次系统调用；没有省掉「仍然在描述符之间复制」这件事，更没有保证之后的 DMA、协议栈或对端路径为零。 CPU 受限的 `30.00` 秒：read/write 发出 `103` 份，吞吐 `230.41` MB/s，CPU `0.9919`，用户态复制 `13824425984` 字节（两倍载荷），内核复制等于载荷；sendfile 发出 `446` 份，吞吐 `997.69` MB/s，CPU `0.9978`，用户态复制 `0`，内核复制仍是整份载荷 `29930553344` 字节。线路受限时两边都是 `44` 份、`98.43` MB/s，CPU 分别为 `0.4237` 与 `0.0984`。 splice(2) 进一步说实际复制通常被避免，但页仍可能被复制，`SPLICE_F_MOVE` 还曾是空操作。所以「零拷贝」在这里是「少走用户态」，不是「链路上计数为零」。这些吞吐和 CPU 是教学虚拟时钟上的数字，不是宿主 `sendfile` 的测量。

题 2. 怎样量化小请求的批量等待？为什么批量能在高到达率下提高吞吐，却可能恶化低负载延迟？200 毫秒这个数字从哪来？

答案 要同时记录到达率、批大小或超时、系统调用次数、吞吐，以及平均 / 最长等待。本课到达 `200000` 次 / 秒时，不批量受系统调用能力限制，吞吐只有 `100000.00`，等待为 `0`；批量 `16` 后吞吐 `200000.00`，平均等待 `37.50` 微秒，最长 `75.00` 微秒。到达 `10` 次 / 秒时，不批量等待为 `0`；用 200 毫秒超时每次凑到 3 条，系统调用从 `300` 降到 `100`，平均等待 `100.00` 毫秒，最长 `200.00` 毫秒，吞吐仍是 `10.00`。10 毫秒超时甚至凑不齐第二项，只是每条多等 `10.00` 毫秒。 这就是权衡：批量摊掉固定的系统调用成本，但请求要等批次或超时。低负载时等来的不是更高吞吐，只是更长的延迟。 200 毫秒来自 tcp(7) 对 TCP_CORK 的记载（2026-11-14 读到 man-pages 6.19，页脚 2026-04-19）：cork 时间有 200 毫秒上限，到期会自动发送。它是文档值，不是宿主测量；本课用它做低负载教学超时，用来落实「量化小请求批量等待」。

题 3. 为什么不能在 sendfile 返回之后立刻改源文件或回收缓冲？官方原文怎么说？本课有没有给出接收端看到的字节？

答案 sendfile(2) NOTES 要求：若 `out_fd` 是带 zero-copy 支持的套接字或管道，已传输的那部分输入文件必须保持未修改，直到对端读完。调用返回只表示内核接受了这次传输，并不表示对端已经消费，也不表示你重新取得了那部分页的所有权。这正是「忽略文件变化和异步发送的缓冲所有权」。 教学实验在返回之后、消费之前修改文件，只把 `violates_unmodified_until_consumed` 标为真，并写明 `receiver_bytes_not_invented`。本课没有编造接收端是旧数据、新数据还是二者的混合。正确做法是：在对端消费完成（或改用会立即复制的路径）之前，不要改那份文件，也不要复用那块缓冲。

本课小结

  • 减少用户态与内核态复制、或合并多次操作，可以降低固定成本，但缓冲区生命周期和排队等待会变复杂。零拷贝并不意味着整个链路零复制。
  • CPU 受限时，教学 sendfile 吞吐是 997.69 MB/s，read/write 是 230.41 MB/s；线路受限、吞吐同为 98.43 MB/s 时，CPU 从 0.4237 降到 0.0984。sendfile 的用户态复制为 0，内核复制仍等于载荷。
  • 小请求到达 200000 次 / 秒时，批量 16 把吞吐从 100000.00 拉到 200000.00，平均等待 37.50 微秒。到达 10 次 / 秒、超时 200 毫秒时，平均等待 100.00 毫秒，吞吐并不增加。批量提升吞吐，可能恶化低负载延迟。
  • sendfile 返回后、对端消费前修改文件，违反官方「保持未修改直至被消费」的约定。不要忽略异步发送的缓冲所有权。
  • 这些是教学虚拟时钟上的数字，不是生产 RTT，也不是宿主 sendfile / splice 的输出。ZeroCopyEngine 不是 Redis，也不是 Linux 零拷贝栈。200 毫秒来自 tcp(7) 的文档记载。
