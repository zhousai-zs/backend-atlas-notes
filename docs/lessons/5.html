第 5/208 课：终端、路径与命令组合

节点：a-shell · 域：A · 子类：工具与程序执行 · 难度：入门 · 前置：a-os

一句话：Shell 解释命令并连接程序的输入输出，是操作 Linux 开发环境的基本界面。

1. 学习目标与为什么后端要懂

完成本课后，你应该能够：

  1. 解释绝对路径与相对路径的区别，并能判断一条命令实际操作的是哪个文件。
  2. 说明标准输入、标准输出、标准错误分别是什么，以及重定向如何改变它们的方向。
  3. 用管道把多个命令组合起来，完成“统计日志中错误次数”这类任务。
  4. 在命令失败后查看退出码，并解释退出码 0 与非 0 的含义。
  5. 正确处理带空格的文件名，避免变量未引用导致的分词与通配符展开。
  6. 理解节点给出的取舍：短命令适合探索，复杂且重复的任务应写成可检查的脚本。

节点对“为什么”的说明很直接：能够独立编译、查看文件、查找日志并执行可复现操作。 对即将进入腾讯微信公众号后台开发的后端工程师来说，这不是“运维才需要”的技能，而是日常工作的基本操作界面：

  • 查线上日志：服务把访问日志、错误日志写到某台机器的某个目录。你需要先确认自己在哪、日志的绝对路径是什么，再用 grep、awk、sort、uniq 统计错误码。
  • 定位故障：某次发布后错误率上升，你要在日志里按时间、接口、错误码过滤，并确认统计命令本身有没有失败。
  • 可复现：排查过程如果只留在终端历史里，别人无法复核。把关键命令整理成脚本，才能让结论可重复。
  • 避免误操作：路径写错、重定向写错、变量没加引号，都可能让命令操作到错误的文件，甚至清空日志。理解语义比记住命令更重要。

本课不要求你成为 Shell 专家，而是建立一套能验证的终端操作模型：命令从哪里读数据、把结果写到哪里、成功还是失败、文件名如何被解释。

2. 从直觉到原理：四个核心要点

2.1 Shell 是什么：命令的解释器与连接器

终端里你输入一行命令，例如：

grep "ERROR" /var/log/wechat/app.log | wc -l

Shell 做的主要事情可以概括为：

  1. 解析这行文本：识别命令名、参数、管道、重定向和引号。
  2. 启动程序：为 grep 和 wc 分别创建进程。
  3. 连接输入输出：把 grep 的标准输出接到 wc 的标准输入。
  4. 等待并报告结果：等待命令结束，并通过退出码表示成功或失败。

这里要区分两个概念：

  • Shell 是解释命令的程序，常见的有 Bash、Zsh、sh 等。它本身不负责“搜索日志”，而是负责把 grep 启动起来并接好管道。
  • 命令 通常是一个可执行程序，例如 ls、grep、cat、wc。程序只关心自己从标准输入读到什么、向标准输出写什么。

节点摘要说“Shell 解释命令并连接程序的输入输出”，这句话的落点就在第 2、3 步：Shell 的核心价值不是替代程序，而是把许多小程序的输入输出拼接起来。

2.2 绝对路径与相对路径

直觉

路径就是“文件在文件系统中的位置”。有两种写法：

  • 绝对路径：从根目录 / 开始写，位置唯一，不依赖你当前所在目录。
  • 相对路径：从当前工作目录开始写，位置取决于你现在在哪。

例如：

/var/log/wechat/app.log      # 绝对路径
logs/app.log                 # 相对路径
./logs/app.log               # 相对路径，显式表示“当前目录下”
../logs/app.log              # 相对路径，先回到上一级目录

常用命令：

pwd                 # 打印当前工作目录
ls                  # 列出当前目录内容
ls /var/log/wechat  # 用绝对路径列出目录
cd /var/log/wechat  # 切换到绝对路径
cd logs             # 切换到当前目录下的 logs
cd ..               # 回到上一级目录
cd ~                # 回到当前用户的家目录

原理：路径如何被解析

相对路径的解析依赖当前工作目录（current working directory，cwd）。每个进程都有自己的 cwd。Shell 在执行命令前，会以 Shell 的 cwd 为基准解释相对路径。

假设当前目录是 /home/backend：

cat logs/app.log

实际访问的是 /home/backend/logs/app.log。如果你先执行：

cd /var/log/wechat
cat logs/app.log

同样的相对路径就变成了 /var/log/wechat/logs/app.log。命令文本没变，目标可能完全变了。 这是线上排查时最常见的误操作来源之一。

路径中的几个特殊成分：

写法 含义
/ 根目录，也是绝对路径的起点
. 当前目录
.. 上一级目录
~ 当前用户的家目录（由 Shell 展开）
- 在 cd - 中表示上一次所在目录

后端场景：先确认“我在哪”

查日志前，先确认路径，而不是凭记忆直接 rm 或 >：

pwd
ls -l /var/log/wechat/

如果日志路径来自配置，优先使用配置中的绝对路径，或者先 cd 到明确目录再使用相对路径。对删除、覆盖、批量修改这类危险操作，绝对路径通常更安全，因为它不随 cwd 变化。

带空格的文件名

空格在 Shell 中默认是参数分隔符，不是文件名的一部分。因此：

cat my log.txt

会被解释为把 my 和 log.txt 两个参数传给 cat，而不是读取名为 my log.txt 的文件。正确写法是加引号或转义：

cat "my log.txt"
cat 'my log.txt'
cat my\ log.txt

这三种写法都能让 Shell 把 my log.txt 当作一个参数。第 2.5 节会进一步解释单引号、双引号和反斜杠的区别。

2.3 标准输入、标准输出与重定向

直觉：每个程序都有三个默认通道

Unix 风格的程序通常默认打开三个标准流：

名称 文件描述符 默认连接 作用
标准输入（stdin） 0 终端键盘 程序从这里读数据
标准输出（stdout） 1 终端屏幕 程序把正常结果写到这里
标准错误（stderr） 2 终端屏幕 程序把错误信息写到这里

“默认连接终端”意味着：你不做任何重定向时，输入来自键盘，正常输出和错误都显示在屏幕上。重定向就是在启动程序前，改变这些文件描述符指向的位置。

输出重定向

echo "hello" > out.txt       # 覆盖写入 out.txt
echo "world" >> out.txt      # 追加到 out.txt 末尾

关键区别：

  • > 会先截断目标文件。如果目标文件是线上日志，执行 > app.log 会立刻清空它。
  • >> 追加，不截断已有内容。

把标准错误单独写入文件：

grep "ERROR" /var/log/wechat/app.log > matches.txt 2> errors.txt

这里：

  • > matches.txt 只重定向 stdout（文件描述符 1）。
  • 2> errors.txt 重定向 stderr（文件描述符 2）。

如果想让 stdout 和 stderr 都进入同一个文件：

command > all.log 2>&1

2>&1 的含义是“把文件描述符 2 指向文件描述符 1 当前指向的位置”。因此顺序很重要：

command > all.log 2>&1   # 正确：两者都进 all.log
command 2>&1 > all.log   # 错误理解：stderr 仍指向终端，stdout 才进文件

第二种写法中，2>&1 先执行，此时 fd 1 还指向终端，所以 stderr 被复制成“终端”；随后 > all.log 只改变 fd 1。结果就是错误仍打印在屏幕上。重定向按从左到右生效。

有些 Shell 支持更简洁的 &>：

command &> all.log

但如果你写脚本并希望兼容更多 Shell，> all.log 2>&1 更通用。

输入重定向

wc -l < /var/log/wechat/app.log

< 把文件内容接到程序的标准输入。这里 wc -l 从 stdin 读，不把文件名当作参数，因此输出只有行数，没有文件名。对比：

wc -l /var/log/wechat/app.log

后者把路径作为参数传给 wc，输出通常包含行数和文件名。

丢弃不需要的输出：

command > /dev/null 2>&1

/dev/null 是一个特殊设备，写入的内容会被丢弃。常用于“只关心退出码，不关心输出”的场景。

原理：重定向发生在程序启动之前

重定向不是程序内部的功能，而是 Shell 在 fork/exec 前后对文件描述符做的安排。程序启动后，它看到的 fd 0、1、2 已经指向新的文件或管道，程序本身不需要知道“输出被重定向了”。

这也解释了一个常见现象：程序往 stdout 写的内容和往 stderr 写的内容，可以分别被送到不同地方。 日志系统常把正常访问日志写 stdout、错误写 stderr，再由进程管理器分别收集。

2.4 管道：把字节流从一个程序送到另一个程序

直觉

管道符 | 把左边命令的标准输出接到右边命令的标准输入：

grep "ERROR" /var/log/wechat/app.log | wc -l

含义是：

  1. grep 从日志中筛出包含 ERROR 的行，写到 stdout。
  2. Shell 把 grep 的 stdout 接到 wc 的 stdin。
  3. wc -l 从 stdin 读入这些行，统计行数。

屏幕上最终只看到数字，因为 wc 的 stdout 仍然指向终端。

原理：管道传递的是字节流

这是本节点验收要求之一：能解释管道传递的是字节流。

管道不是把“行对象”“JSON 对象”或“错误记录结构”传给下一个程序，而是把左边程序写出的字节原样送过去。右边程序看到的只是连续的字节，至于这些字节如何分行、如何解析，由右边程序自己决定。

例如：

printf 'ERROR 500\nINFO 200\nERROR 502\n' | wc -c

wc -c 统计的是字节数，不是行数，也不是错误条数。管道里没有“错误对象”，只有文本字节。grep 之所以能按行工作，是因为它自己按换行符解析输入。

这也带来两个实际影响：

  • 文本协议很常见：日志、CSV、JSON 行都可以通过管道处理，只要上下游对字节格式达成一致。
  • 二进制数据要小心：如果上游输出二进制，下游却按文本处理，可能被截断或破坏。处理文件名列表时，换行符本身可能出现在文件名中，因此有了 find -print0 与 xargs -0 这类以 NUL 分隔的约定。

常用组合

统计日志中不同错误码的次数：

grep "ERROR" /var/log/wechat/app.log \
  | awk '{print $NF}' \
  | sort \
  | uniq -c \
  | sort -nr

逐段解释：

  • grep "ERROR"：筛出错误行。
  • awk '{print $NF}'：取每行最后一个字段（假设日志把错误码放在末尾）。
  • sort：排序，让相同错误码相邻。
  • uniq -c：统计相邻重复项的次数。
  • sort -nr：按次数从大到小排序。

统计某个接口的请求数：

grep "/cgi-bin/message" /var/log/wechat/access.log | wc -l

查看错误码分布：

awk '{print $9}' /var/log/wechat/access.log | sort | uniq -c | sort -nr | head

这些命令都很短，适合在终端里探索。若统计逻辑复杂、需要反复执行，就应写成脚本并加入错误检查，这对应节点的取舍：短命令适合探索，复杂重复任务应写成可检查脚本。

管道与退出码的关系

默认情况下，管道的退出码是最后一个命令的退出码。例如：

grep "ERROR" app.log | wc -l

即使 grep 因为文件不存在而失败，只要 wc 成功执行，整个管道的退出码仍可能是 0。这在脚本里很危险：你可能拿到一个“成功”的统计结果，但实际上日志根本没读到。

Bash 可以用 set -o pipefail 让管道中任意一个命令失败时，整个管道返回非 0：

set -o pipefail
grep "ERROR" app.log | wc -l
echo $?

是否开启 pipefail 是设计权衡：开启后更容易发现上游失败，但也会改变依赖“最后一个命令成功即可”的既有脚本行为。写生产脚本时应明确选择，而不是依赖默认值碰运气。

2.5 退出码：命令成功还是失败

直觉

每个进程结束时都会返回一个退出状态码。Shell 用特殊变量 $? 读取上一条命令的退出码：

ls /var/log/wechat/app.log
echo $?

约定是：

  • 0：成功。
  • 非 0：失败。不同数值可以表示不同失败原因，但具体含义由程序定义。

注意：$? 只保留最近一条命令的退出码。你执行了 echo $? 之后，$? 就变成 echo 自己的退出码（通常是 0）。因此要立刻检查：

grep "ERROR" /var/log/wechat/app.log
status=$?
echo "grep exit status: $status"

先把退出码保存到变量，再打印或判断，避免被后续命令覆盖。

在条件中使用

if grep -q "ERROR" /var/log/wechat/app.log; then
  echo "found errors"
else
  echo "no errors or read failure"
fi

grep -q 表示安静模式，只关心是否匹配，不输出匹配行。if 判断的是命令的退出码是否为 0。

用 || 和 && 组合：

grep "ERROR" app.log > /dev/null || echo "grep failed or no match"

这里要区分两种“非 0”：

  • grep 没找到匹配时通常返回 1，这不一定是“命令执行故障”，而是“没有匹配”。
  • 文件不存在、权限不足等错误通常返回 2 或其他非 0 值。

排查线上问题时，不能只看“有没有输出”，还要看退出码和 stderr。命令失败后能查看退出码，是本节点的验收要求之一。

常见退出码示例

true;  echo $?    # 0
false; echo $?    # 1
ls /no/such/path  # 报错
echo $?           # 非 0，具体值由 ls 决定

在脚本里，如果希望某条命令失败就立即停止，可以谨慎使用：

set -e

但 set -e 有许多边界情况（例如命令出现在 if 条件、|| 左侧时不会触发退出），不能把它当成万能的错误处理。更可控的方式是显式检查关键命令：

if ! grep -q "ERROR" /var/log/wechat/app.log; then
  echo "log check failed" >&2
  exit 1
fi

这里把错误信息写到 stderr（>&2），把失败状态传给脚本的调用者，符合“错误走错误通道”的惯例。

2.6 引号：控制 Shell 如何解释文本

三种常见写法

写法 行为
单引号 '...' 内部内容几乎原样保留，不展开变量，不展开通配符
双引号 "..." 保留为一个参数，但会展开变量、命令替换等
反斜杠 \ 转义下一个字符，使其失去特殊含义

例子：

name="wechat backend"

echo '$name'   # 输出字面量 $name
echo "$name"   # 输出 wechat backend
echo $name     # 输出两个参数：wechat 和 backend

最后一行最关键：未引用的变量会发生分词（word splitting）。$name 展开成 wechat backend 后，Shell 再按空格把它拆成两个参数。如果这个变量是文件名、路径或用户输入，程序收到的参数数量就可能不对。

未引用变量还会触发通配符展开

节点的误区明确指出：

未引用变量会触发分词与通配符展开。

例如当前目录有 app.log、app.log.1、app.log.2：

pattern="app.log*"
echo $pattern     # Shell 可能把它展开成多个文件名
echo "$pattern"   # 输出字面量 app.log*

未引用时，变量展开后的 * 会参与路径名展开（globbing）；加双引号后，* 被当作普通字符。很多“脚本在某个目录下行为不对”的问题，根源都是这里。

正确处理带空格的文件名

错误写法：

file="my log.txt"
cat $file          # 被拆成 cat my log.txt，可能读错文件

正确写法：

file="my log.txt"
cat "$file"        # 一个参数，完整文件名

遍历文件名时，不要用 for f in $(ls)，因为 $(ls) 的输出会按空白分词，遇到空格、换行就出错。更稳妥的方式是让 find 用 NUL 分隔输出：

find /var/log/wechat -name '*.log' -print0 \
  | xargs -0 grep -l "ERROR"

-print0 用 NUL 字节分隔文件名，xargs -0 按 NUL 读取。因为 Unix 文件名中不能包含 NUL，这种分隔方式不会把带空格或换行的文件名拆坏。这正是“管道传递字节流”在工程上的一个直接应用：选择一种不会与数据内容冲突的分隔符。

引号与命令替换

双引号内可以展开命令替换：

today=$(date +%F)
echo "log date: $today"

如果命令替换的结果可能包含空格，仍然要加双引号：

dir=$(mktemp -d)
ls "$dir"

单引号内不会展开：

echo '$HOME'   # 字面量 $HOME

选择原则可以简化为：

  • 需要字面量时用单引号。
  • 需要变量展开时用双引号，并且默认给变量加双引号。
  • 只有在明确知道分词或通配符展开是想要的行为时，才不加引号。

3. 常见误区与设计权衡

3.1 路径相关误区

误区 后果 更稳妥的做法
以为相对路径永远指向同一个文件 cd 后命令操作了别的目录 危险操作前先 pwd，或使用绝对路径
忘记空格需要引用 cat my log.txt 把文件名拆成两个参数 cat "my log.txt"
把 ~ 当成普通字符 单引号内 ~ 不展开 需要家目录时不要放在单引号里
用 cd 改变全局位置后忘记切回 后续命令都在错误目录执行 在脚本中使用子 Shell 或绝对路径

3.2 重定向相关误区

误区 后果 更稳妥的做法
用 > 追加日志 目标文件被截断 追加用 >>
认为 2>&1 顺序无所谓 stderr 可能仍留在终端 写成 > file 2>&1
只看屏幕输出，不看 stderr 漏掉错误原因 分别重定向并检查退出码
把正常结果和错误混在一个文件 后续统计被错误信息污染 正常走 stdout，错误走 stderr

3.3 管道相关误区

误区 后果 更稳妥的做法
以为管道传递结构化对象 下游按字节解析时得到意外结果 明确上下游的文本格式与分隔符
以为管道中任一命令失败都会让整体失败 上游失败被最后一个命令掩盖 需要时开启 set -o pipefail
对二进制数据按行处理 数据被破坏或截断 使用合适的二进制安全工具与分隔符
忘记管道会并发启动多个进程 资源占用、缓冲行为与单命令不同 复杂场景用脚本分步处理并记录中间结果

3.4 退出码相关误区

误区 后果 更稳妥的做法
用输出是否为空判断成功 成功但无匹配、失败但无输出都可能混淆 同时检查退出码和 stderr
在 echo $? 之后才想读取上一条命令的状态 读到的是 echo 的退出码 立即保存到变量
认为 grep 返回 1 一定是故障 可能只是没有匹配 区分“无匹配”和“读取失败”
盲目依赖 set -e 某些上下文不会按预期退出 对关键步骤显式判断

3.5 引号相关误区

误区 后果 更稳妥的做法
变量一律不加引号 分词、通配符展开导致参数数量错误 默认写成 "$var"
用 for f in $(ls) 遍历文件 空格、换行文件名被拆坏 用 find -print0 配合 xargs -0
在单引号里期待变量展开 得到字面量 需要展开时用双引号
把用户输入直接拼进命令 可能触发意外的通配符或命令解析 加引号、校验输入，必要时避免 eval

3.6 设计权衡：一行命令还是脚本

节点给出的权衡是：

短命令适合探索，复杂重复任务应写成可检查脚本。

可以这样理解：

  • 探索阶段：你不知道日志格式、字段位置、错误码分布，用短命令逐步试错最快。例如先 head 看几行，再 grep 过滤，再 awk 取字段。
  • 固化阶段：当命令需要反复执行、被别人复用、或用于生产判断时，应写成脚本。脚本可以加入参数校验、set -o pipefail、明确的退出码、日志输出和注释，便于审查与复现。

一行命令的优点是即时、灵活；缺点是难以审查、难以测试、错误容易被管道掩盖。脚本的优点是结构清晰、可版本控制；缺点是需要维护。选择标准不是“哪个更高级”，而是这次操作是否需要可复现和可审查。

4. 动手实践：用管道统计错误次数，并处理带空格文件名

本实践对应节点要求：用管道统计日志错误次数，正确处理带空格文件名。 下面每一步都可以直接执行。

步骤 1：建立实验目录

mkdir -p /tmp/shell-lab/logs
cd /tmp/shell-lab
pwd

预期：pwd 输出 /tmp/shell-lab。这一步同时验证了绝对路径与 cd 后的当前工作目录。

步骤 2：创建一个带空格的文件名

log_file="/tmp/shell-lab/logs/wechat app.log"
printf '%s\n' \
  '2026-10-30 10:00:01 INFO 200 /cgi-bin/message' \
  '2026-10-30 10:00:02 ERROR 500 /cgi-bin/message' \
  '2026-10-30 10:00:03 INFO 200 /cgi-bin/user' \
  '2026-10-30 10:00:04 ERROR 502 /cgi-bin/message' \
  '2026-10-30 10:00:05 ERROR 500 /cgi-bin/user' \
  '2026-10-30 10:00:06 WARN 429 /cgi-bin/message' \
  > "$log_file"

注意这里使用了 "$log_file"。如果写成 > $log_file，路径中的空格会导致分词，重定向目标可能变成错误的位置。

步骤 3：确认文件存在且能正确读取

ls -l "/tmp/shell-lab/logs/wechat app.log"
wc -l "/tmp/shell-lab/logs/wechat app.log"

预期：文件存在，wc -l 输出 6。对比错误写法：

wc -l $log_file

如果 log_file 变量未加引号，Shell 会把它拆成 /tmp/shell-lab/logs/wechat 和 app.log 两个参数，wc 的行为就不再是读取那一个完整文件。这个对比可以帮助你直观看到分词的影响。

步骤 4：用管道统计 ERROR 行数

grep "ERROR" "/tmp/shell-lab/logs/wechat app.log" | wc -l

预期：输出 3。

这里管道传递的是 grep 写出的字节流，wc -l 按换行符统计行数。grep 不传递“错误对象”，只传递匹配到的文本行。

步骤 5：按错误码统计次数

grep "ERROR" "/tmp/shell-lab/logs/wechat app.log" \
  | awk '{print $3}' \
  | sort \
  | uniq -c \
  | sort -nr

预期输出类似：

      2 500
      1 502

逐段含义：

  • grep "ERROR"：只保留错误行。
  • awk '{print $3}'：取第 3 个字段，即错误码。
  • sort：让相同错误码相邻。
  • uniq -c：统计连续重复项。
  • sort -nr：按次数降序排列。

步骤 6：检查命令失败后的退出码

先执行一个会失败的命令：

grep "ERROR" "/tmp/shell-lab/logs/does-not-exist.log"
status=$?
echo "exit status: $status"

预期：grep 向 stderr 报错，status 为非 0。注意要先把 $? 保存到 status，否则后面的 echo 会覆盖它。

再检查成功命令：

grep -q "ERROR" "/tmp/shell-lab/logs/wechat app.log"
echo "exit status: $?"

预期：输出 0。

再观察“无匹配”的情况：

grep -q "FATAL" "/tmp/shell-lab/logs/wechat app.log"
echo "exit status: $?"

预期：非 0（grep 通常返回 1）。这说明非 0 不一定代表程序崩溃，也可能只是没有匹配。排查时应结合 stderr 和具体退出码判断。

步骤 7：安全处理多个带空格的文件名

再创建一个带空格的文件：

printf '%s\n' '2026-10-30 11:00:00 ERROR 503 /cgi-bin/pay' \
  > "/tmp/shell-lab/logs/pay service.log"

用 NUL 分隔遍历并统计：

find /tmp/shell-lab/logs -type f -name '*.log' -print0 \
  | xargs -0 grep -h "ERROR" \
  | wc -l

预期：输出 4（原文件 3 条，新文件 1 条）。

如果写成 find ... | xargs grep，文件名中的空格可能被 xargs 当作分隔符，导致参数拆分错误。-print0 与 -0 的组合保证文件名按 NUL 分隔，不会因空格或换行而损坏。

步骤 8：把探索命令整理成可检查脚本（可选但推荐）

创建 /tmp/shell-lab/count_errors.sh：

#!/usr/bin/env bash
set -o pipefail

log_dir="${1:?usage: count_errors.sh <log-dir>}"

if [ ! -d "$log_dir" ]; then
  echo "not a directory: $log_dir" >&2
  exit 2
fi

count=$(
  find "$log_dir" -type f -name '*.log' -print0 \
    | xargs -0 grep -h "ERROR" \
    | wc -l
)

echo "ERROR count: $count"

执行：

chmod +x /tmp/shell-lab/count_errors.sh
/tmp/shell-lab/count_errors.sh /tmp/shell-lab/logs
echo "script exit status: $?"

这个脚本体现了本课的多个要点：参数加引号、目录存在性检查、pipefail、错误写 stderr、用退出码表达失败。它比一行命令更适合重复执行和审查。

5. 自测题

题 1：相对路径会指向哪里？

当前工作目录是 /home/backend，执行：

cd /var/log/wechat
cat logs/app.log

cat 实际尝试读取哪个文件？如果希望无论当前目录在哪都读取 /var/log/wechat/logs/app.log，应该怎么写？

答案： cat 读取的是 /var/log/wechat/logs/app.log，因为 cd 后当前工作目录变成了 /var/log/wechat，相对路径 logs/app.log 以它为基准解析。若要不受当前目录影响，应使用绝对路径：

cat /var/log/wechat/logs/app.log

题 2：为什么 cat $file 可能出错？

假设：

file="/var/log/wechat/wechat app.log"
cat $file

这条命令可能有什么问题？给出正确写法，并解释原因。

答案： 未加引号的 $file 会发生分词，路径中的空格被 Shell 当作参数分隔符，cat 可能收到 /var/log/wechat/wechat 和 app.log 两个参数，从而读取错误的文件或报错。正确写法是：

cat "$file"

双引号保证变量展开后仍作为一个参数传递，不会因空格被拆开，也不会让变量内容中的 * 等字符触发通配符展开。

题 3：管道失败为什么可能被掩盖？

执行：

grep "ERROR" /var/log/wechat/not-exist.log | wc -l
echo $?

grep 读取失败，但整个管道的退出码可能是什么？为什么？在 Bash 中如何让上游失败也导致整个管道失败？

答案： 默认情况下，管道的退出码是最后一个命令的退出码。这里 wc -l 成功执行（从空输入统计出 0），所以整个管道可能返回 0，尽管 grep 因文件不存在而失败。这会让人误以为统计成功。Bash 中可以开启：

set -o pipefail

开启后，管道中任意一个命令返回非 0，整个管道就返回非 0。生产脚本中应明确是否需要这一行为，并结合 stderr 与退出码一起判断。
