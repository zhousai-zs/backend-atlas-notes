导读

一个直觉例子：表格加了一列

财务部的共享表格原来有「日期、金额、状态」三列，状态只有「已付 / 未付」。某天有人加了第四列「备注」，又给状态加了一个新值「部分已付」。

  • 老的报表脚本按列名取数：读到不认识的「备注」列，应该忽略而不是崩溃——这是「未知字段」。
  • 老脚本里写着 if 状态 != "未付": 计入已收款：读到「部分已付」时，脚本不报错，却把只付了一半的单子算成全额收款——这是「线格式可解析，但业务语义不兼容」。
  • 有人用老脚本「读出来改个日期再写回去」，结果脚本只认识三列，写回时把「备注」整列抹掉了——这是「读-改-写丢字段」，回滚时最容易发生。
  • 表格不是一瞬间换掉的：有的同事已经用新模板，有的还在用旧脚本——这是「新旧客户端共存」。

接口演进要处理的就是这四件事，只是「表格」换成了 protobuf 消息，「同事」换成了滚动发布中的几百个实例。

接上前置课

  • f-protobuf：学了字段号、wire type 和二进制编码——线上传的是字段号，不是字段名，这是本课所有兼容规则的物理基础。
  • f-model：学了怎样给接口建数据模型（实体、状态、可选/必填）——本课讨论这些模型随时间变化时如何不破坏调用方。
  • protobuf.dev 的 Best Practices 开宗明义：客户端和服务端永远不会恰好同时更新，即使你努力让它们同时更新；任何一方都可能被回滚。所以不能假设「两边同步上线就没事」。

教学时间线（教学假设）

某内容后台的「文章详情」接口要上 v2：新增 cover_style（封面样式）字段，文章状态枚举新增 ARTICLE_STATE_FANS_ONLY = 3（仅粉丝可见）。

时间 事件
T+0 发布服务（写端）和详情服务（读端）同时开始滚动升级，计划 1 小时内 100%
T+15min 30% 实例已是 v2。v2 发布服务开始写出 FANS_ONLY 文章
T+18min 舆情反馈：部分游客能看到「仅粉丝可见」文章。排查：仍是 v1 的详情服务实例判可见性写的是 state != DRAFT 就展示，不认识的 3 被当成公开
T+20min 另一类告警：旧版后台管理页渲染状态标签时 Name(3) 抛异常，页面 500
T+25min 决定回滚到 v1。回滚后接口全部 200，没有任何解析错误，大家松了口气
T+2 天 修好后重新发布 v2，发现回滚期间被编辑过标题的文章 cover_style 全没了：v1 的编辑路径把消息转成内部 DTO 再写回，只拷了自己认识的字段

这条时间线里没有一次 protobuf 解析失败。出问题的是：语义（未知枚举当公开）、实现方式（用名字渲染枚举）、数据路径（读-改-写丢未知字段）、发布顺序（读端还没全量认识新值，写端就开始产生它）。

错误做法与正确做法对照

环节 错误做法 正确做法
新枚举 黑名单 state != DRAFT 就展示 白名单：只有 PUBLIC 放行，未知值走最严格分支并计数
渲染枚举 Name(state) 直接取名字 先判断值是否已知，未知显示「未知状态」
新字段缺失 新代码把 "" 当「用户选了空样式」 用 optional 区分「没传」和「传了空」，没传走业务默认值
读-改-写 拷到 DTO 再序列化 在解析出的原消息上修改，保留 unknown fields
发布顺序 读写端同时放量 先全量发布「认识新值」的读端，再打开写端产生新值
测试 只测 v2 客户端 × v2 服务端 v1/v2 × v1/v2 四种组合 + 回滚演练的契约测试

本课三条主线

  1. 新增字段和未知字段：线格式层面，新旧版本各自看到了什么。
  2. 语义兼容与版本策略：能解析之后，业务含义是否一致；选择怎样的演进方式。
  3. 灰度、契约测试和回滚：如何在真实的新旧组合里证明兼容，以及如何安全退回。

学习目标

学完本课，你应该能够：

  1. 能解释新增字段和未知字段。（goals 原文）
  2. 能独立完成：模拟v1/v2客户端与服务端四种组合，验证字段缺失和新枚举。（goals 原文）
  3. 能说清 protobuf 二进制线格式中「字段号 + wire type」为什么让新增字段、重命名（仅二进制）安全，而复用编号、改类型危险。
  4. 能区分 proto3 隐式 presence 与 optional 显式 presence，并据此设计字段缺失时的默认行为。
  5. 能举出至少三种「线格式可解析但语义不兼容」的变更（新枚举落入默认分支、单位变化、默认值变化），并给出保守兜底写法。
  6. 能按 expand-contract 顺序安排一次带新字段、新枚举的灰度发布，并列出按版本分桶的观测指标。
  7. 能为「回滚不因新数据无法解析而失败」设计契约测试与回滚演练，并证明读-改-写不丢数据。

为什么后端要懂

why 原文：让滚动发布和回滚不破坏数据与调用方。

后台服务几乎从不「停机升级」：

  • 滚动发布期间新旧版本必然共存。几百个实例分批替换，一个请求可能是 v2 网关 → v1 业务服务 → v2 存储服务；调用方（App、前端、其它团队的服务）的升级节奏你也控制不了。
  • 回滚时新数据已经写进去了。代码能回滚，数据不会。v2 写入存储、消息队列、缓存的消息，回滚后要被 v1 读，被 v1 改写，再被将来的 v2 重新读。
  • 破坏「调用方」表现为报错、展示错误、越权；破坏「数据」表现为静默丢字段——后者往往几天后才被发现，而且难以恢复。

线格式兼容 对方的字节我能解析吗？ 删掉 view_count = 4 后把 4 号复用为 like_count：同为 varint，解析不报错，但旧数据里的阅读数 12345 被读成了 12345 个赞（本课实验实测）
业务语义 解析出来的值，两边理解一致吗？ 新增 FANS_ONLY，旧服务按「非草稿即公开」处理
默认行为 字段没传时，两边各自怎么理解？ v2 把「不传可见性」从默认公开改成默认仅自己可见；旧客户端不传，结果文章全被藏起来
新旧客户端共存 发布期间所有组合都还能工作吗？ 30% 实例是 v2 时，v1 服务读 v2 数据、v2 服务读 v1 数据会同时发生

「滚动发布期间必须在旧服务与新客户端等组合中验证兼容性。」

四种组合各有自己的风险点：

服务端 v1 服务端 v2
客户端 v1 基线。仍要回归：v2 上线后又回滚时，这一格读的可能是 v2 写入的数据 字段缺失：v1 客户端不传 cover_style，服务端要有合理默认；v1 客户端收到 FANS_ONLY 时能否安全展示
客户端 v2 新客户端遇上旧服务（发布早期或回滚后）：新字段被忽略，新功能不可用但不能出错；旧服务读到新枚举要保守处理 目标态：新字段、新枚举的完整语义

这四格里，平时最容易被漏测的是右上和左下，而回滚场景会把「v2 写入的数据」带进左上这一格。本课的动手实践会把四格都真实跑一遍。

核心知识点

本课讨论的"兼容"有三层：二进制线格式能不能解析、解析出来的业务语义对不对、发布和回滚期间新旧组合会不会互相踩。三层都过了，才算一次安全的接口演进。

下面的场景是教学假设：公众号内容后台有一个文章详情接口，返回 Article 消息；v1 只有标题、正文、状态，v2 新增封面样式，并给文章状态增加"仅粉丝可见"。不涉及任何真实产品的内部实现，只借这个场景讲通用方法。

1. 新增字段和未知字段

1.1 线格式只认字段号，不认字段名

protobuf 的二进制线格式里，每个字段由两部分组成：

  • tag：(field_number << 3) | wire_type，决定"这是几号字段、后面怎么读"；
  • payload：字段值本身，编码方式由 wire type 决定。

常见 wire type：0 是 varint（int32/int64/bool/enum 等），1 是 64 位，2 是 length-delimited（string/bytes/嵌套消息），5 是 32 位。

举例：字段号 5、类型 string，wire type 是 2，tag = (5 << 3) | 2 = 42 = 0x2A。解析器读到 0x2A，就知道后面跟一个长度前缀加字节串。字段名根本不出现在二进制里，所以：

  • 二进制层面重命名字段是安全的（但 JSON/text format 不安全，见 1.6）；
  • 字段号一旦发布就是契约的一部分，删字段后不能把编号让给新字段。

1.2 一份 v1/v2 的 .proto 对比

v1 的定义如下（与本课实践 practice95/article_v1.proto 一致）：

syntax = "proto3";
package atlas.article;

enum ArticleState {
  ARTICLE_STATE_UNSPECIFIED = 0;
  ARTICLE_STATE_PUBLIC = 1;
  ARTICLE_STATE_DRAFT = 2;
}

message Article {
  int64 id = 1;
  string title = 2;
  ArticleState state = 3;
  int64 view_count = 4;
}

v2 只做两件事：新增字段号 5，给枚举末尾加一个值 3（practice95/article_v2.proto）。包名不变——这是「在原消息上演进」，不是另起 v2 包。

enum ArticleState {
  ARTICLE_STATE_UNSPECIFIED = 0;
  ARTICLE_STATE_PUBLIC = 1;
  ARTICLE_STATE_DRAFT = 2;
  ARTICLE_STATE_FANS_ONLY = 3;     // v2 新增：仅粉丝可见，教学假设
}

message Article {
  int64 id = 1;
  string title = 2;
  ArticleState state = 3;
  int64 view_count = 4;
  optional string cover_style = 5; // v2 新增：封面样式；optional 才能区分"没传"和"传了空串"
}

用 v2 序列化 Article(id=1, title="t", state=FANS_ONLY, cover_style="big")，本机实测字节为 08 01 12 01 74 18 03 2a 03 62 69 67：08=1 号 varint、12=2 号 length-delimited、18 03=3 号 varint 值 3、2a 03 "big"=5 号字符串——和上面算出的 tag 0x2A 对得上。

注意两个细节：

  • 新字段必须用没用过的字段号，这里是 5；
  • 新枚举值加在末尾，编号 3 也是新的，不能把 3 让给别的含义。

1.3 旧解析器读到新字段：跳过并放进 unknown fields

v1 的代码只认识 1~4 号字段。当它解析一条 v2 写出的数据时，遇到字段号 5：

  1. 按 tag 读出字段号和 wire type；
  2. 发现自己的 schema 里没有 5 号字段；
  3. 按 wire type 算出这个字段占多少字节，跳过 payload；
  4. 把这段原始字节记进 unknown fields（未知字段集合）。

所以"旧代码读新数据"通常不会解析失败。但"读到"不等于"理解"，更不等于"改写后还在"：

  • 只读路径：旧服务忽略 cover_style，照常返回它能返回的字段，没有影响；
  • 读-改-写路径（代理、ETL、缓存回填）：旧服务把消息解析成 v1 对象，修改别的字段，再序列化。现代 proto3 实现（3.5 之后，以所读版本为准）在解析后重新序列化时会保留 unknown fields，因此 cover_style 不会丢；但不同语言、不同版本、手写编码或某些中间件不保证这一点，必须在自己使用的实现上验证；
  • 如果旧代码把消息转成 JSON 再存回去，未知字段可能直接丢失，或者解析直接报错。

1.4 新解析器读旧数据：字段缺失得到默认值

反过来，v2 解析一条 v1 写出的数据，消息里没有 5 号字段，cover_style 取默认值 ""；state 如果没写，取 0，也就是 ARTICLE_STATE_UNSPECIFIED。

这里有一个 proto3 的常见坑：普通标量字段无法区分"没传"和"传了零值"。v1 客户端传 title = "" 和完全不传 title，在 v2 读出来都是 ""。如果业务需要区分，常见做法是：

  • 用 optional string cover_style = 5; 开启显式 presence（proto3 的 field presence，具体支持情况以所读文档和语言版本为准）；
  • 或用包装类型，例如 google.protobuf.StringValue。

两种做法都会改变"有没有值"的判断方式，接入前先确认序列化、JSON 映射和代码生成的行为。

1.5 未知枚举值：线格式能保留，业务代码未必看得懂

枚举在线上就是一个变长整数。v1 的 ArticleState 里没有 3，读到 ARTICLE_STATE_FANS_ONLY = 3 时会发生什么，取决于 proto 版本和语言实现：

  • 按 protobuf.dev 的口径，旧客户端可能把新枚举值看作未设置，getter 返回默认值；
  • 同时 proto3 的枚举支持未知值 round-trip：解析后再序列化，数值 3 可以保留下来；
  • 有些语言的 getter 会返回 UNRECOGNIZED 或原始数字，有些则退化成默认值（proto2 的 closed enum 会把未知值放进 unknown fields）。
  • 本机实测（protobuf Python 7.36.2，proto3）：v1 读 v2 数据，old.state == 3，数值原样保留；但 v1 的 EnumTypeWrapper(ArticleState).Name(3) 抛 ValueError: Enum ArticleState has no name defined for value 3——「能解析」和「代码能处理」是两回事。

这两件事不矛盾：业务代码读到的默认值，不代表线格式把值丢了。工程上不要赌某一端的具体行为，而要做到：

  1. 旧代码里所有 switch/if 枚举的分支必须有 default，且 default 走保守路径；
  2. 新枚举值只加在末尾，不复用旧编号；
  3. 需要删除枚举值时，同样要 reserved 其编号和名字。

教学假设的例子：文章列表页的旧版本只认识"草稿/已发布"，遇到"仅粉丝可见"若没有 default 分支或 default 当成公开，就会把仅粉丝可见的文章展示成公开文章，这是业务语义事故，而不是解析错误。

1.6 为什么不能用 JSON/text format 做数据交换

二进制线格式里字段名不参与编码，所以改名字、加字段，旧二进制解析器都能跳过。JSON 和 protobuf text format 是按字段名匹配的：

  • 旧代码遇到新字段名，默认可能直接报错；
  • 需要显式打开类似 ignore_unknown_fields 的选项才可能跳过（选项名和行为以语言实现为准）；
  • 新增枚举值时，旧代码如果按字符串匹配枚举，也会失败或落到未知分支。

所以：RPC API 和存储用二进制 protobuf 消息，不要把 JSON/text format 当成持久化格式或跨服务交换格式。如果确实要对外提供 JSON，就要把 JSON 当成另一套契约单独做兼容测试。

1.7 Python 实测：默认值与未知字段

下面是 practice95/contract_test.py 里的真实片段（ArticleV1/ArticleV2 由 schema.py 用 descriptor_pb2 动态构造，不需要 protoc）：

from google.protobuf import unknown_fields, json_format
b2 = ArticleV2(id=8, title="fans", state=3, view_count=9, cover_style="big").SerializeToString()

old = ArticleV1.FromString(b2)                     # 不抛异常
print(old.state)                                   # 3   ← open enum 保留数值
print([(f.field_number, f.data) for f in unknown_fields.UnknownFieldSet(old)])
                                                   # [(5, b'big')]  ← 进了 unknown fields
print(old.SerializeToString() == b2)               # True ← 原样再序列化，新字段还在

v2_from_v1 = ArticleV2.FromString(ArticleV1(id=7).SerializeToString())
print(v2_from_v1.HasField("cover_style"), repr(v2_from_v1.cover_style))   # False ''

JSON 路径则严格得多（同样是实测）：

js = json_format.MessageToJson(ArticleV2.FromString(b2))   # "state": "ARTICLE_STATE_FANS_ONLY", "coverStyle": "big"
json_format.Parse(js, ArticleV1())
# ParseError: Failed to parse state field: Invalid enum value ARTICLE_STATE_FANS_ONLY ...
x = json_format.Parse(js, ArticleV1(), ignore_unknown_fields=True)
print(x.state)   # 0 —— 不报错了，但状态变成 UNSPECIFIED，cover_style 也没了

ignore_unknown_fields=True 看似「解决了兼容」，实际是把新枚举静默变成 0、把新字段静默丢掉；如果这个对象再被写回存储，数据就真的丢了。

还有一个容易忽略的点：不要依赖跨构建的序列化稳定性。同一消息在不同版本、不同语言、不同字段顺序下序列化出的字节可能不同，不能拿序列化字节直接做缓存键、去重键，跨版本/跨语言的 golden 断言也应比较字段值（本课实践里「v1 原样再序列化与 v2 字节一致」只是在固定的 Python 实现与版本下验证 unknown fields 被原样保留）。需要稳定标识时，用业务主键或显式计算的摘要。

2. 语义兼容与版本策略

2.1 线格式兼容 ≠ 语义兼容

解析成功只是第一层。下面这些变更，两端都能解析，但业务会出错：

  • 单位变化：v1 的 due_time 是毫秒，v2 改成秒，字段号和类型都没变，解析没问题，值差 1000 倍；
  • 默认行为变化：v1 不传可见性时默认公开，v2 把默认改成"仅自己可见"，旧客户端不传字段，语义就变了；
  • 可选变必填：v2 业务要求 cover_style 必填，但 v1 客户端不会传，服务端校验直接失败；
  • 枚举语义扩展：旧端不认识"仅粉丝可见"，default 分支若按"公开"处理，就把受限内容放出去了；
  • 布尔扩展：is_deleted 只有 true/false，将来要表达"删除中/已删除/恢复中"时无路可走，应该一开始就用 enum。

2.2 安全变更与破坏性变更清单

变更 二进制线格式 业务语义与注意事项
新增可选字段，使用新编号 安全 旧端忽略；新端缺省值必须有合理含义
新增枚举值 可解析 旧端 default 必须走保守路径，否则语义破坏
删除字段，reserved 编号和名字 安全 旧数据里的该字段变成 unknown fields；编号和名字都不能复用
重命名字段 安全 仅限二进制；JSON/text format 按名字匹配，会失败
修改字段类型 破坏性 即使 wire type 相同，解释方式也可能变
复用已删除的 tag 号 破坏性 旧数据会被当成新字段解析，静默错乱
修改字段默认值 破坏性 版本错位时两端对"未设置"读出不同结果
repeated 改为 scalar 破坏性 会丢数据
scalar 改为 repeated 有条件可行 proto2 及 proto3 [packed=false] 下二进制可行，但业务语义仍需检查
新增 required 字段 禁止 proto3 已无 required；proto2 也不要新增

两条容易被忽略的规则：

  • 删除字段时，除了 reserved 5;，还要 reserved "cover_style";，防止编号和名字被后来的人复用；
  • 删除枚举值时也要 reserved。只删定义不 reserved，等于给未来埋了一个"编号复用"的雷。

2.3 枚举设计：第一个值是 UNSPECIFIED

按 protobuf.dev 的建议（以所读版本为准）：

  • 枚举第一个值应为 FOO_UNSPECIFIED = 0，作为"未设置/未知"的显式表达；
  • 新增值加在末尾，不复用编号；
  • 旧端所有分支都要有 default，且 default 的语义要保守：未知可见性按"不可见/最严格"处理，未知状态按"需要人工审核"处理，而不是按"公开/正常"处理；
  • 不要用 bool 表示现在只有两种、将来可能更多的状态。

教学假设：文章可见性 v1 只有"公开/私密"，v2 增加"仅粉丝可见"。如果 v1 的列表接口把未知值当公开，灰度期间就会出现"仅粉丝文章出现在公开列表"的越权展示；正确做法是未知值按不可见处理，等读端全部升级后再放开。

2.4 版本策略：加字段、并行 v2，还是能力协商

三种常见策略，按变更规模选：

  1. 在原消息上加字段：适合向后兼容的小步演进，例如新增 cover_style。包名不变，成本最低；风险是语义慢慢漂移，必须配合契约测试和弃用计划。
  2. 新包名/新消息并行：例如 package article.v2，定义一套新的 Article。适合字段类型要改、单位要改、语义要大改的场景。做法是 v1/v2 并行一段时间，读端先支持双读或迁移，写端切换，确认 v1 无流量后再下线。代价是两套 schema 和两套测试的维护成本。
  3. 能力协商/特性开关：客户端上报支持的接口版本或特性，服务端按能力决定返回什么；或者服务端用开关控制是否写新字段。适合无法强制升级的客户端。注意开关必须可回滚，且不能让新旧语义在同一个字段上打架。

配套的两条实践：

  • RPC API 和存储用不同的消息类型。对外可以是 ArticleView，落库可以是 ArticleRecord。这样 API 的兼容策略不会把存储 schema 锁死，存储的内部字段也不必暴露给调用方。
  • 弃用流程：先标 deprecated（字段或 RPC），再观测调用量和字段读取量，确认无人使用后删除，并 reserved 编号和名字。删除枚举值同理。弃用期要覆盖至少一个完整的发布周期，具体时长按业务节奏定。

3. 灰度、契约测试和回滚

3.1 发布顺序：先读端，后写端，最后清理

接口演进推荐 expand-contract（扩展-收缩）的顺序：

  1. Expand（扩展读端）：先发布能识别新字段、新枚举的读服务。此时写端还不产生新值，旧数据也能正常读。旧代码的 default 分支要在这时补齐。
  2. Migrate（写端放量）：再让写端产生新字段/新枚举，先小流量灰度，观察旧读端的表现。
  3. Contract（清理）：确认旧读端都已升级或下线，再清理兼容分支、删除旧字段并 reserved。

教学假设：文章状态新增"仅粉丝可见"时，先让详情、列表、审核、搜索等所有读服务认识 3 并走保守分支；再让发布服务写 3；最后清理"只有两种状态"的旧假设。顺序反了，旧读服务就会先看到不认识的值。

3.2 灰度矩阵：四种组合都要跑

课程练习要求模拟 v1/v2 客户端与服务端的四种组合，验证字段缺失和新枚举。矩阵如下：

客户端 服务端 重点观察
v1 v1 基线，确认旧行为不变
v1 v2 旧客户端不传新字段；服务端默认值是否合理；新枚举在旧界面如何展示
v2 v1 新字段被旧服务忽略或保留；旧服务读-改-写是否丢字段；新枚举旧服务是否报错
v2 v2 目标态，字段和新枚举的完整语义

观测指标建议按 client_version、server_version 分桶：

  • 解析失败数、反序列化异常率；
  • 未知枚举值计数（可以在代码里显式统计 default 分支命中）；
  • 新字段缺失率（判断升级覆盖率）；
  • 业务状态分布，例如"仅粉丝可见"文章的展示、审核、搜索路径是否异常；
  • 按版本分桶的错误率和延迟，避免只看总量掩盖局部问题。

日志里记录版本号和字段是否存在即可，不要把文章正文等敏感内容打进日志。

3.3 契约测试：把每个版本的样本存档

契约测试的目标不是"测一遍业务逻辑"，而是固定住"哪个版本能读哪种数据"。做法：

  1. 每个版本的 schema 存档，至少保留已发布过的版本；
  2. 保存 golden 样本消息：v1 旧数据、v2 新数据、带未知字段的数据、带未知枚举值的数据；
  3. CI 里跑三类用例：旧读新、新读旧、旧读改写新（验证 unknown fields 是否保留）；
  4. 对枚举单独加用例：未知值必须走 default 的保守分支；
  5. 如果对外还有 JSON 接口，JSON 路径单独测，不能拿二进制的结果代替。

schema 层面可以用 buf breaking 一类的检查工具，把当前 schema 和主干或已发布版本做对比，拦截删字段不 reserved、改类型、复用编号等问题。具体规则和命令以所读工具文档为准。

注意：golden 断言不要直接比较序列化后的字节，跨构建、跨语言、字段顺序变化都可能不同。应该比较字段值，或者固定实现和版本后再做字节级断言。

3.4 回滚：先确认旧版本读得懂新数据

回滚不是"把镜像换回去"这么简单。回滚前至少确认：

  • 旧版本能解析新版本已经写入的数据：未知字段会跳过，未知枚举值不导致异常；
  • 旧版本读-改-写不会丢新字段。如果会丢（老实现、第三方库、JSON 管道），先关掉写新字段的开关，再回滚；
  • 数据库、消息队列、缓存里的数据格式都检查一遍，不要只检查 RPC；
  • 双写场景先停新写路径或关特性开关，观察一段时间，再回滚代码，避免旧代码覆盖新字段；
  • 回滚后保留新字段的数据，不要顺手清理，等下次升级继续用。

如果新数据已经被旧代码以 JSON 形式写回，且旧代码不认识新字段，数据可能已经丢了。这类路径要在发布前就纳入契约测试，而不是等回滚时才发现。

3.5 小结

把三点连起来看：

  • 新增字段和未知字段解决"字节能不能读懂"：字段号是契约，未知字段要能跳过，必要时保留；
  • 语义兼容和版本策略解决"读懂了会不会做错事"：枚举 default 要保守，单位、默认值、必填性都不能悄悄改；
  • 灰度、契约测试和回滚解决"在真实的新旧组合里验证过没有"：先读端后写端，四象限矩阵，样本存档，回滚前确认旧版本能读新数据。

线格式可解析不代表业务语义兼容。长期兼容能降低升级耦合，但保留旧语义会增加维护负担，所以每次演进都要同时准备弃用和清理计划。具体到本课场景，就是：先让所有读端认识"仅粉丝可见"并保守处理，再让写端产生它，最后用契约测试和回滚演练证明新旧组合都不会丢数据、不会放错权限。

常见误区

原节点给出的核心判断是：「线格式可解析不代表业务语义兼容。」

这句话至少要拆成三层来看。第一层是线格式：二进制能按字段号和 wire type 解出来，不报错。第二层是接口契约：双方对字段号、字段类型、出现条件和默认行为有共识。第三层才是业务语义：同一个值在旧代码和新代码里被解释成同一件事。前两层通过，第三层仍可能出错。

教学假设：文章详情接口的 state 枚举新增「仅粉丝可见」。旧客户端可以把这个新值解析出来，但如果它的逻辑是“不是 PUBLIC 就当草稿”，那么一篇仅粉丝可见的文章会被显示成草稿，甚至进入错误的编辑入口。解析成功，业务结论却是错的。

再比如，把发布时间从秒改成毫秒，字段类型没变、字段号没变，线格式完全兼容，但旧服务会把 1.7e12 当成一个荒谬的秒级时间戳；把未设置字段的默认值从 0 改成“当前时间”，两端对同一条缺失字段的记录会读出不同结果。它们都属于“能解析，但不兼容”。

因此每次演进都要分别回答三个问题：线格式变了吗？契约变了吗？语义变了吗？下面这些误区，大多是把第一层的成功当成了第三层的成功。

误区一：复用已删除字段的编号或名字

误区：删除一个字段后，觉得编号空着浪费，下一版又拿来放新字段；或者只删代码里的读写逻辑，不在 .proto 里做 reserved。

后果：历史数据、消息队列里的旧消息、尚未升级的客户端，仍可能按旧含义写入该编号。新代码用新类型读取旧字节，轻则得到垃圾值，重则解析失败；本课实验实测：删掉 int64 view_count = 4 后把 4 号复用成 int64 like_count，旧数据里 view_count=12345 不报任何错，直接被读成 like_count=12345；反过来，旧代码读到新字段也会误判。问题往往在回滚、补数据或跨版本联调时才暴露。

正确做法：删除字段时同时 reserved 其编号和名字，删除枚举值也要 reserved。编号只增不复用，名字也不要给新字段再用。以所读 protobuf 文档版本为准，reserved 是编译器和后来者都能看到的硬约束，不是一句注释。

误区二：以为客户端和服务端会同时升级

误区：联调时只测 v2 客户端打 v2 服务端，认为发布完成后大家自然都是新版本；或者把“我这边测过了”当成兼容性结论。

后果：滚动发布期间真实存在四种组合：v1 客户端 × v1 服务端、v1 × v2、v2 × v1、v2 × v2。旧客户端还可能长期不升级。只测一种组合，等于把另外三种留给线上流量去验证。对应节点 acceptance 的要求：所有兼容组合都要有契约测试。

正确做法：把四种组合写进契约测试矩阵，至少覆盖新字段缺失、新枚举值、未知字段保留、回滚后的读改写。教学假设：草稿/发布服务滚动升级时，让 v1 与 v2 实例同时处理同一篇草稿，验证双方都能读、都能写，并且不会把对方新增的字段抹掉。

误区三：回滚时旧版本遇到新数据就报错，或读改写时丢掉新字段

误区：只考虑“新代码如何读旧数据”，不考虑“旧代码如何读新代码写下的数据”；或者认为回滚就是把镜像换回去，数据自然也会回去。

后果：

  • 新版本写入的存储消息里带了新字段或新枚举值，回滚后的旧版本解析失败，服务起不来或请求大面积报错。
  • 旧版本能解析，但读出来以后做了一次“读—改—写”，把不认识的字段重新序列化时丢掉，造成静默数据损坏。
  • 消息队列里已经堆积了新格式消息，旧消费者回滚后无法处理，只能跳过或阻塞。
  • 契约测试只覆盖正向升级，没有覆盖回滚，问题在故障恢复最紧张的时候出现。

对应节点 acceptance 的要求：回滚不因新数据无法解析而失败。

正确做法：

  • 回滚演练要使用新版本真实写下的数据，而不是旧版本的测试夹具。
  • 读改写路径要验证未知字段是否保留。一般 protobuf 知识：现代 proto3 实现解析后再序列化会保留未知字段（3.5 之后，以所读版本文档为准），但不要把它当成所有语言、所有手写解析器都自动具备的能力。
  • 内部 DTO 映射不要只挑认识的字段，否则在业务层就把未知字段丢了。本课实践实测：回滚到 v1 naive（DTO 拷贝）对 50 篇文章读改写，接口全部 200、parse_error=0，前滚回 v2 后 cover_style 保留 0/50；v1 safe（原消息上改）保留 50/50。
  • 存储消息和 API 消息分开设计，回滚时至少保证存储层可读；必要时让新字段先只写不读，观察一个发布周期后再启用读逻辑。
  • 教学假设：草稿服务升级后写入“仅粉丝可见”状态，回滚前先确认旧版本对该状态的默认分支是拒绝写入还是降级为草稿，不能让它误发布。

误区四：用 JSON 或 text format 做内部数据交换，还随意重命名、加枚举值

误区：觉得 JSON 可读性好，就拿它做服务间消息或存储格式；字段重命名时只改新代码，或者新增枚举值时不考虑旧消费者。

后果：

  • 二进制线格式里字段名不参与编码，改字段名通常不影响兼容；JSON 里字段名就是契约，重命名等于删除旧字段再加新字段，旧代码直接读不到。
  • 旧代码遇到不认识的枚举字符串，可能反序列化失败，而不是像二进制枚举那样保留未知值。
  • text format 和 JSON 都不具备 protobuf 二进制线格式那种按字段号演进的能力，跨版本解析更脆弱。
  • 一旦把 JSON 当存储格式，历史数据的字段名会被永久冻结，后续清理成本更高。

正确做法：

  • 内部 RPC 和存储优先使用二进制 protobuf 消息，不用 text format 或 JSON 做数据交换。
  • 如果外部 HTTP 接口必须用 JSON，把它当成独立契约管理：字段只增不删、改名走新增别名和迁移期、枚举新增值要确认旧客户端行为。
  • 对外 JSON 与内部消息之间做显式转换，不要让内部字段名直接暴露成外部契约。
  • 契约测试要覆盖旧版本解析新 JSON 的行为，包括未知字段和未知枚举值。

误区五：用 bool 表达以后可能扩展的状态

误区：现在只有“是/否”两种状态，就加一个 bool is_fans_only；以后要多一种可见范围，再继续加 bool is_friend_only、bool is_internal_only。

后果：

  • 多个 bool 会出现互斥、组合和优先级问题，旧代码只认识其中一个，读到新组合时行为不确定。
  • 字段语义从“是否仅粉丝可见”扩展成“可见范围”时，旧字段无法表达新值，只能再加字段并处理冲突。
  • 默认值 false 同时承担“未设置”和“明确为否”两种含义，版本错位时无法区分。

正确做法：

  • 只要状态存在扩展可能，就用 enum，而不是 bool。
  • 枚举第一个值设为 FOO_UNSPECIFIED = 0，让“未设置”和业务值分开。
  • 按 protobuf.dev 的说法，旧客户端遇到新枚举值时可能把字段看作未设置、getter 返回默认值（proto3 open enum 在一些实现里则保留原始数值，本课 Python 实测 state == 3）；无论哪种，业务代码都要明确这个默认分支是拒绝、降级还是走通用逻辑。
  • 一般 protobuf 知识：proto 枚举可以 round-trip 未知枚举值，但业务代码不能假设自己认识所有值。

误区六：把序列化字节当缓存键或做签名比较

误区：把 protobuf 序列化后的字节直接做缓存 key、去重指纹或签名内容，认为同样的业务对象一定得到同样的字节。

后果：

  • 序列化结果不保证跨构建、跨语言、跨版本稳定，字段顺序、未知字段、map 顺序等都可能变化。
  • 同一个业务对象在不同版本算出不同 key，缓存命中率下降，甚至出现同一实体多份缓存。
  • 用序列化字节做签名比较时，升级序列化库或消息定义就可能让旧签名全部失效。
  • 这类问题通常不报错，只是悄悄多占存储、多打下游。

正确做法：

  • 缓存 key 用明确的业务主键和版本前缀，不用序列化字节。
  • 需要指纹时，显式定义参与计算的字段和规范化编码，并给指纹加版本号。
  • 签名比较使用协议规定的规范化输入，不直接拿内存里的序列化结果。
  • 把“跨构建序列化稳定性”当成不存在的保证，以所读文档版本为准。

设计权衡

原节点给出的 tradeoff 是：「长期兼容降低升级耦合，但保留旧语义会增加维护负担。」

兼容不是免费的。每保留一个旧字段，就要在文档、序列化定义、读写路径、契约测试和监控里保留它；每保留一个旧枚举值，就要在业务分支里回答“旧值现在该怎么处理”。时间一长，代码里会出现大量“为什么这里还判断 LEGACY_*”的注释，新人不敢删，老人也说不清。

教学假设：文章服务为了兼容旧客户端，同时保留 is_fans_only 和新的 visibility 枚举。双写期间每次发布都要保证两个字段一致；读路径还要先看新字段、缺失时回退旧字段。等所有读者升级后，旧字段才能停止写入，但仍不能复用编号，只能 reserved。这就是“升级耦合降低”换来的“长期维护负担”。

常见的兼容成本包括：

  • 兼容层代码：新旧字段映射、默认分支、版本判断，往往散落在多个服务里。
  • 双写与回填：过渡期写两份、读时回退，回填历史数据还要限流和校验。
  • 旧字段长期留存：不能删编号、不能改语义、不能改默认值，测试矩阵持续变大。
  • 认知负担：值班和排障时要先判断消息来自哪个版本，日志和监控也要按版本切分。

三种方案也可以组合：内部存储消息按 v2 设计，对外 RPC 仍在 v1 上增量演进，由服务内部做转换。关键是明确哪一层承担兼容责任，不要让每个调用方各自猜。

何时值得做破坏性变更

破坏性变更不是绝对不能做，而是要算清楚代价和窗口。以下情况通常值得考虑：

  • 调用方完全可控，能在同一发布窗口内一起升级，例如内部管理后台。
  • 旧语义已经造成持续的数据错误或安全问题，继续兼容等于保留缺陷。
  • 有明确的数据迁移方案和回滚方案，迁移期间新旧数据能共存并可校验。
  • 旧客户端可以下线，或者有强制的升级手段和足够的通知周期。
  • 变更收益足够大，能抵消双写、转换层和契约测试的长期成本。

反之，面对无法强制升级的外部客户端、长期保留的历史存储数据、以及仍在消费旧消息的离线任务，破坏性变更要非常谨慎。教学假设中的公众号后台场景，如果调用方包含第三方或大量不可控客户端，就更偏向增量演进和长弃用期。

弃用周期取决于什么

弃用周期不是拍脑袋定一个“三个月”，而是由几个现实约束共同决定：

  • 客户端更新周期：强制更新能力弱、长尾版本多的客户端，需要更长窗口。
  • 存储数据保留时间：历史数据还在，旧字段的读取逻辑就不能立刻删；编号则永久保留。
  • 日志和消息队列里的历史数据：离线回放、审计和对账任务可能仍在读旧格式。
  • 回滚窗口：至少要覆盖一次完整发布和回滚周期，避免回滚后无代码可读新数据。
  • 观测与通知：要能统计还有多少调用方在用旧字段，否则无法判断何时真正可以下线。

一个可执行的做法是：先停止写入旧字段，观察一个完整发布周期；再停止读取并保留转换逻辑；最后删除代码但永久 reserved 编号和名字。每一步都用契约测试和线上指标确认没有残余流量。

API 消息与存储消息要不要分开

公开的最佳实践建议 RPC API 和存储使用不同的消息类型。收益是两边可以独立演进：对外接口可以隐藏内部字段，存储可以保留更久的兼容字段，回滚时也不必被 API 契约绑死。

成本也很直接：需要维护两套定义和一层映射代码，容易出现字段漂移、默认值不一致和转换遗漏；每次新增字段都要改两处并补测试。若早期消息很简单，强行拆分可能过度设计。

判断标准一般看两点：存储数据的生命周期是否明显长于 API 版本周期；以及 API 契约是否需要对调用方隐藏内部结构。只要其中一点成立，分开通常更划算。教学假设：文章正文在存储里保留草稿、审核、发布多个阶段的历史字段，而对外详情接口只暴露当前可见结果，这种场景就适合分开建模。

两版 schema 的差别（article_v2.proto）：

enum ArticleState {
  ARTICLE_STATE_UNSPECIFIED = 0;
  ARTICLE_STATE_PUBLIC = 1;
  ARTICLE_STATE_DRAFT = 2;
  ARTICLE_STATE_FANS_ONLY = 3;     // v2 新增：放在最后；v1 只看到数值 3
}
message Article {
  int64 id = 1;
  string title = 2;
  ArticleState state = 3;
  int64 view_count = 4;
  optional string cover_style = 5; // v2 新增：optional 才能区分"没传"和"传了空串"
}

safe 与 naive 服务端的区别就是本课的两类风险：

维度 naive（反面教材） safe（正确做法）
语义：未知枚举 黑名单：return state != DRAFT，不认识的 3 被当成"公开" 白名单：只有 PUBLIC 放行；未知值按最严格（不可见）处理并计数 unknown_enum
回滚：读-改-写 DTO 拷贝：Article(id=..., title=..., state=..., view_count=...)，只拷自己认识的字段 在解析出的原消息上改 title 再序列化，unknown fields 随之保留

逐条阅读卡

Don't Re-use a Tag Number

  • 要点：tag 号标识线格式字段；复用编号会让旧数据被新定义误读。
  • 与本课实践的对应：v1/v2 四种组合必须覆盖“旧数据被新字段号读取”。
  • 待验证：构造旧消息后以新 schema 解析，记录实际读到的值、unknown fields 与是否报错。

Reserve Tag Numbers

  • 要点：删除字段应写 reserved 4; 和 reserved "old_tag";，编号和名字都保留，防止人和工具再用。
  • 与本课实践的对应：删除 old_tag 的发布检查项与代码评审检查。
  • 待验证：所用编译器/代码生成器对 reserved 冲突是否编译报错；proto3 语法以所读版本为准。

Include an Unspecified Value in an Enum

  • 要点：枚举首值用 FOO_UNSPECIFIED = 0；旧客户端可能把新枚举值视作未设置、getter 返回默认值，但二进制可 round-trip 未知枚举值。
  • 与本课实践的对应：新增 FANS_ONLY = 3，以及 v1 读取时的兜底。
  • 待验证：本版本生成代码对未知枚举值的 getter、has_*、重新序列化行为。

Don't Change the Default Value

  • 要点：默认值变化在版本错位时会让两端对“未设置字段”读出不同结果；不要把默认值当业务开关。
  • 与本课实践的对应：新增字段缺省时的可见性或审核策略。
  • 待验证：未设置、显式设置为默认值、旧端解析三种情况是否可区分。

Don't Go from Repeated to Scalar

  • 要点：repeated→scalar 会丢数据；scalar→repeated 在 proto2 及 proto3 [packed=false] 下可能二进制可行，但 API 语义与实现差异仍需谨慎。
  • 与本课实践的对应：标签列表、图片列表等字段的演进。
  • 待验证：以目标版本验证 packed 与 JSON/文本路径，不以“能编译”代替兼容性测试。

Don't use Text Format Messages for Interchange

  • 要点：text format/JSON 依赖字段名，重命名或新增枚举值时旧代码可能解析失败；二进制线格式不编码字段名。
  • 与本课实践的对应：服务间数据交换与调试日志不能混用；调试展示可读，交换仍走二进制。
  • 待验证：新增枚举值、重命名字段在旧 JSON 解析器上的失败方式。

Never Rely on Serialization Stability

  • 要点：同一消息跨构建/跨版本的字节不保证稳定，不能把序列化结果当缓存键、幂等键或内容哈希。
  • 与本课实践的对应：文章详情缓存、消息去重键。
  • 待验证：对同一消息多次运行/不同进程序列化并比较；改用业务 ID+版本做键。

Use Different Messages For RPC APIs and Storage

  • 要点：RPC 契约和存储格式的演进节奏不同；共用消息会把外部兼容压力带进存储，或把存储迁移暴露给调用方。
  • 与本课实践的对应：文章详情 API 与草稿/发布存储消息分开定义。
  • 待验证：检查现有 proto 是否一份消息同时承担 RPC 与落盘；若是，先加适配层再演进。

边界 - 公开文档只能说明 protobuf 的通用规则，不能推断任何企业内部实现、字段或发布流程。 - Python 实验用于模拟“缺失字段、未知字段、未知枚举、序列化后读回”的语义；C++ 生成代码、反射和 unknown field 保留细节以对应版本为准。 - “业务语义兼容”需另写领域断言：线格式不报错，不等于可见性、计数、审核状态正确。

自测题

题 1：新增 FANS_ONLY=3 后，v1 服务为什么仍可能出事故？

题干 文章状态定义为 ARTICLE_STATE_UNSPECIFIED=0, ARTICLE_STATE_PUBLIC=1, ARTICLE_STATE_DRAFT=2；v2 新增 ARTICLE_STATE_FANS_ONLY=3。v1 服务读到 v2 写入的 FANS_ONLY 消息时，线格式可以解析。为什么仍可能出事故？v1 代码应如何写兜底？发布顺序应怎样？

答案 线格式能解析只说明字段号和 wire type 能走通；v1 不认识 3，可能把状态看成未设置/getter 返回默认值。若 v1 的默认分支被写成“公开可见”，仅粉丝文章就可能被错误曝光；若过滤、审核、推荐把未知值当 PUBLIC，也会产生错误行为。v1 应把未知/未设置状态放进显式的保守分支：不可公开、拒绝或转人工，并打点记录；不能依赖 switch 的 default 静默放行（本课实践：v1 naive 黑名单让游客看到 20/20 篇 FANS_ONLY，v1 safe 白名单为 0，同时 unknown_enum 计数 80 可用于告警；代价是回滚期间粉丝也暂时看不到这 20 篇）。若 v1 会重写消息，应尽量保留未知枚举的原始数值，避免 round-trip 丢失。发布顺序：先让所有可能读取新值的实例升级并具备安全兜底，灰度验证后再允许写入 FANS_ONLY；滚动期间避免未升级实例接读写流量；回滚时先停止写入新值，再回退读取方。

解析 这是“可解析但语义不兼容”。枚举新增是线格式层面的前向兼容变化，不是自动的业务兼容。契约测试必须覆盖“v2 写、v1 读”；只测“v1 写、v2 读”会漏掉旧读取方。未知枚举的 getter 与保留行为和实现版本有关，以所读文档及实际运行时为准。

题 2：删除 old_tag=4 后复用编号 4，会发生什么？

题干 v2 删除了 string old_tag = 4;，半年后同事新增 int64 like_count = 4;。线上仍有历史消息和可能回滚的旧客户端。会发生什么？怎么预防？

答案 历史消息仍可能带有 tag 4。若旧字段与新字段的 wire type 相同，新解析器会把旧值直接解释成 like_count，形成脏计数且很难发现；若 wire type 不同，不同实现和代码路径可能跳过、放入 unknown fields 或报错，不能把“这次碰巧不兼容”当成保护。更危险的是，旧客户端回滚后又会把 tag 4 当成 old_tag。删除时必须 reserved 4; 和 reserved "old_tag";，并在 CI/lint 中检查 reserved 冲突；新字段改用从未使用过的编号。

解析 tag 号是长期契约，不是代码里的局部变量。编号复用的故障往往跨发布周期、跨存储副本才暴露。预防依赖 schema 规范、代码评审、lint 和历史数据生命周期检查；具体工具能力以所读文档和项目版本为准。

题 3：v2 数据回滚到 v1，如何证明能解析且不丢数据？

题干 v2 已写入带新字段的数据，此时需要回滚到 v1。如何证明“回滚不因新数据无法解析而失败”，并且不丢数据？给出契约测试矩阵和关键断言。

答案 先固定 v1/v2 的 schema、运行时版本和样本，再跑四种组合；每种组合都做“读—校验—读改写—再校验”，不能只做一次反序列化。

写入方 读取方 必测内容
v1 v1 基线字段、默认值、旧数据回归
v1 v2 新字段缺省语义、迁移/兼容逻辑
v2 v1 新字段被忽略时能否解析、基础字段是否正确、未知字段是否保留
v2 v2 新字段、新枚举的正常读写与回滚后语义

关键断言： 1. v1 读取 v2 数据不抛解析异常，文章 ID、标题、正文、状态等基础字段保持一致。 2. 新字段不会映射到任何 v1 字段；v1 业务逻辑不会因未知字段改变可见性、计数或审核状态。 3. v1 读改写后重新序列化，v2 仍能读到新字段的原值；现代 proto3 实现通常在 3.5 之后保留未知字段，但必须以本项目实际版本验证。 4. 未知枚举值在 v1 中不得被误当成 PUBLIC；若实现能保留原始数值，回写后仍应是 FANS_ONLY。 5. 存储链路要做端到端测试：若中间层按已知字段重建消息，unknown fields 会被丢掉，回滚就会丢数据。 6. 用 v2 数据快照做回滚演练：停写新值、备份、让 v1 处理、再让 v2 读回并比对；比对失败则阻断回滚。

本课 test.sh 第 5 段就是这个演练的缩小版：v1 safe 读改写 ok=50, fail=0, parse_error=0，前滚 v2 后 cover_present=50；换成 DTO 拷贝的 naive 版本同样全部 200，但 cover_present=0——只断言「不报错」是抓不住的。

解析 “v1 能启动”不等于“回滚安全”。证明对象是数据在 v1 读写之后仍可被 v2 解释，且业务字段没有变化。unknown fields 的保留是版本相关实现细节，不能只凭常识；契约测试矩阵覆盖“所有兼容组合有契约测试”，回滚演练对应“回滚不因新数据无法解析而失败”。

本课小结

  • 接口演进要同时处理线格式兼容、业务语义、默认行为和新旧客户端共存；滚动发布与回滚是主战场。
  • 新增字段和 unknown fields 是兼容的起点，但旧端“能解析”不代表业务流程正确；未知字段保留能力以实现版本为准。
  • 枚举新增必须显式处理未知值，首值使用 *_UNSPECIFIED=0；默认分支不得静默放行。
  • 删除字段必须 reserved 编号和名字；永远不复用 tag，不靠 wire type 碰巧不匹配来兜底。
  • 不改字段类型、默认值；repeated/scalar 变更按文档与实测评估；跨服务交换不用 text format/JSON。
  • RPC API 与存储使用不同消息；不要把序列化字节当作缓存键或跨构建稳定标识。
  • 灰度与回滚需要四种组合的契约测试、数据快照演练和“先读后写”的发布顺序，验收关注所有兼容组合与回滚可解析性。
  • 权衡：长期兼容降低升级耦合，但保留旧语义增加维护负担；公开文档不推断企业内部实现，C++/运行时细节以所读版本文档为准。
