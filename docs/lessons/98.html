参考资料 B+Tree与索引访问路径：参考文档 / 原始资料（dev.mysql.com，文档）
摘要 B+Tree类索引以页为单位组织有序键，范围访问、回表和页分裂共同影响读写成本。

边界说明：本课中出现的「内容后台」「付费订单」「某用户已支付且落在时间窗口内的订单」等场景都是教学假设，用来让概念落地，不代表腾讯/微信或任何企业的内部实现。配套代码是 Python 3 标准库加 sqlite3 写的教学模型：一棵按页组织的 B+Tree，加上用 sqlite3 的 EXPLAIN QUERY PLAN 做访问路径对照。它不是 InnoDB，也不是 MySQL 优化器；页容量被刻意设成 16 个键，是为了让页分裂和填充率在两千行数据里就能看清。本课出现的扫描行数、页读写和耗时只来自这次教学实验，不能当成生产 MySQL 的性能数据。InnoDB 的页大小、填充策略和物理结构以 MySQL 8.4 官方文档为准（本文已核对 The Physical Structure of an InnoDB Index，访问日期 2026-11-11）。

导读

一个直觉：图书馆的书和卡片目录

图书馆里的书按索书号排在书架上。索书号连续的书挨在一起，同一层书架（一「页」）上能放的本数有限。这就是聚簇主键：数据本身就按主键顺序躺在叶子页里，按订单号点查或按订单号范围扫，走的是这棵树。

前台还摆着一套卡片目录，按「作者 → 书名 → 出版年」排。卡片上写着索书号。你要找「某位作者、某一本书、某一年」时，顺着这套目录的最左前缀就能翻到那一小叠卡片。如果目录的第一项是作者，你却只记得出版年，卡片无法从中间插入，只能从头翻到尾。这就是联合索引的左前缀。

卡片上如果已经写了你要的全部信息（比如册数、是否在馆），你不用再跑去书架，这叫覆盖索引。卡片上只有索书号、你还想看内容简介时，必须拿着索书号再走一趟书架，这叫回表。每多做一套目录，每进一本新书都要多写一张卡片，满了的抽屉还要拆成两个——索引能让查询少翻很多页，但会把写入和存储放大。

「目录里能查到」不等于「查得快」。一整面抽屉都是「已支付」这种低选择性标签时，即使用了这套目录，你仍然要翻掉其中的一半卡片。

接上前置

  • a-tree：搜索树为什么能按对数层数定位，有序键为什么适合范围扫描。本课把它落到「以页为单位的 B+Tree」：内部页只放分界键和子页编号，真正的记录在叶子，叶子之间有顺序指针。
  • g-mysql：SQL 怎样经过连接和会话到达服务器。本课不再讨论连接池和绑定参数，而是问：这条 SELECT 到达存储引擎之后，沿哪条访问路径读数据，要读多少页、回不回表、写入时要维护几棵树。

前面单独看都学过：树能查找，SQL 能发出去。本课把它们组装成「为订单查询选择联合索引」，然后看组装之后才出现的问题：列顺序错了，EXPLAIN 仍然显示用了索引，扫描行数却差两个数量级；索引里缺一个要返回的列，每一行都要回表；给低选择性列和每条经常更新的列都建索引，查询看似「有索引」，写入却被写放大拖住。

一次索引查询的生命周期

  SQL
    WHERE user_id=? AND status=? AND created_at BETWEEN ? AND ?
    SELECT order_id, ...
        │
        ▼
  选计划（教学模型里的 plan_safe / plan_naive）
        ① 看每棵二级索引能不能用上最左前缀
        ② 等值条件可以从左往右连续使用，遇到第一个范围条件后停止
        ③ 需要的列是否都在这棵索引里？能则覆盖，否则回表
        │
        ▼
  沿 B+Tree 下行
        ④ 从根页走到目标叶子（内部页只比较分界键）
        ⑤ 在叶子上按 [start, end] 顺序扫描，不够就沿 next_leaf 走下一页
        ⑥ 用剩余谓词过滤（没用进前缀的条件在这里做）
        ⑦ 非覆盖：取出主键，再走一遍聚簇索引（回表）
        │
        ▼
  返回行，并留下计数：rows_examined、pages_read、bookmark_lookups

正常路径看起来只是「走索引」。本课真正要讲的是：第 ① 步如果把「索引里出现过这个列」当成「能用这个索引」，就会从错误的一侧走进树；第 ③ 步如果永远回表，覆盖索引的收益会全部消失；第 ⑤ 步如果范围很大或选择性很低，即使用了索引，examined 仍然接近全表。

教学场景（教学假设）

内容后台的订单服务要支撑这类查询：某用户、已支付、落在某个时间窗口里的订单。灰度期间出现了三件「看起来用了索引」的事：

  1. 有人建了 (created_at, user_id, status)，EXPLAIN 里确实是 SEARCH ... USING INDEX，但扫描行数是正确联合索引的大约 96 倍；
  2. 查某用户某状态下的 amount 时，索引里没有金额，每一行都拿主键回表；即使后来把 amount 加进了索引，naive 路径仍然每次回表；
  3. 只按 status = 'paid' 查，计划里写着 USING COVERING INDEX，实际却是一次整索引扫描；同时表上还挂了三个二级索引，两千行插入的写页数大约是只保留主键时的 4 倍。

实践里这三件事都复现了，而且查询结果是对的。结果对、计划里出现了 INDEX，都不等于访问路径是便宜的。

本课三条主线

  1. 多列索引与左前缀：联合索引的列顺序决定能用多长的前缀，范围条件会截断后面的列；
  2. 覆盖索引和回表：二级索引的叶子默认带主键，要的列都在索引里就可以不回聚簇索引；
  3. 选择性、页分裂与写放大：低选择性索引即使用上了也扫很多行；页满了要分裂；每多一棵二级树，插入都要多写。

三条主线对应三个很容易分开学、合在一起才出问题的点。只会背「最左前缀」但不看执行计划，可能把 (created_at, user_id, status) 当成「三个列都有了」；只会建覆盖索引但执行时仍然回表，页数优势出不来；只记得「要建索引」却不看选择性和写入成本，会得到一张读得一般、写得很痛的表。下面按这个顺序展开。

学习目标

学完本课，你应该能够：

  1. 能解释多列索引与左前缀（goals 原文）；
  2. 能独立完成：为订单查询设计联合索引，用 EXPLAIN 比较扫描行数与写入成本。（goals 原文）；
  3. 面对 (user_id, status, created_at)，说出哪些 WHERE 能 SEARCH 进这棵树，哪些只能 SCAN 或只用到部分前缀；
  4. 分清覆盖索引和回表：同样 20 行命中，为什么非覆盖路径会多出 20 次回表、页数从 5 变成 66；
  5. 解释「使用索引不代表查询必然高效」：同样是 USING INDEX，按 status 走低选择性索引要扫 1000 行，按 user_id 只需 20 行；
  6. 报告查询收益的同时报告额外存储和写放大：本课里三个二级索引把总页数从 149 升到 829，把插入写页数从 2292 升到 9632。

为什么后端要懂

节点的 why 原文是：「从执行计划理解慢查询而非只给所有列加索引。」拆开看，至少有两层。

正确的路径，而不只是正确的结果。 后台几乎每天都要写「按用户 + 状态 + 时间窗口」这类列表查询。结果集对，只说明谓词最终被应用了；真正决定延迟和负载的是途中读了多少页、回了多少次表。实践里同一条 Q1（user_id=42 AND status='paid' AND created_at BETWEEN 10000 AND 15000），正确前缀扫描 4 行、4 页就得到 4 条命中；把列顺序做成 (created_at, user_id, status) 之后，仍然能搜到同一 4 行，但 examined 变成 384，页数变成 28。如果只看「有没有索引」「结果对不对」，这两种计划会被当成同一件事。

写入和存储是查询收益的账单。 每加一条二级索引，插入、更新、删除都要维护另一棵 B+Tree，页满了还要分裂。本课在 2000 行订单上，只保留聚簇主键时写了 2292 页、分裂 146 次、共 149 页；加上一条联合索引后写页 4720、总页 366；三条二级索引后写页 9632、总页 829。查询快了一截，账单写在写入路径和磁盘占用上。入职后做慢查询优化，报告里必须同时出现「扫描少了多少」和「多占了多少、写入多了多少」，这正是本节点的验收标准。

把「单独看都像对的、合在一起才贵」的情况列成表，入职后可以当排查清单用：

失败情况 谁先发现 若处理不当会怎样 本次实践中的对照
联合索引列顺序与查询不符 EXPLAIN 仍可能显示 SEARCH / USING INDEX 结果对，但扫描行数差一到两个数量级 正确前缀 examined=4；错序 examined=384
只记住「索引里有这个列」 按非前导列查询时 无法二分定位，只能扫叶子链 status 单独查询：safe 走聚簇 SCAN，examined=2000
需要的列不在二级索引里 每行一次回表的页读 命中行一多，回表变成随机点查 20 行金额查询：回表 20 次、66 页；覆盖 0 次、5 页

入职后你多半直接用公司现成的表结构和 EXPLAIN，但出问题时要知道往哪查：

  • 「这条查询有索引还是慢」，先看执行计划用了哪个索引、用了多长前缀、是 SEARCH 还是 SCAN，再看扫描行数是不是接近命中行数；
  • 「选了几个列却几乎没过滤」，先看范围条件是不是截断了后面的列，或查询根本没碰到最左列；
  • 「索引已经包含返回列，为什么仍然很慢」，先看是不是在回表，以及执行层有没有忽略覆盖；
  • 「读写都变慢、磁盘涨得快」，先数二级索引的数量，并看插入是否在随机位置分裂。

核心知识点

1. 多列索引与左前缀

联合索引不是「这几列各建一条索引再 OR 起来」，而是把多列拼成一个复合键，按字典序排进同一棵 B+Tree。键 (user_id, status, created_at, order_id) 的比较是先比 user_id，相等再比 status，再比 created_at，最后用主键打散相同组合。于是：

  • user_id=42 AND status='paid' AND created_at BETWEEN 10000 AND 15000 对应树上一段连续区间，可以从根页一路落到起点叶子，再沿 next_leaf 扫到终点；
  • 只有 user_id=42 时，仍然是一段连续区间（该用户所有状态、所有时间），前缀长度为 1；
  • 只有 status='paid' 时，'paid' 散落在每个 user_id 段里，这段索引上不存在一个可以二分进去的连续区间。

等值条件可以从左往右连续使用；遇到第一个范围条件之后，后面的列不能再用来划定区间，只能当剩余谓词做过滤。所以 (user_id, status, created_at) 很适合「先定位用户和状态，再在时间上做范围」。如果把顺序改成 (created_at, user_id, status)，同一条 Q1 只能用上 created_at 这一段范围，user_id 和 status 变成在大段叶子里做过滤。

实践里 2000 行订单、100 个用户，Q1 的命中是 4 行。两种联合索引、两种计划给出的访问路径如下（教学模型自己的 EXPLAIN 文本）：

计划 索引列顺序 用上的前缀 剩余谓词 examined 页数 命中
safe (user_id, status, created_at) user_id, status, created_at 无 4 4 4
错序但规划正确 (created_at, user_id, status) 只有 created_at user_id, status 384 28 4
naive（错序 + 强制回表） 同上 created_at user_id, status 412 40 4

四行结果完全一致（ids_match=True）。差别全部在路上：正确前缀几乎只碰命中行；错序索引把时间窗口里的 384 行都翻了一遍，再扔掉不符合用户和状态的那些。naive 路径还要为过滤后的行回表，examined 和页数再高一截。

同一棵正确的 (user_id, status, created_at) 上，另外两条查询把「前缀用不满」说得更清楚：

查询 用上的前缀 examined 命中 含义
status='paid'（safe） 无，走聚簇 SCAN 2000 1000 最左列不在谓词里，不能进这棵二级树
user_id=42 AND created_at BETWEEN ...（中间有洞） 只有 user_id 20 4 范围落到了被跳过的 status 之后，只能扫该用户全部 20 行再过滤时间

「中间有洞」是左前缀里很常见的坑：你以为 user_id 和 created_at 都在索引里，就一定能在时间上做范围，其实 status 挡在中间，时间条件只能当 residual。

sqlite3 用同一份 2000 行数据和同一条 Q1，EXPLAIN QUERY PLAN 给出了同一件事情的另一张口吻（这是 sqlite 的计划，不是 MySQL 的 EXPLAIN）：

无索引：          SCAN orders
错序 idx_wrong：  SEARCH orders USING INDEX idx_wrong (created_at>? AND created_at<?)
正确 idx_safe：   SEARCH orders USING INDEX idx_safe (user_id=? AND status=? AND created_at>? AND created_at<?)
只查 status：     SCAN orders USING COVERING INDEX idx_safe

注意后两行都出现了 INDEX，但一个是带完整前缀的 SEARCH，一个是 SCAN。USING COVERING INDEX 在这里只表示 sqlite 可以只读索引、不必回表，并不表示它按 status 做了一次点查。使用索引、覆盖索引、高效，是三件不同的事。

用一条规则来记列顺序：把等值条件放在左边，把范围条件放在等值之后，把只为覆盖而追加的列放在最后。 本课 Q1 的自然顺序就是 (user_id, status, created_at)；若还想覆盖 amount，写成 (user_id, status, created_at, amount)，不要把 amount 插到时间前面。

2. 覆盖索引和回表

InnoDB 一类的存储里，表的主数据就在主键 B+Tree 的叶子上，这叫聚簇。二级索引的叶子不存放完整行，而是「索引键 + 主键」。教学模型沿用这个结构：创建二级索引时，如果定义里没有 order_id，会自动把它追加到键尾，既保证键唯一，也让 SELECT order_id 有机会被覆盖。

于是一次二级索引查询有两条出口：

  • 覆盖：计划需要的列都能从二级叶子上取到（键里的列、附带的包含列、主键），不再访问聚簇树；
  • 回表：拿出主键，再对聚簇树做一次点查。命中行有多少，就多多少次随机点查。

实践里查「某用户、已支付」的 order_id 和 amount，命中 20 行：

路径 索引 回表次数 examined 页数 耗时（教学模型）
safe 覆盖 (user_id, status, amount) 0 20 5 0.030 ms
safe 非覆盖 (user_id, status) 20 165 66 0.099 ms
naive（即使索引已覆盖仍回表） (user_id, status, amount) 20 165 65 0.069 ms

非覆盖路径的 examined 是 165 而不是 20，是因为 20 次回表会在聚簇叶子上继续比较键，这些比较也被计进了 rows_examined。页数从 5 跳到 66，才是回表真正贵的地方：二级叶子是一段连续扫描，聚簇点查则可能落到 20 个不同的主键页上。

naive 路径的对照很刻意：索引已经包含 amount，计划却仍然「ALWAYS 回表」。结果一样对，页数几乎和不覆盖时一样。这说明覆盖不是「把列写进 CREATE INDEX 就自动生效」，执行时还必须真的从索引叶子取列。生产里要在执行计划中确认这一点——sqlite 的说法是 USING COVERING INDEX；MySQL 8.4 里对应的是 Extra 中出现 Using index（以你实际看到的 EXPLAIN 文本为准，本课没有连真实 MySQL）。

sqlite 对同一条「按用户和状态取 amount」的对照是：

未覆盖（只有 idx_safe）：SEARCH orders USING INDEX idx_safe (user_id=? AND status=?)
已覆盖（idx_cover）：    SEARCH orders USING COVERING INDEX idx_cover (user_id=? AND status=?)

前面多一个 COVERING，就是少一次回表。为了覆盖而追加的列要放在联合索引的右边，以免破坏左边的前缀。

3. 选择性、页分裂与写放大

选择性。 一个谓词值如果对应表里很大一部分行，即使用索引定位到了这个值，你也得把这些行逐个读出来。2000 行里 paid 有 1000 行（一半），每个用户只有 20 行。同样是 COVERING SEARCH：

索引 查询 examined 命中 页数
(status) status='paid' 1000 1000 128
(user_id) user_id=42 20 20 6

两条计划都「用了索引」，扫描量差 50 倍。给 status 单独建索引，对「列出所有已支付订单」这类查询几乎就是一次半表扫描；它解决不了 Q1，反而让每次插入多维护一棵树。选择性要看的是「这个条件能把行数收到多小」，不是「这一列有没有索引」。

页分裂与填充率。 B+Tree 以页为单位。教学模型每页最多 16 个键，叶子满了就要分裂成两页，并可能把一个分界键推到父页——父页满了再裂，一直裂到根，树就长高。分裂怎么切，决定页有多满。

官方文档对 InnoDB 聚簇索引的描述是（8.4，访问日期 2026-11-11）：插入时会尝试给页留出 1/16 的空闲；按顺序插入时页大约 15/16 满，随机插入时页的满度在 1/2 到 15/16 之间。默认页大小是 16KB，在实例初始化时由 innodb_page_size 决定。本课没有实现 16KB 页，但用两种分裂策略模拟「满度」这件事：

  • naive：一律对半切。顺序插入主键时，左边那一页再也接不到新行，叶子填充率最后只有 0.502，2000 行占了 249 个叶子、树高 4、共 280 页，分裂 276 次；
  • safe：如果这次插入落在最右叶子（顺序追加），按 15/16 做右偏切，左边几乎是满的。同样 2000 行主键，填充率 0.9328，叶子 134，树高 3，共 149 页，分裂 146 次。
def _split_point(self, nkeys: int, right_biased: bool) -> int:
    if right_biased and self.split_mode == "safe":
        # 顺序插入时让左页接近 15/16 满，对应文档里 sequential 的填充
        return min(nkeys - 1, (MAX_KEYS * 15) // 16)
    return nkeys // 2

填充率差一倍，不是微优化：同样的 2000 行，对半切多占一个树高、将近一倍叶子页。随机写入的二级索引（如按 user_id）做不到这种右偏，满度会更接近文档说的「一半到 15/16」。InnoDB 在重建索引时还有 sorted index build 和 innodb_fill_factor；页的填充率掉到 MERGE_THRESHOLD（默认 50%）以下时，会尝试合并以回收页。这些是生产引擎的细节，教学模型没有做合并，只把「分裂策略影响占用」跑了出来。

写放大。 每条二级索引都是一棵要与聚簇树一起维护的 B+Tree。一次 INSERT 要写主键叶子，还要往每一棵二级树里插一把键；任何一页满了都会多一次分裂写。2000 行、safe 分裂下的账单：

表上的二级索引 写页数 分裂次数 二级索引页 总页数
无（只有主键） 2292 146 0 149
1 条 (user_id, status, created_at) 4720 360 217 366
3 条（再加上 status、amount） 9632 816 680 829

从 0 条到 3 条，写页数大约变成 4.2 倍（2292 → 9632），总页数大约变成 5.6 倍（149 → 829）。第三条里那条 (status) 对 Q1 几乎没有帮助，却把写入和存储一起推高——这就是「给所有列加索引」的典型账单。

如果更新的是索引列本身（比如把订单从 pending 改成 paid），二级树里往往是先删旧键再插新键，写放大比一次插入更明显。本课没有单独测更新，但机制是同一套：多一棵树，就多一次删除和一次插入，并且都可能分裂。

三条主线的收束

列顺序决定你在树上能跳到多准的一段叶子；覆盖决定这段叶子够不够用，要不要再付一次回表；选择性和分裂策略决定这段叶子本身有多长、这棵树平时有多贵。三者分开都好讲，合在一张订单表上才会同时出现「EXPLAIN 里有 INDEX、结果也对、系统却又慢又占空间」。

常见误区

节点 pitfalls 原文是：「使用索引不代表查询必然高效。」它可以拆成下面几句具体的话。

EXPLAIN 里出现 INDEX，不表示前缀用对了。 sqlite 对错序索引给出的是 SEARCH orders USING INDEX idx_wrong (created_at>? AND created_at<?)，看起来和正确计划一样「用了索引」。真正的差别在括号里：错序只用上了时间范围，教学模型里因此扫了 384 行。只看「有没有 USING INDEX」会把这两种计划当成一类。

覆盖扫描也可以很贵。 只按 status 查询时，sqlite 给出 SCAN orders USING COVERING INDEX idx_safe。它确实没回表，也确实在用索引，但它是整条叶子链扫过去。教学模型的 safe 路径选择不走这棵以 user_id 开头的树，而是聚簇 SCAN，examined=2000；naive 路径坚持「索引里有 status」，扫二级叶子再回表，examined 飙到 9970。两种「跟索引有关」的计划都不高效。

列都在索引里，不等于范围都能用上。 (user_id, status, created_at) 对 user_id + created_at 这种「中间有洞」的条件，只能用 user_id 前缀，该用户的 20 行都要看，时间条件是 residual。不要看见列名出现在索引定义里就认为它们会一起参与定位。

结果集对，不能证明路径便宜。 上面所有对照的命中行都一致。慢查询分析要看 examined、页数和是否回表，而不是只看返回值。

把索引加满不会自动变快，但会自动变贵。 低选择性的 (status)、很少被当作前缀的单列索引，写入成本是确定的，查询收益可能接近零。

设计权衡

节点 tradeoffs 原文是：「索引提高读取能力，也增加写放大和维护开销。」实践把这句话落到了可以并列填写的两列数字上。

为哪条查询付钱。 Q1 是「某用户 + 某状态 + 时间窗口」，(user_id, status, created_at) 把 examined 从错序的 384 收到 4，这是值得付的一棵树：多 217 个索引页、写页从 2292 升到 4720。再为 status、amount 各加一条单列索引，总页数到 829、写页到 9632，对 Q1 几乎没有额外帮助。索引要按查询的前缀来设计，而不是按列的出现次数来堆。

覆盖还是更窄的索引。 把 amount 追加进联合索引，20 行查询的回表从 20 降到 0、页数从 66 降到 5。代价是索引叶子更宽，同样一页放更少的键，范围扫描可能多读几页，写入也要多维护这个列。如果 amount 经常被改，更新路径还会多一次删键再插键。覆盖值得做，但是加在「已经对上前缀」的那棵树上，而不是另起一棵很宽、却对不上查询的树。

顺序键和随机键。 主键若按订单号顺序追加，右偏分裂能让叶子接近 15/16 满（本课 0.9328）；二级索引的键（用户、状态）更接近随机插入，分裂更碎，占用更接近「一半到 15/16」。把随机性很大、选择性又低的列放在联合索引最左，既不利于查询，也容易让这棵树更「胖」。

用执行计划做取舍，而不是用感觉。 验收要求「能解释索引列顺序」，并且「报告同时包含查询收益和额外存储」。一份负责任的变更说明至少要有：目标查询的计划（前缀、是否覆盖）、扫描行数的前后对比、新增索引的页数或体积、插入路径的写放大。本课的数字来自教学模型，生产上要换成你在目标 MySQL 版本上实际跑出的 EXPLAIN 和统计，但报告的结构可以一样。

教学模型的硬边界再强调一次：每页最多 16 个键；pages_written 按「一次插入里被改过的页数」累计，不是 InnoDB 的 redo 或 flush 统计；计划器是我们写的规则，不是 MySQL 优化器。sqlite 部分只负责 EXPLAIN QUERY PLAN 文本和结果一致性。

步骤 1：准备数据与目标查询

generate_orders() 固定生成 2000 行订单：100 个用户循环分配，status 大约一半为 paid（1000 行），created_at 落在 1000–29000，金额是一个确定的线性公式。目标查询 Q1 是：

user_id = 42 AND status = 'paid' AND created_at BETWEEN 10000 AND 15000

在这份数据上命中恰好 4 行。先不要建索引去「调」这个数字，它应当由数据生成函数决定；测试里用同一套生成函数做 gold，再要求各条计划的命中 id 完全一致。

步骤 2：两条执行路径

OrderTable.plan_safe 从聚簇主键和所有二级索引里挑访问路径：从左统计能用上的等值前缀，最多再收一个范围列，其余谓词当 residual；需要的列都在索引里则标记 COVERING，否则回表。评分按「前缀更长、能覆盖、键更短」的顺序。

OrderTable.plan_naive 的两个刻意错误是：

  1. 只要索引列集合与谓词有交集，就「用这棵树」，即使最左列根本不在谓词里——这时它会 SCAN 整条叶子链；
  2. 无论索引是否已经覆盖，都 ALWAYS 回表。

对照时不要改查询结果的计算方式：两条路径都必须用完整谓词过滤，保证结果与 gold 一致，差异只出现在 examined、页数和回表次数上。

步骤 2.1：左前缀在代码里怎么判断

plan_safe 对每个索引从左往右走一遍列，等值就纳入前缀，碰到第一个范围列后停止，后面即使出现在索引定义里也不再用来划区间：

used, saw_range = [], False
for c in columns:
    if c in equals and not saw_range:
        used.append(c)
        continue
    if c in ranges and not saw_range:
        used.append(c)
        saw_range = True
        continue
    break

所以 (user_id, status, created_at) 面对 Q1 时 used 是三列；面对 user_id + created_at 时，status 不在谓词里，循环在第二列 break，created_at 只能当 residual。plan_naive 不走这套规则，只要索引列和谓词有交集就开扫。

范围扫描本身在 btree.py 的 range_scan：先从根下行到 lo 所在叶子，再沿 next_leaf 顺序吐出 lo <= key <= hi 的记录。页在这次下行和沿链前进时计入 pages_read，落入区间的每一行计入 rows_examined。回表则是另一次对聚簇树的 search。

源码与文档阅读

节点指定的资料是 MySQL 8.4 参考手册 17.6.2.2 The Physical Structure of an InnoDB Index（dev.mysql.com，英文文档，访问日期 2026-11-11）。节点在资源说明里希望重点核对「多列索引与左前缀」和「覆盖索引和回表」，但这篇正文本身主要讲的是页的物理形态和填充，并没有展开左前缀或回表。阅读时按页面上实际出现的内容来，不要把本课其他章节的结论当成这篇文档里的原句。

这篇文档里与本课直接对应、且已核对过的要点：

  1. 除空间索引外，InnoDB 索引是 B-tree，记录存在叶子页。 空间索引用 R-tree。文档用的是 “B-tree” 这个词；本课标题沿用节点的 「B+Tree」，指的是「记录在叶子、叶子可顺序穿起来」这一类结构。不要在笔记里写成「官方文档称其为 B+Tree」，那不是该页的用词。
  2. 默认页大小 16KB，由实例初始化时的 innodb_page_size 决定，不是会话级可以随便改的参数。本课用 16 个键模拟「一页会满」，没有模拟 16KB。
  3. 插入聚簇索引时会尝试留出 1/16 空闲。 顺序（升序或降序）插入后，页大约 15/16 满；随机插入时，页的满度在 1/2 到 15/16 之间。这是对照 5 里两种分裂策略的文档依据。教学模型的 0.9328 和 0.502 是我们自己那套 16 键页上的填充率，方向与文档一致，数值不能当成 InnoDB 的实测。
  4. 重建或创建 B-tree 索引时走 sorted index build，innodb_fill_factor 控制构建时每页填到百分之多少，余量留给后续增长；该值为 100 时，聚簇索引页仍会留出 1/16。空间索引不支持这种构建方式。
  5. 页填充率低于 MERGE_THRESHOLD（未指定时默认 50%）时，InnoDB 会尝试收缩树以回收页。 教学模型没有实现合并，所以你只会在实验里看到分裂让树变大，看不到删除之后的回收。

建议的阅读方法：先只读这一页，用自己的话写下「页多大、顺序插入和随机插入的满度、什么时候合并」。然后再回到本课实践，看哪一组数字在模拟其中哪一条，哪一组（左前缀、回表）需要另找手册章节或用 EXPLAIN 验证。记录：文档版本 8.4、访问日期 2026-11-11、实际打开的 URL、你亲自跑过的 ./test.sh 输出。

边界：教学实验只模拟语义和计数，不代表 InnoDB 的页内记录格式、change buffer、缓冲池刷新和优化器代价模型。

题 1：订单查询是 WHERE user_id=? AND status=? AND created_at BETWEEN ? AND ?。为什么 (user_id, status, created_at) 和 (created_at, user_id, status) 都能返回同一 4 行，但扫描行数差了近两个数量级？只按 status=? 查时，为什么即使用了覆盖索引也不高效？

题 2：查「某用户已支付订单的金额」命中 20 行。为什么非覆盖索引会读 66 页、回表 20 次，而把 amount 加进索引后只需 5 页、回表 0 次？如果执行层忽略覆盖，会怎样？把 amount 插到 (user_id, amount, status) 这种位置有什么风险？

答案 - 二级索引叶子默认是「索引键 + 主键」。要 `amount` 但不在索引里时，必须拿 `order_id` 再走聚簇点查。20 次点查可能落在许多不同主键页上，所以 pages=66、lookups=20、examined=165（回表过程中的键比较也被计入）。 - 索引变成 `(user_id, status, amount)` 后，需要的列都在叶子上，COVERING，lookups=0、pages=5、examined=20。sqlite 文本从 `USING INDEX idx_safe` 变成 `USING COVERING INDEX idx_cover`。 - naive 路径在已经覆盖的树上仍然 ALWAYS 回表，lookups=20、pages=65，和没有覆盖几乎一样。覆盖必须在执行时生效，不能只看 `CREATE INDEX` 语句。 - 为覆盖追加的列应放在前缀右边。若把 `amount` 插到 `status` 前面，等值前缀在 `amount` 处被截断，`status` 可能变成 residual，Q1 这类查询会退化。覆盖是附加能力，不能破坏左前缀。

题 3：为什么「给所有列加索引」不能当默认策略？请用本次实验的写入和存储数字，以及选择性对照，说明一份合格报告应该同时包含哪些内容。顺序插入时，对半分裂和 15/16 右偏分裂对占用有什么影响？这和官方文档哪句话对应？

答案 - 每条二级索引都是一棵要一起维护的 B+Tree。2000 行订单上，只保留主键：写页 2292、总页 149；加一条 Q1 需要的联合索引：写页 4720、总页 366（索引页 217）；再加 `(status)` 和 `(amount)` 两条：写页 9632、总页 829（索引页 680）。查询收益如果写的是 Q1 的 384 → 4，账单就必须把 149 → 366 或 829 一并写上。 - `(status)` 对 `paid` 是 COVERING SEARCH，但 examined=1000（半张表）；`(user_id)` 查一个用户只需 20 行。低选择性索引「用上了」也不便宜，却确定地增加写放大。 - 合格报告至少包括：目标查询的列顺序和计划（前缀、是否覆盖）、扫描行数/回表的前后对比、新增索引带来的页数或体积、写入路径的放大。这就是验收标准里的「查询收益和额外存储」。 - 对半切后主键叶子填充率 0.502、249 个叶子、树高 4；右偏 15/16 切填充率 0.9328、134 个叶子、树高 3。对应 8.4 文档：顺序插入时页大约 15/16 满，随机插入在 1/2 到 15/16 之间。教学模型的数值不能直接当成 InnoDB 的实测，但方向是同一句话。

本课小结

  • B+Tree 类索引以页为单位组织有序键，范围访问、回表和页分裂共同影响读写成本。
  • 多列索引与左前缀：等值条件从左连续使用，范围条件截断后面的列。实践中同一条 Q1，正确顺序 examined=4，错序 examined=384，结果却是同一 4 行。
  • 覆盖索引和回表：二级叶子带主键，要的列都在索引里就可以不回聚簇树。20 行金额查询，非覆盖回表 20 次、66 页，覆盖 0 次、5 页；执行时若仍强制回表，覆盖收益会全部消失。
  • 选择性、页分裂与写放大：status='paid' 即使用索引也要扫 1000 行，按 user_id 只需 20 行。顺序插入用 15/16 右偏分裂时填充率 0.9328、134 个叶子；对半切只有 0.502、249 个叶子。三条二级索引把写页 2292 推到 9632，总页 149 推到 829。
  • 验收：能解释索引列顺序；报告同时包含查询收益和额外存储。实践中 Q1 的 384 → 4 必须和 149 → 366（或 829）写在同一份报告里。
  • 误区：使用索引不代表查询必然高效。USING INDEX 可能只是一次大范围 SEARCH，甚至是一次 COVERING SCAN。
  • 权衡：索引提高读取能力，也增加写放大和维护开销。先为真正的查询前缀付钱，再谨慎决定要不要为覆盖加列，不要给低选择性列默认各建一条。

学完后可以用三句话自检：这条查询在联合索引上用了多长的最左前缀，范围条件有没有截断后面的列；要的列能不能在二级叶子上取完，还是每行都在回表；新增的索引让扫描少了多少，又让页数和写入多了多少。三句都能答上来，并且能指出 practice98 里对应的那组数字，这一课就算过关。

如果有一句答不上来，先回到对应的实验表，再回到文档里关于页和填充率的那几句，不要只把结论背下来。
