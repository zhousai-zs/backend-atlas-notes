边界说明

本课讨论通用的服务发现机制与工程权衡。文中出现的内容后台、图文发布服务、存储服务、扩缩容与滚动发布等场景，均为便于理解而设定的教学假设，不表示任何具体公司的内部实现。

涉及 gRPC resolver、Consul、etcd、Kubernetes 等框架或系统的具体行为时，请以你所读文档的对应版本为准。不同版本在 API 形态、缓存策略、重试与错误语义上可能不同，本课只讨论稳定的概念与边界，不替任何版本书写细节。

导读

一个直觉：骑手手里的通讯录

想象你点了一份外卖。骑手手里有一本通讯录，上面写着商家的地址。第一天商家在 A 街 3 号，骑手顺利取餐；第二天商家搬到了 B 街 8 号，通讯录却没更新，骑手仍按旧地址走，结果扑空。又比如商家临时关门，通讯录上却还写着“营业中”，骑手到了也只能干等。

骑手需要的不是“一个永远正确的地址”，而是一套能跟上变化的机制：地址变了要有人通知，通知有延迟时要能及时发现，实在找不到时要有明确的兜底动作。服务发现面对的是同一类问题。

调用方手里拿着的往往不是“服务名字”，而是一份“地址清单”。这份清单会过期、会变长变短，甚至暂时为空。系统是否可靠，很大程度上取决于调用方如何处理这份不断变化的通讯录。

接上前置：连接池里连的是“地址”

前置节点 d-pool 讲的是连接池：复用长连接可以省掉握手成本，提升吞吐，也能控制并发连接数。但连接池复用的对象，本质上是“到某个地址的连接”。一旦后端实例扩缩容、故障迁移或滚动发布，地址集合就变了：

  • 新实例上线：池里没有它的连接，流量分不过去，扩容在调用方看来像没生效。
  • 老实例下线：池里还留着指向它的连接，继续复用就会失败；如果池子只做“取出即用”，故障会直接透传给业务。
  • 实例被重新调度：旧连接可能看起来还“活着”，实际早已不可用，成为僵尸连接。
  • 地址批量替换：如果一看到更新就清空整个池子，会误伤仍然健康的连接，造成瞬时抖动。

所以连接池解决的是“连接复用”，服务发现解决的是“地址从哪来、什么时候该换”。两者必须配合：池子越稳，越需要发现机制及时告诉它哪些地址该退出、哪些地址可以加入，否则稳定的池子反而会把流量锁死在陈旧地址上。

先把三个词摆清楚

为了避免后面混淆，先约定三个词的用法：

  • 逻辑服务：调用方眼里的稳定名字，例如“存储服务”。它不随实例增减而变化。
  • 端点：一次可连接的实例地址，通常是 host:port。端点会随扩缩容和调度变化。
  • 地址列表：某个时刻逻辑服务对应的端点集合。它是快照，会过期，也可能为空。

服务发现做的，就是在“逻辑服务”和“地址列表”之间建立一条可持续更新的映射关系；负载均衡则决定如何把请求分配到列表中的端点。两者常常一起出现，但职责不同。

教学时间线：一次扩容引发的调用失败

下面是一个教学假设的时间线，用来把问题串起来（场景为虚构，仅用于说明机制）：

  1. 图文发布服务通过服务名调用存储服务，客户端缓存了一份地址列表，其中有 3 个实例。
  2. 存储服务扩容，新增 2 个实例，注册中心里的端点变成 5 个。
  3. 调用方尚未刷新缓存，仍按 3 个旧实例发请求，新实例分不到流量，扩容效果被浪费。
  4. 随后旧实例中的 1 个被缩容下线，但调用方缓存里还留着它。
  5. 调用方继续向这个已下线地址发起连接，出现连接拒绝或超时。
  6. 如果此时把超时当成业务错误重试，重试又会打到同样的陈旧地址，故障被放大。
  7. 运维看到的是“存储服务不稳定”，而真实原因是“调用方地址视图落后”。

这条时间线说明：地址变化本身不是故障，真正的故障是“调用方对地址变化的反应不够快、不够稳”。服务发现的价值，不是让地址不变，而是让变化被可控地吸收。

错误做法与正确做法对照

场景 错误做法 正确做法
获取地址 把 IP 和端口写死在配置文件或代码里 通过服务名解析端点，把地址当作可变的运行时数据
缓存地址 启动时拉一次，之后永不更新 订阅变更或定期重新解析，并设置合理的缓存与过期策略
遇到空列表 直接 panic、空指针或无限重试 明确失败并快速返回，或按既定策略受控降级
地址更新 清空并重建整个客户端/连接池 增量替换端点，保留仍在使用且未失效的对象
实例摘除 只改注册中心，调用方无感知 让更新传播到调用方，并对旧连接做优雅处理
健康判断 注册成功即视为可服务 区分“已注册”与“业务已就绪”，必要时做健康检查
解析失败 把解析错误当成业务错误吞掉 区分解析失败与业务失败，给出可观测的错误路径
重试策略 对陈旧地址做无差别重试 先刷新地址视图，再在有限预算内重试

本课三条主线

  • 客户端与代理发现：地址解析放在调用方进程内，还是交给独立的代理/负载均衡层？前者减少跳数、贴近调用方，后者把治理逻辑集中起来，但多了一跳，升级与运维方式也不同。
  • watch、TTL 和缓存：调用方如何知道地址变了？靠订阅推送（watch）、靠 TTL 过期，还是定期轮询？缓存能降低解析压力，但也带来“看到旧数据”的窗口，三者需要配合。
  • 健康、摘除与恢复：实例什么时候算可用？下线时如何从端点列表里摘除？故障恢复后如何重新纳入流量？这三件事决定了系统在抖动中的表现，也决定了“注册成功”与“真正可服务”之间的差距。

学习目标

学完本课，你应当能够：

  1. 用自己的话解释“服务发现把逻辑服务映射为动态端点”这句话的含义。
  2. 能解释客户端发现与代理发现两种方式的差异，并说出各自的取舍。
  3. 说明 watch、TTL 与缓存三者在“地址更新传播”中的分工与边界。
  4. 描述实例健康、摘除与恢复的完整生命周期，以及常见误区。
  5. 能独立完成：实现本地服务目录并动态增删实例，观察旧连接处理与恢复。
  6. 在空端点场景下，能设计明确的失败路径或受控降级方案，而不是让进程崩溃或无限重试。
  7. 能识别“注册成功不等于业务就绪”这类隐蔽问题，并在设计中留出就绪判断的位置。
  8. 面对地址更新时，能说明为什么不应销毁正在使用的对象，以及增量更新的基本思路。

  • 能独立完成：实现本地服务目录并动态增删实例，观察旧连接处理与恢复。

为什么后端要懂

节点 why 原文：避免实例扩缩容或故障后仍调用陈旧地址。

这句话听起来像常识，但它背后是一整类线上问题的总称。后端服务几乎不可能长期跑在一组固定不变的机器上，地址变化是常态，而不是异常。理解服务发现，本质上是在理解“分布式系统里，调用方如何与不断变化的基础设施保持同步”。

地址变化从哪里来

  • 扩缩容：流量高峰时增加实例，低谷时减少实例。端点集合可能在几分钟甚至几十秒内变化。
  • 故障迁移：某台机器或某个实例不可用，调度系统把工作负载迁到别处，地址随之改变。
  • 滚动发布：新版本分批替换旧版本，旧实例逐步退出，新实例逐步加入，期间新旧地址并存。
  • 容器重新调度：容器被重启或漂移到其他节点后，往往拿到新的 IP，旧 IP 不再代表原来的服务。

这些变化大多是正常运维动作，不是事故。问题在于，如果调用方没有及时感知，正常运维也会表现成故障。一个成熟的系统，不应该要求“地址永远不变”，而应该假设“地址一定会变”，并为此设计更新路径。

写死 IP 或配置文件的问题

把地址写死在代码或静态配置里，短期看很省事，长期却处处受限：

  • 运维动作被放大：每次扩缩容都要改配置、重启或重新发布，本来几分钟能完成的事情变成一次发布。
  • 配置容易漂移：不同环境、不同实例之间的配置不一致，排查问题时很难判断“到底是代码问题还是配置问题”。
  • 无法表达集合：只能手工维护列表，容易漏改、错改，实例多了之后几乎不可维护。
  • 恢复速度受限：故障迁移时，人工更新永远慢于自动调度，恢复时间被拉长。
  • 环境耦合：同一份代码在不同环境需要不同地址，配置管理复杂度上升。

更合理的做法是把“服务名”作为稳定契约，把“地址列表”作为运行时数据，由服务发现机制负责把前者解析成后者。这样，扩缩容和调度对业务代码透明，运维动作也不需要以发布为代价。

陈旧地址的后果

调用方拿到陈旧地址后，后果通常不是“一次请求失败”这么简单：

  • 连接失败：目标实例已下线，连接被拒绝，请求直接失败。
  • 超时放大：地址不可达时，连接或请求可能先经历一段超时等待，延迟被拉长；如果再加上重试，放大效应更明显。
  • 流量打到已下线或未就绪实例：即使连接能建立，实例也可能正在退出或尚未完成初始化，请求被静默丢弃或返回错误。
  • 掩盖真实容量：新扩容的实例分不到流量，监控上看起来“扩容没效果”，实际是地址没传播过去。
  • 故障定位困难：错误表现为零散的超时或连接拒绝，容易让人怀疑网络或下游业务，而不是地址视图。

四个必须应对的难点

节点摘要指出，客户端必须应对缓存、过期、空列表与更新竞态。这四件事各有一句话的经验：

  • 缓存：缓存能避免每次调用都去解析地址，降低解析压力和延迟，但缓存本身就是“旧数据”的来源，必须明确它何时可信、何时必须刷新。
  • 过期：没有过期机制的缓存会永久停留在某个历史快照上，TTL 或重新解析策略决定了调用方能多快看到变化。
  • 空列表：解析结果可能为空，此时必须有明确的失败语义或受控降级路径，而不是让空指针或异常穿透到业务层。
  • 更新竞态：地址更新与正在进行的请求、正在建立的连接、正在回收的对象之间会产生竞态，处理不当会误杀健康连接或漏掉新端点。

服务发现不是“接一个注册中心就完事”，而是围绕这四点在调用方建立一套稳定的地址生命周期管理。注册中心只负责“记录和传播”，真正决定系统表现的，是调用方如何消费这些变化。

一个教学假设：三个典型时刻

为了把“为什么”落到具体动作上，可以设想三个教学假设的时刻：

  • 扩容时刻：新实例已经注册，但调用方地址视图还是旧的。此时正确动作是尽快刷新并让新端点参与负载均衡，而不是继续按旧列表分配。
  • 下线时刻：实例准备退出，调用方还持有它的连接。此时正确动作是停止向它发送新请求，并给在途请求留出完成时间，而不是立刻粗暴关闭。
  • 恢复时刻：实例故障后重新可用，地址重新出现。此时正确动作是逐步纳入流量并观察健康度，而不是一次性把所有压力打上去。

这三个时刻分别对应“更新传播”“优雅摘除”“受控恢复”，也是本课后续实验要观察的重点。它们共同说明：服务发现的难点不在“拿到地址”，而在“地址变化时，调用方做什么”。

与连接池、负载均衡的关系

服务发现不是孤立的一层。它向上给负载均衡提供可选的端点集合，向下依赖注册中心或 DNS 等解析来源；连接池则在这些端点之上维护连接。三者职责可以粗略地概括为：

  • 服务发现：这份地址列表现在是什么？变化了吗？
  • 负载均衡：这次请求应该发给列表里的哪一个？
  • 连接池：到这个端点的连接是复用还是新建？什么时候回收？

任何一层把“地址”当成永恒不变的常量，都会在地址变化时出问题。反过来，只有三层都对“地址会变”有明确假设，系统才能在扩缩容和故障中保持稳定。

从一次排障说起

假设监控显示某个下游服务错误率上升，但下游自身的 CPU、内存、业务指标都正常。一个常见的方向是检查调用方的地址视图：是不是还有实例已经下线却仍在列表里？是不是新实例已经上线但调用方从未刷新？是不是解析结果一度为空，而调用方没有明确处理？沿着“地址从哪来、多久没更新、空了怎么办”去排查，往往比盲目怀疑下游业务更快接近真相。

三个常见误解

  • “注册成功就等于可以接流量”：注册只说明实例把自身信息写入了某个目录，不代表依赖已就绪、端口已可服务。注册与就绪是两件事。
  • “有缓存就等于有服务发现”：缓存只是快照。没有更新与过期策略，缓存越久，距离真实状态越远。
  • “地址变了就重建一切”：重建看似彻底，实际会误伤正在使用的对象，造成不必要的抖动；更新应当是增量的、可回退的。

厘清这些误解，有助于在设计和排障时把注意力放在“地址视图是否新鲜、更新是否安全”上，而不是停留在“注册中心有没有数据”。

为什么在内容后台场景里更明显

以教学假设的图文发布链路为例：发布服务调用存储服务写入素材和正文，存储服务在活动期间扩缩容，发布服务则可能同时有多个实例在跑。只要有一个调用方实例的地址视图落后，就可能出现“部分发布成功、部分超时”的不一致现象，排查时又因为请求分散在不同实例上而难以复现。

这类场景的共同点是：调用链不长，但每个环节都可能是多实例；流量有峰谷，运维动作频繁；一次请求往往包含多次下游调用，任何一次打到陈旧地址都会拖长整体延迟。服务发现做得好不好，直接体现在这些日常链路的稳定性上。

把判断力落到日常

在设计和评审中，可以用下面几个问题快速检验：

  • 这个服务名解析出来的地址，多久会更新一次？更新失败时会发生什么？
  • 地址列表为空时，调用方是明确失败、快速返回，还是进入不可控的重试？
  • 实例下线时，是否有机制停止新请求并等待在途请求结束？
  • 地址更新时，是否会误伤仍在使用中的连接或请求对象？
  • 监控能否区分“解析失败”“连接失败”“业务失败”，而不是笼统记成下游错误？

如果这些问题回答不清，服务发现就还停留在“接入了注册中心”的阶段，而不是“能在地址变化中保持稳定”的阶段。

本课的边界

本课聚焦调用方如何消费地址变化，不展开注册中心的存储模型、选主机制或具体产品的运维细节；这些内容需要结合你所读文档的对应版本来核对。实验也只使用本地服务目录模拟端点变化，目的是观察旧连接处理与恢复，而不是复刻某个生产系统。

带着这些边界读后面的内容，可以把注意力放在机制和判断上：地址为什么变、调用方如何知道、知道之后如何安全地更新。

核心概念

服务发现的核心不是“拿到一次地址”，而是让调用方在地址变化时仍能做出正确决策：地址从哪里来、缓存多久、更新如何排序、空列表意味着什么、旧连接何时可以关闭。

服务发现要解决的问题可以写成一条映射：

逻辑服务名 storage.internal  ->  [10.0.0.11:50051, 10.0.0.12:50051, ...]

教学假设：图文发布服务需要调用存储服务。发布实例从 3 个扩到 6 个、滚动重启替换 IP、某台机器故障时，调用方不能继续把请求发往旧地址。服务发现负责把“稳定的逻辑名”翻译成“当前可用的端点列表”，并把这个列表的变化传递给调用方。

“端点”在本课只指可连接的地址，例如 host:port。注册中心里可能还有权重、机房、版本等信息，但本课不假设某个系统的具体字段；需要时应以所读文档版本为准。

1. 客户端与代理发现

客户端发现

客户端自己完成两件事：向注册中心或命名服务查询实例列表；在列表上执行负载均衡、重试、熔断等策略。gRPC 的公开模型是：客户端用 name resolver 把目标 URI 解析成地址列表，再交给 load balancing policy；resolver 产生地址更新后，由 LB 策略管理子连接。内置 dns resolver，也可以按 scheme 注册自定义 resolver。以上细节以所读 grpc.io Custom Name Resolution 文档版本为准。

目标 URI 的例子：

dns:///storage.internal:50051      # 使用内置 DNS resolver
myreg:///storage.internal          # 自定义 scheme，需注册对应 resolver

注意 dns:/// 里的三个斜杠：dns:// 后面本应是 authority（例如指定 DNS 服务器），这里为空表示用默认配置，第三个斜杠之后才是要解析的 host:port；不同 resolver 对 URI 的解析规则可能不同，以文档和实现为准。

代理发现

客户端只连接一个相对固定的入口：四层/七层负载均衡器、API 网关或 sidecar。代理持有注册中心连接，查询实例列表并转发请求。客户端不知道真实实例地址，扩缩容对客户端透明。

教学假设：发布服务配置 storage.internal:50051 指向集群内代理；存储服务从 3 个实例扩到 6 个时，发布服务不需要改配置，代理更新后端池即可。这只是通用后台的讲解场景，不代表任何公司的实际架构。

DNS 方式

DNS 也可以承担“逻辑名 -> 地址”的基础发现：客户端解析 A/AAAA 记录，按 DNS TTL 缓存。它简单、语言无关，但通常只提供地址集合，不提供业务就绪状态、权重和快速摘除语义；是否使用 SRV、如何做健康检查，取决于具体系统，以所读文档版本为准。

对照表：

维度 客户端发现 代理发现 纯 DNS
额外网络跳数 0 1（到代理） 0（解析后直连）
典型新增延迟 解析与缓存开销，通常很小 多一跳转发（量级需在自己环境实测） 首次解析有延迟，命中缓存后很小
治理逻辑位置 每个客户端进程 代理/网关集中 很薄，主要靠 DNS 与客户端
多语言升级成本 高，每种语言都要接 resolver/LB 低，升级代理即可 低，但能力有限
故障面 注册中心、resolver、LB 策略都在客户端侧 代理成为关键路径 DNS 故障或缓存过期影响大
地址变化生效 resolver 推送/重解析后立即或很快 代理更新后端池 受 TTL 与各级缓存约束

权衡可以引用节点原文：「客户端发现减少代理跳数，但分散了治理逻辑与升级成本。」因此，实例规模大、语言栈统一、追求低延迟时客户端发现更合适；多语言、希望集中治理时代理发现更常见。两者也可以组合：客户端 resolver 找到代理，代理再做后端发现。

在 Linux 上观察解析

getent hosts storage.internal
dig storage.internal A +noall +answer
dig storage.internal A +noall +answer | awk '{print $2, $1}'  # TTL 与地址

getent hosts 走系统 NSS，可能命中 /etc/hosts、systemd-resolved 或其他缓存；dig 直接问 DNS，答案行第二列是 TTL。两者结果不一致时，先分清是 DNS 记录变了，还是系统/应用缓存还没过期。教学示例：把 TTL 设为 5 秒便于实验观察，生产环境要结合故障切换速度与查询压力设定，不能照搬。

2. watch、TTL和缓存

客户端拿到地址后，还要决定“什么时候重新拿”。常见两类机制：

方式 典型做法 优点 代价
轮询 / TTL 每隔 N 秒查询，或缓存到期后重新解析 实现简单，服务端压力可预测 更新有延迟；空窗期可能继续用旧地址
watch / 订阅 长轮询或流式订阅，服务端在变更时推送 生效快，减少无效查询 连接管理、断线重连、事件乱序更复杂

具体是长轮询、HTTP streaming 还是双向流，要看所用注册中心/命名服务文档；本课只讨论语义，不假设某个产品的 API。

为什么客户端必须有本地缓存

注册中心不是永远可用的。网络分区、发布升级、限流都可能让查询失败。若客户端每次请求都同步查注册中心，注册中心就会进入请求关键路径，故障时整个调用链一起失败。更稳妥的做法是：内存里保留最后已知的端点列表，查询/订阅失败时继续使用，同时标记“陈旧”，并按策略限制陈旧时间。

缓存要回答三个问题：

  1. 这份列表对应哪个版本，是否比当前版本旧？
  2. 最后一次成功更新时间是什么，已经陈旧多久？
  3. 列表为空时，是“服务真的没有实例”，还是“查询失败/数据还没同步”？

TTL 过短与过长

教学示例：实例列表 10 秒变化一次。TTL 设为 1 秒，客户端大约 1 秒内能看到变化，但 1000 个客户端就是约 1000 QPS 的查询压力；TTL 设为 60 秒，查询压力降到约 17 QPS，但故障实例可能被继续调用近 1 分钟。真实取值要结合变更频率、可接受的陈旧窗口和注册中心容量，不能只看其中一个数字。

DNS 还有多层缓存：应用自己的 resolver 缓存、连接池里已经建立的连接、操作系统/NSS 缓存、JVM 等运行时的 DNS 缓存（具体属性、默认值和是否缓存失败结果，以所用版本文档为准）。因此“改完 DNS 记录”不等于“所有客户端立刻使用新地址”。排查时要逐层确认，而不是只重复 dig。

更新竞态与空列表

watch 连接可能重连，事件可能重复、延迟或乱序到达。一个实用规则是让每次更新携带单调递增的版本号/修订号：只接受 version > current_version 的更新，旧版本直接丢弃。没有版本号时，至少要用“生成序号 + 来源”避免旧响应覆盖新响应；不要用到达顺序猜测新旧。

空列表尤其危险。注册中心返回空，可能是实例确实全部下线，也可能是注册中心故障后返回了默认空值。两种策略都可以接受，但必须明确：

  • 受控降级：保留最后非空列表，并记录 degraded=True 与陈旧时长；超过最大陈旧窗口后仍然失败，避免无限期调用早已不存在的地址。
  • 明确失败：立即清空并返回 UNAVAILABLE，让上层快速失败或走降级逻辑，而不是把请求发到空集合。

这正对应验收中的「空端点时明确失败或受控降级」。最糟糕的是“空列表被当成没有更新”，既不失败也不告警。

        self._endpoints: tuple[str, ...] = ()

    def publish(self, endpoints, version=None) -> Update:
        if version is None:
            self._version += 1
        else:
            self._version = version
        self._endpoints = tuple(endpoints)
        return Update(self._version, self._endpoints)

        self.endpoints: tuple[str, ...] = ()
        self.degraded = False

    def apply(self, update: Update) -> tuple[str, ...]:
        if update.version <= self.version:
            return self.endpoints
        self.version = update.version
        if update.endpoints:
            self.endpoints = update.endpoints
            self.degraded = False
            return self.endpoints
        if self.on_empty == "keep_last_good" and self.endpoints:
            self.degraded = True
            return self.endpoints
        self.endpoints = ()
        raise RuntimeError("UNAVAILABLE: resolver returned no endpoints")

cache = ResolverCache("keep_last_good")
print(cache.apply(directory.publish(["10.0.0.11:50051"])))
print(cache.apply(directory.publish([])))
print("degraded:", cache.degraded)

try:
    ResolverCache("fail").apply(Update(1, ()))
except RuntimeError as exc:
    print(exc)

3. 健康、摘除与恢复

节点给出的注意事项是：「注册成功不代表实例业务已经准备就绪。」进程已经监听端口，并不等于配置加载完成、缓存预热完成、下游连接可用。教学假设：存储服务启动后要加载索引、连接对象存储和数据库；若注册后立刻接收图文发布请求，前几秒可能大量超时，调用方还会把这段失败计入健康统计。

因此要把“活着”和“能接业务流量”分开：

检查 回答的问题 失败后的常见动作
liveness 进程是否还活着、是否死锁 重启进程
readiness 现在是否能安全接收业务流量 从端点列表摘除，不重启
startup/warmup 初始化是否完成 暂不接流量，完成后转为 ready

具体探针名称、默认阈值和字段语义，K8s 等平台各不相同，以所读文档版本为准。关键原则是：下游故障通常不应触发 liveness 重启，否则会把“依赖挂了”放大成“自己也不断重启”。

健康检查分主动和被动。主动检查可以是应用层 HTTP 接口、RPC 探针或 TCP 连接；TCP 能连上只说明端口在监听，不能证明业务能查数据库。被动检查则统计超时、连接失败、5xx，连续 N 次失败后摘除。教学示例可用“10 秒窗口内连续 3 次失败”说明，但生产参数必须按错误率和流量调，不能把示例当默认值。

摘除实例要优雅下线，顺序通常是：

  1. 先把实例标记为 not ready，或从注册中心注销；
  2. 等待目录/watch 传播，给客户端留出更新窗口；
  3. 停止接收新请求，继续处理在途请求；
  4. 在途请求完成或到达 drain 截止时间后关闭连接池；
  5. 进程退出。

教学示例：把 drain 上限设为 30 秒，并让传播等待覆盖至少一个 TTL/watch 周期；具体秒数取决于系统。顺序反过来——先关进程再摘除——客户端会在一段时间内继续把请求发到已经死掉的地址。

客户端侧同样要遵守验收中的「更新不销毁正在使用的对象」。收到新列表时，不要原地清空旧连接；应先用新地址构建新的子连接集合，再原子替换快照。旧端点标记为 closing，正在使用它的请求通过引用计数持有；最后一个请求 release 后才真正关闭。这样发布滚动重启时，旧连接上的在途请求不会被“更新”打断。

from dataclasses import dataclass, field
import threading


@dataclass
class Endpoint:
    addr: str
    refs: int = 0
    closing: bool = False
    closed: bool = False
    lock: threading.Lock = field(default_factory=threading.Lock)

    def acquire(self) -> bool:
        with self.lock:
            if self.closing or self.closed:
                return False
            self.refs += 1
            return True

    def release(self) -> None:
        with self.lock:
            self.refs -= 1
            if self.closing and self.refs == 0:
                self._close_if_idle()

    def close_when_idle(self) -> None:
        with self.lock:
            self.closing = True
            self._close_if_idle()

    def _close_if_idle(self) -> None:
        if self.closing and self.refs == 0 and not self.closed:
            self.closed = True
            print(f"close {self.addr}")


class EndpointSnapshot:
    def __init__(self, addrs):
        self._lock = threading.Lock()
        self._current = tuple(Endpoint(a) for a in addrs)

    def current(self):
        with self._lock:
            return self._current

    def replace(self, addrs):
        fresh = tuple(Endpoint(a) for a in addrs)
        with self._lock:
            old, self._current = self._current, fresh
        for endpoint in old:
            endpoint.close_when_idle()
        return fresh


snapshot = EndpointSnapshot(["10.0.0.11:50051"])
in_flight = snapshot.current()[0]
assert in_flight.acquire()
new_endpoints = snapshot.replace(["10.0.0.12:50051"])
print("new:", [e.addr for e in new_endpoints])
in_flight.release()

恢复阶段：实例重新 ready 后再加入目录。判定不能只看“进程启动了”，还要看业务探针连续成功、关键下游可用、预热任务完成。教学示例可以要求连续 3 次成功、观察 10 秒，但阈值要按服务特性设定。

恢复不是简单地把地址加回去，至少要确认：

  • readiness 连续成功（教学示例为 3 次）；
  • 关键下游连接可用，预热任务已完成；
  • 缓存命中率达到阈值；
  • 最近一个观察窗口内错误率和延迟在预算内。

摘除也要防抖：短时网络抖动不应立刻永久删除实例，可以结合连续失败次数和恢复观察期；但抖动窗口不能长到让故障实例持续接收流量，具体参数以所用系统文档为准。

如果代理/LB 支持慢启动，可让权重从 1 -> 5 -> 10 逐步增加（教学示例，是否支持以版本为准），避免冷缓存实例瞬间被打满。没有慢启动时，至少观察新实例的错误率和延迟，再决定是否扩大流量。摘除不是永久删除，恢复也不等于立刻全量。

一个滚动重启的教学时序：

  • t=0：A/B/C 三个实例都 ready；
  • t=0：A 标记 not ready，目录开始传播；
  • t=5：A 停止新请求，进入 drain，上限 30 秒；
  • t=35：A 退出，启动 A' 并做 warmup；
  • t=50：A' 探针连续成功，重新加入目录；
  • t=60：按同样步骤处理 B、C。

这些秒数只是示例，真实发布系统可能有不同的并发度和等待策略；但“先摘除、再 drain、最后关闭，恢复后重新加入”的顺序不变。

收束：客户端/代理发现决定地址从哪里来，watch/TTL/缓存决定地址变化何时生效，健康与优雅摘除决定变化过程中谁可以接流量、旧对象何时关闭。三者合在一起，才能在扩缩容和滚动重启时既不调用陈旧地址，也不打断在途请求。

本部分聚焦两个问题：服务发现落地时最常见的错误是什么，以及如何在练习中观察地址变化对连接和请求的影响。下面的图文发布服务调用存储服务、实例扩缩容、发布滚动重启等场景均为教学假设，用于说明通用后台问题；不涉及任何特定公司的内部实现。

常见误区与设计权衡

服务发现的难点通常不在“拿到地址”，而在“地址变化时系统仍然可控”。下表把常见误区放在一起对照。

误区 典型表现 可能后果 改进方向

需要强调：注册中心里的“已注册”只是控制面状态，不等于数据面已经可用。尤其是滚动重启、依赖初始化、线程池预热等阶段，地址可达与业务就绪之间可能存在时间差。

与 gRPC 名称解析的核对点

以下只列公开文档中的通用要点，具体 API、默认值和边界行为以所读文档版本为准：

  • gRPC 客户端使用 name resolver 把目标 URI（例如 dns:///host:port）解析为地址列表，再交给负载均衡策略。
  • gRPC 内置 dns resolver，也可以按 scheme 注册自定义 resolver。
  • resolver 产生地址更新后，由负载均衡策略管理子连接。
  • resolver 可以返回错误或空地址列表，客户端需要定义这两种情况的处理方式。
  • DNS 解析结果存在缓存与重新解析行为，缓存时长和刷新时机以所读文档版本为准。

这些要点与本课的练习一一对应：目录相当于自定义 resolver 的数据源，版本号相当于更新序号，客户端快照相当于 resolver 产出的地址列表，旧连接释放则对应负载均衡策略下的子连接管理。

class Resolver:
    def apply(self, version, addrs):
        with self.lock:
            if version == self.version: return        # 没变化
            if version < self.version:                # 乱序到达的旧版本
                log(f"stale_update ignored version={version} current={self.version}"); return
            if not addrs and self.policy == "keep" and self.snapshot:
                if not self.degraded: log(f"empty endpoints degraded=1 keep_last={len(self.snapshot)}")
                self.degraded = True; self.version = version; return
            self.degraded = False
            # 复用仍在列表里的 Endpoint 对象，只为新地址创建
            new = {a: self.eps.get(a) or Endpoint(a) for a in addrs}
            removed = [e for a, e in self.eps.items() if a not in new]
            self.eps = new; self.snapshot = tuple(new.values()); self.version = version
        log(f"update version={version} endpoints={','.join(addrs) or '-'}")
        for e in removed: e.retire()   # 只标记 closing；在途计数归零时才真正关闭

    def pick(self):
        snap = self.snapshot                          # 读一次不可变元组，无需加锁
        if not snap: raise RuntimeError("UNAVAILABLE: no endpoints")   # fail 策略落到这里
        for _ in range(len(snap)):
            e = snap[next(self.rr) % len(snap)]
            s = e.acquire() if not e.closing else None   # acquire 内 inflight += 1
            if s: return e, s
        raise RuntimeError("UNAVAILABLE: all endpoints retiring")

Endpoint.retire() 把 closing 置真并记录当时的在途数；release() 每次把 inflight 减 1，减到 0 且 closing 时关闭池里所有连接并打印 closed_after_inflight=N。注意两点：一是 fail 策略下空列表会真正清空快照，pick 抛出 UNAVAILABLE，真实系统应映射成协议约定的错误码；二是 keep 策略下版本号仍然前进，这样恢复时的新版本不会被误判为旧版本。

自测题

1. 注册成功后立即收到流量，前几秒大量超时

题干： 一个新实例进程启动后马上向注册中心注册，注册接口返回成功，流量随即被分配过来，但前几秒出现大量超时。请说明最可能的原因和修正办法。

答案： 最可能的原因是“注册成功”只证明注册中心接受了记录，不等于实例已经具备处理业务的能力。此时进程可能还在加载配置、建立数据库或存储连接、预热缓存、初始化线程池，监听端口也可能尚未完全就绪。修正方式是把“可注册”与“可服务”分开：先完成监听、依赖连接、配置加载和必要的预热，再通过 readiness 检查；只有 readiness 通过的实例才进入可发现地址集合。liveness 与 readiness 不要混用，避免进程还活着却被误判为可接流量。客户端侧仍应保留超时、重试和熔断作为兜底。

解析： 这正对应本课 pitfalls：“注册成功不代表实例业务已经准备就绪。”注册中心负责记录和分发地址，不负责证明业务就绪；服务端要把 readiness 作为发布门槛，客户端要把超时与重试作为保护，而不是把注册成功当成健康证明。

2. 注册中心短暂故障返回空列表，客户端应如何处理

题干： 注册中心短暂故障时返回了空地址列表，客户端是否应该把它当成“当前没有实例”并立刻清空本地缓存？请给出两种策略及各自适用场景。

答案： 不应把空列表直接当成成功结果，也不应无条件永久沿用旧地址。应区分“解析出错”和“确实没有可用实例”，并明确选择以下一种策略：

  • 明确失败： 停止向该服务发起新请求，返回清晰的错误并记录原因，例如让上游看到“服务发现暂不可用”。适用于对正确性要求高、不能安全使用陈旧端点的操作，例如关键写入或必须确认当前实例集合的场景。
  • 受控降级： 在限定窗口内使用 last-known-good 地址或预置的静态种子，同时标记为降级、限制流量、设置最大陈旧时间并告警；窗口到期仍无有效地址则转为明确失败。适用于可容忍短暂陈旧、可用性优先的读路径或非关键操作。

无论选哪种，都要避免“空列表等于一切正常”的静默成功，也要避免无限期使用旧地址。策略应可配置、可观测，并有明确的恢复条件。

解析： 本题对应验收项“空端点时明确失败或受控降级”。空端点是一个需要被解释的信号，不是普通的成功响应；两种策略没有绝对优劣，关键是按业务正确性、可用性目标和可接受的陈旧上限来选择，并把行为写进代码与运行手册。

3. 收到新地址列表后直接关闭所有旧连接再建新连接

题干： 客户端收到新的地址列表后，立即 close 所有旧连接，再建立新连接。会出什么问题？怎样实现“更新不销毁正在使用的对象”？地址更新乱序到达时又该如何防护？

答案： 直接关闭旧连接会让正在处理的请求失败，造成瞬时错误和延迟抖动；大量连接同时重建还可能形成连接风暴，丢失原有的负载均衡状态。更稳妥的做法是：先解析并建立新连接，完成健康检查后把新端点加入可用集合；流量逐步切换；旧连接继续服务，直到引用计数归零再延迟关闭，并配合优雅摘除与排空。这样“更新”只改变目录和选择结果，不会销毁仍被请求持有的连接对象。

对于乱序更新，给每次目录变更分配单调递增的版本号或 epoch，应用时只接受比当前更新的版本；旧版本直接忽略。把更新处理串行化到单一入口，必要时合并短时间内的重复更新，并保证应用操作幂等。这样即使旧更新后到，也不会覆盖新地址集合。gRPC 内部如何传递更新、LB 策略如何管理子连接，以所读文档版本为准；引用计数延迟关闭是本课扩展。

解析： 本题对应验收项“更新不销毁正在使用的对象”。判断标准不是“新列表已经生效”，而是“切换过程中在途请求仍能完成，旧对象在无人引用后才释放”。版本号与单入口串行化解决顺序问题，引用计数与延迟关闭解决生命周期问题，两者缺一不可。

本课小结

  • 服务发现把逻辑服务映射为动态端点；端点会因扩缩容、发布滚动重启和故障而变化。客户端必须显式处理缓存、过期、空列表与更新竞态，避免继续调用陈旧地址。
  • 客户端发现与代理发现是两种职责放置方式。前者减少代理跳数，但把治理逻辑和升级成本分散到各个客户端；后者把治理集中到代理，但增加一跳与代理自身的可用性要求。
  • watch、TTL 和缓存共同决定“多久能看到变化”和“旧地址还能用多久”。要定义刷新触发、最大陈旧时间和失败时的保留策略；DNS 缓存与重新解析行为以所读文档版本为准，TTL 细节不要跨版本臆断。
  • 健康、摘除与恢复要区分“已注册”和“已就绪”：注册成功不代表实例业务已经准备就绪。实例应先通过 readiness 再接收流量，摘除时优雅排空，恢复时避免抖动与惊群。
  • 空端点必须按验收项处理：要么明确失败，要么受控降级。不能把空列表静默当成成功，也不能无限期沿用旧地址；降级要有时间上限、可观测信号和恢复条件。
  • 收到更新时，先建立并验证新端点，再切换流量，旧对象通过引用计数延迟关闭，确保“更新不销毁正在使用的对象”。乱序更新用单调版本号或 epoch 加单入口串行化来防护。
  • 本课的取舍是：客户端发现减少代理跳数，但分散了治理逻辑与升级成本。选择方案时要结合团队边界、故障隔离、发布节奏和可观测性，而不是只看一次调用的延迟。
  • 边界：公开资料只用于核对客户端 name resolution 的语义和示例，不能推断任何企业内部实现；框架行为、版本号、空列表策略和连接关闭细节均应以所读文档版本和本课实验为准。
