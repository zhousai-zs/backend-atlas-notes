第 17/208 课：类型、表达式与控制流

节点：b-syntax · 域：B · 子类：语法与类型 · 难度：入门 · 前置：a-compile、a-binary

一句话：C++ 程序由具备类型的对象和表达式组成，控制流决定语句执行顺序；隐式转换、整数提升及未初始化对象会影响结果，不能仅依赖表面语法。

1. 学习目标与为什么后端要懂

1.1 学习目标

完成本课后，你应该能够：

  1. 解释初始化与类型转换：说清默认初始化、值初始化、零初始化的差别；识别隐式转换、整数提升与窄化（narrowing），并能用 static_cast 或显式类型消除编译警告。
  2. 熟练使用分支、循环和函数：用 if / switch / for / while 表达清晰控制流，把校验与运算拆成可读的函数。
  3. 掌握作用域、const 与输入校验：知道局部变量的生命周期；对不应修改的对象加 const；对命令行 / 网络输入做个数、格式、范围校验。
  4. 独立完成节点实践：实现带参数校验的命令行计算器，并开启常用编译警告（-Wall -Wextra -Wpedantic -Wconversion -Wshadow -Werror）。
  5. 在微信公众号后台场景里，能把「回调 XML/JSON 字段解析、配置项数值转换、限流计数」写成边界明确、可编译且警告干净的基础逻辑，而不是「凑合能跑」。

1.2 验收标准

节点给出的验收标准有两条，本课会反复回扣：

  • 能修复窄化转换警告。 例如把 double 赋给 int、把更大整数塞进更小类型时，-Wconversion / -Wnarrowing 会报警；要用显式 static_cast 或改用合适类型，并确认语义可接受（截断是否故意）。
  • 能说明局部变量未初始化的风险。 节点 pitfalls：变量定义并不总会进行零初始化。 栈上的 int x; 在多数情况下是未初始化，读取它是未定义行为（UB）；调试时可能「碰巧是 0」，上线优化后变成随机值或被优化掉。

1.3 为什么微信公众号后台要懂类型与控制流

节点对「为什么」写得很干脆：写出可编译且边界明确的基础功能。 放到即将入职的腾讯微信公众号后台：

  • 回调与消息解析。 微信推送的 XML/JSON 里字段是字符串；转成 int64_t 时间戳、枚举状态码时，必须校验格式与范围，否则一次脏数据就能让服务进程走进未定义行为或错误分支。
  • 配置与限流计数。 QPS 阈值、重试次数、超时毫秒——类型选错（int vs int64_t）或隐式窄化，会在高峰流量下悄悄溢出。
  • 错误路径要明确。 「参数不够 / 非法运算符 / 除零」必须提前返回并给出可读错误，而不是算出一个垃圾结果再往后传——这与后台网关的参数校验习惯一致。
  • 编译警告即契约。 打开 -Werror 把警告当错误，能在 CI 阶段拦住窄化、遮蔽变量、未使用结果等问题，比线上用核心 dump 便宜得多。

所以本课要建立的肌肉是：类型表达意图；初始化不留灰区；控制流先校验再计算；用编译器警告当免费的代码审查。

2. 从直觉到原理：三个核心要点

2.1 初始化与类型转换

直觉：盒子里有没有东西，以及能不能换个更小的盒子

  • 对象有类型：int、double、std::string 决定能存什么、占多少内存、允许哪些运算。
  • 初始化 ≠ 定义：写了 int x; 只是「声明并定义了一个对象」，不保证里面是 0。
  • 转换有代价：double → int 会丢小数；long long → int 可能截断高位——这叫窄化，编译器在列表初始化或开启 -Wconversion 时会提醒你。

原理：几种初始化与常见转换

写法 常见含义（简化）
int x;（块作用域） 默认初始化 → 未初始化（不确定值）
int x{}; / int x = 0; 值初始化 / 显式赋值 → 确定为 0
int x = 3.9; 隐式转换，截断为 3；可能有警告
int x{3.9}; 列表初始化，窄化在 C++11+ 非法
static_cast<int>(3.9) 显式承认「我知道会截断」

整数提升：较小整数类型参与运算时，常先提升为 int，再算结果。表面「两个 short 相加」实际按 int 规则走——不能只看字面语法。

#include <iostream>

int main() {
    int a{};                 // 明确为 0
    double b = 3.7;
    // int c = b;            // 隐式窄化，-Wconversion 可能报警
    int c = static_cast<int>(b);  // 显式：接受截断 → 3
    std::cout << a << ' ' << c << '\n';
}

例子：公众号配置里的超时毫秒

配置文件读出 "1500.5"（误写成小数）。若直接 int timeout = std::stod(s); 可能触发转换警告，且静默丢掉 0.5。更好的做法：先解析为 double 或校验「必须是整数形式」，再 static_cast 到目标类型，并记录日志。

2.2 分支、循环和函数

直觉：先问「能不能算」，再问「怎么算」

命令行计算器 ./calc 3 + 4 的控制流应是：

  1. 参数个数对不对？
  2. 左右操作数是不是合法数字？
  3. 运算符是否在 + - * / 集合内？
  4. 若是除法，除数是否为 0？
  5. 以上都通过 → 计算并输出。

每一步失败都早返回，避免把错误状态带进后续逻辑。

原理：结构化控制流

  • 分支：if / else if / else 表达互斥路径；运算符集合小时也可用 if 链或查表。
  • 循环：校验字符串「是否为数字」时遍历每个字符；注意边界（空串、只有符号、多个小数点）。
  • 函数：把「打印用法」「判断是否数字」抽成函数，主流程只剩编排——可读性与单测都更好。
bool is_number(const std::string& s) {
    if (s.empty()) return false;
    std::size_t i = 0;
    if (s[0] == '+' || s[0] == '-') {
        if (s.size() == 1) return false;
        i = 1;
    }
    bool seen_digit = false;
    bool seen_dot = false;
    for (; i < s.size(); ++i) {
        unsigned char ch = static_cast<unsigned char>(s[i]);
        if (std::isdigit(ch)) { seen_digit = true; continue; }
        if (ch == '.' && !seen_dot) { seen_dot = true; continue; }
        return false;
    }
    return seen_digit;
}

注意这里对 s[i] 使用 static_cast<unsigned char> 再交给 std::isdigit——避免 char 为负时的未定义行为，同时演示「显式转换消除警告/隐患」。

2.3 作用域、const 与输入校验

直觉：谁看得见、谁能改、外来的都不信任

  • 作用域：在 { } 里定义的局部变量，离开作用域即销毁；不要返回指向局部变量的指针/引用。
  • const：const std::string op = argv[2]; 表明后续不应改运算符字符串，接口意图更清晰。
  • 输入校验：argc、字符串格式、除零——全部视为不可信输入，与处理 HTTP 查询参数同一原则。

原理：生命周期与常量正确性

int main(int argc, char* argv[]) {
    if (argc != 4) {
        // 错误路径：不进入后续未初始化的结果变量
        return 1;
    }
    const std::string left(argv[1]);
    const std::string op(argv[2]);
    const std::string right(argv[3]);
    // ... 校验后再定义并初始化 result
    double result = 0.0;  // 定义即初始化
    // ...
}

公众号后台类比：解析 MsgType、Event 时，先确认字段存在且枚举合法，再进入业务分支；const 保护「已校验快照」不被后续代码改写。

3. 常见误区与设计权衡

3.1 误区：变量定义并不总会进行零初始化

节点 pitfalls：变量定义并不总会进行零初始化。

int maybe_bad(bool use) {
    int x;          // 未初始化
    if (use) x = 42;
    return x;       // use==false 时读取 UB
}

int good(bool use) {
    int x = 0;      // 显式初始化
    if (use) x = 42;
    return x;
}
  • 全局 / 静态存储期对象会零初始化；块作用域内置类型默认初始化后值不确定。
  • -Wuninitialized（常配合 -O1）能抓住不少路径；但不要依赖「编译器一定报」——习惯上定义即初始化。
  • 实践目录中的 uninit_demo.cpp 用注释对比这两条路径，供对照学习。

3.2 权衡：显式类型 vs auto

节点 tradeoffs：显式类型利于接口清晰，auto适合避免重复表达类型。

显式类型 auto
接口 / 头文件 读者一眼看到契约 可能要跳到右边初始化表达式
长迭代器类型 啰嗦 auto it = m.find(k); 很合适
窄化风险 写 int x = expr; 时类型意图清楚，但仍可能隐式转 auto x = expr; 跟随右侧，有时反而避免无意窄化
建议 函数参数、返回值、成员优先显式 局部、类型显而易见或极其冗长时用 auto

后端代码评审里常见约定：对外 API 显式，函数内部可 auto——与节点权衡一致。

5. 自测题（附答案）

Q1. 为什么 int x; 在函数里通常不能当成「x 已经是 0」？节点 pitfalls 想强调什么？

答案 块作用域的内置类型默认初始化后值是**不确定的**（未初始化），只有静态/线程存储期等对象才会零初始化。读取未初始化局部变量是未定义行为：调试时可能碰巧为 0，优化或换平台后变成随机值甚至被优化删除。节点 pitfalls「变量定义并不总会进行零初始化」强调：**定义即初始化**（如 `int x = 0;` 或 `int x{};`），不要依赖「语言会帮你清零」的错觉。

Q2. 什么是窄化转换？如何在开启 -Wconversion -Werror 时修复相关警告？

答案 窄化指可能丢失信息的转换，例如 `double`→`int`（丢小数）、更大整数→更小整数（截断高位）。修复：改用能容纳语义的类型（如继续用 `double`），或在确认截断可接受时写 `static_cast<目标类型>(表达式)` 表达意图；列表初始化 `int x{3.14};` 在 C++11+ 直接非法，可改为显式转换或改类型。验收要求「能修复窄化转换警告」即指能看懂报警并选择上述之一。

Q3. 节点 tradeoffs 如何看待显式类型与 auto？写命令行计算器的 main 参数与局部运算结果时你会怎么选？

答案 节点 tradeoffs：显式类型利于接口清晰，`auto` 适合避免重复表达类型。`main` 的对外契约（`argc`/`argv`、返回 `int`）保持显式；运算符字符串可用 `const std::string` 显式表明只读；局部若类型冗长可用 `auto`，但像 `result` 这种核心数值更推荐显式 `double result = 0.0;`，既初始化又让读者看见精度选择。

7. 小结

  • 类型与初始化决定对象「是什么、有没有确定值」；局部变量要养成定义即初始化。
  • 隐式转换与整数提升会改变你以为的运算规则；窄化用显式转换或改类型修警告。
  • 控制流先校验再计算；const 与作用域表达「谁能改、活多久」。
  • 显式类型清接口，auto 减重复——按场景取舍。
